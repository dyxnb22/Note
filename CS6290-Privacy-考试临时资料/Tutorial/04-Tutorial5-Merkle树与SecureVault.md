# 第四部分：Tutorial 5 —— Merkle 树与 SecureVault 托管

## 22. Merkle 树

### 22.1 构造和包含证明

叶子：

~~~text
h_i = H(m_i)
~~~

内部节点：

~~~text
h_parent = H(h_left || h_right)
~~~

根为 r。证明第 k 个叶子存在，需要叶子值、每层兄弟哈希和左右方向。验证者从 H(m_k) 开始逐层合并，最后和 r 比较。时间与证明大小都是 O(log n)。

### 22.2 用途

- **篡改证据**：任意叶子变化会改变根；
- **轻客户端**：只下载一条路径而不是完整数据；
- **数据可用性抽样**：随机抽查部分叶子；
- **并行和增量更新**：不同分支可以独立计算。

Ethereum 中常见的根包括 state root、transaction root 和 receipts root。交易树是有序集合承诺；状态树则更像支持动态 key-value lookup/update 的认证字典。

### 22.3 Ethereum MPT 与普通 Merkle tree

普通 Merkle tree 适合固定、有序的列表；Ethereum 的 Merkle Patricia Trie（MPT）支持按账户地址或 storage key 查找，能够证明：

- 某个 key 对应某个值（membership）；
- 某个 key 不存在（non-membership）；
- 状态更新前后根如何变化。

## 23. SecureVault 题的系统设计

### 23.1 冷热钱包分层

题设建议约 97% 资产放在冷端，约 3% 放在热端。冷端可以是地理分散、隔离网络的 M-of-N 多签：只有至少 M 个不同密钥共同批准才能转出。

若内鬼只有一个且 M>1，不能单独转账；但如果攻击者能串通至少 M 个签名者，安全性仍会失败，所以还要做：

- 密钥、人员、地区和团队分离；
- HSM/硬件钱包和离线备份；
- 双人控制和操作审批；
- 防篡改日志、定期审计和密钥轮换。

### 23.2 热钱包的 50,000 tx/day 架构

热端的目标不是把所有资产放在线，而是只保持业务流动性。可组合：

- MPC 或 HSM，避免单台服务器持有完整私钥；
- policy engine：白名单、额度、审批等级；
- 每小时/每日 velocity limit；
- 异常行为检测和 circuit breaker；
- 多个隔离的 sharded hot wallets；
- 批处理、归集和定期 sweep 到冷端。

热钱包比例的简单原则是：

~~~text
hot fraction = L / A
~~~

其中 L 是最大预期日流出量加安全缓冲，A 是总资产。热端应尽量小，但不能小到正常业务频繁阻塞。

### 23.3 20 国监督和 BFT

如果是固定成员的跨国机构，适合 permissioned consortium 或 hybrid 模型。标准 BFT 假设通常要求：

~~~text
n > 3f
~~~

也就是容忍少于三分之一恶意节点。可以用地区委员会先局部签署，再由全球层最终确认，但必须考虑地区相关故障、网络分区、密钥治理和法域冲突。

### 23.4 事故响应

发现异常时先暂停提现或触发 circuit breaker，再隔离系统、撤销 API 凭证、轮换密钥、保全日志。之后：

1. 评估受影响范围和剩余干净资金；
2. 轮换受影响密钥，必要时把干净资金 sweep 到新钱包；
3. 与交易所、取证团队、律师、监管方和保险方协作；
4. 复盘并增加额度、时间锁、分级审批、白名单、监控和演练。
