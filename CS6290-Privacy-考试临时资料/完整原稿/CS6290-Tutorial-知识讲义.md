### 0.1 本文常用符号

- H：密码学哈希函数；输出长度通常记为 κ 位。
- txid：交易的哈希标识。
- UTXO：尚未花费的交易输出。
- Δ：网络消息最大延迟的模型参数。
- q：共识中提交一个决定所需的 quorum（法定人数）。
- n：节点总数；f：攻击者控制的节点数。
- negl(κ)：关于安全参数 κ 的可忽略函数。
- ⊥：不交付、终止或 abort。

### 1. 钱、稀缺性和共识

#### 1.1 钱为什么存在

钱不是物理上天然存在的物体，而是一种由社会共同接受的记账和转移价值的制度。教材强调钱的四个经典功能：

- **交换媒介**：买卖双方不需要互相想要对方手中的物品。
- **计价单位**：商品和债务可以用同一尺度比较。
- **延期支付标准**：未来的债务可以用钱表示。
- **价值储藏**：价值可以从现在转移到未来。

区块链主要关心的是：一份数字资产不能被同一个人同时花两次。数字文件可以无限复制，因此我们必须让全网对“谁拥有哪一份稀缺状态”形成一致看法。

#### 1.2 稀缺性、所有权和共识

在区块链中，一枚“币”不是一个可以复制的文件，而是账本中一个可被当前所有者解锁、且尚未被花费的状态对象。要判断一笔转账是否合法，节点至少要回答：

1. 被引用的资产是否确实存在？
2. 它是否还没有被花费？
3. 发起者是否有权花费它？
4. 同一资产是否同时被另一笔冲突交易花费？

如果存在一个可信的中央机构，可以让它决定哪一笔交易有效。但区块链的目标正是尽量去掉这个必须被信任的中介，把规则写成所有节点都能执行的代码和密码学检查。

#### 1.3 对手模型：为什么要假设“世界很坏”

安全协议不能只考虑诚实用户。对手可能会：

- 延迟、重排或丢弃自己控制的消息；
- 发送互相矛盾的消息；
- 创建大量虚假身份；
- 反复试验随机数；
- 试图双花、伪造签名或构造恶意区块。

诚实参与者遵守协议；攻击者可以偏离协议，但通常受到计算能力、网络假设或权益约束。一个安全结论必须明确“攻击者能做什么”和“我们没有让攻击者做什么”。

### 2. 密码学安全模型

#### 2.1 PPT 对手

密码学中的对手通常是**概率多项式时间**（probabilistic polynomial time，PPT）算法：

- **概率性**：可以使用随机数；
- **多项式时间**：运行时间关于安全参数 κ 是多项式级别，不能穷举指数规模空间。

这不是说现实中的攻击者真的只运行某个固定时间，而是把“可计算攻击”形式化为一类可分析的算法。

#### 2.2 安全参数与可忽略函数

安全参数 κ 决定密钥长度、哈希输出长度、证明参数等。函数 f(κ) 称为**可忽略函数**，如果对任意多项式 p(κ)，当 κ 足够大时都有：

~~~text
f(κ) < 1 / p(κ)
~~~

直观地说，可忽略概率比任何反多项式都下降得快。

例子：

- 2^(-κ)、e^(-κ) 是可忽略的；
- 1/κ^100 **仍然不是**可忽略的，因为它只是固定阶的反多项式；
- 若 f 和 g 都可忽略，则 f+g、max(f,g)、以及 poly(κ)·f(κ) 仍然可忽略。

安全证明常会把很多“小概率坏事件”并起来，因此可忽略函数对有限次并集、乘以多项式的封闭性非常重要。

#### 2.3 Union Bound（并合界）

对任意事件 E_1,…,E_t：

~~~text
Pr[E_1 ∪ … ∪ E_t] ≤ Σ_i Pr[E_i]
~~~

它不要求事件独立。证明可以用归纳法：

- t=1 时显然成立；
- 假设对 t 个事件成立，则

~~~text
Pr[(E_1 ∪ … ∪ E_t) ∪ E_(t+1)]
≤ Pr[E_1 ∪ … ∪ E_t] + Pr[E_(t+1)]
≤ Σ_(i=1)^(t+1) Pr[E_i].
~~~

所以，如果每个坏事件的概率都是可忽略的，而坏事件数量只是多项式个，那么“至少发生一个坏事件”的概率仍然可忽略。

#### 2.4 Game-based security

教材用“游戏”定义安全性：

1. Challenger 按规则生成密钥、输入或挑战；
2. 对手得到允许看到的信息并运行攻击算法；
3. 对手输出攻击结果；
4. 游戏输出 1 表示攻击成功，输出 0 表示失败。

协议安全的含义是：对任意 PPT 对手 A，都有：

~~~text
Pr[Game_A(κ)=1] ≤ negl(κ).
~~~

这样写的好处是可以精确区分“协议必须保证什么”和“攻击者不能以显著概率做到什么”。例如，签名安全不是一句“签名很难伪造”，而是说在给定公钥、允许攻击者请求签名的条件下，攻击者不能对一个未请求过的消息产生有效签名。

#### 2.5 计算归约

归约证明的结构是：

> 假设有攻击者 A 能以非可忽略概率攻破新协议，构造一个攻击者 A*，把 A 当作子程序，并利用 A 的输出攻破底层密码学原语。

如果底层原语安全，那么 A* 不存在；因此 A 也不可能存在。这是“新系统的安全性继承自旧原语”的标准方法。

### 3. 网络、Sybil 和 Non-eclipsing 假设

区块链节点通过点对点网络传播消息。网络可能延迟和重排消息。教程里最重要的网络事实是：

> 不同节点在同一时刻看到的消息顺序可能不同；“我先看到”不是全网共识中的“全网先发生”。

**Sybil 攻击**是攻击者创建任意多的身份。如果协议把“一人一票”当成权力来源，攻击者可以用大量虚假身份占多数。因此区块链需要把权力绑定到难以伪造的资源，例如：

- PoW：计算工作量；
- PoS：锁定的权益；
- 许可制 BFT：事先批准的节点身份。

**Non-eclipsing 假设**：任意两个诚实节点之间存在一条只经过诚实节点的通信路径。它不意味着每条连接都诚实，而是意味着攻击者不能把某个诚实节点完全隔离成只看见攻击者的局部世界。

启动和发现对等节点的方法可以是硬编码的引导节点、人工配置或外部目录。启动方式本身不等于共识安全，但它会影响节点能否看到诚实网络。

### 4. 哈希函数和签名

#### 4.1 哈希函数

哈希函数可以写成：

~~~text
H : {0,1}* → {0,1}^κ
~~~

输入可以任意长，输出固定为 κ 位。它需要高效计算，但希望以下攻击都只能以可忽略概率成功。

##### 碰撞抵抗（collision resistance）

攻击者不能找到两个不同的输入 x ≠ y，使得：

~~~text
H(x) = H(y).
~~~

由于输入空间大于输出空间，碰撞在数学上必然存在（鸽巢原理）；密码学要求的是，PPT 对手不能有效找到碰撞。生日攻击大约需要 2^(κ/2) 次尝试，而不是 2^κ 次。

##### 原像抵抗（preimage resistance）

给定目标 y，不能有效找到 x 使 H(x)=y。对理想的 κ 位哈希，穷举原像大约需要 2^κ 次尝试。

##### 第二原像抵抗（second-preimage resistance）

给定一个已有消息 x，不能找到不同的 x' 使：

~~~text
H(x') = H(x).
~~~

三者的攻击任务不同：碰撞是自由选两个输入；原像是给定输出反推输入；第二原像是给定一个具体输入替换它。教材通过归约说明某些安全性质可以从更强的底层性质继承，做题时要先写清楚游戏中的挑战者给了攻击者什么。

#### 4.2 数字签名

签名方案通常包含：

- Gen：生成公钥 pk 和私钥 sk；
- Sig(sk,m)：用私钥签署消息 m；
- Ver(pk,m,σ)：验证签名 σ 是否有效。

正确性要求合法签名能被验证。安全性通常是 EUF-CMA（existential unforgeability under chosen-message attack）：攻击者可以请求任意消息的签名，但不能对一个没有请求过的消息生成有效签名。

区块链把签名用于证明“花费者拥有私钥”，把哈希用于给交易、区块和 Merkle 树提供完整性绑定。签名主要解决**授权**；哈希主要解决**身份、完整性和承诺**，二者不能互相替代。

### 5. UTXO、交易和币的生命周期

#### 5.1 什么是 UTXO

UTXO 是一笔历史交易创建、但目前尚未被花费的输出。它通常由下面的 outpoint 唯一标识：

~~~text
(txid, output_index)
~~~

一个 UTXO 至少包含：

- 金额；
- 花费条件，例如收款公钥、地址或锁定脚本。

“unspent”不是说它没有被人使用过，而是说它还没有作为输入被合法消耗；一旦被花费，它就从 UTXO set 中删除。

#### 5.2 输入和输出如何转移价值

- 每个**输入**指向一个旧输出 (txid,index)，并提供满足该输出锁定条件的解锁数据，通常是签名。
- 每个**输出**创建一个新的 UTXO，并把金额锁定给下一个所有者。

交易满足价值守恒不等式：

~~~text
Σ input_value ≥ Σ output_value.
~~~

两者之差就是交易费。输入可以有多个，输出也可以有多个，因此一笔交易可以合并若干旧 UTXO、支付一个收款人，并把剩余金额送回找零地址。

#### 5.3 为什么不用一张“每个用户一个余额”的表

UTXO 模型的核心优点是：

1. **防双花是结构性的**：输入必须引用当前未花费的输出；一旦被使用就从集合删除。
2. **验证局部化**：验证某笔交易时，可以逐个检查输入是否存在、未花费且签名正确。
3. **并行性更好**：不花费同一 UTXO 的交易在很多场景下可以独立检查。

用户余额不是一个永久存储的单一变量，而是该用户能够解锁的所有 UTXO 金额之和。例如某用户有 0.4 BTC、0.6 BTC 两个可花费 UTXO，则余额是 1.0 BTC。

#### 5.4 交易验证

节点验证交易时通常检查：

1. 输入引用的 UTXO 存在；
2. 每个输入对应的 UTXO 当前未被花费；
3. 签名和脚本满足花费条件；
4. 输入金额不小于输出金额；
5. 同一交易内部没有重复引用同一个输入；
6. 交易格式、大小和其他协议规则有效。

交易组成一个从旧输出指向新输出的有向图。coinbase 交易是挖矿奖励的特殊来源，不能简单地把它当成普通输入；普通交易的合法性最终可以沿着图追溯到已经认可的 coinbase 或创世状态。

#### 5.5 Hash pointer

区块头中的“前一区块哈希指针”不是一个裸哈希，而是：

~~~text
hash pointer = 数据位置/引用 + 被引用数据的哈希
~~~

引用帮助节点找到前一区块，哈希帮助节点验证取到的数据没有被篡改。单独一个哈希通常不能拿来检索原始数据，因为哈希是单向压缩，不能从输出反推出输入，也没有“数据存放在哪里”的信息。

### 6. 区块、双花和工作量证明

#### 6.1 为什么交易还不够

两笔交易可能引用同一个 UTXO。若网络完全同步，大家可以按到达顺序选第一笔；但在实际分布式网络中，消息会延迟，因此需要一种全网可验证的顺序结构。区块把一批交易放在一起，并通过前向哈希链接到先前的区块，形成链。

区块链账本的两个基本性质：

- **Safety（安全性）**：两个诚实节点不会把冲突的交易都当成已经确定的结果。
- **Liveness（活性）**：诚实用户提交的合法交易最终会被记录或得到处理。

它们是不同的：只保证安全而拒绝所有交易，可以不双花但没有活性；只追求快速收录而不处理冲突，则可能不安全。

#### 6.2 三个看似简单但失败的规则

##### 规则一：彻底拒绝所有双花

攻击者先让 T' 被接受，再发布冲突交易 T''。如果“任何涉及双花的交易都使旧交易失效”，那么 T' 也可能被追溯推翻。诚实用户永远不知道支付何时稳定。

##### 规则二：接受“最先看到”的交易

节点 A 可能先看到 T'，节点 B 可能先看到 T''。网络没有一个自动产生的全局“第一时间”，所以两个商户可能分别接受不同的交易。

##### 规则三：在某个时间窗口 w 内拒绝双花

异步网络中没有所有节点共同认可的到达时间；攻击者还能延迟一笔消息，让不同节点对“是否在窗口内”得出不同结论。

因此，系统需要可验证的排序和具有累积成本的竞争，而不是依赖本地观察。

#### 6.3 PoW 的核心

矿工寻找一个 nonce，使区块头哈希小于目标 T：

~~~text
H(block_header) < T.
~~~

在随机预言机近似下，每次尝试独立成功的概率约为：

~~~text
p = T / 2^κ.
~~~

找到一个有效 nonce 的期望查询次数约为 1/p。矿工无法通过聪明地“预测”哈希来替代尝试，因此攻击者想让自己的链追上诚实链，就必须承担与诚实矿工相竞争的工作量。

区块通常含有：前一区块指针、交易集合或交易承诺、时间相关字段、难度目标以及 nonce。创世区块没有普通的前一区块。节点把尚未进区块的候选交易放进 mempool；挖矿算法从中选择交易、构建区块并搜索工作量证明。

#### 6.4 目标、链选择和概率最终性

区块越难挖，单位时间产生的区块越少；协议通过目标和难度调节平均区块间隔。最长链规则更准确地说是选择**累计工作量最大、且满足验证规则的链**。

因此 Bitcoin 风格的最终性是概率性的：一笔交易后面有 k 个区块时，被替代的概率随着 k 增大而下降，但在纯 PoW 模型中不等于绝对零。这个“确认数越多越稳”正是教程后面 Common Prefix 的直观来源。

### 7. 链的三种核心美德：CP、CG、CQ

教材把“链很安全”拆成可证明的性质。

#### 7.1 Common Prefix（共同前缀）

对任意两个诚实节点的链视图，去掉各自最后 k 个区块后，剩余部分应该互为前缀关系。写成直观形式：

~~~text
truncate_k(C_1) 是 truncate_k(C_2) 的前缀
或反过来。
~~~

最后 k 个区块可能仍处于竞争或传播中；更深的部分应当收敛。Common Prefix 直接对应安全性：如果某笔交易已经处于稳定前缀，另一个诚实节点就不能在同一稳定位置看到冲突交易。

#### 7.2 Chain Growth（链增长）

在一段时间/若干轮内，诚实节点的链至少增加一定数量的区块。它防止攻击者让网络“停住”，也是合法交易最终向稳定前缀推进的基础。

#### 7.3 Chain Quality（链质量）

在任意足够长的区块片段中，攻击者区块不能占据过高比例；等价地，诚实区块要保持正密度。Chain Quality 防止攻击者虽然没有绝对多数，但通过长期私挖或选择性发布完全控制链内容。

#### 7.4 Stable read 和 Nakamoto race

**Naive read** 直接读取当前最长链，可能把链尾的临时分叉当成稳定事实。**Stable read** 去掉最后 k 个区块再读取，把等待换成更低的反转概率。

当诚实矿工和攻击者同时找到区块时，会出现短暂分叉。若诚实网络能在新的收敛机会中快速看到同一延长区块，诚实链会重新统一；这就是教材所说的 honest convergence。

### 8. 攻击、修复和 Healing

#### 8.1 少数算力对手

即使攻击者少于一半，也可能：

- 发布交易后再尝试私下延长另一条链，进行双花；
- 利用过小的确认深度制造回滚风险；
- 通过网络时序、交易传播和短暂分叉影响交易排序；
- 进行 selfish mining：隐藏自己挖到的区块，寻找让公开链更偏向自己的发布时机。

少数攻击能否成功取决于确认深度、网络延迟、算力比例和协议参数，不能简单地说“少于 50% 就任何事都做不了”。

#### 8.2 多数对手

当攻击者拥有足够大的工作量比例时，可以更可靠地控制链的扩展速度，重写最近历史、审查交易、实施双花。它仍然不能凭空花费没有私钥的钱，也不能让无效交易通过诚实节点的验证，但可以掌握排序和历史选择。

#### 8.3 Healing

当攻击者停止或降低攻击，诚实节点继续广播和挖矿，链可以重新收敛。Healing 的意义是：安全系统不只要在攻击瞬间有性质，也要分析攻击后多久恢复到诚实链、哪些交易需要重新确认，以及客户端如何从分叉中选择稳定前缀。

---

### 9. 经济学：密码学安全之外的另一层安全

#### 9.1 三种视角

- **密码学模型**：攻击者可以任意偏离协议，只要受计算、网络和资源假设限制。
- **博弈论模型**：参与者是理性的，会选择最大化收益的策略。
- **更理想的模型**：诚实多数参与者理性，少数攻击者仍可任意恶意。

一个协议即使密码学上允许某种攻击，也可能因为攻击不赚钱而在经济上安全；反过来，激励设计有漏洞时，理性矿工会主动偏离协议。

#### 9.2 区块奖励、交易费和矿工选择

矿工收入通常来自区块补贴和交易费。补贴按协议安排逐渐减少时，交易费的重要性上升。矿工选择交易不是简单“按金额最大”：在区块大小有限的情况下，最大化总费收入通常接近一个 0/1 knapsack（背包）问题，同时还受依赖关系、优先费、MEV 和验证成本影响。

钱包也要决定何时提交交易、愿意支付多少费、如何合并 UTXO。固定难度和可变难度、epoch、交易量与网络拥堵之间相互影响。钱包类型还会影响密钥保存、是否在线和隐私泄露。

核心原则是：

> 协议规则告诉参与者“什么有效”，激励决定参与者“愿不愿意照做”。

### 10. 账户模型、UTXO 模型和状态机复制

#### 10.1 账户模型对比 UTXO

账户模型直接维护状态：账户余额、nonce、合约存储等。交易通常是“从账户状态执行一个状态转换”。优点是合约逻辑和账户交互自然；代价是验证与并发依赖更集中在全局状态上。

UTXO 模型把可花费对象显式拆开，交易消费旧对象并创建新对象；账户模型把同一个账户的余额更新为新的状态。

#### 10.2 Replay attack 和 nonce

如果一笔合法转账可以被原样重复执行，攻击者可以复制消息让账户多次扣款。账户模型通常使用 nonce：每个账户的下一笔交易必须使用下一个序号，执行过的 nonce 不能再次执行。

这说明“签名有效”不等于“交易只能执行一次”；抗重放需要把交易序号、链标识或域分离信息纳入状态转换和签名语义。

#### 10.3 State Machine Replication

区块链可以抽象成状态机复制：

~~~text
新状态 = Apply(旧状态, 已达成共识的交易序列)
~~~

只要所有诚实节点从相同初始状态执行相同的、有效的交易序列，它们就会得到相同状态。共识负责排序，状态机负责执行和验证。

### 11. Light client、Merkle 树和快速启动

#### 11.1 为什么需要轻客户端

全节点需要保存和验证完整的区块、交易图和 UTXO/state。对移动设备、低带宽设备或只关心一个地址的用户来说，完整下载和重放成本很高。

轻客户端希望在不保存全账本的情况下：

- 验证某笔支付是否在链上；
- 验证某个状态值；
- 为地址构造交易；
- 检查区块头链是否满足共识规则。

#### 11.2 Merkle inclusion proof

对叶子消息 m_i：

~~~text
h_i = H(m_i)
parent = H(left || right)
~~~

逐层哈希后得到根 r。若要证明 m_k 在树中，只需要提供：

- H(m_k) 的起点；
- 每一层的兄弟哈希；
- 当前节点在左边还是右边的方向位。

验证者按方向逐层合并，最终检查是否得到公布的根 r。树有 n 个叶子时，证明大小和验证哈希次数约为 O(log n)。

Merkle 根本身不是数据；它是对整棵树的短承诺。若哈希具有碰撞抵抗，攻击者不能给同一个根构造两份互相冲突的有效路径，除非找到碰撞。

#### 11.3 轻客户端验证和局限

轻客户端可以同步带有前一区块承诺的 header chain，再请求交易或状态的 Merkle proof。它通常仍需信任：

- header chain 的共识规则；
- 自己连接到的网络没有完全 eclipse 它；
- 服务方没有隐藏关键数据；
- Merkle proof 对应的根确实属于稳定区块。

因此，证明“某交易在一个有效区块里”与证明“没有另一笔冲突交易”不是完全同一个问题。后者需要更强的链安全和数据可用性假设。

### 12. 教材 Chapter 11–13：正式安全证明的路线

#### 12.1 形式化环境

教材把前面直观的区块链规则放入一个可证明模型，主要组件包括：

- **随机预言机模型**：每次对新的输入调用哈希时得到独立随机的 κ 位输出；同一输入重复调用得到相同输出。
- **同步性参数 Δ**：诚实消息在最多 Δ 时间内送达。
- **离散时间/量化轮次**：把连续时间简化成协议轮次，便于数挖矿查询。
- **rushing adversary**：在一个轮次中，攻击者可以先看到可见的诚实消息，再决定自己发什么。
- **Sybil adversary 与 non-eclipsing**：攻击者可以有多个身份，但不能完全隔离所有诚实节点。
- **honest majority assumption**：诚实算力或有效查询比例超过攻击者，且有一定余量。

#### 12.2 Honest party / PoW / Longest chain

诚实算法的核心循环是：

1. 接收并验证区块与交易；
2. 选择当前累计工作量最大的有效链；
3. 将链上交易从 mempool 中移除；
4. 在链尾构造区块并搜索 PoW；
5. 发现有效区块后广播；
6. 若看到更优链，则更新本地视图。

validate 通常递归检查创世区块、前向指针、PoW、交易有效性、UTXO 变化和其他协议约束。最长链不是“最长字符串”，而是有效且累计工作量最大的候选链。

#### 12.3 Safety 和 Liveness 的正式含义

- **Safety**：任何两个诚实节点的稳定账本不会对同一位置作出冲突决定；等价地，不会稳定确认同一 UTXO 的两个冲突花费。
- **Liveness**：诚实提交的合法交易，只要持续被诚实网络传播，最终会进入诚实节点的稳定账本。

教材先证明：

1. Common Prefix ⇒ Safety；
2. Chain Growth + Chain Quality ⇒ Liveness。

这一步把“系统不会双花/不会卡住”转化为更容易从随机挖矿过程分析的链性质。

#### 12.4 典型执行、Chernoff 和配对论证

PoW 查询可以近似为 Bernoulli 试验。对一组查询 S，记：

- Y(S)：诚实成功查询数量；
- Z(S)：攻击者成功查询数量。

在诚实优势足够时，通过 Chernoff bound 可以证明，在几乎所有执行中，Y(S) 不会显著低于期望，而 Z(S) 不会显著高于期望。把这些坏事件用 union bound 合并，就得到“典型执行”以至少 1-negl(κ) 的概率发生。

证明链增长时，分析一个时间窗口中诚实成功的查询是否足以新增区块；证明共同前缀时，使用 patience lemma、pairing lemma 和收敛机会，说明攻击者的分叉需要持续追上诚实链，但在典型执行中无法以显著概率做到。最终得到的不是绝对确定性，而是：

~~~text
违反安全性质的概率 ≤ negl(κ)
~~~

## 第二部分：Tutorial 3 —— TBL、SDD 与可靠 AI agent

Tutorial 3 的主题虽然不是传统区块链算法，但它教的是**如何把复杂系统任务做得可靠、可审查、可验证**。

### 13. Team-Based Learning（TBL）

#### 13.1 核心观点

可靠 agent 依靠约 80% 的人类引导、审查和验证，而不是继续堆更多 prompt。人类的角色不是被动写 prompt，而是**可靠性工程师**：设计任务边界、验收标准、工具、测试、可观测性、回滚和审查点。

TBL 的三个动作：

- **Guide**：给出目标、边界和成功定义；
- **Verify**：检查结果是否真的满足规则；
- **Critique**：主动寻找反例、遗漏和偏差。

#### 13.2 四阶段协议

可以把一次可靠任务固定为：

1. **Spec**：写清楚目标、非目标、约束和验收标准；
2. **Plan**：拆成可执行、可独立验证的步骤；
3. **Execute**：逐步实施并记录证据；
4. **Review**：由人或另一个 agent 审查，并检查测试、diff、日志和最终产物。

反偏差规则：如果大家一开始就完全同意，必须暂停并主动问“最可能错在哪里？”因为过快的一致可能只是共享同一个假设或确认偏误。

#### 13.3 为什么 peer critique 胜过 solo prompting

单个 agent 容易出现：

- 确认偏误：只寻找支持原方案的证据；
- 盲点：没有独立角色发现遗漏；
- 漂移：任务越做越偏离最初目标；
- “看起来正确”：输出语法正确，但没有满足真实需求。

同伴审查要求对方证明结论、指出边界条件，并把“我认为正确”换成“这是可复核证据”。

---

### 14. Spec-Driven Development（SDD）

#### 14.1 为什么 AI 时代更需要规格

LLM 擅长生成看起来合理的代码，但较弱于：

- 发现没有写出来的需求；
- 维持多步骤目标的一致性；
- 识别真正的边界条件；
- 自己证明实现符合需求。

因此 SDD 是：

~~~text
需求 + 约束 + 验证
~~~

它在错误还便宜的时候加入检查点。

#### 14.2 “vibe coding” 为什么会失败

典型链条是：

~~~text
模糊 prompt → agent 猜测 → 代码看起来合理 → 静默偏离真实需求
~~~

症状包括巨大的 diff、反复试错、把所有资料塞进上下文、没有明确验收条件、没有独立审查。SDD 用“契约 + 检查”替代猜测。

#### 14.3 一页规格就是一个契约

最小规格只要回答三个问题：

1. **Goal**：要解决什么问题？
2. **Constraints**：必须遵守什么边界？包括安全、性能、兼容性、数据格式。
3. **Acceptance**：怎样通过可观察结果判断完成？

推荐的一页模板：

~~~text
Feature:
Goal:
Non-goals:
User flows:
Acceptance criteria:
Constraints:
Verification plan:
~~~

验收条件要可测试。不要写“很快”“安全”“用户体验好”；要写成：

- 在 1000 req/min 下 p95 延迟小于 200 ms；
- 错误登录不能暴露账户是否存在；
- 每个用户每小时最多 5 次密码重置；
- 重试使用指数退避，最多 3 次。

#### 14.4 SDD 什么时候用、什么时候跳过

适合使用 SDD：

- 至少 3 个步骤；
- 存在边界条件；
- 多人协作；
- 涉及安全、数据、金钱或声誉；
- 错误修复成本高。

可以跳过完整 SDD：

- 单文件的小修改；
- 一次性的抛弃式脚本；
- 没有人会审查、文档本身比任务更重的情况。

原则是“最小而活的工件”：规格少于 1–2 页，任务清单大约 10–30 个 checkbox，文档更新属于完成任务的一部分。

---

### 15. GitHub Spec Kit 工作流

Spec Kit 把 SDD 固化为仓库内的可审查工件：

~~~text
specify → plan → tasks → implement
~~~

常见命令序列：

~~~text
/speckit.constitution
/speckit.specify
/speckit.plan
/speckit.tasks
/speckit.implement
~~~

#### 15.1 Constitution

Constitution 是项目规则，应该只有 5–10 条、可执行、可检查，例如：必须有测试、错误必须记录、禁止把大 JSON 塞进聊天、要支持回滚、敏感数据不能写日志。

#### 15.2 Specify

Specify 写“做什么”和“为什么”，不急着决定具体技术架构。它应该包含用户行为、非目标和 Given/When/Then 验收条件，避免写成长篇设计论文。

#### 15.3 Plan

Plan 只记录关键架构选择、数据契约、风险和验证策略；它是供审查的工程计划，不是小说。

#### 15.4 Tasks

一个好任务应该小、可执行、可独立验证并产出证据，例如“新增接口并补充失败场景测试”。坏任务是“实现整个支付系统”。如果任务无法在一个清晰的 diff 和一组测试里检查，就应该继续拆分。

#### 15.5 Implement

实施阶段每一步都应该留下：

- 代码 diff；
- 测试命令和结果；
- 生成的文件或截图；
- 当前进度；
- 失败原因与下一步。

没有证据，就没有可信度。

#### 15.6 常见陷阱

- 文档太多：用 artifact budget 限制数量；
- 文档过时：文档更新纳入 done；
- 计划无人审查：把计划审查设为实现前的 gate；
- 计划和另一份计划互相漂移：只保留一个 canonical plan。

### 16. Context Engineering：上下文也需要内存管理

把上下文窗口看成有限而易失的 RAM，把磁盘文件看成容量大、可持久化的磁盘：

- RAM/上下文：快，但小，压缩或换轮次后可能丢失；
- 磁盘：慢一点，但能保存任务状态、研究结果、错误和决定。

不要把所有文档都粘贴进上下文。采用 progressive disclosure：

1. 先读很小的近期摘要；
2. 找到与当前步骤有关的文件；
3. 只加载相关段落；
4. 行动后验证并把结果写回磁盘。

#### 16.1 Planning-with-Files 三文件状态机

多步骤任务可以只保留三个工作文件：

- task_plan.md：路线、任务清单和当前步骤；
- findings.md：研究结果、决定和重要假设；
- progress.md：已做事项、命令证据、失败和下一步。

四条防漂移规则：

1. 先建计划再执行；
2. 两次查找之后就把发现写入 findings.md；
3. 所有错误写入 progress.md；
4. 同一策略连续失败两次后必须换策略，而不是重复尝试。

progress.md 不应只写“完成了”，而应写：做了什么、运行了什么命令、得到什么输出、为什么失败、接下来改变什么。

### 17. Agent 架构、Actor–Critic 和断言

#### 17.1 God Model fallacy

一个巨大模型不自动解决任务分解、独立验证、长程状态和可靠集成问题。更实用的架构是：

- **Supervisor**：规划、分派、整合；
- **Minions/tools**：执行范围窄、输出精确的子任务；
- **Critic**：独立审查和找反例。

#### 17.2 Actor–Critic loop

可靠 agent 是循环而不是一次性生成：

~~~text
Actor 提议/执行 → Critic 检查 → 更新计划和日志 → 必要时用新策略重试
~~~

没有 critic，就没有工程纪律；只有提示词而没有可执行验证，输出仍然只是猜测。

#### 17.3 Guardrails 与 Assertions

- **Guardrails**：限制格式、风格、策略和权限；
- **Assertions**：在运行时检查真实状态，例如测试、schema、性能阈值、错误码和不变量。

Guardrail 只能约束“应该怎么输出”，assertion 才能验证“现实中是否真的正确”。自主程度越高，越需要 runtime assertions、日志、监控和 rollback，而不是只写一个更好的 prompt。

#### 17.4 Superpowers 和统一工作流

Tutorial 中的 Superpowers 代表一种 skills-driven workflow：把 brainstorming、写计划、执行计划、TDD、系统调试和 code review 变成默认习惯，而不是临时提醒。典型过程是：

~~~text
brainstorm → 压缩成 spec → plan → tasks → TDD implement → review/evidence
~~~

它和 Spec Kit 可以结合：Superpowers 负责互动式思考和计划，Spec Kit 负责将结果固定为仓库内工件；两者必须共享一个 canonical plan。课堂实验可按“范围/验收 → 小任务 → 测试/断言 → 调试 → 完成审查/证据”执行。

#### 17.5 Tutorial 3 的总原则

~~~text
SDD = 契约 + 可验证标准
Context engineering = 磁盘持久状态 + 渐进加载
TBL = 同伴批评 + 反偏差 + 验证文化
可靠 agent = Plan → Act → Critique → Evidence
~~~

## 第三部分：Tutorial 4 —— Bitcoin、双花与 Reliable Broadcast

### 18. UTXO 基础题

#### 18.1 UTXO 的完整定义

UTXO 是旧交易创建、尚未被花费的特定输出，由 (txid, index) 标识，包含金额和花费条件。它在 ledger 上是一个仍然存在于当前 UTXO set 中的可解锁对象。

#### 18.2 余额计算

~~~text
balance(user) = Σ value(u)，其中 u 是 user 能解锁的所有 UTXO。
~~~

例如用户有 0.4 BTC 和 0.6 BTC 两个可花费 UTXO，余额就是 1.0 BTC；不能把历史上已经花掉的输出再次加进去。

#### 18.3 交易守恒

输入引用旧输出，输出创建新 UTXO：

~~~text
Σ outputs ≤ Σ inputs,
fee = Σ inputs - Σ outputs.
~~~

#### 18.4 Coin 和 hash pointer

在 Bitcoin 的数据结构里，coin 就是一个可花费的 UTXO。哈希指针包含“定位数据的引用”和“验证数据的哈希”；裸哈希不能反向取回前一区块。

### 19. 为什么简单双花规则都不够

- **全部拒绝双花**：攻击者可以先让 T' 被接受，再发 T''；如果任何双花都会让旧交易失效，付款永远无法稳定。
- **first-seen**：不同节点看到的先后次序可以不同；两个商户可能接受不同冲突交易。
- **限定窗口 w**：异步网络没有统一到达时间，节点无法一致判断两笔交易是否在窗口内。

共识需要对冲突交易进行全网可验证的排序和稳定选择，而不是依赖本地第一印象。

### 20. PBFT vs Nakamoto

| 维度 | PBFT | Nakamoto consensus |
|---|---|---|
| 参与方式 | 通常是固定的、许可制验证者集合 | 无许可开放参与，权力绑定到 PoW 算力 |
| 故障假设 | 标准设置容忍少于 n/3 Byzantine 节点 | 需要诚实算力占多数，安全通常是概率性的 |
| 最终性 | 达到提交条件后通常是确定最终性 | 通过更多确认降低回滚概率，通常是概率最终性 |
| 性能 | 节点间消息较重，常见通信成本接近 O(n²) | 开放参与、消息结构简单，但吞吐/延迟受 PoW 和分叉影响 |
| 能源 | 不需要 PoW 能耗 | PoW 需要大量计算能源 |

### 21. Reliable Broadcast（RBC）

#### 21.1 目标

异步、带认证信道的网络中，指定 sender S 输入比特 b。每个节点最终输出 0/1 或 ⊥。RBC 要满足：

- **Consistency / Agreement**：两个诚实节点不会输出不同的比特；
- **Validity**：sender 诚实时，所有诚实节点输出 sender 的 b；
- **Totality**：如果某个诚实节点输出一个比特，那么最终所有诚实节点都会输出一个比特。

它相当于给 leader-based SMR 提供“大家看到同一个提案，或者都不交付”的最小保证。

#### 21.2 Scale up：用 n 节点黑盒扩展到 m>n

已知黑盒协议 Π 在 n 个节点中最多容忍 f<n/3 个坏节点，并且只能运行一次。构造：

1. 公布一个包含 sender 的委员会 C，大小为 n；
2. 只有 C 内部运行一次 Π；
3. 委员会成员得到 v∈{0,1} 后，向全部 m 个节点发送认证消息 (RELAY,v)；
4. 任意节点收到 f+1 个不同委员会成员对同一 v 的 relay 后，输出 v。

为什么有效：

- **一致性**：f+1 个 relay 至少有一个诚实成员；诚实成员只 relay 黑盒协议输出的唯一值，所以两个不同值不可能都形成有效证书。
- **有效性**：sender 诚实时，委员会所有诚实成员最终输出 b。需要足够多诚实 relay 形成证书，即

~~~text
n - f ≥ f + 1  （等价于 n ≥ 2f + 1）。
~~~

在通常的 f<n/3 条件下成立；如果题目采用更强的严格不等式 n-f>f+1，那也是足够条件。

- **全体性**：若某个诚实节点已从 f+1 个 relay 得到 v，其中至少一个 relay 来自诚实委员会成员。黑盒 RBC 的 totality 让所有诚实委员会成员最终输出 v 并 relay，其他诚实节点最终也收集到 f+1 个 relay。

#### 21.3 Tight bound：f=n/3

此时诚实委员会有 n-f=2f 个。阈值条件是 2f≥f+1，即 f≥1；所以对题目假设的可运行黑盒（且通常 n>3）仍然成立。关键不是机械地代入 f<n/3，​​而是检查 relay 证书是否能由足够多诚实成员形成。

#### 21.4 Shrink down：用 n 节点黑盒模拟成 3 个真实节点

设 n 可被 3 整除，黑盒能容忍 f=n/3。三个真实节点 Q_1,Q_2,Q_3 各自模拟 n/3 个虚拟节点：

1. 把 n 个虚拟节点分成 V_1,V_2,V_3；
2. Q_i 在本地运行 V_i 中所有虚拟节点的程序；
3. 若虚拟节点 u∈V_i 给 v∈V_j 发消息，Q_i 通过真实认证信道向 Q_j 转发 (sender-id, receiver-id, payload)；
4. Q_j 把消息交给对应的虚拟接收者；
5. 模拟 sender 的输入比特，并用黑盒输出作为真实节点输出。

若最多一个真实节点恶意，则最多 n/3 个虚拟节点恶意，刚好在黑盒容错范围内。因此黑盒的 consistency、validity、totality 继承到三个真实节点。

## 第四部分：Tutorial 5 —— Merkle 树与 SecureVault 托管

### 22. Merkle 树

#### 22.1 构造和包含证明

叶子：

~~~text
h_i = H(m_i)
~~~

内部节点：

~~~text
h_parent = H(h_left || h_right)
~~~

根为 r。证明第 k 个叶子存在，需要叶子值、每层兄弟哈希和左右方向。验证者从 H(m_k) 开始逐层合并，最后和 r 比较。时间与证明大小都是 O(log n)。

#### 22.2 用途

- **篡改证据**：任意叶子变化会改变根；
- **轻客户端**：只下载一条路径而不是完整数据；
- **数据可用性抽样**：随机抽查部分叶子；
- **并行和增量更新**：不同分支可以独立计算。

Ethereum 中常见的根包括 state root、transaction root 和 receipts root。交易树是有序集合承诺；状态树则更像支持动态 key-value lookup/update 的认证字典。

#### 22.3 Ethereum MPT 与普通 Merkle tree

普通 Merkle tree 适合固定、有序的列表；Ethereum 的 Merkle Patricia Trie（MPT）支持按账户地址或 storage key 查找，能够证明：

- 某个 key 对应某个值（membership）；
- 某个 key 不存在（non-membership）；
- 状态更新前后根如何变化。

### 23. SecureVault 题的系统设计

#### 23.1 冷热钱包分层

题设建议约 97% 资产放在冷端，约 3% 放在热端。冷端可以是地理分散、隔离网络的 M-of-N 多签：只有至少 M 个不同密钥共同批准才能转出。

若内鬼只有一个且 M>1，不能单独转账；但如果攻击者能串通至少 M 个签名者，安全性仍会失败，所以还要做：

- 密钥、人员、地区和团队分离；
- HSM/硬件钱包和离线备份；
- 双人控制和操作审批；
- 防篡改日志、定期审计和密钥轮换。

#### 23.2 热钱包的 50,000 tx/day 架构

热端的目标不是把所有资产放在线，而是只保持业务流动性。可组合：

- MPC 或 HSM，避免单台服务器持有完整私钥；
- policy engine：白名单、额度、审批等级；
- 每小时/每日 velocity limit；
- 异常行为检测和 circuit breaker；
- 多个隔离的 sharded hot wallets；
- 批处理、归集和定期 sweep 到冷端。

热钱包比例的简单原则是：

~~~text
hot fraction = L / A
~~~

其中 L 是最大预期日流出量加安全缓冲，A 是总资产。热端应尽量小，但不能小到正常业务频繁阻塞。

#### 23.3 20 国监督和 BFT

如果是固定成员的跨国机构，适合 permissioned consortium 或 hybrid 模型。标准 BFT 假设通常要求：

~~~text
n > 3f
~~~

也就是容忍少于三分之一恶意节点。可以用地区委员会先局部签署，再由全球层最终确认，但必须考虑地区相关故障、网络分区、密钥治理和法域冲突。

#### 23.4 事故响应

发现异常时先暂停提现或触发 circuit breaker，再隔离系统、撤销 API 凭证、轮换密钥、保全日志。之后：

1. 评估受影响范围和剩余干净资金；
2. 轮换受影响密钥，必要时把干净资金 sweep 到新钱包；
3. 与交易所、取证团队、律师、监管方和保险方协作；
4. 复盘并增加额度、时间锁、分级审批、白名单、监控和演练。

## 第五部分：Tutorial 6 —— PoS、Calldata 与安全/活性韧性

### 24. Proof of Stake

PoS 的典型流程：

1. **质押**：验证者锁定 collateral，作为安全押金；
2. **选择 proposer**：协议按质押权重和随机性选出区块提议者；
3. **验证和投票**：其他验证者检查签名、余额、nonce、gas 和状态转换，并对区块 attestation；
4. **最终化、奖励和惩罚**：收到足够有效票后区块进入链或被最终化；诚实者获得奖励，双签等恶意行为可能被 slash。

PoS 相比 PoW 的优点是能耗低；挑战是质押集中会导致权力集中，也要认真设计长程攻击、惩罚、密钥安全和退出机制。

### 25. Ethereum calldata 的可见性

#### 25.1 当前调用中的函数

函数 F 在交易 T 执行时可以读取 T 的 calldata。Solidity 中可通过 msg.data，EVM 中可用 CALLDATASIZE、CALLDATALOAD、CALLDATACOPY。答案是 **Yes**。

#### 25.2 后续交易中的函数

之后的交易 T_next 再调用同一个 F 时，msg.data 是 T_next 的 calldata，不能直接读取旧交易 T 的 calldata。答案是 **No, not directly**。

例外是：T 执行时主动把 calldata 存到了合约 storage，后来读取的是已经存储的状态，不是跨交易回溯读取历史执行上下文。

#### 25.3 人类查看

公链上的交易 calldata 是公开数据。区块最终化后，人类可以通过全节点、RPC 或区块浏览器读取它。答案是 **Yes**，除非考虑加密应用层等额外隐私机制；Ethereum 基础 calldata 本身不保密。

### 26. Safety / Liveness resilience

设总节点数为 n，提交一个决定需要 q 个票。

#### 26.1 Liveness resilience

攻击者控制 f 个节点并让它们完全不投票，剩下 n-f 个诚实节点仍需形成 quorum：

~~~text
n - f ≥ q
⇒ f ≤ n-q.
~~~

因此：

~~~text
f_l = n-q.
~~~

#### 26.2 Safety resilience

两个大小为 q 的 quorum 在 n 个节点中至少相交：

~~~text
|Q_1 ∩ Q_2| ≥ 2q-n.
~~~

如果攻击者控制整个交集，就可以在两个冲突决定中重复投票。因此要保持安全，需要：

~~~text
f < 2q-n.
~~~

最大整数安全韧性是：

~~~text
f_s = 2q-n-1.
~~~

整体韧性为：

~~~text
f_overall = min(f_s, f_l)
          = min(2q-n-1, n-q).
~~~

#### 26.3 最优 quorum

让两边尽量平衡：

~~~text
2q-n-1 = n-q
3q = 2n+1
q ≈ (2n+1)/3.
~~~

因为 q 必须是整数，实际选最接近的整数并比较 min(f_s,f_l)。

#### 26.4 n=40，优先保证 f=15 的安全性

要求：

~~~text
2q-40-1 ≥ 15
2q ≥ 56
q ≥ 28.
~~~

最小整数 quorum 是 q=28。此时：

~~~text
f_l = 40-28 = 12.
~~~

也就是说，安全性可以承受 15 个对手，但活性只能承受 12 个节点不参与；若 13 个节点离线，只剩 27 个，不足以形成 28 票。高价值金融系统可以接受这种安全优先的停机风险，但必须用冗余、监控、运维演练和快速恢复来承担它。

## 第六部分：Tutorial 7 —— DEX、AMM、ERC-20 与费用市场

### 27. DEX 和 Uniswap 的 AMM

DEX 不依赖中心化订单簿撮合，而是让：

1. LP 向智能合约存入一对资产；
2. 交易者直接和池子交换；
3. 合约按公式自动计算价格和输出数量；
4. LP 按份额退出并取回两种资产。

Uniswap v2 风格 AMM 使用恒定乘积：

~~~text
x · y = k,
~~~

其中 x,y 是池中两种 token 的数量，k 在忽略手续费和交易过程变化时保持不变。池子的边际价格大致由 y/x 决定；交易会改变比例，套利者会把池价和外部市场价拉回一致。

### 28. LP 的收益与损失

- **交易费**：每笔 swap 的一部分分给 LP，通常用 APR 表示；APR 是简单年化，不自动包含复利。
- **流动性挖矿**：协议额外发放治理/原生 token，若奖励再投资，常用 APY 表示，包含复利。
- **Impermanent Loss（IL）**：两种资产的相对价格变化时，AMM 自动再平衡，LP 的组合价值可能低于自己直接持有原始资产的价值。价格偏离越大，IL 通常越大。

“无常”只表示若价格回到初始比例，损失可能消失；如果此时退出，损失就实际实现了。

### 29. ERC-20

ERC-20 是 Ethereum 上的**同质化 token** 标准，单位之间可互换。核心函数包括：

~~~text
totalSupply()
balanceOf(account)
transfer(to, amount)
transferFrom(from, to, amount)
approve(spender, amount)
allowance(owner, spender)
~~~

题目只要求三个，但理解六个更完整：approve 设置授权额度，transferFrom 使用这个额度代表用户转账。

### 30. Uniswap 数值题

初始池子：

~~~text
6 ETH + 9600 DAI
k = 6 × 9600 = 57600.
~~~

价格升到 3600 DAI/ETH 后，稳定池满足：

~~~text
y = 3600x
x·y = 57600
3600x² = 57600
x = 4,
y = 14400.
~~~

因此 LP 取回 4 ETH + 14,400 DAI，按新价格估值：

~~~text
4×3600 + 14400 = 28800 DAI.
~~~

如果自己一直持有 6 ETH + 9600 DAI：

~~~text
6×3600 + 9600 = 31200 DAI.
~~~

相对直接持有的无常损失为：

~~~text
31200 - 28800 = 2400 USD.
~~~

这 2400 的经济受益者主要是**套利者**：他们在池价仍低于外部 ETH 价格时，用 DAI 从池中买走 ETH，直到池子达到新的价格比例。套利者获得差价，池子则留下更多 DAI、更少 ETH。

### 31. EIP-1559 priority fee

如果 tx1 的 priority fee 是 y，tx2 是 2y，并且二者都满足 max fee 约束，tx2 **更可能**被区块生产者优先打包，但不保证一定在 tx1 前执行。

原因包括：

- 更高 tip 只是经济激励，不是协议强制排序；
- tx1 可能更早抵达生产者的 mempool；
- 生产者要最大化总收益，可能优先考虑 MEV，而非单纯 tip；
- nonce、交易依赖、gas limit、私有 relay 和构块策略也会影响排序。

## 第七部分：Tutorial 8 —— 链上隐私、Pedersen、隐身地址和环签名

### 32. 交易 tx_7f3a 的链上分析

交易输入：

~~~text
addr_X: 0.8
addr_Y: 0.5
addr_Z: 0.2
~~~

输出：

~~~text
addr_M: 1.0
addr_N: 0.487
~~~

#### 32.1 共同输入启发式

三输入同时被一笔交易花费，常见推断是它们可能受同一控制者管理，因为发起者需要解锁三份输入。但这是启发式，不是密码学证明；CoinJoin、PayJoin 或协作交易会故意打破这种推断。

#### 32.2 找零判断

addr_N 很可能是找零地址，因为 0.487 是不规整的剩余数额，而 1.0 更像支付金额；新地址、脚本类型和地址格式与输入匹配也会增强该推断。若用户重复使用地址，整个收款、找零和支出历史会被串联。

#### 32.3 网络层泄露

即使链上地址不直接写真实姓名，第一次广播 IP、ISP 观察、spy nodes 和 mempool 时间也可能把某个地址与网络身份绑定。常见缓解包括 Tor/I2P/VPN、多样化 peer、随机 relay、Dandelion++ 风格传播和避免从同一节点持续广播。

### 33. Pedersen commitment 与 Confidential Transactions

Pedersen 承诺可写成：

~~~text
C(v,r) = g^v h^r.
~~~

其中 v 是金额，r 是随机盲因子。它具有：

- **隐藏性**：不知道 r 时不能从承诺看出 v；
- **绑定性**：在离散对数假设下，不能把同一个承诺打开成两个不同金额；
- **加法同态性**：

~~~text
C(a,r_a) · C(b,r_b)
= g^(a+b)h^(r_a+r_b)
= C(a+b, r_a+r_b).
~~~

因此验证者可以检查输入承诺的乘积是否等于输出承诺的乘积（必要时把手续费承诺纳入），从而验证金额守恒，而不需要看到具体金额。

#### 33.1 负金额攻击

如果只检查承诺上的代数守恒，不检查范围，攻击者可以把某个“金额”解释成负数，伪造看似守恒的交易。Range proof 要证明：

~~~text
v ∈ [0, 2^64)
~~~

且不泄露 v。这样既保证非负，也限制数值范围，避免溢出和负值。

### 34. Stealth address

地址复用会泄露收款总额、付款人关系和未来支出。隐身地址用一次性公钥替代公开重复地址，典型 ECDH 思路是：

1. 收款人发布扫描公钥和支出公钥；
2. 发送者选择随机数 r，计算共享秘密；
3. 从共享秘密和收款人公钥派生一次性地址 P；
4. 发送者把临时公钥 R 和支付一起发布；
5. 收款人用扫描私钥从 R 得到同一共享秘密，扫描出属于自己的 P；
6. 收款人用支出私钥控制这个一次性输出。

观察者看到很多不同地址，但不能直接把它们链接到同一个收款人。

### 35. Ring signature 与 key image

环签名把真实签名者隐藏在一组候选公钥中。若环大小为 5，验证者知道五个候选中的某一个签了名，但不能知道是哪一个。

问题是：完全匿名会让同一个输出被重复花费。于是引入 **key image**：

- 由真实私钥和被花费输出确定性生成；
- 对不同花费应唯一；
- 验证者看不到真实私钥，但能检查 key image 是否已经出现；
- 重复出现说明 double spend。

它实现“隐藏谁花钱，但阻止同一输出花两次”。

### 36. Monero、Zcash、Tornado Cash 和 Privacy Pools

- **Monero**：环签名隐藏发送者，stealth address 隐藏接收者，RingCT 与 Bulletproofs 隐藏金额；隐私机制默认/强制使用，匿名集更一致。
- **Zcash**：shielded 交易使用零知识证明隐藏交易信息，但如果用户选择透明模式或 shielded 使用率很低，实际匿名集可能较小，使用者可能更显眼。
- **Tornado Cash**：把存款和取款解耦，用零知识证明证明“我知道一个有效存款的秘密”，但不泄露是哪一笔；这也引出开放源码数学工具与制裁规则之间的法律和治理问题。
- **Privacy Pools**：把存款归入 association set，用户可用零知识证明自己属于允许的集合，而不必公开全部交易历史，试图平衡隐私与合规。

## 第八部分：Tutorial 9 —— ZKP、zk-SNARK 与 Proof of Solvency

### 37. ZKP、NIZK、ZK-SNARK 的关系

层次关系可以记为：

~~~text
ZK-SNARK ⊂ NIZK ⊂ ZKP
~~~

- **ZKP**：最广义的零知识证明，可能交互；证明者让验证者相信自己知道 witness，同时不泄露 witness。核心性质是 completeness、soundness/proof of knowledge、zero-knowledge。
- **NIZK**：非交互零知识证明，证明者发送一份 proof，验证者独立检查；可能依赖 CRS/可信设置。
- **ZK-SNARK**：一种具体的 NIZK，强调 succinct（证明短、验证快）和 argument of knowledge（通常是计算安全，而非无条件/统计安全）。

注意“proof”和“argument”的术语区别：argument 通常只要求计算能力受限的攻击者不能伪造；这正适合复杂电路和区块链验证，但安全性依赖计算假设。

### 38. 简化版交易所 Proof of Solvency

#### 38.1 目标

交易所希望证明：链上资产 Assets 足以覆盖所有客户负债，但不公开每个客户的余额。

设客户余额为 bal_i。把叶子定义为客户数据，构造 Merkle tree，根为 R，总负债：

~~~text
B = Σ_i bal_i.
~~~

交易所发布 public statement (R,B)，并用 zk-SNARK 证明自己知道 witness：

~~~text
{(bal_i, Π_i)}_(i=1)^n
~~~

其中 Π_i 是叶子到 R 的 Merkle proof。电路检查：

1. 所有 bal_i 的和等于公开的 B；
2. 每个 Π_i 确实把对应叶子连到 R。

任何人验证 proof 并检查 B≤Assets。客户私下收到自己的 (bal_i,Π_i)，验证余额是否正确以及叶子是否属于 R。

技术细节：题目把叶子 0 设成随机 256-bit 数，是为了让树叶数为 2 的幂时有一个不代表客户的填充叶；真实设计中叶子还必须包含唯一身份和版本/快照信息。

#### 38.2 Attack A：相同余额的叶子复用

若 Alice 和 Bob 的余额都为 x，恶意交易所只放一个值为 x 的叶子，然后把同一叶子证明发给两人。SNARK 中 x 只被求和一次，但真实负债是：

~~~text
x(Alice) + x(Bob) = 2x.
~~~

两人都能验证自己的余额和 Merkle proof，因此都不会投诉；他们不知道两个人共享了同一个叶子。

#### 38.3 Mitigation B：叶子绑定唯一客户

把叶子改成：

~~~text
Leaf_i = H(clientID_i || bal_i)
~~~

或 H(username_i,bal_i)。即使余额相同，不同客户 ID 也会产生不同叶子；电路和求和必须对所有不同客户记录分别计数。

#### 38.4 Attack C：恶意客户 Eve 与交易所串通

交易所可以直接把 Eve 的记录从树中省略：

1. 只用诚实客户构造根 R'；
2. 只计算诚实客户的总负债 B'；
3. 生成对 (R',B') 有效的 SNARK；
4. 给诚实客户发送正确余额和路径；
5. Eve 不投诉，因为她在串通。

若 Eve 的余额占一半，公开 B' 就可能只有真实总负债的一半，但所有诚实客户的个人验证都通过。这个例子说明：

> 有效 proof 只证明公开 statement 为真；它不自动证明 statement 覆盖了现实世界中的所有客户。

#### 38.5 Mitigation D：绑定客户集合和数量

除了 (R,B)，还要绑定客户集合或客户数量 N，并让电路证明：

- 所有叶子是 H(clientID_i,bal_i)；
- ID 互不重复；
- 叶子数量等于公开/外部承诺的 N；
- 每个有效客户都被纳入快照。

但只公开“交易所声称 n=100”还不够，因为交易所可以声称 n=50。因此 N 应来自外部可核验的客户注册表、审计快照、签名客户集合承诺或其他公开约束。n 解决的是“无声遗漏”；唯一 ID 解决的是“重复计数/叶子复用”。

## 第九部分：Tutorial 10a —— 双向支付通道、Watchtower 与三方攻击

### 39. Watchtower 的作用

双向支付通道中，双方会不断交换带有 revocation 的承诺交易。旧状态通常仍可能被某一方广播；如果对方不在线监控链，攻击者就可能利用旧状态取走不该得的钱。

Watchtower 是代用户监控链的第三方服务：

1. 用户把旧承诺交易的识别信息和惩罚所需数据以隐私保护方式交给 watchtower；
2. watchtower 监控区块链；
3. 一旦发现对手广播已撤销/过时状态，立即提交 justice/punishment transaction；
4. 在 timelock 到期前夺回或惩罚违规方的输出。

它的价值是把“用户必须一直在线”变成“用户只需信任 watchtower 会及时观察并提交交易”。实际系统还要考虑 watchtower 自身故障、隐私泄露、费用预留和多 watchtower 冗余。

### 40. 三方支付通道为什么会失效

题设的 3-party channel 用 3-of-3 funding。以 A 的承诺交易为例：

- B 和 C 的余额是立即可取；
- A 的余额放在 7 天 timelock 后可取的输出中；
- 如果 A 之前已经更新状态，她曾把旧状态的 preimage x_A 给 B 和 C；B 或 C 可凭 x_A 立即惩罚性花费 A 的旧输出。

现在旧状态是：

~~~text
A=90, B=5, C=5
~~~

当前状态是：

~~~text
A=10, B=10, C=80
~~~

A 广播旧的承诺交易。链上旧状态会把 C 的余额从 80 退回 5，旧状态中 A 的 90 被延迟；B 已经知道 x_A，可以立即提交惩罚交易去花掉这 90。C 理论上也知道 x_A，可以竞争这笔惩罚交易，但题目允许 A、B 在 C 反应前连续发交易，因此 B 可以抢先。

最终 A+B 合计得到旧状态中的 95 BTC，而不是当前状态中的 20 BTC；C 只得到 5 BTC。两者差额：

~~~text
(95 - 20) = 75 BTC.
~~~

A 和 B 可以在链下分掉这 75 BTC。这里的根本问题不是 3-of-3 多签不够强，而是：

> 两方协作后，可以把一个本应由诚实第三方执行的惩罚竞赛变成自己控制的交易竞赛；单一旧状态的 revocation 机制没有为多方协作提供全局一致的惩罚和唯一关闭路径。

因此，两方通道的 revocation 机制不能直接、无条件地推广到多方通道。多方通道需要更复杂的状态机、全局 revocation、额外 timelock/证书或专门的多方协议。

## 第十部分：Tutorial 10b —— Bridge 与 Rollup

### 41. 两类 Bridge 的信任模型

#### 41.1 Consensus / externally verified bridge

一组外部委员会、验证者或多签观察源链，然后在目标链上签署“某事件有效”。用户必须信任：

- 委员会不会串通达到错误阈值；
- 密钥不会泄露；
- 委员会会持续运行；
- 它观察源链的方式没有被攻击。

它可以支持不同链，但引入了额外信任层。

#### 41.2 Validating / native / light-client bridge

目标链上直接验证源链的区块头、共识证明、验证者签名或 light client 规则。用户主要信任：

- 源链共识本身；
- 目标链上的 light client 实现正确；
- 源链最终性和消息可用性假设成立。

通常 validating bridge 的外部信任假设更少、保证更强，因为不需要把“源链发生了什么”交给一个额外委员会口头担保；但它更复杂、验证成本更高，仍然继承源链共识失败的风险。

### 42. Rollup 为什么把交易数据明文写到 L1

Rollup 不只需要一个 state root。把交易数据（或足以重建它的等价数据）发布到 L1 是为了：

- 让任何人重建 L2 状态；
- 让 optimistic rollup 的挑战者重新执行交易；
- 让 validity rollup 的用户在 sequencer 消失时恢复状态；
- 支持强制退出、取款和数据可用性；
- 防止协调者只发布一个无法解释的状态承诺。

根只能承诺某个状态，不能单独告诉其他人“从旧状态如何得到新状态”。

### 43. Optimistic Rollup 的交易签名

一般答案是：**需要把签名或等价的认证数据包含在可用的 L2 transaction data 中**。

原因是 fraud proof 允许任何挑战者重建并重执行状态转换，必须检查发送者确实授权了该交易；如果只发布无签名的交易内容，协调者可以伪造任意账户操作，挑战者无法独立验证。

有一个设计上的例外：如果系统愿意把“只有受信任 sequencer 的批签名才有效”当成额外信任假设，可以省略每个用户签名，但这会削弱 permissionless 验证和欺诈证明的独立性。标准、无需额外信任的 optimistic 设计应发布签名或可验证的等价认证信息。

### 44. Validity / ZK Rollup 的交易签名

就“L1 验证状态转换是否正确”而言，**不一定需要把每个 65-byte 签名原样放进 L1 calldata**。ZK proof 的电路可以在证明生成过程中验证签名，L1 verifier 只验证简洁 proof。

但要区分两个问题：

- **正确性**：签名检查可以由 ZK proof 证明；
- **可用性/退出**：用户仍可能需要交易数据或压缩后的等价数据来重建状态、恢复账户和退出。

所以“签名不必原样上链”不等于“所有交易信息都可以不发布”。是否压缩、隐藏或只发布承诺，取决于 data availability 和强制退出设计。

### 45. 中心化协调者能否阻止 Alice 提款

#### 45.1 有强制退出和数据可用性时

协调者可以暂时审查或延迟 Alice 的 L2 交易，但不能永久阻止：

- Alice 可以把 forced transaction 放入 L1 inbox；
- 任何人都能提交取款或退出请求；
- L1 合约有 escape hatch/force inclusion；
- L2 状态数据仍可被重建。

#### 45.2 没有 escape hatch 或数据不可用时

若协调者既控制唯一入口，又不发布足够数据，用户无法重建余额，也没有 L1 强制路径，那么它确实可以长期阻止提款。Rollup 的“去中心化”不能只看证明系统，还要看排序、数据发布、审查抗性和退出机制。

### 46. L1 拥堵时的 Challenge Censorship 攻击

攻击者在 L1 极度拥堵、gas 极高时发布错误状态，希望挑战者来不及把 fraud proof 纳入 L1。

一个完整缓解方案应包括：

1. **Censorship-resistant challenge inbox**：L1 合约允许任何人把挑战登记到公开队列；
2. **Forced inclusion**：验证者/排序者必须在规定 L1 区块或队列期限内包含该挑战，不能由单一 coordinator 决定是否看见；
3. **Challenge bond 与预留费用**：挑战者提前锁定 bond 或协议提供 gas escrow，避免高峰 gas 让合法挑战者完全付不起；
4. **期限延长规则**：若挑战已在 L1 队列中登记但尚未执行，或 L1 的拥堵/活性下降达到阈值，challenge window 暂停或顺延；
5. **多方监控**：任何 watcher 都可代提交挑战，不依赖一个挑战者在线；
6. **可验证的逃生路径**：即使 coordinator 审查 L2，也能把强制交易或 fraud proof 直接送到 L1。

关键思想是：不能只说“挑战期有 7 天”，而要让挑战者在这 7 天里**有一条不经过恶意协调者、可获得 L1 inclusion 的路径**。否则时间窗口只是纸面保证。
