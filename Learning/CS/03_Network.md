# 计算机网络

本页聚焦 TCP/IP 网络的分层、寻址、传输和排障。HTTP、TLS、DNS、Cookie 等 Web 协议集中在 [HTTP 与 Web 协议](04_HTTP与Web协议.md)，Socket 与 Java I/O 见 [Java I/O 与网络编程](../Backend/Java/面试题库/02_IO与网络编程.md)，Web 攻击与防御见 [应用安全](../Backend/Architecture/应用安全.md)。

## 分层模型

| TCP/IP 层 | 主要职责 | 常见协议或对象 |
| --- | --- | --- |
| 应用层 | 定义应用消息与交互 | HTTP、DNS、SSH、SMTP |
| 传输层 | 端到端进程通信 | TCP、UDP、QUIC |
| 网络层 | 跨网络寻址和路由 | IP、ICMP |
| 链路层 | 同一链路中的帧传输 | Ethernet、Wi-Fi、ARP |

OSI 七层模型更适合解释职责，TCP/IP 模型更接近互联网实际实现。排障时从应用症状出发，逐层检查解析、连接、路由和链路，不必机械从第一层开始。

## 一次数据传输

应用数据向下经过封装：

```text
应用消息
→ TCP Segment / UDP Datagram
→ IP Packet
→ Link Frame
→ 物理信号
```

接收端反向解封装。每层只承诺自己的语义：链路成功不代表 TCP 成功，TCP 成功也不代表业务处理成功。

## IP 与路由

IP 地址标识网络接口在某个网络中的位置。路由器根据目标地址和路由表选择下一跳，通常采用最长前缀匹配。

CIDR 使用前缀长度表示网络，例如 `192.168.1.0/24`。判断两个地址是否在同一子网，需要分别与子网掩码按位与并比较网络号。

IPv6 提供更大的地址空间并简化部分报文头设计，但迁移期间常与 IPv4 双栈共存。应用不应假设地址总能塞入 IPv4 字符串或 32 位整数。

## ARP 与邻居解析

IPv4 在局域网内通过 ARP 把下一跳 IP 映射为 MAC 地址。目标不在本子网时，主机解析的是默认网关的 MAC，而不是远端服务器的 MAC。

ARP 缓存减少广播，但缓存陈旧或冲突会导致局域网通信异常。IPv6 使用 Neighbor Discovery 完成类似职责。

## ICMP、ping 与 traceroute

ICMP 用于错误报告和网络诊断。`ping` 常用 Echo Request/Reply 测试可达性和往返时间；`traceroute` 利用 TTL/Hop Limit 逐跳过期来观察路径。

ping 失败不等于 HTTP 一定失败：网络可能屏蔽 ICMP，但允许 TCP/HTTPS。反过来 ping 成功也只证明部分网络路径可达，不证明端口、TLS 和应用健康。

## NAT

NAT 在地址或端口之间建立映射，使多个内网主机共享公网地址，也常用于边界控制。它会破坏端到端可达性，并给 P2P、回调和入站连接带来额外机制。

排查 NAT 问题时确认源/目标地址、端口映射、连接跟踪表和回程路径是否一致。

## TCP 与 UDP

| 维度 | TCP | UDP |
| --- | --- | --- |
| 连接 | 面向连接 | 无连接 |
| 数据语义 | 有序字节流 | 独立数据报 |
| 可靠性 | 重传、排序、流量与拥塞控制 | 由应用按需实现 |
| 头部与延迟 | 相对更高 | 较低 |
| 典型场景 | HTTP/1.1、HTTP/2、数据库连接 | DNS、实时媒体、QUIC 底层 |

UDP 不是“不可靠所以不能用”。当应用能容忍丢失、自己定义确认，或希望在用户态实现传输策略时，UDP 很合适。HTTP/3 的 QUIC 就构建在 UDP 之上。

## TCP 建立连接

三次握手的核心是双方确认彼此的发送和接收能力，并同步初始序列号：

```text
Client → SYN(seq=x)
Server → SYN(seq=y), ACK(x+1)
Client → ACK(y+1)
```

服务端收到 SYN 后维护半连接状态，第三次 ACK 后进入全连接队列。SYN Flood 会消耗半连接资源，可结合 SYN Cookies、队列调优、限流和流量清洗防护。

## TCP 半连接队列、全连接队列和 `accept()` 是什么关系？

核心回答：服务端 `listen` 后，尚未完成握手的连接处于半连接管理结构；握手完成后等待应用取走的连接进入全连接/accept 队列；`accept()` 从已完成队列取得一个连接并返回新的已连接 Socket。TCP 握手由内核协议栈完成，因此应用暂时没有调用 `accept()` 时，队列未满的连接仍可能完成握手，但得不到及时处理。

队列满时的丢弃、重传或 Cookie 行为受内核版本和配置影响。排障要同时看 SYN backlog、accept queue、监听 Socket、应用 accept 速率、文件描述符和 CPU，而不是只调大 `backlog`：应用卡住时更大的队列只是延后失败。

> 参考：[小林 Coding：TCP 半连接队列和全连接队列](https://www.xiaolincoding.com/network/3_tcp/tcp_queue.html)、[没有 accept，可以建立 TCP 连接吗](https://www.xiaolincoding.com/network/3_tcp/tcp_no_accpet.html)

## TCP 关闭连接

TCP 是全双工连接，两个方向需要分别关闭，因此常表现为四次挥手。主动关闭方进入 TIME_WAIT，用于吸收旧报文并确保最后 ACK 可以重传。

大量 TIME_WAIT 不一定是故障；要结合连接创建频率、端口范围、长连接复用和服务角色判断。随意缩短 TIME_WAIT 可能引入旧报文污染。

## TCP 可靠性

TCP 通过序列号、确认、校验和、重传、滑动窗口和拥塞控制提供可靠有序字节流。

- 流量控制保护接收方，依据接收窗口。
- 拥塞控制保护网络，依据拥塞窗口和丢包/时延信号。
- 重传处理可能丢失的 Segment。
- Keepalive 探测长时间无数据的连接，不等于业务心跳。

应用仍需请求级 Deadline，因为 TCP 连接正常不代表业务能在可接受时间内返回。

## TCP 连接的一端断电、进程崩溃或拔网线，另一端会立即知道吗？

核心回答：不一定。进程正常退出时内核通常关闭 Socket 并发送 FIN/RST；主机断电或网络中断无法保证发出任何报文，对端可能继续保持连接，直到下一次读写失败、重传超时、TCP Keepalive 或业务心跳判定失联。拔网线后若网络及时恢复，原连接甚至可能继续工作。

因此“Socket 还在 ESTABLISHED”不能证明对端业务健康。长连接协议需要业务心跳、请求 Deadline、断线重连、重复请求幂等和会话恢复；TCP Keepalive 的探测周期通常也不足以替代业务级故障检测。

常见追问：服务端没有 `listen` 时，目标主机通常会对 SYN 返回 RST 或无响应，具体受防火墙影响；已经建立的连接收到异常 SYN/FIN 时按序列号和当前状态机处理，不能背成“必然立即断开”。

> 参考：[小林 Coding：TCP 连接一端断电和进程崩溃有什么区别](https://www.xiaolincoding.com/network/3_tcp/tcp_down_and_crash.html)、[TCP Keepalive 和 HTTP Keep-Alive 是一个东西吗](https://www.xiaolincoding.com/network/3_tcp/tcp_http_keepalive.html)

## 粘包与拆包

TCP 不保存应用消息边界。一次 `write` 可能被多次读取，多次写入也可能在一次读取中返回。常见协议 framing：

- 固定长度。
- 分隔符。
- 长度字段 + Payload。
- 自描述协议格式。

所谓“粘包”不是 TCP 错误，而是应用错误地把字节流读取边界当成消息边界。

## 网络排障路径

```text
域名是否解析正确
→ 路由是否可达
→ 目标端口是否监听
→ 防火墙/安全组/NAT 是否允许
→ TCP 是否建连
→ TLS 是否握手
→ HTTP 是否返回
→ 网关和应用是否健康
→ 下游和数据库是否超时
```

常用证据：

- `dig`/`nslookup`：DNS 结果。
- `ip addr`、`ip route`：本机地址和路由。
- `ping`、`traceroute`：基础路径。
- `ss`：监听端口和连接状态。
- `nc`、`curl -v`：端口、TLS 和应用响应。
- `tcpdump`：握手、重传、RST 和报文方向。

## 场景判断

### 服务启动但请求不到

确认进程是否存活、监听的是 `127.0.0.1` 还是 `0.0.0.0`、端口是否正确、防火墙和容器端口是否开放，再检查反向代理路由。

### 连接建立后中断

区分 FIN 正常关闭、RST 异常重置、读写超时、空闲连接回收和进程崩溃。客户端、网关、服务端和下游的超时顺序应逐层递减或按预算统一设计，避免上游先超时而下游继续浪费资源。

### 网页一直转圈

从浏览器 Network 面板判断 DNS、连接、TTFB 还是内容下载慢，再沿 CDN、网关、应用、线程池、连接池和数据库向下定位。

## 验收清单

- 能解释数据经过每一层增加了什么头部和语义。
- 能计算 CIDR 网络范围并判断下一跳。
- 能解释 TCP 三次握手、四次挥手和 TIME_WAIT。
- 能区分流量控制、拥塞控制、重传和 Keepalive。
- 能解释为什么 TCP 没有应用消息边界。
- 能用分层证据定位“能 ping 但不能访问”和“端口通但请求超时”。

## 交换、广播域与 VLAN

二层交换机根据 MAC 地址表转发以太网帧。未知目标或广播帧会在同一广播域内泛洪；广播域过大可能带来无效流量和故障扩散。

VLAN 在逻辑上划分二层广播域，Trunk 链路可以携带多个 VLAN。不同 VLAN 之间通信通常需要三层路由和明确的访问控制。

环形二层拓扑可能产生广播风暴和 MAC 表震荡，因此需要生成树协议或由无环的现代网络设计避免环路。

## 子网规划

CIDR `/n` 表示网络前缀占 n 位。规划子网时需要明确：

- 网络地址和广播地址。
- 可分配主机范围。
- 默认网关。
- 是否存在地址重叠。
- 路由表中最长前缀匹配结果。

容器、VPC、VPN 和本地网络的网段重叠，是“服务存在但路由错误”的常见原因。

## 路由协议

- 静态路由：配置简单，适合规模小且拓扑稳定的网络。
- OSPF/IS-IS：内部网关协议，基于链路状态计算域内路径。
- BGP：自治系统之间交换可达前缀和策略，不只追求最短物理路径。

路由控制平面负责学习路径，数据平面负责按转发表转发报文。收敛期间可能出现短暂丢包、环路或黑洞。

## TCP 拥塞控制深化

流量控制保护接收方，拥塞控制保护网络。发送方根据拥塞窗口、接收窗口和在途数据决定可发送量。

常见机制包括：

- 慢启动：快速探测可用容量。
- 拥塞避免：更谨慎地增加发送速率。
- 快速重传/恢复：根据重复 ACK 等信号响应丢包。
- 基于丢包或带宽/RTT 估计的不同算法。

高带宽高时延网络需要足够大的带宽时延积，否则单连接无法充分利用链路。缓冲过大又可能造成 Bufferbloat 和高尾延迟。

## Socket 编程边界

服务端典型链路：

```text
socket → bind → listen → accept → read/write → close
```

客户端通常执行：

```text
socket → connect → read/write → close
```

工程上必须处理：

- 部分读写，不能假设一次调用处理完整消息。
- EINTR、EAGAIN 和连接重置。
- 读超时、写超时、连接超时和空闲超时。
- 半关闭与对端正常关闭。
- 连接池复用与失效连接。
- 应用消息边界和最大帧长度。

## 排障命令的证据链

每条命令只回答一层问题，并把时间戳与服务日志对齐；不要看到 `ping` 通就断言 HTTP 业务可用。

```bash
# 解析层：确认使用了哪个 DNS 服务器和返回地址。
dig +short example.com

# 传输/协议层：观察连接、TLS、重定向和响应头。
curl -v --connect-timeout 3 --max-time 10 https://example.com/healthz

# 链路层：只在授权环境抓包，并避免把 Cookie/Token 保存到共享目录。
sudo tcpdump -i any -nn 'host example.com and port 443'
```

命令输出应记录环境、目标、时间和脱敏规则；抓包不是默认可执行的生产操作。

## 抓包实验

建议用一个最小 HTTP 服务完成：

1. 抓取 DNS 查询。
2. 观察 TCP 三次握手。
3. 观察 TLS ClientHello/ServerHello 与证书。
4. 观察 HTTP 请求响应。
5. 主动制造超时、RST 和重传。
6. 将浏览器、`curl -v`、服务日志和 `tcpdump` 时间线对齐。

抓包内容可能含 Token、Cookie 和个人数据，应只在授权环境中操作并安全保存。

## 线上接口突然大量超时，如何区分网络、应用和下游问题？

核心回答：先用同一时间窗口把超时拆成 DNS、建连、TLS、TTFB 和响应下载，再从客户端/网关 Trace 找第一个耗时异常的跨度；连接都未建立时查解析、路由、丢包和监听，已建连但 TTFB 高时查线程池、连接池、GC、锁和下游，响应已产生但客户端未收到时再查代理缓冲、带宽、重传与客户端取消。

证据链应至少包含：`dig` 的解析结果和 TTL、`ss` 的连接状态、客户端分阶段耗时、网关与服务端同一 traceId、目标进程线程/连接池指标，以及必要时授权抓包中的 SYN 重传、RST、零窗口或应用数据时间线。`ping` 通、端口通、HTTP 200 都只能证明各自一层，不能替代业务成功证据。

常见追问：超时后服务端可能仍在执行，因此写操作要有 deadline 传播、取消、幂等键和状态查询；重试应基于错误分类和总预算，避免把局部慢请求放大成重试风暴。

## TIME_WAIT 和 CLOSE_WAIT 很多分别说明什么？可以直接调小内核参数吗？

核心回答：TIME_WAIT 通常出现在主动关闭连接的一方，用于吸收旧报文并保证最后 ACK 可重传；CLOSE_WAIT 表示对端已发 FIN，而本地应用尚未完成关闭。前者多要检查短连接创建率、连接复用和端口压力，后者优先检查代码是否遗漏关闭、线程是否卡住以及资源清理是否执行。

不能看到数量大就直接调小等待时间：高 QPS 短连接服务可能有大量正常 TIME_WAIT；贸然复用端口或缩短时间会增加旧报文干扰风险。先按本机角色、状态增长速度、源/目标四元组、文件描述符和端口范围判断是否真的耗尽，再修复连接生命周期或调整架构，最后才在压测和回滚方案下评估参数。

> 参考：[小林 Coding：计算机网络面试题](https://www.xiaolincoding.com/interview/network.html)（TIME_WAIT/CLOSE_WAIT）。网络分层与常见协议追问可延伸到[JavaGuide：计算机网络常见面试题](https://javaguide.cn/cs-basics/network/other-network-questions.html)。

## 来源与验证边界

TCP/IP、HTTP、TLS、DNS 和 QUIC 的具体行为以对应 RFC、操作系统文档和目标实现版本为准。本文的抓包步骤是排障练习，不代表可以在未授权网络上采集流量；性能结论要用固定链路、内核和负载复测。
