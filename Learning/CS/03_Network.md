# 计算机网络

本篇覆盖链路层到传输层的底层概念与排障方法。HTTP、缓存、Cookie 与 CDN 见 [HTTP 与 Web 协议](04_HTTP与Web协议.md)；TLS、证书与密码学见 [信息安全与密码学](08_信息安全与密码学.md)；I/O 多路复用、epoll 与零拷贝见 [OS](05_OS.md)；把本篇概念落到一条真实代理链路的案例见 [VPN、Clash 与 VPS 的工作原理](VPN.md)。

## 分层模型

| TCP/IP 层 | 主要职责 | 常见协议或对象 |
| --- | --- | --- |
| 应用层 | 定义应用消息与交互 | HTTP、DNS、SSH、SMTP |
| 传输层 | 端到端进程通信 | TCP、UDP、QUIC |
| 网络层 | 跨网络寻址和路由 | IP、ICMP |
| 链路层 | 同一链路中的帧传输 | Ethernet、Wi-Fi、ARP |

OSI 七层模型更适合解释职责，TCP/IP 模型更接近互联网实际实现。排障时从应用症状出发，逐层检查解析、连接、路由和链路，不必机械从第一层开始。

### OSI 七层职责速记

| 层（自下而上） | 主要职责 | 记忆提示 |
| --- | --- | --- |
| 物理层 | 传输比特流 | 电、光、无线信号 |
| 数据链路层 | 同一链路内的帧传输与寻址 | 帧、MAC |
| 网络层 | 跨网络寻址与路由 | 包、IP |
| 传输层 | 端到端传输与进程间通信 | TCP、UDP、端口 |
| 会话层 | 建立、管理和终止会话 | 管“会话” |
| 表示层 | 数据表示与格式转换，可涉及加密/解密、压缩 | 管“如何表示” |
| 应用层 | 为应用提供网络服务与协议 | HTTP、DNS、SMTP |

**易错点：**题目问“负责建立/管理/终止会话的是哪层；负责数据格式转换、加密的是哪层”，依次是**会话层、表示层**，选 **B**。OSI 是职责划分的参考模型；实际协议栈中的功能可能跨层实现，不应把模型与具体实现简单一一对应。

## 一次数据传输

应用数据向下经过封装：

```text
应用消息
→ TCP Segment / UDP Datagram
→ IP Packet
→ Link Frame
→ 物理信号
```

接收端反向解封装。每层只承诺自己的语义：链路成功不代表 TCP 成功，TCP 成功也不代表业务处理成功。

## 交换、广播域与 VLAN

二层交换机根据 MAC 地址表转发以太网帧。未知目标或广播帧会在同一广播域内泛洪；广播域过大可能带来无效流量和故障扩散。

VLAN 在逻辑上划分二层广播域，Trunk 链路可以携带多个 VLAN。不同 VLAN 之间通信通常需要三层路由和明确的访问控制。

环形二层拓扑可能产生广播风暴和 MAC 表震荡，因此需要生成树协议或由无环的现代网络设计避免环路。

## MTU 与分片

MTU 是链路层单帧可承载的最大载荷，以太网默认 1500 字节。IP 报文超过路径 MTU 时会被分片，任一分片丢失整包就要重传，分片也给 NAT、防火墙等中间设备带来处理负担，因此现代协议尽量主动避免分片：TCP 依据 MSS（MTU 减去 IP 和 TCP 头）在握手时协商分段上限，应用层应控制 UDP/DNS 等报文尺寸；IPv6 不允许中间路由器分片，只允许源端通过 PMTUD 探测路径 MTU。

工程上要特别注意隧道开销：PPPoE、WireGuard、VXLAN 等封装会占用字节数，使内层有效 MTU 变小。典型故障是“网页能打开、传大文件或 TLS 握手卡住”，处理方式是调小内侧接口的 MTU 或做 MSS clamping。

## ARP 与邻居解析

IPv4 在局域网内通过 ARP 把下一跳 IP 映射为 MAC 地址。目标不在本子网时，主机解析的是默认网关的 MAC，而不是远端服务器的 MAC。

ARP 缓存减少广播，但缓存陈旧或冲突会导致局域网通信异常。IPv6 使用 Neighbor Discovery 完成类似职责。

## IP 与路由

IP 地址标识网络接口在某个网络中的位置。路由器根据目标地址和路由表选择下一跳，通常采用最长前缀匹配。

CIDR 使用前缀长度表示网络，例如 `192.168.1.0/24`。判断两个地址是否在同一子网，需要分别与子网掩码按位与并比较网络号。

IPv6 提供更大的地址空间并简化部分报文头设计，但迁移期间常与 IPv4 双栈共存。应用不应假设地址总能塞入 IPv4 字符串或 32 位整数。

## 子网规划

CIDR `/n` 表示网络前缀占 n 位。规划子网时需要明确：

- 网络地址和广播地址。
- 可分配主机范围。
- 默认网关。
- 是否存在地址重叠。
- 路由表中最长前缀匹配结果。

容器、VPC、VPN 和本地网络的网段重叠，是“服务存在但路由错误”的常见原因。

## 路由协议

- 静态路由：配置简单，适合规模小且拓扑稳定的网络。
- OSPF/IS-IS：内部网关协议，基于链路状态计算域内路径。
- BGP：自治系统之间交换可达前缀和策略，不只追求最短物理路径。

路由控制平面负责学习路径，数据平面负责按转发表转发报文。收敛期间可能出现短暂丢包、环路或黑洞。

## ICMP、ping 与 traceroute

ICMP 用于错误报告和网络诊断。`ping` 常用 Echo Request/Reply 测试可达性和往返时间；`traceroute` 利用 TTL/Hop Limit 逐跳过期来观察路径。

ping 失败不等于 HTTP 一定失败：网络可能屏蔽 ICMP，但允许 TCP/HTTPS。反过来 ping 成功也只证明部分网络路径可达，不证明端口、TLS 和应用健康。

## NAT

NAT 在地址或端口之间建立映射，使多个内网主机共享公网地址，也常用于边界控制。它会破坏端到端可达性，并给 P2P、回调和入站连接带来额外机制。

排查 NAT 问题时确认源/目标地址、端口映射、连接跟踪表和回程路径是否一致。

Linux 的 NAT 依赖 netfilter 的连接跟踪表（conntrack）。表满时新连接被直接丢弃，`dmesg` 出现 `nf_conntrack: table full, dropping packet`，表现为随机性的新建连接失败；处理方式包括对不需要状态跟踪的流量用 NOTRACK 豁免、调大 `nf_conntrack_max`、缩短 established 超时，超大连接量场景改用无状态转发。当前用量看 `/proc/sys/net/netfilter/nf_conntrack_count` 与 `nf_conntrack_max`。

## netfilter 与 iptables

iptables 在内核 netfilter 的钩子上实现包过滤与改写。表定义功能：raw 豁免连接跟踪，mangle 修改报文字段，nat 做地址/端口转换，filter 做过滤；链定义时机：PREROUTING、INPUT、FORWARD、OUTPUT、POSTROUTING。入站包走 PREROUTING → INPUT，转发包走 PREROUTING → FORWARD → POSTROUTING，本机发出走 OUTPUT → POSTROUTING；同一条链内按 raw → mangle → nat → filter 的优先级匹配。只观测不拦截可以用计数器或 LOG 目标。nftables 是其替代品，语法更统一，排障前先确认系统用的是哪一套；云安全组工作在宿主机/网关层，与本机规则是两道关。

## DNS

域名解析是网络排障的第一环。解析通常依次经过浏览器与系统缓存、本地递归解析器，再按需访问根、顶级域和权威服务器：递归解析器代替客户端完成整条查询链，权威服务器给出所属区域的最终答案。

排障时先确认实际使用的解析器、返回的地址和 TTL，再判断是缓存未刷新、解析污染还是配置错误。记录类型、传输方式（UDP/TCP 与 DoH/DoT）和缓存运维细节见 [HTTP 与 Web 协议](04_HTTP与Web协议.md)。

## 负载均衡与高可用

负载均衡分四层与七层。四层（LVS/云负载均衡）在内核按 IP 和端口转发，性能高但不理解应用协议；七层（Nginx/HAProxy/网关）终止连接后按 URL、Header 路由，能做 TLS 终止、重写和灰度发布，成本更高。常见组合是 LVS 做四层入口、Nginx 做七层、keepalived 保证均衡器自身高可用。

| LVS 模式 | 改写内容 | 响应路径 | 主要约束 |
| --- | --- | --- | --- |
| NAT | 目标 IP/端口（DNAT/SNAT） | 响应经过均衡器 | 均衡器易成带宽瓶颈；支持端口映射 |
| DR | 帧的 MAC 地址 | 真实服务器直接返回客户端 | 同一二层；真实服务器配 VIP 并抑制 ARP |
| TUN | IP 隧道封装 | 真实服务器解封后直接返回 | 真实服务器需支持隧道，可跨网段 |

Nginx 常用负载均衡算法有轮询、加权轮询、ip_hash、least_conn 和一致性哈希；会话保持优先用应用层共享存储或粘性 Cookie，而不是依赖 ip_hash。keepalived 基于 VRRP：一组机器共享 VIP，按优先级选出 MASTER 响应 ARP 和网关流量，其余为 BACKUP，MASTER 失联后 BACKUP 超时接管；它还常用来管理 LVS 的健康检查与转发规则。脑裂指 MASTER 与 BACKUP 都存活但心跳中断（VRRP 组播被防火墙拦截、心跳链路故障），双方同时持有 VIP 造成 ARP 漂移和流量分裂；预防靠独立心跳链路、放行 VRRP（IP 协议号 112）和资源仲裁，切换后要发免费 ARP 让交换机刷新 MAC 表项。

## TCP 与 UDP

| 维度 | TCP | UDP |
| --- | --- | --- |
| 连接 | 面向连接 | 无连接 |
| 数据语义 | 有序字节流 | 独立数据报 |
| 可靠性 | 重传、排序、流量与拥塞控制 | 由应用按需实现 |
| 头部与延迟 | 相对更高 | 较低 |
| 典型场景 | HTTP/1.1、HTTP/2、数据库连接 | DNS、实时媒体、行情组播、QUIC 底层 |

UDP 不保证数据一定送达、按序到达或只到达一次；UDP 不是“不可靠所以不能用”。当应用能容忍丢失、自己定义确认，或希望在用户态实现传输策略时，UDP 很合适。行情组播可通过 UDP 向多个订阅者低延迟分发数据，但若业务不能容忍丢失，需要由应用检测缺口并通过补发或重新同步等机制恢复。HTTP/3 的 QUIC 就构建在 UDP 之上。

要在 UDP 上实现可靠传输，需要在应用层或用户态补齐序列号与确认、超时与快速重传、滑动窗口式的流量/拥塞控制和按序重组；工程上优先用成熟方案（QUIC、KCP、WebRTC 数据通道）而不是自行造轮子，动机通常是绕开 TCP 队头阻塞、摆脱内核协议栈约束、获得可定制的拥塞控制。实时音视频等场景也可以放弃完全可靠，只做前向纠错和抖动缓冲。

## TCP 建立连接

三次握手的核心是双方确认彼此的发送和接收能力，并同步初始序列号：

```text
Client → SYN(seq=x)
Server → SYN(seq=y), ACK(x+1)
Client → ACK(y+1)
```

两次握手无法达成这个目标：网络中滞留的历史 SYN 到达服务端时，服务端会直接建立连接并分配资源，而客户端根本不使用这条连接；第三次 ACK 给了客户端拒绝历史连接的机会，也让服务端确认自己发出的 SYN+ACK 已被收到。初始序列号随机生成，既防止第三方猜测伪造，也避免与同四元组旧连接的报文序列号重叠。第三次 ACK 可以携带数据，前两次不能；客户端重复发送 SYN 时，服务端按状态机重发 SYN+ACK，不会重复建连。

服务端收到 SYN 后进入半连接队列，完成第三次 ACK 后进入全连接队列，`accept()` 从全连接队列取出已完成的连接。握手由内核协议栈完成，因此应用暂时没有调用 `accept()` 时，队列未满的连接仍能完成握手，只是得不到及时处理。队列满时的丢弃、重传或 SYN Cookie 行为受内核版本和配置影响；排障要同时看 SYN backlog、accept 队列、应用 accept 速率、文件描述符和 CPU，而不是只调大 `backlog`——应用卡住时更大的队列只是延后失败。

SYN Flood 会消耗半连接资源，可结合 SYN Cookies、队列调优、限流和流量清洗防护。

## TCP 关闭连接

TCP 是全双工连接，两个方向需要分别关闭，因此常表现为四次挥手。收到 FIN 的一端可能还有数据没发完，所以它的 ACK 和自己的 FIN 通常不能合并，只有收到 FIN 后立即关闭的场景才合并成三次。主动关闭方进入 TIME_WAIT，用于吸收旧报文并确保最后 ACK 可以重传；CLOSE_WAIT 表示对端已发 FIN，而本地应用尚未完成关闭。

TIME_WAIT 要等 2MSL（两倍报文最大生存时间）：一是最后一个 ACK 若丢失，对方重传 FIN 时本方仍在连接中，可以重发 ACK，避免对方停在 LAST_ACK 反复重传；二是让本连接的旧报文在网络中自然消亡，避免污染复用相同四元组的新连接。FIN 丢失则对端停在 FIN_WAIT_2 或 LAST_ACK，依赖超时或 RST 收敛。

大量 TIME_WAIT 不一定是故障；要结合连接创建频率、端口范围、长连接复用和服务角色判断。CLOSE_WAIT 偏多时优先检查代码是否遗漏关闭、线程是否卡住以及资源清理是否执行。

不能看到数量大就直接调小等待时间：高 QPS 短连接服务可能有大量正常 TIME_WAIT；贸然复用端口或缩短时间会增加旧报文干扰风险。先按本机角色、状态增长速度、源/目标四元组、文件描述符和端口范围判断是否真的耗尽，再修复连接生命周期或调整架构，最后才在压测和回滚方案下评估参数。

## TCP 可靠性

TCP 通过序列号、确认、校验和、重传、滑动窗口和拥塞控制提供可靠有序字节流。

- 流量控制保护接收方，依据接收窗口。
- 拥塞控制保护网络，依据拥塞窗口和丢包/时延信号。
- 重传处理可能丢失的 Segment。
- Keepalive 探测长时间无数据的连接，不等于业务心跳。

重传有两种触发方式：超时重传在 RTO 到期后补发，快速重传在收到若干重复 ACK 时立即补发；SACK 让接收方报告已收到的不连续区间，避免不必要的重传。接收窗口降为 0 时发送方停发并周期发送零窗口探测，恢复依赖应用及时读取数据。发送端的 Nagle 算法合并小包以降低开销，与接收端延迟确认叠加可能放大交互式业务的延迟，低延迟场景可用 `TCP_NODELAY` 关闭。

“连接还在 ESTABLISHED”不等于对端业务健康：进程正常退出时内核通常发送 FIN/RST，主机断电或网络中断则不会发出任何报文，对端可能长期保持连接，直到下一次读写失败、重传超时或保活探测判定失联；拔网线后网络及时恢复，连接甚至能继续工作。因此长连接需要业务心跳、请求 Deadline、断线重连、重复请求幂等和会话恢复。另需区分两种“保活”：TCP Keepalive 是内核探测机制，默认周期约 2 小时起，不适合业务级故障检测；HTTP Keep-Alive 是应用层连接复用，解决的是“尽量别关连接”。

发送方可发送的数据量由拥塞窗口、接收窗口和在途数据共同决定。常见拥塞控制机制包括：

- 慢启动：快速探测可用容量。
- 拥塞避免：更谨慎地增加发送速率。
- 快速重传/恢复：根据重复 ACK 等信号响应丢包。
- 基于丢包或带宽/RTT 估计的不同算法。

高带宽高时延网络需要足够大的带宽时延积，否则单连接无法充分利用链路。缓冲过大又可能造成 Bufferbloat 和高尾延迟。

应用仍需请求级 Deadline，因为 TCP 连接正常不代表业务能在可接受时间内返回。

## 粘包与拆包

TCP 不保存应用消息边界。一次 `write` 可能被多次读取，多次写入也可能在一次读取中返回。常见协议 framing：

- 固定长度。
- 分隔符。
- 长度字段 + Payload。
- 自描述协议格式。

所谓“粘包”不是 TCP 错误，而是应用错误地把字节流读取边界当成消息边界。

## Socket 编程边界

服务端典型链路：

```text
socket → bind → listen → accept → read/write → close
```

客户端通常执行：

```text
socket → connect → read/write → close
```

工程上必须处理：

- 部分读写，不能假设一次调用处理完整消息。
- EINTR、EAGAIN 和连接重置。
- 读超时、写超时、连接超时和空闲超时。
- 半关闭与对端正常关闭。
- 连接池复用与失效连接。
- 应用消息边界和最大帧长度。

单机能承载的连接数理论上由四元组决定，对同一监听地址和端口约为客户端 IP 数 × 客户端端口数；实际瓶颈是文件描述符上限（`ulimit -n`、`fs.file-max`）、每连接的内核结构与收发缓冲区内存、CPU 和 conntrack。端口号 65535 只限制一个客户端 IP 对同一目标地址与端口的出向连接数，不是服务端连接上限；客户端端口耗尽可用 `ip_local_port_range` 扩范围、`tcp_tw_reuse` 复用时间等待端口，根本办法是长连接复用与连接池。

本篇关注调用序列与网络错误语义；I/O 多路复用（select/poll/epoll）、Reactor 模型和零拷贝等系统侧实现见 [OS](05_OS.md)。

## 排障

### 分层排障路径

```text
域名是否解析正确
→ 路由是否可达
→ 目标端口是否监听
→ 防火墙/安全组/NAT 是否允许
→ TCP 是否建连
→ TLS 是否握手
→ HTTP 是否返回
→ 网关和应用是否健康
→ 下游和数据库是否超时
```

### 命令与证据链

每条命令只回答一层问题，并把时间戳与服务日志对齐；不要看到 `ping` 通就断言 HTTP 业务可用。

常用证据：

- `dig`/`nslookup`：DNS 结果。
- `ip addr`、`ip route`：本机地址和路由。
- `ping`、`traceroute`：基础路径。
- `ss`：监听端口和连接状态。
- `nc`、`curl -v`：端口、TLS 和应用响应。
- `tcpdump`：握手、重传、RST 和报文方向。

```bash
# 解析层：确认使用了哪个 DNS 服务器和返回地址。
dig +short example.com

# 传输/协议层：观察连接、TLS、重定向和响应头。
curl -v --connect-timeout 3 --max-time 10 https://example.com/healthz

# 链路层：只在授权环境抓包，并避免把 Cookie/Token 保存到共享目录。
sudo tcpdump -i any -nn 'host example.com and port 443'
```

命令输出应记录环境、目标、时间和脱敏规则；抓包不是默认可执行的生产操作。

### 场景判断

#### 服务启动但请求不到

确认进程是否存活、监听的是 `127.0.0.1` 还是 `0.0.0.0`、端口是否正确、防火墙和容器端口是否开放，再检查反向代理路由。

#### 网卡丢包

先分段确认丢在本机、链路还是对端。本机沿收包路径（网卡 DMA → 硬中断 → 软中断 → 协议栈 → socket 队列）查统计：`ip -s link` / `netstat -i` 看 RX errors/dropped；`ethtool -S eth0` 看网卡队列是否溢出（ring buffer 满、missed），可调大队列或开启多队列/RPS 分流；软中断处理不过来时看 ksoftirqd 的 CPU 占用和 `/proc/net/softnet_stat` 的 dropped 列；再查 UDP 接收缓冲不足（`netstat -su`）、conntrack 表满和防火墙规则计数。链路和对端用多点 `tcpdump` 对比：本机发出但对端没收到、对端回复但本机没收到，分别指向出向、链路和入向问题。

#### 连接建立后中断

区分 FIN 正常关闭、RST 异常重置、读写超时、空闲连接回收和进程崩溃。客户端、网关、服务端和下游的超时顺序应逐层递减或按预算统一设计，避免上游先超时而下游继续浪费资源。

#### 网页一直转圈

从浏览器 Network 面板判断 DNS、连接、TTFB 还是内容下载慢，再沿 CDN、网关、应用、线程池、连接池和数据库向下定位。

#### 线上接口突然大量超时

先用同一时间窗口把超时拆成 DNS、建连、TLS、TTFB 和响应下载，再从客户端/网关 Trace 找第一个耗时异常的跨度：连接未建立时查解析、路由、丢包和监听；已建连但 TTFB 高时查线程池、连接池、GC、锁和下游；响应已产生但客户端未收到时再查代理缓冲、带宽、重传与客户端取消。`ping` 通、端口通、HTTP 200 都只能证明各自一层，不能替代业务成功证据。超时后服务端可能仍在执行，写操作要有 deadline 传播、取消、幂等键和状态查询；重试应基于错误分类和总预算，避免把局部慢请求放大成重试风暴。

### 抓包实验

建议用一个最小 HTTP 服务完成：

1. 抓取 DNS 查询。
2. 观察 TCP 三次握手。
3. 观察 TLS ClientHello/ServerHello 与证书。
4. 观察 HTTP 请求响应。
5. 主动制造超时、RST 和重传。
6. 将浏览器、`curl -v`、服务日志和 `tcpdump` 时间线对齐。

抓包内容可能含 Token、Cookie 和个人数据，应只在授权环境中操作并安全保存。
