# 信息安全与密码学

本篇负责安全的通用原理和密码学边界；Web 应用攻击与防御见 [应用安全](../Backend/Architecture/应用安全.md)，Agent 特有威胁见 [Agent 安全与威胁建模](../Agent/07_Agent安全与威胁建模.md)。

## 1. 安全目标与威胁模型

经典目标：

- 机密性：未授权主体不能读取。
- 完整性：未授权主体不能篡改。
- 可用性：合法主体能够在需要时使用。
- 真实性：能够确认主体或数据来源。
- 可追责性：关键动作有不可混淆的审计证据。

威胁建模先列资产、主体、信任边界、入口、攻击者能力和影响，再选择控制措施。安全不是功能清单，而是对明确攻击假设的风险控制。

## 2. 随机数、熵与 Nonce

密码学操作依赖不可预测的随机数。普通伪随机数适合模拟，不一定适合生成密钥、Token 或 Nonce。

- 密钥必须来自密码学安全随机源。
- Nonce 要满足协议要求：有的要求唯一，有的还要求不可预测。
- 盐值用于让相同密码产生不同派生结果，不需要保密，但应随机且每个密码独立。
- 初始化向量 IV 的唯一性/随机性要求取决于具体加密模式。

不要自行拼接时间戳、用户 ID 和普通随机数生成安全 Token。

## 3. Hash、MAC 与密码存储

密码学 Hash 提供固定长度摘要，并追求抗原像、抗第二原像和抗碰撞。

Hash 只能检测变化，不能证明消息来自谁。需要共享密钥认证消息时使用 MAC/HMAC。

密码不能直接用快速 Hash 保存。应使用专门的密码哈希/KDF，例如 Argon2、scrypt、bcrypt 或 PBKDF2，并配置足够成本、独立盐值和升级策略。

## 4. 对称加密

对称加密使用同一密钥加密和解密，速度快，适合大量数据。优先使用经过验证的 AEAD 方案，例如 AES-GCM 或 ChaCha20-Poly1305，同时提供机密性和完整性。

常见错误：

- 重用不允许重复的 Nonce。
- 使用 ECB 暴露数据模式。
- 只加密不认证，导致篡改不可检测。
- 自行设计 Padding 或组合算法。
- 把密钥写入代码、镜像或日志。

## 5. 非对称加密与数字签名

公钥和私钥承担不同角色：

- 公钥加密、私钥解密：保护只有私钥持有者能读取的数据。
- 私钥签名、公钥验证：证明消息由私钥控制者签发且未被篡改。
- 密钥交换：协商共享秘密，之后通常使用对称加密传输数据。

签名不等于加密，也不自动证明现实身份；必须知道公钥属于谁、信任关系如何建立。

## 6. 证书与 PKI

证书把主体身份、域名和公钥绑定，并由证书颁发机构签名。验证证书通常包括：

- 构建并验证证书链。
- 检查有效期。
- 检查域名。
- 检查用途和算法。
- 按系统策略处理吊销状态。

信任根一旦被错误加入，攻击者可能签发看似合法的证书。证书自动续期也要监控失败和部署是否生效。

## 7. TLS 基本链路

TLS 通常完成：

1. 协商协议版本和密码套件。
2. 服务端提供证书。
3. 客户端验证证书与域名。
4. 双方执行密钥交换。
5. 使用派生出的会话密钥进行认证加密。

现代 TLS 常通过临时密钥交换提供前向保密：长期私钥未来泄漏时，过去抓取的会话仍不应被直接解密。

HTTPS 保护传输过程，不代表服务端可信、输入安全或数据落盘后仍加密。

## 8. 身份、认证与授权

- 身份识别：你声称是谁。
- 认证：如何证明。
- 授权：认证后能做什么。
- 审计：实际做了什么。

多因素认证要求不同类型的因素，而不是两个同类密码。Session、JWT、OAuth 2.0 和 OIDC 解决的层次不同；Token 必须验证签名、签发者、受众、有效期和权限范围。

授权应在可信服务端执行，采用默认拒绝和最小权限。资源级授权不能只依赖“用户已登录”。

## 9. 密钥与 Secret 生命周期

完整生命周期包括生成、分发、存储、使用、轮换、吊销、备份、审计和销毁。

工程原则：

- 不在代码、镜像、前端包或日志中保存 Secret。
- 工作负载使用短期身份和最小权限。
- 区分数据加密密钥和密钥加密密钥。
- 轮换要支持新旧密钥过渡并可撤销。
- 泄漏后不仅替换密钥，还要评估历史访问和派生凭证。

## 10. 系统与容器安全

系统安全边界包括用户、进程、文件权限、系统调用、网络和内核。容器主要依赖 namespace、cgroup、capability 和安全策略隔离，并不等同于虚拟机边界。

基本措施：

- 非 root 运行，删除不需要的 capability。
- 只读根文件系统，限制可写路径。
- 限制系统调用和网络访问。
- 固定基础镜像和依赖版本。
- 对宿主机接口、Docker Socket 和特权容器保持高风险判断。

## 11. 软件供应链安全

供应链风险来自依赖、构建环境、CI 身份、制品仓库和发布流程。

建议形成：

```text
来源确认 → 版本锁定 → 依赖扫描 → 隔离构建
→ 生成 SBOM → 制品签名 → 部署验证 → 漏洞响应
```

扫描工具只能发现已知模式；仍需 Code Review、权限隔离、构建可复现性和运行时控制。

## 12. 安全测试

不同方法覆盖不同问题：

- SAST：静态检查源码和数据流。
- DAST：从运行中的外部接口测试。
- SCA：检查第三方组件和许可证。
- Secret Scan：发现误提交凭证。
- Fuzzing：用大量异常输入寻找崩溃和边界错误。
- 渗透测试：在授权范围内验证组合攻击路径。

安全测试必须定义授权、目标、时间和数据边界，不能对未授权系统执行攻击性验证。

## 13. 常见失败认知

- Base64 是编码，不是加密。
- Hash 不是加密，通常不可逆。
- “使用 HTTPS”不等于应用安全。
- JWT 不等于加密，也不天然可撤销。
- 加密数据但明文记录日志，仍然可能泄漏。
- 内网不是可信边界。
- 算法公开并不会削弱现代密码系统；安全应依赖密钥而非算法保密。

## 最小实践

1. 为一个登录与文件上传服务画信任边界。
2. 用标准库实现 HMAC 签名并验证篡改会失败。
3. 检查一个 TLS 证书的域名、链和有效期。
4. 为项目建立 Secret、依赖和制品的供应链检查清单。
5. 设计一次密钥泄漏后的轮换、吊销和审计流程。

## 验收清单

- 能区分 Hash、MAC、加密和签名。
- 能解释证书链、TLS 和前向保密的作用。
- 能说明密码为什么不能使用普通快速 Hash 存储。
- 能为密钥写出完整生命周期。
- 能从威胁模型选择控制，而不是只罗列安全名词。
