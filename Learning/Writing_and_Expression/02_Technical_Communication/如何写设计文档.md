# 如何写设计文档

设计文档帮助参与者判断方案是否适合当前问题，并保存选择理由。先说明问题和约束，再解释方案、替代选择及验证方式。

## 问题与约束决定讨论范围

交代现有行为、受影响的对象，以及为什么需要改变。目标描述希望出现的结果，非目标说明本次暂不处理的事项。

时间、性能、成本、兼容性、团队能力和上线风险会限制可选方案。把这些条件写出来，评审者才能按相同标准讨论。

## 方案说明需要哪些内容

| 部分 | 要回答的问题 |
|---|---|
| 背景与问题 | 现状哪里不满足需要，有什么证据？ |
| 目标与非目标 | 本次解决到什么程度？ |
| 约束 | 时间、资源、兼容性和风险有哪些限制？ |
| 方案 | 请求、数据和状态怎样流动，模块与接口怎样分工？ |
| 替代方案 | 为什么选当前方案，其他选择有哪些成本？ |
| 失败与恢复 | 哪些条件下会失败，怎样发现和恢复？ |
| 实施与验证 | 怎样分阶段修改、观察效果和回退？ |

小型变更可以合并章节；复杂设计可把接口细节和计算放入附件。内容深度取决于读者与决策，不必凑齐固定篇幅。

## 示例：把同步导出改为后台任务

假设大文件导出占用请求过久。文档先给出复现条件与超时现象，再比较继续优化同步处理、限制文件规模和改为后台任务。

若选择后台任务，说明请求如何创建任务、用户如何查询状态、处理失败后怎样重试，以及结果如何授权访问。同时写出代价：用户需要等待，系统增加任务存储、执行与查询维护。

验证要观察任务是否最终完成，不能只看接口更快返回。上线前还需考虑新旧流程的过渡，失败时怎样停止放量，以及已经创建的任务由谁继续处理。

## 让评审与后续维护使用同一份依据

说明选择当前方案的理由，并比较替代方案的代价。未确认的前提列为开放问题，不用确定语气掩盖缺口。

评审后记录决定与变化。后续维护者需要看到当时的条件，才能判断原方案是否仍适用；如果约束改变，应更新或补充决策记录。
