# 专业技术文档与困难沟通

本篇覆盖 RFC、ADR、API/SDK 文档、Runbook、事故通报、Postmortem、数据表达、管理层摘要和高冲突沟通。

## 1. 文档先服务决策

写前明确：

- 谁要读？
- 读完要判断或执行什么？
- 已知和未知是什么？
- 需要多大细节？
- 何时过期？

同一技术事实面对工程师、管理者和用户，应使用不同抽象层级，但不能改变事实。

## 2. RFC

RFC 适合需要跨团队评审的较大变更：

```text
摘要 → 背景/问题 → 目标/非目标
→ 约束 → 候选方案 → 推荐方案
→ 数据/API/流程 → 失败与安全
→ 迁移/发布/回滚 → 验证
→ 未决问题
```

RFC 在决策前开放讨论；批准后记录结论和变化。不要把已经决定的方案伪装成征求意见。

## 3. ADR

ADR 更短，记录一项架构决策：

```text
状态、日期、背景、决策、替代方案、
正负影响、验证和复审条件
```

后续改变时新增 ADR 取代旧记录，而不是抹除历史。

## 4. API 文档

至少包含：

- 认证与权限。
- 请求、响应和字段语义。
- 幂等、分页、限流和版本。
- 错误码与恢复。
- 示例和边界。
- 变更与弃用。

示例必须通过自动测试或从 Schema 生成，避免文档与实现漂移。

## 5. SDK 文档

SDK 读者需要：

- 安装和兼容版本。
- 最小成功示例。
- 配置、超时和重试。
- 错误类型。
- 生命周期与资源关闭。
- 线程/异步安全。
- 升级迁移。

不要只包装 API 而隐藏关键失败语义。

## 6. Runbook

Runbook 面向值班和恢复：

```text
触发症状 → 影响判断 → 安全检查
→ 诊断命令/证据 → 缓解步骤
→ 验证恢复 → 升级联系人
→ 回滚/清理
```

命令标注环境、权限、预期输出和风险。高危动作需要确认和备份。

## 7. 事故首次通报

首次通报只需要：

- 发生时间和影响。
- 已知/未知。
- 当前缓解动作。
- 下一次更新时间。
- 负责人和沟通渠道。

不要在事实未清时猜根因或归责。

## 8. Postmortem

结构：

- 摘要与影响。
- 时间线。
- 检测和响应。
- 技术与组织条件。
- 哪些控制有效/失效。
- 根因和促成因素。
- 修复项、负责人和期限。

“人为错误”不是终点，要继续问系统为何允许、为何未检测、为何难恢复。

## 9. 数据与图表

先给结论，再给图表证据。图表必须注明：

- 指标定义和单位。
- 时间范围。
- 样本与过滤。
- 基线或对照。
- 不确定性。
- 来源。

避免截断坐标轴、双轴误导、只选有利时间窗口和把相关写成因果。

## 10. 管理层技术摘要

一页内回答：

```text
要做什么 → 为什么现在做
→ 业务影响 → 选项与成本
→ 主要风险 → 推荐决策
→ 需要谁批准什么
```

技术细节放附录，正文保留影响决策的机制。

## 11. 异议与反对意见

先准确复述对方关切，再区分：

- 事实分歧。
- 假设分歧。
- 价值/优先级分歧。
- 风险承受差异。
- 信息或权责不对称。

回应证据和取舍，不把异议者当阻力。

## 12. 困难沟通

使用可观察事实而非人格判断：

```text
具体行为/事件 → 影响 → 需要
→ 对方视角 → 共同方案 → 跟进
```

涉及绩效、骚扰、安全或法律风险时，保留事实记录并使用正式组织渠道。

## 13. 跨团队协作

写清：

- 共同目标。
- 接口与所有权。
- 依赖日期。
- 风险与升级路径。
- 决策人。
- 完成定义。

会议后发送决策、行动项和未决问题，而不是只发录屏。

## 14. 文档生命周期

每篇重要文档标记 Owner、状态、版本、最后核对日期和失效条件。过期文档应归档或明确警告，不能继续作为执行依据。

## 15. 练习

从真实项目产出：

1. 一份 RFC。
2. 一条 ADR。
3. 一个 API/SDK Quickstart。
4. 一份故障 Runbook。
5. 一份事故通报和 Postmortem。
6. 一页管理层摘要。

每项保留原稿、修改稿、反馈和实际使用结果。

## 验收清单

- 文档明确读者、决策和有效期。
- 方案包含替代、失败、迁移与回滚。
- Runbook 可由非作者执行。
- 事故文档区分事实、推断和行动。
- 图表可追溯口径与来源。
- 困难沟通记录事实、影响、请求和跟进。
