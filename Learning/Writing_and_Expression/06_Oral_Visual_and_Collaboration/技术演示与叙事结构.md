# 技术演示与叙事结构

技术演示的目标不是把所有细节讲完，而是让听众在有限时间内理解问题、证据、取舍和下一步行动。

## 1. 先写演示合同

~~~text
听众：
他们已经知道什么：
需要做的决定：
可用时间：
必须证明的事实：
不能展开的细节：
风险和可能质疑：
演示后的行动：
~~~

同一个系统，对管理者讲价值、风险和资源，对工程师讲边界、数据和验证，对用户讲任务和反馈，不应使用同一套顺序。

## 2. 推荐结构

1. 结论或要做的决定。
2. 背景和真实问题。
3. 约束、目标和非目标。
4. 方案与关键机制。
5. 证据、演示和失败路径。
6. 取舍、风险和未解决问题。
7. 请求反馈或明确行动。

先给地图，再进入细节。演示失败时要能退回静态证据，不把网络或现场操作当成唯一证明。

## 3. 演示证据

- 运行前说明输入、环境和预期。
- 运行中展示关键状态，而不是只展示最终成功页面。
- 运行后解释日志、指标、错误和边界。
- 对不可复现的部分标明假设。

## 4. 准备真实演示时

用同一个 Go 服务或 Agent Runtime 做三版演示：

- 三分钟：只讲问题、结果和风险。
- 十分钟：补系统边界、关键取舍和故障。
- 三十分钟：加入代码、指标和现场问答。

## 真实演示时检查

听众能复述问题、方案、证据和下一步；你能在没有隐藏失败的情况下回答“为什么这样设计”和“如果失败怎么办”。
