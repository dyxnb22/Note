# Learning 维护规范

这份规范定义知识库的完成标准。目标不是让文件数量更多，而是让学习路径足够轻、正文能够按需使用、局部维护不会牵动整个知识库。

## 两个互不混淆的层次

| 层次 | 回答的问题 | 更新频率 |
|---|---|---|
| 总索引与主题索引 | 某个目标应该从哪里进入？ | 结构变化时更新 |
| 主题正文与实践 | 概念是什么、项目如何验证？ | 出现新理解、证据或版本变化时更新 |

学习路线只在主题入口或实践 README 中说明，不单独维护个人完成度。完整知识关系依靠相对链接和反向链接自然形成，不手工维护一张覆盖全库的知识图谱。

## 文档类型

| 类型 | 作用 | 最低要求 |
|---|---|---|
| `map` | 说明学习路径、主题边界和先修关系 | 不复制正文；每个链接说明为什么值得进入 |
| `concept` | 解释一个可复用概念或机制 | 问题、最小心智模型、机制、边界、一个必要例子、关联主题；不强制练习 |
| `guide` | 帮助完成一个任务 | 前置条件、步骤、验证、失败处理；只保留完成任务需要的示例 |
| `reference` | 提供稳定查询入口 | 范围清晰、结构可扫描、标明版本边界 |
| `case` | 用事实验证抽象 | 背景、约束、取舍、证据、结果和不可验证部分 |
| `practice` | 承载可运行练习 | 环境、运行命令、预期结果、失败路径和实验记录 |

只有标题、两段摘要或通用练习的内容不是独立文档：应合并到模块主文档，或明确标为待发展的 seed。

## 问答型题库标准

语言、后端、AI 和 Agent 的面试题库统一采用“题目 → 结论 → 机制 → 边界 → 追问/验证”的结构：

- 每个核心问题使用一个疑问句标题，答案紧跟在题目下面，不把题目和答案拆成两张页面。
- 先给可以直接复述的结论，再解释为什么；涉及实现时补充关键数据结构、调用链或最小代码片段。
- 每道题至少补一个边界、反例、故障场景或追问，避免只停留在名词解释。
- 需要动手确认的内容放入“验证”小节，并链接到实践、案例或官方文档；代码是验证手段，不替代答案。
- 同一个机制只保留一个主答案。其他语言或场景只写差异与应用角度，并链接到主答案，避免维护多份互相漂移的八股。

题库的 README、复习路线和主题速答卡属于导航辅助页，不强行改成逐题正文。概念、指南、案例和实践继续遵循各自文档类型；“问答优先”只约束题库和速答内容，不把整个 Learning 目录改成面试清单。

## 内容标准

一篇成熟主题文档至少回答以下问题中的四个：

1. 它解决什么问题，和相邻概念有什么边界？
2. 关键机制或因果链是什么？
3. 哪些前提下有效，哪些情况下会失效？
4. 有什么真实例子、反例或可运行示例？
5. 如果需要验证，证据位于哪个实践、案例或来源？
6. 结论来自哪里，哪些信息可能变化？

不要为了套模板而保留空泛章节。概念正文不默认附带编码练习；已有真实项目覆盖时，只链接到对应实践。没有独立内容时，宁可把相关结论合并为一个紧凑段落。

## 学习与维护的边界

- 术语未解释、关键前置缺失、内容矛盾或链接失效会阻塞当前理解：立即修正。
- 表达略显生硬、例子不够好、编号和标签不统一：记下来，下次使用该主题时再顺手修正，不中断学习。
- 每次只维护当前主题及直接依赖；不因为一处修改顺手巡检所有目录。
- 已经掌握的内容可以通过项目说明、代码、决策或复盘确认，不要求重新阅读和重新练习。
- 新主题先进入当前项目或 `Resources`；只有形成可复用结论后才进入长期正文。

## 来源与时效

- 稳定基础知识优先引用教材、标准、论文或官方文档。
- API、模型、框架、监管、税制、交易规则和健康建议必须记录核对日期。
- 个人总结可以保留，但应与事实来源、案例证据和已复现结果区分。
- 外部链接应指向支持当前结论的具体页面，不只链接首页。
- 引用不是装饰：正文中的关键结论应能对应到来源。

默认不维护 `type`、`status` 等文档状态属性：它们很容易把整个知识库变成未完成任务列表。只有自动查询确实需要某个属性时才添加，并同时说明谁消费它。

存在明显时效性的文档，可以只记录核对日期：

```yaml
---
last_verified: YYYY-MM-DD
---
```

内容是否可靠由来源、边界、案例或实践证据体现，不靠统一写成 `developing` 或 `mature`。尚未形成正文的想法留在当前项目、`Resources` 或维护待办，不创建占位页。

## 代码示例

- 标为具体语言的代码块应语法完整，或明确写成 `text` / `pseudocode`。
- 可运行示例应给出依赖、入口和预期结果；长代码移入实践项目，正文只保留关键片段。
- 示例必须体现超时、错误、权限、资源释放等与主题直接相关的失败路径。
- 伪代码不得伪装成可复制运行的生产实现。

## 导航与链接

- `Learning/INDEX.md` 说明目录边界，是唯一总入口，负责按目标导航。
- 主题 README 只说明本主题的边界、主线和少量关键入口。
- 模块 README 列出本目录内容，不复制整篇总结和通用练习。
- 使用从当前文件出发的最短相对链接；不写绕回 `Learning/` 的路径。
- 合并或重命名前先检查所有入链，完成后再删除旧文件。
- 跨主题索引优先链接到对方稳定入口；只有确实需要特定概念时才深链正文。这样局部拆分不会要求全库同步改动。
- 默认不维护关键词标签体系：目录说明主题，链接说明关系。只有自动工作流确实消费的少量状态标签才保留。
- 对正文数量较多、以查询为主的专题，可以维护一个局部详细目录；它应替代文章页脚互链，而不是扩散成全库关系图。

## 合并判断

满足任意两项时，优先合并：

- 两篇文档回答同一个核心问题；
- 核心机制、例子或练习大面积重复；
- 单篇删除模板后只剩少量 bullet；
- 必须依赖另一篇才能形成完整解释；
- 标题不同，但复习时无法说明为什么要分别打开。

保留拆分的理由应是读者目标不同、维护频率不同、篇幅过长，或一篇是概念而另一篇是案例/实践。

## 完成检查

每次局部整理后运行：

```bash
python3 scripts/verify_notes.py
```

脚本只检查本地链接和代码围栏，不生成索引，也不修改正文。随后再确认：

- 没有失效的本地链接和未闭合代码围栏；
- 没有已经完成却仍标为“预定内容”的目录；
- 没有无说明的占位文档；
- 主题边界在 README 中可解释，正文不存在明显双份主文档；
- 技术示例和关键公式经过验证；
- 易变或高风险内容有来源、日期和边界；
- 实践项目与长期知识文档分开维护。
