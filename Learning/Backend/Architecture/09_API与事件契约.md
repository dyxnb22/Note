# API 与事件契约

API 设计的核心不是选择 REST 还是 RPC，而是建立跨进程、跨团队、跨版本仍能保持稳定的合同。本篇覆盖同步接口、异步事件和流式协议的共同边界。

## 1. 先定义合同

合同至少包含：

- 请求、响应和事件 Schema。
- 字段语义、单位、时区、金额精度和缺省值。
- 身份、权限和租户边界。
- 幂等性、重试和并发语义。
- 错误分类与恢复动作。
- 超时、取消、分页和限流。
- 版本兼容、弃用和审计策略。

只给出一份字段示例不等于完成契约；必须说明失败和演进。

## 2. REST

REST 风格以资源和统一接口组织 HTTP API：

- URI 表达资源身份，避免把所有动作都写成动词路径。
- GET/HEAD 应安全且幂等。
- PUT 通常表示替换或在指定标识创建，应幂等。
- PATCH 表示部分更新，幂等性取决于补丁语义。
- DELETE 的重复调用应返回稳定、可理解的最终状态。
- POST 常用于创建或命令，不天然幂等。

HTTP 状态码负责协议层结果，业务错误码负责稳定分类。不要所有响应都返回 200 再把失败藏进正文。

## 3. RPC 与 gRPC

RPC 适合以操作和服务能力为中心的内部调用。gRPC 使用 Protocol Buffers 描述接口，支持代码生成、双向流和 Deadline。

RPC 必须显式面对远程失败：

- 请求可能未到达。
- 请求可能执行成功但响应丢失。
- 客户端超时后服务端可能仍在执行。
- 自动重试可能造成重复写入。

Deadline 和取消应沿调用链传播；服务端收到取消后应尽快停止无意义工作。

## 4. Schema 设计

字段设计原则：

- 字段名表达稳定业务语义，不泄漏数据库列名。
- ID 明确作用域和格式，但不要要求消费者解析内部结构。
- 时间统一使用明确时区的标准格式或约定单位的时间戳。
- 金额使用最小货币单位整数或精确定点表示。
- 区分字段缺失、`null`、空字符串和空集合。
- 枚举必须考虑未知值和向前兼容。

外部输入先进行语法、类型和范围校验，再进入领域逻辑。

## 5. 兼容性与版本演进

兼容变更通常包括新增可选字段、新增不影响旧客户端的行为。危险变更包括删除/改名字段、改变含义、收窄范围或复用旧枚举值。

Protocol Buffers 中：

- 不复用已经删除的字段编号。
- 新字段提供可兼容默认行为。
- 消费者应容忍未知字段。
- 枚举新增值时，旧客户端不能假设只存在已知值。

版本号不能替代迁移方案。先让消费者兼容新旧格式，再切生产者，最后观察并删除旧路径。

## 6. 幂等与并发控制

写接口要区分：

- 业务幂等：同一业务动作只能生效一次。
- 请求去重：相同幂等键返回同一结果。
- 条件更新：基于版本号或 ETag 避免覆盖。

幂等键需要定义作用域、有效期、请求内容绑定和冲突处理。只在缓存中短暂记录请求 ID，可能无法覆盖服务重启和长时间重试。

## 7. 错误合同

稳定错误对象可包含：

```text
code          机器可判断的稳定分类
message       面向开发者或用户的安全描述
details       结构化字段错误或上下文
request_id    排障关联标识
retryable     是否允许在当前条件下重试
```

区分参数错误、认证失败、权限不足、资源不存在、并发冲突、限流、依赖失败和内部错误。不要把堆栈、SQL、密钥或内部拓扑返回给客户端。

## 8. 分页、过滤与排序

- Offset 分页简单，但深分页成本高且并发写入下容易重复或遗漏。
- Cursor 分页把位置编码为不透明游标，适合连续浏览。
- Keyset 分页按稳定排序键继续查询，性能和一致性通常更好。

排序必须稳定，必要时加入唯一 ID 作为次级排序键。游标应绑定查询条件，不能让客户端任意篡改内部状态。

## 9. Webhook

Webhook 是反向调用，生产者无法控制消费者是否可用。

设计要求：

- 事件 ID 和幂等消费。
- 签名、时间戳和重放窗口。
- 快速确认，耗时逻辑异步处理。
- 指数退避、最大重试、死信和人工重放。
- 事件查询或对账接口。
- Secret 轮换和投递审计。

HTTP 200 只代表接收端确认，不一定代表业务处理完成。

## 10. 事件契约

事件描述已经发生的事实，命名优先使用过去式，例如 `OrderPaid`。事件包含：

- 唯一事件 ID。
- 事件类型和 Schema 版本。
- 聚合/实体 ID。
- 发生时间和生产时间。
- 因果或关联 ID。
- 租户和必要的追踪上下文。
- 最小必要业务载荷。

生产者不能假设只会有一个消费者；消费者也不能依赖未写入契约的投递顺序和恰好一次语义。

## 11. 顺序、重复与投递语义

消息系统常见语义：

- At-most-once：可能丢，不重复。
- At-least-once：不轻易丢，但可能重复。
- Exactly-once：只在限定系统和操作范围内成立，端到端副作用仍需业务幂等。

全局顺序成本高。优先按业务键分区，保证同一聚合内的局部顺序，并用版本号识别乱序和缺口。

## 12. Streaming 与背压

流式接口要定义：

- 消息边界和事件类型。
- 心跳、空闲超时和断线重连。
- 游标或 Last-Event-ID。
- 客户端处理不过来时如何背压。
- 是否允许丢弃、采样或合并。
- 取消后资源如何释放。

SSE 适合服务端单向事件，WebSocket 适合双向消息，gRPC Streaming 适合强 Schema 的服务间通信。协议选择取决于代理兼容、连接规模和交互模型。

## 13. 契约测试

测试层次：

- Schema 校验：样例与实际消息都符合定义。
- Consumer-driven Contract：生产者变更不破坏消费者依赖。
- 兼容性检查：新旧版本互通。
- 故障测试：超时、重复、乱序、限流和部分响应。
- Replay：历史事件能否被新消费者安全处理。

生产流量观测中还要记录未知字段、旧版本调用量和弃用接口使用者。

## 设计检查清单

- 谁是事实源，谁负责生成 ID？
- 写操作是否幂等，重复请求返回什么？
- 并发更新如何防止覆盖？
- Timeout、Retry、Deadline 和取消如何传播？
- Schema 变更是否向前/向后兼容？
- 事件重复、乱序、缺失如何检测和恢复？
- 错误码能否指导调用方采取明确动作？
- 是否有契约测试、弃用指标和迁移计划？

## 最小实践

为“创建订单 → 支付回调 → 发货”设计 REST API、Webhook 和领域事件，补充幂等键、版本字段、错误码、重试、乱序与对账测试。

## 来源与验证边界

HTTP 语义参考 IETF HTTP Semantics，消息模式参考《Enterprise Integration Patterns》，Protobuf/gRPC 行为以当前官方规范为准。本文给出设计不变量，不替代具体网关、SDK 和消息中间件的版本文档。
