# 生产系统工程

本篇把性能、容量、可观测性、SRE 和事故处理连接成一条可验证链路。目标不是堆监控工具，而是从用户目标出发，使用证据判断系统是否健康、瓶颈在哪里、变更能否安全发布。

## 1. 从用户目标开始

先定义工作负载与目标：

- 请求类型和关键用户路径。
- 吞吐量、并发量和数据量。
- 延迟分位数，而不只平均值。
- 可用性和正确性要求。
- 峰值、突发和季节性。
- 允许的降级、丢失和恢复时间。

性能结论必须绑定硬件、版本、配置、数据集和并发模型，否则难以复现。

## 2. 延迟、吞吐与并发

基本关系：

```text
Little's Law: L = λW
```

稳定系统中，平均在途数量 L 等于平均到达率 λ 乘以平均停留时间 W。它可用于检查连接池、队列长度和并发上限是否合理。

吞吐提高不保证延迟下降。系统接近饱和后，队列通常快速增长，尾延迟恶化。应观察 p50、p95、p99 和超时率。

## 3. 容量规划

容量估算步骤：

1. 估算平均和峰值请求量。
2. 按请求类型拆读写比例和资源成本。
3. 估算存储增长、索引和副本开销。
4. 找到单实例安全容量。
5. 加入故障、发布和流量突发余量。
6. 用压测校准假设。

不能把理论峰值直接当安全容量；GC、Compaction、备份、节点故障和依赖抖动都会消耗余量。

## 4. 基准测试

好的 Benchmark 要求：

- 固定环境、版本和数据集。
- 预热并区分冷启动与稳态。
- 同时记录吞吐、延迟、错误和资源。
- 多轮运行并给出分布。
- 一次只改变关键变量。
- 避免客户端先成为瓶颈。

微基准用于比较局部实现，负载测试用于验证预期流量，压力测试寻找极限，浸泡测试发现泄漏和长期退化。

## 5. 性能剖析

推荐从资源症状逐层定位：

```text
用户延迟
→ 服务队列与依赖耗时
→ CPU / 内存 / 磁盘 / 网络
→ 进程、线程、锁、GC
→ 热点函数与系统调用
```

常用证据：

- CPU Profiling 和火焰图：时间花在哪些调用栈。
- Allocation/Heap Profiling：对象分配、保留和泄漏。
- Lock Profiling：竞争、等待和临界区。
- `perf`、`strace`：硬件事件和系统调用。
- 数据库执行计划和慢查询。
- 网络抓包与重传统计。

先测量再优化；优化后使用同一工作负载复测，并检查是否把成本转移到了其他资源。

## 6. CPU、内存、磁盘与网络

### CPU

区分用户态、内核态、I/O wait、Steal 和负载。CPU 不高但延迟高，可能是在等待锁、队列或外部依赖。

### 内存

区分工作集、缓存、堆、堆外内存和 Page Cache。关注分配速率、GC 暂停、Swap、OOM 和内存回收能力。

### 磁盘

关注 IOPS、吞吐、队列深度、读写延迟和 fsync。随机小 I/O 与顺序批量 I/O 的成本差异很大。

### 网络

关注连接数、带宽、丢包、重传、RTT、连接建立和 DNS/TLS 时间。连接池过小会排队，过大可能压垮下游。

## 7. 可观测性的三类信号

- Logs：离散事件和上下文，适合解释发生了什么。
- Metrics：聚合时间序列，适合趋势、告警和容量。
- Traces：一次请求跨服务的因果路径，适合定位分布式延迟。

三者通过稳定的 `trace_id`、`span_id`、`request_id` 和业务 ID 关联。日志不能承担所有指标，Metrics 也不能保存高基数字段。

## 8. 指标方法

服务端常用 RED：

- Rate：请求速率。
- Errors：错误率。
- Duration：延迟分布。

资源常用 USE：

- Utilization：资源繁忙比例。
- Saturation：排队或超额程度。
- Errors：硬件/系统错误。

指标要有清晰单位和标签边界。用户 ID、请求 ID 等高基数字段不应作为普通 Metrics Label。

## 9. 分布式追踪与 OpenTelemetry

一个 Trace 由多个 Span 构成。Span 应记录：

- 操作名、开始结束时间和状态。
- 服务、版本和环境。
- 下游依赖和关键事件。
- 安全且有界的属性。

上下文必须跨 HTTP、RPC、消息和后台任务传播。异步消费应通过 Link 或父子关系表达因果，而不是伪造同步调用链。

OpenTelemetry 提供统一的埋点、上下文传播和导出模型；采集端、Collector 和后端存储可以独立演进。

## 10. SLI、SLO 与错误预算

- SLI：实际测量的服务指标。
- SLO：目标区间，例如 30 天内 99.9% 的合格请求。
- SLA：对外承诺及可能的补偿。
- 错误预算：允许不达标的比例。

可用性 SLI 的分母和“合格请求”必须定义清楚。只看进程存活会掩盖业务错误、极慢响应和错误结果。

错误预算用于平衡发布速度和可靠性：预算消耗过快时减少风险变更、优先修复可靠性，而不是把它当作可以主动制造故障的额度。

## 11. 告警

好告警意味着需要人采取动作。优先：

- 基于用户症状或 SLO Burn Rate。
- 包含影响、证据入口和 Runbook。
- 有去重、聚合、抑制和升级策略。
- 能区分紧急 Pager 与普通 Ticket。

单个 CPU 阈值通常只是诊断信号，不一定代表用户受影响。

## 12. 限流、背压与负载保护

当输入超过处理能力时，必须决定：

- 拒绝、排队、降级、采样还是丢弃。
- 队列最大长度和等待时间。
- 按用户、租户、接口还是全局限流。
- 重试是否会放大流量。
- 下游恢复后如何避免瞬时洪峰。

无界队列只是把过载变成更晚的内存耗尽和超时。背压要沿调用链传播。

## 13. 发布与变更安全

发布前后至少验证：

- 构建产物、配置和数据库迁移版本。
- 单元、集成、契约和关键路径测试。
- 容量余量和回滚条件。
- Canary/灰度的对照指标。
- 新旧版本 Schema 兼容。
- 自动回滚是否会造成二次破坏。

数据库迁移优先采用 Expand/Contract：先增加兼容结构，再双读写或迁移，最后在确认无旧消费者后收缩。

## 14. 事故响应

事故流程：

```text
发现 → 分级 → 建立负责人和沟通渠道
→ 控制影响 → 保存证据 → 恢复
→ 验证 → 复盘 → 跟踪改进
```

恢复优先于追责和完整根因。变更冻结、降级、回滚、切流和扩容都要考虑可逆性与副作用。

复盘关注系统条件、检测缺口和防复发措施，不把“操作失误”作为终点。

## 15. 最小实验

1. 为一个 API 定义工作负载、SLI 和 SLO。
2. 做阶梯式负载测试，找到吞吐拐点和 p99 变化。
3. 用 Profiling 或火焰图定位一个 CPU 热点。
4. 串起一次 HTTP → 数据库调用的 Trace。
5. 设计 Burn Rate 告警和对应 Runbook。
6. 演练一次依赖超时、限流、降级和恢复。

## 验收清单

- 性能结论包含环境、负载、指标和对照。
- 能用 Little's Law 检查队列或并发量级。
- 能从用户延迟逐层定位到资源和代码。
- Logs、Metrics、Traces 能通过上下文关联。
- SLI/SLO 和错误预算使用真实用户结果定义。
- 过载时存在有界队列、背压和明确降级。
- 发布、回滚和事故响应均有可执行 Runbook。
