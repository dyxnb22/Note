# 日志、指标与链路追踪

这里维护语言无关的可观测性问答；Java 的 SLF4J、Logback、MDC 等实现细节见 [Java 日志与可观测性题](../Java/面试题库/17_Java日志与可观测性.md)。

## 日志、指标和 Trace 分别回答什么问题？

答：日志记录离散事件和上下文，指标把大量事件聚合成可告警的时间序列，Trace 展示一次请求跨服务、队列和数据库的因果链。排障时先用指标发现范围，再用 Trace 定位路径，最后用结构化日志解释具体状态，不能只依赖一种信号。

## 生产日志应该记录什么？

答：至少记录时间、级别、服务、实例、环境、请求/Trace ID、接口或业务动作、耗时、结果和错误类型；必要时记录订单号或任务 ID。密码、Token、身份证号和完整请求内容等敏感信息不能直接写入日志，日志字段和保留周期也应有数据治理规则。

## 如何设计一条日志采集链路？

答：应用输出结构化日志，采集器负责缓冲、解析、脱敏和批量发送，存储按实时查询与长期分析分流，展示层按服务、版本、租户和 Trace 关联查询。设计时必须说明采集失败、重复、迟到、单条大小、保留周期和日志系统故障时的降级方式。

## 什么是 RED/USE 观测方法？

答：RED 关注请求类服务的 Rate、Errors、Duration，适合判断接口是否变慢或失败；USE 关注资源的 Utilization、Saturation、Errors，适合判断 CPU、内存、磁盘、连接池等资源是否饱和。它们是组织指标的抓手，不是替代业务成功率和队列积压的固定面板。

## Trace ID 为什么需要跨线程、消息和服务传递？

答：Trace ID 把同一业务请求的多个处理片段串起来，跨 HTTP、RPC、消息和异步任务时必须通过 Metadata/Header/Message Header 传递，并在异步任务完成后保留父子关系。线程池复用、消息重试和后台任务不能隐式假设当前上下文仍然有效。

## 可观测系统常见的工程风险是什么？

答：高基数标签会拖垮指标存储，日志级别过高会增加磁盘和网络成本，Trace 采样过低会丢失长尾，采集器阻塞又可能拖慢业务。应设置采样、限流、脱敏、保留和成本预算，并用一次真实故障演练验证观测链路本身不会成为单点。

## 验证清单

- [ ] 能从指标定位异常范围，再用 Trace 和日志还原一次请求。
- [ ] 能说明敏感字段、采样、高基数和日志系统故障的处理。
- [ ] 能把可观测数据接到告警、SLO、Runbook 和事故复盘。
