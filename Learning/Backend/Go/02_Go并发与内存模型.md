# Go 并发与内存模型

本篇关注 Goroutine 的所有权、同步、取消、背压和内存可见性。目标不是“多用 Channel”，而是让并发任务可终止、可观测、可验证。

## Goroutine 生命周期

创建前回答：

- 谁启动？
- 谁等待？
- 如何停止？
- 错误传给谁？
- 阻塞在哪里？
- 最大数量是多少？

不能回答这些问题的 Goroutine 很可能泄漏。

## Channel 所有权

通常由发送方关闭 Channel，因为它知道不会再发送。接收方不应为了让自己退出而关闭仍可能被发送的 Channel。

- 无缓冲 Channel 同步交接。
- 有缓冲 Channel 解耦有限突发。
- 缓冲区不是无限容量方案。
- 从已关闭 Channel 读取剩余值后得到零值和 `ok=false`。
- 向已关闭 Channel 发送会 Panic。

## Select

`select` 同时等待多个通信操作。加入 `ctx.Done()` 处理取消，加入 Timer 处理超时。`default` 会使 Select 非阻塞，错误使用容易形成忙循环。

循环内使用 `time.After` 可能不断创建 Timer；长生命周期代码应明确创建、停止和复用。

## Context

Context 沿调用链传播 Deadline、取消和少量请求级值。

- 作为第一个参数传递。
- 不存入长期结构体作为全局状态。
- 不用它传递普通可选参数。
- 创建子 Context 后调用 Cancel。
- 下游必须实际监听 Context。

取消并不会强制中断任意函数；阻塞库不支持 Context 时需要隔离或替代。

## Mutex、RWMutex 与 Atomic

锁保护不变量而不只是单个字段。临界区应短小，不在持锁时执行不可控网络调用。

RWMutex 只在读多写少且临界区成本足够时可能有利；Atomic 适合简单计数、标志和无锁协议，不适合把复杂业务状态拆成多个彼此不一致的原子变量。

## 内存模型与 happens-before

数据竞争发生在多个 Goroutine 并发访问同一内存，至少一个为写且没有同步。程序没有数据竞争，才能可靠推理可见性。

Channel 发送/接收、锁解锁/加锁、Goroutine 启动等建立特定 happens-before。不要依赖“某行通常先执行”或时间延迟作为同步。

## 并发模式

- Worker Pool：有界并发处理任务。
- Fan-out/Fan-in：并行处理后合并。
- Pipeline：阶段化处理并传播取消。
- Semaphore：限制并发资源。
- Single Owner：一个 Goroutine 独占可变状态。

模式必须包含错误、取消、队列满和下游变慢时的行为。

## 错误传播

多个并发任务中，第一处关键失败通常应取消兄弟任务并等待清理。错误要保留任务身份和输入上下文。

不要启动 Goroutine 后只把错误写日志；调用方会误以为整体任务成功。

## Race 与并发测试

Race Detector 能发现实际执行路径上的数据竞争，不能证明所有调度均正确。测试需要：

- 多次运行。
- 随机延迟和调度。
- 超时避免永久挂起。
- Goroutine 数量基线。
- 关闭、取消和异常路径。

## 最小实验

1. 复现 Goroutine 泄漏并用 Profile 定位。
2. 为 Worker Pool 加并发上限、取消和错误传播。
3. 使用 Race Detector 修复一次共享 Map 竞争。
4. 比较 Mutex、单所有者 Channel 和 Atomic 的边界。
5. 模拟下游变慢，验证队列有界和背压。

## 验收清单

- 每个 Goroutine 都有所有者和结束路径。
- Channel 关闭责任明确。
- Context 取消能传到真实阻塞点。
- 共享状态由一个完整同步策略保护。
- Race、泄漏、超时和过载均有测试。

## 来源与验证边界

同步语义以 Go Memory Model、Context、sync 和 runtime 官方文档为准。Race Detector 只覆盖执行到的路径，并发正确性仍需不变量、生命周期和故障测试共同证明。
