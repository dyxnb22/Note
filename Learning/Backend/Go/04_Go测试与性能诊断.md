# Go 测试与性能诊断

本篇把正确性、并发、Benchmark、pprof 和生产诊断连成闭环。

## 单元与表驱动测试

表驱动测试适合覆盖输入组合。子测试名称应表达场景，断言失败要显示输入、期望和实际结果。

接口替身只模拟当前边界；不要把整个数据库或 HTTP 框架都 Mock 成与真实行为无关的脚本。

## 集成测试

数据库、消息和网络行为使用真实依赖或容器化依赖验证：

- Schema 与约束。
- 事务和并发更新。
- 序列化和错误映射。
- 超时、断连和重试。

测试数据必须隔离、可重复并能并行运行。

## Fuzz 与属性测试

Go Fuzzing 适合 Parser、序列化、边界输入和纯函数不变量。好的属性包括：

- 编码后解码得到原值。
- 排序结果有序且元素集合不变。
- 无论输入如何都不 Panic。
- 幂等操作执行两次结果不变。

## 注释版最小测试骨架

下面的片段假设项目已有 `ParseID` 函数；接入时替换被测函数和包名即可。注释重点说明测试要证明的性质，而不是只追求覆盖行数。

```go
func FuzzParseIDNeverPanics(f *testing.F) {
	// 先放入几个有意义的种子，避免 Fuzz 从完全随机输入开始。
	f.Add("user_123")
	f.Add("")

	f.Fuzz(func(t *testing.T, input string) {
		// Parser 对任意外部输入都不能 Panic；错误应通过返回值表达。
		_, _ = ParseID(input)
	})
}

func BenchmarkParseID(b *testing.B) {
	input := "user_123456"
	b.ReportAllocs() // 同时观察 ns/op、B/op 和 allocs/op。
	b.ResetTimer()   // 不把测试数据准备时间算进被测函数。

	for i := 0; i < b.N; i++ {
		// 防止编译器认为结果无用而消除整个调用。
		if _, err := ParseID(input); err != nil {
			b.Fatal(err)
		}
	}
}
```

真实项目还应补一个取消测试：创建 `context.WithCancel`，启动 Worker，调用 `cancel()` 后断言 Worker 在有界时间内退出，并检查没有遗留 Goroutine。否则“支持取消”只是接口声明，没有资源生命周期证据。

## Benchmark

Benchmark 前：

- 固定输入与环境。
- 避免编译器消除结果。
- 区分初始化和被测操作。
- 报告 Allocation。
- 多轮比较并使用统计工具。

微基准变快不代表端到端延迟变好。

## pprof

常见 Profile：

- CPU：热点调用栈。
- Heap/Alloc：保留与分配。
- Goroutine：阻塞和泄漏。
- Mutex：锁竞争。
- Block：同步阻塞。

Profile 有开销和敏感信息风险，生产暴露必须鉴权、限时并控制访问。

## Trace

Runtime Trace 适合查看调度、网络、GC 和 Goroutine 生命周期。分布式 Trace 负责跨服务请求；两者解决不同层次问题。

## 故障诊断顺序

```text
用户症状 → 服务 RED → 下游/数据库
→ CPU/内存/网络 → Goroutine/锁/GC
→ 热点代码 → 最小修复 → 复测
```

## 静态与并发检查

流水线至少运行格式化、`go vet`、测试、Race（按成本安排）和依赖检查。Linter 规则应解释目的，避免把告警数量当质量指标。

## 最小实验

1. 为 Parser 添加 Fuzz Test。
2. 比较两个实现的 `ns/op`、`B/op` 和 `allocs/op`。
3. 制造 Goroutine 泄漏、锁竞争和分配热点。
4. 分别用 Goroutine、Mutex 和 Heap Profile 定位。
5. 在负载测试中验证优化对 p99 的影响。

## 验收清单

- 测试覆盖正常、失败、取消和并发。
- Benchmark 可复现且报告分配。
- 能选择正确的 Profile 类型。
- 优化同时验证吞吐、尾延迟、错误和资源。

## 来源与验证边界

工具语义参考 Go Testing、Fuzzing、Diagnostics 和 pprof 官方文档。Benchmark 与 Profile 高度依赖编译器、硬件和工作负载，不跨环境直接比较绝对数字。
