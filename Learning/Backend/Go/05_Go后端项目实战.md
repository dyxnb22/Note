# Go 后端项目实战

这篇把语言、并发、HTTP、数据库、测试和生产诊断串成一个可验收项目。可运行的第一阶段位于 [实践/go-backend-service](./实践/go-backend-service/README.md)；它故意只使用标准库和内存 Repository，后续阶段再引入 PostgreSQL、遥测和部署依赖。

## 1. 项目目标与非目标

目标：实现一个订单服务，支持创建与查询订单，并证明重复请求、并发访问、超时、关闭和依赖失败时行为可解释。

非目标：不追求复杂业务 UI，不用框架代码量代替后端能力，不用单个 QPS 数字证明语言优劣。

核心合同：

```text
POST /orders       Idempotency-Key 必填；创建或返回同一请求的已有订单
GET  /orders/{id}  查询订单
GET  /healthz      进程存活检查
```

## 2. 分阶段路线

| 阶段 | 重点 | 完成证据 |
|---|---|---|
| 0. 可运行基线 | Module、分层、JSON、错误映射、内存 Repository | `go test -race ./...` 通过 |
| 1. 生命周期 | Context、请求超时、Server 超时、SIGTERM | 慢请求取消与优雅关闭测试 |
| 2. 持久化 | PostgreSQL、迁移、连接池、事务、唯一约束 | 干净库和升级库迁移测试 |
| 3. 跨系统可靠性 | 库存客户端、幂等、有限重试、Outbox | 超时、重复和响应丢失故障测试 |
| 4. 可观测性 | 结构化日志、RED 指标、Trace、Build 信息 | 一次请求可跨入口、数据库和下游关联 |
| 5. 质量与性能 | 单元、集成、Fuzz、Benchmark、pprof、负载 | Profile 解释 p99 拐点；优化前后可复测 |
| 6. 交付 | Docker、CI、配置、健康检查、灰度和回滚 | 新环境可重复部署；回滚演练成功 |

## 3. 推荐目录与依赖方向

```text
cmd/api/              进程入口、依赖装配、信号和关闭
internal/httpapi/     HTTP 解析、校验、错误映射
internal/order/       订单用例、领域类型、Repository 接口
internal/postgres/    PostgreSQL Repository 与迁移
internal/inventory/   外部库存客户端
migrations/           可审查、可重放的 Schema 迁移
tests/                跨组件和端到端测试
```

依赖从入口和适配器指向应用核心；`internal/order` 不导入 HTTP、SQL Driver 或遥测 SDK。只有存在真实替换边界时才定义 Interface。

## 4. 阶段 0：建立正确基线

先运行实践项目，阅读请求如何经过 Handler、Service 和 Repository。确认：

- 输入长度有限，未知 JSON 字段被拒绝。
- 业务错误映射为稳定错误码，不泄露内部细节。
- `Idempotency-Key` 的重复请求返回同一订单。
- 内存 Repository 在并发访问下没有数据竞争。
- Server 配置读取、写入、Header 和空闲超时。

不要在这一阶段加入 ORM、Web 框架、依赖注入框架和消息队列；先让边界可以被测试。

## 5. 阶段 1：Context 与关闭

为请求设置总预算，并把 Context 传到 Service、Repository 和下游客户端。超时需要区分：尚未提交、已经提交但响应丢失、调用方主动取消。

关闭顺序：标记不再就绪 → 停止接受新请求 → 在 Deadline 内等待在途请求 → 停止后台任务 → Flush 遥测和关闭连接池 → 超时后退出。

测试不能只用 `time.Sleep` 猜时序；使用 Channel 或 Barrier 控制“请求已进入依赖”的时刻。

## 6. 阶段 2：PostgreSQL 与事务

把 Repository 替换为 PostgreSQL 实现，但保留同一契约：

- 使用参数化 SQL。
- 为幂等键建立唯一约束，而不是只在应用内先查后写。
- 事务只覆盖数据库内必须共同成立的不变量。
- 设置连接池上限、连接生命周期和获取等待指标。
- 迁移同时在空数据库与上一版本数据上验证。

并发创建同一幂等键时，以数据库约束决定唯一事实；应用捕获冲突后读取已存在订单。

## 7. 阶段 3：下游、重试与 Outbox

增加库存服务客户端，分别配置连接、TLS/响应头、单次调用和整体请求预算。只对明确瞬时且操作幂等的失败有限重试，并加入抖动；重试次数必须受总预算约束。

如果创建订单后还要发布事件，数据库事务不能直接覆盖消息系统。使用 Outbox：订单与待发布事件在同一事务写入，后台 Publisher 领取、发送并记录结果；消费者按事件 ID 幂等处理。

## 8. 阶段 4：观测与安全

最小观测面：

- HTTP 请求率、错误率和 p50/p95/p99。
- 数据库连接池等待、查询耗时和事务失败。
- 下游调用耗时、超时、重试和熔断状态。
- Goroutine、Heap、GC 和进程资源。
- Request ID、Trace ID、Order ID 与 Build Version。

路由指标使用模板而不是原始 ID，防止高基数。日志不记录 Token、完整连接串或未经处理的请求体。pprof 只在受控网络、鉴权和限时条件下开放。

## 9. 阶段 5：测试与性能证据

```bash
gofmt -w .
go vet ./...
go test ./...
go test -race ./...
go test -run=^$ -fuzz=Fuzz -fuzztime=20s ./...
go test -bench=. -benchmem ./...
```

测试矩阵至少包含：非法 JSON、超大请求、重复键、并发重复、资源不存在、数据库超时、下游 5xx、客户端取消、SIGTERM 和迁移失败。

性能实验固定 Go 版本、硬件、数据规模和依赖延迟，同时报告吞吐、尾延迟、错误率、CPU、内存和 GC。先采 Profile，再修改，再用相同负载复测。

## 10. 最终验收

- [ ] 新环境用一条说明完成构建、测试、迁移和启动。
- [ ] 所有 Goroutine 有所有者、停止方式、错误传播和数量上限。
- [ ] 重复创建不会生成重复订单或重复事件。
- [ ] Context 取消到达真实数据库和网络阻塞点。
- [ ] 日志、指标和 Trace 能解释一次失败请求。
- [ ] Race、集成、故障、负载与关闭测试均有固定入口。
- [ ] 发布有健康门禁、灰度观察、回滚条件和演练记录。
