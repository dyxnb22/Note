# Go 编码题与系统设计

> 递进路径：先写算法和数据结构，再写并发原语，最后完成后端系统设计；每题都要说不变量、复杂度、错误和测试。

## Level 1｜基础算法

### 1. 如何反转单链表？

答：维护 `prev`、`cur` 和 `next`，每轮先保存 next，再把 cur.Next 指向 prev，最后向后移动；时间 O(n)，空间 O(1)。要处理空链表、单节点和是否允许修改原链表，并说明循环链表不能直接套用。

### 2. 如何按 K 个一组反转链表？

答：先检查剩余节点是否至少 K 个，再局部反转这 K 个节点并把上一组尾部连接到新头，递归或迭代处理后续；时间 O(n)，额外空间 O(1)（迭代）。关键是不丢失组后节点和正确更新组头/尾，面试时先写普通反转 helper。

### 3. 如何实现两数之和和三数之和？

答：两数之和用 map 记录已见值 O(n)；三数之和先排序，固定一个数后用双指针收缩其余区间，时间 O(n²)，并跳过重复值。要说明是否允许重复下标、结果是否去重和整数溢出边界。

### 4. 如何设计 LRU Cache？

答：map 保存 key 到双向链表节点的指针，链表头表示最近使用，尾部表示最久未使用；get/put 都是 O(1)。Go 中要明确节点所有权、容量为零、更新旧值和并发保护；如果加锁，锁保护的是 map 与链表的一致不变量。

### 5. 如何合并多个有序链表？

答：把每个链表头放入最小堆，每次取最小节点，把它的 next 放回堆；时间 O(N log k)，空间 O(k)。如果 k 很小可两两合并；要处理 nil 链表、重复值和是否复用原节点。

## Level 2｜并发编码题

### 6. 实现一个有界 Worker Pool，要求传递第一个错误并支持取消。

答：创建带 buffer 的任务 channel、固定 worker、父 context 和结果收集；提交方监听 `ctx.Done()`，worker 处理任务后上报错误，首个关键错误调用 cancel，关闭任务输入后等待全部 worker。不能让 worker 在结果 channel、任务 channel 或下游调用上永久阻塞。

```go
type Job func(context.Context) error

func RunPool(ctx context.Context, jobs []Job, workers int) error {
	if workers <= 0 {
		return fmt.Errorf("workers must be positive")
	}
	ctx, cancel := context.WithCancel(ctx)
	defer cancel()

	queue := make(chan Job)
	errCh := make(chan error, 1)
	var wg sync.WaitGroup

	worker := func() {
		defer wg.Done()
		for {
			select {
			case <-ctx.Done():
				return
			case job, ok := <-queue:
				if !ok {
					return
				}
				if err := job(ctx); err != nil {
					select {
					case errCh <- err:
					default:
					}
					cancel()
					return
				}
			}
		}
	}

	wg.Add(workers)
	for i := 0; i < workers; i++ {
		go worker()
	}
	stopped := false
	for _, job := range jobs {
		select {
		case queue <- job:
		case <-ctx.Done():
			stopped = true
		}
		if stopped {
			break
		}
	}
	close(queue)
	wg.Wait()
	select {
	case err := <-errCh:
		return err
	default:
		return ctx.Err()
	}
}
```

面试时应主动指出：示例还需要仔细处理提交循环的 `break` 语义、空任务、父 context 已取消、错误优先级和 `context.Canceled` 的返回约定；重点是讲清状态和退出路径，而不是追求现场代码一次完美。

### 7. 如何实现并发安全计数器？

答：简单计数用 `sync/atomic`，复合状态用 Mutex，热点场景可分片后聚合；读写必须遵守同一同步协议。要说明计数是否允许丢失、是否需要精确快照、是否跨进程以及溢出/重启持久化，不能把 atomic 当成分布式计数器。

### 8. 如何实现一个安全的定时任务？

答：使用 ticker 或调度器触发，但每次执行必须有 context、超时、并发策略和错误记录；如果任务不能重入，要用租约/分布式锁或持久化状态。关闭时停止 ticker、取消任务并等待已执行实例，不能在 handler 内再次无界启动 goroutine。

### 9. 如何写一个可重试的 Go HTTP 调用？

答：先设置请求 context 和 transport/client 超时，再根据错误类型、状态码、方法和幂等键决定是否重试；使用有上限的指数退避加 jitter，响应 body 要关闭，重试次数和耗时写入 Trace。连接超时与服务器已处理但响应丢失要分别处理。

## Level 3｜系统设计题

### 10. 设计一个 Go 任务队列，要求支持租约、重试和恢复。

答：任务表保存 ID、输入版本、状态、尝试次数、lease_until、worker、结果引用和错误；领取用条件更新/租约，worker 心跳续租，完成用版本号提交，崩溃后过期任务可重试。任务 ID 和业务幂等键分开：前者防止消息重复，后者防止外部副作用重复；未知结果需要查询/对账。

### 11. 设计一个 Go 限流器，如何选择令牌桶、漏桶和滑动窗口？

答：令牌桶限制平均速率且允许突发，漏桶平滑输出，滑动窗口直接限制时间段内次数。先按租户、用户、路由和下游资源确定 Scope，再明确超限是拒绝、排队还是降级；单机可用 mutex/atomic，分布式要有原子存储、时间策略和过期清理。

### 12. 设计一个订单服务，如何防止重复扣款？

答：入口以业务幂等键和请求摘要落库，订单状态用状态机和唯一约束；扣款请求携带同一幂等键，下游返回未知时通过查询对账，不直接重新扣款。数据库事务只覆盖本地状态，跨服务通过 Outbox、事件和补偿；审计记录每次状态迁移和调用结果。

### 13. 如何把一个 Go 服务从单体改造成可观测的异步系统？

答：先梳理同步调用和共享状态，定义事件 schema、任务状态和幂等 ID，再把耗时/可重试步骤放入有界队列；服务通过 context 传播 deadline，Trace 贯穿请求—消息—worker—数据库，指标区分排队和执行。迁移用双写/影子/灰度并准备回滚，不直接把函数改成 goroutine。

### 14. Go 项目如何证明并发改动没有引入回归？

答：单测验证状态不变量和错误路径，Race Detector 检查实际数据竞争，benchmark 比较吞吐/分配/延迟，压力测试覆盖队列满、下游慢、取消和关闭，pprof/trace 确认资源没有泄漏。最终用业务指标验证，不以“测试没挂”替代正确性。

### 15. Go Fuzz Test 适合发现什么问题？

答：适合解析器、序列化、边界输入和“不应 panic”的纯函数；好的属性包括编码后再解码保持等价、排序保持元素集合、任意输入都返回稳定错误而非崩溃。Fuzz 发现的最小样本要沉淀为回归测试，外部副作用不应直接在 fuzz 中执行。

### 16. Benchmark、pprof 和端到端负载测试如何配合？

答：Benchmark 比较局部实现的 ns/op、B/op、allocs/op，pprof 定位真实进程的 CPU/内存/锁/阻塞热点，端到端负载测试验证连接池、数据库、队列和 p99。三者必须固定版本、数据和工作负载，微基准变快不代表服务尾延迟或错误率变好。

### 17. 设计一个支持分片上传、断点续传和异步处理的 Go 服务。

答：上传会话保存文件版本、大小、分片数、hash、已完成分片和过期时间；分片写入临时对象后幂等确认，合并由单一状态迁移或锁保护，成功后原子切换可见版本。解析/转码进入有界队列，Worker 用租约和心跳恢复；下载/查询只读取已发布版本，清理覆盖超时会话、孤儿分片和失败半成品。

### 18. 面试中如何解释 Raft 的 Leader、日志复制和脑裂边界？

答：节点通过任期和多数票选出 Leader，Leader 追加日志并复制到多数节点后提交，Follower 按提交索引应用；网络分区时少数派不能提交新日志，旧 Leader 发现更高任期后退回 Follower。Raft 只解决共识日志，不自动解决业务幂等、快照、客户端重试、线性化读和外部副作用；实现题要说明超时、重复消息和成员变更。

### 19. Go 服务负载升高但 QPS 没变，如何建立证据链？

答：先按时间窗口比较 CPU、GC、goroutine、mutex/block、连接池、队列、下游延迟和错误率，再用 pprof 定位 CPU/分配/阻塞，用 trace 看调度和网络，用数据库执行计划/慢日志和消息积压确认外部瓶颈。压测复现时固定版本、数据、连接数和负载模型，修复后同时比较 P99、资源、成本和业务成功率。
