# Go 语言与 Runtime

> 递进路径：先讲值语义和数据结构，再讲接口、编译器、调度器和 GC；实现细节要注明 Go 版本。

## Level 1｜语言语义：值、引用与类型

### 1. Go 是按值传递还是按引用传递？

答：Go 的函数参数传递是按值复制。数组会复制全部元素；slice、map、channel 的值内部包含指向运行时结构的描述信息，因此复制后可能共享底层数据或状态，但这不等于语言存在“按引用传递”。回答时要区分复制描述符和共享底层对象。

### 2. Array 和 slice 有什么区别？

答：数组长度属于类型，赋值和传参通常复制整个数组；slice 是指向底层数组的指针、长度和容量描述符，适合动态序列。slice 本身按值复制，但多个 slice 可能共享底层数组；API 返回或并发传递 slice 时要明确是否允许调用方修改数据。

### 3. `append` 什么时候会导致 slice 重新分配？

答：当追加后的长度超过容量时，runtime 通常分配新的底层数组并复制元素；未超过容量时可能复用原数组。因此 append 后旧 slice 与新 slice 是否共享不能只看元素内容，要看容量和实际分配。跨边界需要独立所有权时显式复制，性能结论用 benchmark 验证。

### 4. map 的基本语义和并发边界是什么？

答：map 提供键到值的映射，读取不存在的键返回值类型零值，`delete` 不要求键存在；遍历顺序不应依赖。普通 map 不能在没有同步的情况下并发读写，可能产生数据竞争甚至运行时错误；并发场景可选择互斥锁、单所有者 goroutine、分片 map 或 sync.Map，取决于访问模式。

### 5. nil map、空 map 和 nil slice 有什么区别？

答：nil map 可以读、删和 `len`，但直接写会 panic；空 map 已初始化，可以写入。nil slice 的长度和容量为零，可以 append，append 可能返回新的底层数组；空 slice 可能是非 nil 的零长度值。序列化、接口比较和业务“是否提供”语义要明确区分 nil 与 empty。

### 6. `make` 和 `new` 有什么区别？

答：`new(T)` 分配一个 T 的零值并返回 `*T`；`make` 只用于 slice、map、channel 等引用型运行时结构，返回初始化后的 T。make 的 len/cap、map 的可写状态和 channel 的缓冲容量会影响行为；不要为了“堆分配”机械使用 new，逃逸由编译器决定。

### 7. 值接收者和指针接收者如何选择？

答：值接收者复制接收者，适合小型不可变语义；指针接收者可以修改对象、避免大对象复制并统一方法集。选择重点是类型语义和接口满足关系，而不是单纯追求性能；如果部分方法使用指针接收者，通常只有 `*T` 满足包含这些方法的接口。

### 8. Go interface 的运行时表示和 nil 陷阱是什么？

答：接口值包含动态类型和动态值，只有两者都为空时接口才是 nil。把一个 nil 指针放入接口后，接口可能具有动态类型，因此 `iface == nil` 为 false；调用方法还可能在方法内部解引用 panic。解决方式是明确接口合同、在边界处理 nil，不要用反射掩盖类型设计问题。

### 9. 泛型和接口分别适合什么场景？

答：泛型适合对类型参数做算法、容器和数据变换复用，约束可以用 type set 表达允许的类型集合；接口适合表达运行时能力和业务替换边界。先问需要编译期类型复用还是运行时多态，再选择。小接口通常由使用方定义，泛型约束要精确，不能为了消除少量重复制造复杂类型参数。

### 10. string、[]byte 和 []rune 如何选择？

答：string 是不可变字节序列，适合文本和只读键；[]byte 适合协议、文件和可变二进制；[]rune 表示 Unicode code point，适合按字符而非字节处理，但转换会分配和占用更多内存。一个“字符”还可能由多个 code point 组成，用户感知字符处理需要更高层规则。

## Level 2｜控制流与运行时

### 11. `defer` 的执行顺序和常见陷阱是什么？

答：defer 在函数返回前执行，多个 defer 按后进先出；参数通常在 defer 语句执行时求值，但闭包捕获变量要看变量本身的生命周期和版本语义。它适合释放资源和记录收尾，但在大循环中累积大量 defer 可能延迟释放；要理解命名返回值、panic 和 defer 修改返回结果的交互。

### 12. panic 和 error 应该怎么区分？recover 何时有效？

答：可预期的业务失败用 error 返回，panic 用于无法继续的程序不变量、初始化错误或明确的框架边界；recover 只在同一 goroutine 的 defer 中生效。服务边界可以恢复 panic 防止整个进程退出，但必须记录堆栈、终止当前请求并确认共享状态没有被破坏，不能把 panic 当普通流程控制。

### 13. 什么是逃逸分析？如何验证？

答：编译器根据值的引用是否超出当前栈帧来决定分配位置；返回局部变量的指针在 Go 中是安全的，但该值可能逃逸到堆。用 `go build -gcflags=-m` 查看编译器提示，用 `go test -bench=. -benchmem` 比较分配次数和耗时；减少逃逸不能牺牲清晰性。

### 14. Go 的 G、M、P 分别是什么？

答：G 是 goroutine，M 是操作系统线程，P 是执行 Go 代码所需的调度资源。P 持有本地运行队列，调度器会处理阻塞系统调用、网络轮询、抢占和 work stealing。Goroutine 创建成本低但仍会消耗栈、调度、内存和下游资源，必须有所有者、退出路径和并发上限。

### 15. Go GC 关注哪些指标？

答：Go 使用并发垃圾回收，在吞吐、CPU 和暂停之间平衡；高分配速率、过大的堆和长期存活对象会增加 GC 压力。排查时看 heap、allocation rate、GC CPU、pause、对象保留和请求延迟；`sync.Pool` 只能做临时对象复用，不能存业务状态或当可靠缓存。

### 16. Go Module、Package 和 internal 的边界是什么？

答：Module 由 `go.mod` 描述依赖和版本，package 是编译和导入的组织单位，`internal` 限制包只能被父目录树内的代码导入。项目应锁定依赖、记录 Go 版本和构建信息，避免 init 副作用和循环依赖；可复现构建还要处理 build tag、平台和嵌入资源。

### 17. 如何解释 range、闭包和变量捕获问题？

答：循环变量、闭包和 goroutine 组合时要明确闭包捕获的是变量还是当轮值，不能依赖调度“碰巧”先执行；应显式把当前值作为参数传入或在循环体创建独立副本。不同 Go 版本对循环变量语义有变化，面试中应注明项目版本并用最小实验验证。

## Level 3｜边界与验证

### 18. Go 的零值设计有什么优点和边界？

答：很多类型的零值可以直接使用，减少初始化样板并让结构体易组合；但 map、channel、指针、接口和带资源的对象需要区分 nil 的可读/可写/可关闭行为。API 设计要让零值尽可能安全，不能假设所有零值都代表“空但可用”。

### 19. 如何判断一个性能问题是否需要优化 Go Runtime？

答：先用 pprof、trace、benchmark、alloc profile 和执行指标确认热点，区分锁等待、网络、数据库、GC 和真实 CPU；只有在热点和收益明确时才调整对象分配、池化、调度或 GC 参数。Runtime 细节随版本变化，不能从一篇文章的微基准推导所有服务的结论。

### 20. Go 代码为什么强调显式错误？

答：error 是普通值，调用方必须决定重试、降级、返回还是终止，错误路径更容易被测试和观测。错误应使用 `%w` 保留原因、用 `errors.Is/As` 做分类，避免只比较字符串；错误信息要包含操作上下文，但不泄露密钥和敏感数据。

### 21. 如何设计一个让接口易测试的 Go 类型？

答：由使用方定义最小接口，在边界注入时钟、随机数、HTTP 客户端、数据库和队列；核心业务保持纯函数或显式状态转移。Mock 只验证合同和关键调用，不把每个内部函数都抽成接口；真实协议、序列化、权限和超时还要用集成测试覆盖。

### 22. map 查询为什么常写成 `value, ok := m[key]`？

答：map 读取不存在的键会返回值类型零值，单独读取无法区分“键不存在”和“键存在但值正好是零值”；双返回值的 `ok` 表达存在性。这个边界会影响配置合并、缓存命中、状态机和 JSON/API 映射，不能只靠零值猜测业务语义。

### 23. Go 的 package、导出规则和 `internal` 如何影响项目边界？

答：同一目录的 Go 文件属于同一个 package，大写标识符对包外可见，小写只在包内可见；`internal` 限制导入者必须位于指定父目录树内。把 Handler、领域、存储和适配器分包时，应让依赖方向和可见性共同保护边界，而不是只靠目录命名。

### 24. Build tag、`go:embed` 和版本信息为什么属于交付问题？

答：Build tag 和目标平台会改变编译出来的代码，`go:embed` 会把资源纳入二进制，版本信息影响诊断和回滚；它们都应进入可复现构建和发布检查。面试时要说明依赖锁定、构建平台、制品内容和运行时配置如何对应，不能只说“Go 编译成一个二进制”。

### 25. Go 泛型的 type set、`~T` 和接口方法约束如何影响 API 设计？

答：type set 限定类型参数可接受的底层类型或联合集合，`~T` 允许底层类型相同但命名不同的类型参与；如果接口还声明方法，类型参数必须同时满足类型集合和方法集合。约束应表达算法真正需要的能力，不能用 `any` 后在运行时反射补救，也不能把复杂 type set 暴露成难以阅读的公共 API。

### 26. Go 的构建与发布如何证明“运行的就是构建的内容”？

答：构建脚本固定 Go/toolchain、module 依赖、build tags、目标平台和嵌入资源，通过 `-ldflags` 写入版本、commit 和构建时间；制品生成后记录 hash，启动日志和健康接口暴露可追踪版本。发布验收还要覆盖配置、迁移、回滚和跨平台差异，不能只看本地 `go build` 成功。

## 验证边界

- slice、interface、逃逸、调度器和 GC 的实现细节必须以目标 Go 版本和 benchmark/profile 为准。
