# Go 主题速答卡

| 主题 | 30 秒回答 |
|---|---|
| slice | slice 是指针、长度、容量描述符，按值复制但可能共享底层数组；append 超过容量可能重新分配，跨 API 要明确所有权。 |
| map | map 读不存在返回零值，遍历无稳定顺序，普通 map 不能无同步并发读写；复杂状态通常用 Mutex/单所有者，特定读多写少才考虑 sync.Map。 |
| interface nil | interface 由动态类型和值共同组成；nil 指针放入接口后接口可能非 nil。要区分接口判断、类型断言和方法内部解引用。 |
| make/new | new 返回零值指针，make 初始化 slice/map/channel 运行时结构；分配位置由逃逸分析决定，不要机械追求 new。 |
| defer/panic | defer 返回前 LIFO 执行，适合释放资源；error 处理可预期失败，panic 用于不变量/初始化边界，recover 只在同一 goroutine 的 defer 中有效。 |
| GMP | G 是 goroutine，M 是线程，P 是执行 Go 代码所需的调度资源；阻塞、网络轮询、抢占和 work stealing 影响调度，但 G 仍需生命周期和上限。 |
| Channel | Channel 既是通信也是同步/背压边界；发送方通常负责关闭，关闭后继续读会得到剩余值和 `ok=false`，向已关闭 channel 发送会 panic。 |
| Context | Context 传播取消和 deadline，应作为第一个参数并实际监听；不能存长期结构体或传普通业务参数。 |
| 内存模型 | 数据竞争是并发读写无同步；channel、锁和启动等建立特定 happens-before，sleep 和日志顺序不是同步。 |
| MySQL | 联合索引、MVCC、锁和执行计划要结合数据分布判断；加索引不能替代事务边界、状态机和幂等。 |
| Kafka | 分区内有序，至少一次可能重复；副作用消费仍要业务幂等，exactly-once 不自动覆盖外部数据库/API。 |
| pprof | CPU、heap/alloc、goroutine、mutex/block 和 trace 分别定位热点、分配、阻塞和调度；先基线再优化。 |
| gRPC/HTTP2/Protobuf | gRPC 用 IDL 生成强类型代码，通常基于 HTTP/2 多路复用和 Protobuf；工程上仍要处理 deadline、流式背压、兼容、认证、错误和重试边界。 |
| 心跳/长连接 | 心跳用于发现连接或租约失效，不等于业务成功；要区分 TCP/应用层心跳、空闲超时、重连抖动、重复连接和优雅关闭。 |
| 缓存一致性 | 先定义陈旧窗口和事实来源，再选择失效、回填、版本、事件或对账；热 Key、击穿和未知写入结果都要有降级策略。 |
| Fuzz/Benchmark | Fuzz 找输入边界和“不应 panic”的性质，Benchmark 比较局部实现，pprof/trace 和端到端压测验证真实服务；三者不能互相替代。 |
