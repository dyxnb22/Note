# Go 并发与内存模型

> 递进路径：先讲任务生命周期，再讲同步、取消、背压、错误传播和测试；并发题的核心不是“会不会开 goroutine”。

## Level 1｜Goroutine、Channel 与 Select

### 1. 启动一个 goroutine 前必须回答哪些问题？

答：谁启动、谁等待、谁负责停止、错误传给谁、可能阻塞在哪里、最大数量是多少。没有 owner、join/等待路径和取消信号的 goroutine 很容易泄漏；无界 fan-out 还会把下游过载和内存增长藏起来。

### 2. Channel 的关闭责任是谁？

答：通常由知道“不会再发送”的发送方关闭，接收方不应为了退出而关闭仍可能被发送的 channel。关闭后可读完缓冲中的值，再得到零值和 `ok=false`；向已关闭 channel 发送会 panic。多发送者场景应由协调者关闭，或用 context/完成计数表达结束。

### 3. 有缓冲和无缓冲 channel 有什么区别？

答：无缓冲 channel 让发送和接收同步交接；有缓冲 channel 允许有限突发并解耦生产/消费，但容量用尽后仍会阻塞。缓冲区是背压边界，不是无限队列；要定义满载时等待、丢弃、拒绝或降级的行为。

### 4. `select` 如何处理取消和超时？

答：`select` 同时等待多个通信操作，通常把 `ctx.Done()` 和 timer 放入分支处理取消/截止时间；`default` 会让 select 非阻塞，循环中误用容易形成忙等。长生命周期代码要管理 timer，避免在高频循环里无界创建 `time.After`。

### 5. 如何保证一个 channel pipeline 能安全退出？

答：每个阶段都监听 context，输入关闭后停止读取并关闭自己拥有的输出；发送前检查取消，消费者退出时生产者不能永久阻塞。关闭顺序、错误传播、部分结果和等待所有 goroutine 必须有明确协议，不能只靠主函数返回让后台 goroutine 自己消失。

## Level 2｜同步与内存可见性

### 6. Mutex、RWMutex 和 atomic 如何选择？

答：Mutex 保护一个完整不变量，适合大多数共享状态；RWMutex 只有在读多写少、读临界区足够大且竞争测量证明有收益时使用；atomic 适合计数器、标志和设计清晰的无锁协议。不要把多个 atomic 字段拼成没有一致性保证的复杂事务。

### 7. 什么是 data race？happens-before 如何帮助推理？

答：多个 goroutine 并发访问同一内存、至少一个是写且没有同步，就可能产生 data race。channel 发送/接收、锁解锁/加锁、goroutine 启动等特定关系建立 happens-before，使写入对另一方可见；不能用 sleep、日志顺序或“通常先执行”代替同步。

### 8. sync.Map 什么时候适合，什么时候不适合？

答：sync.Map 适合读多写少、键集合相对稳定或不同 key 由不同 goroutine 频繁访问的特定场景；普通 map 加 Mutex 更容易表达复杂不变量、类型和批量更新。选择前用 workload benchmark，不要把 sync.Map 当成普通 map 的无脑升级。

### 9. sync.Once 常见用途和边界是什么？

答：sync.Once 保证初始化函数最多执行一次，适合延迟创建客户端、配置或只读共享对象；如果初始化函数 panic，后续调用是否再次执行要按标准库语义和项目版本验证。它不适合需要重试、刷新或按租户初始化的状态，后者应使用显式状态机。

### 10. 如何避免死锁？

答：固定多个锁的获取顺序，缩小临界区，不持锁执行不可控网络/磁盘调用，使用有界等待和超时，并记录锁等待时间。代码评审时画出锁与资源依赖图；测试中加入高并发、取消和异常路径。RWMutex 也会死锁，不能因为“读锁安全”而忽略升级/嵌套。

## Level 3｜并发模式与错误传播

### 11. 如何设计 Worker Pool？

答：创建有界任务队列和固定数量 worker，提交方在队列满时产生背压；每个任务携带 context、ID、deadline 和状态，worker 处理后上报结果并释放资源。父任务取消时停止接收新任务并等待已开始任务清理；关键错误应取消兄弟任务，不能只打日志。

### 12. Fan-out/Fan-in 的安全边界是什么？

答：只有相互独立、无共享副作用的任务才适合并行 fan-out；总并发受 semaphore/worker 数限制，fan-in 按成功、失败、超时、取消分别聚合。部分结果不能被当成完整事实，输出要说明缺口和置信度；副作用任务还需要幂等键和顺序/状态约束。

### 13. 如何传播并发任务中的第一个关键错误？

答：创建父 context 和错误收集器，首个关键错误取消兄弟任务，等待所有已启动任务结束后再返回；错误要保留任务 ID、输入摘要和根因。使用 `errgroup` 等工具时仍要理解其取消、等待和并发限制语义，不能把“返回第一个 error”误当成所有资源都已清理。

### 14. Context 的正确用法是什么？

答：Context 通常作为函数第一个参数，向下游传播取消、deadline 和少量请求级值；创建子 context 后调用 cancel，服务/数据库/HTTP 客户端必须实际监听它。不要把 context 存入长期结构体、用它传普通可选参数或用 `context.Background()` 在中间层切断调用链。

### 15. 如何实现一个带超时、取消和部分结果的并发调度器？

答：为总任务和每个子任务设置 deadline，使用有界 worker pool；每项状态写入结果集合，结束原因区分 success/error/timeout/cancelled，父任务取消时停止投递并等待 workers。聚合器在收到足够的成功证据后可以结束，但必须取消剩余任务并确认它们没有遗留资源或副作用。

### 16. 什么是 goroutine 泄漏？如何验证？

答：goroutine 因 channel 无人接收、锁、网络、ticker 或后台循环没有退出条件而长期存活，持续占用栈和引用。验证时看 goroutine profile、数量基线、阻塞栈和任务生命周期；测试中覆盖正常完成、取消、超时、下游关闭、panic 和队列满，不能只测试成功路径。

### 17. Race Detector 能证明并发正确吗？

答：不能。Race Detector 能发现实际执行路径上的数据竞争，但没有执行到的调度、死锁、活锁、错误的业务不变量和泄漏仍可能存在。并发正确性需要 race、压力、随机调度、确定性关闭协议、状态不变量和故障测试共同证明。

## Level 4｜工程追问

### 18. 如何处理下游变慢造成的背压？

答：给队列、连接池、worker、HTTP 客户端和数据库设置上限；当下游变慢时让提交方等待、拒绝、降级或采样，而不是继续堆积。指标要包含队列长度、等待时长、活跃任务、超时和丢弃数；恢复时还要防止积压瞬间把下游再次打爆。

### 19. 取消能否撤销一个已经发出的请求？

答：取消通常只能停止本地等待和后续工作，不能保证远端已经接收的副作用被撤销；响应超时也不代表远端没有成功。对外部写操作要使用幂等键、状态查询、补偿或对账，结果未知时不能直接重新提交。

### 20. 如何测试并发服务的关闭流程？

答：制造生产者过快、消费者失败、下游阻塞、任务超时、context 取消和进程收到退出信号的场景；验证新任务不再进入、已启动任务有界结束、channel 关闭顺序正确、连接释放、没有 goroutine 泄漏。时间控制尽量用 fake clock、barrier 和 channel，不靠长时间 sleep。

### 21. `time.After`、`Ticker` 和定时器在长生命周期任务中有什么边界？

答：高频循环里反复创建 `time.After` 会增加临时对象和定时器压力；长生命周期任务应显式创建并停止 `Timer/Ticker`，退出时释放资源。定时器只是触发信号，不是取消协议，仍要监听 Context、处理任务重入、累计延迟和关闭顺序。

### 22. `sync.Once` 和 `sync.Pool` 分别适合什么场景？

答：`sync.Once` 保证一次初始化，适合只需创建一次且失败策略明确的共享依赖；需要重试、刷新或按租户创建时应使用显式状态机。`sync.Pool` 只适合可安全重置的临时对象复用，不能存业务状态、连接或必须命中的缓存；两者都不能替代业务锁和生命周期管理。
