# Rust 编码题与系统设计

> 递进路径：先写能通过编译器的基础算法，再把所有权、错误、并发和服务状态放进设计。

## Level 1｜基础编码题

### 1. 如何在 Rust 中实现两数之和？

答：用 `HashMap` 保存已访问值到下标，遍历时查找 `target - value`，找到后返回；时间 O(n)，空间 O(n)。需要注意整数溢出策略、重复值和借用 map 时的可变/不可变借用冲突；可以先查找，再插入，减少借用范围。

### 2. 如何合并区间？

答：按起点排序，维护当前区间；若下一个区间与当前重叠则更新右端点，否则把当前结果推入 Vec 并开始新区间。时间 O(n log n)，空间取决于排序和输出。Rust 中可以先让数据拥有 `Vec<(i32, i32)>`，避免为了借用排序而让生命周期复杂化。

### 3. 如何用迭代器实现过滤、映射和聚合？

答：`iter()` 借用元素，`iter_mut()` 可变借用，`into_iter()` 消费集合并转移元素所有权；再组合 `filter/map/fold/collect` 表达流水线。要说明惰性求值、闭包捕获和收集类型，不能把每个 iterator 链都当成一定零成本，复杂闭包仍需 profile。

### 4. 如何安全地统计文本中单词频率？

答：按明确的 Unicode/分隔规则切分，使用 `HashMap<String, usize>` 或借用切片统计；如果输入缓冲在统计期间有效，可以借用，若结果要跨越缓冲生命周期则拥有 key。要限制输入大小、处理非法 UTF-8，并决定大小写、标点和规范化策略。

### 5. 如何设计 LRU Cache 的 Rust 所有权模型？

答：核心难点不是 HashMap，而是 map、节点链表和 key/value 所有权如何同时安全维护。简单面试答案可以说明 `HashMap<K, Entry>` 加有序结构，更新访问顺序时要避免悬挂引用；生产中可以使用成熟 crate 或索引/句柄而不是手写自引用链表。还要补容量、过期、并发和缓存一致性。

## Level 2｜错误与并发编码题

### 6. 如何写一个返回 `Result` 的文件解析器？

答：边界函数把 IO、UTF-8、格式和业务校验错误分层，返回带上下文的 `Result<T, E>`；调用方用 `?` 传播可处理错误，在 API 边界映射成稳定错误码。按行读取可控制内存，错误中携带文件路径和行号但避免泄露敏感内容；测试正常、空文件、非法行、超大行和半成品输出。

### 7. 如何实现有界 async Worker Pool？

答：用有界 channel 发送任务，固定数量 Tokio task 消费；任务带 ID、deadline 和取消语义，首个关键错误通知父任务，关闭发送端后等待 workers。不要在 worker 中持有同步锁跨 `.await`，也不要把无界 `spawn` 当成并发控制；结果要区分成功、失败、超时和取消。

```rust
async fn worker_loop(
    mut rx: tokio::sync::mpsc::Receiver<Job>,
    cancel: tokio_util::sync::CancellationToken,
) {
    loop {
        tokio::select! {
            _ = cancel.cancelled() => break,
            maybe_job = rx.recv() => match maybe_job {
                Some(job) => {
                    let result = job.run().await;
                    // 生产代码需要把 result 写入状态表或结果 channel。
                    let _ = result;
                }
                None => break,
            }
        }
    }
}
```

重点是说明 channel 关闭、取消、任务状态和错误传播；示例假设 `Job::run` 已经是可取消或有界的异步操作。

### 8. 如何实现带超时的异步 HTTP 调用？

答：给真实请求 Future 包上 timeout，携带 request ID/幂等键，响应按 schema 校验并及时释放资源；区分连接失败、服务端错误、解析失败、超时和结果未知。只读请求可按策略重试，副作用请求必须查询状态或对账，不能把 timeout 直接当成没有发生。

### 9. 如何用所有权设计一个任务状态机？

答：用 enum 表达 Pending/Running/Succeeded/Failed/Cancelled 等有限状态，方法只允许合法迁移并返回新的状态或错误；状态中保存版本、租约、尝试次数和结果引用。持久化时用条件更新防止旧 worker 覆盖新状态，Rust 类型能减少非法状态，但不能替代数据库并发控制。

## Level 3｜系统设计题

### 10. 设计一个 Rust 文件索引服务，如何控制资源和恢复？

答：请求层校验路径、权限和大小，任务表保存索引版本/状态/进度，worker 通过有界 channel 和租约执行；文件按块读取，解析和索引结果分阶段提交，进程重启从 checkpoint 恢复。目录遍历、文件读取和数据库操作都需 timeout/cancel/错误分类，不能让一个坏文件拖垮整个队列。

### 11. 设计一个 Tokio 网络服务，如何避免 executor 被阻塞？

答：网络处理使用 async I/O，CPU/同步文件/外部命令放到受控 blocking 线程池或专用 worker；所有入口有并发上限、超时和响应大小限制，连接池与任务 channel 有界。通过 async trace、P95、任务数、线程池饱和和下游指标验证是否真正改善，不能只把函数标成 async。

### 12. 设计一个 Rust 工具注册和调用服务，如何处理类型和权限？

答：注册表保存工具名称、版本、输入 schema、权限 scope、超时和执行器；调用先解析/校验参数、检查租户和授权，再在受限任务中执行，返回结构化状态和调用 ID。工具版本和副作用要幂等，执行记录可回放/审计；trait 负责能力边界，权限不能只写在 trait 或 Prompt 中。

### 13. Rust 什么时候比 Go/Python 更合适？

答：当服务需要稳定的低延迟、资源上限、跨平台二进制、内存安全和编译期并发约束，同时团队能承担更复杂的类型/生命周期学习成本时，Rust 的收益更明显。快速变化的业务胶水和数据处理可能更适合 Python，简单高并发服务和团队交付可能更适合 Go；最终用基线、故障成本和维护能力验证。

### 14. 如何回答“Rust 安全所以不会有 bug”这种追问？

答：Rust 主要消除了大量内存安全和数据竞争类别的问题，不保证业务逻辑、死锁、资源耗尽、错误处理、权限和远端一致性正确。仍要设计状态机、超时、背压、审计和测试；类型安全是可靠系统的基础，不是系统验收结论。

### 15. Rust 文件/进程工具如何避免路径逃逸和资源失控？

答：先规范化路径并检查其位于允许工作区，明确符号链接和 TOCTOU 策略；启动子进程使用参数数组而不是拼接 shell，限制 cwd、环境、网络、运行时间、输出大小和子进程数量。stdout/stderr、退出码、超时和取消都要进入结构化结果，不能只返回一段字符串。

### 16. Rust Web 服务如何划分 DTO、领域验证、数据库和安全边界？

答：请求先反序列化 DTO，再做字段和业务状态验证，服务层负责状态机和幂等，Repository 负责参数化查询、连接池和短事务；迁移要版本化并验证空库/旧数据。认证、授权、CORS/CSRF、请求体/分页上限和错误脱敏属于服务合同，不能由编译器或 ORM 自动保证。

### 17. Rust 性能题如何从“零成本抽象”落到证据？

答：先在 release 构建固定输入、并发、硬件和依赖，分别测吞吐、P95/P99、内存、分配、启动和二进制大小；再用 benchmark、采样 profile、tracing、heap profiler 或 cargo bloat 定位。重点关注 clone、扩容、堆分配、Arc/锁、动态分发和缓存局部性，不凭语言宣传下结论。

### 18. 宏、unsafe 和 FFI 的面试边界是什么？

答：宏在编译期生成代码，不是运行时反射；能用函数、trait 或泛型解决时不要用复杂宏。unsafe 要缩小范围并写 SAFETY 不变量，FFI 要明确 ABI、布局、NUL 字符串、谁分配/释放、空指针、线程和 panic 边界；不能把 unsafe 当性能开关。

### 19. Rust Agent Runtime 的 Provider、Tool 和 Checkpoint 如何分层？

答：Provider Adapter 只处理认证、DTO、流式事件和错误分类，核心 Runtime 使用稳定的 `ModelOutput`/`Usage`/`ProviderError`；Tool 先做 Serde 解析、业务校验、权限和副作用合同，再执行；Checkpoint 保存版本化状态、预算、工具结果、幂等键和恢复位置。进程崩溃后要能判断动作是否发生，不能仅靠日志或内存 Vec 恢复。

### 20. 设计一个 Axum + Tokio + 数据库的 Rust API，如何处理请求、事务和取消？

答：handler 只做提取、认证和响应映射，服务层把 DTO 转成领域命令，Repository 使用短事务和参数化查询；请求 deadline 传入下游，但事务提交和外部副作用不能因为客户端断开就假设已回滚。慢 I/O、文件和 CPU 任务放入有界 worker，状态表记录任务/幂等键/版本，关闭时通过 cancellation 和 JoinHandle 有界收尾。

### 21. 设计一个 Rust FFI 文件处理库，如何保证 C/Go 调用安全？

答：导出窄的 `extern "C"` 接口和 opaque handle，输入采用指针+长度并校验空指针、溢出、UTF-8/字节和资源上限；创建与释放由同一侧配对，错误通过状态码/错误对象返回，不能让 panic 穿过 ABI。内部把 unsafe 集中在小模块，外围用拥有类型和测试证明别名、生命周期、线程和 double-free 边界。

### 22. 一个 Rust take-home 服务如何从“能跑”提升到“值得合并”？

答：先保证 README 能复现运行和测试，再补输入限制、错误分类、日志/Trace、并发上限、超时/取消、数据库/对象存储替换边界和安全默认值；测试覆盖成功、非法输入、下游失败、重复请求和优雅退出。最后列出尚未解决的生产问题、选择的取舍和可量化的下一步，不用无关抽象掩盖缺口。
