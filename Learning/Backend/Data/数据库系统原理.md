# 数据库系统原理

本篇解释不同数据库共享的底层问题；[SQL](SQL.md)、[MySQL](MySQL.md)、[PostgreSQL](PostgreSQL.md)、[Redis](Redis.md) 等文档负责具体产品实现和使用。

## 1. 数据库解决什么问题

数据库不仅是“把数据写到磁盘”，还要同时提供：

- 明确的数据模型和约束。
- 可组合的查询能力。
- 并发访问下的隔离。
- 进程或机器故障后的恢复。
- 数据量增长后的索引、分区和复制。
- 权限、审计、备份和生命周期管理。

选型应先明确一致性、查询模式、写入模式、数据规模、延迟目标和恢复目标，再讨论产品。

## 2. 关系模型与关系代数

关系模型把数据表示为关系（表）、元组（行）和属性（列）。Schema、主键、外键、唯一约束和检查约束共同定义合法状态。

关系代数的核心操作：

- 选择：按条件保留行。
- 投影：选择列。
- 并、差、笛卡尔积。
- Join：按相关条件组合关系。
- 重命名：解决属性名和关系别名问题。

SQL 是声明式语言：用户描述要什么，优化器决定如何获取。逻辑查询结果和物理执行计划必须分开理解。

## 3. 建模与规范化

规范化通过函数依赖减少冗余和更新异常：

- 1NF：属性保持原子性。
- 2NF：非主属性完全依赖整个候选键。
- 3NF：减少非主属性对候选键的传递依赖。
- BCNF：每个决定因素都是候选键。

反规范化可以减少 Join 或预先计算，但必须明确：

- 哪个字段是事实源。
- 冗余数据何时更新。
- 更新失败如何修复。
- 是否可以接受短暂不一致。

## 4. 页、记录与缓冲池

磁盘数据库通常以页为基本 I/O 单位。页内包含记录、槽目录和管理信息；记录可能定长、变长或溢出到其他页。

缓冲池把热点页留在内存中。关键问题包括：

- 页命中率。
- 脏页何时刷盘。
- 预读和顺序访问。
- 淘汰策略。
- 数据页、索引页和日志之间的竞争。

数据库内存高不一定是泄漏，可能是缓冲池主动利用内存。判断时要结合可回收性、命中率和系统换页。

## 5. 索引结构

### B+Tree

B-Tree/B+Tree 变体适合磁盘数据库，因为扇出高、树高低，范围扫描可以沿叶子节点顺序进行。

需要理解：

- 聚簇索引与二级索引。
- 联合索引的键顺序。
- 覆盖索引。
- 页分裂和填充因子。
- 随机主键对局部性的影响。

### LSM Tree

LSM 把随机写转化为内存表和顺序文件写入，通过 Compaction 合并多层数据。它通常写入友好，但读取可能要检查多个层级，并产生写放大、读放大和空间放大。

### Hash 与其他索引

Hash 适合等值查询但不天然支持范围；倒排索引适合文本检索；空间索引适合几何范围；向量索引服务近似最近邻。索引必须匹配访问模式。

## 6. 查询处理与优化

查询执行大致经历：

```text
解析 → 绑定与语义检查 → 逻辑计划 → 规则/成本优化 → 物理计划 → 执行
```

优化器要选择：

- 全表扫描还是索引扫描。
- Join 顺序。
- Nested Loop、Hash Join 或 Merge Join。
- 聚合和排序算法。
- 是否并行。

成本估计依赖行数、选择率、数据分布和相关性。统计信息过期或列之间高度相关时，估算可能严重偏差。

排查慢查询应比较“估算行数”和“实际行数”，而不是只看是否使用索引。

## 7. 事务与隔离

ACID：

- Atomicity：事务要么全部完成，要么全部撤销。
- Consistency：事务把一个合法状态转换为另一个合法状态；业务不变量仍需应用和约束共同保证。
- Isolation：并发事务的中间状态按隔离级别隐藏。
- Durability：提交结果在约定故障范围内可恢复。

隔离模型需要关注脏读、不可重复读、幻读、丢失更新、写偏差和序列化异常。MVCC 通过多版本减少读写冲突，但不等于天然串行化。

## 8. 并发控制

常见机制：

- 两阶段锁：增长阶段获取锁，收缩阶段释放锁。
- MVCC：读取符合可见性规则的版本。
- 乐观并发控制：提交时检查读写集合或版本。
- Serializable Snapshot Isolation：检测可能形成危险结构的事务。

锁粒度、锁顺序和事务长度会影响吞吐与死锁。应用层的“先查再写”必须考虑并发窗口，优先使用唯一约束、条件更新或原子语句守住不变量。

## 9. WAL 与崩溃恢复

Write-Ahead Logging 要求相关数据页落盘前，对应日志先持久化。日志通常记录足够的重做/撤销信息。

恢复需要回答：

- 哪些事务已经提交？
- 哪些修改必须重做？
- 哪些未提交修改必须撤销或忽略？
- Checkpoint 如何减少扫描范围？
- fsync 到哪里才算满足持久性合同？

提交成功只代表满足数据库当前同步策略；磁盘控制器、操作系统缓存、复制确认级别和多机故障范围也要纳入合同。

## 10. 复制、分区与一致性

复制提高读取能力和可用性，分区提高单集群容量；两者解决的问题不同。

复制设计包括：

- Leader/Follower、Multi-Leader 或 Leaderless。
- 同步、半同步或异步确认。
- 故障转移和脑裂防护。
- 复制延迟下的读一致性。

分区设计包括 Hash、范围和目录路由。需要处理热点、跨分区查询、再均衡和全局唯一约束。

Quorum 读写常写作 `R + W > N`，但这只在明确的副本、版本和故障假设下提供交集，不自动解决并发冲突和陈旧副本。

## 11. 分布式事务

常见方案：

- 2PC：协调多个参与者原子提交，但协调者和资源锁定会影响可用性。
- Saga：把长事务拆成局部事务和补偿动作，不保证中间状态不可见。
- Transactional Outbox：业务数据和待发送事件写入同一本地事务，再异步投递。
- 幂等消费与对账：把不可避免的重复和不确定结果收敛。

方案选择取决于业务不变量、可见中间态、补偿可行性和故障恢复时间。

## 12. 备份、恢复与数据生命周期

高可用不能替代备份。必须分别定义：

- RPO：最多能接受丢失多少数据。
- RTO：最多能接受恢复多久。
- 全量、增量和日志备份策略。
- 时间点恢复。
- 恢复演练和备份校验。
- 归档、删除、脱敏和审计。

没有实际恢复演练的备份，只是未经验证的希望。

## 13. 选型问题清单

1. 核心数据模型和查询路径是什么？
2. 必须守住哪些不变量？
3. 峰值读写量、数据量和增长率是多少？
4. 是否需要范围查询、全文检索、图遍历或向量检索？
5. 一致性、延迟和可用性如何取舍？
6. 如何扩容、备份、恢复和迁移？
7. 团队能否运维它，故障时是否有证据链？

## 最小实践

- 为一个订单模型写出主键、唯一约束、外键和关键检查约束。
- 对同一 Join 比较 Nested Loop、Hash Join 和 Merge Join 的前提。
- 使用执行计划定位一次估算行数偏差。
- 模拟事务并发，复现丢失更新或写偏差。
- 执行一次备份与时间点恢复演练并记录 RPO/RTO。

## 验收清单

- 能从关系模型解释 SQL，而不是只背语法。
- 能说明 B+Tree、LSM 和 Hash 索引的读写权衡。
- 能解释查询优化器为什么会选错计划。
- 能区分原子性、隔离性、业务一致性和副本一致性。
- 能描述 WAL、Checkpoint 和崩溃恢复的基本链路。
- 能为复制、分区和事务方案写出故障边界。
