# PostgreSQL 备份恢复与高可用演练

备份、复制和高可用解决的问题不同。备份回答“数据能否恢复”，复制回答“副本能否跟上”，故障切换回答“业务能否在规定时间内继续”。

## 1. 先定义 RPO 和 RTO

- RPO：最多允许丢失多长时间的数据。
- RTO：故障发生后，最多允许多长时间恢复服务。

没有 RPO/RTO，就无法判断同步复制、异步复制、归档频率和恢复演练是否满足需求。

## 2. 备份层次

- 逻辑备份：适合对象级迁移和较小数据集，恢复通常较慢。
- 物理基础备份：适合完整实例和大数据量恢复。
- WAL 归档：与基础备份结合，支持时间点恢复。
- 业务导出：补充关键业务对象校验，但不能替代数据库备份。

备份成功只证明文件产生，不证明能恢复。恢复后必须校验表、约束、序列、权限和业务不变量。

## 3. 恢复演练

在隔离环境中记录：

~~~text
备份来源与时间：
目标恢复时间点：
数据库版本和扩展：
恢复命令：
恢复耗时：
WAL 是否完整：
关键表行数/金额/状态校验：
失败点与修复动作：
~~~

至少演练：

- 从逻辑备份恢复。
- 基础备份加 WAL 时间点恢复。
- 恢复到新环境后让应用只读验证。
- 恢复失败、磁盘不足或扩展版本不匹配。

## 4. 复制与切换

副本延迟、网络分区、旧主继续接收写入和客户端连接缓存，都可能让“切主成功”变成数据分叉。

切换流程应明确：

1. 停止或隔离旧主写入。
2. 确认候选副本的 WAL 位置和延迟。
3. 提升副本并更新路由。
4. 验证应用连接、写入和关键业务不变量。
5. 防止旧主重新加入并产生脑裂。
6. 记录丢失数据窗口和后续重放方式。

只有一个 Standby 不等于自动高可用；故障检测、选主、路由和旧主隔离同样重要。

## 最小演练

使用订单服务生成一组已知订单和事件：

1. 建立基础备份和 WAL 归档。
2. 写入几笔订单后模拟实例损坏。
3. 恢复到故障前某个时间点。
4. 比较订单、幂等键、事件和账户事实。
5. 记录 RPO、RTO 和无法恢复的边界。
