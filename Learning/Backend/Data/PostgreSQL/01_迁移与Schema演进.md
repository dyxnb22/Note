# PostgreSQL 迁移与 Schema 演进

数据库迁移不是“把几条 DDL 放进脚本”，而是在线业务在多个应用版本、多个数据状态之间移动时，持续维护不变量。

## 1. 先写不变量

迁移前先写清：

- 哪些列必须非空、唯一或满足范围约束。
- 金额、状态、时间和租户字段由谁负责解释。
- 旧应用、旧数据和新应用是否会同时存在。
- 迁移失败后，允许回滚、重试还是只能前向修复。

约束优先放在数据库中。应用校验可以改善错误提示，但不能替代唯一约束、外键、检查约束和事务边界。

## 2. Expand → Migrate → Contract

跨版本发布优先采用三阶段：

1. **Expand**：增加兼容的新列、索引或表，不立即删除旧结构。
2. **Migrate**：应用双写或后台回填，逐批校验新旧值一致。
3. **Contract**：停止旧应用使用，确认回填完成后再删除旧列或旧约束。

不要把“加列、全表回填、删列”塞进一次上线事务。大表写入可能持有锁、产生大量 WAL、影响副本延迟和磁盘空间。

## 3. DDL 的风险

每一条迁移都要回答：

- 是否需要表锁或索引构建锁？
- 是否会扫描全表？
- 是否会产生大量 WAL？
- 是否能在业务流量下完成？
- 中断后再次执行是否安全？
- 旧版本应用能否继续工作？

大表索引要评估并发创建、构建时间、磁盘临时空间和失败后的清理。迁移工具的“脚本执行成功”不等于线上变更安全。

## 4. 迁移测试

至少准备三种数据库：

- 空数据库：验证从零构建。
- 上一稳定版本数据库：验证升级路径。
- 带真实分布特征的脱敏数据：验证锁、耗时、空间和执行计划。

每次迁移保存：

~~~text
数据库版本、应用版本、迁移编号、开始/结束时间
数据量、锁等待、WAL 增量、失败日志、回滚或修复命令
~~~

## 5. 常见失败

- 只在空库测试，线上旧数据触发唯一约束冲突。
- 先删除旧列，再发现旧版本实例仍在运行。
- 给高频写表增加不合适的索引，导致写延迟和 WAL 增长。
- 用应用内“先查后写”代替数据库唯一约束。
- 把不可逆的数据转换误写成可以自动回滚的迁移。

## 最小练习

给订单表增加一个可选的业务状态字段：

1. 先增加字段和兼容读取。
2. 分批从旧状态映射新状态。
3. 记录无法映射的行并暂停收紧约束。
4. 开启新写入路径。
5. 校验新旧状态，再决定是否删除旧字段。

验收标准：迁移可重复执行；中途失败可以继续；旧版本读取不会崩溃；异常数据不会被静默覆盖。
