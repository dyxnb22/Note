# PostgreSQL 连接池、并发与锁排障

数据库并发问题通常不是单个锁的问题，而是连接数、事务长度、应用超时、重试和资源上限共同形成的反馈回路。

## 1. 连接池不是数据库扩容

连接池控制应用侧并发，但不能无限增大：

- 连接数过多会放大 CPU、内存和锁竞争。
- 池等待时间会隐藏数据库饱和。
- 长事务会占用连接并阻碍旧版本回收。
- 每个服务都按自己的峰值配置，整体可能超过数据库承载。

容量估算至少同时考虑数据库最大连接数、服务实例数、每实例池大小、后台任务和运维连接。连接池上限应与超时、排队和降级策略一起设计。

## 2. 事务边界

事务内只保留必须共同成立的数据库不变量：

- 不要在事务中等待外部 HTTP。
- 不要让用户输入或模型输出决定无限长事务。
- 读取后长时间思考再写入时，重新确认事实是否仍有效。
- 发生序列化失败、死锁或连接断开时，重试整个事务而不是只重放一条语句。

## 3. 锁排障路径

排查顺序：

1. 找到正在等待的会话。
2. 找到阻塞它的持锁会话。
3. 查看持锁事务开始时间和最后活动。
4. 关联应用请求、用户、实例和部署版本。
5. 判断是正常竞争、长事务、忘记提交、DDL 还是异常重试。
6. 先保护业务，再决定取消会话、回滚发布或修复代码。

不要只看“锁数量”。必须知道锁等待时间、阻塞链和业务影响。

## 4. 队列与并发更新

使用 SKIP LOCKED 领取任务时，还需要：

- 任务状态和租约时间。
- Worker 崩溃后的重新领取规则。
- 最大重试次数和死信。
- 任务处理的幂等键。
- 长时间占用任务的监控。

行锁只能协调当前数据库事务，不能替代跨系统幂等、外部副作用确认和补偿。

## 5. 故障练习

构造以下场景：

- 一个事务持锁，另一个事务等待。
- 事务超过应用请求超时但数据库仍在执行。
- 多个 Worker 竞争同一批任务。
- 两个事务以相反顺序更新资源，形成死锁。
- 数据库短暂不可用，应用开始重试。

验收标准：

- 能从等待会话找到根因。
- 客户端取消不会让后台事务无限运行。
- 死锁或序列化失败重试不会产生重复业务事实。
- 连接池耗尽时服务有明确的错误和降级行为。
