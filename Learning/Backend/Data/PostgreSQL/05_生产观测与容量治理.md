# PostgreSQL 生产观测与容量治理

数据库观测要同时覆盖请求、连接、事务、锁、I/O、WAL、表膨胀、副本和备份。单看 CPU 或 QPS，无法解释多数生产问题。

## 1. 最小观测面

| 层次 | 指标 |
|---|---|
| 请求 | 查询次数、耗时分位数、错误和取消 |
| 连接 | 活跃、空闲、池等待、连接建立失败 |
| 事务 | 持续时间、提交/回滚、序列化失败、死锁 |
| 锁 | 等待时长、阻塞链、长事务 |
| 存储 | 数据文件、WAL、临时文件、磁盘水位 |
| 维护 | Autovacuum、Dead Tuple、表/索引膨胀 |
| 复制 | LSN、延迟、复制槽、接收/回放状态 |
| 备份 | 最近成功时间、WAL 连续性、恢复演练结果 |

指标需要绑定数据库、实例、表或查询指纹，但不要把用户 ID、订单 ID 等高基数字段直接作为标签。

## 2. 告警不是阈值堆积

每条告警都要包含：

- 用户影响或数据风险。
- 可能原因和排查入口。
- 立即缓解动作。
- 升级条件和责任人。
- 恢复后的验证与复盘。

例如“磁盘增长”不只提示空间不足，还要区分数据增长、WAL 保留、复制槽失联、临时文件和日志膨胀。

## 3. 容量模型

容量估算至少考虑：

~~~text
峰值请求 × 每请求 SQL 数 × 事务/连接占用
数据增长 × 索引膨胀 × 备份/WAL 保留
副本数量 × 恢复临时空间 × 扩容迁移空间
~~~

压测不能只报告吞吐量。应同时记录 p95/p99、错误率、连接池等待、CPU、内存、I/O、WAL 和副本延迟。

## 4. 维护策略

- Autovacuum 参数按表的写入量、行宽和更新模式评估。
- 长事务要有发现、归属和终止策略。
- 大表、热点索引和高频更新表单独做容量预算。
- 备份、VACUUM、索引构建和批处理要避免同时争抢资源。
- 任何自动清理都必须有保护条件和恢复路径。

## 最小项目

为订单服务建立数据库 Runbook：

1. 制造慢查询、连接池耗尽、锁等待和副本延迟。
2. 采集指标、日志和查询计划。
3. 按 Runbook 找到根因并恢复。
4. 回写告警阈值、误报和未覆盖场景。

只有另一位读者能够依照 Runbook 完成排查，才算形成可复用能力。
