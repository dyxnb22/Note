# PostgreSQL 查询计划与性能诊断

性能诊断的目标不是“看到全表扫描就加索引”，而是解释估算、实际执行、数据分布、锁等待和资源消耗之间的差异。

## 1. 固定问题边界

记录完整请求路径：

~~~text
用户请求 → 应用排队 → 连接池等待 → SQL 执行
→ 锁等待/I/O/CPU → 返回应用 → 序列化与网络
~~~

先确认数据库是否是瓶颈。只看 SQL 自身耗时，可能把连接池耗尽、下游超时或应用排队误判成慢查询。

## 2. 读取计划

对读查询优先比较：

- 估算行数与实际行数。
- 访问路径是否符合数据选择性。
- Join 两侧输入规模是否符合预期。
- Sort、Hash 是否产生临时文件。
- Buffer 命中和实际读取。
- 是否发生锁等待。

EXPLAIN ANALYZE 会真正执行语句。对写语句必须在安全的可回滚事务或隔离副本中运行，不能把诊断命令直接复制到生产环境。

## 3. 估算错误的来源

常见原因包括：

- 统计信息过期。
- 多列之间存在相关性，但优化器按独立分布估算。
- 数据倾斜或热点值。
- 表在短时间内发生大量写入。
- 表达式、隐式类型转换或函数让索引无法匹配。
- 测试数据太小，无法代表线上分布。

修复顺序应是：确认数据和统计信息 → 检查 SQL 语义 → 检查索引 → 评估结构改变。不要先强制索引或把所有查询改成 Nested Loop。

## 4. 索引的成本

索引同时带来：

- 读取路径选择。
- 写入、更新和删除的额外成本。
- 存储和备份体积。
- VACUUM 与维护成本。
- 优化器选择空间变大。

候选索引必须用代表性数据验证选择性、计划稳定性、写入影响和容量。部分索引、表达式索引和覆盖索引都要与实际查询谓词保持一致。

## 最小练习

为订单查询准备小数据、偏斜数据和大数据三组样本，分别比较：

1. 无索引、单列索引、组合索引。
2. 等值过滤、时间范围和排序。
3. 估算行数与实际行数。
4. 低选择性条件下优化器为什么选择顺序扫描。

验收标准：能解释计划变化，而不是只报告“加索引后变快”。
