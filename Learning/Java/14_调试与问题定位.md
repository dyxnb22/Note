# 14 调试与问题定位

定位故障要把观察与解释分开。响应变慢是现象，线程池、连接池、SQL 或远端等待是不同候选原因；先确认时间、版本与受影响范围，再让证据排除假设，最后验证改动是否解除同一条故障链。

## 从现象建立可比较的边界

先固定输入、负载、环境和数据，区分平均延迟与尾延迟、失败请求与成功请求、单实例与全服务。Trace 将一次请求拆成获取资源、执行与等待，日志用请求 ID 或业务号说明状态变化；两者需要对齐时间与版本。

“线程多”“CPU 低”“数据库有慢查询”都不足以单独证明根因。例如 RUNNABLE 可以包含本地 I/O 等待，WAITING 也可能只是空闲工作线程，必须结合栈位置、持续时间和资源指标理解。

## 一个连接池耗尽的推理过程

假设服务有 10 个数据库连接，SQL 本身只需几十毫秒，但事务中还等待一个耗时约 5 秒的远端调用。若整个过程都持有连接，每秒可完成量会受到约 10/5 的资源容量限制；继续增加 HTTP 工作线程主要增加等待者。

| 观察 | 支持或排除的解释 | 下一步证据 |
|---|---|---|
| SQL 执行耗时稳定，获取连接等待升高 | 不能只归因于 SQL 变慢 | 分开记录连接获取、占用与 SQL 时间 |
| 池活跃连接长期达上限 | 连接不足以满足当前占用需求 | 找到哪些调用持有连接、何时归还 |
| 线程栈持续等待获取连接 | 请求被资源池阻塞 | 与同一时间窗的池等待指标对应 |
| 已获取连接的请求在等待远端响应 | 长占用可能来自事务范围 | 对照事务边界与远端调用的 Trace |

修复应缩短不必要的资源占用，并同时保护业务一致性。若把远端动作移出事务，就要重新定义本地事实、待办状态、幂等和恢复，不能只删掉注解。修复后在相同负载下比较连接占用、等待、吞吐、错误率和原业务不变量。

## 让工具回答一个具体问题

CPU 持续高时用采样定位热点，再区分计算、GC、重试、自旋或正则回溯；单次线程栈只是一个瞬间，持续热点需要多次采样与 CPU 数据相互印证。

等待或死锁可通过 jcmd 的 Thread.print -l、线程栈与锁依赖观察。堆增长则比较 GC 后存活量，沿支配树与 GC Roots 找到持有者；堆外增长还需结合 Native Memory Tracking 与进程指标。堆转储的开销与数据范围要先评估，工具选择对应[JVM 的资源分类](04_JVM.md#OOM%20的资源分类)。

业务状态问题则沿订单、任务或消息 ID 还原时间线。客户端超时、数据库提交、消息投递和远端执行可能有不同结果，必须查询相应事实，不能根据一个异常就推断整条链路回滚。

## 从最小修复得到回归证据

保留能触发原因的最小输入与失败条件，验证正常、重复、超时、取消和关闭等相关路径。测试应观察不变量或可见行为，而非仅复述修改后的代码。

编译与打包成功不代表测试实际运行，测试通过也不代表已经完成外部联调。分别保存运行数量、关键断言、真实请求与响应，以及尚未覆盖的边界，才知道修复结论成立到哪里。跨组件失败语义见[可靠性与一致性](../Architecture/04_可靠性与一致性.md)。
