# 07 Java 数据访问

一次数据库调用同时涉及查询语义、连接生命周期、事务与对象状态。先沿请求理解这些边界，再选择 JDBC、MyBatis 或 ORM，才能解释为什么 SQL 本身很快，接口仍可能等很久。

## 应用与持久化的职责

```text
Controller：协议输入与输出
→ Application Service：业务用例与事务边界
→ Repository / Mapper：持久化合同
→ JDBC / ORM：执行、映射与对象管理
→ Connection Pool：借还连接
→ Database：约束、事务与访问路径
```

Repository 表达领域所需的读写能力，复杂报表可使用独立查询模型，不必让所有查询都变成聚合实体操作。接口 DTO、领域对象与持久化模型是否分开，取决于变化边界，不能把某一种分层命名当成所有项目的强制结构。

实体直接进入 Web 响应，可能暴露持久化字段、触发额外查询或在上下文关闭后访问未加载关系。ResultSet、游标与流也携带资源生命周期，向上透传时必须明确由谁消费和关闭；只是把返回类型改为 Stream，并不会自动释放连接。

## JDBC 资源与参数化查询

JDBC 流程是取得连接、准备语句、绑定值、执行、映射结果并释放资源。连接池让 close 通常归还逻辑连接；独立 JDBC 代码应使用 try-with-resources，框架事务中的连接则通过框架约定获取和释放，不能随意绕过其绑定机制。

下面的片段假定 connection 由调用方管理，负责关闭自身创建的语句和结果集：

```java
String sql = "SELECT id, amount FROM orders WHERE user_id = ? AND status = ?";
try (PreparedStatement statement = connection.prepareStatement(sql)) {
    statement.setLong(1, userId);
    statement.setString(2, status);
    try (ResultSet rs = statement.executeQuery()) {
        while (rs.next()) {
            long id = rs.getLong("id");
            BigDecimal amount = rs.getBigDecimal("amount");
            // 在约定范围内转换为需要的结果，不向外返回 rs。
        }
    }
}
```

参数绑定区分 SQL 结构与值，不把值重新解释为拼接后的 SQL 语法。PreparedStatement 是否使用服务端预编译或驱动模拟，要看驱动与配置，安全性不能简化为“服务端一定先解析一次”。动态列名、表名、排序方向仍需固定映射或允许列表，不能作为普通值参数替代结构。[应用安全](../Architecture/应用安全.md)进一步解释注入边界。

### 大结果集与流式消费

驱动的默认取数与缓冲行为并不统一，fetchSize 通常也不能脱离驱动条件保证固定内存。分页、游标、流式读取都要结合事务、结果集模式与关闭规则验证；例如 pgJDBC 游标取数要求关闭自动提交、使用前向结果集和适当 fetchSize 等条件。[pgJDBC 查询与游标](https://jdbc.postgresql.org/documentation/query/)

大导出还要限制并发、持续时间与下游写入速度。JPA Stream 或 Hibernate ScrollableResults 仍受持久化上下文和连接占用约束，持续处理大量实体时也要控制上下文规模。

## 连接池容量与等待

单实例池上限乘以实例数，再加后台任务、运维与其他应用连接，应留在数据库可承担的总预算内。增加池容量可能增加锁竞争、上下文切换和排队，并不保证吞吐增长；容量最终依真实混合负载下的吞吐、尾延迟与资源占用确定。

获取连接超时只限制借连接阶段，不等于 SQL 超时、锁等待超时或整个请求 deadline。idle、active、pending 与持有时长需要同时观测，才能区分连接不足、使用缓慢与长期未归还。

### HikariCP 的回收与告警

maxLifetime 控制连接总生命周期，但不会在借出期间强行回收；keepaliveTime 面向池内空闲连接，idleTimeout 又是另一类闲置回收规则。数据库、代理的总寿命与空闲超时应分别确认，不能统一把所有空闲限制机械当成连接总寿命。

leakDetectionThreshold 在借用时间过长时提供获取位置的线索，长事务同样可能触发，不代表堆栈所在位置已经被证明是真正泄漏。配置需结合相应版本约束、回收与保活行为。[HikariCP 配置](https://github.com/brettwooldridge/HikariCP#configuration-knobs-baby)

### 从等待连接追到实际持有者

getConnection 超时只说明某次借用没及时完成。把同一时段的池指标、应用线程、事务时长与数据库会话对齐，查看已借出连接在执行 SQL、等待锁、等远端还是已经遗失释放路径；大量等待者的栈本身不包含全部持有者信息。

## MyBatis 的映射与缓存

MyBatis 保留 SQL 控制权并提供参数和结果映射。普通值使用 #{} 绑定，${} 是文本替换，结构元素必须经过允许列表；动态 SQL 还要定义空集合、可选条件与批量大小的行为。

常见 Mapper 代理把映射方法定位到语句并交给 SqlSession 执行，继承、默认方法与注解映射等也有各自处理路径。相应 namespace 与 statement id 要一致，映射方法不宜依赖重载区分；创建代理的时机也不必然都是应用启动时。

### 会话缓存与 namespace 缓存

一级缓存通常是 SqlSession 范围，也可将 localCacheScope 设为 STATEMENT；一次接口调用或整个 HTTP 请求不天然等于同一个会话。会话缓存可能返回同一对象引用，修改结果也会影响后续观察。[MyBatis 会话与缓存](https://mybatis.org/mybatis-3/java-api.html)

二级缓存需显式配置，namespace 的更新失效并不自动覆盖所有跨表、跨 namespace 与外部写入。应用层查询缓存也一样要说明一致性与失效，不能只换一个位置就解决问题。插件还可能改变 SQL 与缓存行为，应验证插件组合的顺序。

### PageHelper 与分页上下文

常见 PageHelper 用法通过线程上下文把分页参数交给后续查询拦截器。正常拦截路径通常包含清理，但设置后没有执行预期查询等分支仍需按使用版本与 API 管理作用域；同线程后续 SQL 可能误消费遗留参数。

count 与数据页通常是分开的查询，不自动拥有同一快照。深分页的成本也取决于数据库访问路径，不是引入插件就能消除。

## 深分页与稳定游标

基于 offset 的查询通常仍需访问并跳过前面的候选行，深度增大就可能放大工作量。索引覆盖、先取主键再关联可以减少部分代价，keyset 则沿上次位置继续查，但失去廉价任意跳页的能力。

```sql
SELECT id, created_at, amount
FROM orders
WHERE created_at > :last_time
   OR (created_at = :last_time AND id > :last_id)
ORDER BY created_at, id
LIMIT :page_size;
```

这是使用命名参数框架的 SQL 示意，实际还需匹配索引、固定过滤条件，并约定首屏与游标编码。末尾加入唯一键能解决同值排序不确定性，但排序字段变化或跨页可见数据变化仍可造成跳过或重复；需要稳定快照的导出应另行设计快照、边界或不可变排序键。

## JPA、上下文与对象状态

JPA 标准与 Hibernate 等实现需要区分。持久化上下文跟踪托管实体及其状态，flush 将待执行变更同步到数据库，不等于事务已经 commit；flush 的触发也不只在代码显式调用时。

### N+1 与查询模型

若每个列表元素再懒加载关联，SQL 数量会随结果规模增长。fetch join、EntityGraph、批量抓取或独立投影查询都可能改善，但集合抓取与分页的组合还要查看生成 SQL、行数和内存，不能只数接口返回对象。

### 延迟加载与会话生命周期

脱离相应上下文后，访问尚未初始化的懒加载关系通常会失败；事务提交是否使实体脱管取决于上下文管理方式，不能把 commit 与 detach 画等号。关闭上下文、显式 detach/clear 等才是需要追踪的对象状态变化。[Hibernate 持久化上下文](https://docs.hibernate.org/orm/6.6/userguide/html_single/#pc)

Open Session in View 可将上下文延至 Web 请求末尾，但不保证全程占着同一连接，也不会把后续查询自动纳入先前事务。其代价是隐藏查询、事务外访问与资源时间不易察觉，应由明确的取数范围与时机约定决定是否采用。

### 脏检查与批量更新

脏检查可基于快照比较，也可能结合字节码增强，不能断言所有实现每次都逐字段扫描。大批量场景应比较实体更新与 bulk DML 的成本和语义：后者通常绕过实体回调与当前托管状态，需要刷新、清理或重新加载来避免陈旧对象，不能与脏检查路径盲目混用。

## 事务边界与远端副作用

业务用例确定本地事务范围，约束、条件更新与锁保护数据库事实。“先查没有，再插入”仍需唯一约束或等价并发控制。完整传播、代理可见性、回滚规则见[Spring 核心](08_Spring核心.md)，不要把非 public 方法或被 catch 的异常一律判断为事务失效。

REQUIRES_NEW 使用独立事务时会改变提交关系并可能多占连接；NESTED 依赖保存点支持，外层回滚仍撤销其结果。二者都要满足实际代理调用和资源管理器条件。

RPC、邮件与外部消息不能被本地数据库 rollback 撤销。提交后回调仅解决触发时机，无法单独保证交付；需要恢复能力时，业务数据与 Outbox 记录同事务写入，再由投递者去重、重试和对账。见[任务、消息与补偿](../Architecture/05_任务、消息与补偿.md)与[可靠性与一致性](../Architecture/04_可靠性与一致性.md)。

## 读写分离与读己之写

复制延迟可能使写后读走副本时看不到最新事实。关键读走主库、按会话暂时粘主、等待回放到已知位点，分别有不同成本；固定等待 N 秒只是窗口假设，不是延迟超过窗口时仍成立的保证。

观测应覆盖写入到副本可见的业务时延，并结合位点、复制状态与路由。单一延迟指标和网络连通性不足以证明某次读已能看到自己的写入。

## 死锁、锁等待与事务重试

MySQL/InnoDB 的死锁通常回滚被选中的整个事务；锁等待超时在默认配置下通常只回滚当前语句，也可受相关配置影响。不能把两种失败都当成“事务已自动全部回滚”，应先确定当前状态，再在干净事务边界内重试可重放用例。[InnoDB 错误处理](https://dev.mysql.com/doc/refman/8.4/en/innodb-error-handling.html)

重试要有次数、退避与总预算，还需保护已发生的外部副作用。缩短持锁、统一更新顺序、使用正确索引与条件更新可减少冲突；数据库证据与锁机制见[MySQL](../Data/MySQL.md)。

## Schema 兼容演进

先增加兼容结构，发布能兼容新旧结构的代码，再回填、校验、切换读写，观察后删除旧结构。版本化迁移需明确执行归属与锁机制，存量库接入还要核对基线，不能因工具显示成功就认定数据语义正确。

应用回滚与 Schema 回滚是两件事，破坏性 DDL 和回填未必可逆。大表变更应按具体数据库算法评估锁、回放延迟、磁盘与恢复；INSTANT、INPLACE 和影子表工具各有条件，不是通用的无锁开关。生产结构不应依赖 ORM 临时推断。

## 多数据源与路由时机

独立数据源需明确由哪个事务管理器管理；多个独立数据库资源通常不能由同一个普通本地事务原子提交。优先让必须强一致的修改落在同一资源边界，跨资源再设计一致性协议与补偿。

AbstractRoutingDataSource 在实际取得目标连接时选择路由，连接已绑定后改路由键不会自动换库；普通事务管理器可能在开始时取连接，延迟连接代理则可能推迟。因此路由上下文应在相应获取与事务边界前设置，并在结束时恢复，不能只看注解在源码中的位置。

## 用目标数据库验证行为

纯映射和逻辑可快速验证，约束、方言、锁、隔离与迁移则需目标数据库版本的集成场景。H2 能帮助验证某些调用和事务边界，但不能据其通过就证明 MySQL 或 PostgreSQL 的特定锁行为成立。

让场景包含空集、NULL、重复值、并发更新、失败回滚与旧结构升级，并核对生成 SQL、真实提交结果与资源释放。这样验证的是持久化行为与约定，而非仅确认一个 Repository 方法成功返回。
