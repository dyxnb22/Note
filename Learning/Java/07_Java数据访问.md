
# Java 数据访问

## Java 数据访问应该如何分层？

```text
Controller
→ Application Service：用例与事务边界
→ Repository / Mapper：持久化合同
→ JDBC / ORM
→ Connection Pool
→ Database
```

Repository 表达**领域需要的读写能力**，不应只是数据库表的机械镜像；复杂报表和查询可以使用专门 Query Service，避免把聚合查询硬塞进领域实体。

### DO/Entity/DTO 的转换应该发生在哪一层？

DO/PO 只存在于 Repository 层；Service 收发 DTO；Web 层只看到请求/响应模型。把 ORM 实体直接透传给 Controller 有两个后果：懒加载代理越过会话后访问就抛异常，以及表结构变化直接泄漏成接口字段变化。

### 为什么 Service 层不该出现 SQL 拼接和 ResultSet？

SQL 是持久化合同的实现细节，散落到用例层之后，改索引、拆表都要动业务代码。ResultSet 绑定着连接的生命周期，向上透传等于把连接占用扩散出数据访问层。Service 只应依赖领域语义的方法（如 `findPayableOrders`），不依赖查询机制。

## JDBC 查询如何避免资源泄漏和 SQL 注入？

JDBC 的基本流程是**获取连接、创建参数化语句、执行、映射结果并释放资源**。实际项目应使用连接池和 `try-with-resources`，不要为每个请求建立物理连接。

必须使用参数绑定：

```java
String sql = "SELECT id, amount FROM orders WHERE user_id = ? AND status = ?";
try (PreparedStatement statement = connection.prepareStatement(sql)) {
    statement.setLong(1, userId);
    statement.setString(2, status);
    try (ResultSet rs = statement.executeQuery()) {
        // 显式映射需要的列
    }
}
```

**参数绑定解决值注入问题**，但动态表名、列名和排序方向不能作为普通参数绑定，必须**使用白名单映射**。注入的完整攻击面（拼接、二阶注入、批量接口）见 [应用安全](../Architecture/应用安全.md)。

### PreparedStatement 为什么能防注入？

预编译把 SQL 结构和参数分开：语句模板先完成语法解析，参数只作为值绑定，不参与语法解析。拼接进来的 `1=1` 在参数位上只是普通字符串，成不了语法的一部分。所以防线是"结构白名单 + 值参数化"两条腿，缺一不可。

### 大结果集怎么避免 OOM？

默认驱动会把整个结果集拉进内存。三种处理：分页取；游标/流式读取（MySQL 用 `fetchSize=Integer.MIN_VALUE` 或 `useCursorFetch`，PostgreSQL 要求 `autocommit=false` + fetchSize），逐批消费；JPA 侧用 `Stream`/`ScrollableResults` 并在事务内及时关闭。导出、对账类任务走异步批处理，不走同步接口。

## Java 连接池大小如何确定，连接池耗尽又该如何排查？

**连接池容量不是越大越好**。它受到数据库最大连接数、服务实例数、查询耗时和峰值并发共同约束：

```text
数据库连接预算
÷ 服务实例数
≥ 单实例连接池上限 + 运维余量
```

需要同时配置获取**连接超时、连接存活检测、最大生命周期和泄漏检测**。连接池耗尽通常是**慢 SQL、长事务、连接未释放或下游拥塞的结果**，而不只是池太小。

### 池到底应该配多大？

经验起点是"连接数 ≈ 数据库 CPU 核数 × 2 + 磁盘数"这类按等待/计算比估算的公式，本质是：连接主要在等磁盘和网络时，少量并发就能打满吞吐；超过之后吞吐不涨，上下文切换和锁竞争反而上升。**最终值靠真实负载压测的 p99 定**，不是拍一个 100。

### HikariCP 为什么快，配置上最该盯什么？

快在精简字节码、无锁的 ConcurrentBag 借还、预编译代理类。对使用方更要紧的是两个参数：`maxLifetime` 必须**小于数据库侧 `wait_timeout` 和中间件的空闲回收**，否则会拿到已被服务端关闭的连接；`leakDetectionThreshold` 让未归还的连接打印获取时的堆栈，直接定位泄漏点。

### 连接池耗尽怎么排查？

现象是 `getConnection` 等待超时。顺序：先看池指标（active/idle/waiting）；再抓线程 dump，大量线程栈停在等待连接处，往上找第一个持锁的线程在干什么——慢 SQL、事务内调 RPC、还是借了不还；最后对齐数据库侧 processlist 和锁等待。**多数结论是"用得慢或不还"，不是"池太小"**。`wait_timeout`、锁等待和 processlist 的数据库侧细节见 [MySQL](../Data/MySQL.md)。

## MyBatis 如何控制 SQL、安全和缓存边界？

MyBatis 让开发者保留 SQL 控制权，并负责参数映射和结果映射，适合查询复杂、需要精细优化的系统。

- `#{}` 使用**预编译参数**，普通值必须优先使用它。
- `${}` 是**文本替换**，只能用于经过白名单映射的结构元素。
- 动态 SQL 要覆盖空集合、可选条件和批量大小边界。
- 一级缓存属于会话范围；二级缓存会增加一致性和失效复杂度，不应默认开启。
- 插件会影响执行器、参数、结果或 SQL，必须限制职责并测试顺序。

Mapper 方法应体现业务查询意图，例如 `findPayableOrders`，而不是暴露无限组合的通用条件对象。

### Mapper 接口为什么没有实现类也能注入？

启动时为接口生成 JDK 动态代理（`MapperProxy`）：方法调用按"接口全名.方法名"定位到映射语句 id，再转发给 `SqlSession` 执行。由此能推出几条工程约束：方法名要和 statement id 对齐、接口不宜重载、返回类型决定映射方式。

### 二级缓存为什么生产默认关？

缓存粒度是 namespace，一次跨表更新要推理哪些 namespace 失效，集群下还有跨节点一致性问题，收益被失效复杂度吃掉。需要缓存在应用层做：缓存领域查询结果，写明失效条件，语义可控。

### PageHelper 的原理和坑？

`ThreadLocal` 传递分页参数 + 拦截器改写 SQL 追加 `LIMIT`，count 语句单独执行。经典坑：分页参数消费后没清理，"污染"下一条本不该分页的 SQL；count 与数据页分两次查询导致不一致。深分页本身慢是数据库扫描机制问题，见下一题——`LIMIT offset` 的代价和索引关系见 [MySQL](../Data/MySQL.md)。

## 深分页为什么慢，Java 侧怎么优化？

`LIMIT 1000000, 20` 要求数据库扫描并丢弃前 100 万行，页越深越慢。三条路：

- **游标/keyset 分页**：`WHERE id > #{lastId} ORDER BY id LIMIT 20`，每页只走索引定位，代价是不能跳页。
- **延迟关联**：子查询先只取主键分页，再用主键回表取整行，减少回表量。
- **业务上限**：限制可翻页深度，深浏览场景（导出、对账）改异步任务。

### keyset 分页怎么处理排序键不唯一？

用复合游标 `(sort_col, id)` 做双键比较，保证顺序稳定且不漏不重。游标分页和"跳到第 N 页"的产品交互天然冲突，设计时二选一。

## JPA/ORM 适合什么场景，有哪些常见风险？

JPA/ORM **适合实体关系清晰、以聚合读写为主的场景**，优势是**对象映射、脏检查和统一持久化模型**。需要注意：

- N+1 查询。
- 懒加载越过事务边界。
- 级联操作扩大写入范围。
- 批量更新绕过当前持久化上下文。
- 对象模型与高性能报表查询之间的张力。

复杂查询可以使用投影、原生 SQL 或独立查询模型，不必强迫所有数据访问都经过实体图。

### N+1 怎么发现、怎么解决？

发现：看 SQL 数量是否随结果集大小线性膨胀（日志、监控打点）。解决：`join fetch`、`@EntityGraph`、`@BatchSize` 批量取；更常用的是拆查询模型——列表页只要 ID 和摘要字段，详情页再按需取关联。

### LazyInitializationException 的根因是什么？

懒加载代理只能在持久化上下文（Session/EntityManager）存活期间初始化；事务提交后实体脱管，访问未加载的关联就抛异常。正确解法是把读取放进事务边界内，或用 fetch join 显式取数；Open Session in View 只是把问题推迟到请求线程，还拉长了连接占用，不该作为默认。

### 脏检查什么时候变成性能事故？

flush 时把实体快照逐字段对比。把大结果集整批 load 进持久化上下文再改个别字段，flush 的对比成本和内存都失控；大批量更新应该用 bulk update（`UPDATE ... WHERE`）绕开实体。注意 bulk update 不触发 `@PreUpdate` 等回调，也不同步一级缓存中的实体，两套路径不能混用。

## Java 应用的事务边界应该如何设计？

事务通常放在 Application Service 的**完整业务用例**上。事务内应避免长时间远程调用、文件处理和用户等待。

要明确：

- 事务隔离级别及并发异常。
- 哪些异常触发回滚。
- 多数据源和读写分离时连接来自哪里。
- 消息发布与数据库提交如何保持一致。
- 重试发生在事务内还是事务外。

唯一约束、条件更新和锁用于**保护数据库事实**；应用层的"**先查再写"不能代替并发控制。**

### @Transactional 什么时候会失效？

同类自调用（绕过代理）、非 public 方法、异常被 catch 吞掉、默认只回滚 `RuntimeException`/`Error`（受检异常要 `rollbackFor`）、传播行为配错、以及在新线程里操作导致事务上下文不跟随。每次都要能回答"这次调用走没走代理"。

### REQUIRES_NEW 和 NESTED 有什么区别？

`REQUIRES_NEW` 挂起当前事务，开独立事务，内层提交后外层回滚也影响不到它——"操作日志必须留存"用这个。`NESTED` 是保存点：内层回滚到保存点，外层回滚则整体回滚。二者对"外层失败"的语义完全不同。

### 事务里能不能调 RPC、发消息？

原则：**事务内只做可回滚的本地操作**。RPC 和 MQ 是外部副作用，回滚不掉，还拉长持锁时间。一致的做法：把副作用挪到提交之后（`TransactionSynchronization.afterCommit`、领域事件），或者用 Outbox 表——业务行和消息行同一本地事务写入，再由独立投递器发送。Outbox、本地消息表与对账见 [任务、消息与补偿](../Architecture/05_任务、消息与补偿.md) 和 [可靠性与一致性](../Architecture/04_可靠性与一致性.md)。

## 读写分离后怎么保证"读己之写"？

写后立即读被路由到从库就读不到。按场景选：关键读强制走主库（注解或 Hint）；会话粘性（同一用户写后 N 秒内的读路由主库）；位点/GTID 等待（确认从库回放到写事务后再读）；或前端短缓存过渡。方案要写明延迟窗口和失效条件，不能默认"反正最终一致"。

### 主从延迟的监控口径是什么？

不是 ping 通不通，而是"主库最新写入在从库可见"的端到端延迟：以 GTID/位点回放延迟为基础，业务侧再对"写入→从库可读"打点。路由切换和降级阈值按这个口径定，`Seconds_Behind` 之类指标有已知盲区，不能单独作为依据。

## 数据库死锁和锁等待超时，Java 侧怎么处理？

死锁由数据库判定并回滚一方（MySQL 错误 1213，锁等待超时 1205）。Java 侧要**分类处理**：识别这两类错误码，只对可重放的事务做有限次重试，重试前重读状态、加退避，不能把所有 `SQLException` 一律重试——不可重放的事务重试就是重复副作用。

### 应用侧怎么减少死锁？

缩短事务、多表加锁固定顺序、批量操作先排序再统一顺序提交、用条件更新和唯一约束替代"先查再写"。锁的机制、`SHOW ENGINE INNODB STATUS` 的解读见 [MySQL](../Data/MySQL.md)。

## Java 项目的数据库 Schema 变更如何发布？

Schema 变更应通过版本化迁移工具管理，并**满足向前、向后兼容的发布窗口**。常见顺序是：

1. **先增加兼容的新列或新表。**
2. **发布同时兼容新旧结构的代码。**
3. **回填和校验历史数据。**
4. **切换读写路径。**
5. **观察稳定后再删除旧结构。**

不要让 ORM 在生产环境中自动推断并修改 Schema。

### Flyway/Liquibase 怎么避免多实例并发迁移？

迁移工具靠数据库锁保证同一时刻只有一个执行者；流水线里也应固定由单实例执行迁移再滚动发布。存量库首次接入用 baseline 建立版本基线。变更脚本和代码一起 review、一起回滚演练，`ddl-auto` 类自动建表只允许出现在开发环境。

### 大表变更为什么需要 Online DDL？

直接 DDL 可能长时间锁表、主从延迟放大。用 gh-ost/pt-osc 这类影子表工具，或 MySQL 8 的 INSTANT/INPLACE 能力；即便如此也要评估磁盘翻倍、外键和大表回填的影响。哪些 DDL 走哪种算法，机制见 [MySQL](../Data/MySQL.md)。

## 多数据源和动态数据源怎么管理事务？

固定多数据源：每个数据源独立 `DataSource` + `TransactionManager`，事务显式路由到对应管理器；跨库写没有本地事务，靠业务设计避免或走最终一致。动态路由（租户、读写分离）：`AbstractRoutingDataSource` 在**获取连接那一刻**决定路由键，所以路由键必须在事务开启前设置——事务开始后再切库是无效的。

### 跨库还能怎么办？

优先从建模上避免：把强一致的聚合放进同一个库；跨库读用 API/事件聚合；跨库写用明确的补偿或最终一致方案。不要为了省一次拆分而引入分布式事务。

## 如何验收 Java 数据访问能力？

- Repository 是否在真实数据库或容器化数据库上做集成测试？
- 唯一约束、外键、事务回滚和并发更新是否验证？
- SQL 是否覆盖空集、NULL、重复值和时间边界？
- 慢查询、连接池耗尽和死锁是否有可观测数据？
- 数据库迁移能否从旧版本实际升级并回滚应用？

### 集成测试用 H2 还是 Testcontainers？

H2 快，但方言行为和 MySQL/PostgreSQL 不同——锁行为、隔离级别、函数、执行计划都对不上，死锁和锁等待这类题在 H2 上根本复现不了。核心路径用 Testcontainers 起真实库，纯逻辑单测不碰数据库；两者按"验证什么"分工，不用一个替代另一个。
