# 设计模式：从变化点到可维护代码

设计模式不是要背下来然后套进代码的“标准答案”，而是对**反复出现的设计问题及其权衡**起名字。学模式时，重点不是记结构图，而是能解释：原代码哪里难改、模式把哪种变化隔离了、为此增加了什么复杂度。

## 先判断问题，再考虑模式

看到大量 `if/else`、一堆包装类或很多接口，并不意味着一定要引入模式。先厘清以下几点：

1. **什么在变化？** 是算法、对象创建、外部接口、对象状态，还是处理步骤？
2. **变化是否会持续发生？** 如果需求稳定、变化点只有一处，直接实现通常更清晰。
3. **希望变化被限制在哪里？** 例如只新增一个策略类，而不修改调用方；或只在系统边界适配第三方接口。
4. **抽象的代价是否值得？** 模式会带来类、间接调用和理解成本；只有它减少的未来修改成本更大时才值得引入。

一个实用的判断标准是：**未来新增一种变化时，能否局部完成，而不用改动一串不相关的代码？** 模式帮助代码围绕稳定部分组织，把变化点隔离起来。创建型、结构型、行为型是 GoF 的分类方式，适合查阅和记忆，但不是选模式的第一步。

## 从一个例子理解策略、注册表和工厂

假设订单有普通、会员和优惠券三种折扣。一开始把规则写在一个方法里很直接：

```java
Money calculate(Order order) {
    switch (order.discountType()) {
        case VIP -> { /* 会员折扣 */ }
        case COUPON -> { /* 优惠券折扣 */ }
        default -> { /* 无折扣 */ }
    }
}
```

如果折扣类型很稳定、逻辑也简单，这样完全可以。若折扣算法持续增加，且希望每种算法独立测试和维护，可以把变化部分提取为策略：

```java
interface DiscountStrategy {
    Money calculate(Order order);
}

final class VipDiscount implements DiscountStrategy {
    @Override
    public Money calculate(Order order) {
        // 会员折扣规则
        return order.total();
    }
}
```

调用方只依赖统一接口：

```java
final class DiscountService {
    private final Map<DiscountType, DiscountStrategy> strategies;

    DiscountService(Map<DiscountType, DiscountStrategy> strategies) {
        this.strategies = Map.copyOf(strategies);
    }

    Money calculate(Order order) {
        DiscountStrategy strategy = strategies.get(order.discountType());
        if (strategy == null) {
            throw new IllegalArgumentException("Unsupported discount type");
        }
        return strategy.calculate(order);
    }
}
```

这里有两个相关但不同的概念：

- **策略（Strategy）**：把可互换的算法封装起来，解决“怎么计算”。
- **注册表（Registry）/查找表**：根据类型找到已有的实现，解决“按什么键找到哪一个”。上面的 `Map` 本身就是注册表。
- **工厂（Factory）**：封装对象的创建，解决“如何创建、创建哪个对象”。若创建过程复杂、依赖运行时参数、需要管理生命周期，工厂可能有价值；如果只是从已经创建好的策略中查一个，称为注册表更准确。

GoF 的**工厂方法**有更具体的含义：定义创建产品的接口，并由子类决定实例化哪种产品。日常代码中的“简单工厂”或“工厂类”常被宽泛地称作工厂，但不必和 GoF 工厂方法混为一谈。

**何时不需要拆？** 只有两三个稳定分支、每个分支很短、变化不频繁时，`switch` 可读性可能更好。设计目标不是消灭所有分支，而是让经常变化的部分更容易独立扩展。

## 常用模式：问题、结构和权衡

### 策略（Strategy）：替换一组算法

**问题信号：** 同一项业务有多套可替换算法，调用方不应该关心算法内部细节。

**结构：** 调用方依赖策略接口；每个具体策略实现一种算法；调用方或注册表选出本次使用的策略。

**收益：** 新增算法时可以新增实现，不必把算法细节继续堆进原方法；各算法也容易单独测试。

**代价与边界：** 策略数量太少、算法极其简单时，接口和注册表反而增加跳转成本。策略通常由调用方按输入选择；如果对象因自身状态而改变行为，更接近状态模式。

### 建造者（Builder）：把复杂对象的组装变清楚

当构造参数很多、可选项多，或者创建时需要校验一组约束，建造者可以把“逐步组装”与“最终对象”分开：

```java
Report report = Report.builder()
    .title("Monthly sales")
    .from(startDate)
    .to(endDate)
    .includeRefunds(false)
    .build();
```

`build()` 适合校验必填项和不变量；构造出的对象通常应尽量不可变。建造者不是所有 DTO 的默认写法：对象字段少、可选项少时，构造器或静态工厂更直接。也要避免为了 Builder 再建多层 Builder 继承体系。

### 适配器（Adapter）与外观（Facade）：边界转换和高层入口

这两个模式都可能包住其他对象，但目标不同。

- **适配器**转换接口，让已有的不兼容组件能接入内部接口。通常放在外部系统边界，避免第三方字段和调用方式扩散到领域代码。
- **外观**为复杂子系统提供一个较简单的高层入口；它不一定转换接口，重点是隐藏调用多个子系统的流程细节。

```java
interface PaymentGateway {
    PaymentResult pay(PaymentRequest request);
}

final class VendorPaymentAdapter implements PaymentGateway {
    private final VendorClient client;

    VendorPaymentAdapter(VendorClient client) {
        this.client = client;
    }

    @Override
    public PaymentResult pay(PaymentRequest request) {
        // 转换内部请求/响应，并调用第三方 SDK
        return convert(client.charge(convert(request)));
    }
}
```

如果一个 `CheckoutFacade` 再统一协调库存、优惠、支付和订单服务，它承担的是简化子系统调用的外观职责。适配器负责“说同一种接口语言”，外观负责“把一组操作组织成更简单的入口”。

### 装饰器（Decorator）与代理（Proxy）：包装同一接口，意图不同

两者都可以持有一个同接口对象，再把调用转发给它，所以只看类的结构往往无法区分；要看它承担的**意图**：

- **装饰器**：组合式地给对象叠加可选能力，例如压缩、加密、缓存。多个装饰器可以按顺序组合。
- **代理**：控制对目标对象的访问，例如权限校验、懒加载、远程调用或事务拦截。

```java
interface Image {
    void display();
}

final class LoggingImage implements Image { // 装饰器示意
    private final Image delegate;

    LoggingImage(Image delegate) {
        this.delegate = delegate;
    }

    @Override
    public void display() {
        System.out.println("before display");
        delegate.display();
    }
}
```

真实项目里的包装器可能同时具有两种特征；分类时看它主要解决的问题，不必强行只贴一个标签。叠加包装器也会带来调用顺序、异常传播和排查调用链的成本。

在 Java 中，JDK 动态代理基于接口和 `InvocationHandler`；CGLIB 通过生成目标类的子类来增强调用。两者都可用于代理式增强，但实现机制不同。Spring AOP 会根据配置和目标类型选择代理方式；具体约束及事务问题应结合 Spring AOP 的代理机制理解，而不是简单归结为“反射代理”。

### 责任链（Chain of Responsibility）：把请求交给一串处理者

**问题信号：** 请求需要经过多个处理节点；节点可能处理、拒绝，或继续传给下一个节点。

**关键设计点：** 顺序由谁决定？某个节点处理后是否停止？异常是中断、转成结果，还是交给统一错误处理？这三点不明确，链条就很难维护。

```java
interface Handler {
    Result handle(Request request);
}

final class AuthHandler implements Handler {
    private final Handler next;

    AuthHandler(Handler next) {
        this.next = next;
    }

    @Override
    public Result handle(Request request) {
        if (!isAuthenticated(request)) {
            return Result.unauthorized();
        }
        return next.handle(request);
    }
}
```

如果所有校验器都必须依次执行，且没有“由一个节点接手并决定是否传递”的语义，通常称为处理管道（pipeline）更直观。责任链和管道实现上可能相似，但业务语义应说清楚。节点之间若强依赖或顺序不断动态变化，显式流程编排可能更合适。

### 状态（State）：让对象状态和行为一起变化

当不同状态允许的操作不同，或状态相关的分支不断增长，可以显式建模状态和合法迁移。订单例如：

```text
待支付 ──支付成功──> 已支付 ──发货──> 已发货
   │                   │
   └──取消────────────> 已取消
```

要处理的不只是“每个状态对应一个类”，还包括：非法迁移如何拒绝、重复事件如何处理、并发更新如何防止覆盖、状态变化如何持久化。状态少且行为简单时，枚举加清晰的转换表可能已经足够；状态对象适用于状态行为差异明显、分支难以维护的情况。

**和策略的区别：** 策略通常由外部选择某种算法；状态通常由对象当前状态决定行为，并伴随状态迁移。两者都可能用接口和多个实现，但“谁决定使用哪个实现、是否发生迁移”不同。

### 观察者（Observer）：一个变化通知多个订阅者

发布者不直接依赖每个订阅者，而是通过订阅关系通知它们，适合“一次变化触发多个相对独立的后续动作”。

- 同步通知容易理解，但订阅者耗时或抛异常会影响发布者。
- 异步通知需要考虑事务提交时机、重复消费、顺序、重试和积压。
- 订阅关系需要能取消；注意监听器、线程池或闭包意外持有对象导致资源泄漏。

进程内观察者和消息中间件事件不是同一种可靠性承诺。若事件必须与数据库事务可靠一致，需要专门设计事务边界和投递机制，不能仅仅把同步调用改成异步就认为问题解决了。

### 桥接（Bridge）：拆分两个独立变化维度

如果两个维度都要独立扩展，直接为每种组合建子类会出现组合爆炸。桥接让一个抽象持有另一个实现：

```text
PaymentOperation（支付操作：支付、退款）
        └──持有──> PaymentChannel（支付渠道：渠道 A、渠道 B）
```

以后可以独立增加支付操作或渠道，而不必为每一种“操作 × 渠道”组合写一个类。关键是两个维度**确实独立变化**；若只是为了多一个接口而拆分，桥接会增加不必要的间接层。

**和适配器的区别：** 桥接通常在设计时主动拆分变化维度；适配器通常在已有接口之间做兼容转换。

## 几组容易混淆的模式

| 对比 | 核心区别 |
| --- | --- |
| 工厂方法 vs 抽象工厂 | 工厂方法通常创建一种产品；抽象工厂创建一组需要彼此匹配的相关产品 |
| 适配器 vs 外观 | 适配器转换不兼容接口；外观简化多个子系统的调用流程 |
| 装饰器 vs 代理 | 装饰器重点是组合叠加能力；代理重点是控制访问、生命周期或调用位置 |
| 策略 vs 状态 | 策略让调用方选择算法；状态由对象当前状态决定行为并发生迁移 |
| 策略 vs 模板方法 | 策略通过组合替换算法；模板方法固定算法骨架，通过子类或钩子替换部分步骤 |
| 桥接 vs 适配器 | 桥接是设计时拆分变化维度；适配器通常为兼容既有接口而引入 |
| 组合 vs 责任链 | 组合表达树形的“部分—整体”；责任链表达请求沿处理节点传递 |

## GoF 23 种模式速查

下面的分类用于建立全景和查阅。每个模式的具体形式会随语言、框架和上下文变化；不必为了覆盖清单里的所有模式而在项目中使用它们。

### 创建型

| 模式 | 核心意图 | 典型场景 |
| --- | --- | --- |
| 工厂方法 | 将产品创建延迟给具体创建者 | 根据业务类型创建不同产品 |
| 抽象工厂 | 创建一组相互匹配的产品 | 多套基础设施各自提供一组配套组件 |
| 建造者 | 分离复杂对象的组装过程与最终表示 | 可选参数多、创建时需要校验的配置对象 |
| 原型 | 复制已有对象，避免重复初始化 | 复杂模板对象的批量复制 |
| 单例 | 限制某个容器或作用域内的实例数量 | 共享配置、无状态服务等；需谨慎管理全局状态 |

**注意：** Spring 默认的 singleton 是每个 `ApplicationContext` 中、每个 Bean 定义一个实例，不等于整个 JVM 进程只有一个实例。

### 结构型

| 模式 | 核心意图 | 典型场景 |
| --- | --- | --- |
| 适配器 | 转换已有接口或数据结构 | 第三方 SDK、旧接口兼容 |
| 桥接 | 把两个独立变化的维度拆开 | 支付操作 × 支付渠道 |
| 组合 | 用树结构统一处理单个对象和对象集合 | 菜单、组织架构、语法树 |
| 装饰器 | 在保持接口的情况下组合叠加职责 | 流处理、缓存或其他可选增强 |
| 外观 | 为复杂子系统提供高层入口 | 统一协调多个组件的调用 |
| 享元 | 共享可复用的细粒度对象，把变化状态交给外部 | 大量重复、可共享的对象 |
| 代理 | 控制对目标对象的访问或真实调用时机 | 权限检查、远程调用、懒加载、AOP |

### 行为型

| 模式 | 核心意图 | 典型场景 |
| --- | --- | --- |
| 责任链 | 请求沿处理节点传递 | 过滤器、审批、校验管道 |
| 命令 | 把请求封装成对象 | 排队执行、重试、审计、撤销 |
| 迭代器 | 隐藏集合内部结构，统一遍历方式 | `Iterable` / `Iterator`、树遍历 |
| 中介者 | 集中管理一组对象之间的交互 | 复杂 UI 组件协作、聊天室 |
| 备忘录 | 在不暴露内部细节的前提下保存状态快照 | 撤销、回滚、版本恢复 |
| 观察者 | 一个对象变化时通知多个依赖者 | 事件订阅、领域事件 |
| 状态 | 根据对象内部状态切换行为 | 订单、审核、营销状态机 |
| 策略 | 封装一组可互换算法 | 折扣、路由、计费、风控 |
| 模板方法 | 固定算法骨架，把部分步骤留给子类或钩子 | 固定流程中允许步骤定制的框架方法 |
| 访问者 | 把对稳定对象结构的操作抽离出来 | 对稳定语法树增加多种分析操作 |

**Java/Spring 提醒：** `JdbcTemplate` 常被用来说明“模板”风格，但它主要通过回调复用流程，不完全等同于经典模板方法的“继承后覆写步骤”。动态代理和声明式事务是代理思想在框架中的应用；具体行为还要看 Spring AOP 的代理方式和调用边界。

## 模式组合与实际落地

模式经常组合使用，但组合应由职责需要推动，而不是为了让代码“看起来用了设计模式”。

- `Strategy + Registry`：按类型找到对应算法，再执行它；若对象创建也复杂，再考虑工厂。
- `Adapter + Facade`：先归一外部接口，再为上层提供稳定的高层入口。
- `Decorator + Proxy`：都可包装对象，但应分别说明是在叠加可选能力，还是控制访问。
- `Chain + Template Method`：固定的整体流程中，每个处理节点或步骤仍可扩展；注意不要把简单循环抽象成多层框架。
- `Command + Observer`：命令表达“要执行什么”，事件表达“发生了什么”；可以配合，但语义、失败处理和重试边界不同。

引入模式前，先写清它隔离了哪个变化点，以及新增了哪些间接层。若模式组合让对象创建、调用顺序和异常传播更难追踪，说明抽象可能已经过度。

## 复习时抓住这几件事

- 能从代码中的变化点解释为什么考虑某个模式，而不是只背定义。
- 能说清模式减少了哪种修改成本，也能说出它增加的复杂度。
- 区分“算法可替换”“接口不兼容”“访问需要控制”“状态改变行为”等不同问题。
- 先用最简单可读的实现；只有变化真实存在且值得隔离时，再引入模式。
