# 04 JVM：类型、执行与对象存活

JVM 先把类型引入运行时，再执行方法和分配对象，GC 则沿引用关系判断哪些内存仍需保留。类型何时初始化、对象是否可达、哪类资源耗尽是三个不同问题。本章区分 JVM 的逻辑模型与 HotSpot 17 的常见实现，后续版本的收集器变化另行说明。

## Java 类加载过程与类加载器

### 类加载、连接与初始化

| 阶段 | 保存或建立的内容 |
|---|---|
| 加载 | 取得并定义 class 字节流，建立运行时类型与 Class 对象 |
| 验证 | 检查文件、类型、字节码与引用约束 |
| 准备 | 为类变量建立存储并赋默认值 |
| 解析 | 把符号引用解析到运行时目标 |
| 初始化 | 执行静态字段显式赋值与静态初始化块等逻辑 |

验证、准备、解析合称连接；解析可延迟到实际需要时，不能把这张表理解成所有引用必在初始化前一次性解析完。普通 static int value=1 在准备后先有默认值，显式赋值发生在初始化阶段；编译期常量的主动使用规则见[语言与运行时](01_语言与运行时.md#类与实例的初始化顺序)。

### 类加载器的职责

JDK 17 常见层次是 Bootstrap、Platform、Application，再按应用需求增加自定义加载器；JDK 8 的 Extension 属于旧版本命名。运行时类身份由定义加载器与二进制类名共同决定，同名字节码被不同定义加载器定义后也可能无法互相强转。

标准 ClassLoader 通常先委派父加载器，再尝试自己的来源。它帮助共享上层类型、避免重复定义；核心包定义和模块访问还受额外规则约束，不能只靠“先父后子”解释全部安全性。

SPI 可借助线程上下文类加载器，让框架找到应用提供的实现，并不等于所有类都改成子优先。Web 容器与插件可选择不同委派策略，但接口类型仍需跨边界一致；Tomcat 的应用隔离见[容器类加载](12_Tomcat.md#Web%20应用的类加载隔离)。

### 对象与类的生命周期

对象从可达变为不可达后，只是取得被回收的条件，不保证立即释放。普通类的卸载则受定义加载器等更长生命周期约束，不能因为一个对象不用了就判断整个类可以卸载。

动态加载新版本通常创建新的加载器与类型，旧类型仍可能由线程、缓存或旧实例持有。替换成功与旧版本完全退出是两个阶段，恢复和释放策略都需要设计。

## JVM 运行时基础

### 运行时数据区

| 区域 | 线程关系 | 逻辑作用 |
|---|---|---|
| 程序计数器 | 线程私有 | 记录当前执行位置，native 方法执行时其值未定义 |
| Java 虚拟机栈 | 线程私有 | 保存方法栈帧、局部变量、操作数栈等 |
| 本地方法栈 | 线程私有 | 支持 native 方法，HotSpot 通常与线程栈结合实现 |
| Java 堆 | 线程共享 | 对象与数组的主要分配和 GC 管理区域 |
| 方法区 | 线程共享 | 类型、方法与运行时常量池等逻辑数据 |

方法区是规范概念，HotSpot 8 起以本地内存中的元空间取代永久代保存类元数据；不能把“方法区”与某一版本物理区域完全等同。堆外还包括线程栈、代码缓存、元空间和直接缓冲等多种内存，进程占用不等于 Java 堆大小。

### JVM 参数的作用范围

| 参数 | 直接影响的范围 |
|---|---|
| -Xms / -Xmx | 堆初始与最大大小 |
| -Xss | 平台线程的栈大小 |
| -XX:MaxMetaspaceSize | 元空间上限 |
| -XX:MaxDirectMemorySize | JDK 直接缓冲分配相关上限，不能统管所有本地分配 |

堆外申请还受操作系统与容器限制，增大 Xmx 可能挤压进程其他部分。新生代比例与 -Xmn 等参数依赖收集器，不应从旧分代配置直接搬到 G1 等自适应策略中。

## Java 对象与字节码执行

### 对象分配与初始化

new 需要相应类型可用并完成必要初始化，随后建立对象的默认字段值，再执行构造链与实例初始化逻辑。HotSpot 常用 TLAB 等方式降低分配竞争；JIT 还可能内联、消除分配或进行标量替换，源码中的每个表达式不必对应可直接观测的一次物理分配。

HotSpot 17 普通对象常由对象头、实例字段与对齐部分组成；数组另有长度信息。Mark Word、类指针、压缩指针与对齐设置影响具体布局，它们是实现细节，不是 Java 类声明能固定的跨平台尺寸。

### 方法调用与栈帧

规范模型中，方法调用建立栈帧，局部变量表保存参数和局部值，操作数栈承接字节码计算，运行时引用支持方法与字段解析。方法完成后把结果交给调用者；JIT 内联不必保留同样的物理调用形态。

下面的静态 add 可用 javap -c 查看：两个参数加载到操作数栈，相加，再返回。完整程序也区分了字符串对象身份与内容。

```java
public class StringIdentityDemo {
    static int add(int left, int right) { return left + right; }

    public static void main(String[] args) {
        String literal = "abc";
        String fresh = new String(literal);
        assert add(2, 3) == 5;
        assert fresh != literal;
        assert fresh.equals(literal);
        assert fresh.intern() == literal;
    }
}
```

### 运行时常量池与字符串池

class 常量池保存字面量、描述符与符号引用，加载后形成运行时所需的常量池信息。字符串字面量解析到可复用的 String 对象，intern 返回与内容对应的规范引用；堆中的字符串对象与虚拟机的查找索引不是同一件东西。

new String(literal) 在对象身份语义上产生不同 String，但不可变的底层字符数据可以由实现共享。是否预先解析字面量、是否被优化会改变实际分配行为，因此不能仅数一行源码中的引号与 new 来推算内存成本。

### 直接内存与容量

ByteBuffer.allocateDirect 申请直接缓冲，可避免部分 Java 堆与本地 I/O 缓冲之间的复制，但本身仍有分配、寻址与释放成本。JDK 直接缓冲的回收与可达性、Cleaner 等实现有关，池化框架还可能使用引用计数和自己的释放协议。

MaxDirectMemorySize 并不覆盖所有 JNI 或第三方本地分配。排查时同时观察缓冲保留量、框架池、进程与容器内存；Native Memory Tracking 帮助分析 HotSpot 记账的本地分配，也不能代替所有第三方内存观测。

## JVM 垃圾回收

### 可达性与 GC Roots

从 GC Roots 沿相关强引用可达的对象需要保留；孤立对象图内部即使互相强引用，也可能整体不可达。这正是可达性分析与单纯引用计数的差别。

根来源包括活动栈帧中的引用、JNI 根与虚拟机内部根等；类的静态字段也参与可达关系，但不能把所有动态类及其静态字段永远当作独立、不可回收的根。存活性必须结合整个加载器和对象图分析。

### 引用类型与可回收性

| 引用 | 关键语义 | 使用边界 |
|---|---|---|
| 强引用 | 从根经强引用可达时保留 | 有强引用字段不等于整个图仍从根可达 |
| SoftReference | 由回收器按内存需求处理软可达对象 | 不适合提供可预测容量与命中率的缓存承诺 |
| WeakReference | 对象被判定为弱可达时可清除 referent | 仍有强可达路径时不会只因一次 GC 就失效 |
| PhantomReference | 配合 ReferenceQueue 观察相应清理阶段 | 不可通过 get 取得 referent |

弱引用只弱化其目标。WeakHashMap 的 value 仍被强引用，value 若又引用 key，还会影响 key 的可回收性；key 清除与条目清理、value 最终失去所有强可达路径也不是同一时刻。

不可达不保证即时回收，finalize 也不能提供可靠资源释放。文件、连接等应通过显式关闭或 try-with-resources 管理，业务提交更不能依赖析构与回收时机。

### 回收算法与成本

标记-清除先标记存活对象，再清理未标记空间，可能产生碎片；复制把存活对象转移到其他区域，代价与存活量和预留空间有关；整理通过移动减少碎片，也需要修正引用。并发算法还须在应用继续修改引用时维持正确视图。

分代利用寿命分布，对不同区域选择不同策略，并记录跨代引用。传统 Eden、Survivor、Old 模型有助于理解对象晋升，但晋升年龄、动态年龄判断、大对象处理与分配担保都由具体收集器和版本决定，不能把“15 次”当成所有对象固定的晋升时刻。

### 收集器的目标与版本

| 收集器 | 主要取舍 |
|---|---|
| Serial | 单线程收集，适合相应小规模与资源条件 |
| Parallel | 并行回收，侧重吞吐，回收阶段会暂停应用线程 |
| G1 | Region 化与分代，按停顿目标和空间预测选择回收集合 |
| ZGC / Shenandoah | 将更多工作并发执行，以资源与实现成本换取低停顿目标 |

CMS 的初始标记、并发标记、重新标记、并发清除及其碎片问题可用于理解历史设计；CMS 已在 JDK 14 移除，ParNew 也是历史组合，不能在 JDK 17 照抄相应参数。

JDK 17 的 ZGC 与后续分代模式不同：Java 21 引入分代 ZGC，23 将其设为默认，24 移除非分代模式。讨论参数与行为前先固定目标 JDK、发行版和收集器，再比较相同负载下的吞吐、尾延迟、CPU、存活集与内存余量。

### G1 的 Region 与回收

G1 把堆分为等大小 Region，并动态分配为 Eden、Survivor、Old 等角色；超过半个 Region 大小的对象按 Humongous 规则处理，可能需要连续 Region。标记可并发推进，Young/Mixed 的对象转移等阶段仍需暂停应用线程。

MaxGCPauseMillis 是启发式目标，不是每次停顿的硬上限。调小目标可能缩小单次回收工作，却增加频率或空间压力；调优需要同时观察分配速率、存活量、转移余量和吞吐，不能只盯一个 pause 数字。[JDK 17 G1 指南](https://docs.oracle.com/en/java/javase/17/gctuning/garbage-first-g1-garbage-collector1.html)

### GC 事件、STW 与请求延迟

Young、Mixed、Old、Full 等事件名称要按当前收集器解释，旧资料中的 Major 也不总有统一含义。类卸载可能伴随相应回收阶段，但不等于每次类卸载都必须执行一次全堆 Full GC。

STW 还涉及让线程进入可安全处理的状态。GC pause 与 safepoint 日志的时间口径可能不同，应分别检查到达安全点、在安全点执行与总耗时，而不是统一用一个 GC 指标代替请求停顿。

长时间 native 调用或阻塞系统调用不自动等于“无法进入安全点”；HotSpot 对 native、blocked 等状态有专门判定。排查要看具体线程状态与日志，必要时区分 JNI 临界区等约束。[HotSpot 17 安全状态判定](https://github.com/openjdk/jdk17u/blob/master/src/hotspot/share/runtime/safepoint.cpp)

可用 -Xlog:gc*,safepoint 开启相应日志；在 shell 中运行时应对含星号的参数加引号。诊断选项与字段按目标 JDK 解释，不能只设置一个超时延迟值就假定一定会输出完整超时线程栈。

### 类卸载与元数据回收

普通类卸载需要其定义加载器等满足可回收条件。若线程、静态注册、缓存或实例仍使加载器可达，只清理少数业务对象也不会释放该加载器定义的全部元数据。

插件或热部署应停止旧任务、注销回调、清理上下文并释放对应资源，再观察加载器与类数量是否回落。特殊类型如隐藏类有额外规则，不应拿普通类的简化条件覆盖全部 JVM 类型。

## JVM 内存问题诊断

### OOM 的资源分类

| 现象 | 首先区分的资源 | 证据 |
|---|---|---|
| Java heap space | 堆容量、活对象或持续保留 | GC 后存活趋势、Heap Dump、引用链 |
| StackOverflowError | 递归深度、循环调用或栈帧 | 调用栈与递归终止条件，属于栈溢出而非堆 OOM |
| Metaspace | 类元数据与加载器保留 | 类数量、加载器引用与卸载情况 |
| Direct buffer memory | JDK 直接缓冲分配 | 分配上限、缓冲保留与释放 |
| unable to create native thread | 线程、进程或本地资源限制 | 线程数、栈占用、操作系统与容器限制 |
| GC overhead limit exceeded | 相应收集器过多回收却进展有限 | 回收频率、存活量、容量与保留关系 |

### 泄漏与容量不足

泄漏是业务已不再需要的数据仍通过可达路径保留，容量不足则可能是合法存活集就超过资源上限，二者都可能导致申请失败。静态集合、未注销监听器、线程池上下文与类加载器常形成较长持有链；连接未关还可能先耗尽外部资源，而非先出现 Java 堆错误。

### 内存问题的证据链

先比较负载与 GC 后稳态，再用支配树与 GC Roots 查持有者；堆外问题另结合 NMT、框架池和进程指标。Heap Dump 可能有较大开销，VisualVM 等工具也需与目标 JDK 和部署环境匹配。

jstat 观察相应运行统计，jcmd 提供线程、堆和本地内存等诊断命令，jstack/jmap 常用于兼容已有排障流程。它们的结果各有时间与范围，不能把一个工具当成全部进程资源的完整视图。

### CPU 热点与线程定位

先确认 CPU 消耗来自应用计算、GC、重试、自旋或本地调用，再结合采样与多次线程栈。Linux 可用 top -H、pidstat 观察线程，并按该平台的 native 线程标识对应 JVM 栈；macOS 等平台应使用相应工具或 JFR，不能直接照搬 Linux 命令。

一次 RUNNABLE 栈不证明它正在持续消耗 CPU，一次 WAITING 栈也不证明死锁。要把持续时间、调度、资源等待和请求链路对齐，再用相同输入验证修复，完整方法见[调试与问题定位](14_调试与问题定位.md)。
