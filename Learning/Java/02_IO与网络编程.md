# 02 I/O 与网络编程

数据离开内存后会遇到编码、协议、部分读写和资源生命周期。先区分 I/O 模型，再理解 NIO 的缓冲与连接处理。

## I/O 基础概念

跨进程传递的是协议字节，接收方再根据约定恢复数据结构。阻塞、非阻塞和异步描述调用如何等待结果，不决定业务语义。
### 对象编码与跨进程传输

- Java 序列化：使用 `ObjectOutputStream` 和 `ObjectInputStream` 传输字节流。
- 消息传递：通过 MQ 或网络协议传输序列化后的数据。
- RPC：使用 gRPC 等框架调用另一个 JVM 的服务。
- 共享存储：将数据写入数据库或 Redis，由另一个 JVM 读取。

跨服务传输时通常使用明确、可演进的跨语言协议，而不是直接传输 Java 内存对象。

### Java 原生序列化的边界

Java 原生序列化的问题包括：

- **跨语言能力差。**
- **数据体积和性能**需要结合对象结构与负载测量。
- 类演进和 **`serialVersionUID` 容易造成兼容问题**。
- 反序列化存在**安全风险**，不能对不可信输入直接调用 `readObject()`。

实际项目通常根据场景使用 JSON、Protobuf 或 Avro。Protobuf 需要 `.proto` 定义，常用于**服务间通信**，具体体积与性能仍需测量；JSON 可读性好，但同样需要 Schema、字段兼容和输入限制。

`serialVersionUID` 用于检查序列化类的版本标识，例如 `private static final long serialVersionUID = 1L;`。显式声明可以保持标识稳定，标识相同仍需遵守字段与类型演进的兼容规则；未声明时，默认标识由类结构计算，结构变化可能改变它。版本标识和数据兼容性需要一起设计。[Java 序列化版本规范](https://docs.oracle.com/en/java/javase/17/docs/specs/serialization/version.html)

### BIO、NIO 与 AIO

| 模型  | 特点                      | 核心概念                     |
| --- | ----------------------- | ------------------------ |
| BIO | 同步阻塞，代码简单，但大量连接通常需要大量线程 | Stream、Socket            |
| NIO | 包含通道、缓冲与多路复用；可选择通道支持非阻塞模式 | Channel、Buffer、Selector |
| AIO | 异步 I/O，操作完成后通知应用        | CompletionHandler、Future |


NIO 不等于所有 API 都非阻塞：SocketChannel 创建时默认阻塞，配置为非阻塞后才能注册到 Selector；FileChannel 不属于可选择通道。非阻塞读写不会为等待数据一直停住，但 Selector.select 本身可以阻塞等待就绪，应用还要主动读写和处理结果。AIO 的结果通过完成通知或 Future 等方式取得。

I/O 模型与线程模型不是同一个维度。BIO 也可以使用线程池，NIO 也需要线程执行编解码和业务逻辑；关键是等待 I/O 时线程是否被占用。


下面只检查通道模式，不建立网络连接，可在 JDK 17 编译运行：

```java
import java.nio.channels.SelectionKey;
import java.nio.channels.Selector;
import java.nio.channels.SocketChannel;

public class ChannelModeDemo {
    public static void main(String[] args) throws Exception {
        try (SocketChannel channel = SocketChannel.open();
             Selector selector = Selector.open()) {
            assert channel.isBlocking();
            channel.configureBlocking(false);
            channel.register(selector, SelectionKey.OP_CONNECT);
            assert !channel.isBlocking();
            assert selector.keys().size() == 1;
        }
    }
}
```

### 流、通道、缓冲区与选择器

**Stream（流）：**
- 字节流：处理二进制数据
- 字符流：处理文本，需要**显式指定字符集**（不能依赖系统默认编码）
- 装饰器组合：底层流（读写原始数据） + 缓冲流（提高效率） + 数据流（读写基本类型），逐层增强
- 当前作用域拥有的可关闭资源优先用 try-with-resources 管理；借用或共享资源遵守其所有者的释放协议

**Channel、Buffer、Selector（NIO 三件套）：** Channel 是数据传输通道，Buffer 是数据容器，Selector 是多路复用器。

工作流程：
1. Selector 盯着多个 Channel
2. 某个 Channel 有事件就绪 → Selector **通知应用**
3. 应用从 Channel 读数据 → **先放进 Buffer**
4. 应用从 Buffer 取出来处理

## NIO 的缓冲与消息边界

连接就绪只说明可以尝试读写，实际处理仍要结合本次字节数、协议边界和缓冲区状态。尚未收齐或发送完的数据需要保留到下一次操作。

### 半包、短写与缓冲状态

**读写特性：**
- 半包：一次读可能读不到完整消息（比如 `Hello World` 分两次到：`Hello` + ` World`）
- 短写：一次调用可能只写出 Buffer 中的部分待发送字节，非阻塞连接暂时不可写时也可能返回 0

**返回值判断：**
- 正数：实际读/写了多少字节
- 0：本次没有转移字节，可能暂未就绪或 Buffer 没有剩余空间；不能仅凭 0 判断整个连接健康
- `read` 返回 -1：输入方向已到末尾，可能是对端半关闭；`write` 用返回的非负字节数表示本次进度，不能当作对端业务已处理的确认

**消息边界处理：** TCP 只管字节流，不管消息边界，需要自己划分：
- 长度字段：消息开头加长度（如 `10:HelloWorld`）
- 分隔符：用特殊符号隔开（如 `Hello\n`）
- 固定长度：每条消息固定长度

因此，Buffer 的剩余字节、单次读写结果和协议中的完整消息长度是三个不同的量，处理连接时需要分别维护。[SocketChannel 读写语义](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/nio/channels/SocketChannel.html)

### 文件路径、大小与原子写入

优先使用 `java.nio.file.Path` 和 `Files`。**大文件不要一次性读入内存**；**按流或 Channel 分块处理，并限制上传大小、路径和并发**。

写重要文件时可采用"**写临时文件 → flush/fsync → 原子替换**"的模式。请求原子移动还可能因文件系统不支持而失败，应明确处理该结果。原子替换保证路径切换的可见性，与断电后的持久性是不同承诺；文件内容强制落盘、目录项与底层存储的保证也需按平台确认，不能把 flush 一律等同于 fsync。

### 示例：Buffer 的读写模式转换

Buffer 同时记录容量 capacity、当前位置 position 和读写边界 limit。写入后调用 flip，将刚写入的区域变为可读区；消费部分数据后调用 compact，把未消费的数据移到开头，保留它继续接收后续内容。

```java
import java.nio.ByteBuffer;
import java.nio.charset.StandardCharsets;

public class BufferDemo {
    public static void main(String[] args) {
        ByteBuffer buffer = ByteBuffer.allocate(4);
        buffer.put(new byte[]{'a', 'b', 'c'});
        assert buffer.position() == 3;
        buffer.flip();
        byte first = buffer.get();
        assert buffer.limit() == 3 && first == 'a';
        buffer.compact();
        assert buffer.position() == 2;
        buffer.put((byte) 'd');
        buffer.flip();
        byte[] remaining = new byte[buffer.remaining()];
        buffer.get(remaining);
        assert new String(remaining, StandardCharsets.UTF_8).equals("bcd");
    }
}
```

保存为 `BufferDemo.java`，使用 `javac BufferDemo.java` 编译，再用 `java -ea BufferDemo` 执行断言。`compact` 保留的是未消费的字节；直接 `clear` 只重置位置与边界，不会替应用保存那段协议内容，也不代表将缓冲区中的旧字节清零。

网络短写时也要保留尚未发送的部分，等连接再次可写后继续；一次 Channel.write 返回不等于全部字节已经写出。

## 网络服务的并发与资源边界

缓冲区解决单个连接中的数据连续性，线程与事件循环决定多个连接怎样共享执行资源。处理不过来的工作还需要通过队列和并发上限形成背压。

### 网络服务的线程模型

**Reactor 模型：** 事件分发器根据就绪事件调用处理器，可采用单 Reactor 或多 Reactor，并不固定为一套线程数量。短小且非阻塞的处理可以留在事件循环，阻塞调用和昂贵计算应隔离到有容量限制的执行资源，否则会拖慢共享该循环的其他连接。

**设计要点：**
- 线程划分：Acceptor（接收连接）、I/O Worker（读写）、业务线程池各多少
- 资源限制：写队列上限、背压（**处理不过来就喊停**）策略
- 超时控制：空闲连接、读写、请求级超时
- 容错：半关闭、断线、重连策略

### 虚拟线程与资源上限

Java 21 虚拟线程降低**大量阻塞式 I/O** 任务的**线程创建和调度成本**，使"一个请求一个线程"的代码更容易扩展。它不提升 CPU 密集计算（虚拟线程不会让代码跑更快），也不会消除数据库连接、下游并发和内存等资源上限。

使用虚拟线程仍要限制数据库连接和外部调用并发。阻塞操作与载体线程固定等实现问题要结合实际 JDK 版本分析，并用对应负载验证。
