# Java I/O 与网络编程

## I/O 基础概念

### 对象如何跨 JVM 传输？

- Java 序列化：使用 `ObjectOutputStream` 和 `ObjectInputStream` 传输字节流。
- 消息传递：通过 MQ 或网络协议传输序列化后的数据。
- RPC：使用 gRPC 等框架调用另一个 JVM 的服务。
- 共享存储：将数据写入数据库或 Redis，由另一个 JVM 读取。

跨服务传输时通常使用明确、可演进的跨语言协议，而不是直接传输 Java 内存对象。

### 为什么不推荐 Java 原生序列化？

Java 原生序列化的问题包括：

- **跨语言能力差。**
- **数据体积和性能**通常不如专用协议。
- 类演进和 **`serialVersionUID` 容易造成兼容问题**。
- 反序列化存在**安全风险**，不能对不可信输入直接调用 `readObject()`。

实际项目通常根据场景使用 JSON、Protobuf 或 Avro。Protobuf 需要 `.proto` 定义，体积小、编解码性能好，适合**服务间通信**；JSON 可读性好，但同样需要 Schema、字段兼容和输入限制。

> **`serialVersionUID` 是什么？** 序列化的版本号，反序列化时 JVM 会对比字节流里的 ID 和当前类的 ID，不一致就报 `InvalidClassException`。不手动声明的话，改了类（加字段等）ID 会自动变，旧数据就反序列化不了。建议手动声明 `private static final long serialVersionUID = 1L;`。

### BIO、NIO、AIO 有什么区别？

| 模型  | 特点                      | 核心概念                     |
| --- | ----------------------- | ------------------------ |
| BIO | 同步阻塞，代码简单，但大量连接通常需要大量线程 | Stream、Socket            |
| NIO | 同步非阻塞，可用多路复用监听多个连接      | Channel、Buffer、Selector  |
| AIO | 异步 I/O，操作完成后通知应用        | CompletionHandler、Future |


NIO 的"非阻塞"指**读写调用不会一直等待**；"同步"指应用线程**仍需主动获取就绪事件并处理读写**。AIO 则由异步操作完成后通知应用。

I/O 模型与线程模型不是同一个维度。BIO 也可以使用线程池，NIO 也需要线程执行编解码和业务逻辑；关键是等待 I/O 时线程是否被占用。

### Stream、Channel、Buffer 和 Selector 分别解决什么问题？

**Stream（流）：**
- 字节流：处理二进制数据
- 字符流：处理文本，需要**显式指定字符集**（不能依赖系统默认编码）
- 装饰器组合：底层流（读写原始数据） + 缓冲流（提高效率） + 数据流（读写基本类型），逐层增强
- 所有资源用 `try-with-resources` 关闭

**Channel、Buffer、Selector（NIO 三件套）：** Channel 是数据传输通道，Buffer 是数据容器，Selector 是多路复用器。

工作流程：
1. Selector 盯着多个 Channel
2. 某个 Channel 有事件就绪 → Selector **通知应用**
3. 应用从 Channel 读数据 → **先放进 Buffer**
4. 应用从 Buffer 取出来处理

## NIO 细节

### NIO 如何处理半包和短写？

**读写特性：**
- 半包：一次读可能读不到完整消息（比如 `Hello World` 分两次到：`Hello` + ` World`）
- 短写：Buffer 容量有限，一次可能写不完全部数据

**返回值判断：**
- 正数：实际读/写了多少字节
- 0：没有数据可读/可写，但连接还在（不是关闭）
- -1：对端正常关闭输入流（真的结束了）

**消息边界处理：** TCP 只管字节流，不管消息边界，需要自己划分：
- 长度字段：消息开头加长度（如 `11:HelloWorld`）
- 分隔符：用特殊符号隔开（如 `Hello\n`）
- 固定长度：每条消息固定长度

### 文件 I/O 如何避免风险？

优先使用 `java.nio.file.Path` 和 `Files`。**大文件不要一次性读入内存**；**按流或 Channel 分块处理，并限制上传大小、路径和并发**。

写重要文件时可采用"**写临时文件 → flush/fsync → 原子替换**"的模式。跨文件系统移动不一定原子，**错误处理和恢复策略必须明确**。

## 网络与并发

### 网络服务线程模型怎么设计？

**Reactor 模型：** 一个线程（Reactor）专门监听事件，收到连接后交给 Worker 处理读写，**业务逻辑再交给独立线程池**。事件循环线程不能做阻塞操作（DB 查询、远程调用），否则会拖慢所有连接。

**设计要点：**
- 线程划分：Acceptor（接收连接）、I/O Worker（读写）、业务线程池各多少
- 资源限制：写队列上限、背压（**处理不过来就喊停**）策略
- 超时控制：空闲连接、读写、请求级超时
- 容错：半关闭、断线、重连策略

### 虚拟线程改善什么，不能解决什么？

Java 21 虚拟线程降低大量阻塞式 I/O 任务的**线程创建和调度成本**，使"一个请求一个线程"的代码更容易扩展。它不提升 CPU 密集计算（虚拟线程不会让代码跑更快），也不会消除数据库连接、下游并发和内存等资源上限。

使用虚拟线程**仍要限制外部并发**，并检查 `synchronized`、本地调用等可能导致载体线程固定的问题。
