# 指标体系与事件模型

指标不是报表上的数字，而是对系统行为、用户价值和业务决策的可复核定义。

## 1. 指标合同

每个指标都要写：

- 名称和业务含义。
- 分子、分母和去重单位。
- 时间窗口、时区和数据延迟。
- 过滤条件、归因规则和版本。
- 数据来源、负责人和质量检查。
- 适用范围以及不能解释的内容。

“活跃用户”“转化率”“收入”如果没有这些定义，团队可能在讨论不同的数字。

## 2. 指标层次

建议分成：

- 结果指标：最终价值，如完成订单、有效使用或留存。
- 驱动指标：影响结果的行为，如完成关键步骤。
- 护栏指标：成本、错误、投诉、延迟、风险和公平性。
- 诊断指标：帮助定位问题，不直接作为目标。

北极星指标不是唯一目标。只优化一个指标，可能通过伤害体验、成本或长期信任得到虚假增长。

## 3. 事件模型

事件至少包含：

~~~text
event_name
event_id
occurred_at
recorded_at
actor_id / anonymous_id
object_id
source / version
properties
consent / permission context
~~~

事件定义要区分发生时间和入库时间，允许重复、迟到和更正，并保留 Schema 版本。不要把用户输入原文和敏感字段默认塞进事件属性。

## 4. 漏斗、留存与队列

- 漏斗需要明确步骤顺序、时间窗口和重复行为。
- 留存需要说明回访事件、起始队列、观察窗口和数据成熟度。
- 队列分析按首次行为或业务状态分组，避免把不同生命周期混在一起。
- LTV 等长期指标要标记成熟度和预测假设，不能把短期外推当成事实。

## 5. 数据质量门槛

指标上线前验证：

- 事件是否丢失、重复或乱序。
- 客户端和服务端是否重复上报。
- 版本切换是否改变分母。
- 删除、权限和用户导出是否生效。
- 离线重算能否与线上看板对账。

## 处理真实决策时检查

为一个订单或 Agent 任务设计事件表、指标字典、漏斗、留存和三条护栏指标；写出一条重复上报和一条迟到事件的处理规则。
