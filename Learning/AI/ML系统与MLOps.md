# ML 系统与 MLOps

本篇关注模型从实验走向稳定服务的完整生命周期。模型结构和训练原理见 [DeepLearning](DeepLearning/README.md)；Agent 应用的模型调用、评测和部署见 [Agent](../Agent/README.md)。

## 1. ML 系统不是一个模型文件

生产 ML 系统通常包含：

```text
数据采集 → 校验与版本 → 特征/样本
→ 训练 → 评测 → 模型注册
→ 部署 → 推理 → 监控 → 反馈与再训练
```

模型只是其中一个制品。代码、数据、依赖、超参数、随机种子、硬件和预处理共同决定结果。

## 2. 问题定义与基线

训练前明确：

- 预测目标和使用场景。
- 标签定义和获取延迟。
- 离线指标与线上业务指标。
- 错误类型的业务成本。
- 推理延迟、吞吐和资源约束。
- 简单规则或传统模型基线。

离线分数提高不等于线上价值提高。指标必须能反映实际决策成本。

## 3. 数据与标签版本

数据集版本至少记录：

- 来源、时间范围和查询逻辑。
- Schema、数据量、过滤和去重规则。
- 标签生成方法与质量抽样。
- 训练/验证/测试切分。
- 权限、许可、隐私和删除要求。

避免数据泄漏：

- 时间穿越：使用预测时刻之后的信息。
- 同一实体同时进入训练和测试。
- 预处理在全量数据上拟合。
- 标签字段或其代理变量进入特征。

## 4. 特征与训练/推理一致性

训练和在线推理必须使用同一语义的预处理。常见偏差来自：

- 默认值和缺失值处理不同。
- 时区或窗口边界不同。
- 类别字典、Tokenizer 或归一化参数不同。
- 实时特征比离线特征晚到。
- 代码分支和依赖版本不同。

优先复用同一转换代码或生成制品，并通过样例和统计分布进行一致性检查。

## 5. 实验追踪

一次实验至少绑定：

- 代码提交。
- 数据集版本。
- 配置与超参数。
- 随机种子。
- 运行环境和硬件。
- 训练曲线、评测指标和制品。
- 结论、失败和下一步。

实验追踪工具负责记录，不能替代实验设计。多次试验后只报告最好结果会造成选择偏差。

## 6. 可复现训练

完全位级确定性在不同硬件和算子上可能成本很高，但至少应做到结果在预期区间内可重复。

控制项包括：

- 固定代码、数据和依赖。
- 记录随机种子与非确定性算子。
- 固化容器和驱动/CUDA 兼容信息。
- 保存训练配置与 Checkpoint。
- 将评测脚本与模型制品一起版本化。

## 7. 模型评测

评测不仅看总体平均：

- 按用户、地域、设备、数据时间和关键类别切片。
- 查看混淆矩阵、校准和置信度。
- 评估鲁棒性、异常输入和分布外样本。
- 检查公平性、隐私和安全风险。
- 比较延迟、吞吐、显存和成本。

测试集应冻结并限制反复人工调参造成的污染。必要时保留最终盲测集。

## 8. 模型注册与发布门禁

模型注册表保存版本、来源、指标、审批、部署状态和回滚关系。发布门禁应比较候选与当前生产版本：

- 核心离线指标不退化。
- 关键切片满足阈值。
- 模型格式和依赖可加载。
- 推理性能满足预算。
- 安全与合规检查通过。
- 能回滚到已验证版本。

## 9. 在线推理

服务模式包括：

- 在线同步：低延迟请求。
- 异步任务：耗时推理。
- 批处理：周期性处理大量数据。
- Streaming：连续事件推理。
- Edge/On-device：在设备端运行。

Batching 能提高吞吐，但会增加排队延迟。动态批处理需设置最大批量和等待时间，并观察尾延迟。

## 10. 推理优化

常见手段：

- 更高效的模型架构或蒸馏。
- 量化与低精度计算。
- 算子融合和编译优化。
- KV Cache、前缀缓存或结果缓存。
- 动态/连续批处理。
- 模型并行与张量并行。

每种优化都要复测精度、稳定性、延迟分布、显存和硬件兼容。平均吞吐不能掩盖单请求尾延迟。

## 11. 部署策略

- Shadow：复制生产流量但不影响用户结果。
- Canary：少量流量使用新模型。
- A/B Test：比较业务效果。
- Champion/Challenger：当前模型与候选长期对照。
- Blue/Green：两套环境快速切换。

新旧模型的前后处理、特征和返回 Schema 必须兼容。回滚模型时也要考虑缓存、特征版本和数据库状态。

## 12. 线上监控

监控四层：

| 层 | 示例 |
| --- | --- |
| 系统 | CPU/GPU、显存、队列、错误、延迟 |
| 数据 | 缺失、范围、Schema、分布漂移 |
| 模型 | 预测分布、置信度、校准、切片指标 |
| 业务 | 转化、人工接管、投诉、错误成本 |

没有即时标签时，可以先监控输入/输出漂移和代理指标，但不能把漂移直接等同于模型失效。

## 13. 漂移与反馈闭环

- Data Drift：输入分布变化。
- Concept Drift：输入和目标之间的关系变化。
- Label Drift：目标类别比例变化。
- Training-serving Skew：训练和服务处理不一致。

再训练不能只由时间触发。应明确数据积累、指标退化、人工复核、审批和回滚条件，避免错误反馈被模型继续放大。

## 14. 安全、隐私与治理

需要管理：

- 训练数据授权、个人信息和删除请求。
- 数据投毒与模型供应链。
- 模型提取、反演和成员推断。
- 制品访问、签名和完整性。
- 高风险用途的人工审批和审计。

训练数据被删除后，是否需要重新训练、反学习或仅阻止后续使用，应根据法规和系统能力明确记录。

## 14.1 模型制品与发布门禁（注释版）

模型文件本身不足以支持回滚。发布制品至少要绑定代码、数据、预处理、评测和运行时版本。

```python
def release_gate(candidate, baseline, *, hard_limits, required_artifacts):
    # 缺少任一制品时拒绝发布，避免“权重在但无法复现输入语义”。
    missing = [name for name in required_artifacts if not candidate.artifacts.get(name)]
    if missing:
        return {"released": False, "reason": "missing_artifacts", "items": missing}

    # 安全、兼容性和数据泄露属于硬门槛，不能用平均指标提升抵消。
    for metric, limit in hard_limits.items():
        if candidate.metrics.get(metric, 0) > limit:
            return {"released": False, "reason": f"hard_limit:{metric}"}

    return {
        "released": candidate.metrics["quality"] >= baseline.metrics["quality"],
        "candidate": candidate.version,
        "baseline": baseline.version,
    }
```

真实门禁还应比较分桶质量、延迟、成本、输入 Schema 兼容性和回滚耗时；“离线准确率更高”不能单独证明线上发布值得。

## 15. 最小项目

完成一个小模型的生产闭环：

1. 版本化数据和 Schema。
2. 记录训练配置、代码与指标。
3. 注册候选模型并设置发布门禁。
4. 用 API 提供推理，采集延迟、错误和输入统计。
5. Shadow/Canary 发布新版本。
6. 制造 Schema 漂移并验证告警与回滚。

## 验收清单

- 任一模型版本都能追溯代码、数据、配置和评测。
- 训练/推理转换有一致性测试。
- 发布门禁同时覆盖质量、性能、安全和兼容性。
- 线上监控区分系统、数据、模型和业务。
- 漂移、再训练、灰度和回滚有明确触发条件。
