# 05 工程基础与交付

先用 package 和接口保持依赖清楚，再用测试、剖析和可追溯构建支持服务迭代。工具输出需要与具体版本、输入和负载一起解释。

## 依赖、可见性与构建输入

module 固定依赖关系，package 组织代码边界；构建平台、资源和版本信息再决定最终交付的产物。

### Module 与依赖版本

Module 由 `go.mod` 描述依赖和版本，package 是编译和导入的组织单位，`internal` 限制包只能被父目录树内的代码导入。项目应锁定依赖、记录 Go 版本和构建信息，避免 init 副作用和循环依赖；可复现构建还要处理 build tag、平台和嵌入资源。

### Package、导出与 internal

同一目录中参与一次构建的普通 Go 源文件应属于同一个 package；测试文件还可使用包名加 _test 的外部测试包。大写标识符对包外可见，小写只在包内可见；`internal` 限制导入者必须位于指定父目录树内。把 Handler、领域、存储和适配器分包时，应让依赖方向和可见性共同保护边界，而不是只靠目录命名。

### Build tag 与嵌入资源

Build tag 和目标平台会改变编译出来的代码，`go:embed` 会把资源纳入二进制，版本信息影响诊断和回滚；它们都应进入可复现构建和发布检查。需要明确依赖锁定、构建平台、制品内容和运行时配置如何对应，不能只说“Go 编译成一个二进制”。

### 构建产物与运行版本

构建脚本固定 Go/toolchain、module 依赖、build tags、目标平台和嵌入资源，通过 `-ldflags` 写入版本、commit 和构建时间；制品生成后记录 hash，启动日志和健康接口暴露可追踪版本。发布验收还要覆盖配置、迁移、回滚和跨平台差异，不能只看本地 `go build` 成功。

## 用可控输入观察行为

测试边界应对应可以替换的外部依赖。确定输入、时钟和失败点之后，业务规则与并发收尾就能分别验证。

### 可替换依赖与测试边界

由使用方定义最小接口，在边界注入时钟、随机数、HTTP 客户端、数据库和队列；核心业务保持纯函数或显式状态转移。Mock验证接口约定和关键调用，不把每个内部函数都抽成接口；真实协议、序列化、权限和超时还要用集成测试覆盖。

### 从模块到测试文件

一个可执行服务可以先按下面的职责组织，只有需要隔离变化时再拆更多包：

```text
orders/
  go.mod
  cmd/server/main.go       # 配置、装配、启动与退出
  internal/order/         # 业务规则与使用方需要的接口
  internal/httpapi/       # HTTP 参数与响应转换
  internal/storage/       # 具体数据访问
```

`internal/order` 可以依赖存储能力接口，具体实现由 main 装配。这样业务测试可以直接调用规则，网络与数据库协议则由各自集成测试覆盖。

下面两段分别保存为 `names.go` 和 `names_test.go`，放在同一个已初始化的 module 中。

```go
package names

import (
    "errors"
    "strings"
)

func Normalize(text string) (string, error) {
    name := strings.TrimSpace(text)
    if name == "" { return "", errors.New("name must not be blank") }
    return name, nil
}
```

```go
package names

import "testing"

func TestNormalize(t *testing.T) {
    got, err := Normalize("  Ada  ")
    if err != nil || got != "Ada" { t.Fatalf("got %q, error %v", got, err) }
    if _, err := Normalize("  "); err == nil { t.Fatal("blank name accepted") }
}

func BenchmarkNormalize(b *testing.B) {
    b.ReportAllocs()
    for i := 0; i < b.N; i++ {
        if _, err := Normalize("  Ada  "); err != nil { b.Fatal(err) }
    }
}
```

`go test ./...` 验证正常与错误行为；`go test -bench=. -benchmem ./...` 度量这个输入下的局部实现。前者不证明性能，后者不证明整个服务容量，数据含义要分别记录。

### 并发回归与故障路径

单测验证状态不变量和错误路径，Race Detector 检查实际数据竞争，benchmark 比较吞吐/分配/延迟，压力测试覆盖队列满、下游慢、取消和关闭，pprof/trace 确认资源没有泄漏。最终用业务指标验证，不以“测试没挂”替代正确性。

### Fuzz Test 与输入性质

适合解析器、序列化、边界输入和“不应 panic”的纯函数；好的属性包括编码后再解码保持等价、排序保持元素集合、任意输入都返回稳定错误而非崩溃。Fuzz 发现的最小样本要沉淀为回归测试，外部副作用不应直接在 fuzz 中执行。

## 从局部测量到运行观测

Benchmark 比较局部实现，Profile 解释资源消耗，服务指标和 Trace 连接真实请求。它们回答的问题不同，结论需要绑定各自负载。

### Benchmark、Profile 与负载测试

Benchmark 比较局部实现的 ns/op、B/op、allocs/op，pprof 定位真实进程的 CPU/内存/锁/阻塞热点，端到端负载测试验证连接池、数据库、队列和 p99。三者必须固定版本、数据和工作负载，微基准变快不代表服务尾延迟或错误率变好。

### 日志、指标与 Trace

日志说明发生了什么，记录结构化事件、request/task ID、错误分类与关键状态。

指标观察变化趋势，包括QPS、成功率、P95、超时、重试，以及连接池、队列、GC和资源使用情况。

Trace记录HTTP、DB、Redis、Kafka和后台任务之间的调用关系。排查时将调用记录与pprof/trace、业务指标结合；敏感header、token与用户内容仍需脱敏。

### pprof 与 runtime trace

CPU profile 定位耗 CPU 的调用路径，heap/alloc profile 定位存活和分配热点，goroutine profile 查看阻塞和泄漏，mutex/block profile 查看锁与阻塞，runtime trace 查看调度和时序。采样要和真实负载、版本和时间窗口对应，采集本身也要有权限和成本控制。

## 发布后的兼容与恢复

可复现产物只是发布的起点；配置、数据与调用方还需要在新旧版本共存时保持可用。

### 兼容发布与回滚

发布前检查兼容性，并安排旧/新协议与State Schema的过渡。灰度或影子流量期间，观察错误率、P95、资源、业务成功率和消息积压。

回滚代码时还要检查配置、数据库迁移、事件版本和缓存能否配合恢复。发布前写明停止条件，并确认回滚入口可用。

### 在独立项目中验证

先运行 `go test ./...`，涉及并发读写时再用 `go test -race ./...` 覆盖实际执行路径。Benchmark 和 Fuzz 需要对应测试函数，命令不会替项目自动生成有效场景。关闭与取消应等待事件或任务完成，避免靠随机休眠猜测时序。
