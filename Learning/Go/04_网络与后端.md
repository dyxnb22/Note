# 04 网络与后端

从 HTTP 请求进入服务，到数据库、缓存和消息，再到长连接与文件上传。通用数据库原理由 Data 课程维护，这里聚焦 Go 服务的调用与资源边界。

## HTTP 请求与资源生命周期

一个请求既占用服务端处理能力，也可能借用出站连接。入口保护、请求取消和客户端复用需要在同一条调用链中配合。

### HTTP 服务的启动与关闭

启动阶段加载并校验配置、创建日志/Trace、数据库和 HTTP 客户端等依赖，再开始监听；关闭时先从负载均衡摘除或停止接收新任务，再调用 server shutdown 让在途请求有界完成，最后关闭连接池、队列和后台 goroutine。关闭超时要记录未完成请求并退出，不能无限等待。

### Middleware 与业务边界

认证、request ID、日志、Trace、限流、统一错误和响应头等横切逻辑适合 middleware；业务授权、状态机和数据一致性放服务层。Middleware 要定义顺序、是否短路、错误格式和资源释放，不能把关键业务副作用隐藏在不可见的中间层。

### HTTP Client、Transport 与响应体

复用 HTTP Client 和 Transport 可以利用连接池、Keep-Alive 和 DNS/连接管理，避免每次请求创建新资源；同时要设置连接、TLS、响应头、整体请求和空闲连接超时，并限制并发/响应大小。请求完成后要关闭 response body，超时后的副作用请求还要走幂等/对账。

### 示例：一次完整 HTTP 往返

`http.Handler` 接收请求并写响应，`HandlerFunc` 将普通函数适配为 Handler。中间件包装下一层 Handler，因此执行顺序由包装关系决定。下面使用本机临时测试服务器，程序不依赖外部网站。

```go
package main

import (
    "context"
    "encoding/json"
    "fmt"
    "io"
    "net/http"
    "net/http/httptest"
    "time"
)

type Health struct { Status string `json:"status"` }

func withHeader(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        w.Header().Set("X-Course", "http")
        next.ServeHTTP(w, r)
    })
}

func main() {
    mux := http.NewServeMux()
    mux.HandleFunc("/health", func(w http.ResponseWriter, r *http.Request) {
        if r.Method != http.MethodGet {
            w.WriteHeader(http.StatusMethodNotAllowed)
            return
        }
        w.Header().Set("Content-Type", "application/json")
        _ = json.NewEncoder(w).Encode(Health{Status: "ok"})
    })
    server := httptest.NewServer(withHeader(mux))
    defer server.Close()
    client := server.Client()
    ctx, cancel := context.WithTimeout(context.Background(), time.Second)
    defer cancel()
    req, err := http.NewRequestWithContext(ctx, http.MethodGet, server.URL+"/health", nil)
    if err != nil { panic(err) }
    resp, err := client.Do(req)
    if err != nil { panic(err) }
    defer resp.Body.Close()
    if resp.StatusCode != http.StatusOK { panic("unexpected HTTP status") }
    var health Health
    if err := json.NewDecoder(io.LimitReader(resp.Body, 4096)).Decode(&health); err != nil { panic(err) }
    fmt.Println(health.Status, resp.Header.Get("X-Course")) // ok http
}
```

依次发生的是路由匹配、处理函数编码 JSON、客户端检查状态、读取并解码响应体，最后释放资源。`Do` 返回成功只说明拿到了 HTTP 响应，4xx/5xx 仍需应用检查；关闭响应体和读完响应体也不同，复用连接还取决于协议与响应消费情况。具体行为见 [net/http](https://pkg.go.dev/net/http)。

### API 网关与依赖保护

按租户、用户、路由和下游资源做分层限流，限制并发、请求大小、连接和总预算；依赖失败区分超时、限流、权限和未知结果，选择缓存、旧数据、静态响应或明确错误降级。网关只做通用边界，业务授权和幂等仍由下游服务确认。

## 调用方式与完成时机

同步调用让上游等待结果，消息则把完成时间交给后续消费者。流式通信延长了这段关系，也让背压和取消成为协议的一部分。

### 同步 API、RPC 与异步消息

REST 适合面向资源的同步外部 API，RPC 适合内部强类型低延迟调用，消息队列适合解耦、削峰和异步重试。选择取决于调用方是否需要立即结果、顺序、持久化、重放和副作用；协议本身不能替代超时、鉴权、幂等和版本兼容。

### gRPC、HTTP/2 与 Protobuf

gRPC 是调用模型和代码生成约定，HTTP/2 提供多路复用、流和头部压缩等传输能力，Protobuf 负责 schema、二进制编码和跨语言消息约定；三者不是同一个层次。设计还需包含 schema 演进、字段兼容、deadline、metadata、认证、错误映射和是否允许重试，不能只说“比 REST 快”。

### 流式 RPC 的背压和取消

除了 IDL 和 deadline，还要处理流的背压、半关闭、客户端中断、消息大小、顺序、重试和取消；不能让框架自动重试不可重入的写操作。Trace、认证元数据和错误码要贯穿客户端/服务端，流结束原因要区分正常完成、取消、超时和协议错误。

## 请求进入数据库与缓存

请求穿过网络之后，连接池、事务和查询路径继续限制并发。缓存缩短部分读路径，同时引入失效、回填与热点问题。

### 从请求到事务与消息

以创建订单为例，handler 先解析输入与身份，service 校验业务状态，repository 在同一个 Tx 内写订单与 Outbox，提交后再异步发布。不要在事务内用池句柄 `db.Exec` 替代 `tx.Exec`，否则语句可能跑在另一条连接上。

| 阶段 | 持有的资源 | 失败后的观察 |
|---|---|---|
| 请求解析 | 请求体与处理 goroutine | 是否返回了稳定的输入错误 |
| 获取数据库连接 | 池容量与等待时间 | 是等待耗尽还是 SQL 本身慢 |
| 本地事务 | 事务连接、锁与日志 | 提交成功、回滚或提交结果未知 |
| Outbox 发布 | 持久化事件与投递进度 | 事件是否重复、是否可重放 |
| 消费副作用 | 业务幂等键和结果记录 | 超时后能否查询真实终态 |

后面的索引、缓存和消息章节分别解释这条链路上的机制，完整原理通过文末 Data 课程连接。

### sql.DB、连接池与事务

`sql.DB` 是并发安全的连接池句柄，不是单条连接；应设置最大打开/空闲连接、连接寿命和获取等待指标。事务内的语句必须使用同一个 `Tx`，提交前不要调用不可控外部服务，读完 rows 要关闭并检查错误；跨数据库与消息/HTTP 的一致性用 Outbox、幂等和补偿解决。

### 联合索引与查询条件

联合索引按列顺序组织，查询通常要从最左列开始利用连续的索引前缀；等值条件、范围条件、排序和选择性会影响后续列是否还能用于缩小扫描。不能简单说“缺一列就完全不用索引”，要看执行计划、数据分布和是否出现索引条件下推。

### MVCC 与一致性读

MVCC 通过历史版本和可见性规则让一致性读尽量不阻塞写，具体可见性由事务隔离级别和 Read View 决定；当前读/写仍然需要锁。它不自动解决业务状态机、跨表副作用、跨服务事务或重复请求，仍要配合约束和幂等。

### 慢查询与执行计划

先记录 SQL、参数、耗时、扫描行和锁等待，再用 EXPLAIN/执行计划、索引信息和数据分布判断是全表扫描、回表、排序、连接、锁或外部等待；修改索引/SQL 后在接近生产数据上复测。不要只根据“加索引”或单次开发库结果下结论。

### Redis 的数据模型

String 可做值/计数，Hash 做对象字段，Set 做去重，Sorted Set 做按分数排序，List/Stream 可做队列或事件流。还要说明过期、淘汰、持久化、热点 key、缓存击穿和集群；Redis 是加速和短状态组件，关键事实需要可靠主存储。

### 缓存失效与回填竞态

先确定允许的陈旧窗口，再选择先写库后失效缓存、写穿或事件通知；缓存 value 带版本/时间，读取时必要时校验或回源，关键更新有重试和对账。高并发下要处理并发重建、删除与回填竞态，不能把“删缓存”当作所有一致性问题的答案。

### 热点、击穿与回源保护

先区分热点访问、缓存失效、空值穿透和数据库慢查询；热点 key 可用本地短缓存、请求合并/单飞、随机 TTL 和预热，回源设置并发上限并允许旧值/降级。更新要以数据库为事实来源，用版本/事件/对账处理并发失效和回填竞态，不能只加 Redis 或只删一次缓存。

## 异步完成与重复执行

数据库提交、消息发布和消费者执行分属不同阶段。持久化任务保存恢复依据，稳定业务号则让重复请求沿原有事实继续推进。

### Outbox 与消息发布

常用 Outbox：在同一数据库事务中写业务状态和待发布事件，后台发布器读取 Outbox 并用事件 ID 做幂等；消费端仍需去重和状态校验。分布式事务、消息 exactly-once 和网络重试都不能自动保证外部 API 副作用不重复。

### Kafka 分区、顺序与重复

同一分区内按 offset 有序，跨分区不保证全局顺序；消费者组把分区分配给成员，扩缩容会触发重平衡。至少一次投递通常可能重复，消费者要按业务 ID 幂等；生产确认、副本和 offset 提交策略降低丢失，但外部数据库/API 仍需独立处理。

### 消息积压与消费容量

先看生产速率、消费速率、分区数、单条处理耗时、重试/死信和下游限流，判断是消费者不足、热点分区、慢依赖还是错误循环；再通过扩容消费者、优化批量、隔离慢任务、限速生产或降级恢复。不能只盲目加消费者，分区和下游容量可能才是瓶颈。

### 幂等 API 与状态记录

相同业务意图重复提交，最终业务效果和返回结果可控。入口要求稳定幂等键，数据库用唯一约束保存请求摘要、状态和结果；并发重复请求返回处理中/已完成，结果未知时查询下游。幂等记录要有过期和数据清理策略，不能只在内存 map 中去重。

### 请求状态与任务状态

请求 context 到期只代表调用方停止等待，后台任务可能已开始或完成；需要把同步请求状态和持久化任务状态分开，返回 task ID/查询接口或明确取消语义。对外部副作用通过幂等键、状态查询和对账判断真实结果，不能把 context cancel 直接写成业务失败。

## 长连接、文件与订单的业务约束

调用链上的约束最终落到具体资源：连接需要心跳与收尾，文件需要分块与合并，订单需要维护库存和状态。

### 长连接、心跳与重连

应用层 ping/pong 用于发现对端和网络路径是否仍可用，连接空闲超时、读写 deadline 和 TCP keepalive 是不同层次；服务端要限制连接数、消息大小和单连接发送队列。重连采用退避/抖动并避免风暴，消息用 ID/序号去重或恢复，关闭时先停止生产、发送 close、等待在途写入，再释放连接。

### 分片上传与合并安全

客户端为文件和分片生成稳定 hash，服务端先校验上传权限、大小和分片编号，持久化已完成分片状态；合并前检查数量、hash 和目标版本，使用临时文件/文件锁或对象存储的原子完成语义，成功后再切换可见版本。重复上传、并发合并、断线、过期清理和恶意超大分片都要有边界，不能只把分片拼接到最终路径。

### 订单创建与库存约束

创建入口用幂等键和请求摘要，订单状态落库并用唯一约束避免重复；库存扣减在明确的事务/条件更新中完成，跨服务事件通过 Outbox 发布，消费者按订单事件 ID 幂等。超时后查询订单和库存状态，不能因为客户端没收到响应就再次扣库存；指标覆盖成功率、锁等待、消息延迟和对账差异。
