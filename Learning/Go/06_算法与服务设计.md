# 06 算法与服务设计

先用不变量解释局部数据结构，再把任务、幂等、租约和恢复放进完整服务。算法练习按需要阅读，系统方案要明确事实存储与外部副作用。

## 数据结构把不变量落实到操作

链表、索引、访问链和堆用不同结构限制更新方式。理解局部操作维护的关系，才能把它们用于缓存与有序数据处理。

### 单链表反转

维护 `prev`、`cur` 和 `next`，每轮先保存 next，再把 cur.Next 指向 prev，最后向后移动；时间 O(n)，空间 O(1)。要处理空链表、单节点和是否允许修改原链表，并说明循环链表不能直接套用。

### 分组反转链表

先检查剩余节点是否至少 K 个，再局部反转这 K 个节点并把上一组尾部连接到新头，递归或迭代处理后续；时间 O(n)，额外空间 O(1)（迭代）。关键是不丢失组后节点和正确更新组头/尾，可先实现普通反转 helper。

### 两数之和与三数之和

两数之和用 map 记录已见值 O(n)；三数之和先排序，固定一个数后用双指针收缩其余区间，时间 O(n²)，并跳过重复值。要说明是否允许重复下标、结果是否去重和整数溢出边界。

### LRU 的索引与访问顺序

map 保存 key 到双向链表节点的指针，链表头表示最近使用，尾部表示最久未使用；get/put 都是 O(1)。Go 中要明确节点所有权、容量为零、更新旧值和并发保护；如果加锁，锁保护的是 map 与链表的一致不变量。

### 示例：用索引和访问链实现 LRU

Map 负责定位节点，双向链表负责维护访问顺序。每次读取或更新都把节点移到链首，超出容量后删除链尾，并同步删除 Map 中的索引。

```go
package main

import "container/list"

type entry struct { key string; value int }
type LRU struct { capacity int; order *list.List; index map[string]*list.Element }

func NewLRU(capacity int) *LRU {
    if capacity < 0 { panic("negative capacity") }
    return &LRU{capacity: capacity, order: list.New(), index: make(map[string]*list.Element)}
}
func (c *LRU) Get(key string) (int, bool) {
    node, ok := c.index[key]
    if !ok { return 0, false }
    c.order.MoveToFront(node)
    return node.Value.(entry).value, true
}
func (c *LRU) Put(key string, value int) {
    if node, ok := c.index[key]; ok {
        node.Value = entry{key, value}
        c.order.MoveToFront(node)
        return
    }
    c.index[key] = c.order.PushFront(entry{key, value})
    if c.order.Len() > c.capacity {
        oldest := c.order.Back()
        delete(c.index, oldest.Value.(entry).key)
        c.order.Remove(oldest)
    }
}
func main() {
    cache := NewLRU(2)
    cache.Put("a", 1); cache.Put("b", 2)
    if value, ok := cache.Get("a"); !ok || value != 1 { panic("missing a") }
    cache.Put("c", 3)
    if _, ok := cache.Get("b"); ok { panic("b was not evicted") }
    cache.Put("a", 4)
    if value, _ := cache.Get("a"); value != 4 { panic("update lost") }
    empty := NewLRU(0); empty.Put("x", 1)
    if _, ok := empty.Get("x"); ok { panic("zero capacity retained an entry") }
}
```

不变量是 Map 和链表中的键集合相同，每个键恰好一个节点，节点数不超过容量。例子是单 goroutine 的内存结构；并发使用时，一次 Get 的移动和一次 Put 的查找、插入、淘汰必须受同一个同步协议保护。它也没有实现 TTL 或持久化。

### 最小堆合并有序流

把每个链表头放入最小堆，每次取最小节点，把它的 next 放回堆；时间 O(N log k)，空间 O(k)。如果 k 很小可两两合并；要处理 nil 链表、重复值和是否复用原节点。

## 任务从内存执行走向崩溃恢复

进程内的并发上限保护资源，持久化状态和租约则在进程退出后保存接管依据。先确定任务身份，再讨论何时重试与何时判定结束。

### 有界任务执行

固定数量 worker 从任务通道接收工作，首个关键错误取消兄弟任务。发送方停止提交后关闭输入并等待 worker；实现和取消限制见 [并发与内存模型](./03_并发与内存模型.md#示例：协作取消的有界%20Worker%20Pool)。

### 并发计数与快照

简单计数用 `sync/atomic`，复合状态用 Mutex，热点场景可分片后聚合；读写必须遵守同一同步协议。要说明计数是否允许丢失、是否需要精确快照、是否跨进程以及溢出/重启持久化，不能把 atomic 当成分布式计数器。

### 定时任务与防重入

使用 ticker 或调度器触发，但每次执行必须有 context、超时、并发策略和错误记录；如果任务不能重入，要用租约/分布式锁或持久化状态。关闭时停止 ticker、取消任务并等待已执行实例，不能在 handler 内再次无界启动 goroutine。

### 租约任务队列与崩溃恢复

任务表保存 ID、输入版本、状态、尝试次数、lease_until、worker、结果引用和错误；领取用条件更新/租约，worker 心跳续租，完成用版本号提交，崩溃后过期任务可重试。任务 ID 标识同一个逻辑任务，业务幂等键标识应被去重的业务意图；重复投递仍可能发生，去重与安全重试依赖持久化记录、唯一约束和条件更新。外部结果未知时需要查询/对账。

### 租约恢复的一次时间线

任务领取成功后从版本 7 变为版本 8，worker A 持有这次租约。A 暂停到租约过期，worker B 重新领取并取得版本 9。A 恢复后即使完成计算，也不能用版本 8 覆盖版本 9；完成更新必须带版本条件。

版本条件阻止旧 worker 写入本地终态，外部扣款还必须复用业务幂等键。租约失效不代表外部动作没有发生，所以恢复过程仍需查询与对账。

## 流量与副作用的约束

限流控制工作进入系统的速度，幂等和状态机控制已经进入的工作怎样产生效果。文件与订单都需要把这两种约束同时考虑。

### 令牌桶、漏桶与滑动窗口

令牌桶限制平均速率且允许突发，漏桶平滑输出，滑动窗口直接限制时间段内次数。先按租户、用户、路由和下游资源确定 Scope，再明确超限是拒绝、排队还是降级；单机可用 mutex/atomic，分布式要有原子存储、时间策略和过期清理。

### HTTP 重试与幂等

先设置请求 context 和 transport/client 超时，再根据错误类型、状态码、方法和幂等键决定是否重试；使用有上限的指数退避加 jitter，响应 body 要关闭，重试次数和耗时写入 Trace。连接超时与服务器已处理但响应丢失要分别处理。

### 订单状态与重复扣款

入口以业务幂等键和请求摘要落库，订单状态用状态机和唯一约束；扣款请求携带同一幂等键，下游返回未知时通过查询对账，不直接重新扣款。数据库事务只覆盖本地状态，跨服务通过 Outbox、事件和补偿；审计记录每次状态迁移和调用结果。

### 上传与异步处理服务

上传会话保存文件版本、大小、分片数、hash、已完成分片和过期时间；分片写入临时对象后幂等确认，合并由单一状态迁移或锁保护，成功后原子切换可见版本。解析/转码进入有界队列，Worker 用租约和心跳恢复；下载/查询只读取已发布版本，清理覆盖超时会话、孤儿分片和失败半成品。

## 异步与复制扩大了状态边界

跨进程之后，某个节点的局部结果无法直接代表整个系统的终态。消息、复制和负载数据帮助解释这种变化带来的成本。

### 从同步服务演进到异步系统

先梳理同步调用和共享状态，定义事件 schema、任务状态和幂等 ID，再把耗时/可重试步骤放入有界队列；服务通过 context 传播 deadline，Trace 贯穿请求—消息—worker—数据库，指标区分排队和执行。迁移用双写/影子/灰度并准备回滚，不直接把函数改成 goroutine。

### Raft 与多数派日志

节点通过任期和多数票选出 Leader；Leader 可直接按多数复制来确认当前任期日志提交，先前任期日志则随当前任期条目的提交被间接确认，不能只数它的副本。Follower 按提交索引应用；网络分区时少数派不能提交新日志，旧 Leader 发现更高任期后退回 Follower。Raft 只解决共识日志，不自动解决业务幂等、快照、客户端重试、线性化读和外部副作用；实现时仍需处理超时、重复消息与成员变更。[Raft 论文第 5.4 节](https://raft.github.io/raft.pdf) 解释了提交规则的安全性。

### 负载变化的证据链

先按时间窗口比较 CPU、GC、goroutine、mutex/block、连接池、队列、下游延迟和错误率，再用 pprof 定位 CPU/分配/阻塞，用 trace 看调度和网络，用数据库执行计划/慢日志和消息积压确认外部瓶颈。压测复现时固定版本、数据、连接数和负载模型，修复后同时比较 P99、资源、成本和业务成功率。

### 从算法走向工程

算法复杂度描述输入规模增长时的成本；服务容量还受数据库、网络、锁、队列和下游限制。通用算法推导见 [算法设计与复杂度](../CS/算法设计与复杂度.md)，系统案例见 [Architecture](../Architecture/01_系统设计.md)。
