# 02 Runtime 与性能

语言语义说明程序应当发生什么；Runtime 负责调度、内存和回收。先把程序中的值、引用和存活关系看清，再用测量解释成本。

## 编译结果怎样开始执行

源代码先经过编译成为进程中的代码；运行后，调度器在有限执行资源上推进 goroutine。分配位置和调度行为属于不同层面。

### 从源代码到进程

`go build` 编译包及其依赖并生成产物，程序启动后由 Runtime 初始化调度、堆和后台工作。局部值是否放在栈上由编译器分析决定；源代码中的 `new`、指针或返回值不能单独证明发生了堆分配。

### G、M、P 与调度

G 是 goroutine，M 是操作系统线程，P 是执行 Go 代码所需的调度资源。P 持有本地运行队列，调度器会处理阻塞系统调用、网络轮询、抢占和 work stealing。Goroutine 创建成本低但仍会消耗栈、调度、内存和下游资源，必须有所有者、退出路径和并发上限。

## 分配与对象存活

逃逸分析判断对象能否安全放在当前栈帧等局部存储中，GC 再根据可达关系判断堆对象是否仍需保留。slice 的长度与底层数组的存活范围正好展示了两者的差别。

### 逃逸分析与分配成本

编译器分析对象的引用和存活范围，决定它能否安全留在栈上；对象大小和具体实现限制也可能影响分配。返回局部变量的指针在 Go 中是安全的，编译器会保证所指对象仍然有效。源码中的取地址、`new` 或返回值本身，不能单独证明最终发生了堆分配；具体结果要结合内联与该次构建的分析提示。

### 垃圾回收与对象存活

Go 使用并发垃圾回收，在吞吐、CPU 和暂停之间平衡；高分配速率、过大的堆和长期存活对象会增加 GC 压力。排查时看 heap、allocation rate、GC CPU、pause、对象保留和请求延迟；`sync.Pool` 只能做临时对象复用，不能存业务状态或当可靠缓存。

### 示例：小切片与大底层数组

GC 从可达关系判断数据是否仍需保留。函数只返回很短的 slice，也可能让一整块底层数组继续可达；长度小并不证明存活内存小。

```go
package main

import "fmt"

func main() {
    data := make([]byte, 1024)
    data[0] = 7
    shared := data[:1]
    owned := append([]byte(nil), shared...)
    data[0] = 9
    fmt.Println(len(shared), cap(shared), shared[0], owned[0]) // 1 1024 9 7
}
```

`shared` 仍指向原数组，`owned` 拥有独立元素。示例展示共享关系与容量，不测量 GC 时机。是否值得复制取决于保留时长、数据规模与复制频率：短期借用常更便宜，长期保存一小段大缓冲区时独立复制可能降低存活内存。

## 从资源竞争解释延迟

分配、回收与等待都会增加请求耗时，处理方法却不同。先区分现象对应的资源，再用同一负载比较修改前后的结果。

### 调度、阻塞与回收怎样共同影响延迟

当 goroutine 等待 channel 或网络时，运行时通常可以调度其他工作；CPU 密集任务仍需争用执行资源，锁等待也不会因为 goroutine 轻量就消失。大量创建任务会同时增加栈、排队和下游压力。

分配速率描述单位时间产生多少新对象，存活堆描述还有多少对象可达。短命临时对象可能提高回收频率，长期持有缓冲区可能提高存活堆；看到堆大先找引用保留，看到分配高再找热路径，不能将二者当成同一种原因。

| 现象 | 先检查的证据 | 机制解释 |
|---|---|---|
| CPU 高、分配增长 | CPU 与 alloc profile | 计算本身或分配/回收工作增加 |
| goroutine 持续增长 | goroutine profile 与任务退出条件 | 工作堆积或等待无法结束 |
| CPU 不高、请求变慢 | 队列、锁、连接池、下游耗时 | 等待占主导，增加 CPU 不一定有效 |
| live heap 长期增长 | heap profile 中的保留路径 | 对象仍可达，需检查缓存或长生命周期引用 |

### 从性能现象定位资源瓶颈

先用 pprof、trace、benchmark、alloc profile 和执行指标确认热点，区分锁等待、网络、数据库、GC 和真实 CPU；只有在热点和收益明确时才调整对象分配、池化、调度或 GC 参数。Runtime 细节随版本变化，不能从一篇文章的微基准推导所有服务的结论。

### 把分配结论落到证据

在独立 Go 项目中，可用 `go build -gcflags=-m ./...` 查看逃逸提示，用 `go test -bench=. -benchmem ./...` 比较局部实现的耗时与分配。编译器提示解释某次构建，Benchmark 解释某组输入；服务是否改善，还要看实际负载中的延迟、错误率和资源。
