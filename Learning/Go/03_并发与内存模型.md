# 03 并发与内存模型

并发先解决任务归属、退出和资源上限，再选择 Channel、锁或原子操作。可见性需要同步关系，任务完成需要明确等待。

## 任务归属与通信协议

goroutine 的轻量只降低启动成本。通道由谁发送、何时关闭、满载时怎样处理，决定多个任务能否共同结束。

### Goroutine 的所有者与生命周期

启动 goroutine 的调用方需要负责传递取消信号、接收错误并等待结束。明确它可能阻塞的位置和最大数量，才能在父任务返回时收回资源；无界 fan-out 则会把任务积压转化为栈、内存和下游压力。

### Channel 容量与同步

无缓冲 channel 让发送和接收同步交接；有缓冲 channel 允许有限突发并解耦生产/消费，但容量用尽后仍会阻塞。缓冲区是背压边界，不是无限队列；要定义满载时等待、丢弃、拒绝或降级的行为。

### Channel 的关闭协议

通常由知道“不会再发送”的发送方关闭，接收方不应为了退出而关闭仍可能被发送的 channel。关闭后可读完缓冲中的值，再得到零值和 `ok=false`；向已关闭 channel 发送会 panic。多发送者场景应由协调者关闭，或用 context/完成计数表达结束。

## 共享状态与内存可见性

通信可以转交数据，多个任务也可以共同访问状态。后一种情况需要同步保护完整不变量，并为写入建立可见性关系。

### 数据竞争与 happens-before

多个 goroutine 并发访问同一内存、至少一个是写且没有同步，就可能产生 data race。channel 发送/接收、锁解锁/加锁、goroutine 启动等特定关系建立 happens-before，使写入对另一方可见；不能用 sleep、日志顺序或“通常先执行”代替同步。

### Mutex、RWMutex 与 atomic

Mutex 保护一个完整不变量，适合大多数共享状态；RWMutex 只有在读多写少、读临界区足够大且竞争测量证明有收益时使用；atomic 适合计数器、标志和设计清晰的无锁协议。不要把多个 atomic 字段拼成没有一致性保证的复杂事务。

### sync.Map 的适用范围

sync.Map 适合读多写少、键集合相对稳定或不同 key 由不同 goroutine 频繁访问的特定场景；普通 map 加 Mutex 更容易表达复杂不变量、类型和批量更新。选择前用 workload benchmark，不要把 sync.Map 当成普通 map 的无脑升级。

### sync.Once 的一次初始化

`sync.Once.Do` 只调用一次初始化函数；函数发生 panic 后，后续 `Do` 也不会重新执行它。因此初始化失败若需要重试、刷新或按租户管理，就要使用显式状态机，不能把 Once 当成重试器。[sync.Once.Do](https://pkg.go.dev/sync#Once.Do)

### 临时对象与 sync.Pool

`sync.Pool` 适合可安全重置的临时对象复用，池中对象可能随时被移除。因此它不能保存业务状态、连接或必须命中的缓存，也不能代替业务锁和资源生命周期管理。

### 死锁与锁顺序

固定多个锁的获取顺序，缩小临界区，不持锁执行不可控网络/磁盘调用，使用有界等待和超时，并记录锁等待时间。代码评审时画出锁与资源依赖图；测试中加入高并发、取消和异常路径。RWMutex 也会死锁，不能因为“读锁安全”而忽略升级/嵌套。

## 取消沿调用链传播

取消信号只有被每个阻塞点实际监听，才会改变任务行为。它负责停止继续工作，已经交给外部系统的副作用还要依靠业务状态恢复。

### Context 的传播与使用

Context 通常作为函数第一个参数，向下游传播取消、deadline 和少量请求级值；创建子 context 后调用 cancel，服务/数据库/HTTP 客户端必须实际监听它。不要把 context 存入长期结构体、用它传普通可选参数或用 `context.Background()` 在中间层切断调用链。

### select、超时与取消

`select` 同时等待多个通信操作，通常把 `ctx.Done()` 和 timer 放入分支处理取消/截止时间；`default` 会让 select 非阻塞，循环中误用容易形成忙等。长生命周期代码要管理 timer，避免在高频循环里无界创建 `time.After`。

### Pipeline 的退出路径

每个阶段监听context，输入关闭后停止读取，并关闭自己拥有的输出。发送与接收的阻塞等待也要通过select监听取消；只在发送前检查一次，会漏掉随后进入的阻塞。

消费者退出时，生产者仍需响应取消并结束。关闭顺序、错误传播、部分结果和等待所有goroutine的方式要分别约定；主函数返回不能代替这些步骤。

### Timer、Ticker 与长生命周期

高频循环里反复创建 `time.After` 会增加临时对象和定时器压力；长生命周期任务应显式创建并停止 `Timer/Ticker`，退出时释放资源。定时器只是触发信号，不是取消协议，仍要监听 Context、处理任务重入、累计延迟和关闭顺序。

### 取消与外部副作用

取消通常只能停止本地等待和后续工作，不能保证远端已经接收的副作用被撤销；响应超时也不代表远端没有成功。对外部写操作要使用幂等键、状态查询、补偿或对账，结果未知时不能直接重新提交。

## 有界并行、结果汇总与背压

任务拆开以后，执行数、等待数和结果汇总都需要上限。下面把 worker、错误传播与取消组合到同一执行过程，观察它们怎样互相配合。

### Worker Pool 的任务边界

创建有界任务队列和固定数量 worker，提交方在队列满时产生背压；每个任务携带 context、ID、deadline 和状态，worker 处理后上报结果并释放资源。父任务取消时停止接收新任务并等待已开始任务清理；关键错误应取消兄弟任务，不能只打日志。

### Fan-out 与 Fan-in

独立任务可直接并行 fan-out，共享状态或有先后依赖的任务则需先定义同步与执行关系；总并发受 semaphore/worker 数限制，fan-in 按成功、失败、超时、取消分别聚合。部分结果不能被当成完整事实，输出要说明缺口和置信度；副作用任务还需要幂等键和顺序/状态约束。

### 错误传播与兄弟任务取消

创建父 context 和错误收集器，首个关键错误取消兄弟任务，等待所有已启动任务结束后再返回；错误要保留任务 ID、输入摘要和根因。使用 `errgroup` 等工具时仍要理解其取消、等待和并发限制语义，不能把“返回第一个 error”误当成所有资源都已清理。

### 超时、取消与部分结果

为总任务和每个子任务设置 deadline，使用有界 worker pool；每项状态写入结果集合，结束原因区分 success/error/timeout/cancelled，父任务取消时停止投递并等待 workers。聚合器在收到足够的成功证据后可以结束，但必须取消剩余任务并确认它们没有遗留资源或副作用。

### 下游变慢时的背压

给队列、连接池、worker、HTTP 客户端和数据库设置上限；当下游变慢时让提交方等待、拒绝、降级或采样，而不是继续堆积。指标要包含队列长度、等待时长、活跃任务、超时和丢弃数；恢复时还要防止积压瞬间把下游再次打爆。

### 示例：协作取消的有界 Worker Pool

下面是完整标准库程序。任务通道不缓存任务，固定 worker 数限制同时执行的任务；首个任务错误触发取消，提交方关闭通道后等待所有 worker 结束。

```go
package main

import (
    "context"
    "errors"
    "fmt"
    "sync"
)

type Job func(context.Context) error

func RunPool(parent context.Context, jobs []Job, workers int) error {
    if workers <= 0 {
        return errors.New("workers must be positive")
    }
    for _, job := range jobs {
        if job == nil {
            return errors.New("nil job")
        }
    }
    if err := parent.Err(); err != nil {
        return err
    }
    ctx, cancel := context.WithCancel(parent)
    defer cancel()
    queue := make(chan Job)
    var wg sync.WaitGroup
    var once sync.Once
    var firstErr error
    wg.Add(workers)
    for i := 0; i < workers; i++ {
        go func() {
            defer wg.Done()
            for job := range queue {
                if ctx.Err() != nil {
                    return
                }
                if err := job(ctx); err != nil {
                    once.Do(func() { firstErr = err; cancel() })
                    return
                }
            }
        }()
    }
submit:
    for _, job := range jobs {
        select {
        case <-ctx.Done():
            break submit
        case queue <- job:
        }
    }
    close(queue)
    wg.Wait()
    if firstErr != nil {
        return firstErr
    }
    return parent.Err()
}

func main() {
    jobs := []Job{
        func(context.Context) error { return nil },
        func(context.Context) error { return nil },
    }
    fmt.Println(RunPool(context.Background(), jobs, 2)) // <nil>
}
```

`Wait` 返回后才读取 `firstErr`，使主 goroutine 不与 worker 并发访问该结果。多个任务近乎同时失败时，记录的是率先进入 `once` 的错误；其他错误没有聚合。

取消是协作协议：任务必须监听 context 或自行有界结束；这里不会强杀忽略取消的任务，也不会恢复任务的 panic。取消与成功完成同时发生时仍可能返回父 context 的错误，调用方不能据此断言外部副作用没有发生。

## 关闭过程与并发诊断

等待任务结束之后，才能判断资源是否已归还。任务数量、阻塞栈与错误路径共同帮助区分正常等待、资源泄漏和同步错误。

### 服务关闭与资源回收

服务关闭先停止接单，再传播取消、结束生产并等待已启动任务，最后释放它们依赖的客户端和连接池。关闭等待应有截止时间，尚未完成的持久化任务需要留下可恢复状态。

验证时制造生产过快、消费者失败、下游阻塞和取消等场景，观察通道关闭顺序、任务终态与资源释放。时间控制可使用可控时钟、barrier 和 channel，避免用长时间 sleep 猜测任务已经结束。

### Goroutine 泄漏

goroutine 因 channel 无人接收、锁、网络、ticker 或后台循环没有退出条件而长期存活，持续占用栈和引用。验证时看 goroutine profile、数量基线、阻塞栈和任务生命周期；测试中覆盖正常完成、取消、超时、下游关闭、panic 和队列满，不能只测试成功路径。

### Race Detector 的覆盖边界

Race Detector 检查实际执行路径上的数据竞争。没有执行到的访问、死锁、活锁、错误的业务不变量和泄漏仍需分别分析；压力测试、确定的关闭协议和故障路径测试提供的是不同维度的证据。

同步规则见 [Go 内存模型](https://go.dev/ref/mem)；通道发送、关闭和锁只在规定条件下建立可见性，`sleep` 不能代替同步。完整服务入口见 [网络与后端](./04_网络与后端.md)。
