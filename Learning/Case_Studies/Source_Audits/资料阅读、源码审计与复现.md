# 技术资料证据与复现工作流

本文只保留“如何把资料变成可验证知识”的流程；具体主题知识回到对应目录，项目未取得源码时不宣称逐文件精读。

## 1. 先定义问题

写清：要回答的具体问题、范围、读者、时间点、成功证据和不能回答的部分。先拆定义、机制、实现、性能、风险和版本，不要从搜索结果直接拼结论。

## 2. 来源与证据

| 来源 | 适合证明 |
|---|---|
| 官方规范/API/公告 | 当前行为、字段、限制和兼容性 |
| 论文/标准/RFC | 方法、假设、实验与协议语义 |
| 源码/测试/提交 | 实际实现、边界和版本差异 |
| Benchmark/生产记录 | 在特定数据和环境下的性能 |
| 博客/课程/二手总结 | 入口、解释和线索，不作唯一依据 |

每条结论标记 `direct`（直接证据）、`inferred`（有依据推断）、`uncertain`（待核验），同时记录来源、版本、发布日期/核对日期和适用范围。

## 3. 按资料类型阅读

- 论文：问题 → 方法 → 数据 → 指标 → 基线 → 局限；先看图表和实验设置，再读推导。
- RFC/标准：术语、状态机、消息合同、错误和兼容性；区分规范要求与实现建议。
- 官方文档：安装/最小例子 → API 合同 → 限制/安全 → 版本变更；不要把示例默认值当生产建议。
- 源码：入口 → 调用链 → 状态/数据结构 → 错误路径 → 测试 → 发布配置。
- Benchmark：环境、数据集、版本、参数、基线、重复次数和统计方式必须同时记录。

## 4. 复现与审计

```text
固定版本/环境 → 固定输入和参数 → 运行基线
→ 保存日志/输出/耗时 → 改一个变量 → 比较结果
→ 记录不能复现的原因和适用边界
```

复现记录至少包含代码/数据/依赖版本、随机种子、硬件、命令、输出、失败日志和结论。性能结论必须说明数据分布、并发、缓存和测量口径；不能把单次运行写成普遍规律。

## 5. 易变信息

模型 ID、API 字段、价格、依赖版本、网络参数、法律/监管、税制、交易规则和产品限制都要记录核对日期。回答时区分“文档当前写什么”和“系统实际验证了什么”；旧资料不能因为措辞确定就当成当前事实。

## 6. 知识沉淀

每条笔记尽量保留：

```text
问题 → 结论 → 证据 → 推理/假设 → 反例/限制 → 可复现实验 → 下一步
```

不要把摘录堆成正文；先用自己的话解释，再保留最小必要原文和链接。把新失败、反例和版本差异加入主题文章或 Eval，不另开重复总结页。

## 7. 版权与引用

记录来源并使用自己的总结；只保留必要短引文，不复制整篇文章、课程或论文。附件、源码和数据按许可使用，无法公开的内容只记录可验证的主题结论。

## 8. 研究记录模板

```yaml
question: "要验证什么"
scope: "版本、数据和时间范围"
sources:
  - url: "https://..."
    type: "official|paper|source|benchmark"
    checked_at: "YYYY-MM-DD"
claims:
  - text: "结论"
    evidence: "章节、代码、实验或输出"
    status: "direct|inferred|uncertain"
reproduction:
  command: "..."
  environment: "..."
  result: "..."
limits: "不能推出什么"
next_step: "..."
```

## 研究输出发布时检查

- 问题范围和版本明确；
- 关键结论有分级证据；
- 代码/数据/环境/命令可复现或明确说明不可复现；
- 结论与推断、事实与建议分开；
- 反例、限制、版权和下一步已记录。
