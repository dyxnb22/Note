# 拼团交易平台

拼团是一条交易与营销协作链路，不只是一个下单页面：资格判断、优惠试算、锁单、支付、回调、组队进度、结算、退款和补偿必须分别建模。

## 分层与模块

```text
API → App → Domain → Infrastructure
                  ↑
             Trigger/Task/Message
```

仓库按 `api`、`app`、`domain`、`infrastructure`、`trigger`、`types` 分模块。接口负责协议，应用层编排用例，领域层承载活动/人群/交易规则，基础设施接入数据库、缓存、消息和支付，Trigger 接收定时任务、消息和回调。

## 核心事实

- 试算回答“现在应付多少”；锁单回答“优惠和库存是否暂时占住”。
- 订单、组队、支付、库存和权益分别使用状态机，不能用多个布尔字段隐式表达。
- 支付回调必须验签、校验金额和业务号，并允许重复到达。
- 过期订单释放库存和优惠权益，不能只依赖一次定时任务。
- 成团、未成团、退款、结算和发券都需要可重试、可对账、可人工修复。

## 规则与可靠性

营销规则适合用策略、责任链或规则树组合；资格、价格计算、库存预占和权益发放要拆成不同步骤。跨服务调用使用幂等键、状态条件更新、超时、重试上限和补偿任务。

## AI 排障延伸

项目中的日志标准化、ELK 查询和 MCP 工具可以形成：

```text
日志/指标 → 工具化检索 → Agent 分析 → 结构化诊断报告
```

工具只提供受控查询能力，不能把日志系统和服务器执行权限无条件暴露给模型。

## 可复现实验设计

### 1. 先把四条状态机画清楚

不要只画“下单成功”主流程，而要分别列出订单、拼团、支付和库存的合法状态与迁移条件：

| 对象 | 典型状态 | 必须验证的不变量 |
| --- | --- | --- |
| 订单 | 待支付、已支付、已取消、已退款 | 一个业务单只能对应一个最终支付结果 |
| 拼团 | 待成团、已成团、已失败 | 人数不能超过上限，终态不能被普通事件逆转 |
| 支付 | 待支付、处理中、成功、失败 | 同一支付单重复回调不能重复记账 |
| 库存 | 可售、预占、已扣减、已释放 | 可售数、预占数和已售数变化必须守恒 |

为每条迁移记录触发事件、前置条件、事务边界、幂等键、失败补偿和审计字段。测试至少覆盖“合法迁移成功”和“非法迁移被拒绝”。

### 2. 并发库存与重复支付实验

库存实验可用 100 个并发请求争抢 10 件商品，分别比较：

- 数据库条件更新：`update ... set stock = stock - 1 where stock > 0`；
- Redis Lua 原子预占；
- 先查后改但没有锁的错误实现。

验收时同时检查成功订单数、剩余库存、重复业务单和失败请求原因，不能只看接口返回码。

支付回调实验应重复、乱序和并发发送同一通知，并校验签名、商户号、业务单号、金额、币种和支付状态。以支付平台事件号或“支付单号 + 状态”作为幂等依据；数据库唯一约束是最后防线，但不能替代业务校验。

### 3. 消息可靠性与补偿

如果支付事务后需要通知拼团、库存或营销系统，可比较“事务内直接发消息”和 Outbox：

1. 本地事务同时写业务表与事件表。
2. 独立发布器投递事件，并记录投递次数与最后错误。
3. 消费者按事件 ID 幂等处理。
4. 故意在提交前、提交后、发送后和消费中途杀死进程。
5. 验证重启后不会丢事件，也不会重复产生业务结果。

超时订单释放库存应以明确的截止时间和当前状态为条件；定时扫描、延迟消息或时间轮都要考虑重复触发。每日对账至少比较业务订单、支付流水、退款流水和库存流水，差异进入人工处置队列。

### 4. 证据矩阵与验收

| 结论 | 代码/配置证据 | 测试证据 | 运行证据 |
| --- | --- | --- | --- |
| 不超卖 | 条件更新、Lua 或锁实现 | 高并发争抢测试 | 库存与成功订单守恒 |
| 回调幂等 | 唯一键、状态条件、验签逻辑 | 重复/乱序回调测试 | 仅一条有效支付流水 |
| 消息不丢 | Outbox、重试和死信配置 | 故障注入测试 | 事件最终送达且结果唯一 |
| 超时可恢复 | 关闭订单与释放逻辑 | 时钟推进/重复执行测试 | 订单和库存最终一致 |

完成案例时保留固定数据集、启动命令、依赖版本、测试报告和关键日志；没有真实运行证据的部分继续标注为设计或待验证。
