# Redis 轻量游戏状态

钓鱼佬网页游戏是一个轻量案例：Java 和 Python 两个版本复用同一业务模型，用 Redis 保存高频、短生命周期的游戏状态。

## 建模方式

先定义游戏规则、用户状态、道具、积分和过期行为，再分别设计 API 与 Redis 访问层。业务规则不能因为使用 Redis 就散落在字符串 key 和序列化代码中。

## Redis 适用边界

- 适合高频读写、按用户/场景定位、结构简单且允许按 TTL 管理的数据。
- 需要明确 key 命名、序列化版本、TTL、并发更新、重建和 Redis 不可用时的行为。
- 关键账务、不可丢失事实和复杂查询不应只保存在缓存中。
- 双语言实现的比较重点是业务边界、数据访问隔离、接口一致性和可复现性，不是语法差异。

## 最小检查清单

- 状态是否有版本或更新时间，能否防止乱序覆盖？
- 重复请求是否幂等，计数/道具扣减是否原子？
- 过期状态如何清理，过期后是否允许重建？
- 配置、初始化数据、启动和测试步骤是否记录？
- Redis 故障时是降级、只读、重建还是阻断写入？

## 深化实验：从可用到可恢复

### 数据模型与生命周期

先为每类键写一张契约表：键名模式、字段、类型、版本、TTL、数据所有者、写入者和重建来源。状态值应包含 `schemaVersion` 与 `updatedAt`；升级结构时采用双读、惰性迁移或离线迁移，并明确旧版本何时停止支持。

TTL 不是随手设置的缓存参数。实验应验证续期策略、批量过期抖动、过期后重建，以及“会话过期但索引未过期”等孤儿数据。重要状态若只能从 Redis 找回，它就不是普通缓存，需要持久化与备份设计。

### 原子性、幂等与乱序

- 用 Lua 或事务把“校验版本—扣减道具—更新状态—记录请求号”放进一个原子边界。
- 用 `requestId` 保存短期幂等结果，重复请求返回原结果。
- 用版本号或逻辑序号拒绝旧事件覆盖新状态。
- 对热点玩家或房间压测，观察吞吐、P95/P99 延迟、冲突率和大键。

测试需包含同一玩家双击、两个设备并发操作、网络超时后重试，以及事件乱序到达；最终校验资源不能为负、奖励不能重复发放、版本只能前进。

### 故障与重建

依次注入 Redis 短暂超时、连接池耗尽、主从切换、进程重启和缓存清空。为不同数据选择阻断写入、只读降级、使用本地快照或从权威存储重建，不要用一个兜底策略覆盖所有状态。

重建实验记录恢复点目标、恢复时间目标和最大可接受数据丢失量。若采用 AOF/RDB，也要实际恢复一次，而不是把“已开启持久化”等同于“可以恢复”。

### 跨语言契约与验收

Java 服务和 Python/脚本客户端共享 JSON Schema 或 Protobuf 契约，并用同一批 golden cases 验证字段默认值、枚举、时间和大整数。验收证据包括：

- 固定种子下可重复的状态演进；
- 并发测试中不变量始终成立；
- 故障恢复后数据可解释、可重建；
- 键数量、内存、命中率、过期量和慢命令可观测；
- 所有结论标注为代码已核对、测试已运行或仍待联调。
