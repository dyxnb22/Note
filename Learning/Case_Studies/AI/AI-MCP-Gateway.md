# AI MCP Gateway

AI MCP Gateway 把普通 HTTP/RPC 接口转换成标准化 MCP 工具，并解决协议、Session、权限和分布式部署问题。它不是简单反向代理，而是一个带状态和治理能力的工具网关。

## 核心链路

```text
OpenAPI/业务接口
      ↓
协议解析与参数映射
      ↓
网关配置 → 工具元数据 → MCP Client 调用
      ↓
JSON-RPC / SSE / Streamable
      ↓
Session、鉴权、错误映射、审计
```

## 模块职责

- `api`：管理端、SSE、Streamable 的接口契约。
- `domain`：网关、协议、鉴权、LLM、Session 的模型和生命周期。
- `case`：SSE/Streamable 用例、Session 和消息处理。
- `infrastructure`：MyBatis、Redis/Redisson、HTTP 网关和协议数据访问。
- `trigger`：HTTP 控制器和 Redis Session 事件监听。
- `app`：Spring Boot、WebFlux/WebMVC、数据库、Redis、线程池和模型配置。

## Session 设计

本地内存保存活跃连接对象，Redis 保存可同步的会话元数据并发布节点事件。分布式部署要区分：

- 本地连接对象：不能简单跨节点共享。
- 会话元数据：可以持久化、同步和恢复。
- 节点归属：创建节点、访问时间、过期清理和删除事件。

客户端切换节点时，要么路由到创建节点，要么在新节点重建本地 Session。

## 协议与安全

- JSON-RPC 要统一请求、响应、错误和工具调用语义。
- SSE 与 Streamable 共用领域能力，但连接建立、请求头、流式响应和关闭语义分别适配。
- OpenAPI 解析按 path/query/header/body 等参数类型使用策略表，避免巨型条件分支。
- 工具发现、调用和配置分别授权；参数需要 schema 校验，危险工具需要二次确认、审计和取消。

## 深化验证方案

### 协议兼容矩阵

不要用一次成功调用代表协议兼容。建立包含 JSON-RPC 请求、通知、错误、取消和超时的用例集，再分别通过 SSE 与 Streamable HTTP 执行：

| 场景 | 关注点 |
| --- | --- |
| 初始化与能力协商 | 版本、能力和不支持项是否明确 |
| 工具发现 | schema、分页、权限过滤和缓存更新 |
| 工具调用 | 参数校验、业务错误与协议错误映射 |
| 流式输出 | 分片顺序、断线、背压与结束语义 |
| 取消与超时 | 上游能否真正终止下游工作 |

兼容测试应固定协议样例和客户端版本，并把原始请求/响应脱敏保存为回归夹具。

### Session 与故障矩阵

分别测试粘性路由命中、请求切到另一节点、节点宕机、Redis 事件丢失或重复、Session 过期和客户端断线重连。对每种故障明确 Session 是恢复、重建还是失败，并校验资源是否释放、旧连接是否失效、重复事件是否幂等。

长连接压测不能只报告 QPS，还要观察活动连接数、每连接内存、事件循环阻塞、首包时间、完整响应时间、异常关闭率和重连风暴。

### 工具治理

工具注册和调用至少经过租户、用户、客户端、工具与资源五层授权。服务端以 schema 校验参数，对文件路径、网络目标和命令类参数做额外约束；危险操作采用预览、明确确认、短时授权、取消和完整审计。

审计记录应能回答谁在何时通过哪个客户端调用了哪个版本的工具、关键参数摘要、授权依据、执行结果与关联请求号，同时避免记录密钥和原始敏感数据。

### 补齐测试证据

现有 `Tests run: 0` 是明确缺口。应先修正 Surefire/JUnit 发现配置，再分层建立：

- 协议解析和策略选择单元测试；
- Session、鉴权、注册和调用集成测试；
- MySQL/Redis 与模拟 MCP Server 的容器化测试；
- 双节点切换、断网和重复事件的故障测试；
- 连接数阶梯压测与资源回收测试。

只有报告中出现实际执行数、失败数、环境版本和可复现命令，才能把“构建成功”升级为“测试通过”；真实 Provider 和生产网络仍需单独标注待联调。
