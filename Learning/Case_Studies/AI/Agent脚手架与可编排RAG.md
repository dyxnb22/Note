# Agent 脚手架与可编排 RAG

这类项目把模型、工具、上下文、工作流、会话和观测抽成可复用底座，再通过管理端配置具体 Agent。

## 三层结构

1. **模型与工具底座**：Spring AI、LangChain4j、Google ADK、MCP 和模型适配。
2. **执行脚手架**：Runner、Loop、Sequential、Parallel、Session、Plugin、Skills 和回调。
3. **业务配置**：Prompt、Advisor、知识库、工具组合、权限和场景流程。

Agent 不是一段 Prompt；它至少包含决策、执行、状态、停止条件和失败处理。

## RAG 链路

```text
文档/SQL/TXT/Word/Git
        ↓
解析 → 切分 → 向量化 → 召回 → 重排 → 上下文装配
        ↓
模型回答 → 引用/结构化输出 → 评估与反馈
```

PostgreSQL 可保存向量数据，Redis 适合标签、配置和快速状态；管理端维护模型、Client、MCP、Advisor、Prompt 等资源，应用代码与具体 Agent 配置解耦。

## 边界

- `Loop`、`Sequential`、`Parallel` 是控制结构；Runner 是执行边界；Plugin/Hook 承载治理和观测。
- Planning/FlowAgent 适合把复杂请求分解为规划、执行和汇总，但强状态、强权限业务仍应由领域代码控制。
- RAG 解决知识缺失和更新问题；不能替代权限校验、业务规则和结果验证。
- 动态配置必须有版本、发布、回滚、权限和审计，不应把所有逻辑藏在拖拉拽流程里。

## 深化为可运营的 Agent 平台

### 配置发布与回滚

模型、Prompt、工具、知识库、Advisor 和流程图都应形成不可变版本。一次发布记录版本差异、创建者、审批者、目标环境、灰度比例和回滚版本；运行请求绑定确切配置快照，避免后台修改导致同一请求前后语义不同。

灰度先覆盖内部流量和低风险租户，监控质量、错误、延迟与成本。回滚既要恢复配置，也要考虑已经开始的长流程、缓存和索引版本。

### Eval 数据集与指标

评测集按真实任务类型、难度、语言、权限和风险分层，并分离开发集与盲测集。至少衡量：

- 最终答案正确性、引用支持率和拒答准确性；
- 检索 Recall@K、MRR/nDCG、上下文命中率与无依据回答率；
- 工具选择、参数正确、步骤完成和副作用是否符合预期；
- 轨迹长度、重复调用、恢复能力、延迟与单任务成本。

模型评分只作为一种信号。关键任务加入规则校验、人工抽样和可执行断言，并保存模型、配置、数据集和评分器版本。

### 权限、删除与恢复

检索前按租户、用户和资源权限过滤，生成后再次验证引用资源仍可访问。删除文档时应追踪原文、切片、向量、关键词索引、缓存和备份的处理状态，并用“删除后不可检索”测试验证。

工作流在工具调用前后保存 checkpoint，记录幂等键与外部副作用。通过进程崩溃、网络中断、模型超时和人工取消测试恢复；重放时跳过已经确认完成的副作用，对状态不明的操作转人工判断。

### 容量与证据矩阵

阶梯增加并发、知识库规模和工具时延，观察首 token、总延迟、队列等待、Token/调用成本、向量库负载、模型限流和失败率。为租户设置预算、并发和速率上限，并验证超限行为。

| 能力结论 | 最低证据 |
| --- | --- |
| 配置可回滚 | 发布记录、快照绑定和实际回滚演练 |
| RAG 有提升 | 固定盲测集上的基线对比与误差分析 |
| 工具调用可控 | 权限/确认/取消测试及脱敏审计 |
| 流程可恢复 | 故障注入后的 checkpoint 与副作用核对 |
| 成本可运营 | 分任务成本、容量拐点和限流结果 |

结论按“设计完成、代码存在、测试通过、环境联调、生产观察”分级，避免把架构图或演示结果当作已经运营验证。
