# 05.2 Skill 与协作编排

本页从 Skill 的组成和加载方式讲起，再比较 Skill 与多 Agent，最后讨论委托、安全和改进。

## Skill 基础

### 1. Skill、Prompt、Tool、Workflow 和 Agent 的边界分别是什么？

答：按职责区分，不把“写了一段说明”当成执行权限。

| 对象 | 主要职责 |
|---|---|
| Prompt | 表达当前任务、约束与模型所需信息 |
| Skill | 组织可发现、按需加载的步骤、领域知识和配套资源 |
| Tool | 以结构化合同执行一个可调用动作，不保证天然原子或可回滚 |
| CLI | 一种具体的 Tool 接口，仍受命令白名单和运行环境权限约束 |
| Workflow | 用代码定义主要节点、分支和恢复路径，可包含模型与工具 |
| Agent | 根据目标与环境反馈动态选择后续动作 |
| MCP Server | 通过协议向宿主提供工具、资源和提示模板 |
| Harness | 组织上述能力并提供运行约束、验证、观测与恢复 |

Skill 内容可写明适用/不适用情形、输入输出、步骤、错误与退出条件，并按需引用脚本、资源和验证方法。文件格式与宿主扩展分开看，实际授权由执行层维护。[Agent Skills 格式](https://agentskills.io/specification)。


### 2. “一个 Agent × N 个 Skill”与“多个专用 Agent”的核心差异是什么？

答：前者通常共享同一个 Loop、身份、State 和基础模型，**只按任务加载不同的能力包**；后者拥有相对独立的上下文、策略、生命周期和权限，需要通信与结果聚合。Skill 更适合流程相近、共享事实多的能力；独立 Agent 只有在模型/权限/上下文隔离、并行执行或独立生命周期带来明确收益时才值得引入。

关联：[[Learning/Agent/05_Multi-Agent与Workflow/Multi-Agent与Workflow#2. 如何从 Workflow/单 Agent 基线逐步引入多 Agent？|Multi-Agent 与 Workflow题2]]

### 3. Skill 的渐进式披露应该分几层？为什么不能首轮把全部正文和工具 Schema 都塞给模型？

答：Agent Skills 的基本加载结构是：目录元数据（名称、描述等）→ 激活时读取 `SKILL.md` 正文 → 正文引用到的脚本、参考资料与资源。工程实现可以增加候选召回或能力摘要，但要与这三类内容区分。

工具 Schema 是否延后加载是宿主的另一项能力治理策略，不是每个 Skill 的必需格式。按需加载能减少无关内容、选择混淆和 Token；每次激活仍要检查来源与权限。[加载层次与集成方式](https://agentskills.io/client-implementation/adding-skills-support)。

### 4. 嵌套 Skill 和参数化 Skill 有什么价值？如何防止递归、参数污染和能力越权？

答：嵌套能复用通用步骤，参数化能让同一流程适配不同数据源、输出格式或风险等级。工程上要定义允许的子 Skill、最大深度、调用预算、参数 Schema 和默认值；参数必须在边界处校验，子 Skill 只能继承明确授予的能力，不能因为父 Skill 传入一个“管理员”字符串就获得更高权限。

### 5. Skill 如何做版本、依赖和兼容性管理？

答：给 Skill、工具 Schema、脚本和评测集建立可追踪版本，记录依赖、输入输出兼容范围和变更类型；发布前跑发现、加载、执行、卸载和安全回归，灰度后保留回滚版本。不要只升级一份 Markdown，因为工具合同、权限和上下文模板的变更也可能破坏旧任务。

## 多 Agent 协作模式

### 6. Leader-and-Workers、Supervisor 和 Peer-to-Peer 三种协作方式如何取舍？

答：Leader-and-Workers 适合中心节点拆分独立子任务并聚合结果；Supervisor 更适合持续观察、验收、重试和调整路线；Peer-to-Peer 灵活但状态和终止条件更难控制。优先选择通信拓扑最简单、责任最清晰的模式，并用任务成功、延迟、Token、故障传播和维护成本证明复杂拓扑的必要性。

关联：[[Learning/Agent/05_Multi-Agent与Workflow/Multi-Agent与Workflow#3. Planner、Executor、Critic、Router、Supervisor 分别负责什么？|Multi-Agent 与 Workflow题3]]

### 7. 跨 Agent 委托、协议与身份传播如何设计？

答：

**任务合同字段：**

| 字段 | 说明 |
|------|------|
| 任务 ID | 唯一标识，用于幂等和追踪 |
| 委托方/执行方身份 | 谁发起、谁执行 |
| 目标与能力声明 | 任务要做什么，执行方需具备什么能力 |
| 输入/输出 Schema | 结构化输入、输出格式和附件引用 |
| 硬约束 | 截止时间、预算、权限 Scope |
| 状态/进度/取消 | 状态语义、进度上报、取消信号 |
| 验收标准与证据要求 | 成功判定、证据引用、版本 |
| 重试与幂等 | 重试条件、业务操作键及 attempt 关系 |
| 异常语义 | 拒绝、失败、部分成功、未知结果及人工升级条件 |

合同还应说明哪些事实已验证、哪些只是待处理建议，避免子 Agent 把上游猜测当成事实。

身份与权限也要绑定到这份任务合同：子 Agent 只获得完成子任务所需、且不超过父任务授权范围的能力；父 Agent 不应把完整 Context 或自身凭证直接传下去。权限范围、Context 最小化和服务端执行校验见 [[Learning/Agent/07_可靠性与安全/身份治理与跨Agent#12. 子任务合同应如何定义输入、输出、权限和终止条件？|身份治理与跨 Agent 题12]]。

---

**追问：Agent Handoff 与 Agent as Tool 有什么区别？**

Handoff 是把当前任务的后续控制权交给另一个 Agent，由对方继续负责一段会话或目标；Agent as Tool 把另一个 Agent 封装成有输入输出合同的黑盒子，调用方仍拥有主流程控制权。需要连续接管、上下文切换或专业权限时可用 Handoff；需要边界清楚、可超时重试、只返回结果的子任务更适合 Agent as Tool。

---

**追问：委托任务如何传播身份、预算、截止时间、取消和证据要求？**

上游生成带 Scope 的委托上下文和 deadline/budget，子 Agent 只能在剩余额度和资源范围内执行；取消通过任务状态/信号传播，结果带证据、版本和副作用状态返回。子 Agent 不能自行提升权限、延长期限或把预算无限转给下游。

---

**追问：Capability Card 或发现信息应该声明什么？**

应声明能力名称、输入输出、限制、支持的任务类型、身份/权限要求、版本、超时、预算、证据和失败语义。发现信息本身也可能被污染，使用前要验证来源、签名/版本和实际执行合同。

---

**追问：跨 Agent 调用遇到超时、取消、重复投递或部分成功时，协议需要表达什么？**

协议应定义任务状态、进度、截止时间、取消信号、业务幂等键、重试条件和结果引用，并区分未开始、执行中、成功、失败、未知和部分成功。取消不等于撤销已发生的副作用；未知/部分结果要进入对账或补偿流程，细节见 [[Learning/Agent/09_工程化与系统设计/02_Durable与生产运维#10. 如何处理“外部请求已经成功，但 Agent 没收到响应”的未知结果？|Durable 与生产运维题10]]。

---

**追问：MCP、A2A 和普通 Function Calling 的本质区别是什么？什么时候该用哪个？**

| 协议 | 本质 |
|------|------|
| Function Calling | 一次模型调用提出动作 |
| MCP | Host 与工具/资源服务的能力协议 |
| A2A | Agent 之间的任务委派与协作协议 |

三者可以组合，但都不自动解决业务成功判定、权限、可靠恢复和评测。

进程内节点适合同一应用、共享状态、低延迟和统一发布；普通 API 适合稳定的服务合同和明确的请求/响应；A2A 适合独立 Agent 之间的能力发现、任务委托、异步进度和独立生命周期。若参与者由同一团队部署且不需要跨系统发现、异步长任务或独立权限，引入 A2A 往往只增加协议、身份、超时和排障成本。

### 8. 如何避免多 Agent 因上下文复制、自然语言闲聊和反复确认而失控？

答：重复劳动、循环调用和责任边界的主答案见 [[Learning/Agent/05_Multi-Agent与Workflow/Multi-Agent与Workflow#7. 如何避免多 Agent 之间重复劳动、循环调用和责任不清？|Multi-Agent 与 Workflow 第 7 题]]。本入口只补充通信差异：只传子任务所需的结构化字段、增量和证据引用，长内容留在受控存储中按需读取，共享状态由明确 owner 写入；不用自然语言闲聊代替任务状态机。

### 9. 如何隔离被委托 Agent 的身份、数据和副作用权限？

答：子 Agent 的数据和权限边界见 [[Learning/Agent/07_可靠性与安全/可靠性与安全#11. 如何让不同 Agent 只能看到自己需要的数据？|可靠性与安全题11]]。委托侧再补三点：子身份绑定 Scope 和过期时间；每次 Tool 调用重新鉴权；Trace 记录原始用户、委托链和执行者。任务文本或返回结果不能提升权限。

## 工程化与评测

### 10. 如何评测 Skill 的发现、加载、使用和卸载质量？

答：分别构造应触发、不应触发和相似 Skill 混淆样本，测发现准确率、误触发率、加载延迟、上下文增量、工具选择、任务成功和卸载后的残留行为。再加入权限、版本升级、依赖缺失、参数边界和长任务中途切换用例，防止只测“能不能跑通一个 Demo”。

### 11. Skill 如何做安全的自我改进？如何防止把错误经验或恶意内容沉淀进去？

答：先把成功/失败轨迹和用户反馈转成候选变更，经过脱敏、来源检查、人工或规则审核，在离线评测集和隐藏集上比较后再灰度发布。任何自动生成的 Skill、示例或规则都不能直接获得新权限；保留版本、变更原因、回滚点和异常监控，发现收益只在某类样本上出现时就按场景路由，而不是全量覆盖。

### 12. Skill 指导模型执行危险操作时，如何与工具权限、审批和 Sandbox 配合？

答：Skill 只描述流程、风险和所需能力，不授予权限。工具网关仍按当前身份、资源和操作授权；代码/文件操作由受限 Sandbox 执行。审批绑定与执行前复核见 [[Learning/Agent/07_可靠性与安全/可靠性与安全#17. 如何让用户预览、确认、撤销和回滚 Agent 动作？|可靠性与安全题17]]，沙箱边界见 [[Learning/Agent/07_可靠性与安全/可靠性与安全#13. 代码执行、Shell、浏览器和数据库工具如何沙箱化？|题13]]。
