# 05.2 Skill 与能力复用

## 将任务方法整理为 Skill

Skill 把一类任务的知识、操作步骤和配套资源打包，供执行者按需读取。它提供做法，本身不独立执行任务。

Prompt 写指令，Tool 执行动作，Workflow 安排步骤和分支。一个 Skill 可以同时引用这些做法和能力。

同一个 Agent 可以加载多个 Skill，处理不同类型的工作。若拆成多个 Agent，还要管理各自的上下文、状态、调度和权限。

## 按需加载技能内容

加载器先提供名称和适用描述，选中技能后读取正文，用到脚本或模板时再取配套资源。这种“渐进式披露”减少首轮无关输入。技能选错、资源缺失或版本不兼容时，由宿主报告或处理。

| 层次 | 主要内容 | 解决的问题 |
|---|---|---|
| 目录描述 | 能力名称与适用任务 | 是否值得加载 |
| 技能正文 | 方法、步骤与判断标准 | 怎样处理该类任务 |
| 配套资源 | 参考、脚本与模板 | 需要哪些具体材料 |
| 宿主执行环境 | 实际工具与授权范围 | 哪些动作真正允许执行 |

例如报告技能要求检索能力，但加载正文不会自动授予 search 权限。应用可以记录所需工具并检查可用性；required_tools 这样的字段属于加载器设计，不应被误认为 Agent Skills 标准必填字段。

## 一次报告技能怎样执行

整理制度对比报告时，模型先从目录描述中找到 report 技能，再读取正文中的步骤：收集证据、按维度整理、核查来源、组织结论。执行者随后使用已授权的检索工具取得材料，留下带出处的中间记录，最后生成报告。

运行记录保存本次技能版本、工具调用和报告位置。下次可以复用做法，材料和证据要针对新问题重新取得。

报告涉及两份材料时，同一个 Agent 可以顺序处理；需要并行或隔离时，再由编排层拆成子任务。

## SKILL.md 怎样组织

Agent Skills 格式要求技能目录包含 SKILL.md：开头的 YAML frontmatter 声明 name 与 description，后面是 Markdown 正文。名称需符合规范并与目录匹配；参考材料、脚本和模板放在配套子目录。宿主决定何时加载、怎样执行。[Agent Skills 格式](https://agentskills.io/specification)

整理订单咨询技能时，目录描述写清何时使用，正文说明怎样取得订单与制度证据，脚本实现可重复的处理步骤。把整份制度放进描述，会增加每轮输入，也不便于管理制度版本。需要制度材料时，再调用会检查身份和文档访问权限的检索接口。

## 描述与参数边界

技能描述写清适用任务、所需输入和不适用场景。用途相近时，直接写出区别；例如“解释取消规则”和“执行取消”需要不同流程。加载说明后，缺少的订单事实仍要查询。

参数化 Skill 让同一套步骤接收不同输入，每次传入的参数仍要校验。技能再加载其他技能时，还要限制嵌套深度、可加载的依赖和预算。不能让任意外部参数成为脚本路径或高优先级指令。

## 生命周期与版本

管理端保存来源、版本、依赖和内容哈希，运行端记录本次加载了什么、调用了哪些工具、结果如何。停用技能后，停止向后续请求加入它的内容，并清理需要释放的资源。

删除目录项，不会清除旧对话中的文字，也不会停止已启动的进程。宿主要分别处理：从后续请求的工具目录中移除不再使用的工具；清理临时文件和订阅；检查后续上下文及摘要是否还带着已停用技能的指令。已经启动的进程，需要另外按任务规则停止或等待结束。

## 修改后怎样检查效果

修改技能后，用正常任务、容易混淆的相近任务和不该触发的输入比较新旧表现。发布前审核来源、处理敏感信息并记录版本。

技能正文提出的动作仍须通过宿主和工具入口的权限检查。

## 把技能说明写成能验收的步骤

订单制度咨询可以写成四步：查目标订单，按状态检索制度，保留 source_id 和完整条款，提交答案。证据不足就补查，或以未完成结束。应用可把提交入口命名为 finish，并在轨迹中保存每步动作和依据。

测试时加入两个对照输入：“是否可以取消”应选中咨询技能；“替我取消”必须进入业务写入与授权流程。只测试前者，看不出误触发。

比较新旧描述时，记录是否选对技能、是否误触发，以及描述占用的输入 Token 数。描述写得过宽，可能让技能更常被加载，却把咨询误导成写操作。
