# 05.1 Multi-Agent 与 Workflow

本页只围绕编排与协作：单 Agent 基线、角色、通信、委托、并发与聚合。通用运行约束已归入 [Loop 与 Harness](../01_基础架构/Loop控制与Harness.md)，能力复用与加载见 [Skill 与协作](./Skill与协作编排.md)。

## 基础认知：什么时候需要多 Agent

### 1. Workflow 与 Agent 的边界是什么？

答：

**Workflow 的优缺点：**

| 优点 | 缺点 |
|------|------|
| 可解释、可测试、可控 | 遇到未知分支需提前枚举 |
| 易做权限和 SLO | 维护成本随场景增长 |

**如何让 Workflow 某一步具备 Agent 灵活性：** 给该节点定义严格输入输出和预算，让模型只在候选动作集合中选择，并由执行器验证结果；Workflow 负责前置条件、后置验收、重试和回退。保留全局可观测性，局部获得动态能力。

**原则：** 把稳定路径保留为 Workflow，把真正需要开放决策的节点封装成受限 Agent。

---

**追问：轻量 while Loop、显式 Workflow 和图编排分别适合什么场景？**

固定几步、少量工具和短生命周期任务用普通函数或 Loop 足够；存在明确分支、循环、并行、审批和恢复时用 Workflow/图；复杂框架只有在状态、观测和运维收益能抵消抽象成本时才引入。选型从任务不变量出发，不从框架流行度出发。

---

**追问：LangChain、LangGraph 和手写 Workflow 应该如何选择？**

手写代码适合状态少、流程稳定、需要强控制的服务；LangChain 适合复用 Provider、Prompt、Retriever 和 Tool 等组件；LangGraph 适合显式 State/Node/Edge、循环、并行、Checkpoint、interrupt 和流式事件。选择要看状态复杂度、恢复/回放、团队维护和升级成本，不能因为 Demo 代码短就引入框架，也不能把框架 API 当作 Agent 原理。
---

### 2. 如何从 Workflow/单 Agent 基线逐步引入多 Agent？

答：

**演进路径：**

| 阶段 | 适用场景 |
|------|---------|
| Workflow | 路径固定、输入输出稳定 |
| 单 Agent | 边界清楚但路径动态 |
| 多 Agent | 职责清晰、权限隔离、可并行 |

**选型判据（满足任一才考虑拆分）：**

| 判据 | 说明 |
|------|------|
| 职责边界 | 子任务目标是否独立 |
| 可并行性 | 是否可同时执行 |
| 权限差异 | 不同任务是否需要不同权限 |
| 上下文隔离 | Context 是否需要隔离 |

**收益：**

| 收益 | 说明 |
|------|------|
| 职责隔离 | 每个 Agent 只关注自己的领域 |
| 专业上下文 | 子 Agent 拿到更聚焦的 Context |
| 并行执行 | 独立子任务可同时进行 |
| 权限分层 | 不同 Agent 不同权限边界 |

**代价：**

| 代价 | 说明 |
|------|------|
| 消息序列化 | Agent 间通信需要编解码 |
| 上下文传递 | 跨 Agent 传递 Context 增加 Token |
| 状态一致性 | 共享状态并发写入需协调 |
| 调度开销 | 任务分派、优先级、背压控制 |
| 结果聚合 | 多个子结果需要去重、校验、合并 |
| 故障传播 | 子 Agent 失败可能影响父 Agent |
| 延迟放大 | fan-out + 聚合 + 通信叠加 |

**成本收益权衡：** 只有拆分后的成功率、可维护性或安全性收益能抵消通信、延迟和故障传播成本时才用多 Agent。测量每个 Agent 的增量成功率、延迟、成本和失败率，而不是只看最终平均分。

**面经问法：Agent Teams 还是固定 Workflow？**流程和合规步骤稳定、完成条件明确时优先 Workflow；子任务边界需要动态生成、可以独立并行且有清晰专业分工时再试多 Agent。用任务成功率、人工返工、延迟、Token/调用成本、失败恢复和维护成本与单 Agent/Workflow 基线比较。

来源：[蚂蚁 Agent 开发一面](https://www.nowcoder.com/feed/main/detail/7a0ddb8e077041d4b72ba9e5290ad36a)；[小红书 AI Agent 开发面经](https://www.nowcoder.com/discuss/939320406547103744)。

---

**追问：什么证据证明多 Agent 比单 Agent 或 Workflow 更值得？**

在相同任务、模型预算和环境下，多 Agent 应在成功率、长尾覆盖、权限隔离、并行效率或可维护性上有稳定收益，并量化通信、延迟、Token、故障和运维成本。没有基线和消融实验时，"角色更多"不是证据。

---

**追问：三倍 Token 仅换来少量成功率提升，是否保留？**

按任务切片判断那一点提升是否集中在关键长尾或安全场景，并计算人工节省、延迟、可靠性和运维收益；做去掉某个角色、减少上下文或改成 Workflow 的消融。若没有达到业务价值/成本门槛，就回退到更简单的架构。

---

**追问：效果提升但延迟与成本翻倍，是否上线？**

按业务价值比较任务成功率、长尾收益、人工节省和安全收益与新增成本/延迟/SLO 违约；分用户和任务类型灰度，可能只对复杂或高价值任务启用多 Agent。若简单任务收益不明显，应做复杂度路由而不是全量启用。

## 角色、架构模式与协作机制

### 3. Planner、Executor、Critic、Router、Supervisor 分别负责什么？

答：先分职责，再决定实现边界。

| 角色 | 职责 | 可能的实现 |
|---|---|---|
| Planner | 拆分目标、生成或修订计划 | 规则、模型调用、Agent 或 Workflow 节点 |
| Executor | 在授权范围执行动作并返回事实 | 确定性工具执行器，或具备受限工具的 Agent |
| Critic | 按标准检查产物与证据 | 程序验证器、模型审查或独立审查 Agent |
| Router | 判断请求进入哪条路径 | 规则、分类器、模型节点或独立 Agent |
| Supervisor | 分配任务、跟踪进展、验收与聚合 | 固定编排器，或动态协调多个 Agent 的控制器 |

Planner/Critic 可以独立成 Agent，Router 也可以只是单一 Workflow 的入口。应通过独立上下文、任务生命周期、权限和验收边界判断是否需要多 Agent，而不是按角色名计数。[模式参考](https://www.anthropic.com/engineering/building-effective-agents)。

---

**追问：Master + Sub-Agent 架构如何设计？优点和问题是什么？**

| 角色 | 职责 | 设计要点 |
|------|------|---------|
| **Master** | 任务拆分、路由、聚合 | 不能盲信子结果，需校验 Schema、来源、状态、验收条件 |
| **Sub-Agent** | 专长执行 | 最小权限、必要 Context、明确输入输出合同、独立错误语义 |

优点是职责清晰、可独立评测和替换；问题是通信/延迟/成本增加，Master 判断错误会放大失败。演进路径：单 Agent → 规则拆分 → 简单 Master-Worker → 动态 Supervisor → 独立 Agent 服务。

关联：[[Learning/Agent/05_Multi-Agent与Workflow/Skill与协作编排#6. Leader-and-Workers、Supervisor 和 Peer-to-Peer 三种协作方式如何取舍？|Skill 题6]]

### 4. 多 Agent 如何通信？消息、共享状态、黑板和事件总线分别有什么特点？

答：消息适合显式请求/响应和解耦，共享状态便于读取当前事实但并发冲突多，黑板适合多个角色贡献中间结果，事件总线适合异步长任务和回放。选择取决于一致性、实时性、任务规模和审计要求，不能让所有 Agent 直接修改一个大对象。

### 5. 哪些子任务适合并行，哪些必须串行？

答：互不依赖、只读、没有共享写冲突的检索或独立分析适合并行；依赖上一步事实、更新同一资源、需要审批或顺序有业务意义的动作必须串行。并行结果还要统一超时、取消、排序和部分失败语义。

### 6. 并行 Agent 的结果如何合并？冲突如何解决？

答：

**合并流程：**
1. 子 Agent 返回结构化结果、证据、置信度和状态
2. 确定性聚合器去重、校验和排序
3. 冲突按来源、时间、任务权威性处理

**State 并发写入防护：**

| 措施 | 说明 |
|------|------|
| 字段 owner | 每个字段指定写入者，避免多 Agent 覆盖同一大对象 |
| 写入语义 | 事件、版本/CAS、Reducer 或分区状态 |
| 冲突记录 | 显式记录冲突来源、依据和版本 |
| 仲裁规则 | 按业务规则仲裁，无法判断转人工 |

**关键原则：** 不能用"最后写入者获胜"掩盖错误。不要让一个模型凭感觉拼接互相矛盾的事实。

跨 A2A/Task API 仲裁时也要保留来源 Agent、委托链、证据、版本和最终裁决，不能简单平均多个模型的意见。

**面经变体：多个 Agent 同时修改同一文件或状态**时，先按字段/资源指定写入者；文件修改让子 Agent 在隔离分支或工作区输出 Patch，由单一协调者核对基线版本、检查冲突后串行提交。共享 State 使用版本号/CAS 或事件合并，不能让多个 Agent 直接覆盖同一可变对象。

来源：[蚂蚁 Agent 开发一面](https://www.nowcoder.com/feed/main/detail/7a0ddb8e077041d4b72ba9e5290ad36a)；[小红书 AI Agent 开发面经](https://www.nowcoder.com/discuss/939320406547103744)。

**追问：两个子 Agent 对同一个事实给出冲突结论，父 Agent 如何判断、合并或升级人工？**

先用权威工具或原始数据回查，再按时间、适用范围、证据引用和任务验收标准判断。不能确定时保留冲突和不确定性并升级人工，不按模型自报置信度盲选；冲突样本写入 Trace 和回归集。

### 7. 如何避免多 Agent 之间重复劳动、循环调用和责任不清？

答：为每个 Agent 定义能力/权限边界、任务状态和完成标准，消息中携带任务 ID、依赖和已完成事实；设置最大委派深度、调用次数、Token/时间预算和无进展检测。父 Agent 负责最终验收，子 Agent 不得把未验证的计划当成结果。

---

**追问：子 Agent 经常重复调用同一个工具，应该修改拆分、通信协议、Harness 还是 Prompt？**

先从 Trace 判断重复是因为父子状态没共享、任务合同不清、工具结果未被识别还是模型策略问题；优先修复状态/协议和执行层幂等，再优化 Prompt。不能只加"不要重复调用"一句话，因为它没有事实和执行约束。

关联：[[Learning/Agent/01_基础架构/Agent基础与架构#14. 如何避免 Agent 重复调用同一个工具？如何检测无进展循环？|Agent 基础与架构题14]]

### 8. 一个 Agent 如何把任务委派给另一个 Agent？

答：任务合同、身份/预算/取消传播和异常语义见 [[Learning/Agent/05_Multi-Agent与Workflow/Skill与协作编排#7. 跨 Agent 委托、协议与身份传播如何设计？|Skill 编排与协作第 7 题]]。本页重点：无论合同如何传播，父 Agent 保留授权与最终验收责任，委派不能绕过租户、工具和人工审批策略。

### 9. 如何让多 Agent 任务支持取消、暂停、恢复和重放？

答：为整棵任务树设置可传播的取消令牌和状态，关键节点保存 Checkpoint，子任务记录租约、结果和副作用状态；恢复时先检查版本和外部事实。重放使用冻结消息/工具 Fixture，避免真实副作用再次发生。

关联：[[Learning/Agent/01_基础架构/Loop控制与Harness#5. Stop-Resume 与 Hang-Wait 的语义有什么区别？如何选择？|Loop 题5]]

### 10. 多 Agent 并发会产生哪些性能问题？

答：问题包括模型调用 fan-out、上下文复制、下游限流、队列堆积、结果聚合、锁竞争和尾部延迟放大。优化顺序是减少不必要拆分、限制并发、并行独立读、缓存稳定上下文和使用模型路由，同时监控任务级而非只看单请求延迟。

## 场景追问：从单 Agent 演进到多 Agent

### 11. 一个研究任务包含检索、分析、写作和审校，如何组合 Skill、Workflow、Supervisor 和独立 Agent？

答：常见做法是由一个主 Agent 加载检索、分析、写作和审校 Skill，再用 Workflow 固定“取证 → 分析 → 写作 → 审校”的顺序。只有执行顺序需要随证据动态调整，且每个阶段都有明确验收条件时，才加 Supervisor。若分析需要隔离的代码环境、审校必须独立，或子任务可大规模并行且权限/模型不同，再把相应环节拆成独立 Agent。最终写作只使用已验证证据，并核对引用和事实。
