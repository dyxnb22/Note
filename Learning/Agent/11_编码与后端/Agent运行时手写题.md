# 11.1 Agent 运行时手写题

前半部分串起运行链路，后半部分练习有限 Loop、工具执行器和异步调度。模型底层性能问题回到模型专题；实现时重点验证状态、授权、预算、取消和外部副作用。

## 运行链路与实现前置


### 1. 如何写出一个最小但可控的 ReAct Agent Loop？

答：核心是有限状态循环：组装任务与观察 → 调模型 → 解析“最终答案”或结构化 Tool Call → 校验工具白名单与参数 → 执行并写入 Observation → 检查验收/预算/无进展 → 继续或停止。伪代码可以是：

```text
while budget_ok and not finished:
    decision = model(context(state))
    if decision.final: return verify(decision.answer)
    call = validate(decision.tool_call)
    result = execute(call)
    state = append_observation(state, result)
return stop_with_reason(state)
```

关键不在“有一个 while”，而在最大轮数、超时、权限、结构化结果、幂等、失败分类和业务验收都由代码控制。

### 2. 如何实现一个可修订的 Plan-and-Execute 运行时？

答：Planner 输出带版本的任务图，每个节点声明输入、依赖、前置条件和成功证据；Runtime 校验后只执行已就绪节点，并把工具事实写回 State。前置条件失效时，将未执行节点标记为 stale，只重规划剩余分支；已完成的副作用保留结果，不从旧计划盲目重放。限制重规划次数、深度和预算，并用验证结果而不是计划文本推进状态。

### 3. Tool Calling 的 Schema、参数校验和执行结果应该如何衔接？

答：Provider 内容块的归一化与调用配对见 [[Learning/Agent/10_模型与推理/02_Provider适配与框架选型#8. Provider 的 typed content block 如何归一化为内部 `ToolCall` 和 `ToolResult`？|Provider 适配与框架选型题8]]。

本题聚焦执行边界：调用进入执行器前，由服务端校验参数、资源和权限；返回值记录调用 ID、状态、错误类型、数据版本和证据引用。模型文本不能证明工具已执行。校验分工见 [[Learning/Agent/04_Tool与协议/Tool Calling与MCP#5. 工具参数校验应该由模型、服务端还是两者共同完成？|Tool Calling 与 MCP题5]]。

### 4. 工具调用失败时，重试、退避、换工具和人工接管如何组合？

答：按 [[Learning/Agent/07_可靠性与安全/可靠性与安全#27. 工具错误应该如何分类并决定处理或重试？|可靠性与安全题27]] 的错误分类处置：参数错误最多让模型修正一次；暂时性错误只对幂等调用限次退避；不支持的能力改走受限路径，权限拒绝则停止或请求用户；结果未知先对账。所有分支都受次数、时间和总预算限制，并写入 Trace。

### 5. 如何保证带副作用的 Tool 在重复投递下仍然安全？

答：幂等键对应一次业务意图，由业务/执行服务持久化请求、状态和结果。相同请求重投时返回已知结果或进入对账，不重复产生副作用；相同键携带不同参数时应拒绝。

键的组成和未知结果处理见 [[Learning/Agent/09_工程化与系统设计/02_Durable与生产运维#4. 幂等键应该由哪些信息组成？|Durable 题4]]、[[Learning/Agent/09_工程化与系统设计/02_Durable与生产运维#10. 如何处理“外部请求已经成功，但 Agent 没收到响应”的未知结果？|题10]]。消息队列的 exactly-once 不能替代业务幂等。

### 6. 并行调用多个只读 Tool 后，如何聚合、去重、排序并处理部分失败？

答：先为每个调用记录 correlation ID、来源、版本、状态和超时，再由确定性聚合器按实体/证据键去重、按权威性/时间排序，并显式保留部分失败。只有相互独立且无共享副作用的调用才并行；聚合器不能把缺失结果当空事实，最终回答应说明覆盖范围和不确定性。

### 7. 滑动窗口、摘要记忆和向量记忆如何组合，才能避免上下文无限增长？

答：滑动窗口保留近期交互和未完成动作，摘要记忆压缩已完成阶段的目标、事实、决策和未决问题，向量/结构化记忆保存跨会话且经过筛选的偏好或经验。写入长期记忆要经过来源、时间、冲突、权限和用户意愿检查；检索后仍要按当前任务相关性和新鲜度过滤，不能把相似旧内容直接当当前事实。

### 8. 混合检索、Rerank、查询扩展和 Grounding Check 分别解决什么问题？

答：关键词/BM25 擅长精确术语和编号，向量检索擅长语义相似，混合检索提高召回覆盖；Rerank 对候选按问题相关性重新排序；查询扩展补充同义词、实体和子问题；Grounding Check 检查回答是否被证据支持。它们增加延迟和误召回风险，应按召回、证据覆盖、答案忠实度、P95 和成本做分层消融，而不是全部叠加。

### 9. 如何用程序验证和 LLM 评审共同判断一条 Agent 轨迹是否成功？

答：先用程序检查结构化输出、工具状态、测试退出码、业务状态、权限和引用存在性，再用规则或 LLM Judge 评估答案是否覆盖目标、解释是否基于证据和交互是否合适；最终成功由任务级验收定义。LLM 评审不能覆盖真实副作用或任意事实校验，应使用 Rubric、校准样本和人工复核处理高风险/分歧样本。

**可测试性补充：**把 Model Adapter、Context Builder、策略、工具执行器、State Machine 和 Validator 拆成可注入的边界；状态转移用单测，模型和工具用 Fixture，真实协议与权限用集成测试，历史失败用 Replay，完整任务用 Eval。每个测试都应说明验证的是决策、执行还是业务结果。

## 手撕与后端追问

### 10. 手撕一个带最大轮数、工具白名单和结构化结果校验的 Agent Loop，关键状态有哪些？

答：至少记录 `task_id`、State/版本、轮数、截止时间、Token/调用预算、工具白名单、每轮决策、Tool Call 状态、已验证结果、错误计数、幂等键和 StopReason。状态更新要持久化；恢复时重新检查版本与权限。有限 Loop 的推进顺序见题1。

### 11. 手撕一个带超时、指数退避、幂等键和错误分类的 Tool Executor，如何避免重复副作用？

答：执行器先按幂等键读取记录：已成功则返回原结果，执行中则返回可查询状态，未知则进入对账；只有确认未开始，才以原键原子地写入“执行中”并调用下游。完成后持久化结果。瞬时错误按上限退避，参数、权限和业务错误返回结构化失败；超时保持未知，按 [[Learning/Agent/09_工程化与系统设计/02_Durable与生产运维#10. 如何处理“外部请求已经成功，但 Agent 没收到响应”的未知结果？|Durable 题10]] 对账。

### 12. 手撕一个异步 Fan-out/Fan-in 调度器，如何处理并发上限、超时、取消和部分结果？

答：为每个子任务记录状态和 Deadline，用信号量限制并发，完成或超时后把结果写入统一集合；总任务取消时，要向已启动的子任务传播 Cancellation Token，并等待其安全停止或记录其状态，避免遗留后台协程。聚合阶段按成功、失败、超时、取消分开处理，返回部分结果和缺口；对可重试的只读任务使用明确的幂等键与预算，最终由验收器判断是否足够完成主任务。

## 手写练习的验收清单

| 练习 | 最小实现边界 | 至少验证这些失败路径 |
|---|---|---|
| 有限 Loop | Context Builder、ModelResult、State、Tool Registry、预算和停止判断分开 | 直接回答、未知工具、参数不合法、结果回填、无进展、预算耗尽 |
| Tool Executor | 解析/授权/执行/验证分阶段；幂等状态落在持久化边界 | 相同键相同参数、相同键不同参数、超时结果未知、权限拒绝、重启后查询状态 |
| Fan-out/Fan-in | 限制并发，独立记录子任务状态，确定性聚合 | 部分失败、总期限、父任务取消、子任务迟到结果、资源清理 |

先用 Scripted/Fake Provider 与可控工具验证状态转移，再用真实 Provider 和隔离环境检查协议。Mock 通过不能证明真实模型会正确选择工具；真实网络超时也不能代替可重复的故障注入。
