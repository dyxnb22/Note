# 检索系统工程

本篇深入 RAG 下方的检索基础设施：索引、ANN、混合检索、更新、容量和评测。[RAG](RAG.md) 负责从摄取到生成与引用的完整应用链路，[知识系统](知识系统.md) 负责来源、权限、版本和删除治理。

> **学习位置**：先读 [RAG](RAG.md) 了解应用链路，再按项目需要深入本文；本文不重复 RAG 的生成、引用和 Agentic RAG。

## 1. 检索合同

先定义：

- 文档与 Chunk 的唯一 ID。
- 可检索正文、标题、字段和 Metadata。
- 权限过滤发生在哪一层。
- 更新与删除多久生效。
- 查询延迟、吞吐和召回目标。
- 无结果、冲突和过期资料如何处理。

检索系统返回候选证据，不直接保证最终答案正确。

## 2. 词项检索

倒排索引记录词项到文档的映射。BM25 结合词频、逆文档频率和文档长度归一化，适合：

- 精确术语、编号、代码和专有名词。
- 查询词与文档词重合明显。
- 需要较强可解释性。

分词、停用词、大小写、同义词和语言分析器会显著影响结果。代码、中文和混合语言通常需要不同 Analyzer。

## 3. 向量检索

Embedding 把查询和文档映射到向量空间，再按相似度寻找近邻。常见度量：

- Cosine Similarity。
- Dot Product。
- Euclidean Distance。

模型训练时使用的相似度和归一化方式应与索引配置一致。向量相近表示模型认为语义相关，不代表事实一致或权限允许。

**Embedding 选型口述**：先定语言/领域与是否可私有化，再定维度与延迟；中英通用场景常点名 **BGE** 等开源召回模型。换 Embedding = 新索引 + 双写/别名切换，不能混空间。

### 向量库怎么选（面试口径）

| 选项 | 典型定位 | 注意 |
|---|---|---|
| Chroma / 内存 FAISS | 本地原型 | 非生产多副本真相源 |
| pgvector | 已有 Postgres、中小规模 | 运维统一；极大规模要评估 |
| Qdrant / Milvus / 云托管 | 大规模、过滤与运维 | 学习与成本；锁定版本 |
| Pinecone 等纯托管 | 少运维 | 数据驻留、成本、迁移 |

决策顺序：数据驻留与权限 → 过滤/多租户 → 规模与延迟 → 运维能力 → 价格。不要只背产品名。

## 4. 精确 KNN 与 ANN

精确 KNN 扫描全部向量，召回准确但成本随数据量增长。ANN 用近似结果换取延迟、内存和吞吐。

主要结构：

- HNSW：多层近邻图，查询快、召回高，但内存占用和构建成本较高。
- IVF：先聚类到倒排桶，再搜索部分桶。
- PQ：压缩向量降低内存和距离计算成本，但会损失精度。
- Disk-based ANN：把部分结构放磁盘，以更低内存服务大规模索引。

参数必须用真实查询集调优，不能只照搬默认值。

## 5. HNSW

HNSW 通过多层图导航：

- 上层稀疏图用于快速接近目标区域。
- 底层稠密图用于精细搜索。
- `M` 影响每个节点连接数、内存和召回。
- `efConstruction` 影响建索引质量和速度。
- `efSearch` 影响查询召回与延迟。

删除、更新和高并发构建会影响图质量与维护成本。要观察 Tombstone、重建和版本切换策略。

## 6. Chunk 与向量表示

Chunk 不是越小越精确：

- 太小会失去定义、主语和上下文。
- 太大会稀释主题并浪费 Context。
- 固定长度切分可能破坏表格、代码和章节。

可组合：

- 结构化切分。
- Parent-child Retrieval。
- Sentence Window。
- Multi-vector 表示。
- 标题、路径和实体 Metadata。

切分策略必须通过下游召回和引用测试验证。

## 7. Metadata 与权限过滤

过滤字段应类型稳定并建立合适索引。权限必须在候选进入模型上下文前执行。

两种常见策略：

- Pre-filter：先限制允许集合再做近邻搜索，安全直观但可能降低 ANN 效率。
- Post-filter：先检索再过滤，可能不足 K 条，且不能让未授权内容进入后续步骤。

实际系统可用分区、租户索引、允许列表 Bitmap 或迭代扩大候选等方式平衡安全和召回。

## 8. 混合检索

词项检索擅长精确匹配，向量检索擅长语义表达。混合方案：

1. 并行召回候选。
2. 分别归一化或排名。
3. 使用加权、RRF 等方法融合。
4. 去重并进入 Reranker。

直接相加 BM25 和向量分数通常没有意义：二者量纲、分布和校准都不同，「0.8 向量分」与「12.3 BM25 分」不可比。

### RRF（Reciprocal Rank Fusion）

RRF 按**名次**融合，不按原始分数：

\[
\mathrm{RRF}(d)=\sum_{r\in R}\frac{1}{k+\mathrm{rank}_r(d)}
\]

- \(R\)：各路检索器（如 BM25、向量）。
- \(\mathrm{rank}_r(d)\)：文档 \(d\) 在该路结果中的名次（从 1 起）；未进入该路 TopN 可不计或视为很大名次。
- \(k\)：平滑常数，文献与工程里常用 \(k=60\)，减轻「第一名碾压」并稳定融合；应用固定测试集再调，不要玄学改。

操作要点：

- 融合前用稳定文档/Chunk ID **去重**，保留每路命中证据（哪一路、名次、原始分）。
- 先各路取 TopN，再 RRF，再可选 Cross-Encoder Rerank；RRF 不能修复「正确答案根本没进任何一路」。
- 评测应对比：仅 BM25、仅向量、RRF、RRF+Rerank；按查询类型切片（精确标识符 vs 口语改写）。
- 加权 RRF 或学习融合可以做，但要防止过拟合小评测集；权限过滤仍在融合前或融合时强制生效。

## 9. Query Understanding

查询前可进行：

- 拼写和术语规范化。
- 实体、时间和过滤条件抽取。
- 多查询扩展。
- HyDE 或假设文档生成。
- 对话查询改写为独立问题。

改写可能丢失约束或引入不存在的事实，因此要保留原查询、限制次数并在评测中单独比较。

## 10. Reranking

Reranker 对较小候选集做更精细的查询—文档相关性判断。设计时确定：初始候选数、Rerank 后保留数、延迟预算、长文截断、权限与去重顺序。Reranker 只能重排已召回内容，无法修复召回阶段完全遗漏。

### 三种相关度形态（面试加分）

| 形态 | 做法 | 特点 |
|---|---|---|
| Bi-encoder 召回 | Query / Doc 分别 Embedding，ANN 近邻 | 快，适合百万级召回 |
| Cross-encoder 精排 | Query+Doc 拼进同一编码器打分（如 **BGE-Reranker**、Cohere Rerank） | 准，只跑 TopN（常见 50–100） |
| Late Interaction（如 **ColBERT**） | Token 级交互、预计算文档侧表示 | 精度与成本介于二者；实现与索引更重 |

默认叙事：BM25+向量召回 → RRF → Cross-encoder 精排。提到 ColBERT/Late Interaction 作为「既要精度又要可控成本」的折中即可，不必假装线上已上。

## 11. 更新、删除与版本

索引生命周期：

```text
采集 → 解析 → Chunk → Embedding → 写索引
→ 验证 → 激活版本 → 更新/删除 → 重建
```

需要处理：

- 幂等摄取和内容 Hash。
- 文档更新后旧 Chunk 删除。
- Embedding 模型升级时双索引或全量重建。
- 失败重试和部分成功。
- 删除请求的传播延迟。
- 回滚到上一索引版本。

向量和正文存储之间必须有稳定 ID，避免引用错位。

## 12. 容量与性能

估算：

- 向量数 = 文档数 × 平均 Chunk 数。
- 原始向量内存约为数量 × 维度 × 每维字节。
- 还需加图边、Metadata、倒排和运行时缓存。
- 查询成本受候选、过滤选择率、`efSearch`、并发和磁盘影响。

使用真实租户分布测试热点、过滤和更新；均匀随机数据通常会高估生产性能。

## 13. 离线评测

评测集至少包含查询、相关文档/Chunk、相关等级和无答案标记。

指标：

- Recall@K：相关结果是否进入候选。
- Precision@K：候选中相关结果比例。
- MRR：第一个相关结果的位置。
- NDCG：考虑多级相关性的排序质量。
- Zero-result Rate。
- 权限泄漏率和过期资料命中率。

标注存在主观性时，应给出指南、多人一致性和争议处理。

## 14. 在线评测与诊断

在线信号包括：

- 点击、引用展开、复制和后续改写。
- 用户纠正、人工接管和任务成功率。
- 延迟、成本、零结果和超时。
- 按查询类型、租户和索引版本切片。

点击可能受位置偏差影响，不能直接当相关性真值。线上实验需要控制版本、流量和统计显著性。

## 15. 最小实验

1. 建立一组含编号、同义表达和无答案查询的测试集。
2. 比较 BM25、向量和混合检索的 Recall@K。
3. 调整 HNSW `efSearch`，画召回—延迟曲线。
4. 加入 Reranker，确认它只能改善候选内排序。
5. 更新和删除文档，验证旧 Chunk、权限和引用全部失效。

### 15.1 RRF 与 Recall@K 最小实现（可运行）

先用稳定的 Chunk ID 做融合，避免把不同检索器的原始分数直接相加。这个实现只处理名次和去重，方便拿固定样例验证融合逻辑。

```python
from collections import defaultdict


def reciprocal_rank_fusion(
    ranked_lists: list[list[str]],
    *,
    k: int = 60,
) -> list[tuple[str, float]]:
    scores: defaultdict[str, float] = defaultdict(float)
    for ranked in ranked_lists:
        for rank, chunk_id in enumerate(ranked, start=1):
            # 同一路结果中的重复 ID 只保留第一次出现，避免异常数据人为抬分。
            if chunk_id not in ranked[: rank - 1]:
                scores[chunk_id] += 1.0 / (k + rank)
    return sorted(scores.items(), key=lambda item: item[1], reverse=True)


def recall_at_k(
    gold: dict[str, set[str]],
    results: dict[str, list[str]],
    *,
    k: int,
) -> float:
    if not gold:
        return 0.0
    hit_count = 0
    for query_id, relevant_ids in gold.items():
        # 无答案查询应单独统计拒答率，这里只计算有金标证据的查询。
        if relevant_ids and set(results.get(query_id, [])[:k]) & relevant_ids:
            hit_count += 1
    return hit_count / sum(bool(ids) for ids in gold.values())
```

实验记录应同时保存查询类型、每一路 TopN、融合后的 TopK、耗时和权限过滤前后候选数。只有一个汇总 Recall@K，无法判断 RRF 是修复了词法漏召回、向量漏召回，还是只是改变了结果顺序。

## 验收清单

- 能从查询类型选择词项、向量或混合检索。
- 能解释 HNSW 参数对召回、延迟和内存的影响。
- 权限过滤在模型上下文之前生效。
- 索引更新、删除、模型升级和回滚可验证。
- 离线指标能按检索阶段定位失败。
