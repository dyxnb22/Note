# 03 Memory 与 State

## 按用途区分 Context、State 与 Memory

Context 是本轮模型输入，State 记录当前任务的事实与进度，Memory 保存后续交互可能用到的信息。三者可以存在同一数据库中，但用途、更新规则和访问权限不同。

“用户偏好简短回答”可以进入长期 Memory；“订单已经取消”应以业务系统为准；“任务正在等待查询结果”属于任务 State。把三者都存成聊天文本，会让系统难以判断哪个值仍有效。

## 把查询结果写入 State

订单查询返回订单号、发货状态和物流单号后，执行器保存原始结果，运行时把已确认字段写入 State，并更新查询进度。下一轮就能用物流单号继续查物流。

同一条结果可以原样存档、提取字段写入 State，也可以选取一部分放进下一轮 Context。订单发货状态通常只服务于当前任务；用户明确确认的沟通偏好，则可能留作长期 Memory。

## 哪些字段允许模型更新

程序可以接收模型提出的计划和待查线索，但只写入允许模型提供的字段。权限、剩余预算和完成状态由可信程序维护。

| 字段类型 | 合理的维护者 | 更新依据 |
|---|---|---|
| 候选计划 | 模型提出，程序接收 | 结构合法且符合任务范围 |
| 当前业务事实 | 工具与业务系统 | 可信查询及其版本 |
| 权限与身份 | 身份和授权服务 | 服务提供的当前用户、租户及权限 |
| 费用与调用额度 | 运行时记账 | 预留、实际使用和核对结果 |
| 完成状态 | 运行时或验证器 | 任务完成判据 |

例如接收新计划时，只更新计划字段；remaining_calls 由预算管理代码扣减，task_status 则由运行时按完成判据更新。模型提交的同名字段应被拒绝或忽略。

## 长期记忆的写入与召回

长期记忆随内容一起保存所属用户、来源、记录时间、用途和使用范围，通过有效状态和版本判断能否继续使用。用户确认的稳定偏好可以单独保存；模型抽取的候选事实要先校验。

读取记忆时，先按当前用户和租户筛选，排除当前用途不允许读取或已经失效的记录，再按相关性与新鲜度排序。向量相似度只能帮助找到相近内容，不能判断它是否仍适用；敏感信息或重要决策优先回查业务系统。

## 纠正、冲突与遗忘

用户把“居住城市”从上海改成深圳时，新版本成为当前值，旧值可以按保留策略删除，或只向获准查看历史的用户开放。索引和缓存也要失效，恢复流程不能把旧快照重新发布成当前值。

来源冲突时，记录差异与时间，按具体字段的权威来源处理。例如，用户偏好优先采用用户的明确确认，账户余额则以业务账本为准。时间衰减可以降低陈旧候选的召回优先级，不应悄悄改写事实。

## Memory、RAG 与其他存储

Memory 说明信息为什么保留，RAG 说明怎样检索信息来辅助生成，所以长期记忆也可以通过 RAG 读取。旧订单记录只能说明历史状态，当前状态仍要查业务系统。

## 状态的持久化与并发更新

State 保存当前字段与证据引用，原始文件和较大的工具结果可以另存。保存状态时一并记下代码、状态结构和策略的版本，恢复旧任务时才知道怎样读取或迁移。

并行子任务各自返回结果，聚合器按字段合并：计划保留为候选，业务事实采用已验证的工具结果，预算由运行时记账。合并入口拒绝子任务无权更新的字段。

## 用版本条件拒绝过期更新

假设两个编辑者同时读到版本 1。第一个提交时要求“当前版本仍为 1”，成功后升到版本 2；第二个仍携带预期版本 1，就应被拒绝。这个规则称为比较并交换或版本条件更新。

| 操作 | 预期版本 | 实际版本 | 结果 |
|---|---|---|---|
| 编辑者 A 提交新计划 | 1 | 1 | 接受，生成版本 2 |
| 编辑者 B 提交旧计划 | 1 | 2 | 冲突，保持版本 2 |
| B 重新读取后合并 | 根据新事实决定 | 2 | 只提交仍适用的变化 |

发生冲突后，需要重新读取状态，再判断怎样合并。如果只把版本号改成 2，然后重发整份旧状态，第一个编辑者 A 刚才的修改就会丢失。

版本条件只解决旧状态覆盖新状态的问题。执行者的接管与租约见[持久化执行与恢复](../09_工程化与系统设计/02_Durable与生产运维.md#用租约与运行代次确定接管者)。
