# Agent 部署与生产化

本页只讨论 Agent/LLM 应用相对普通 Web 服务新增的生产问题。Docker、环境变量、反向代理、健康检查、CI/CD 和通用回滚流程见 [Backend Delivery](../Backend/Delivery/README.md)，不在这里重复维护。

> **职责边界**：本文负责发布对象、配置、版本兼容、运行 Profile、预算和 Worker 生命周期；SLO、告警、灰度 runbook、事故分级与 Kill Switch 演练的完整内容见 [Agent 运维与事故响应](Agent运维与事故响应.md)。

## 生产对象不只是代码

Agent 系统的一次发布可能同时改变：

- 应用代码和依赖。
- 模型及模型快照。
- System Prompt、Few-shot 和模板。
- Tool Schema、权限和执行器。
- RAG 索引、Embedding、Reranker 和知识版本。
- Workflow 图、状态 Schema 和 Checkpoint 兼容性。
- Eval 数据集、阈值和安全策略。

每个对象都需要独立版本，运行记录必须能还原“哪次请求使用了哪组版本”。只记录 Git SHA 无法复现实际行为。

## 三档运行 Profile

| Profile | 适用场景 | 核心约束 |
| --- | --- | --- |
| Local | 本地实验 | 本地状态、低成本模型、模拟工具、禁止真实副作用 |
| Team | 团队共享服务 | 用户身份、持久化状态、并发隔离、配额和审计 |
| Production | 对外或关键业务 | 高可用、灰度、发布门禁、SLO、灾备和人工兜底 |

Team Server 不等于“更高权限”，而是同一工具合同在多用户、持久化和并发环境中的运行方式。权限仍按用户、租户和任务上下文计算。

## 配置与密钥

Agent 特有配置包括模型、温度、最大输出、上下文预算、工具白名单、循环步数、审批规则和检索参数。

配置必须：

- 绑定明确版本并记录到 Trace。
- 在启动或发布阶段完成类型与范围校验。
- 区分普通配置、敏感密钥和动态策略。
- 支持灰度和快速回滚。
- 防止工具结果、异常和日志泄露密钥。

密钥只通过密钥管理系统或受控环境注入，不能写入 Prompt、知识库、代码仓库或普通配置中心。

## Prompt 与模型版本

Prompt 应像代码一样评审和测试，但不能只按文本文件管理。建议生成不可变的 `prompt_version`，记录模板、变量 Schema、Few-shot、模型和解码参数。

模型升级要做：

1. 离线回归：质量、安全、工具选择和结构化输出。
2. 影子流量：不影响真实用户地比较结果。
3. 小流量灰度：按稳定键分组，避免用户反复切换版本。
4. 监控错误、延迟、成本和人工接管率。
5. 达标后逐步扩大，否则回滚整组版本。

不能因为平均质量上升就忽略长尾安全退化。

## 发布门禁

通用 Eval Harness、安全回归和 Candidate/Baseline 比较由 [Eval 与测试体系](10_Eval与测试体系.md) 与 [Agent Eval 实验方法](09_Agent%20Eval实验方法.md)维护。部署侧只追加三项检查：

1. 发布对象的版本矩阵完整，Prompt、模型、工具、策略、索引和状态 Schema 可回溯；
2. 预算、Checkpoint/Schema 兼容性和 Worker 生命周期检查通过；
3. 灰度使用稳定分组，并预先写下停止条件。

SLO、告警、灰度 runbook 和事故处置见 [Agent 运维与事故响应](Agent运维与事故响应.md)。
## 状态与持久化

服务重启不能丢失长任务或让副作用重复发生。生产运行时要明确：

- 会话状态、Workflow 状态和长期 Memory 分别存在哪里。
- Checkpoint 的事务边界和 Schema 版本。
- Worker 如何通过 Queue、Lease 和 Heartbeat 认领任务。
- 节点如何使用幂等键。
- 已提交数据库但未发布事件时如何恢复。
- 超过重试上限后如何进入 DLQ 和人工处理。

详细原理见 [Durable Execution 与分布式可靠性](06_Durable%20Execution与分布式可靠性.md)。

## 限流、预算与背压

至少同时控制：

- 用户级、租户级和全局请求速率。
- 单任务步数、Token、费用和墙钟时间。
- 模型、Embedding、向量库和工具的并发。
- Queue 长度、等待时间和丢弃/降级策略。

限流不能只放在入口。一个请求可能触发多次模型和工具调用，内部 fan-out 会放大真实负载。达到预算时应进入明确的停止、降级或人工接管状态，而不是无限重试。

## 灰度与回滚

本页只保留部署相关的兼容性约束：灰度键使用用户或租户的稳定 Hash；有状态 Workflow 必须使用兼容的图和状态 Schema；回滚对象要覆盖代码、Prompt、模型、工具、索引和配置。数据库或 Checkpoint Schema 已前向迁移时，不能只回滚应用代码。

具体的流量比例、观测窗口、停止条件、负责人和正在运行任务的处置属于 [Agent 运维与事故响应](Agent运维与事故响应.md)。
## 优雅关闭

普通 HTTP 服务只需停止接收请求并等待处理中请求；Agent Worker 还应：

1. 停止认领新任务。
2. 通知正在运行的节点取消或在安全点停下。
3. 在 Lease 到期前提交 Checkpoint 或释放任务。
4. 关闭流式响应并写明终止原因。
5. 确认外部副作用的状态，避免新 Worker 重复执行。

## 降级与 Kill Switch

部署配置需要预先声明可用的降级档位，例如低成本模型、只读 Agent、固定 Workflow、无工具回答和暂停新任务。每一级都要明确保留的工具、数据、审计和用户提示。

Kill Switch 的操作权限、传播时延、已有任务处理和恢复演练由 [Agent 运维与事故响应](Agent运维与事故响应.md)维护；本页只负责把开关接入运行 Profile 和发布配置。
## 发布闸门的最小实现（注释版）

灰度发布不应只依赖人工观察。下面的示例把硬性安全失败与可权衡的质量指标分开；任何硬门槛失败都直接停止扩大流量。

```python
def rollout_decision(metrics, *, hard_limits, soft_limits):
    # 越权、数据泄露、重复副作用等安全指标不能用平均质量提升抵消。
    for name, limit in hard_limits.items():
        if metrics.get(name, 0) > limit:
            return {"action": "stop_and_rollback", "reason": f"hard_limit:{name}"}

    # 质量/成本/延迟可按预先写下的权衡规则决定继续、暂停或扩大。
    for name, limit in soft_limits.items():
        if metrics.get(name, 0) > limit:
            return {"action": "pause_and_investigate", "reason": f"soft_limit:{name}"}
    return {"action": "continue", "reason": "gates_passed"}
```

每次发布记录 Candidate、Baseline、流量比例、时间窗口、数据集版本、停止条件和实际回滚动作。Kill Switch 也要做演练，确认传播延迟、已有任务处理和恢复权限符合预期。

## 上线检查清单

- 所有发布对象是否有版本并写入 Trace？
- Tool 权限是否按身份和资源动态计算？
- 是否有真实副作用的幂等与对账机制？
- Eval 是否覆盖失败、越权、注入和边界输入？
- 是否设置任务、Token、费用、并发和时间预算？
- Checkpoint 能否跨进程和跨版本恢复？
- 灰度指标、停止条件和回滚负责人是否明确？
- 模型或工具全部不可用时系统怎样降级？
- 是否演练过 Kill Switch、DLQ 和人工修复？
