# 07.2 身份、数据治理与委托

## 委托链中的执行身份

主 Agent 把任务交给研究 Agent，研究 Agent 再调用工具服务。沿这条委托链，要能查到原始用户、委托者和实际执行者；子 Agent 只取得本次任务获准的权限。

“主 Agent 已确认”这条消息不能授予权限。执行器使用程序提供的可信身份，按当前资源和策略检查授权；模型填写的 tenant 或 approved 不作为凭证。

## 子 Agent 只取得子任务需要的范围

假设发起委托的 Agent 有权读取和修改 doc-1，研究 Agent 的角色却只允许读取。那么子任务最多只能读取 doc-1，申请写入也不会扩大权限。委托后仍沿用原租户范围，增加执行者不会增加可访问的租户。

子任务获准的操作，必须同时满足申请范围、角色限制和委托者的实际权限，也就是取三者的交集。期限与预算同样受父任务约束，实际执行时再按当前策略与用户授权复核。

父任务交代目标、可用输入和证据标准，附上当前状态、版本和相关调用记录。能力与凭证也限定在这项子任务内。

## 从登录身份到文档访问范围

身份认证确定“是谁”，授权确定“此刻能对哪个资源做什么”。查询入口根据可信身份及部门、项目、用户组关系生成访问条件，索引保存过滤所需的权限信息。模型自报的 tenant 或角色仍是未验证输入。

RBAC 按角色授予能力，例如允许某类员工使用制度查询；ACL 是资源上的访问控制列表，例如某份文件只允许特定用户组读取；ABAC 则根据主体、资源与环境属性判断，例如地区、项目和数据分类。三者可以组合，但要明确继承、显式拒绝及例外规则，不能把它们简化成一个模型可写的 approved 字段。

员工离开项目后，文档和索引可以完全不变，旧身份快照却可能已经失效。因此，系统既要接收文档权限变更，也要处理用户组变更。查询权威服务、接收失效通知或核验成员关系版本，都可用于检查授权是否仍有效；只靠缓存有效期（TTL），则会在缓存到期前继续沿用旧授权，无法保证撤权即时生效。[文档级访问控制](https://learn.microsoft.com/en-us/azure/search/search-security-best-practices)

例如，用户来自 tenant-A，属于 project-x，成员关系版本为 7。要允许读取，文档也须属于 tenant-A、允许 project-x 访问，而且权威服务中的成员版本仍为 7。若版本已变为 8，旧身份快照就要失效；用户组名字相同也需要重新取得当前成员关系与权限。

用户组相交还不够：令牌须有效，权限继承和显式拒绝也须符合策略。成员关系与文档权限以可信服务为准，旧索引快照和请求方自报字段不能代替它。

关键词搜索、向量搜索、父块展开和图关系扩展都要应用访问条件；交给外部重排服务的材料，还要符合相应使用规则。用户打开引用、下载原文件或查看缓存与历史答案时，仍按产品要求检查当前权限。曾经读过一份材料，不代表以后一直有权读取。

## 身份变更后的缓存与权限

假设 demo 身份可以读取订单 A，private 身份可以读取订单 X。更换可信身份后，访问范围也应随之变化，不能继续复用原身份的结果缓存或授权快照。

因此，身份变更要同时更新成员关系、查询条件和缓存；即使文档没变，用户组版本递增也可能使旧身份快照失效。

## 委托身份与凭证交付

Agent 需要知道“可以查询某类工单”，通常不需要看到调用服务的原始密钥。执行器检查权限后，向凭证服务取得短期、限定用途的凭证，再调用目标服务。模型输入和工具结果只保留必要的业务信息；需要关联实际调用时，使用不含凭证的调用 ID。

运行记录将实际服务调用关联到用户、任务、委托链和业务操作。使用共享服务账号时，在调用入口按当前用户与任务范围收紧权限，模型只看到本任务可用的能力。

凭证需要可轮换、可撤销并有明确有效期。任务取消、审批失效或用户离开项目后，应阻止新的委托执行。凭证不进入 Prompt、长期记忆、普通日志、快照明文或错误堆栈；诊断系统也只能访问必要的脱敏信息。[凭证生命周期与最小权限](https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html)

## 数据分类与最小暴露

公开、内部、机密和受限资料可以有不同的传输、保留与使用规则。复制到缓存、队列、模型请求或其他中间位置后，副本也须遵守原有的访问范围和用途限制。

## 委托结果的接收范围

接收子任务结果时，核对它属于哪个父任务、是否对应当前计划，以及委托是否仍有效。没有采用的结果，也要留下可供审计的记录或受权限保护的记录链接；涉及外部动作时，再查操作记录，核实实际发生了什么。

## 何时使用跨 Agent 协议

A2A 等协议约定不同 Agent 怎样发现彼此、交换消息和交接任务。Agent Card 描述能力和接口，业务授权另行检查。同一团队里的简单节点可以直接调用，无需额外引入跨系统协议。

协议层分别报告请求接收、任务完成和产物可用，业务层负责检查质量、权限与副作用。限制委托深度和总预算，检测重复目标，防止任务在执行者之间循环转交。
