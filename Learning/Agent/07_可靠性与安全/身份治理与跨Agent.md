# 07.2 身份治理、多 Agent 与跨 Agent 协议

本页先梳理身份、权限和数据治理，再讨论能力授权与委托合同，最后判断何时需要多 Agent/A2A。

## 身份与数据治理

### 1. Agent 系统中 Actor、Agent、Service 和 Resource 分别是什么？

答：Actor 是发起或代表操作的主体，可以是用户、管理员或另一个 Agent；Agent 是执行任务的逻辑主体；Service 是承载能力的程序；Resource 是被读取或改变的业务对象。授权要说明“谁以谁的身份对哪个资源做什么”，不能只看调用来源服务。

### 2. 一个授权判断至少应包含哪些维度？

答：至少包含 actor/agent 身份、tenant、resource、operation、当前任务/上下文、策略版本和审批状态，必要时还要有时间、数据分类、目的和风险等级。模型提出的动作不能自带授权结论，服务端必须重新计算。

### 3. 为什么数据分类不能只分“公开/私密”两类？

答：公开、内部、机密、受限数据的访问主体、用途、保留、脱敏和模型传输边界不同；粗粒度分类无法表达支付、凭据、个人信息和专有代码的不同风险。分类应进入检索、工具、日志、缓存和 Provider 路由策略。

### 4. 数据最小化在 Agent 系统里如何落地？

答：只向当前任务提供完成目标所需的字段、时间范围、文档片段和工具能力，按用途限制读写，并在 Context、日志和训练数据中删除无关敏感信息。最小化不是只在 Prompt 中说“不要泄露”，而是从查询、权限和数据返回层减少暴露。

### 5. Secret 的生命周期应如何管理？

答：密钥从秘密系统受控注入，限定作用域和有效期，使用时避免进入模型 Context、普通日志和 Trace，轮换/撤销后使旧凭证失效。工具和 Provider 适配层应提供最小权限，错误输出也要做脱敏。

### 6. 多租户隔离为什么要覆盖数据库、向量库、缓存、工作区、队列和 Trace？

答：不可伪造的 tenant/actor Scope 必须贯穿数据库记录、Memory/State/Checkpoint、向量索引、缓存键、工作区、队列消息、日志和 Trace。每次读取、写入和 Worker 接管都要在服务端校验。

任务恢复时应重新验证当前主体与策略版本；删除请求要覆盖快照、向量和派生记忆。任何一层遗漏，都可能通过搜索、缓存命中、文件路径、任务重放或日志访问泄露数据。仅在界面上显示 tenant_id 不构成隔离。配额和并发上限应按租户设置；跨租户聚合只允许输出经过明确授权和脱敏的统计。

### 7. 数据删除请求为什么不能只删除主数据库中的记录？

答：内容可能复制到倒排/向量/图索引、缓存、摘要、Checkpoint、Trace、回放集、备份和训练派生物。删除流程应追踪所有派生存储并验证不可访问；法定保留的审计也要最小化、脱敏和限制访问。

## 能力授权与委托

### 8. 面向 Agent 的能力授权凭证应绑定哪些条件？

答：应绑定 actor、能力、资源范围、操作类型、参数/操作 hash、租户、策略版本、过期时间和必要的单次使用标记。这样即使凭证被复用，也不能把一个已审批的“给资源 A 做操作 X”扩大成任意写权限。

### 9. 人工审批合同至少要展示什么？

答：审批界面应让用户看清发起者、动作、目标资源、参数、风险影响、依据和有效期；审批记录还要绑定具体主体与操作，并提供撤销入口。审批是否可以执行及其执行前复核见 [[Learning/Agent/07_可靠性与安全/可靠性与安全#17. 如何让用户预览、确认、撤销和回滚 Agent 动作？|可靠性与安全题17]]。

关联：[[Learning/Agent/09_工程化与系统设计/05_实时交互与产品#13. 什么情况下应该澄清，什么情况下应该请求审批？|实时交互与产品题13]]

### 10. 为什么审批不能只是一个布尔值？

答：布尔值只表达“是/否”，无法绑定具体动作和授权有效期。审批应保存为可撤销、可验证的具体授权记录，并在执行前复核；展示字段见题9，执行流程见 [[Learning/Agent/07_可靠性与安全/可靠性与安全#17. 如何让用户预览、确认、撤销和回滚 Agent 动作？|可靠性与安全题17]]。

### 11. 为什么跨 Agent 返回值不能直接作为高权限执行依据？

答：对方可能错误、被注入、权限不足或返回过期事实；“另一个 Agent 说可以”不等于业务授权。上游要验证 Schema、来源、证据、资源权限和当前状态，必要时重新审批和程序化检查。

## 多 Agent 设计与评估

### 12. 子任务合同应如何定义输入、输出、权限和终止条件？

答：输入、输出 Schema、证据和终止状态等通用合同字段见 [[Learning/Agent/05_Multi-Agent与Workflow/Skill与协作编排#7. 跨 Agent 委托、协议与身份传播如何设计？|Skill 与协作编排题7]]。

身份治理还要求每个子任务绑定 actor/tenant、资源与动作 Scope、允许传递的 Context 字段、预算和有效期。子 Agent 不继承父 Agent 的全部权限；检索和工具执行都必须按同一 Scope 在服务端过滤。父 Agent 仍负责审批和最终验收。

关联：[[Learning/Agent/09_工程化与系统设计/05_实时交互与产品#11. 一个 Agent 任务规格至少应包含哪些字段？|实时交互与产品题11]]

### 13. 多 Agent 如何处理部分成功、超时、失败和过期结果？

答：每个子任务记录 ID、attempt、deadline、父任务/计划版本和副作用状态；聚合器只重试失败分支。父任务或计划版本已变化时，拒绝或隔离迟到结果，避免覆盖当前 State；同时保留成功子任务并由父 Agent 做最终验收。

部分成功的用户反馈与补偿见 [[Learning/Agent/07_可靠性与安全/可靠性与安全#5. 如何处理部分成功、部分失败和不可逆动作？|可靠性与安全题5]]；幂等键与未知结果对账分别见 [[Learning/Agent/09_工程化与系统设计/02_Durable与生产运维#4. 幂等键应该由哪些信息组成？|Durable 题4]]、[[Learning/Agent/09_工程化与系统设计/02_Durable与生产运维#10. 如何处理“外部请求已经成功，但 Agent 没收到响应”的未知结果？|Durable 题10]]。

### 14. 如何避免委托循环、语义漂移和错误传播？

答：限制最大委托深度、总预算和重复目标，使用稳定任务/能力 Schema、版本和状态摘要；每次委托验证输入输出和证据，检测相同任务来回转发。下游失败要结构化回传，不能把不确定文本包装成成功。

## 场景追问

### 15. 设计一个跨租户、多 Agent 的研究系统，如何防止子 Agent 越权读取和回传敏感资料？

答：检索服务应先按租户和资源权限过滤，只把完成研究所需的脱敏证据交给子 Agent。结果回传时再检查敏感信息，并记录来源和委托链。子任务凭证与输入授权的通用合同见 [[#12. 子任务合同应如何定义输入、输出、权限和终止条件？|题12]]。

### 16. 一个 Reviewer Agent 认为 Executor 的结论错误，但两者都没有完整证据，你会如何处理？

答：证据不足时，不要让两个 Agent 继续互相说服。先把任务标为“待补证据”或转人工，再查原始数据、运行程序验证，或重新执行只读查询。仍拿不到可靠证据时，保留冲突和影响范围，并按风险降级或拒答。

### 17. 一个委托 Agent 超时后上游想重新派发任务，如何避免重复副作用？

答：请求超时不能说明任务没执行。重新派发前，先用原业务操作 ID 查询任务和外部状态；确认尚未执行后，才用原幂等键重派。新 attempt 仍挂在原父任务下。结果仍不确定时，按 [[Learning/Agent/09_工程化与系统设计/02_Durable与生产运维#10. 如何处理“外部请求已经成功，但 Agent 没收到响应”的未知结果？|Durable 与生产运维题10]] 对账。
