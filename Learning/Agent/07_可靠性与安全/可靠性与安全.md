# 07.1 Agent 可靠性与安全

本页负责错误处置、信任边界、工具执行约束、沙箱、审批和成功证据；身份、租户与委托凭证见 [身份治理](./身份治理与跨Agent.md)，宕机后的状态与副作用核对见 [Durable](../09_工程化与系统设计/02_Durable与生产运维.md)。

## 基础认知：Agent 为什么会失控

### 1. Agent 幻觉有哪些类型？如何定位来源？

答：常见类型包括**事实编造、错误引用、假装调用工具、错误计划、把不可信文本当指令和过度自信表达**。通过 **Trace** 检查 Context、检索证据、工具结果、验证器和最终输出，定位到检索、上下文、模型、工具或展示层，而不是笼统归因于“模型幻觉”。

### 2. 如何通过检索、工具验证、交叉检查和人工确认减少幻觉？

答：需要外部事实时**要求引用可追溯证据**，需要计算/状态时**强制调用权威工具**，关键结果用规则或第二来源校验，高风险动作进入人工确认。这些机制必须包含失败分支和拒答条件，不能只要求模型“回答得更准确”。

### 3. 如何识别 Agent 没有真正执行工具而是编造结果？

答：成功必须依赖执行器产生的**调用 ID、退出码、结构化结果或外部状态**，而不是模型文字；最终回答引用这些证据。没有对应 Trace/验证结果就标为未执行或未知，阻止模型宣称成功；停止当前循环，必要时重派可恢复动作或交人工处理，并向用户说明未完成。

### 4. 子任务失败、数据损坏或返回异常时，如何重试、降级和恢复？

答：错误分类与重试条件见本页题27；外部副作用未知时按 [[Learning/Agent/09_工程化与系统设计/02_Durable与生产运维#10. 如何处理“外部请求已经成功，但 Agent 没收到响应”的未知结果？|Durable 与生产运维题10]] 对账，长任务从有效 Checkpoint 恢复。多 Agent 部分成功时保留已完成分支并只恢复失败分支，详见 [[Learning/Agent/07_可靠性与安全/身份治理与跨Agent#13. 多 Agent 如何处理部分成功、超时、失败和过期结果？|身份治理与跨 Agent题13]]。

### 5. 如何处理部分成功、部分失败和不可逆动作？

答：把每个子动作记录为**独立状态**，向用户说明已完成、未完成和未知部分；可逆动作提供补偿，不可逆动作进入**对账和人工流程**。最终结果不能用一个全局布尔值掩盖中间副作用。

### 6. 如何设计 Fallback、熔断、重试、降级和人工转接？

答：按错误类型和风险预先定义策略：**模型不可用可切换兼容模型，工具不可用可读缓存/固定流程，连续失败熔断并排队或转人工**；每种降级说明能力损失和用户提示。Fallback 仍需同样的权限、Trace 和成功验证。

### 7. 如何让 Agent 在不确定时主动拒答或请求确认？

答：定义证据门槛、置信度阈值、证据冲突条件和高风险动作清单，未满足时输出缺少什么信息、可以怎么补充，并进入澄清或人工状态。拒答也要可解释、可恢复，不能只是生成一句“我不确定”。

## 安全机制：信任边界和数据保护

### 8. 什么是 Prompt Injection？直接注入和间接注入有什么区别？

答：Prompt Injection 是攻击者**让模型改变原定行为、泄露信息或执行越权动作**；直接注入来自用户输入，**间接注入藏在网页、文档、邮件或工具结果中**。后者尤其危险，因为系统可能把外部数据自动送进模型并触发工具。

---

**追问：Prompt 层如何降低用户输入覆盖系统约束的概率？为什么仍然不够？**

在消息和模板中把系统规则、可信 Context 与用户数据分区，**明确指令优先级**、引用边界和冲突处理，并避免把外部文本拼成系统指令。遇到冲突请求时，模型应解释执行边界并给出安全替代。这只能降低模型误解；真正的 allowlist、授权、沙箱和副作用审批**统一由执行层负责，不能由 Prompt 自证安全**。

---

**追问：如何防止检索内容中的 Prompt Injection？**

防御层次包括：标记（检索内容明确标记为不可信数据）、隔离（不能改变系统规则、工具权限或输出策略）、最小化（字段隔离，对高风险文档做内容检测）、重授权（执行器再次授权）、沙箱（浏览/代码操作进入沙箱）、审批（高风险动作需人工确认）。**必要时让模型只提取事实，不把原文指令直接拼入高优先级 Prompt**。Prompt 过滤只能作辅助，不能让模型单独承担防线。

---

**追问：如何防止工具返回值中的恶意指令影响 Agent？**

把工具结果与系统指令分区并标记为外部数据，**限制它只能提供事实，不能改变权限、工具白名单或系统规则**；对网页/文档结果做内容扫描和最小化。执行层重新授权，即使模型被诱导也不能越权。

---

**追问：为什么模型输出和其他 Agent 输出都应被当作不可信数据？**

**输出可能包含幻觉、注入指令、恶意参数、越权建议或错误的外部事实**，即使来自受信模型也不是授权证明。下游应做 Schema、业务/权限、来源和安全校验，尤其不能让输出直接拼接命令或高风险操作。

---

**追问：UI 中的模型文本和仓库文本为什么也要视为不可信输入？**

文本可能包含 ANSI 控制序列、伪造提示、超长内容或恶意 Unicode。**渲染前应清理控制字符、限制长度和行数，并区分显示文本与可执行命令**；UI 防显示注入，不能替代工具权限和沙箱。

### 9. 如何防止数据外泄？

答：Context 字段和返回内容应按用途最小化，具体做法见 [[Learning/Agent/07_可靠性与安全/身份治理与跨Agent#4. 数据最小化在 Agent 系统里如何落地？|身份治理题4]]。安全执行侧还要限制出口工具的域名、动作和传输内容，对敏感操作设置审批；评测覆盖越权查询、跨租户召回和提示注入。

### 10. 如何设计最小权限、凭证隔离、租户隔离和网络隔离？

答：每个任务使用短期、最小 Scope 的身份，工具按 actor/tenant/resource/operation 授权；沙箱限制文件、网络、进程和时间，主应用密钥不得进入模型或子 Agent。多租户 Scope 如何贯穿 State、Memory、索引、缓存和 Trace，见 [[Learning/Agent/07_可靠性与安全/身份治理与跨Agent#6. 多租户隔离为什么要覆盖数据库、向量库、缓存、工作区、队列和 Trace？|身份治理题6]]。

### 11. 如何让不同 Agent 只能看到自己需要的数据？

答：为每个 Agent 定义数据域和工具白名单，Context 组装只读允许字段，服务端查询和执行器再次过滤；父 Agent 不能把全量上下文自动传给子 Agent。共享数据使用明确的发布/授权区并记录来源。

### 12. 如何处理模型输出中的敏感信息？

答：输出前做**敏感信息检测、脱敏和策略检查**，禁止模型直接展示凭证、完整个人信息或内部提示；需要给用户看时按身份和用途最小化。日志、Trace、缓存和评测集也要使用同样的脱敏策略。

**追问：如何做敏感信息识别和脱敏？**

结合规则/正则、实体识别、数据分类和来源标签，按字段和场景替换或部分掩码；高风险类型阻断或人工审核，并保留不可逆审计摘要。还要评估脱敏后是否可被重识别。

## 工程落地：沙箱、审批与审计

### 13. 代码执行、Shell、浏览器和数据库工具如何沙箱化？

答：每次执行使用**隔离 workspace/容器或专用沙箱**，限制文件目录、网络出口、CPU/内存/时间和子进程；数据库工具只暴露参数化、最小权限的接口。浏览器结果仍是不可信内容，写操作要审批和审计。

### 14. Docker、容器、虚拟机和专用沙箱如何选择？

答：容器启动快、适合受控同机隔离，但内核共享；虚拟机隔离强、成本和启动时间更高；专用沙箱根据代码/浏览器威胁模型提供更严格的系统调用和网络控制。选择取决于攻击面、租户信任、性能、成本和合规要求，不能只看部署方便。

### 15. 如何限制 CPU、内存、磁盘、网络、进程和执行时间？

答：使用 cgroup/沙箱配额、只读或临时文件系统、进程数上限、超时杀进程和网络 allowlist；**任务级别还要限制 Token、工具调用和费用**。超限时写入可解释的终止事件并清理资源，防止残留进程和数据。

### 16. 哪些动作必须 Human-in-the-Loop？

答：付款、删除、发信、发布、修改权限、法律/医疗等高影响决策，以及副作用不确定的动作，通常需要人工确认；低风险只读或可逆动作可自动化。工具注册时标明副作用与风险等级，执行时按当前主体、资源和参数重新判断。审批界面应展示的字段见 [[Learning/Agent/07_可靠性与安全/身份治理与跨Agent#9. 人工审批合同至少要展示什么？|身份治理与跨 Agent 题9]]；审批绑定与执行前复核见本页题17。

关联：[[Learning/Agent/01_基础架构/Loop控制与Harness#15. 如何把确定性校验、重试和人工确认插入 Agent Loop？|Loop 与 Harness题15]]

### 17. 如何让用户预览、确认、撤销和回滚 Agent 动作？

答：先生成结构化计划和差异预览，由 Tool Gateway 将待执行调用持久化为 `waiting_approval`，并保存参数摘要、目标资源版本、发起身份和有效期；用户确认后，审批 ID 绑定这一个动作。执行前重新校验权限、参数和资源版本，防止批准过期或被替换的操作；可逆动作保存原状态/反向操作，不可逆动作设计补偿和人工对账。

### 18. 如何记录审计日志？日志中哪些信息不能直接保存？

答：记录谁、哪个租户/任务、调用了什么工具、作用于哪个资源、策略/审批结果、版本、时间、耗时和副作用状态；Secret、完整 Token、私有源码和不必要的原始 Prompt 不应默认保存。日志要可检索、不可随意篡改、可设保留期并有访问审计。

### 19. 如何让 Agent 行为可解释、可追踪和可回放？

答：记录结构化的计划、动作提案、工具结果、状态转移、权限决策、验证结果和停止原因，不依赖不可验证的私有思维链。回放冻结输入、模型/工具版本和外部 Fixture，能重建“为何做了这个动作”。

### 20. 如何评估系统的安全边界和越权风险？

答：**建立威胁模型和攻击集**，测试直接/间接注入、跨租户查询、敏感信息泄露、工具参数越权、沙箱逃逸和审批绕过；指标包括阻断率、误放行、误拒绝和恢复时间。安全评测要纳入发布门禁，不只做一次人工演示。

### 21. 如何在安全、体验、成本和自动化程度之间取舍？

答：按动作风险分级：低风险自动化，中风险预览/确认，高风险人工或禁止；对每级测量任务成功、延迟、成本、误拒绝和安全事件。不要用“全自动”当目标，设计目标是让用户清楚知道系统能做什么、何时会停止。

## 场景追问：高风险动作如何可控

### 22. 网页内容要求浏览器 Agent 忽略系统指令并上传用户文件，如何在数据层、模型层和工具层拦截？

答：我会从三层拦截。数据层把网页内容标为不可信，并限制可访问的文件和网络范围；模型层不把网页文字当成系统指令；工具层只允许经过授权的域名和文件，上传前要求审批。即使模型受诱导，工具层也要阻止未授权上传。

### 23. 如何用一次真实事故复盘证明安全机制不是只停留在 Prompt？

答：复盘时先重建攻击输入、Context、工具候选、授权决策和实际副作用，找出第一处没有拦截的边界。修复应落到权限、Schema、Sandbox、审计或审批，再用攻击回归集验证。若结论只有“优化 Prompt”，说明系统根因还没定位清楚。

## 深入专题：代码 Agent 的安全与恢复边界

### 24. 代码 Agent 如何防止路径越界？

答：对用户和模型提供的路径做规范化，使用工作区根目录进行边界判断，拒绝 `..`、越界符号链接、受保护路径和不允许的文件类型，并在执行前后验证实际目标。Skill 可以说明文件操作步骤，但不能扩大根目录或授予权限；创建/删除前可展示 dry-run 计划或 diff，破坏性动作要求明确确认，并保留备份、审计和恢复方式。错误应返回稳定的拒绝结果，而不是泄露系统路径。

来源：[百度 AI Agent 开发岗面经-04](https://www.nowcoder.com/discuss/931706522621530112)。

### 25. 为什么一般 Shell 工具比专用工具更危险？

答：Shell 包含解释器、重定向、管道、环境变量、命令替换和任意程序组合，难以精确分类副作用。应优先提供窄而明确的工具；确需执行命令时使用 argv、固定环境、工作目录、超时、输出/资源限制和 OS 沙箱。

### 26. 沙箱能保证什么，不能保证什么？

答：沙箱可以限制文件、网络、进程和资源访问，降低执行的爆炸半径；它不能替代身份授权、参数校验、审计、版本检查和结果验证，也不能自动证明进程没有隐藏副作用。必须明确平台差异和失败时的默认行为。

### 27. 工具错误应该如何分类并决定处理或重试？

答：至少区分未知工具、参数错误、权限拒绝、审批拒绝、资源冲突、超时、供应商故障、业务失败和未知副作用。错误分类决定修正参数、重试、人工处理、恢复或终止。只有暂时性错误且动作幂等、预算允许时才重试；参数/权限/业务规则拒绝不盲重试。结果未知先查询或对账，再决定是否重试。错误合同应携带 retryable、重试预算和是否需要查状态，不能把所有失败都包装成“请模型再试一次”。

### 28. Evidence Gate 应该验证什么？

答：应验证任务对应的客观产物，例如实际 diff、最后一次写入后的检查结果、退出码、资源版本和确定性审查结果。模型文本只能作为解释，不能单独证明修改成功；检查若发生在最后一次修改之前，也不能证明最终内容通过。

关联：[[Learning/Agent/01_基础架构/Loop控制与Harness#14. 如何让 Agent 的每个关键步骤都可验证？|Loop 与 Harness题14]]

## 深入专题：副作用恢复与受保护资源

### 29. 如何防止恢复流程本身再次产生副作用？

答：恢复前核对外部副作用的完整机制见 [[Learning/Agent/09_工程化与系统设计/02_Durable与生产运维#8. 长任务恢复前为什么必须核对外部副作用？|Durable 与生产运维第 8 题]]。安全层只补充：恢复检查阶段必须只读，后续自动动作重走授权、幂等和资源版本边界；Replay 只投影事件或使用 Fixture，不调用真实工具。恢复报告应区分已确认、未发生和仍未知的动作，并明确下一步是否需要人工确认。

### 30. 受保护资源被工具或子进程修改时，为什么仍要让调用失败？

答：OS 沙箱可能无法覆盖所有控制面路径，工具层还需要通过前后快照检测受保护资源变化。即使主要目标完成，控制面被篡改也意味着运行不可信；系统应记录安全失败并阻止把结果报告为成功。
