# 10.3 推理服务与模型行为

本页从推理服务性能讲起，再讨论额外推理预算和工具调用连续性，最后判断应改 Prompt、Schema、Harness 还是训练。

## 推理服务基础

### 1. 量化的收益和风险是什么？

答：把权重或部分激活用更低精度表示，减少显存并可能提升吞吐/并发；代价是精度、工具调用格式、长上下文和特定领域任务可能退化。要用目标 Agent Eval 验证，而不是仅看困惑度或跑通模型。

### 2. SFT、RLHF/RL 和 DPO 分别在训练什么？对 Agent 工具行为有什么影响？

答：SFT 通过高质量示例让模型学习如何根据输入生成回答和工具调用轨迹，影响 Agent 是否能按格式调用工具；RLHF/RL 根据奖励进行策略优化，影响 Agent 的规划和拒绝倾向；DPO 用偏好对优化选择倾向，影响 Agent 在候选动作中的取舍。选择取决于数据、奖励可验证性和稳定性。通用训练定义见 [LLM 基础](../../AI/LLM基础.md)，本题重点看它们对 Agent 行为的影响。

### 3. Agent 的端到端延迟应如何拆解？

答：包括网络/排队、模型 Prefill/首 Token、Decode 生成、检索/工具/数据库等待、重试、审批和人工等待；语音还要加 ASR、端点检测和 TTS。分别记录 TTFT、每 Token、工具等待和任务完成 P95，才能判断瓶颈是否在模型计算。

关联：[[Learning/Agent/09_工程化与系统设计/04_代码Agent与ComputerUse#22. GUI Agent 的成本和延迟应该如何拆解？|代码 Agent 与 Computer Use题22]]

### 4. 为什么减少 Agent 轮次和 Context 往往比先优化推理内核更重要？

答：每轮都会重复输入 Context、产生网络往返和工具等待，重复调用还会放大成本和尾延迟；删除无效步骤、压缩输入、并行独立查询和合理路由通常收益更直接。推理内核优化应建立在真实瓶颈和质量不退化的证据上。

## 额外推理预算与工具调用

### 5. 可见的 Thinking/Reasoning 摘要为什么不能当成原始思维链或审计证据？

答：Provider 返回的摘要可能是选择性、压缩或加密连续性状态，并不等同于模型内部全部计算，也不能证明事实正确或授权合法。审计应依赖输入版本、工具动作、权限决定、工具结果、验证证据和最终状态。

### 6. 自适应推理和固定推理预算的工程差异是什么？

答：自适应方式由模型根据任务决定是否及如何深入，应用通过等级/模式调节总体投入；固定预算给出更明确的目标上限，兼容性和成本控制直观但可能浪费或不足。两者都必须通过 Provider Adapter 隔离，不能把某一家字段当通用协议。

### 7. 开启额外推理预算会增加哪些成本和尾延迟？

答：通常增加输出侧计算/推理 token、首 token 等待、总耗时和长任务 P95/P99，也可能增加工具规划和重复调用。应分别记录推理 token、文本 token、模型/工具成本、TTFT、总时长和成功率。

关联：[[Learning/Agent/10_模型与推理/01_模型与推理基础#8. 如何在模型质量、延迟和成本之间做选择？|模型与推理基础题8]]

### 8. 推理模式下为什么仍然需要 Streaming？

答：额外推理可能让最终文本更晚到达，流式可以保持连接、上报安全的进度状态并改善首响应体验。Streaming 仍不代表任务完成，界面应展示“分析/调用工具”等状态，不应伪装成内部思维逐字输出。

### 9. 工具调用回合中的 thinking 状态或 typed output 为什么必须遵守 Provider 连续性合同？

答：某些协议要求把上一轮模型生成的内容块、签名或 typed items 原样带回，以便服务端验证上下文连续性；删除、重排或自行改写可能导致请求失败或语义断裂。这个规则是 Provider 合同，Adapter 要做兼容测试；执行器仍需独立负责权限、幂等和验证。

### 10. 什么任务值得提高 reasoning/effort，什么任务不值得？

答：多假设诊断、复杂代码分析、算法证明、长链规划和需要整合多次工具结果的任务可能受益；简单分类、字段提取、固定 FAQ 和高吞吐低延迟路径通常不值得。先确认失败原因是推理不足，而不是缺数据、坏工具或错误流程。

### 11. 如何设计额外推理投入的评测实验？

答：固定任务、工具、Context、模型版本和预算环境，对普通/低/中/高投入做多次运行，记录任务成功、关键错误、首 token、总耗时、推理 token、工具调用、成本和分片结果。用质量收益与资源代价制定路由阈值，不以“最高档最好”为前提。

关联：[[Learning/Agent/10_模型与推理/01_模型与推理基础#11. 如何用实验分别验证量化、缓存、批处理和 Prompt 压缩的收益？|模型与推理基础题11]]

### 12. 为什么高推理预算不能弥补坏工具、缺数据或错误权限？

答：模型再多思考也不能凭空获得不存在的证据、修复返回错误的工具或提升被拒绝的权限。应先修 Context、工具合同、数据质量和策略；推理只处理剩余的决策复杂度。

## 模型行为诊断与训练

### 13. Agent 行为由预训练、指令微调、偏好训练和 Harness 如何共同决定？

答：预训练提供语言/代码和世界知识，SFT 教格式与任务示例，偏好或强化训练影响选择、修正和拒绝倾向，Harness 决定工具、Context、权限、反馈和停止条件。线上行为是四者与环境的合成，不能把所有问题都归因于 Prompt 或模型。

### 14. 工具调用训练轨迹应该包含哪些成功和失败样本？

答：包含任务、可用工具、选择与参数、工具结果、成功/失败/超时/权限拒绝、澄清、人工确认、停止原因和程序化成功证据。只收集成功轨迹会让模型学会无条件调用，却不会处理错误、拒绝和不确定性。

### 15. 什么时候先改 Prompt，什么时候改 Tool Schema，什么时候改 Context？

答：协议/格式错误先修消息和 Schema；工具选错先改名称、描述、枚举和工具集合；参数缺字段补 required/服务端校验；信息缺失或噪声大改 Context 选择、检索和状态注入。只有这些层稳定后仍在固定分布中出现模型行为问题，才考虑换模型或训练。

### 16. 结构化输出为什么不能保证工具选择正确或任务完成？

答：结构化输出主要保证可解析的形状，不保证选择了正确工具、参数符合业务语义、没有越权或外部状态真的改变。工具执行器、权限层和程序化验收仍必须独立存在。

### 17. 什么时候值得训练或微调工具调用模型？

答：先判断根因：广泛的推理或工具能力不足，优先评估换模型或按任务路由；模型能力接近目标，但在稳定任务分布上反复出现特定行为问题，且有获授权的高质量成功/失败轨迹时，再考虑微调。Prompt、Schema、Context 和 Workflow 优化仍不足，且 Eval 能证明问题来自模型行为，才进入训练；训练结果要改善工具选择、参数、停止或恢复指标。

### 18. 哪些情况不适合贸然训练？

答：任务还在快速变化、没有可靠标注或程序化验收、失败原因未定位、真正缺的是新工具/新知识、没有安全回归集，或数据授权不清时不适合。训练可能把未解决的系统问题固化成新行为。

### 19. 工具调用训练数据应有哪些安全要求？

答：确认数据用途和授权，脱敏个人信息、密钥、私有代码和危险参数，标注 actor/tenant、工具权限、审批和数据版本，保留拒绝/失败/澄清样本，并隔离训练、验证和攻击集。训练后要做越权、泄露和工具滥用回归。

### 20. SFT、Preference/RL 和程序化奖励各自适合什么监督信号？

答：SFT 适合学习稳定格式、工具选择和停止轨迹；Preference 适合比较规划、解释和安全边界；RL/可验证奖励适合测试通过、Exact Match、状态断言等可程序判断的结果，但要防奖励黑客。优先使用便宜且能定位问题的监督方式。

### 21. 训练后至少要做哪些行为回归？

答：分别检查应调用/不应调用、参数合法率、停止与恢复、越权与危险动作、秘密泄露、成本/轮数及相对基线的任务效果。成功率或拒绝率要结合授权标签和风险切片看：减少误拒绝可以是改善，降低对未授权动作的拦截才是退化。

保留正常、失败、澄清和拒绝样本，避免只用成功轨迹把工具调用训练成无条件执行。

### 22. 为什么 Harness 不能被训练模型替代？

答：训练只能提高在给定观察下的平均决策质量，不能可靠提供权限、预算、幂等、沙箱、审计和外部状态验证。安全边界必须由确定性执行器和策略层强制，即使模型完全不可信也能阻止危险动作。

## 场景追问

### 23. 一个 Agent 经常不调用应该调用的工具，你会如何区分 Schema、Context、模型能力和执行层问题？

答：先用固定任务和 Mock 执行器检查候选工具、名称/Schema 与协议，再确认 Context 是否包含必要目标和证据，以及执行层是否拒绝调用或漏回结果。排除这些问题后，再比较不同模型在同一任务上的选择。只有模型决策缺陷能够稳定复现时，才考虑训练；各层修复方式见 [[#15. 什么时候先改 Prompt，什么时候改 Tool Schema，什么时候改 Context？|题15]]。

### 24. 微调成功轨迹后模型开始“什么都调用工具”，你会如何修复？

答：补入“不该调用工具”、需要澄清、拒绝、工具失败和提前停止等样本，重新定义成功标准，并检查工具描述及训练样本比例。回归集按“该调/不该调、参数、停止”分桶；单纯增加训练步数可能加重无条件调用。

### 25. 一个复杂诊断任务开启高 reasoning 后质量提升但成本翻倍，你会如何制定路由规则？

答：按任务复杂度、风险和历史失败原因分桶，比较不同推理档位的成功率、关键错误、P95、Token、工具调用和费用。只对多步推理确有收益的任务提高预算，其他任务走低档模型或固定 Workflow，并保留超时与安全降级。

### 26. 如果 Provider 升级了消息协议和推理字段，你会如何保证工具回合不丢状态？

答：连续回传哪些内容由 Provider 合同决定，具体规则见题9。升级时为新旧协议分别实现映射并记录版本，再用 Mock 覆盖断流、多工具、取消和恢复。通过后先做影子或小流量灰度，Trace 记录协议和模型版本，便于出问题时回滚到兼容组合。
