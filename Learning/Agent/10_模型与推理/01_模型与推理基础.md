# 10.1 模型与推理基础

本页只保留模型能力如何影响 Agent 的调用、预算、性能和任务成功。Transformer、Attention、Tokenizer、训练算法等通用模型原理以 [LLM 基础](../../AI/LLM基础.md) 和 [AI 面试题库·大模型基础](../../AI/面试题库/01_大模型基础.md) 为主答案。

## 推理机制：生成与性能

### 1. Temperature、Top-K、Top-P 如何影响输出？

答：Temperature 调整分布平滑程度，越高越随机；Top-K 只保留概率最高的 K 个 Token，Top-P 保留累计概率达到阈值的动态集合。Agent 工具调用和结构化输出通常偏低随机性，并用 Schema/验证器兜底。采样参数的原理见 AI 主文档；实际取值要按任务评测。

### 2. Context Window 和 Token Budget 有什么区别？

答：Context Window 是模型一次可接收的输入/历史/输出总容量上限，Token Budget 是某次任务愿意或允许消耗的额度。预算通常小于窗口，并要同时约束输入、输出、工具结果和循环累计成本。

### 3. Prefix Caching、KV Cache 和结果缓存有什么区别？

答：Prefix Cache 复用请求前缀的计算或计费结果，KV Cache 保存生成过程中已计算的注意力状态，结果缓存直接复用完整响应。推理缓存键约束模型、Tokenizer 与精确前缀；应用结果缓存还要绑定主体/权限、资源版本、参数和有效期，并只复用只读结果。缓存命中只代表计算或响应可复用，不代表有副作用动作已经执行。

**追问：为什么 KV Cache 不缓存 Q？**

自回归生成时新 Token 的 Query 只在当前步使用，而历史 Token 的 Key/Value 会在后续每一步重复参与注意力，因此缓存历史 K/V 能避免重复计算。Q 对每个新 Token 都不同且不需要被未来步骤反复读取，所以通常不缓存。

**追问：KV Cache 的收益和代价是什么？**

缓存历史 K/V 可避免每步重复计算，但显存随序列长度、并发、层数和 KV 头数增加。长任务要按真实上下文长度与并发估算容量，并把取消、租户隔离和缓存生命周期纳入服务设计。

### 4. Continuous Batching 解决什么问题？

答：它允许不同请求在生成过程中动态加入/退出批次，提高 GPU 利用率和吞吐，适合长度差异大的在线生成；调度复杂度和尾部延迟控制也随之增加。Agent 场景还要处理取消、优先级、流式和每任务预算。

### 5. vLLM、PagedAttention 和 KV Cache 的关系是什么？

答：KV Cache 保存历史 Token 的注意力键和值，PagedAttention 用类似分页的方式管理不同请求的 KV 内存，vLLM 是基于此的高吞吐推理服务实现。它们优化推理执行和内存管理，不会自动提升 Agent 规划正确率或工具安全。

### 6. LLM 推理优化有哪些常见方法？

答：量化、KV/Prefix Cache、连续批处理、投机解码、注意力 Kernel 优化、上下文压缩、模型路由和输出长度控制都可能有效。先用 Trace 区分排队、Prefill、Decode、网络和工具耗时，再决定优化；降低模型单次延迟不一定能降低 Agent 的任务总时长。FlashAttention 等算法细节回到 AI 主文档。

### 7. 如何估算模型服务的吞吐、并发和显存？

答：先用真实 Trace 得到输入/输出 Token、序列长度、并发和目标 P95。权重显存按模型参数与精度估算；单请求 KV Cache 可粗略按 `2 × 层数 × KV 头数 × 单头维度 × 序列长度 × 每元素字节数` 估算，再乘并发并加上框架开销。MQA/GQA 会减少 KV 头数。头数、维度和精度应从实际模型配置读取；容量还要计入多轮调用、峰值、失败重试和流式连接，不能只用平均长度。

### 8. 如何在模型质量、延迟和成本之间做选择？

答：按任务复杂度和风险分层路由，简单/低风险使用小模型或 Workflow，复杂/关键任务使用更强模型和验证；用任务成功、长尾、安全、P95 和单任务成本综合评估。不要只比较单次 API 价格，Agent 的多轮调用和失败重试才是总成本。

### 9. 如何处理模型上下文窗口溢出？

答：在进入模型前计算 Token 预算，按优先级裁剪重复历史、摘要已完成步骤、检索必要证据和压缩工具结果；必要时拆成子任务或暂停请求用户缩小范围。系统应在溢出前停止并给出原因，不能依赖 Provider 截断掉关键约束。

## 场景追问：模型选择如何服务 Agent

### 10. 一个任务需要复杂工具调用，但成本和延迟都很高，你会换模型、做路由还是增加确定性约束？

答：先用 Trace 拆分模型、工具、排队和 Context 的耗时与 Token，确认瓶颈。工具参数和流程稳定时，用 Workflow/Harness 减少无效循环；任务复杂度差异大时，按复杂度路由。只有输入、证据、工具合同和执行状态都正确，任务仍稳定失败时，才考虑换更强模型。分层定位方法见 [[Learning/Agent/08_评测与可观测/轨迹诊断与线上故障|轨迹诊断与线上故障]]；每项改动都要验证成功率、P95、费用和安全指标。

### 11. 如何用实验分别验证量化、缓存、批处理和 Prompt 压缩的收益？

答：固定任务、模型版本、工具和并发，单变量对照测质量、P95/TTFT、Token、显存、吞吐和费用；量化要看能力退化，缓存要看命中和越权，批处理要看尾部延迟，压缩要看长任务成功率。通过线上灰度确认离线收益可复现。
