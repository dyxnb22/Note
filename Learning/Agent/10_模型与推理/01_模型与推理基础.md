# 10.1 模型生成与推理基础

自回归 Transformer 怎样处理输入、逐步生成输出，会影响调用成本、显存和任务耗时。下面以这种架构为例，其他架构和服务实现可能不同。

## Token 与上下文容量

语言模型处理 Token 序列，一个 Token 不固定对应一个字或词。Context Window 限制单次容量，任务预算限制多轮累计资源：每轮输入要放得下，总费用和时长也不能超额。

输入除用户文字外，还包括指令、历史、工具说明和协议内容。输出也可能占用上下文容量，并消耗任务预算，具体限制需要按所用模型服务核对。应用应为输出留空间，不能只计算问题正文。

## Prefill 与 Decode

Prefill 处理输入，构建后续生成要用的内部状态；Decode 逐步生成输出。用户等到首 Token 的时间，还包括网络和排队，不能全算作 Prefill。

输出更长通常需要更多生成步骤，但端到端时间也受硬件、调度、批处理和工具等待影响。Agent 的多轮总延迟需要把每次调用和等待都算进去。

### 从一次调用推到多轮任务

自回归生成根据已有 Token 预测下一个 Token，再把它接回序列继续预测。Prefill 可以一次处理已知输入；Decode 的后续步骤依赖之前生成的结果。工具调用也属于生成内容，工具结果返回后通常要开始下一次模型请求。

串行运行时，可把一次任务耗时拆成各轮的“排队 + 网络与输入处理 + 输出生成 + 工具等待 + 程序验证”。并行分支看关键路径，不能把所有分支耗时直接相加。首 Token 时间仅覆盖第一段可见输出之前的等待，完整任务时间还包括后续工具和模型轮次。

例如，一次咨询需要三轮模型请求：第二轮带上订单查询结果，第三轮再加入制度材料，因此输入通常会逐轮增长。限制每次 max_tokens 只限制相应请求的生成上限，不能约束所有轮次累计的输入量。测量时至少记录每轮输入/输出用量、开始结束时间和工具耗时；用量缺失要标为未知。

## Temperature、Top-K 与 Top-P

Temperature 调整采样分布的集中程度，Top-K 限制候选 Token 数量，Top-P 限制候选的累计概率。这里的 Top-K 与检索候选 K、RRF 平滑常数 k 是不同参数。服务可能只开放其中一部分，组合方式和默认值也各有约定。

降低随机性通常让输出更稳定，但正确性还要验证。模型版本、服务实现和并行计算也会影响复现，可以用固定模板和程序校验减少差异。

### 温度调节的数学含义

对一组候选 Token 的 logit，温度 T > 0 时可按 softmax(logit / T) 得到概率。为避免直接计算很大的指数，先减去最大值；这不会改变归一化结果。

对 logits=(2, 1, 0)，按 softmax(logit/T) 归一化，可以得到：

| 温度 | 第一项概率 | 第二项概率 | 第三项概率 |
|---|---|---|---|
| T=1 | 约 0.665 | 约 0.245 | 约 0.090 |
| T=0.5 | 约 0.867 | 约 0.117 | 约 0.016 |

这个例子中，温度降低后，最大 logit 对应的 Token 概率更高。

完整采样还包括候选筛选，Top-P 与 Top-K 的应用顺序由服务约定。temperature=0 通常对应服务定义的确定性选择，应另行处理，不能直接代入除法。Token 概率表示生成倾向，事实可靠性需要其他证据判断。

## KV、前缀与结果缓存

KV Cache 保存注意力计算中的键值状态；Prefix Caching 复用可匹配前缀的相关计算；结果缓存直接复用以前的回答或业务结果。前两者主要减少部分计算，结果缓存还受到权限、新鲜度和请求等价性的约束。

命中前缀缓存后，输出仍需生成。共享缓存应隔离身份与数据，命中率取决于服务识别兼容前缀的方式。

## 批处理、量化与资源

Continuous Batching 在生成中动态组织请求，提高设备利用率，也可能改变单次请求的排队与资源竞争。量化通过降低表示精度减少部分显存，能否加速则取决于硬件和内核支持。

模型权重、KV Cache、并发和上下文长度共同影响资源需求。最大并发不能只由参数量推算，要用代表性的输入、输出和调度条件测量。

### 估算 KV Cache 的量级

对每层保留完整历史、K/V 使用相同维度和精度的注意力缓存，可粗略估算：

`字节数 ≈ 2 × 层数 × 并发序列数 × 已缓存 Token 数 × KV 头数 × 每头维度 × 每元素字节数`

系数 2 对应 Key 和 Value。GQA/MQA 会让多个 Query 头共享较少的 KV 头，不能直接拿 Query 头数代入。假设 32 层、单序列 4096 Token、8 个 KV 头、每头 128 维、每元素 2 字节，原始 KV 约为 0.5 GiB；8 个相同长度的序列约为 4 GiB，尚未包含权重、临时计算、内存分块浪费和服务开销。

滑动窗口、前缀共享、压缩、卸载与不同注意力架构会改变占用。该式用于估算量级，实际并发容量按所用缓存策略和目标负载测量。[KV 缓存的张量与增长方式](https://huggingface.co/docs/transformers/cache_explanation)

由估算式可见，上下文长度和并发数各扩大一倍时，原始 KV 约变为四倍。如果工具等待占主导，减小 KV 开销对完整任务耗时的改善可能有限。

## 按任务阶段选择优化方法

一次订单查询可能先由模型选择工具，再等待业务查询，最后由模型组织答案。减少无关历史，主要减少部分输入计算；缩短最终回答，减少输出生成；复用订单查询结果，则可能缩短工具等待。

如果大部分时间在等待物流服务，优先检查工具调用；如果每轮重复输入很长，评估前缀复用。每次改动后用相同任务测量总耗时与资源消耗，确认实际收益。

## 用任务效果决定路由

用相同工具、上下文、完成标准和任务集比较模型的成功率、关键错误、延迟与成本，再决定哪些任务交给轻量模型。文本长短不能直接代表任务难度。比较方法见[评测设计](../08_评测与可观测/评测设计与发布标准.md)。

模型路由和故障回退（Fallback）需要保持所需能力与协议的兼容性。切换模型前确认旧请求状态和工具结果配对，避免把同一业务意图当成新任务再次执行。
