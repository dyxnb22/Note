# 11 端到端 Agent 系统设计

可以先运行[只读订单 Agent 案例](../案例_订单查询Agent.md)，再跟着本章看知识咨询、业务写入、审批和生产交付需要增加哪些处理。

## 以知识咨询服务为例确定目标

先设计一个制度咨询服务：在用户有权查看的文档中寻找依据，返回带来源的回答；没有依据时说明缺口。服务只需读取与解释能力，修改制度或执行交易另设流程。

知识咨询、订单取消和代码修复可以共用相似的运行结构，区别在于事实来源、会产生的变更和验证方式。

## 从订单问题到最终回答

用户问“订单 A 是否能取消”时，业务 API 查询当前状态，制度检索返回适用条件。模型结合两者回答，验证器再对照事实和条款检查结论。

| 阶段 | 主要职责 | 形成的内容 |
|---|---|---|
| 接收目标 | 确定问题与可信身份 | 订单号、任务 ID 与访问范围 |
| 建立状态 | 保存当前任务事实与限制 | 目标、版本、阶段与预算 |
| 提出动作 | 选择需要取得的事实 | 带 ID 的工具提案 |
| 查询订单 | 取得业务事实 | 当前状态、版本与时间 |
| 检索制度 | 取得允许使用的依据 | 条款、适用条件与来源 |
| 验证完成 | 核对目标、状态与证据 | 证据支持的结论，还有哪些问题没查清 |
| 保存结果 | 留下可解释的交付记录 | 最终状态、答案与来源引用 |

历史答案保留当次运行的状态与时间。重新展示时注明它是历史快照，用户查询当前状态时则重新读取业务系统。

## 执行途中复核事实与权限

订单查询时为 pending，答案生成前却已被取消或发货；用户在开始时具有权限，等待期间却离开了项目；制度原文仍能读取，但对应版本已失效。它们分别涉及业务新鲜度、当前授权和规则有效性。

查询结果保存来源、时间、资源版本和状态。只读回答与写操作可以有不同的复核时点；写入的前置条件通常由业务服务在提交时检查，早先查过一次还不够。

恢复任务时，用消息还原交流过程，用业务操作记录核对副作用，再依据可信身份与当前授权限制访问。

## 企业采购取消：从解释制度到确认执行

假设用户请求：“取消采购订单 P-104，并通知项目负责人。”教学业务规则规定：未发货、未进入结算的订单可申请取消，提交前需要指定审批人确认。

任务服务保存目标和可信执行身份。模型可以查找缺失条件、查询制度、解释结果并提出动作；业务规则决定允许怎样改变订单状态，授权服务确认谁能批准，订单系统确认取消是否已发生。

| 阶段 | 取得或形成的内容 | 继续执行的依据 |
|---|---|---|
| 确认目标 | 订单号、取消与通知两个目标、当前身份 | 用户有权处理该订单；指代明确 |
| 查业务状态 | 订单版本 12、未发货、未结算、负责人 ID 或相关记录 | 来自业务 API 的当前事实 |
| 查适用制度 | 与采购类型、组织和日期匹配的制度版本 | 条款明确且有来源 |
| 形成提案 | 取消对象、预期版本、理由与通知范围 | 执行器校验能力和参数 |
| 等待审批 | 审批人、提案摘要、有效期、关联操作 | 可信审批记录覆盖这次动作 |
| 提交取消 | 原业务操作 ID 与条件更新请求 | 当前授权、审批和业务前置条件仍有效 |
| 核实取消 | 操作回执与订单新状态 | 明确确认取消已经完成 |
| 发送通知 | 已确认结果、当前负责人、通知操作记录 | 收件人与内容符合授权范围 |
| 结束任务 | 取消结果与通知结果分别保留 | 两个目标都满足，或清楚说明未完成部分 |

P-104 在等待审批时如果已经发货，版本 12 的提案就不能继续提交。运行时要回查新状态，重新判断还能不能取消、下一步该怎样处理；模型不能为了完成旧目标而忽略业务服务返回的冲突。

等待期间制度也可能失效。原审批只覆盖当时的具体提案，执行时仍按业务约定核验当前制度；范围变了就重新取得所需授权。

## 业务操作、模型调用与通知分别记账

同一取消意图可能经历多次模型回合和网络重试，但应关联到同一业务操作记录。若提交取消后超时，先查询该操作是否已完成。得到明确取消结果后，才把这个事实反馈给模型并开始后续通知。

取消与通知是两个操作：取消成功、通知失败时，不能再次取消，也不应自动恢复订单。任务保留取消回执，仅继续通知或转人工处理。通知重试也需要处理重复发送风险；如果业务服务无法确认是否已发送，应保留未知结果，而不是盲目重发。

一条完整运行记录可以是：任务 T-9，第三轮模型调用 c3 提议取消；运行时关联业务操作 O-7，取得订单取消回执 R-2；通知使用独立操作 N-4。模型重新规划产生 c5 时，O-7 的已确认结果仍然有效，不会因为调用 ID 改变而成为新交易。

向用户说明结果时，按实际记录写，例如“订单已取消，负责人通知尚未确认”。将制度依据、申请受理、审批、取消回执和通知结果分别保存，后续就能查清任务进行到了哪一步。

## 用固定流程约束动态决策

授权、审批、条件写入和结果核对可以放进固定 Workflow。模型处理指代、解释、材料选择和信息缺口，遇到异常再提议补查或澄清，不能自行跳过这些固定步骤。

如果用户只要求解释取消政策，就不创建写操作；只要求起草通知，就不发送；要求执行而缺少订单号，则先澄清。根据目标收窄工具集合，比始终提供全部查询和写入能力更容易控制。

取消结果得到确认、通知达到事先约定的标准，任务才算完成。“进入通知队列”算不算完成，要在执行前定义，不能发送失败后再降低要求。评测覆盖事实、权限、状态变化和用户说明。

## 流式输出与数据保护

流式文本发出后难以撤回。读取数据、选择放进模型的材料时，就要检查权限并处理敏感信息。输出检查还要覆盖相邻片段拼接后的内容，不能只逐段匹配，就认为完整文本安全。

若策略要求完整检查后才能展示，就需要缓冲或分段确认，这会影响实时性。界面应区分模型正在生成的候选文本、已通过检查的内容和最终任务状态。

## 为检索、生成与验证分配预算

检索、生成和验证共享预算。分配时为最后的回答与验证留额度；仍不足以完成时，保留已知事实并说明缺口。

互不依赖的查询可以放在同一轮提出，再由执行器按条件并行处理；依赖前一步结果的查询，需要等待。减少轮次后，先检查任务要求有没有遗漏，再比较用量和耗时。

## 从咨询服务扩展到写操作

只读案例要扩展为真正取消，需要增加写工具、可信授权、当前资源版本和稳定业务操作 ID。业务要求审批时，执行器读取可信审批记录，不能接受模型自报 approved。

接入写工具时，先确定怎样识别同一次操作、失败后从哪里继续、怎样报告结果，再把它接入循环。

## 写清已验证的能力与适用范围

订单取消的事务行为、协程收到取消后的资源清理，是两项不同的测试，结果分别保存。长期稳定性则要在上线后用真实负载观察。

交付说明写明各项检查结果、已测场景和未测条件，具体项目见[Python 生产与交付](../../Python/07_生产与交付.md)。

比较人工与 Agent 的效果时，使用一致的任务范围和完成标准。总投入包括审查、返工、失败处理及运行成本，也包括未完成任务的费用与耗时。

发布记录保存依赖、模型、Prompt、数据、策略和状态结构版本，供后续排查行为变化。
