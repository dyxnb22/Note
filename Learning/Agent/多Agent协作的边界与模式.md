# 多 Agent 协作的边界与模式

多 Agent 不是能力叠加器，而是把一个运行时拆成多个具有独立上下文、工具或权限的执行单元。只有当拆分收益超过通信、重复推理、状态同步和失败恢复成本时，它才比单 Agent 或确定性 Workflow 更合适。

框架实现可参考 [LangGraph](./LangGraph.md) 的 Supervisor 示例；本文只讨论与框架无关的选型、状态、安全和评测边界。

## 1. 先做选型，不先画角色

| 条件 | 更合适的方式 | 原因 |
|---|---|---|
| 步骤固定、状态迁移明确 | [Workflow 与编排](./Workflow与编排.md) | 确定性路径更易测试、恢复和审计 |
| 任务开放但工具与权限相同 | 单 Agent + 明确计划 | 避免重复上下文和协调开销 |
| 子任务相对独立，可并行读取或分析 | Manager–Worker | 并行收益可能覆盖汇总成本 |
| 需要独立质检且错误代价高 | Executor–Reviewer | 让检查与生成使用不同输入和通过标准 |
| 不同子任务必须隔离数据或工具 | 权限隔离的专用 Agent | 降低单个执行单元的权限范围 |
| 多个 Agent 共享写路径或强依赖同一中间状态 | 单 Workflow 或串行执行 | 并行会引入冲突、重复副作用和恢复困难 |

一个实用判定式是：

```text
净收益 = 并行或专门化带来的质量/时间收益
       - 拆解、通信、重复上下文、汇总、冲突和恢复成本
```

无法设计单 Agent 或 Workflow 基线时，也无法证明多 Agent 值得存在。

## 2. 可拆分任务必须满足什么

好的子任务不是“研究一下”“写一下”这类角色描述，而是一个可验证合同：

- 输入：允许读取的上下文、数据版本和依赖产物；
- 输出：结构化 Schema、证据要求和最大长度；
- 权限：工具白名单、资源范围和是否允许写入；
- 预算：步骤、时间、Token、费用和并发上限；
- 终止：完成、失败、需要澄清或交回协调者的条件；
- 验证：谁检查结果，失败后重试、降级还是人工接管。

如果子任务必须持续读取另一个 Agent 尚未稳定的中间状态，说明边界可能切错。优先按可独立验证的产物拆分，而不是按拟人化职位拆分。

## 3. 常见协作模式

| 模式 | 状态流 | 适用场景 | 主要风险 |
|---|---|---|---|
| Manager–Worker | 管理者分派，Worker 返回显式产物 | 多文件只读分析、并行资料整理 | 管理者成为瓶颈，汇总时丢证据 |
| Planner–Executor | Planner 产出计划，Executor 执行并回报 | 长任务、计划和执行权限需分离 | 初始计划过早固化，执行反馈回不去 |
| Executor–Reviewer | 执行者提交结果，Reviewer 按标准验收 | 代码、研究和高风险输出 | Reviewer 复述而不验证，两个模型共享同一偏差 |
| Router–Specialist | Router 按意图选择专用 Agent | 多领域入口、不同工具集合 | 错路由、分类不确定性被隐藏 |
| Candidate–Judge | 多个候选独立生成，再选择或合并 | 高价值且可客观比较的答案 | 成本成倍增长，Judge 偏差决定结果 |

Swarm 或自由对话式协作缺少清晰所有权和终止条件，通常只适合实验，不应作为默认生产结构。

## 4. 状态与通信

默认传递压缩后的显式产物，不共享无限对话历史。协调者维护唯一的任务状态和依赖关系；Worker 只返回约定输出，不私自修改全局计划。

```text
任务状态：pending → running → succeeded / failed / cancelled
产物状态：draft → validated → accepted / rejected
```

两种状态不能混为一谈：Agent 调用成功不代表产物通过验收。消息还可能重复、延迟和乱序，因此每次分派需要 `task_id`、`attempt`、输入版本和幂等键；过期尝试的结果不能覆盖较新的已验收产物。

共享写操作应满足至少一种条件：

- 由单一协调者串行提交；
- 每个 Worker 写入互斥资源，最后通过受控合并；
- 数据库使用事务、条件更新和唯一业务键；
- 文件修改保留基线版本，冲突时停止并重新读取，而不是静默覆盖。

## 5. 可靠性与安全

子 Agent 不继承父 Agent 的全部权限。权限应绑定到当前任务、资源和动作；网络、文件写入、命令执行和外部副作用分别授权。具体威胁与防线见 [Agent 安全与威胁建模](./07_Agent安全与威胁建模.md)和[安全与可控性](./08_安全与可控性.md)。

协调者至少处理：

- 超时、取消和失联 Worker；
- 重复分派和迟到结果；
- 部分成功与汇总失败；
- 递归派生导致的并发和费用失控；
- 多个 Agent 对同一资源的冲突写；
- Worker 输出不符合 Schema、缺少证据或越权请求。

每层派生都必须减少可用预算或受到全局并发上限约束。取消父任务时，应传播取消信号并回收仍在运行的工具、进程和租约。

## 6. 如何证明多 Agent 有价值

使用相同任务集、工具、数据和通过标准，至少比较三组：

1. 单 Agent；
2. 单 Agent + 确定性 Workflow；
3. 多 Agent 方案。

记录端到端任务成功率、关键错误率、人工接管率、P50/P95 延迟、Token/费用、工具调用数和副作用正确性。并行方案还要记录排队时间、汇总失败和冲突率。

做一次消融：移除 Reviewer、减少一个 Worker，或把并行改成串行。如果质量没有显著下降，说明该协作层可能只是增加复杂度。评测设计与回归门槛见 [Agent Eval 实验方法](./09_Agent%20Eval实验方法.md)和 [Eval 与测试体系](./10_Eval与测试体系.md)。

## 7. 常见失败模式

- 用多个角色重复读取同一上下文，只得到措辞不同的相似答案；
- Manager 分派任务后没有输出 Schema，最后只能重新做一遍；
- Reviewer 只评价“看起来不错”，不运行测试或核对证据；
- Worker 可以继续无限派生子 Agent，预算和失败面指数增长；
- 多个 Agent 同时写同一文件或外部系统，没有版本与幂等控制；
- 只比较单次演示效果，没有与简单基线比较成本和失败率。

## 8. 最小实践

选择一个可分成三份只读分析的任务：先用单 Agent 完成，再实现 Manager–Worker。每个 Worker 只接收必要上下文并返回固定 JSON；Manager 检查 Schema、去重证据并汇总。随后注入一个 Worker 超时、一个重复结果和一个错误证据，验证系统能降级完成且不会把未验证产物标为成功。

最终结论应回答：多 Agent 改善了哪个指标，增加了多少成本，在哪类任务上应退回单 Agent 或 Workflow。
