# 06.2 知识摄取、检索与 GraphRAG

本页从文档生命周期和权限开始，接着讲 PDF/OCR/表格解析与检索，最后评估是否需要 GraphRAG。

## 知识系统基本模型

### 1. 一个生产知识系统的对象生命周期可以如何表示？

答：可抽象为 `Source → Document → DocumentVersion → Chunk → IndexRecord → Citation`。Source、版本、所有者、权限和删除状态是事实；Chunk/倒排/向量/图索引是可重建的派生产物，引用要能回到原始版本和位置。

### 2. 为什么 Source、DocumentVersion 和权限是事实，而向量索引是可重建产物？

答：索引会随模型、分块或存储升级重建，不能作为唯一真相；原文版本和授权才决定内容及可见范围。这个事实与派生数据边界见题1，它是安全更新、删除和重建索引的前提。

### 3. 文档摄取的标准流水线应有哪些阶段？

答：发现变化、抓取并校验安全、解析与标准化、质量检查、生成不可变版本、切分和写元数据、建立索引、验证后原子发布。每一步要幂等、可重试、可观测，失败不能让旧索引和新索引半混合。

---

**追问：文档解析、清洗、切分、Embedding、索引、召回、Rerank、生成如何串联？**

先保留结构和来源做规范化，再按语义/结构切块并附文档、页码、权限、版本元数据；生成倒排和向量索引，查询时混合召回、Rerank，最后按预算组装证据并生成。每一步都要记录版本，便于解释和回滚。

---

**追问：标题、脚注、页码、表格与引用关系如何处理？**

在解析阶段保存文档树、表格结构、页码/坐标、父子节点和原始片段 ID，切块时继承这些元数据。生成引用时从元数据反查原文位置，避免只返回没有出处的向量片段。

---

**追问：如何处理 PDF、扫描件、OCR、表格、图片和复杂版式？**

| 阶段 | 说明 |
|------|------|
| 按文件类型选择解析器/OCR | 不同格式用不同工具 |
| 保留页码、坐标、标题层级、表格结构、来源、版本和置信度 | 结构化元数据 |
| 扫描件用 OCR 并记录置信度 | 质量可追溯 |
| 表格转成结构化数据加可读摘要 | 保留表格语义 |
| 图片必要时走视觉模型 | 多模态处理 |

质量门禁：解析结果先做质量检查，再切分、Embedding 和索引。低置信度 OCR、表格关系丢失、重复页和乱码要进入人工或重试队列。答案引用必须能回到原文位置。

### 4. 文档元数据至少应该包含什么？

答：来源 URI、文档/版本 ID、所有者、作者、时间、有效期、权威等级、内容 hash、解析器版本、语言/类型、租户、数据分类、允许用途和权限范围。元数据既服务检索过滤，也服务引用、审计和删除。

### 5. 引用如何回指到具体版本、页码和区域？

答：Chunk 和引用记录保存 document_version_id、页面/段落/表格/区域坐标、原文 hash 和必要的行列信息；回答中的 citation ID 映射到这些记录。这样可以复核证据、处理版本变化和向用户展示准确位置。

关联：[[Learning/Agent/06_RAG与知识库/RAG与检索#19. 如何把检索结果、引用和最终回答建立可追溯关系？|RAG 与检索题19]]

### 6. 知识系统如何处理更新、删除、重命名和权限变化？

答：用内容 hash 和不可变版本检测变化，更新生成新版本并原子切换，删除要标记真相并从倒排、向量、图、缓存和派生摘要中清理；重命名更新引用映射，权限变化立即影响查询过滤。旧版本是否保留由保留策略决定，但不能继续被默认召回。

## 文档解析与质量

### 7. 为什么摄取前要先分类 PDF、扫描件、Office 和表格？

答：数字 PDF、扫描 PDF、混合 PDF、Office 和表格需要不同的解析策略；分类错误可能比模型或向量检索小幅误差更严重，例如把图片当空文本或把表格顺序打散。分类结果还应保留置信度和人工复核入口。

### 8. PDF 解析中的阅读顺序问题有哪些？

答：多栏、页眉页脚、脚注、旋转文字、水印和字体编码都可能让文本顺序错乱。解析时应恢复标题层级和阅读顺序，同时保留页码、边界框和原始区域，不能只输出一段无定位纯文本。

### 9. OCR 质量应该如何评估？为什么不能只给一个总体准确率？

答：至少按字符/行/块或文档质量桶记录置信度、空文本、乱码、数字/专名错误和需要人工复核的比例。总体平均值会掩盖关键表格或金额区域的低质量，应对低置信片段降权、标记或转人工。

关联：[[Learning/Agent/06_RAG与知识库/RAG与检索#4. OCR 准确率和端到端问答准确率如何评估？|RAG 与检索题4]]

### 10. Word、PPT 和 Excel 的解析重点分别是什么？

答：Word 要保留标题、段落、表格、批注和隐藏文本语义；PPT 要区分幻灯片正文、备注、图形和顺序；Excel 要识别工作表、表头、关键列、合并单元格和公式/值。解析结果应能回指原文件和位置。

### 11. 表格为什么不能简单按纯文本切成普通 chunk？

答：合并单元格、重复表头、跨页、无边框和行列关系会在纯文本中丢失；用户问题可能依赖列名、单位和整行条件。应保留结构、表头和行级定位，数值密集查询必要时直接走 SQL/API，检索只负责发现证据。

### 12. 为什么要在切分前先标准化文档？

答：先统一编码、标题层级、语言/类型、租户/分类、解析质量、表格指针和版本信息，后续切分才能沿语义与结构边界进行。直接对脏文本切块会把乱码、页眉和跨表关系固化进索引。

### 13. 文档摄取应设置哪些质量门禁？

答：检查是否为空/乱码、OCR 置信度、标题/表格结构、页码可定位性、敏感数据分类、提示注入、重复、版本和权限元数据完整性。任一关键门禁失败应隔离或人工复核，不应悄悄发布到线上索引。

### 14. 如何设计解析失败隔离、重试和可观测性？

答：每个文档/版本有独立任务和错误码，暂时性依赖错误限次重试，解析器确定性错误进入隔离队列；保留输入 hash、解析器版本、失败阶段和质量指标。单份坏文件不能阻塞整批摄取，也不能用重试掩盖格式不支持。

## 检索系统工程

### 15. 一个检索服务合同至少要定义哪些能力和指标？

答：应定义 Chunk/版本 ID、可搜索字段、权限过滤、更新/删除语义、无结果/冲突/过时处理，以及延迟、吞吐和召回目标。合同还要说明返回分数、来源和引用位置，供上层 Context Builder 和验证器使用。

### 16. 检索服务为什么要保留 BM25、向量和融合排序的分阶段证据？

答：只保留最终候选无法判断问题来自词面召回、语义召回、融合权重还是 Reranker。每阶段应记录候选 ID、来源、原始/归一化得分、过滤原因和版本，再按查询类型比较召回、排序、延迟与权限结果。三种检索的适用场景和融合方式统一见 [[Learning/Agent/06_RAG与知识库/RAG与检索|RAG 与检索]]。

### 17. Embedding 版本和 ANN 索引选型会影响什么？

答：Embedding 模型变化会改变向量空间，旧新向量不能无条件混用；ANN 结构在召回、内存、延迟、过滤和更新能力上有取舍。选型需结合数据规模、隐私、资源、更新频率和可运维性，而不是只记产品名称。

### 18. Chunk、metadata 和权限过滤应该放在哪个阶段？

答：Chunk 在文档解析和标准化后生成，并绑定 metadata、tenant/resource Scope 与文档版本。查询时先按 actor/tenant/resource/action 在倒排、向量和图检索中强制过滤，再在 Context 组装和输出前复核。

若等到生成后才过滤，未授权片段可能已经进入重排、Context 或 Trace，既会挤占 TopK，也会造成信息泄露。在线过滤与缓存键细节见 [[Learning/Agent/06_RAG与知识库/RAG与检索#15. 如何做分租户、分用户、分文档的权限过滤？|RAG 与检索题15]]；图扩展时的节点/边过滤见本专题题25。

### 19. 检索系统如何实现增量更新、幂等、删除和 Embedding 升级？

答：以 source/version/content hash 作为幂等依据，更新时原子替换新版本并删除旧 Chunk，删除任务要覆盖所有派生索引和缓存；Embedding 升级可双写/双索引、离线重建后切换，并准备回滚和部分失败修复。在线查询固定并记录所用索引版本，避免混读不同代索引，也便于定位热切换后的质量回退。

### 20. 如何评估检索质量、权限安全和时效性？

答：离线看 Recall@K、Precision、MRR/NDCG、零结果和引用覆盖，专项看权限泄露必须为零、过时命中和冲突处理；线上观察点击、引用采纳、纠正、人工抽检和尾部分桶。检索分数高不代表最终回答正确。

关联：[[Learning/Agent/06_RAG与知识库/RAG与检索#17. 如何评估 Recall、Precision、MRR、NDCG 和上下文利用率？|RAG 与检索题17]]

### 21. 如何估算向量索引的容量、延迟和成本？

答：先估算文档量、Chunk 数、向量维度、数据类型和副本，再加索引结构、metadata、缓存和增长率；用代表性过滤条件测召回、P95/P99、更新和重建时间。实际工作负载下比较成本/质量，不能只按理论 QPS。

## GraphRAG 与关系检索

### 22. GraphRAG 解决什么类型的问题？为什么不应该默认使用？

答：它适合实体消歧、多跳关系、路径约束和跨大量文档的全局主题总结；普通事实问答通常用权限感知的混合检索更简单。图会引入抽取错误、实体合并、更新、权限扩展、延迟和成本，必须先证明基线不足。

### 23. 一个可追溯的知识图谱对象模型应如何设计？

答：可用 `DocumentVersion → Entity → Relation → Community`，Relation 至少保存证据片段、来源版本、置信度、时间和有效性，Entity 要有规范化 ID 与别名映射，Community 摘要要能回链原文。图边不能脱离证据成为无来源事实。

### 24. Graph-first、retrieve-first 和 community summary 有什么差异？

答：Graph-first 先找实体和关系再回到文档，适合明确的多跳路径；retrieve-first 先召回文本再在局部建图/扩展，降低全图搜索成本；community summary 适合全局主题和群落级问题，但必须能回链具体证据。

### 25. 图扩展为什么也必须做权限过滤？

答：用户可能从一个有权实体沿关系扩展到无权文档、实体或社区摘要；图结构本身也可能泄露资源存在性。应在实体/边/文档版本层按当前 actor、tenant 和 action 过滤，再执行扩展和聚合。

### 26. GraphRAG 的实体合并、关系抽取和时效性有哪些风险？

答：实体过度合并会把不同主体事实混在一起，合并不足会丢失关系；模型可能抽取不存在或过时的边，来源变化后图也可能滞后。需保留证据、置信度、版本和有效期，支持增量更新、冲突标记与删除。

### 27. 如何评估 GraphRAG 是否值得相对普通混合检索增加复杂度？

答：在相同任务集和权限环境下与混合检索基线比较，按多跳成功率、实体消歧、证据链完整性、泄露率、延迟、Token、索引更新和运维成本评估。只有关键任务稳定获益且安全门槛不退化时，才引入 GraphRAG。

## 场景追问

### 28. 设计一个支持权限、版本、表格和引用的企业知识库，如何保证索引不会出现半新半旧？

答：为避免索引版本混杂，应以不可变的 DocumentVersion 为单位完成解析、质量检查和索引，并让所有派生记录携带版本 ID。新版本通过全部门禁后，再原子切换可见版本；旧版本可延迟清理，但不能继续默认召回。查询时按权限和有效版本过滤，引用回指到具体页码或表格区域。

### 29. 一个扫描 PDF 的问答系统回答错了，你会先检查 OCR、切分、召回、重排还是生成？

答：排查时先查看 Trace 和引用，确认原文是否被正确解析，重点检查空文本、乱码、数字/表格 OCR 和阅读顺序。解析没问题，再检查切块、权限过滤、召回和重排；证据已正确进入 Context 但答案仍错时，才查生成和答案验证。定位到流水线中第一个事实丢失点后再修复，不先归咎模型。

### 30. 企业问题需要跨文档、多跳关系推理，你会如何证明 GraphRAG 比混合检索更适合？

答：先为目标业务准备覆盖实体消歧、多跳、事实冲突和权限边界的测试集，再与混合检索基线对比。评价指标和是否引入的门槛见题27；还要确认收益确实来自关系推理，并检查错误边、泄露风险和维护成本。

### 31. 用户被撤权后，如何保证旧向量、缓存、Trace 和图关系不会继续泄露内容？

答：撤权后，授权服务应立即阻止查询和图扩展，并撤销或隔离对应资源的索引。缓存键需绑定 actor、tenant 和权限版本，并及时失效。删除任务还要覆盖向量、倒排、图索引、派生摘要、Trace、回放和备份；依法保留的数据也必须脱敏并限制访问。
