# 推理服务速答（面试 60 秒）

Agent 岗常夹带推理八股。机制细节以 [LLM 基础](../AI/LLM基础.md) 为准；本页只给**可直接口述**的短答，并指向 Agent 侧成本/延迟文档。

## KV Cache

生成第 \(t\) 个 token 时，前 \(t-1\) 个 token 的 K/V 不变。缓存后每步只算新 token 的 K/V，显著降延迟。代价是显存随序列长度涨；长 context 的瓶颈常在 KV 而不在权重。

## Continuous Batching

推理实例不等「整批结束」才组下一批，而是迭代级插入新请求、退出已完成请求，提高 GPU 利用率与吞吐。和「静态 batch 等最慢样本」相对。

## 量化

权重量化到 INT8/INT4 等，减显存、提吞吐。INT8 精度损失通常较小；INT4 更省但要测任务指标。量化不替代错误的 Prompt/检索。

## 推理框架（如 vLLM / TensorRT-LLM）

PagedAttention、连续批处理、高效调度等工程优化，把「能跑」变成「高 QPS」。Agent 服务常把 LLM 当下游：超时、限流、隔离池与降级仍要在 Agent 侧做。

## Speculative Decoding（加分）

小模型草拟、大模型验证，降低有效延迟；依赖草稿质量与实现，不是默认银弹。

## 最小性能账本（注释版）

不要只报模型 tokens/s；Agent 的有效延迟还包括检索、工具、排队、网络和多轮次数。

```python
def end_to_end_budget(*, rounds, model_ms, tool_ms, retrieval_ms, queue_ms):
    # rounds 代表模型/工具循环次数；多一轮通常同时放大延迟和成本。
    total = rounds * (model_ms + tool_ms + retrieval_ms) + queue_ms
    return {"latency_ms": total, "rounds": rounds}
```

性能记录应按版本、硬件、上下文长度、并发、缓存命中和任务类型分桶；没有这些维度的平均 tokens/s 不能直接指导 Agent 架构决策。

## 和 Agent 的关系

- Agent 延迟 ≈ ASR/检索/工具 + **模型首 token 与整段生成** + 网络。
- 优化顺序：少轮次与小上下文 → 路由小模型 → 缓存 → 再抠推理引擎。
- 详见 [成本与性能工程](成本与性能工程.md)。

## SFT / RLHF / DPO（常连带问）

- **SFT**：模仿标注回答与工具轨迹。
- **RLHF**：奖励模型 + 强化学习对齐偏好，贵、难稳。
- **DPO**：用 chosen/rejected 对直接优化，少显式 RM。
- Agent 行为问题优先查 Schema/Harness；训练见 [模型行为与工具调用训练](模型行为与工具调用训练.md) 与 [LLM 基础](../AI/LLM基础.md)。
