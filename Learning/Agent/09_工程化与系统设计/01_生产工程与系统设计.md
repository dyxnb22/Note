# 09.1 Agent 生产工程与系统设计

本页提供平台服务、容量与系统设计总览。长任务、幂等、租约、发布和恢复统一深入 [Durable](./02_Durable与生产运维.md)；应用设计按需进入 [代码 Agent](./04_代码Agent与ComputerUse.md) 或 [实时交互](./05_实时交互与产品.md)。

## 基础认知：服务边界和请求形态

### 1. 如何设计 Agent Gateway？

答：Gateway 负责身份、租户、请求校验、任务创建、模型/工具路由、限流配额、流式协议和 Trace 入口，不直接承担所有业务逻辑。它应把同步短任务和异步长任务统一成可追踪的 task/trace，并将权限和预算传递到下游。

### 2. 同步调用、异步任务、轮询、WebSocket 和 SSE 如何选择？

答：短且确定的请求用同步；长任务用异步任务 + 状态查询；需要服务端持续推送可用 SSE，双向交互/协商多时用 WebSocket，轮询最简单但延迟和请求量较高。选择还要考虑断线重连、取消、鉴权、代理兼容和状态一致性。

### 3. 如何把 Agent 中间过程实时推送到前端？

答：把模型、工具、审批、状态和进度统一成版本化事件，服务端以 task/trace ID 推送安全摘要，前端按序号去重和恢复。用户可见事件与内部调试 Trace 分开，断线后从游标/状态补发，而不是重新执行工具。

### 4. FastAPI 的 SSE 如何与 LangGraph 联动，把节点结果实时推给前端？

答：把图运行产生的节点开始/结束、消息、工具和状态事件转换为 SSE `event/id/data`，通过异步生成器发送；客户端用 `Last-Event-ID` 或任务状态恢复，服务端处理断开取消和心跳。节点事件不能直接等同于成功，最终仍需业务验证和持久化。具体 LangGraph 事件字段与 API 以项目锁定版本为准。

### 5. 如何实现任务的取消、暂停、恢复、重试和幂等？

答：取消/暂停/恢复/重试/幂等的完整状态机、幂等键设计与未知结果对账，见 [[Learning/Agent/09_工程化与系统设计/02_Durable与生产运维|Durable 与生产运维]] 题 1/2/4/10。本题差异点在平台 API 层如何暴露这些控制入口：把控制动作做成带权限校验的任务状态 API，写入持久化标记后由 Worker 在安全点生效，并向调用方返回当前状态与幂等结果。

## 性能机制：并发、限流与成本

### 6. 如何做限流、配额、优先级和成本预算？

答：入口按用户/租户/全局限制请求，内部按模型、工具、Embedding、队列和并发进一步限制；任务记录 Token、费用、步数和时间预算，调度按优先级和剩余预算处理。分级服务要给普通流量保留最低份额，并根据等待时长逐步提升长期排队任务的优先级（aging），避免高优先级持续到达造成饥饿。按优先级监控 P95/P99 等待时间、超时率、成功率和队列深度。限流响应要说明重试时间或降级路径，不能只返回 429。

来源：[百度 AI Agent 开发岗面经-04](https://www.nowcoder.com/discuss/931706522621530112)。

关联：[[Learning/Agent/09_工程化与系统设计/02_Durable与生产运维#18. 预算、限流和背压应该在哪些层同时控制？|Durable 与生产运维题18]]

### 7. 令牌桶、漏桶、固定窗口和滑动窗口如何选择？

答：

| 算法 | 特点 | 适用场景 |
|------|------|----------|
| 令牌桶 | 允许一定突发，控制平均速率 | 限制平均调用 |
| 漏桶 | 输出平滑，但可能增加排队 | 平滑下游负载 |
| 固定窗口 | 简单，但边界突发明显 | 简单限流 |
| 滑动窗口 | 更精确，但存储/计算开销高 | 严格统计 |

选择取决于是否允许突发、下游是否需要平滑和实现成本。模型/工具调用常用**多层组合**而不是只选一种。需结合分布式一致性和成本。

### 8. 如何控制 Agent 平台总并发和内部 fan-out？

答：

**多层并发控制：**

| 层级 | 措施 |
|------|------|
| 入口层 | 按租户和优先级配额 |
| 任务层 | 限制同时运行数、fan-out 深度和总预算 |
| Agent/工具层 | 分别设置 Bulkhead、信号量与有界队列 |
| 租户层 | 按租户配置并发上限，并结合下游限流、平均 Token、P95 延迟和失败率进行压测 |

过载时拒绝、延后或降级。调度时优先级和预算要可观测。监控队列等待、P95、下游错误和 Token 放大，容量由压测决定。

关联：[[Learning/Agent/09_工程化与系统设计/02_Durable与生产运维#25. 如何防止成本、延迟和 stuck loop 在内部 fan-out 下失控？|Durable 与生产运维题25]]

### 9. 如何处理高并发下的请求排队和背压？

答：长任务进入有界队列并按优先级派发；队列满时拒绝、延后或降级，并把背压传给下游，同时向用户返回可查询状态。fan-out 后的多层并发配额见题8；本题重点监控队列等待、调用放大和 P95。

### 10. 如何估算 Token、GPU、内存、网络和数据库容量？

答：先用真实 Trace 得到每任务输入/输出 Token、调用次数、并发、工具结果大小和峰值分位数，再按 QPS、SLO、批处理和冗余计算容量；模型服务看显存/吞吐，状态/Trace 看存储增长和保留期。容量估算必须包含重试、fan-out 和长尾。

### 11. 如何降低延迟？网络、排队、模型、工具、数据库和序列化分别怎么优化？

答：先分段打点找瓶颈：连接复用/地域优化网络，限并发和扩容解决排队，模型路由/缓存/批处理解决推理，工具并行/缓存/超时解决外部等待，索引和字段选择解决数据库，减少大对象和重复序列化。不能只换更快模型而忽略工具等待。

### 12. 缓存在 Agent 系统中有哪些特有风险？如何避免脏数据和越权读取？

答：缓存键必须绑定租户、用户/权限 Scope、资源版本、模型/Prompt/索引版本和请求参数摘要；敏感结果默认不跨用户共享。更新/删除事件主动失效，读取前仍做权限检查。缓存命中要写 Trace，便于发现错误复用。三类缓存（Prefix Cache、KV Cache、结果缓存）的原理和适用场景见 [[Learning/Agent/10_模型与推理/01_模型与推理基础|模型与推理基础]]。

## 可靠工程：消息、存储与高可用

### 13. Kafka、Redis、数据库、对象存储和 OLAP 在 Agent 系统里分别适合放什么？

答：Kafka 适合事件/任务流和可回放消息，Redis 适合短期缓存、限流和低延迟状态，数据库保存任务/业务一致性状态，对象存储保存大文档、代码和 Trace 附件，OLAP 做行为/成本/质量分析。不要把 Redis 当唯一持久化事实，也不要把模型上下文全塞 OLAP。

### 14. Kafka 如何处理消息重复？如何保证消息不丢失？

答：通过生产者确认、持久化、副本、消费者提交策略和重试/DLQ 降低丢失；同一分区按 offset 有序，但跨分区不保证全局顺序。至少一次投递会带来重复，消费端必须幂等。Exactly-once 只覆盖特定 Kafka 处理链路，外部数据库/API 副作用仍需业务幂等、事务边界和对账。

### 15. 如何设计消息去重、幂等和重放机制？

答：消息带事件 ID、任务 ID、版本和业务幂等键，消费者在提交副作用前检查持久化去重表/唯一约束；事件本身不可变，重放使用版本/时间范围和安全 Fixture。去重记录要和业务状态有一致性边界，否则可能出现“去重成功但动作没提交”。

如果任务状态存于 MySQL，可用唯一约束或条件更新保护任务领取与状态迁移，在短事务中一起写状态和 Outbox；远程工具调用放在事务外，避免持锁等待模型或下游服务。死锁、租约过期和外部结果未知仍需单独处理，不能把数据库事务当成跨服务事务。

关联：[[Learning/Agent/09_工程化与系统设计/02_Durable与生产运维#4. 幂等键应该由哪些信息组成？|Durable 与生产运维题4]]

### 16. 如何设计 Trace、Event Log 和 replay？

答：事件包含稳定 ID、父子关系、时间、版本、状态、错误、工具/模型摘要和租户 Scope；原始敏感 payload 单独受控。Replay 如何固定模型/工具响应、验证状态转移而不重复真实副作用，统一见 [[Learning/Agent/09_工程化与系统设计/02_Durable与生产运维|Durable 与生产运维]] 题 32，Trace/Event 设计只需保证事件完整可回放、不耦合真实执行。

### 17. 多租户 Agent 平台如何安全提供跨租户聚合指标？

答：原始明细、查询结果和 Trace 保持租户内访问；跨租户统计只通过显式授权的聚合接口输出脱敏指标，并限制小样本反推个体或租户数据。存储与执行层的租户 Scope 见 [[Learning/Agent/07_可靠性与安全/身份治理与跨Agent#6. 多租户隔离为什么要覆盖数据库、向量库、缓存、工作区、队列和 Trace？|身份治理与跨 Agent 题6]]。

### 18. 如何做跨区域部署和故障转移？

答：无状态入口可多区域，任务/State 需要明确主从、分片、复制延迟和租约归属；故障转移前确认 Checkpoint、幂等和外部副作用，避免双 Worker 执行。模型/工具提供商也要有区域/供应商 Fallback，跨区域会增加一致性和隐私成本。

关联：[[Learning/Agent/09_工程化与系统设计/02_Durable与生产运维#26. 如何设计一个能跨进程、跨机器、跨版本恢复的 Agent 任务系统？|Durable 与生产运维题26]]

### 19. 如何处理模型或工具供应商故障？

答：适配器统一错误并设置超时/熔断/重试，按任务合同切换兼容供应商或降级为只读/固定流程；未完成长任务保留 State，未知副作用先对账。故障策略要在压测和演练中验证，不是线上临时写 Prompt。

关联：[[Learning/Agent/10_模型与推理/02_Provider适配与框架选型#29. Provider 错误为什么需要稳定分类？|Provider 适配与框架选型题29]]

### 20. 如何设计系统的容量评估、压测和故障演练？

答：用真实任务分布和最坏 fan-out 生成负载，测模型、工具、队列、数据库、Trace 的吞吐、P95/P99、成本和错误；注入超时、限流、Worker 崩溃、网络断开、重复投递和供应商故障。验收包括恢复时间、任务丢失率、重复副作用和用户可见状态。

## 系统设计：从需求到上线

### 21. 设计一个企业级文档问答 Agent。

答：文档解析、权限过滤、召回、引用和更新的主链路见 [[Learning/Agent/06_RAG与知识库/RAG与检索#21. 设计一个支持扫描 PDF、表格、权限和增量更新的企业知识 Agent。|RAG 专题题21]]。本题聚焦平台运行：在线问答与异步摄取分开调度，更新任务携带文档版本，并通过队列和 Checkpoint 管理运行与恢复；只将验证通过的索引版本切为可服务状态。Trace 关联租户、文档版本、证据、回答/拒答和任务状态，权限仍在检索和输出边界校验。

### 22. 设计一个可以执行 Python 或 SQL 的数据分析 Agent。

答：模型只提出分析计划/代码，执行器在沙箱和只读数据连接中运行，限制资源、网络和结果大小；输出经过语法、数据行数、类型和关键业务规则校验，再生成解释。代码、输出、数据版本和验证结果写入 Trace，失败时可重试或请求澄清。

### 23. 设计一个代码 Agent，能够查看仓库、编辑文件、运行测试并根据失败结果修复。

答：把一次修改建模成有状态任务：Gateway 校验仓库范围与权限，Worker 在隔离 workspace 和受限沙箱中执行，diff 与验证证据回传后由验收层决定是否完成；任务还要支持取消、超时和环境清理。仓库上下文、补丁冲突与失败恢复的细节见 [[Learning/Agent/09_工程化与系统设计/04_代码Agent与ComputerUse|代码 Agent 与 Computer Use]]。

### 24. 设计一个支持人工审批的客服 Agent。

答：身份和订单权限先确定；Workflow 固定订单状态、退款规则和验收条件，Agent 处理意图歧义、必要澄清与只读知识选择。退款/改地址等副作用生成结构化预览并进入审批状态；审批后重新校验订单版本并用幂等键执行，结果回写并通知用户。超时、拒绝、断线和未知结果都要有恢复和人工处理路径。

关联：[[Learning/Agent/07_可靠性与安全/身份治理与跨Agent#9. 人工审批合同至少要展示什么？|身份治理与跨 Agent题9]]

### 25. 设计一个多租户 Agent 平台，支持配额、隔离、观测和回放。

答：按层划分职责：

- **Gateway**：从认证身份生成不可由 Agent 改写的 tenant Scope，并写入任务。
- **Orchestrator**：按 Scope 调度；Trace 关联租户、版本和操作证据；Replay 只投影历史，不执行工具。
- **Worker 和存储层**：运行时隔离见 [[Learning/Agent/09_工程化与系统设计/02_Durable与生产运维#11. 如何设计多租户任务的并发、资源和状态隔离？|Durable 题11]]；数据层隔离见 [[Learning/Agent/07_可靠性与安全/身份治理与跨Agent#6. 多租户隔离为什么要覆盖数据库、向量库、缓存、工作区、队列和 Trace？|身份治理与跨 Agent题6]]。

## 发布、降级与运行控制

### 26. 生产发布、灰度、预算、降级和事故响应如何连成闭环？

答：组合版本发布、灰度回滚、降级档位与事故响应的完整闭环见 [[Learning/Agent/09_工程化与系统设计/02_Durable与生产运维|Durable 与生产运维]]。系统设计还应将组合版本管理纳入平台统一发布流程，并在 Gateway、工具执行层等控制点部署 Kill Switch，确保撤权能在全链路及时生效，同时保留审计证据。
