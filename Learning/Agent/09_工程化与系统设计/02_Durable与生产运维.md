# 09.2 Durable Execution 与生产运维

本页从长任务状态、幂等和恢复讲起，再覆盖发布运行、预算降级与事故处置。

## 长任务可靠性基础

### 1. Agent 长任务为什么需要显式任务状态机？

答：长任务会跨请求、进程、Worker 和人工等待，不能靠内存中的一个循环变量表示进度。状态机把当前阶段、允许转移、失败语义和恢复入口固定下来，便于重试、审计、指标和人工接管。

### 2. `pending`、`running`、`waiting_approval`、`succeeded`、`failed`、`cancelled` 和 `expired` 应如何区分？

答：`pending` 尚未领取，`running` 正在执行，`waiting_approval` 等待人或策略决定；`succeeded` 有成功证据，`failed` 是不可继续或超过策略的失败，`cancelled` 是主动取消，`expired` 是超过有效期。状态转移要记录事件、操作者、版本和原因。

### 3. Agent 系统为什么通常只能以至少一次执行为现实基线？

答：网络重试、Worker 崩溃和消息重复投递都可能让同一动作被再次尝试；跨模型、队列和外部 API 很难提供端到端 exactly-once。工程上应把“至少一次调度 + 业务幂等/对账”作为基线，而不是假设消息系统能替所有副作用去重。

### 4. 幂等键应该由哪些信息组成？

答：围绕一次业务意图生成稳定操作 ID，并绑定租户、业务对象、操作类型和规范化参数摘要。网络重试、重新投递或 Worker 接管应沿用同一业务幂等键，`attempt_id` 仅用于记录尝试，不能每重试一次就换键。

服务端持久化键、参数摘要、状态与结果；相同键不同参数应拒绝。真正的新业务操作才生成新键，不能仅凭“参数相同”永久合并两次独立的合法操作。

### 5. Checkpoint 和 Journal 分别解决什么问题？

答：Checkpoint 保存从哪里继续所需的最小快照，如节点、状态摘要、预算和待审批动作；Journal 保存有序事件和操作结果，用于审计、诊断和必要时重放。Checkpoint 便于恢复，Journal 便于解释，两者不能互相完全替代。

### 6. Queue、Lease 和 Heartbeat 如何配合？

答：Scheduler/Queue 只把任务交给当前 owner；Worker 用 owner/version CAS 获取 Lease，Heartbeat、Checkpoint 和完成提交都校验当前 fencing token。租约过期不会杀死旧 Worker，Gateway/存储必须拒绝旧 token 的续租与写入，再由新 owner 接管；外部 API 还要靠业务幂等和状态核对，避免重复副作用。

### 7. Outbox 能解决什么一致性问题，不能解决什么问题？

答：Outbox 可在同一数据库事务中把任务状态变化和待发布事件一起写入，避免“状态成功但事件丢失”。它不能让外部支付、发信或第三方 API 与本地事务自动原子化，外部动作仍需幂等、对账和补偿。

### 8. 长任务恢复前为什么必须核对外部副作用？

答：Checkpoint 可能写在外部调用之前或之后，因此崩溃后本地状态未必反映真实副作用。不能仅凭“最后一个节点未完成”就重做动作，必须先查询外部状态。已执行、未执行或仍未知时的处置见题10。

### 9. 任务状态、会话记忆和长期 Memory 为什么不能混为一谈？

答：任务状态描述当前工作流进度和事实，会话记忆服务于当前线程，长期 Memory 是跨请求可检索且有来源/策略的用户或业务信息。三者的生命周期、权限、删除和恢复语义不同，混存容易把临时事实写成长期记忆或让恢复污染新任务。

## 生产运行机制

### 10. 如何处理“外部请求已经成功，但 Agent 没收到响应”的未知结果？

答：把结果标记为 unknown，不直接重试；用幂等键或查询接口核对外部状态。已成功则补写本地记录，明确未成功且动作可安全重试时才用原键重试；无法确定就人工对账。用户界面应说明部分完成和当前状态。

**追问：工具调用已成功但前端断线，重试前如何判断副作用是否发生？**

重连后按 Tool Call ID/幂等键查询任务状态：已成功就补发保存的结果，执行中就显示处理中，确认未执行才沿用原键重试；仍未知时提示待核对，不创建新操作。

**支付场景：**幂等键绑定账户、收款人、金额和币种；查询已支付则补写本地状态，明确未支付才按预算重试，查询失败或状态不一致则冻结后续动作并人工对账。审批预览也要绑定同一对象与金额；确认后若这些字段变化，必须重新审批。

参考面经：[百度 AI Agent 开发岗](https://www.nowcoder.com/discuss/931706522621530112)；[腾讯/百度 Agent 面经汇总](https://www.nowcoder.com/discuss/878600528970735616)。

### 11. 如何设计多租户任务的并发、资源和状态隔离？

答：按租户分区或使用 Scope 绑定的任务键，设置并发、费用、文件和网络配额；Worker 获取 Lease、恢复 Checkpoint 和提交结果时都要核验同一任务 Scope，避免接管时丢失租户边界。底层存储、缓存、索引、工作区和 Trace 的统一隔离要求见 [[Learning/Agent/07_可靠性与安全/身份治理与跨Agent#6. 多租户隔离为什么要覆盖数据库、向量库、缓存、工作区、队列和 Trace？|身份治理与跨 Agent 题6]]。

关联：[[Learning/Agent/07_可靠性与安全/身份治理与跨Agent#6. 多租户隔离为什么要覆盖数据库、向量库、缓存、工作区、队列和 Trace？|身份治理与跨 Agent题6]]

### 12. 什么时候应该重试，什么时候应该进入 DLQ 或人工处理？

答：错误分类和可重试条件见 [[Learning/Agent/07_可靠性与安全/可靠性与安全#27. 工具错误应该如何分类并决定处理或重试？|可靠性与安全题27]]。达到次数/时间上限或无法自动恢复时，将任务写入 DLQ，保留上下文和证据供人工处理；未知副作用先按题10对账，不进入盲目重试。

### 13. Worker 优雅关闭时应完成哪些动作？

答：停止领取新任务，向运行中的节点发送取消或在安全点停下，在 Lease 到期前保存 Checkpoint/释放租约，关闭流式连接并写明终止原因，最后确认外部副作用状态。这样新 Worker 接管时不会重复执行或丢失进度。

### 14. Agent 的 SLI/SLO 除 HTTP 指标外还应监控什么？

答：还要监控任务创建/继续/取消成功率、任务成功、人工接管、越权和秘密泄露、TTFT/任务 P95、工具超时、重试、stuck loop、恢复成功率和每任务成本。代码 Agent、知识问答和批处理的目标应按任务类型分开。

### 15. Agent 的一次生产发布对象为什么不只是代码？

答：模型、Prompt、Few-shot、工具 Schema/执行器、策略、RAG 索引/Embedding、Workflow 图、State Schema、配置和 Eval 门槛都会改变行为。必须记录组合版本，否则只回溯 Git SHA 也无法解释线上结果。

### 16. Prompt、模型、工具、策略、索引和 State Schema 应如何版本化？

答：每类对象有不可变版本，Trace 记录本次运行使用的组合；State Schema 提供迁移器或兼容范围，工具和策略变更要重新跑安全/协议回归。发布和回滚以版本矩阵为单位，而不是把所有变化隐含在配置文件里。

### 17. 稳定分组的灰度和回滚为什么重要？

答：稳定地把同一用户/租户分到同一版本，才能比较质量、成本、延迟和安全变化，避免同一用户在两版之间来回跳。回滚还要处理正在运行的任务：兼容的继续，不兼容的暂停、迁移或人工接管。

### 18. 预算、限流和背压应该在哪些层同时控制？

答：入口控制请求速率，任务层控制步数、Token、费用和墙钟时间，模型/Embedding/工具层控制并发，队列层控制等待长度，执行层控制单次命令/网络资源。只在入口限流无法阻止内部调用放大。

### 19. Agent 生产环境应准备哪些降级档位？

答：可按风险从完整 Agent 降到低成本模型、只读 Agent、固定 Workflow、仅生成建议不执行工具、静态帮助或人工处理。每档必须明确允许的工具、数据、审计、提示和恢复方式，Fallback 不能绕过原有权限。

## 运维与事故响应

### 20. 如何为 Agent 设计可执行的告警，而不是只有监控曲线？

答：每个告警绑定范围、证据和动作，例如 Provider 错误升高切换/降级，stuck loop 增多降低预算并冻结版本，越权尝试立即冻结高风险工具。告警必须带 task、tenant、版本和关联 ID，并有负责人和 Runbook。

### 21. P0、P1、P2 事故可以如何划分？

答：P0 是数据外泄、未授权写入、批量破坏或权限绕过；P1 是大面积失败、成本失控、关键租户不可用或无法恢复；P2 是局部质量、延迟或工具退化。分级依据是影响和风险，不是单纯错误数量。

### 22. Agent 事故响应的标准流程是什么？

答：发现后定级，先用 Kill Switch、撤权或冻结遏制，再保全 Trace、审计和工作区快照，判断影响范围，修复或回滚，分阶段恢复并验证，最后复盘和新增回归 Case。复盘要定位到可修复的 Context、模型、工具、策略、数据或运维层。

### 23. Kill Switch 应该控制什么，为什么不能只写在文档里？

答：它可以禁止写工具、网络出口、特定 MCP、后台队列或降低预算，也可以强制人工审批。开关必须独立于模型 Prompt，有明确操作者权限、审计、传播时延、已有任务处置和恢复演练，否则事故时不可靠。

### 24. 新版本发布时，如何处理仍在运行的旧任务？

答：先停止旧版本接收新任务，按 State/Tool/Policy Schema 判断哪些任务可由旧版完成、哪些可迁移；兼容任务继续或安全迁移，不兼容任务暂停并保留 Checkpoint。不能让旧状态在新图中静默解释成不同动作。

### 25. 如何防止成本、延迟和 stuck loop 在内部 fan-out 下失控？

答：在任务级维护步数、Token、费用、并发和重复意图预算，在模型/工具级设置配额，在 Loop 中检测相同动作和无进展，在队列过载时背压或降级。Trace 记录每次预算消耗与停止原因，不能只统计一次外部请求。

### 26. 如何设计一个能跨进程、跨机器、跨版本恢复的 Agent 任务系统？

答：持久化任务 FSM、Checkpoint 和 Journal，队列通过 Lease/Heartbeat 分配，所有副作用使用幂等键并保留结果；运行记录包含代码、模型、Prompt、Tool、Policy 和 State 版本。恢复时做版本兼容、外部对账和预算重算，不满足条件就转人工。

**面经变体：工具调用超时后服务重启，如何判断继续还是重试？**恢复记录需包含 task ID、State 版本、Checkpoint、Tool Call ID、业务幂等键和副作用状态，确保重启后仍能查询下游。未知结果的处置沿用题10；不能只因本地没有回执就重放最后一次调用。

恢复判定沿用题10；本变体重点补齐任务/State 版本、Checkpoint 与 Tool Call ID，避免跨重启丢失对账依据。

## 场景追问

### 27. 新模型灰度后任务成功率上升，但高风险工具拒绝率下降，你会如何处置？

答：拒绝率下降时，先区分误拒绝减少还是未授权操作被放行。前者可能是改善；本应拒绝的请求却执行成功，才是安全退化。

接着按风险、授权状态和工具类型检查 Trace，比较越权放行、审批绕过、重复副作用、误拒绝和任务成功率。安全硬门槛失败就暂停扩大灰度、冻结相关能力或回滚；若只是合法请求通过率提高，则继续受控观察。

### 28. 线上出现大量任务卡在 `running`，你会从 Queue、Lease、Checkpoint 和外部依赖哪几层排查？

答：排查时先从 Trace 和任务事件确认卡在哪一步：Worker 领取、模型等待、工具等待，还是状态提交；再检查 Lease、Heartbeat、Checkpoint 和下游超时。批量重置或接管前，必须确认没有未知副作用，避免盲目重放。

### 29. 设计一个从完整 Agent 降级到只读、固定 Workflow 和人工处理的运行方案。

答：各降级档位及其能力边界见题19。本题落地时用独立策略配置和 Kill Switch 切换档位，记录审计并告知用户当前能力；还要明确在途任务继续、暂停还是转人工，不能静默改变其执行语义。

## 深入专题：副作用状态与恢复细节

### 30. 如何处理状态 Schema 或执行策略升级后的旧任务？

答：记录任务使用的代码、Provider Adapter、工具、策略和 State Schema 版本，恢复前检查兼容范围；可迁移的状态用显式迁移器转换，不兼容的任务暂停或人工处理。尚未执行的 ToolCall/审批动作还要按当前 Schema、参数摘要和资源版本重新校验，不能让新代码静默用不同语义解释旧字段。

**追问：State Schema 或策略前向迁移后，为什么不能只回滚应用代码？**

旧代码可能无法读取新字段或已写入的新语义，策略、索引和工具版本也可能与旧代码不兼容。回滚必须覆盖相关对象或提供向后兼容迁移；已发生的外部副作用还需对账，不能只恢复进程镜像。

### 31. 为什么 Replay 必须与真实执行分离？

答：Replay 的目的是投影历史状态、界面和停止原因，而不是重新产生文件、网络或支付副作用。它应使用冻结的模型/工具 Fixture，所有执行入口在 Replay 模式下被拒绝或替换为只读实现。

### 32. 如何验证恢复设计真的不会重复副作用？

答：在副作用前、完成后、确认前和确认后分别注入崩溃，检查恢复分类、幂等键、状态提交和用户提示；同时覆盖 Worker 重复领取、Lease 过期、网络超时和查询失败。验收标准应包括“未知状态绝不自动重放”。
