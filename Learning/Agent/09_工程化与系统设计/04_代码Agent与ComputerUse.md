# 09.4 代码 Agent 与 Computer Use

本页先讲代码库定位与可审查修改，再讲验证和失败恢复，最后比较 API、DOM 自动化与视觉操作。

## 代码 Agent 基础

### 1. 一个代码 Agent 的最小工具集应该有哪些？

答：最小集合通常是目录/文件发现、文本或符号搜索、受限读取、可审查编辑/patch、测试执行和 diff 查看。工具少而边界清晰比暴露一个无限制 Shell 更容易授权、评测和回滚。

### 2. 代码 Agent 为什么要先定位代码，而不是直接生成代码？

答：真实修改依赖模块边界、调用关系、类型、测试和构建命令；定位错误会导致改错文件、破坏接口或重复实现。先搜索和读取是为了让修改建立在仓库事实和可回指证据上。

### 3. 文本搜索、符号搜索、AST 和 LSP 分别适合什么问题？

答：文本搜索适合错误信息、配置和快速发现；符号搜索追踪定义/引用；AST 适合结构化分析和安全变换；LSP 提供类型、定义、引用和诊断。它们应组合使用，而不是把任何一种当成万能导航。

### 4. 代码库地图有什么用？为什么不能把它当成事实来源？

答：地图把目录、模块职责、入口和常用命令压缩成导航索引，减少初始探索成本。但代码会变化，地图可能过期，所以关键结论仍需用实际文件、测试和命令验证，并允许重新扫描。

### 5. 代码 Agent 的 Context 应该选择哪些内容？

答：至少包括任务目标、目标文件、直接调用者/被调用者、接口和类型、相关测试、构建命令以及最近错误。每段内容最好带路径、行号或版本，按决策需要扩展，避免把整个仓库无差别塞进窗口。

### 6. 为什么代码中的精确名称和类型关系通常不能只用向量检索替代？

答：代码修复常依赖精确符号、路径、参数和调用关系，语义相似不保证名称和版本正确。向量检索可用于发现相关概念，但应由文本/符号搜索、AST、LSP 和编译器结果确认事实。

### 7. 直接覆盖、唯一替换和 Unified Diff 各有什么风险？

答：覆盖简单但容易丢失并发修改；唯一替换要求旧片段只匹配一次，失败时应停止；Unified Diff 可审查、回滚和定位上下文，但应用前要检查路径、版本和上下文是否仍匹配。

### 8. 模型提出 patch 和 patch 被应用之间为什么必须有边界？

答：模型输出的 patch 是不可信提案，不是已经获准的文件操作；只有拥有工作区和授权控制权的执行器才能应用它。提案不能改变用户文件，也不能自行扩大任务范围；应用前的路径、版本、diff 和审批检查见题9。

## 修改与验证闭环

### 9. 应用代码 patch 前至少检查什么？

答：检查路径在工作区边界内、patch 上下文和文件版本仍匹配、没有覆盖用户并发修改，且变更范围符合授权。路径规范化、符号链接和受保护文件的拒绝规则见 [[Learning/Agent/07_可靠性与安全/可靠性与安全#24. 代码 Agent 如何防止路径越界？|可靠性与安全题24]]。必要时先预览并审批，再应用和查看 diff。

### 10. 代码 Agent 写完后应按什么顺序验证？

答：通常是语法/import，再跑定向单测，随后 lint/format、类型检查、相关集成测试，必要时再跑完整测试。顺序从快到慢；记录命令、目标工作区版本、退出码和实际测试结果。每次写入后都要重新验证，旧版本通过或命令只打印“通过”都不能证明最终产物通过。

### 11. 工具执行结果应包含哪些字段，才能支持后续调试？

答：至少包含命令或工具名、规范化参数摘要、退出码/状态、stdout/stderr 摘要、耗时、工作目录、是否截断、错误码和副作用状态。完整敏感输出不应默认进入模型 Context 或 Trace。

### 12. 如何区分任务开始前已有的 diff 和 Agent 新产生的 diff？

答：任务开始先记录基线 commit、工作区状态和已有 diff，之后把每次应用的 patch 与基线分层记录。最终审查只归因于 Agent 自己的变更，禁止直接覆盖或回滚用户原有修改。

**追问：代码 Agent 如何处理用户已有的未提交修改？**

把已有修改作为受保护基线，不覆盖、不擅自清理；如果 patch 上下文与用户修改冲突，停止自动应用并展示精确冲突，重新定位或请求用户选择。只有获得明确授权，才可改动冲突区域。

### 13. Git Worktree 对并行 Coding Agent 解决了什么问题？没有解决什么问题？

答：每个任务使用独立目录和分支，可以减少文件互相覆盖并保留独立 diff。它不自动解决权限、依赖安装、数据库/网络副作用、合并冲突、清理失败或错误合并，仍需运行时隔离和策略控制。

### 14. 如何防止 Agent 因为测试失败进入重复修复循环？

答：记录失败 fingerprint、涉及文件、测试轮次和最近动作；检测相同 patch/参数、无状态变化或同一错误重复出现，达到上限就停止或请求人工介入。修复应尽量小范围，并由新的验证证据驱动下一步。

### 15. 如何用覆盖率、变更过滤和定向测试判断修改有效？

答：先过滤生成物、lockfile 和纯格式化噪声，比较变更行和关键分支的测试覆盖，再跑与改动直接相关的测试及编译/类型检查。覆盖率只说明测试触达，不等于逻辑正确，最终还要看业务验收。

**场景补充：AST/LSP 难以直接生成有效单测时**，先用它们定位符号、类型和依赖，生成测试骨架；断言和 Fixture 仍要来自行为契约、边界案例和可观察结果。动态行为、反射或难以隔离的副作用可改用 characterization、集成或沙箱测试；语法树和类型信息本身不能证明业务行为正确。

### 16. 为什么“生成了代码”不等于“任务完成”？

答：完成还需要 patch 被合法应用、代码可构建、测试/业务验证通过、变更范围符合授权且没有未处理副作用。模型自述不能代替实际 diff 或运行结果；证据门禁的通用要求见 [[Learning/Agent/07_可靠性与安全/可靠性与安全#28. Evidence Gate 应该验证什么？|可靠性与安全题28]]。

## Computer Use 机制与边界

### 17. Computer Use 与普通 Tool Calling 的执行循环有什么不同？

答：普通工具通常返回结构化事实；Computer Use 由模型根据截图提出坐标或键盘动作，环境执行后再返回截图/事件。视觉状态受焦点、布局、登录和分辨率影响，动作后必须重新观察并验证。

### 18. GUI Agent 的原子动作合同至少应包含什么？

答：动作类型、参数、action_id、目标窗口/会话、超时、取消状态、执行结果和是否产生副作用。适配器把 Provider 动作翻译成内部类型，策略层在执行前校验坐标、窗口、权限和当前 State。

### 19. 为什么动作发送成功不等于界面状态已经成功？

答：点击事件可能落在错误控件、页面尚未加载、弹窗抢焦点或操作只完成了一半。成功必须由 UI 状态、页面 DOM、业务 API 或其他受信事实确认，不能只看“鼠标事件已发送”。

### 20. API、Playwright/Selenium 和 Computer Use 应如何选择？

答：有稳定 API 优先 API；没有 API 但 DOM/选择器稳定时用 Playwright/Selenium；只有 GUI、旧系统或需要视觉判断时才用 Computer Use。文件和 CLI 任务应使用受限文件/命令工具，不要用截图替代结构化接口。

### 21. Computer Use 为什么应该运行在隔离的容器或虚拟机中？

答：视觉动作可能误触宿主机窗口、文件、Cookie、下载和网络资源。隔离环境可以限制文件挂载、网络出口、进程、CPU/内存和会话生命周期，任务结束还应销毁或清理凭据与截图。

### 22. GUI Agent 的成本和延迟应该如何拆解？

答：通用模型、排队和工具耗时见推理行为题3；Computer Use 特有成本是截图分辨率/频率、视觉输入 token、动作数和沙箱时长，特有等待是页面状态变化与截图确认。记录这些指标和重试后，可减少重复截图、用 DOM/API 处理稳定页面，并设置动作与总费用上限。

关联：[[Learning/Agent/10_模型与推理/03_推理与模型行为#3. Agent 的端到端延迟应如何拆解？|推理与模型行为题3]]

### 23. GUI 场景中的高风险动作如何做审批和二次验证？

答：购买、付款、删除、发信、提交等动作应展示目标、参数、证据和影响，经过资源级授权/人工确认；执行后再通过 UI 或 API 核对结果。关键词拦截只能做提示，不能替代身份、资源和当前状态策略。

### 24. GUI Agent 的评测集应该覆盖哪些异常？

答：至少覆盖布局变化、弹窗、焦点丢失、登录过期、网络抖动、半成功、重复提交、危险动作拦截、截图过大、超时和会话清理。评测既要看最终任务，也要检查未经授权的动作和副作用。

## 场景追问

### 25. 设计一个能够修复代码并提交建议级 diff 的 Coding Agent，如何划分观察、修改、验证和审批边界？

答：流程可以分四步：观察并读取 workspace；生成受限 patch，预览并核对基线；获批后应用，并用白名单命令验证；最后由人或规则审查 diff、测试结果和风险，再生成提交/PR 草稿。先提供建议级 diff，用户可以在实际写入前审查。

### 26. 一个 patch 应用失败且仓库同时有用户修改，你会如何恢复？

答：保留失败现场和用户 diff，不强行覆盖；重新读取目标文件、比较基线与当前版本，重新生成更小的 patch 或请求用户解决冲突。恢复后再次检查 diff、测试和授权范围，不能用回滚命令抹掉用户修改。

### 27. 如果一个网页自动化任务既有稳定 DOM 又需要视觉判断，你会如何组合 API、DOM 和 GUI？

答：稳定的数据读写优先走 API，结构稳定的控件用 DOM selector；只有布局探索、画布或非结构化判断才需要视觉模型。三种通道都应复用同一套权限、任务 State、审计和成功校验，不能让 GUI 绕过 API 的安全边界。

### 28. 如果 GUI Agent 重复点击导致重复提交，你会如何从动作、状态和外部副作用三层修复？

答：需要动作、界面状态和业务状态三层配合。动作层为每次操作分配 action_id 并做去重；界面层记录“处理中/已提交”，重试前重新观察；业务层用幂等键和状态查询防止重复提交。结果未知时先查外部状态，不再次点击；仍无法确认就转人工。
