# 12.1 Agent 与 AI 后端综合题

> 本页用跨主题场景串起 Provider、RAG、安全、运行时和平台取舍。先独立设计，再回主专题查边界；项目陈述与证据准备另见 [实践路线与项目表达](./实践路线与项目表达.md)。

## 一、AI 后端与 Provider

### 1. 一个 Python AI 服务从请求进入到最终返回，应该经过哪些确定性边界？

答：请求依次经过身份/租户校验与限流、DTO/schema 校验、带预算和 deadline 的任务创建、模型调用、受限提案执行和业务验收；返回时区分增量事件、任务状态与最终答案。各组件的职责边界见 [[Learning/Agent/10_模型与推理/02_Provider适配与框架选型#21. 设计一个支持多 Provider、工具调用、流式输出和人工审批的 Agent Runtime，你会如何分层？|Provider 适配与框架选型题21]]。FastAPI 返回 200 不代表业务任务成功。

### 2. LLM/第三方接口超时后，如何处理可能已经执行或扣费的未知结果？

答：区分连接未建立、明确拒绝、服务端已处理但响应丢失，以及客户端 deadline 到期。只有确认可安全重试时才退避；结果可能未知时，按 [[Learning/Agent/09_工程化与系统设计/02_Durable与生产运维#10. 如何处理“外部请求已经成功，但 Agent 没收到响应”的未知结果？|Durable 与生产运维题10]] 查询或对账，不能盲目重发。错误分类见 [[Learning/Agent/07_可靠性与安全/可靠性与安全#27. 工具错误应该如何分类并决定处理或重试？|可靠性与安全题27]]。

Provider 场景还要逐次记录 request ID、账单状态、Token/费用和模型版本，便于追查是否已处理或计费。

关联：[[Learning/Agent/09_工程化与系统设计/02_Durable与生产运维|Durable 与生产运维]]与[[Learning/Agent/07_可靠性与安全/可靠性与安全#27. 工具错误应该如何分类并决定处理或重试？|可靠性与安全题27]]

### 3. SSE/Streaming 输出如何处理跨事件边界的敏感词和断线？

答：不能对每个 chunk 独立匹配，因为敏感词可能被拆到相邻事件；要在有限大小的滑动窗口中拼接检测，同时控制缓存长度、延迟和 Unicode 边界。检测到高风险内容时暂停或终止流并记录策略版本，客户端通过事件 ID/序号去重和续接；流中断不代表最终任务失败，最终结果仍要经过完整内容安全、schema 和业务验收。

## 二、RAG 与内容安全

### 4. RAG 的脱敏策略应该放在哪些位置？如何证明脱敏没有破坏召回？

答：摄取时按数据分类和租户策略清理密钥、个人信息和受限字段，索引和缓存保留最小化的权限/版本元数据；查询召回前做权限过滤，Context 组装和输出前再次做字段级检查，日志/Trace/评测集也使用同一套数据治理。用脱敏前后配对集比较 Recall、MRR/NDCG、答案正确率、引用覆盖和越权率，按文档类型、风险等级和长尾查询分桶，不能只看平均召回。

关联：[[Learning/Agent/07_可靠性与安全/可靠性与安全#12. 如何处理模型输出中的敏感信息？|可靠性与安全题12]]

## 三、框架、状态与平台取舍

### 5. 已有 Agent 平台能力时，为什么还要做定制开发？

答：先列出平台已有的模型路由、工具治理、权限、评测、观测和发布能力，再明确业务缺口是数据源、时延/成本、合规、状态模型还是特定交互；定制部分只拥有不可复用的领域差异，通用能力尽量接入平台。回答要说明维护责任、迁移成本、指标收益和失败时的回退方案，而不是用“平台不灵活”概括。

### 6. 一个 Agent/可观测平台的数据链路如何从“产生”走到“展示”？

答：服务/SDK 产生结构化事件和 Trace，采集层做采样、脱敏和批量传输，消息或日志管道负责缓冲，存储层按实时查询与长期分析分流，计算层聚合延迟、Token、成本、质量和错误，展示层按租户/版本/任务切片并关联 Runbook。要同时说明丢失、重复、迟到、成本和隐私边界，不能只画“日志进数据库”。

关联：[[Learning/Agent/08_评测与可观测/评测与可观测性|评测与可观测性]]

### 7. Agent 在 Linux 上运行时，cgroup、内核版本和 profiling 会如何影响线上结论？

答：cgroup 限制 CPU、内存、进程数和 I/O，容器内看到的资源与宿主机、内核调度和文件系统行为可能不同；内核版本会影响网络、epoll、io_uring、OOM 和观测工具。性能问题先区分应用、Runtime、容器配额和下游，再用同一镜像、内核/资源限制、负载和采样开销复现，不能只在开发机跑 benchmark。

### 8. 如何把一个 RAG/Agent 项目讲出业务价值，而不是只讲调用了模型？

答：先说明旧流程的质量、成本或时延基线，再比较固定程序、检索和 Agent 各自解决了什么任务；用任务成功率、引用/召回、人工接管、延迟、Token/费用和安全事件证明增量。解释为什么不用已有平台能力，报告一个失败案例和适用边界；“用了 LangChain/Agent”本身不是业务价值。通用项目陈述顺序见 [[Learning/Agent/12_综合设计与项目表达/实践路线与项目表达#4. 如何把一个练习项目讲成“自己解决了什么工程问题”？|实践路线题4]]。

当前知识库可选 [[Learning/Case_Studies/AI/AI-MCP-Gateway|AI MCP Gateway]] 或 [[Learning/Case_Studies/AI/Agent脚手架与可编排RAG|Agent 脚手架与可编排 RAG]] 练习。说明结论证据来自源码走读、原型、可重复测试、压测还是生产数据；不同证据支持的结论强度不同，不能把设计推断说成线上收益。

### 9. 如何评价 AI 编程工具在团队中的真实收益？

答：把“生成速度”拆成需求澄清、代码审查、测试覆盖、缺陷率、回滚率、交付周期和维护成本，按任务类型和人员经验分桶；要求人类负责边界、权限、依赖和验收，生成代码必须经过测试、静态检查、审查和安全扫描。工具不可靠的场景要有拒用边界，不能用一次 Demo 的代码量证明生产收益。

### 10. 当前 AI 案例只有设计文档或源码审计时，如何回答“你真的做过吗”？

答（项目补充）：直接把“事实、推断、计划”分开。事实是能指向代码、配置、测试输出或可复现实验的内容；推断是基于架构和故障模型得到、但尚未运行验证的结论；计划是下一步准备补的压测、注入或上线方案。可以说“我完成了源码走读和协议/状态设计，并补了这些测试方案”，不能说成“线上已稳定运行”。

面试前为每个案例准备证据表：业务问题、自己修改/分析的文件、启动方式、成功路径、一个可复现失败、测试与指标、没有覆盖的边界。若没有真实数值，就给指标定义、采集点和实验变量，例如任务成功率、工具调用正确率、引用正确率、P95、每任务成本和越权率；明确“尚无基线数字”比编造提升百分比更可信。
