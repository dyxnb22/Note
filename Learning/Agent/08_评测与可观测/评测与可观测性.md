# 08.1 Agent 评测与可观测性

本页定义质量指标、数据集、Trace 与 Badcase 分类；[评测实验与发布门禁](./评测实验与发布门禁.md) 把它落实为可运行的 Case/Harness，[轨迹诊断与线上故障](./轨迹诊断与线上故障.md) 用于定位真实失败。

## 基础认知：什么叫做得好

### 1. Agent 系统应该评估哪些层次：模型、Prompt、Tool、Workflow、任务和产品？

答：

**按系统组件分层：**

| 层次 | 评估内容 |
|------|----------|
| 模型层 | 生成/推理能力 |
| Prompt/路由层 | 意图和格式 |
| Tool 层 | 选择与参数 |
| Workflow/Runtime 层 | 执行和恢复 |
| 任务层 | 是否完成目标 |
| 产品层 | 用户价值、成本和安全 |

**按评测维度分层：** 任务结果、产物正确性、轨迹质量、安全/治理。实现上再分 State/Schema 单测、Mock 协议、隔离场景和线上/Replay。分层能把模型能力问题与工具、Runtime、权限和环境问题分开。

最终文本正确也可能伴随越权、重复副作用或伪造执行；因此任务结果、产物、轨迹与安全要分别报告。安全硬门槛不能被平均质量分抵消。

**多 Agent 评测差异：** 与单 Agent 基线比较任务成功、关键错误/安全违规、人工接管、P50/P95 延迟、Token/费用、工具调用数、失败恢复和长尾切片；再做去掉 Reviewer/Worker/并行的消融。平均成功率提升若伴随高风险退化，不能发布。

**平台面经场景：**证明业务覆盖时，用真实任务构造正常、边界、工具失败和权限拒绝样本，分别观察任务成功、工具选择/参数、安全、延迟和成本；线上故障应能从指标回到 Trace，定位模型、Context、检索、工具或状态管理。平台健康（接口、队列和依赖可用）与 Agent 任务质量要分开监控，接口返回 200 不代表任务成功。

来源：[百度 AI Agent 开发岗面经-04](https://www.nowcoder.com/discuss/931706522621530112)。

### 2. 如何定义 Agent 的任务成功率？

答：先定义可观察的业务验收条件，再统计满足条件且没有未处理副作用/安全问题的任务比例；部分成功、人工接管和超时要单独计分。不能只用模型自评或字符串相似度作为唯一成功标准。

### 3. 如何评估最终答案正确性、完整性、相关性和可读性？

答：正确性看事实/计算是否符合金标准，完整性看必需字段和步骤，相关性看是否回答目标，可读性看结构、语言和引用；可结合确定性断言、人工标注和受控 Judge。指标要按任务类型和风险分桶，避免平均分掩盖关键错误。

### 4. 如何评估工具选择准确率、参数正确率、调用顺序和不必要调用率？

答：建立带正确工具、必要参数、依赖顺序和可选替代路径的标注集，分别计算选择/参数/顺序准确率和无效调用率；高风险动作还看越权阻断。工具选择正确但最终任务失败时要继续看执行和验证层。

关联：[[#30. 如何监控模型选错工具、重复调用和无效规划？|题30]]

### 5. RAG 评测为什么必须把检索、上下文组装和生成拆开？

答：最终回答错误可能来自没召回、排序靠后、Context 被截断或生成阶段没有使用证据；只看答案分数无法定位。检索指标和计算方式统一见 [[Learning/Agent/06_RAG与知识库/RAG与检索|RAG 与检索]]，本页重点是把 Retriever、Context Builder、Generator 和端到端任务分别评分，再联合延迟、Token 与权限违规做根因归类。

### 6. 如何评估幻觉、Groundedness、安全性和拒答质量？

答：构造有证据、无证据、冲突证据、恶意内容和高风险动作样本，检查回答是否有支持、是否会安全拒答、是否越权或编造工具结果。Groundedness 不能只看引用格式，还要判断引用是否真正支持具体结论。

### 7. 如何同时评估质量、延迟、Token、成本和稳定性？

答：把任务成功、P50/P95/P99 延迟、TTFT、输入/输出 Token、单任务费用、错误/超时/重试率放在同一个实验报告中，按模型、任务、租户和版本分桶。Token 下降本身不代表优化；要确认成功率、工具行为和安全没有退化。上线门槛用多目标约束，不能用降低质量换来的低成本称为优化。

关联：[[#28. 如何监控延迟、Token、成本、吞吐、错误率、超时和任务成功率？|题28]]

### 8. 如何判断 Agent 是否真的节省了用户时间？

答：比较基线流程和 Agent 流程的端到端完成时间、人工操作数、重试/纠正次数、转人工率和任务成功率，并控制用户和任务难度差异。只看模型响应时间不够，工具等待和用户确认也应计入。

## 评测机制：如何测量质量

### 9. 没有标准答案时如何评测？

答：把任务拆成可验证约束、必要事实、工具轨迹、风险和输出质量，使用规则断言、执行结果、人工标注和多维 Judge 组合评分。允许多种正确答案时评估是否满足目标和安全边界，而不是要求文本完全一致。

### 10. LLM-as-a-Judge 的优点、问题和改进方法是什么？

答：优点是能评估开放式质量、规模化和解释性较好；问题是偏好偏差、对 Prompt 敏感、可能被格式/模型风格影响，甚至与被测模型同源。用明确 rubric、参考证据、盲评/多评委、人工校准和确定性断言约束它，并监控 Judge 与人工的一致性。

### 11. 如何构建人工标注规范和一致性检查？

答：先定义任务成功、部分成功、安全违规和可接受答案的正反例，再规定字段、等级、证据和不确定处理；多标注员独立标注，测一致性并复盘分歧。标注规范要随 Badcase 更新并版本化。

### 12. 如何构建离线数据集、沙箱、回放集和回归集？

答：离线集覆盖代表性任务和长尾，沙箱提供可控工具/数据，回放集固定历史失败轨迹，回归集包含每次修复和安全边界案例；每条样本保存目标、约束、版本和评分器。避免把生产敏感数据未经脱敏直接复制。

### 13. 如何避免评测集泄漏、重复和过拟合？

答：按用户/模板/实体去重，训练/调优/验证/测试隔离，保留隐藏集和新分布集；限制对测试集的手工调参次数并记录变更。线上随机抽样和新 Badcase 定期加入，但要冻结一部分基准集用于长期比较。

**追问：如何防止评测集泄漏到 Prompt、检索库、示例或训练数据中？**

对评测样本、近似改写和答案建立隔离清单，限制它们进入开发 Prompt、Few-shot、知识库和训练流水线；发布前做文本/语义近邻扫描并保留数据血缘。测试时结合隐藏集、时间切分或真实新样本；发现泄漏后重建评测集，不继续使用已被优化过的分数。

### 14. 如何处理模型输出的随机性？

答：固定能固定的版本、参数、工具 Fixture 和随机种子，对任务做多次运行并报告均值、分位数和失败率；高风险任务用确定性约束和验证器。不要因为一次成功样本就判定系统可靠。

### 15. 如何设计 benchmark，保证不同方案在相同环境下公平比较？

答：固定任务集、输入、知识/工具环境、权限、模型预算和评分器，一次只改变一个变量；明确允许的能力集合，避免人为限制基线或给候选额外信息。比较 Baseline 与 Candidate 的成功、风险、成本和延迟，并按任务类型、长度、风险、租户、语言等切片；为高风险 Slice 设最低门槛和最大退化，不能让平均分掩盖长尾损害。记录版本、调用、Token、延迟和失败路径。

### 16. 如何做 Prompt、模型、工具和策略的 A/B 测试？

答：用用户或任务 ID 做稳定分组，随机分配版本；保持样本、预算和评分器一致，一次只改变一个变量。多次运行和随机输出的统计处理见题31；安全门槛、影子流量与回滚条件见 [[Learning/Agent/08_评测与可观测/评测实验与发布门禁#11. 如何设计一次 Prompt/模型/工具改动的发布门禁？|评测实验与发布门禁题11]]。

关联：[[#31. 如何在模型输出随机的情况下做线上实验？|题31]]

### 17. 如何做线上离线一致性评测？

答：将脱敏后的线上真实 Trace 回放到冻结的模型/工具 Fixture，比较离线评分与线上任务结果/人工反馈；差异通常来自数据新鲜度、随机性、外部依赖或版本漂移。记录环境和版本，不能只重放一段 Prompt。

关联：[[#24. 如何回放一次历史 Agent 运行？|题24]]

### 18. 如何验证一个优化确实提升了长尾场景，而不是只提升平均分？

答：为改动可能影响的长尾任务建立固定回归桶，按难度、输入长度、业务分支、风险和用户类型切片；设置关键桶最低门槛并观察置信区间、最差分位数和失败类型。平均分提升但关键桶退化时不应直接上线；线上稳定分组与灰度回滚见题16和发布门禁专题题12。

关联：[[#32. 如何发现一次改动伤害了某个长尾人群或业务分支？|题32]]

## 诊断方法：如何知道错在哪里

### 19. 如何给 Badcase 分类：路由、上下文、检索、工具、规划、模型、执行还是展示？

答：沿运行链路寻找第一个偏离验收条件的节点：候选路径错是路由，必要事实没进 Context 是上下文/检索，工具选择/参数错是 Tool，步骤和依赖错是规划，执行状态/副作用错是 Runtime，事实对但表达错是展示。分类要指向可修改组件。

关联：[[Learning/Agent/06_RAG与知识库/RAG与检索#13. 如何区分检索失败、阅读失败、推理失败和表达失败？|RAG 与检索题13]]

### 20. 如何从 Trace 中定位第一个错误节点？

答：按时间和父子关系回放 State 转移，先看停止原因和成功证据，再逐项比较 Context、模型输出、工具输入输出、授权和验证结果。第一个不满足 Schema/前置条件或引入错误事实的事件，是优先调查的故障点；还要通过对照或复现实验确认根因。后续错误可能只是前序故障的传播。

### 21. Trace 应该包含哪些字段？

答：至少有 trace/task/tenant ID、父子关系、版本、状态转移、模型请求摘要与 usage、工具调用/授权/审批/结果状态、检索来源、验证结果、耗时、错误码和停止原因。原始敏感内容单独受控，公共字段稳定便于查询和评测。

---

**追问：Rollout 与 Trajectory 分别指什么？为什么要保存整条轨迹？**

Rollout 指在给定任务、模型和环境下采样/运行出的一次执行，Trajectory 指这次执行按时间排列的状态、决策、工具调用和观察序列。只看最终答案无法知道是检索错、工具参数错、循环过长还是最后一步偶然修正；保存轨迹才能做归因、回放、成本分析和过程级评测。

---

**追问：一条可用于分析的 Agent Trajectory 至少应记录哪些字段？**

至少包括任务/会话 ID、输入与任务版本、模型和 Prompt/Skill 版本、每轮 State 版本、结构化模型决策、Tool 名称和参数摘要、工具结果/错误、权限判断、验证结果、Token、延迟、重试、人工事件和最终 StopReason。敏感原文应按权限脱敏或分离保存；仅记录最终文本不能支持可靠复盘。

---

**追问：如何把线上 Badcase 自动回流？**

按错误、低反馈/重问、人工接管、撤销、投诉或安全告警触发采样；脱敏后把用户反馈关联到任务目标、输入、Trace、模型/Prompt/工具版本、工具结果和业务结果，再按需求理解、知识/检索、工具/权限、模型生成、状态推进和产品交互分类。高风险样本先人工复核，回流样本需去重、分级并可追溯。

关联：[[Learning/Agent/08_评测与可观测/评测实验与发布门禁#3. 一条可重放的 Agent 记录至少包含什么？|评测实验与发布门禁题3]]

### 22. 如何设计结构化日志和关联 ID？

答：请求生成 trace_id，任务、模型调用、工具调用和外部请求各有稳定 ID，并通过 parent_id 关联；日志用结构化字段而非只写字符串。ID 要贯穿网关、队列、Worker、模型适配器和工具服务，同时做脱敏和租户隔离。

### 23. 如何追踪一次请求跨越的多个 Agent、模型、工具、队列和数据库？

答：使用分布式 Trace 的 span/event，把 task_id/trace_id 作为传播上下文，记录每个边界的版本、状态、耗时、错误和输入输出摘要；异步队列保存父任务和事件 ID。不要只依赖框架节点名，因为真实副作用可能发生在框架之外。

### 24. 如何回放一次历史 Agent 运行？

答：冻结用户目标、输入与 Context 版本、模型/工具/权限响应、知识与策略版本、时间和随机种子，再在隔离环境按原事件顺序执行；真实支付、写库等副作用替换为只读 Fixture、模拟或幂等对账。验证修复时可只重执行明确选定的节点，但要记录替换变量并保存新旧轨迹。比较回放与原 Trace，定位代码、模型、数据或外部状态变化。

关联：[[#17. 如何做线上离线一致性评测？|题17]]

### 25. 如何识别“最终答案错，但每个工具结果看起来都合理”的问题？

答：检查工具结果是否覆盖目标、Context 是否正确组织、模型是否错误合并/推断、验证器是否缺失；设计跨工具一致性和最终验收检查。局部结果合理不等于任务结论合理，必须有端到端任务级评测。

### 26. 如何做失败路径分析？

答：把 Trace 转成状态转移和错误序列，按第一个错误节点、停止原因、重试/回退路径、资源消耗和用户影响聚类，找出高频/高风险组合。每个修复要绑定回归样本和指标，避免只修一个表面案例。

### 27. 如何把 Badcase 反馈到 Prompt、工具、评测集、模型或 SFT？

答：先确认根因再选手段：指令/格式问题改 Prompt/Schema，工具合同或权限问题改执行器，知识问题改解析/检索，能力分布稳定且有数据才考虑 SFT，评测集同步新增回归。所有修复都要比较基线和副作用。

关联：[[Learning/Agent/08_评测与可观测/评测实验与发布门禁#10. Online feedback、Replay 和永久回归集如何形成闭环？|评测实验与发布门禁题10]]

## 生产闭环：如何持续变好

### 28. 如何监控延迟、Token、成本、吞吐、错误率、超时和任务成功率？

答：按任务、模型、工具、版本、租户和复杂度记录端到端及分段指标，重点看 P95/P99，并按任务统计，而不只看请求；同时结合 Token、成本和成功率分析。告警要绑定可执行动作，如限流、降级、暂停或转人工。

关联：[[#7. 如何同时评估质量、延迟、Token、成本和稳定性？|题7]]

### 29. 如何建立线上告警和人工抽检机制？

答：为成功率、长尾延迟、工具拒绝/失败、异常重复、预算耗尽、安全事件和人工接管设置阈值与趋势告警；随机抽检高风险/新版本/异常 Trace，脱敏后由标注员复核。告警必须有负责人、Runbook 和回滚/降级动作。

### 30. 如何监控模型选错工具、重复调用和无效规划？

答：保存候选工具集、选择、参数、调用顺序、结果、重复哈希和任务目标，计算工具选择准确率、无效调用率、重复率、无进展步数和任务成功关联。单看工具调用次数会误把必要复杂任务当成低效。

关联：[[#4. 如何评估工具选择准确率、参数正确率、调用顺序和不必要调用率？|题4]]

### 31. 如何在模型输出随机的情况下做线上实验？

答：对同一任务重复运行，报告成功率、关键错误和成本的分布及置信区间，不用单次结果下结论；同时记录模型版本、随机参数和外部数据版本。分组与变量控制见题16，高风险变更先离线或影子验证。

关联：[[#16. 如何做 Prompt、模型、工具和策略的 A/B 测试？|题16]]

### 32. 如何发现一次改动伤害了某个长尾人群或业务分支？

答：按租户、任务类型、输入长度、语言、风险、模型路由和用户群体切片监控，设置长尾最低门槛和异常分布检测；抽查变化最大的 Trace。发现问题时暂停扩大、回滚或对该分支路由到旧版本。

关联：[[#18. 如何验证一个优化确实提升了长尾场景，而不是只提升平均分？|题18]]

### 33. 如何为 Agent 设置 SLO、SLA 和安全指标？

答：SLO 定义系统可观测目标，如任务成功率、P95 完成时间、可恢复率和工具可用性；SLA 是对外承诺，通常更保守；安全指标包括越权阻断、敏感泄露、审批绕过、注入成功和审计完整率。指标应按业务风险分级，不要只用 API 200 率。

## 场景追问：从一次 Badcase 到版本发布

### 34. 如何证明一个新增 Agent 能力值得构建？

答：先明确要解决的问题、现有基线和成功指标，再用代表性任务衡量收益，并同时估算权限、状态、调用和维护成本。最后根据收益与风险决定构建、推迟或放弃；“看起来更智能”不能代替证据。
