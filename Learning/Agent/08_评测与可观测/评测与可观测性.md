# 08.1 任务评测与可观测性

## 成功定义先于指标

评测判断任务是否做成，观测记录过程。查询看事实和来源，代码修改看产物与行为，写操作看外部状态和授权；先定成功标准，再选指标。

质量、执行合法性、成本和时间分别记录。越权操作直接判为不合格；拒绝是否正确，要看这个样本原本是否就应被拒绝。

## 从单次动作到完整任务

模型输出、工具参数与结果、检索候选和最终产物都可以单独检查，用于定位错误。各阶段检查通过后，还要看它们合起来是否完成了用户要求。

回归数据通常既有正常任务，也有要求拒绝或停止的样本。通过率统计是否符合各自预期，用户任务成功率则需要按真实任务分布和业务完成条件计算。

时间和费用是否影响通过判定，要在评测前写清，结果报告覆盖全部样本。分母算例、基线和比较方法见 [[Learning/Agent/08_评测与可观测/评测设计与发布标准|评测设计与发布标准]]。

## 程序验证与模型评审

文件是否存在、测试退出码、订单状态和字段约束，适合由程序验证。开放式回答有没有答全、表达是否清楚、是否切题，可以由人工或模型评审。先写清评分标准，用人工标注过的样本检查模型评分是否可靠，对有分歧的结果再复核。

Judge 可能受篇幅、表达、展示顺序或待评文本中的指令影响。要把评分指令和待评内容分开，固定评审模型、提示词等版本，再与人工标注结果比较。外部操作是否成功，另从回执和业务状态核实。

## 数据集与分组结果

样本应覆盖正常任务、边界条件、无答案、历史失败和对抗输入。训练、调参和最终比较的数据应隔离，近重复任务也要去重，避免把记住样本当成能力提升。

“无答案时明确说明缺口”和“应当执行却提前停止”需要不同标签。将二者都记成拒绝，会使成功率与拒绝率失去解释力。

总体平均值可能掩盖少见任务上的退步。按任务类型、语言、文档类型、风险和用户群拆开结果，并报告各组样本量与不确定性。模型输出有随机性时，在相同环境下适当重复运行。

## 配对比较新旧方案

样本保存稳定 ID、输入版本、预期判据和实际结果。新旧方案逐例配对，分成“都成功、只新方案成功、只旧方案成功、都失败”，就能看到修复和回归；只比较总成功数会漏掉这些变化。

同一问题重复运行，用于观察随机性；估计不确定性时仍按独立任务分组，注明任务数和每题重复次数。脚本化结果与真实模型效果的统计区别，见[评测设计](评测设计与发布标准.md)。

模型评审也需要验收：抽取固定人工标注集，分别看它对正确答案和错误答案的判断；比较候选时交换展示顺序，检查偏好是否随位置改变。若 Judge 会把冗长但缺证据的答案判高分，先修订评分标准和校准集，再用它做发布决策。

## 把 RAG 的证据错误分开测量

检索评测检查是否找到可用材料，生成评测检查如何使用这些材料。若把所有失败都归成“幻觉”，就无法判断应该修改索引、检索、上下文还是回答策略。

| 检查对象 | 要回答的问题 | 典型失败 |
|---|---|---|
| 权限范围内的证据召回 | 所需且允许读取的证据是否进入候选 | 合法条款被误过滤、漏召回或版本选错 |
| 上下文覆盖 | 进入模型的内容是否覆盖关键条件 | 召回到例外条款，却在截断时丢失 |
| 结论支撑 | 每个事实性结论是否受所用证据支持 | 原文写“可申请”，答案写“必然批准” |
| 引用对应 | 引用能否定位到支持该结论的位置 | 文档真实存在，但引用段落不相关 |
| 问题完成度 | 用户要求的各部分是否得到处理 | 解释了额度，却没有回答适用日期 |

Groundedness 看证据支撑，Completeness 看应答内容是否完整，Relevance 看是否回应问题。使用这些名称时注明标注和计算方式；忠实摘录原文却没有回答问题，仍可能不合格。[RAG 端到端评测维度](https://learn.microsoft.com/en-us/azure/architecture/ai-ml/guide/rag/rag-llm-evaluation-phase)

例如，可以把回答拆为 4 个可核查结论，其中 3 个被证据支持；按明确约定得到支撑比例 3/4。但如果错误的第 4 个结论涉及关键金额，平均比例不能代替任务判定，应单独记录关键错误。

每条结论是否有证据支持，由人工或经过校准的评审模型标注。评审时区分事实性结论、建议和主观表达，标记部分支持、证据冲突、无法判断等情况，并用人工样本估计误差。固定规则可以核查特定制度、订单状态及适用条件；开放领域的结论还需要更广泛的语义判断。

## 无答案、冲突与撤权也属于正常评测样本

“没有答案”至少有几种来源：材料本来没有覆盖，当前用户无权读取，系统没有找到，或信息缺少关键条件。对用户的说明可以保持必要的概括，内部标签则应区分原因，避免用统一拒绝掩盖检索故障，或通过错误信息泄露无权查看的资料是否存在。

企业样本可以围绕同一问题改变一个条件：换成旧制度、撤销用户组权限、删去关键例外、加入相冲突的有效条款，或让业务 API 返回暂不可用。检查的不只是最终文字，还包括系统是否补查、澄清、停止，以及是否产生了不允许的动作。

参考答案绑定来源版本与适用条件。制度变化后，重新核对标准答案，更新标签时保存依据与原因；比较结果时，区分制度更新引起的答案变化与实际回归。

## 还原一次模型决策需要的轨迹

Agent Trace 关联本轮 Context、动作提案、ToolCall 与 ToolResult、State 变化和验证结果。沿轨迹可以查清：模型看到了什么，提出什么动作，程序实际做了什么。

一次业务操作可能跨多轮模型调用，因此轨迹要保留任务、轮次、调用和业务操作之间的关联。只有耗时和 HTTP 状态时，就查不出提案、消息配对或结果验收哪里出了错。

需要回放时，保存原文或指向不可变版本的引用，限制这些材料的访问权限，并记录工具结果的截断、摘要与来源。hash 用于核对内容，原始输入则由保存的内容或引用重建；轨迹无需包含模型隐藏思维链。
