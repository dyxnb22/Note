# 08.3 轨迹诊断与故障定位

## 从最终症状回到首个偏差

先找出这次运行的版本和完整轨迹，沿输入、上下文、调用、状态、验证的顺序回看。发现首个偏差后，再用实验确认它是否造成后续错误。

反复取得相同工具结果却仍不停止，可能是状态没更新、停止条件没检查，也可能是合法轮询没有期限。

多个组件单独通过检查，完整任务却失败时，检查工具结果是否配回正确的调用、组件版本是否匹配、各节点是否收到完整目标，以及最后是否正确汇总了结果。

## 从提前提交开始排查

假设任务要求先取得订单事实与制度依据，轨迹却只有一次 finish 提案，最终验证失败。先确认查询和检索确实缺失，再查证据为何没有进入执行链。

缺少查询可能有几种原因：模型提前结束，工具目录不对，适配器丢了提案，或历史回填不全。对照上下文、Schema、原始响应和执行事件，逐项排除。

可以先手动固定查询与检索路径，检查执行器是否能产出合格结果；再接入模型，观察它能否稳定选择这条路径。两次实验分别检查执行逻辑和模型决策。

## 固定条件隔离故障层

固定正确证据后重新生成，可以观察问题是否在检索之后；固定模型响应后运行执行器，可以检查执行步骤，以及工具结果是否配回正确的调用。模拟超时、重复结果和取消，可以观察状态转移是否符合约定。

这些实验分别固定证据、模型响应或控制事件；一次尽量只改一个因素，方法见[评测设计](评测设计与发布标准.md#固定条件并逐例配对)。

## 按失败位置选择修复方式

| 症状 | 首先说明什么 | 关注的边界 |
|---|---|---|
| HTTP 成功，但响应根节点类型错误 | 未取得符合协议的模型响应 | 响应来源与适配器 |
| 提案包含未经允许的 tenant 参数 | 输入不符合工具契约 | 参数校验与身份来源 |
| 查询成功，但引用无法支持结论 | 执行成功不等于答案成立 | 证据与完成验证 |

找到首个不符合约定的输入或输出后，修改对应部分：模型说明、协议转换、工具实现或验证规则。

## 离线改善与线上退化

离线数据可能没有覆盖真实噪声、长历史、权限限制和故障，线上任务分布、服务容量或工具版本也可能变化。对照实际输入和版本记录，分清表现退化来自任务质量、基础设施失败，还是用户行为变化。

把排队、首个响应、工具等待和完整任务分别计时。首 Token 提前了，后面的工具仍可能很慢；长任务还要看停滞多久、怎样恢复、何时需要人工接管。

## 故障期间限制受影响的能力

发现异常写工具调用时，先禁用后续轮次的相应写入能力，暂缓执行待处理提案；模型已经生成但尚未执行的调用，也要重新检查。问题如果来自索引、Prompt 或工具版本，要查清哪些版本一起使用时出了问题，不能只回退程序代码。

恢复任务前，区分已经执行的动作、等待中的提案和仍有效的审批。修复后用原始问题与必要证据验证决策变化，并检查限制执行范围后，正常任务是否被错误拒绝。
