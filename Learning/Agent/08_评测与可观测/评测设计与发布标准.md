# 08.2 评测设计与发布标准

两个方案用同一批任务、成功标准和统计方法比较。除了总分，还要看具体哪些任务改善、哪些退步，以及哪些情况没测到。

## 评测样本的组成

每个样本保存稳定 ID、输入、可用环境、预期结果和实际结果。知识任务注明材料版本与权限范围，写操作注明授权条件及预期的外部状态。

以订单咨询为例，可以区分以下问题类型：

| 情形 | 要判断的能力 | 合理结果 |
|---|---|---|
| 订单仍待处理 | 能否根据当前事实选对适用制度 | 给出有依据的咨询结论 |
| 订单已发货 | 区分不同状态的规则 | 使用已发货条款 |
| 订单不在当前范围内 | 资源授权 | 不暴露该订单事实 |
| 引用被替换成编造原文 | 证据核查 | 不接受无依据结论 |
| 原文真实但不适用 | 条件判断 | 不因引用真实就通过 |
| 预算不足以完成 | 停止与部分结果 | 保留已知内容并说明缺口 |

正常咨询、越权请求和预算不足分别统计。正确拒绝可以使负例通过回归检查，但该样本并未完成正常咨询。

## 回归通过率与用户任务成功率

假设六个样本中，两个要求完成，四个要求拒绝或停止。六个都符合预期时，回归通过率是 6/6；实际进入成功终态的比例却只有 2/6。这里分母相同，统计的事件不同：前者统计是否符合各自预期，后者统计是否实际完成任务。不能把回归通过率直接当作线上任务成功率。

估计真实用户任务成功率，要用有代表性的任务分布和足够样本，固定成功标准。安全拒绝、无答案和系统故障分别标注，才能解释失败原因。

## 选择可用的基线

基线选现有可用的做法，再用相同任务和完成标准测试新方案。刻意选注定失败的做法作对照，会夸大改善。

例如，基线按“查询订单 → 检索制度 → 提交答案”执行，共三轮。若制度检索不依赖订单状态，就可以在第一轮并行查订单和通用规则，取得状态后筛选条款，第二轮提交答案。

轮数减少后，还要测量实际费用和延迟。单次输出长度、工具等待，以及模型能否在一轮中稳定提出这些可并行的工具请求，都会影响结果。

## 固定条件并逐例配对

一次比较尽量只改一个部分：换分块或 Embedding 时，保持文档、查询和标签范围可比；比较重排器时固定候选集，比较生成策略时固定证据包。其他条件也变了，就注明。

先看各阶段指标，判断哪一步有改善；再看完整任务结果，确认用户是否因此受益。

比较模型配置时，固定模型、工具与判据，记录用量和时间。同时换模型、Prompt 和检索，即使总分提高，也分不清哪项改动有效。

逐例配对能揭示“只新方案成功”和“只旧方案成功”的样本。独立业务任务数与同题重复次数也应分别报告；确定性脚本重复一百次，不会增加对真实模型能力的同等证据。

## 用回放隔离模型与执行器

固定模型回复后，重新运行执行器，可以检查协议和控制逻辑。固定工具返回值等外部输入后，再调用模型，可以观察它的决策是否改变。模型如果提出历史上没有的新请求，回放中可能没有对应结果；此时要记录缺口，不能补造成功结果。

诊断回放中的写动作交给隔离环境或替身工具，避免分析旧记录时再次提交真实业务操作。原始输入不能只靠哈希值重建，仍要保存原文或可读取的版本引用，并限制访问权限和保留期限。真实任务的恢复见[持久化执行与恢复](../09_工程化与系统设计/02_Durable与生产运维.md)。

## 发布标准与结论范围

比较前就写清最低质量、关键错误上限，以及可接受的延迟和成本，并区分硬性要求与可权衡指标。越权写入这类禁止行为一旦发生，平均分提高也不能抵消。

发布结论写清任务范围、样本量、失败案例和未测条件，不能把小样本改善推广到未测任务。开放回答用经过人工样本校准的 Judge 评分，分歧单独复核；实际动作以执行记录为准。

## 记录模型、数据与配置版本

同一份代码换了模型、Prompt、工具 Schema、数据索引、策略或状态结构，行为也可能变化。因此运行记录要保存这些版本，不能只记代码提交。

要复现这次比较，评测脚本和数据都需保留可取得的固定版本，并记录哈希值；依赖版本、安装方式和配置也要保存。

若要回退运行版本，还需核对旧状态兼容性和已发生的外部操作，并继续按当前授权与有效制度处理请求，见[持久化执行与恢复](../09_工程化与系统设计/02_Durable与生产运维.md)。

## 将线上失败补入回归集

把历史失败的任务条件、可用证据、首个偏差和修复依据保存下来，加入回归集。入库前核对来源、处理敏感信息；制度变化导致标签更新时，记下更新原因。

训练、调参与最终比较的数据需要区分。隐藏集被反复用于调整后，就不再代表完全未见任务；公开榜单也不能替代企业自身的权限、版本、表格和失败场景。
