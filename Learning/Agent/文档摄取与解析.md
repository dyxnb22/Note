# 文档摄取与解析

本文负责企业知识入库中的**解析与结构化**：把 PDF、Office、扫描件、表格和图片变成可治理的 DocumentVersion、可切分的正文和可校验的 Metadata。来源、权限、版本、删除与引用见 [知识系统](知识系统.md)；Chunk 之后的检索与生成见 [RAG](RAG.md)。

解析失败会让后续混合检索、Rerank 和评测全部失真。企业 RAG 的第一道门槛通常不是 Embedding，而是「正文是否忠实、表格是否可复原、低质量内容是否被拦在主索引外」。

## 1. 在流水线中的位置

```text
发现变化 → 拉取 → 病毒/类型/大小检查
  → 文档分类（数字件 / 扫描件 / 混合 / 结构化）
  → 解析路由
  → 版面还原与阅读顺序
  → 表格与对象抽取
  → 质量门禁
  → 标准化正文 + 定位 Metadata
  → 版本落库 → Chunk → 索引
```

每一步保留：原始文件 Hash、解析器名称与版本、页码/区域定位、置信度和失败原因。引用必须能回到原文位置；只有向量没有定位的 Chunk 不能进主索引。

## 2. 先分类，再选解析器

| 类型 | 典型信号 | 优先策略 |
|---|---|---|
| 数字 PDF / 可复制文本 | 抽取文本长度合理、字体对象存在 | 文本层抽取（如 PDF 文本 API），保留标题与阅读顺序 |
| 扫描件 / 图片页 | 几乎无文本层、整页是图像 | OCR 或版面 OCR；必要时多模态模型辅助 |
| 混合文档 | 部分页有文本、部分页是图 | 按页分流，不要整本走同一路径 |
| Office（docx/pptx/xlsx） | 结构化 XML/对象 | 原生解析；不要先转扫描 PDF 再 OCR |
| 纯表格 / 报表 | 网格、合并单元格、无框线表 | 表格专用路径；数值问答考虑 SQL/结构化工具 |

分类错误比模型差一点更致命：把扫描件当数字件会得到空正文；把复杂报表当普通段落会得到字段错位。

## 3. PDF 与版面常见坑

### 数字 PDF

- 双栏、三栏、页眉页脚、脚注会被线性抽取串行，导致「跨栏乱读」。
- 竖排、旋转页、水印层可能插入噪声字符。
- 嵌入字体缺失时，部分抽取器输出乱码或空白。
- 目录、页码、页眉重复出现会污染检索；应降权或剥离为 Metadata。

处理原则：优先恢复**阅读顺序**和**标题层级**，而不是追求「字符数最多」。保留 `page`、`bbox` 或段落路径，供引用和高亮。

### 扫描件与 OCR

- 模糊、倾斜、阴影、装订阴影、印章/水印会显著降低识别率。
- 中英混排、公式、上下标容易被拆成单字或错误语序。
- OCR 输出应带**字/行/块级置信度**；低置信度区域标记为 `needs_review`，不要静默入库。
- 同一文档多次 OCR 要固定引擎版本与预处理参数，否则版本不可复现。

准确率没有统一常数：清晰印刷件、良好扫描件、模糊件、手写件差异极大。生产口径应报告「在某质量分桶上的字段级/段落级正确率」，而不是笼统「OCR 95%」。

### Office 文档

- `docx`：段落、标题样式、表格、页眉页脚、批注与修订要分开处理；隐藏文本与批注默认不应进对外回答索引。
- `pptx`：幻灯片顺序、备注、说话人注释、图表替代文本；忽略备注会丢关键上下文。
- `xlsx`：优先保留 sheet、表头、主键列；大表不要整表塞进一个 Chunk。

## 4. 表格：最大结构损失源

表格是企业文档里最容易「看起来解析成功、语义已坏」的部分。

| 现象 | 后果 | 应对 |
|---|---|---|
| 合并单元格被拆成多个空格 | 字段对不齐，数值归属错误 | 表格模型 / 网格重建；保留 rowspan/colspan |
| 无框线表 | 工具当普通段落，列错位 | 线检测 + 对齐启发式；失败则人工复核 |
| 嵌套表 / 跨页表 | 通用解析器常截断 | 跨页拼接规则；复杂表隔离队列 |
| 表头在中间重复 | Chunk 丢失表头后无法理解列含义 | 切分时携带表头上下文或结构化行记录 |
| 图表当表 | 伪数字、伪行列 | 区分 image/chart 与 table；图表走多模态或人工 |

表格落地形态建议：

1. **结构保留**：JSON/CSV/Markdown 表，附 sheet/page/表标题。
2. **检索形态**：行级或「表头+行」小块进向量/词法索引；整表摘要另存。
3. **计算形态**：数值问答走结构化查询（SQL/API），不要只靠向量相似度回答金额、数量、日期。

规则：能当表的就不要只当散文；能当结构化工具的就不要逼 Embedding 做算术。

## 5. 结构化与半结构化知识

企业知识不全是非结构化长文。入库前要决定每种来源的**权威查询路径**：

```text
政策/手册长文     → 解析 → Chunk → 混合检索 → 生成
产品参数表/订单   → 结构化存储 → 工具/SQL/API
FAQ / 工单摘要    → 短文档 Chunk + 强 Metadata 过滤
混排报表          → 表格结构化 + 叙述段落分别入库
```

### 与向量检索的分工

| 问题类型 | 更合适的路径 |
|---|---|
| 「退货政策怎么说」 | 文档检索 + 引用 |
| 「SKU-123 的额定功率是多少」 | 结构化字段或精确词项 |
| 「上季度华东区 GMV」 | SQL / 指标服务，并校验权限与口径 |
| 「把这张表里异常的行找出来」 | 表结构 + 代码/分析工具，而不是整表 Embedding |

半结构化内容（表中有长说明列）可以：结构化主键过滤 + 说明列向量检索，二者用稳定业务 ID 对齐。

## 6. 多模态：入库 vs 调用

两件事不要混：

| | 入库索引 | 在线调用模型 |
|---|---|---|
| 目的 | 可检索、可引用、可权限过滤、可重建 | 理解当前页/图并回答 |
| 成本形态 | 批处理，可离线重跑 | 按请求计费，受延迟约束 |
| 典型做法 | OCR/版面解析成文本+定位；或存页面图像哈希与缩略图 | Vision/PDF 输入，或检索后再把相关页送给多模态模型 |
| 风险 | 解析丢信息 | 无权整页直喂、成本失控、难审计 |

选型建议：

- **可复制文本**：文本解析入库；不要为了「省事」整本每次 Vision。
- **关键图、印章、复杂版式页**：入库保留图像引用；问答时对召回页做多模态精读。
- **纯扫描库且要全库检索**：必须 OCR/版面链路；仅靠「每次上传给模型」无法做权限过滤与引用定位。
- **高敏文档**：默认不要把原件送给外部多模态 API；先脱敏或本地解析。

多模态调用细节见 [LLM 调用基础](01_LLM调用基础.md) 的 Vision/PDF 节；本文只规定它与摄取的边界。

## 7. 质量门禁与失败隔离

解析输出至少经过这些检查再进主索引：

1. **空/近空**：有效字符低于阈值 → 失败或转 OCR。
2. **乱码率**：替换字符、异常符号占比过高 → 隔离。
3. **OCR 置信度**：块级均值/分位数低于阈值 → `needs_review`。
4. **结构完整度**：标题层级断裂、表格列数剧烈抖动 → 降权或复核。
5. **定位能力**：无法映射回 page/region 的正文 → 不进入可引用主索引。
6. **敏感与注入**：隐藏文本、白字、文档内指令 → 清洗或拒绝。
7. **重复**：近重复文档/版本 → 合并或降权，避免检索被同一来源占满。

失败隔离队列应可运营：按来源、解析器版本、失败码聚合；允许人工修正后带着同一 `document_id` 发新 Version。**解析失败的文档不得静默进向量库**，否则线上会出现「库里有文件但永远召不回正确段」。

## 8. Chunk 前的标准化

解析成功后、切分前，统一：

- 编码、换行、全半角与空白；
- 标题路径（H1/H2… 或样式名）；
- 语言与文档类型标签；
- 权限/租户/密级（来自源系统，不是模型猜测）；
- 解析器版本与质量分数；
- 表格的结构化旁路存储指针。

切分策略仍以 [RAG](RAG.md) 为准：尊重标题、段落、函数、表格边界；Overlap 不能弥补错误的阅读顺序。

## 9. 观测指标

摄取侧至少看：

- 分类准确率（数字件/扫描件误判率）；
- 解析成功率、按失败码分布；
- 空文档率、乱码率、低置信度页占比；
- 表格结构校验通过率；
- 人工复核队列时长与回修率；
- 从原文到可检索版本的延迟；
- 解析器版本变更后的回归（固定样例集）。

回答错误时，排障顺序仍是：原文是否在库 → **解析正文是否完整** → Chunk → 权限过滤 → 召回 → 生成。

## 10. 验收清单

- 能否说明数字 PDF、扫描件、Office、表格各自的默认路径与失败表现？
- 低质量页是否有置信度门槛和不进主索引的规则？
- 表格能否保留行列语义，数值问题是否有结构化出口？
- 任一可引用 Chunk 能否回到 page/region 或等价定位？
- 多模态是「入库」还是「在线精读」，权限与成本边界是否写清？
- 解析器升级是否有固定样例回归？
