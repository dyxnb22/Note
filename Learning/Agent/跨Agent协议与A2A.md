# 跨 Agent 协议与 A2A

本文回答：**多个 Agent 或 Agent 产品如何跨进程/跨厂商协作**，以及和 MCP、多 Agent 编排的边界。进程内 Supervisor/团队模式见 [多 Agent 协作的边界与模式](多Agent协作的边界与模式.md)；工具协议见 [MCP 与工具协议](MCP与工具协议.md)。

> **学习位置**：这是协作专题的最后一篇；只有进程内编排无法满足发现、委托、取消或跨厂商边界时再学习。

## 1. 三个容易混的层

| 层 | 解决什么 | 典型形态 |
|---|---|---|
| 进程内多 Agent | 同一运行时里的角色分工与状态 | LangGraph Supervisor、mailbox |
| 工具协议（MCP） | 模型宿主如何发现/调用外部能力 | tools/list、tools/call |
| 跨 Agent 互联（如 A2A 一类） | Agent 作为网络上的对等服务互相委托任务 | Agent Card、任务消息、流式状态 |

MCP 让 **Client 调 Tool**；跨 Agent 协议让 **Agent 委托另一个 Agent**。不要用 MCP 硬模拟完整委托生命周期，也不要在没有稳定任务边界时引入互联协议。

## 2. 跨 Agent 协作需要的最小合同

无论具体标准名称如何演进，跨 Agent 委托至少要约定：

1. **身份与发现**：对端是谁、能力广告（Agent Card / 清单）、如何鉴权。
2. **任务消息**：目标、输入 Schema、优先级、截止时间、回调地址。
3. **状态机**：已接受 / 进行中 / 需输入 / 成功 / 失败 / 取消。
4. **流式进度**：可选的中间事件，避免长任务黑洞。
5. **取消与超时**：谁有权取消、超时后资源如何回收。
6. **数据边界**：哪些字段可出境、日志与追溯 ID。

没有状态机与取消语义的「HTTP 调另一个 Bot」只是临时集成，不是可运营的 Agent 互联。

## 3. 与 MCP、Workflow 怎么选

```text
只需调用确定性 API / 检索 / 沙箱
  → 工具或 MCP

固定业务流程、强一致状态
  → Workflow / 图编排（可含多角色节点）

需要把子目标交给另一个自主 Agent 产品
  → 跨 Agent 协议或明确的任务委托 API
```

同团队、同部署单元内，优先进程内编排：延迟低、观测统一、权限模型简单。跨团队、跨厂商、需要能力广告与独立扩缩时，再考虑互联协议。

## 4. 安全与治理

- 把对端 Agent 的输出一律视为**不可信内容**（等同检索文档与工具结果），防间接注入。
- 最小权限委托：只传完成子任务所需字段；禁止转发全部用户历史与密钥。
- 审批：对端发起的高风险动作不能绕过本方策略引擎。
- 供应链：能力卡片、端点与证书要有变更审计；不要信任任意公开注册表条目。
- 计费与配额：跨 Agent 调用要有独立预算，防止委托环路烧尽额度。

## 5. 失败模式

- **委托环**：A→B→A 无限派发 → 需要跳数、TTL、任务图去环。
- **语义漂移**：对端「完成」但未满足本方验收 → 要用可程序化验收，不只信自然语言 done。
- **状态分叉**：双方对取消理解不一致 → 以发起方状态机为准并双写审计。
- **发现污染**：能力广告夸大 → 运行时探测 + 合同测试。

## 6. 维护策略

协议名称、字段和传输会变。正文只保留上述不变量；具体 Schema、发现 endpoint 与版本以官方规范为准，并在 [版本与来源](版本与来源.md) 登记核对入口（若项目采用某一标准实现）。

## 决定跨产品委托前检查

如果进程内编排或普通任务 API 已经足够，就不引入跨 Agent 协议：

- 能否说清 MCP 与跨 Agent 委托的差别？
- 委托是否具备状态、取消、超时与追溯 ID？
- 对端输出是否按不可信输入处理？
- 是否有防环与预算？
