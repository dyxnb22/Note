# Agent 学习范围与面试题型

> 这是 Agent 知识库和面试准备的唯一范围入口。它只回答“要学什么、学到什么程度、去哪里看”，不复制正文实现。

## 1. 先确定范围，而不是先收集题目

公开的“大厂真题”大多来自候选人回忆、面经整理或培训资料，通常无法证明是官方题库，也会随岗位和时间变化。因此本目录采用两层证据：

1. 用官方工程资料确定技术边界和设计原则。
2. 用公开面经和系统设计题型发现追问方向，但不把某家公司的一道题当成稳定知识。

当前范围参考：

- [Anthropic：Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)：区分 Workflow 与 Agent，强调先用最简单、可组合的方案。
- [OpenAI：A practical guide to building AI agents](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/)：覆盖运行循环、退出条件、单 Agent、多 Agent、工具和 handoff。
- [Anthropic：Demystifying evals for AI agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)：把任务、试验、评分器、轨迹、结果和评测 Harness 作为完整评测对象。
- [公开的 Generative AI system design interview guide](https://igotanoffer.com/en/advice/generative-ai-system-design-interview)：归纳 RAG、工具、记忆、可靠性、安全、评测、监控、成本和系统设计追问；其中公司示例属于候选人报告汇总，不等同于官方题库。

结论很简单：面试准备不应再建立“阿里一套、腾讯一套、字节一套”的七条技术主线。大多数题目都可以归并到同一组 Agent 工程问题，再按目标岗位加一个场景分支。

## 2. 学习范围分层

### P0：所有 Agent 岗位都应掌握

P0 是共同语言和生产底线。不会这些内容，直接背 LangGraph、MCP 或多 Agent API 没有意义。

| Agent Loop | 模型决策、工具执行、结果回填、继续/结束如何形成状态转移？为什么必须有步数、时间和成本上限？ | [Agent 架构与设计](../03_Agent架构与设计.md) |

### P1：按岗位或项目选择一个主场景

P1 不是所有人都要完整通读。面试前至少选择一个与你经历一致的场景，并能从需求、数据、工具、权限、评测和上线完整讲通。

### P2：只有岗位明确要求时再学

GraphRAG、A2A、Computer Use、语音实时对话、模型训练/RLHF、推理内核、复杂搜索（ToT/GoT）、特定厂商平台和具体向量数据库 API 都属于 P2。它们可以成为加分项，但不应挤占 P0 的循环、工具、安全、评测和生产化时间。

## 3. 题型矩阵：把“大厂题”归并成九类

下面是面经中反复出现的题型边界。题目换业务名，通常仍在考同一个工程决策。

| 题型 | 典型问法 | 面试官真正想听什么 |
|---|---|---|
| 基础与边界 | Agent 和 Workflow 有什么区别？为什么不用普通 API？ | 任务不确定性、动态决策、可控性和复杂度取舍 |
| Agent 运行时 | 设计一个能自主完成任务的 Agent。 | Loop、状态、工具、终止、错误和证据，而不是只画一个 LLM 方框 |
| 工具与动作 | 工具怎么选？调用失败或重复执行怎么办？ | schema、路由、权限、超时、重试、幂等、补偿和审批 |
| Context / Memory | 上下文太长怎么办？记忆放哪里？ | 当前窗口与持久化分离、召回策略、压缩、过期和隐私 |
| RAG / 搜索 | 检索不准、幻觉、表格、权限和文档更新怎么处理？ | 数据质量、混合检索/重排、引用、权限前置、freshness 和评测 |
| 多 Agent / 编排 | 为什么拆多个 Agent？Supervisor 和 handoff 怎么选？ | 单 Agent 基线、拆分收益、协调成本、故障传播和回退 |
| 安全与合规 | 如何防 Prompt Injection？金融/企业 Agent 如何可控？ | 信任边界、最小权限、沙箱、敏感数据、审批、审计和拒答 |
| Eval / 观测 | 如何证明 Agent 变好了？线上出错怎么定位？ | 任务结果、轨迹、工具行为、trace、replay、离线回归和线上指标 |
| 系统设计 | 设计一个高并发、低延迟、低成本的 Agent 服务。 | 约束澄清、数据路径、可靠性、容量、降级、成本、安全和权衡 |

## 4. 面试前的最小题单

### P0 必答题

1. 什么时候用 Agent，什么时候用 Workflow 或普通函数链？
2. 画出一个最小 Agent Loop，并说明成功、失败、取消和预算耗尽如何结束。
3. Tool schema、参数校验、授权、执行和错误结果分别由哪一层负责？
4. 有副作用的工具如何做审批、超时、重试、幂等和补偿？
5. State、Context 和 Memory 的边界是什么？
6. 上下文窗口不够时如何压缩，如何避免把不可信内容当成指令？
7. 如何设计可恢复、可取消的长任务？
8. Agent 的安全边界在哪里，Prompt Injection 如何影响工具权限？
9. 如何评估一个 Agent：只看最终答案够不够？
10. 如何用 trace 和 replay 定位一次错误工具调用？
11. 如何同时控制 P95 延迟、Token 成本和任务成功率？
12. 单 Agent 什么时候拆成多 Agent？拆分后如何证明值得？
13. 从零设计一个生产 Agent，你会先问哪些需求和约束？

### P1 场景题

- 设计企业知识库 Agent：权限检索、引用、更新、删除、表格和多租户。
- 设计 Coding Agent：仓库导航、补丁、命令沙箱、测试、写后验证和恢复。
- 设计客服/订单 Agent：工具副作用、人工升级、SLA、限流、降级和审计。
- 设计大量工具的 Agent：工具发现、分组、路由、描述压缩和权限策略。
- 解释 MCP、Skill、Function Calling 和 LangGraph 的层次差异，并给出不用它们的理由。

## 5. 统一答题模板

系统设计题按下面顺序回答，能把零散知识压缩成一条可评估的链路：

1. **问题与约束**：用户、任务成功标准、数据敏感性、延迟/QPS/SLA、允许的副作用。
2. **最小基线**：先说明是否需要 Agent；能用确定性 Workflow 解决就不要默认动态循环。
3. **数据路径**：输入 → Context/检索 → 模型决策 → 工具执行 → 状态/Trace → 输出或审批。
4. **可靠性**：超时、重试、幂等、checkpoint、取消、降级和人工接管。
5. **安全**：信任边界、权限、沙箱、敏感信息、Prompt Injection 和审计。
6. **评测与上线**：离线样本、轨迹/结果指标、线上监控、灰度、回滚和事故闭环。
7. **取舍**：明确质量、延迟、成本、复杂度和可维护性之间的选择，并说明如何用实验验证。

同一套内容准备三种长度：2 分钟讲项目，10 分钟讲一个机制，45 分钟完成一次系统设计。不要为每家公司重新背一套答案。

## 6. 去重与学习验收规则

- 面试文档只保存范围、题型、答题结构和索引；定义、完整实现和参数细节回到唯一主文档。
- 先完成 P0，再选择一个 P1 场景；P2 只在岗位描述或真实项目需要时进入。
- 框架 API 题必须翻译成通用机制：State/Node/Edge 要能回到 Loop、状态和编排；MCP/Skill 要能回到工具发现、能力边界和渐进式披露。
- 代码示例至少说明权限、状态、预算、错误和副作用边界；语法不完整的协议示意使用 `text` 代码块，不伪装成可运行代码。
- 完成标准不是“看过所有文件”，而是：能实现一个最小可终止 Agent，能完成一个 P1 场景，能用指标和 trace 解释一次成功与一次失败。
