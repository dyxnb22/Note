# 04.1 Tool Calling、MCP 与 A2A

> 阅读顺序：先看工具提案、参数校验、授权、执行和结果配对，再处理失败与副作用，最后比较 MCP/A2A 的服务边界和协议版本。

安全策略以 [可靠性与安全](../07_可靠性与安全/可靠性与安全.md) 为主答案；协议标准字段要与宿主自行维护的治理元数据区分开。

## 基础认知：模型如何调用工具

### 1. Function Calling 的完整流程是什么？

答：应用把**工具名称、用途和参数 Schema** 提供给模型，模型返回**结构化的工具调用**；宿主解析、校验、授权并执行，再把带 `call_id` 的结果回填给模型，模型决定继续、换工具或结束。模型只提出动作建议，不直接执行代码。

**追问：没有 MCP 时，大模型如何调用工具？**

应用在本地注册工具并把 Schema 传给模型，其余仍是 ToolCall → 校验/授权/执行 → ToolResult → 继续 Loop。MCP 只是把发现和调用合同抽到可复用的 Server/Client 边界，没有改变这条执行逻辑。

### 2. Tool Calling 与普通函数调用有什么区别？

答：普通函数调用由程序确定函数和参数，Tool Calling 的函数选择和参数往往由模型提出，因此需要处理不确定性、Schema 错误、权限和提示注入。真正执行仍是普通代码，但外面多了一层模型提案和安全执行边界。

### 3. 工具 Schema 应该包含哪些字段？

答：模型可见的 `inputSchema` 描述必填/可选字段、类型、枚举和范围；协议支持时还可声明 `outputSchema`。Schema 约束数据结构，不授予调用权限；Registry 维护资源 Scope、风险、处理器、预算与错误合同，见题11。

以 MCP 为例，`inputSchema` 与可选的 `outputSchema` 有协议定义；业务权限、重试和审批策略不能只靠描述或 annotation 生效，需要服务端强制执行。[MCP Tools 规范](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)。

### 4. 工具 Description 应明确哪些执行影响和安全边界？

答：说明工具的读写/删除/发送等**副作用、资源范围、前置条件和返回含义**，不要把多个业务能力塞进一个含糊工具。Description 只帮助模型选择，不能授权执行；参数、权限和审批仍由服务端强制校验。适用/不适用条件的通用写法见 [Skill Description 题5](../02_Prompt与上下文/Prompt与Context%20Engineering.md#4-如何写出清晰可判别少歧义的-skill-description)。

### 5. 工具参数校验应该由模型、服务端还是两者共同完成？

答：**模型**通过 Schema 生成较合法的参数；**服务端独立校验**字段、类型、范围、资源权限和跨字段约束。结构合法不等于已授权；授权判断还要结合主体、租户、资源、操作和当前任务，见 [[Learning/Agent/07_可靠性与安全/身份治理与跨Agent#2. 一个授权判断至少应包含哪些维度？|身份治理题2]]。高风险操作还需复核资源版本并执行审批策略。

### 6. 工具结果如何重新放入模型上下文？

答：执行器返回与调用 ID 配对的结构化结果或稳定错误，适配器转成 Provider 要求的 tool result 消息，再由 Loop **追加到下一轮 Context**。结果应**限长、脱敏、标记来源**，并区分事实数据和外部文本。

### 7. 工具返回过大时如何截断、分页或摘要？

答：优先让工具支持**过滤、分页和字段选择**，避免先返回全量；仍过大时按**任务保留必要字段**、生成带引用的**摘要**，并提供继续读取的游标。摘要不能替代关键原始证据，必要时存对象并只把引用放进 Context。

### 8. 如何设计数据库查询、搜索、代码执行、发邮件和支付工具？

答：每类工具都要有最小权限、明确资源范围、输入/输出合同和副作用标记；数据库**优先参数化只读查询**，代码执行用**沙箱**，邮件/支付先**预览和审批**。Registry 还要声明工具的读写属性、可逆性和风险等级，供策略决定确认门槛；审批与补偿流程见 [[Learning/Agent/07_可靠性与安全/可靠性与安全#17. 如何让用户预览、确认、撤销和回滚 Agent 动作？|可靠性与安全第 17 题]]。高风险工具还要有**幂等键、对账和审计**。

## 原理机制：工具如何安全执行

### 9. 如何设计工具的超时、重试、熔断、降级、幂等和补偿？

答：每个工具声明超时、可重试错误和幂等能力；只对**暂时性且幂等的动作做指数退避和上限控制**，连续失败触发**熔断或降级**。副作用未知时**先查询状态，不直接重做**；不可逆操作准备人工对账或补偿流程。

**追问：什么操作必须幂等？如何生成幂等键？**

创建订单、发信、扣款、发布和写库等可能产生副作用的操作需要业务幂等；读取通常天然幂等，但仍要考虑时效和权限。幂等键组成及持久化要求见 [[Learning/Agent/09_工程化与系统设计/02_Durable与生产运维#4. 幂等键应该由哪些信息组成？|Durable 与生产运维题4]]。

**追问：工具调用如何避免重复执行外部副作用？**

执行前先用同一业务幂等键查询本地或下游状态；已成功则返回已存结果，确认未执行才继续，结果未知时先对账。持久化状态和未知结果的处置见 [[Learning/Agent/09_工程化与系统设计/02_Durable与生产运维#10. 如何处理“外部请求已经成功，但 Agent 没收到响应”的未知结果？|Durable 与生产运维题10]]。Loop 去重和 Prompt 提示不能代替业务侧幂等。
关联：[[#22. MCP 请求断开或取消后，如何确认执行状态？|题22]]

### 10. 如何校验工具结果，并防止它改变系统权限或状态？

答：把 Tool Result 视为观察值而非授权事实；校验调用 ID、来源身份、Schema、资源/版本、时间、完整性和截断状态，关键字段再用业务规则或权威查询核实。自由文本标记为不可信，不能改变系统指令、权限、预算或程序 State；证据不足时继续查证或请求人工，而不是直接执行副作用。

### 11. 如何做工具权限、配额、审计、版本和兼容性管理？

答：Registry 作为能力白名单，登记版本、Schema、动作/资源 Scope、副作用、风险、处理器、超时、输出上限和错误合同；运行时按 actor/tenant/task 动态过滤，入口与工具层共同限制配额/并发。每次调用记录版本、策略/审批决策、结果状态和耗时，Schema 变更进入回归和灰度。缺少策略、处理器或测试时应显式失败，不能落入宽泛默认分支。

### 12. 工具数量非常多时，如何做发现、分组、路由、动态加载和淘汰？

答：先按**领域、权限和风险建立目录**，首轮只向模型提供**小型候选集**；确定领域后，再动态加载详细 Schema。高频、低风险工具可缓存；长期不用或容易混淆的工具应淘汰或合并。MCP 工具增加时还要记录 Server/工具版本、身份授权、成功率、超时率、耗时、错误类型和成本。工具选择要用混淆矩阵和不必要调用率评估，不能把整个工具库都暴露给每个 Agent。

来源：[月之暗面 Agent 开发岗面经](https://www.nowcoder.com/discuss/930748911277309952)；[百度 AI Agent 开发岗面经-04](https://www.nowcoder.com/discuss/931706522621530112)。

### 13. 线上 Agent 选错工具，如何从候选集、Description、参数、上下文和模型分别排查？

答：Skill 误选的通用排查方法见 [[Learning/Agent/02_Prompt与上下文/Prompt与Context Engineering#25. 一个 Skill 经常被错误选择，你会先改 Description、路由器、上下文还是模型？为什么？|Prompt 与 Context Engineering 第 25 题]]。工具侧还要检查 Registry 提供的候选集和工具摘要；通常先缩小候选集或补齐字段，再考虑换更大的模型。

## 协议设计：MCP 如何组织能力

### 14. 什么是 MCP？它解决了什么问题？

答：MCP 是 Host/Client 与外部工具、资源和 Prompt Server 之间的**标准化发现与调用协议**，主要**解决跨应用复用和能力合同问题**。它不等于 Agent Loop，也不自动提供业务授权、可靠恢复或安全合规。

### 15. MCP 与 Function Calling、插件、REST API 有什么区别？

答：Function Calling 描述**一次模型到应用的动作提案**，REST API 是服务接口，MCP 规定 **Host 如何发现并调用跨进程/跨服务的工具**、资源和 Prompt，插件通常是产品层集成概念。MCP Server 返回的描述和结果**仍是不可信输入**，Host 必须保留权限与执行控制。

### 16. MCP Server 如何设计？工具、资源和 Prompt 如何组织？

答：Server 声明**能力和版本**，Tools 表示可**执行动作**，Resources 表示**可读取资源**，Prompts 表示**可复用模板**；每项都要有 Schema、错误语义、权限边界和版本。Host 根据任务、用户和策略筛选可见能力，**不能把 `list` 当成全部允许使用**。

### 17. MCP 工具的入参、出参、错误码和版本如何定义？

答：入参用**可验证 Schema 和资源范围**，出参**区分结构化数据、文本和外部来源**，错误码**区分参数、权限、超时、依赖和未知结果**；工具 ID 与 Schema 版本稳定可追踪。**兼容升级应支持旧客户端或明确拒绝并可回滚**。

### 18. MCP 有什么优点和短板？

答：优点是能力发现、跨 Host 复用、协议边界统一和独立部署；短板是**增加网络/进程、认证、版本、供应链、延迟和治理复杂度**，且不替代业务权限、Eval 和 Durable Execution。**单应用内部函数优先直接 Tool Calling**。

### 19. SSE 与 Streamable HTTP 有什么区别？

答：SSE 是 HTTP 上传递服务端事件的编码/流机制；MCP 的 Streamable HTTP 是协议传输方式，可以使用 SSE 承载一次请求的通知和响应。两者不在同一抽象层，不能只按“是否流式”对比。

截至 2026-10-16，官方 2026-07-28 规范以 POST 请求为基础，响应可为 JSON 或请求范围内的 SSE；已移除旧的 GET 流端点和协议级 session。2025 系列规范与旧 HTTP+SSE 的行为不同，接入时必须固定协议版本并核对 SDK 支持，不能照搬旧版会话与续传代码。[当前版本传输规范](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)。

### 20. MCP 返回结果如何流式传递？

答：先分进度通知与最终工具结果。客户端可以提供 `progressToken`，服务端按该请求发送进度；最终响应仍需按工具结果合同结束并校验。使用 SSE 传输不意味着 `tools/call` 自动提供任意 Token 或正文增量接口。

用户可见进度、模型输出增量、MCP 通知与最终结构化结果分别建模。客户端处理关联、限流、结束与失败状态，再决定哪些结果进入下一轮 Context。[MCP Progress](https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/progress)。

### 21. MCP 如何处理认证、权限、租户隔离和审计？

答：连接时验证 Client 身份并映射 actor/tenant Scope；每次调用都由服务端校验资源与操作权限。异步 Worker 只接收完成任务所需的最小 Scope，并在执行前重新校验。审计记录能力发现、调用、拒绝、审批和结果；长期用户 Token 不进入模型 Context。

通用授权维度见 [[Learning/Agent/07_可靠性与安全/身份治理与跨Agent#2. 一个授权判断至少应包含哪些维度？|身份治理题2]]，最小权限和租户隔离见 [[Learning/Agent/07_可靠性与安全/可靠性与安全#10. 如何设计最小权限、凭证隔离、租户隔离和网络隔离？|可靠性与安全题10]]。

### 22. MCP 请求断开或取消后，如何确认执行状态？

答：客户端和执行端都应设置期限，但“停止等待”“停止后续工作”和“撤销已发生的业务副作用”是三件事。

MCP 的取消语义取决于协商的协议版本和传输。Streamable HTTP 可通过关闭该请求的 SSE 响应表示取消；不能假设所有传输都发送同一种通知。

断流不证明 Tool 未执行，服务端仍要保留权威最终状态。未知结果的通用处置见 [[Learning/Agent/09_工程化与系统设计/02_Durable与生产运维#10. 如何处理“外部请求已经成功，但 Agent 没收到响应”的未知结果？|Durable 与生产运维题10]]；MCP 传输差异见题19及规范。

## 设计取舍：协议如何选，系统如何落地

### 23. 什么时候用 API，什么时候用 MCP，什么时候让一个 Agent 调另一个 Agent？

答：API/内部函数是单业务调用接口；只有一个应用、合同稳定时优先，最简单可控。MCP 是跨 Host 发现和调用 Tool、Resource、Prompt 的协议；多个 Host 需要复用能力时才值得引入。A2A/Task API 是 Agent 间委派有状态任务的合同，适合跨系统发现能力并跟踪任务。A2A 要定义身份与租户 Scope、目标、允许工具、预算、进度/取消、超时和结果验收；这些协议都不授予权限或决定自主性，Host 仍负责 Loop、策略和停止。

### 24. 如何设计跨团队、跨语言、跨供应商的工具协议？

答：先定义与语言/SDK 无关的**输入输出、错误、权限、版本、幂等、超时和审计合同**，**再用适配器接入各实现**；所有外部结果都带来源和可追溯 ID。兼容性用契约测试、版本协商和灰度验证，不依赖某个框架的内部对象。

### 25. 如何保证协议升级时的向后兼容？

答：采用新增可选字段和能力协商，保留旧版本解析及错误语义；重大变化做契约测试、双读/双写、灰度和回滚。工具版本合同还要覆盖 Schema、权限和副作用语义，并用旧调用回归；Trace 记录协议/工具版本。运行中的旧任务应明确继续、暂停或迁移，不能静默套用新语义。

### 26. 设计一个支持并行工具调用、取消、重试、审计和回放的工具执行器。

答：执行器接收带任务/调用 ID 的 ToolCall，先做 allowlist、Schema、授权和预算检查，再按依赖图调度。只并行执行彼此独立、没有冲突的只读任务。同一资源上的写操作应串行；确需并发时，使用单写者、事务或版本校验，并通过确定性规则合并结果。每个调用都要有独立超时、取消令牌、幂等键和持久状态；结果统一标记为成功、失败或未知。Trace 记录依赖、顺序、版本和安全摘要，回放使用冻结 Fixture，避免重复真实副作用。

## 进阶机制：能力与权限

### 27. 什么是“能力”和“权限”的区别？

答：能力表示系统“可以做什么”；权限判断当前主体能否对特定资源执行某项操作。向模型暴露工具不等于授权。授权判断维度见 [[Learning/Agent/07_可靠性与安全/身份治理与跨Agent#2. 一个授权判断至少应包含哪些维度？|身份治理题2]]。

## 执行机制：从提案到确定性执行

### 28. 工具执行流水线应该经过哪些阶段？

答：所有工具入口都应经过同一执行通道，避免读、写和命令入口形成授权或审计绕过。流程依次为 Registry 查找、Schema 校验、采集当前事实、策略判断与审批、复核资源版本/摘要、执行并记录证据；任一阶段失败都返回结构化结果。参数校验见题5，Registry 治理见题11。

**追问：为什么原始模型 JSON 不能直接交给执行器？**

原始 JSON 只表达模型想做什么，不证明参数合法、资源仍存在、权限允许或审批仍有效。系统应把它解析为受限 DTO，收集当前事实，完成策略和版本检查，最后生成只包含程序确认字段的内部执行命令。

**追问：高风险工具的审批应该绑定什么？**

绑定主体、工具及版本、规范化参数、资源范围、预览摘要、目标当前版本、有效期和一次性消费状态。只绑定“允许编辑这个文件”过于宽泛，因为审批后参数、内容或目标版本可能已变化。

**追问：什么是审批与执行之间的 TOCTOU 风险？**

审批基于某个时间点看到的资源状态，执行前资源可能已被其他主体修改。应绑定版本/摘要并在执行前比较；发生变化时使审批失效并失败关闭。

**追问：为什么“预览—审批—执行”不等于事务？**

预览只是计划，审批只是授权，执行仍可能中途失败或被进程终止。单文件可用原子替换；多文件要记录逐项效果并设计恢复；跨外部系统依赖幂等、对账和补偿。审批与回滚的产品化设计见 [[Learning/Agent/07_可靠性与安全/可靠性与安全#17. 如何让用户预览、确认、撤销和回滚 Agent 动作？|可靠性与安全第 17 题]]。

### 29. 为什么工具错误应作为 Tool Result 返回，而不是直接抛给模型或用户？

答：参数错误可反馈修正，权限错误应停止，暂时性故障按策略重试，未知副作用进入恢复；统一返回带调用 ID 的结构化错误，让上层按类型处理。**原始异常可能泄露路径、凭证或供应商细节**，应在边界处映射和截断。错误分类主答案见 [[Learning/Agent/07_可靠性与安全/可靠性与安全#27. 工具错误应该如何分类并决定处理或重试？|可靠性与安全题27]]。

### 30. 如何设计一个最小可审计的 Tool Call 记录？

答：记录任务/调用 ID、工具和版本、规范化参数摘要、主体与权限 Scope、事实版本、策略结果、审批结果、开始/结束时间、结果类别和证据引用。敏感参数应脱敏或受控存储，日志本身不能成为绕过权限的第二执行入口。
