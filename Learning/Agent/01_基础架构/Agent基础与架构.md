# 01.1 Agent 基础与架构

本页建立 Agent 的任务边界与最小执行链。先掌握定义、模型/代码分工、继续与停止、成功证据和预算，再进入 [Loop 与 Harness](./Loop控制与Harness.md)；多 Agent 拆分与生产恢复分别在 05、09 展开。

## 基础认知：是什么，为什么需要

### 1. 什么是 Agent？与普通 LLM Chat、Workflow、RPA 和传统后端服务有什么区别？

答：Agent 在目标和授权范围内，根据模型决策与环境反馈动态选择后续动作；宿主负责状态、工具执行、验证和停止。区别主要在控制流和执行方式，而不是“能否调用工具”。

| 范式 | 主要控制方式 | 工具与执行 | 适合的任务边界 |
|---|---|---|---|
| Agent | 模型根据中间结果动态选择路径 | 经宿主校验和授权后调用工具 | 路径难预先枚举，但目标和完成条件可描述 |
| 普通 LLM Chat | 以对话生成回复 | 纯文本聊天可以没有工具；接入工具后也可演化为 Agent | 问答、解释、内容生成 |
| Workflow | 代码定义主要节点、分支与循环 | 可以编排模型、工具和人工步骤 | 路径相对稳定，强调可预测性与验收 |
| RPA | 预设规则驱动界面或业务操作 | GUI、脚本和服务接口 | 重复操作；也可与模型判断结合 |
| 传统后端服务 | 代码与业务规则控制 | 数据库、消息、API 等 | 明确的数据与业务合同 |

这些范式可以组合。Workflow 中可以嵌入受限 Agent，传统服务也可以承载 Agent Runtime。[选型参考](https://www.anthropic.com/engineering/building-effective-agents)。

### 2. Agent 的执行流程是什么

答：**解析目标和权限** → 加载 Context/Memory → 模型根据当前 State 选择直接回答、规划或调用工具 → **校验/授权**（代码层强制检查权限、参数合法性和副作用范围） → **执行工具** → 结果回填 State → **业务验证器判断是否有成功证据**（如数据库状态、测试结果或字段约束） → 验收通过后，经格式和安全校验再返回用户；未通过则携带新 State 进入下一轮。

整个循环还必须设置**预算上限**（步数、Token、时间、费用）和**明确的停止原因**（成功、取消、权限拒绝、无进展或预算耗尽），否则模型调用可能无限循环。

### 3. Agent 的自主性体现在哪里？什么场景该用 Agent，什么场景该用 Workflow？

答：

**自主性体现：**

| 维度 | 说明 |
|------|------|
| 任务分解 | 把目标拆成子步骤 |
| 路径选择 | 根据中间结果决定下一步 |
| 工具选择 | 从候选工具中挑选合适的 |
| 重规划 | 根据观察结果调整计划 |

**但不是越强越好——选型对比：**

| 维度 | Workflow | Agent |
|------|----------|-------|
| 决策方式 | 节点、顺序、分支由代码确定 | 路径由模型根据状态动态选择 |
| 可预测性 | 可预测、易测试 | 灵活但不确定 |
| 适用场景 | 步骤固定、输入输出稳定、合规要求高 | 目标明确但路径取决于检索、工具结果或环境反馈 |
| 控制手段 | 代码控制 | 规则、审批、硬预算 |

**演进原则：** 先做 Workflow 基线，**只有动态性带来可测量的成功率或覆盖率收益时才引入 Agent**。高风险、有副作用或路径稳定的任务应减少自由度，用规则、审批和硬预算换取可控性。生产系统常用 Workflow 负责骨架、Agent 负责局部决策，并为动态部分加硬约束。

### 4. Agent 系统中哪些部分应该由模型决定，哪些部分应该由代码决定？

答：模型适合做意图理解、候选计划、工具选择和自然语言生成；代码应负责权限、参数校验、状态持久化、预算、幂等、沙箱、成功判定和审计。不可逆副作用的执行和安全边界的判断，都不能只依赖 Prompt。

### 5. Agent Framework、Agent Runtime 和 Agent Application 有什么区别？

答：Framework 是开发时使用的抽象和组件；Runtime 是实际推进循环、调度工具、保存状态和处理恢复的运行机制；Application 是面向具体用户的目标、领域规则、数据、工具和交互。一个框架可以同时提供 Runtime 能力，也可以手写 Runtime；三者是职责边界，不必分别对应三个产品或服务。

### 6. 如何从 Demo 演进到生产级 Agent？

答：

**第一步：固定合同与指标**

| 合同类型 | 说明 |
|---------|------|
| 任务合同 | 明确输入、输出、成功标准 |
| 工具合同 | 每个工具的 Schema、权限和错误语义 |
| 状态 Schema | State/Checkpoint 版本化 |

**第二步：补工程能力**

| 能力 | 说明 |
|------|------|
| 权限与身份 | 真实 actor、tenant 级别控制 |
| 预算 | 步数、Token、费用、超时 |
| 持久化/Checkpoint | 状态、副作用、恢复点 |
| 失败恢复 | 错误分类、重试、降级、对账 |
| Trace | 每轮输入/输出/决策/工具结果 |
| Eval | 任务成功率、安全、长尾 |
| 限流 + 灰度 | 并发上限、按用户/任务灰度 |
| 回滚 | 版本化 Prompt/模型/工具/数据/策略，可回退 |

**核心原则：** 生产化的关键不是加更多 Agent 或堆框架，而是让每次运行**可控、可解释、可恢复和可回滚**。每一步都用任务成功和安全指标验证。

### 7. Agent 系统最重要的设计部分是什么？

答：最重要的是把模型的开放式决策放在一个可验证的执行边界内：明确 State、工具权限、终止条件和成功证据。架构图上少画一个 Agent，通常比没有边界地增加 Agent 更可靠。

## 原理机制：如何运行，如何结束

### 8. ReAct 是什么？Reasoning、Action、Observation 如何循环？

答：ReAct 把任务拆成“根据当前信息判断下一步 → 执行动作 → 观察结果”的循环，直到得到答案或触发停止条件。工程实现中不需要暴露模型的私有思维链，只需记录可审计的动作、工具结果、状态变化和停止原因。

### 9. Agent Loop 在什么条件下继续执行、什么条件下结束？

答：只有候选工具调用合法、依赖满足且预算允许时才继续。只有验证器或受信工具给出符合业务验收条件的客观证据时才以成功结束，例如数据库状态、测试结果、引用覆盖或业务字段；模型文本不能独立证明任务完成。取消、权限拒绝、不可恢复错误、无进展和预算耗尽等以明确 StopReason 停止或失败，不能用模糊的 `done` 覆盖不同结果。

### 10. Plan-and-Execute 与 ReAct 有什么区别？

答：ReAct 每轮根据最新观察决定下一步，灵活但可能反复探索；Plan-and-Execute 先生成可检查的任务计划，再逐步执行，适合步骤较多且可拆分的任务。计划必须允许失效和局部重规划，不能把初始计划当成事实。

### 11. Reflection、Critic、Self-Consistency 分别解决什么问题？

答：Reflection 让系统对结果或过程进行复盘，Critic 负责按标准找问题，Self-Consistency 通过多次候选和聚合提高部分推理任务的稳定性。它们都会增加调用成本，只有存在可操作的验证标准时才值得使用。

### 12. Router 模式是什么？如何设计路由条件和兜底分支？

答：Router 先判断请求属于哪个领域、复杂度或风险等级，再进入专用 Workflow/Agent。路由条件应尽量可评测，设置低置信度兜底、人工转接和未知类别分支，避免错误路由后继续自动执行高风险动作。

### 13. 如何避免每一步重新规划导致路径震荡？

答：把稳定的计划和已完成事实写入 State，只有触发事件或前提变化时才重规划；给计划版本、重规划次数和无进展次数设置上限。还可以让 Planner 输出变更原因，检测来回切换的路线。

### 14. 如何避免 Agent 重复调用同一个工具？如何检测无进展循环？

答：

**防重复机制：**

| 措施 | 说明 |
|------|------|
| State/Trace 记录 | 保存工具调用摘要、参数哈希、结果和副作用状态 |
| 幂等键 | 执行器对有副作用操作强制幂等键 |
| 缓存策略 | 只读查询可短缓存，但不能用缓存替代权限检查 |

**检测手段：**

| 指纹维度 | 说明 |
|---------|------|
| 工具名 + 规范化参数 | 比对是否重复相同调用 |
| 返回摘要 | 比对是否没有新事实 |
| State 版本 | 比对状态是否没有推进 |
| 任务距离 | 比对目标是否没有靠近 |

同时设置**轮数、时间、Token 和同类调用预算**作为安全上限。

**触发后处理：** 要求改变策略、缩小问题、换工具、转人工或结束；把"无进展"作为独立 StopReason 和回归样本，而不是无限追加"请继续尝试"。

多 Agent 场景下的重复劳动、循环调用和责任不清问题见 [[Learning/Agent/05_Multi-Agent与Workflow/Multi-Agent与Workflow|Multi-Agent 与 Workflow]]。

---

**追问：长任务如何避免死循环、重复计划和无效重试？**

维护已执行动作和进展指标，设置最大步数/时间/Token/费用、重复调用和无进展检测；重试只针对可恢复、可幂等错误。计划变化需有原因，超过阈值就降级、请求用户或转人工。

关联：[[Learning/Agent/05_Multi-Agent与Workflow/Multi-Agent与Workflow#7. 如何避免多 Agent 之间重复劳动、循环调用和责任不清？|Multi-Agent 与 Workflow题7]]

### 15. 如何处理计划执行到一半发现前提不成立的情况？

答：先把失败事实写入 State，判断是可修正参数、需要补充信息、需要换路径还是任务不可行；只对可恢复部分局部重规划。已经发生的外部副作用要先对账，不能为了让计划“看起来完成”直接重复执行。

### 16. 长任务应该一次性规划还是边执行边规划？为什么？

答：通常采用分阶段规划：先得到粗粒度计划，执行到检查点后根据事实细化。一次性计划容易被环境变化打破，完全逐步规划又会增加调用和震荡；分阶段方式更容易控制成本、恢复和审计。

### 17. 如何为 Agent 设置最大步数、超时、Token 和成本预算？

答：

**预算维度（任务级 State 维护）：**

| 预算类型 | 说明 |
|---------|------|
| 步数 | 最大工具/模型调用轮数 |
| 墙钟时间 | 最大运行时长 |
| 输入/输出 Token | 分别限制输入和生成量 |
| 估算费用 | 按模型单价计算上限 |
| 并发额度 | 同时执行的工具调用数 |

**检查机制：** 每次模型或工具调用前**预扣/检查预算**，子任务不能绕过父任务额度；不同任务类型可有不同上限。

**停止后处理：** 达到阈值就进入明确的 `stopped` / `budget_exhausted` 状态，**保存可解释的部分结果**，不要静默截断；可降级或转人工接管。

## 设计取舍：如何选型，如何拆分

### 18. 多 Agent 拆分的依据是什么？如何决定任务边界？

答：拆分前看五项：目标是否独立、工具权限是否不同、数据域是否天然分区、结果能否独立验收、任务是否可并行。子 Agent 还应有单一职责、独立错误语义和可测试结果，避免按步骤机械拆分。

从 Workflow/单 Agent 基线引入多 Agent 的演进判据及子任务运行时设计，见 [[Learning/Agent/05_Multi-Agent与Workflow/Multi-Agent与Workflow|Multi-Agent 与 Workflow]]。

### 19. 如何设计一个客服 Agent、搜索 Agent、数据分析 Agent 或代码 Agent？

答：先定义任务成功证据和不能做的事，再设计**最小工具集、状态、权限和人工接管点**；随后补检索/执行环境、验证器、Trace、Eval 和预算。不同产品的区别主要在工具和风险边界，不在是否画成多个 Agent。

### 20. 如果让你从零设计一个企业级 Agent 平台，模块如何拆分？

答：至少包括请求入口与身份、模型适配、Context/Memory、编排 Runtime、Tool Gateway、策略/审批、状态与任务队列、Trace/Eval、配置版本和运营后台。平台层提供通用约束，业务层只声明任务、工具和验收标准，避免把权限逻辑散落在 Prompt 中。平台运行时/网关/容量视角见 [[Learning/Agent/09_工程化与系统设计/01_生产工程与系统设计|生产工程与系统设计]]。

### 21. 为什么长任务不能只靠一次 Agent Loop 持续运行？

答：问题不在于 `while` 本身，而在于上下文、进程寿命和外部副作用需要分别管理。

- **模型输入**：不压缩历史时，工具调用与观察持续增加输入，可能超过窗口或引入噪声。若第 i 轮输入约为 `L0 + (i-1)Δ`，n 轮累计输入为 `nL0 + Δn(n-1)/2`；不能一概说累计成本随轮数线性增长。实际费用和延迟还取决于缓存、输出量与服务调度。
- **运行寿命**：审批、排队、部署、进程崩溃和网络中断都可能跨过当前连接与 Worker 的寿命；内存中的循环变量不足以恢复。
- **恢复语义**：需要持久化任务状态、Checkpoint、事件和副作用记录，由调度器接管。恢复前检查所有权、版本和外部事实，再决定继续、跳过、对账或人工处理。

实现主线见 [[Learning/Agent/09_工程化与系统设计/02_Durable与生产运维|Durable 与生产运维]]。

### 22. 如何处理 Agent 运行中模型、工具、数据库或网络故障？

答：错误分类和单次调用的处置见 [[Learning/Agent/07_可靠性与安全/可靠性与安全#27. 工具错误应该如何分类并决定处理或重试？|可靠性与安全题27]]。系统层用超时、熔断和依赖隔离限制故障传播，用健康检查发现不可用依赖，并设置总重试预算；必要时切换兼容 Provider，或降级为只读/固定流程。

任务状态和未知副作用的恢复见 [[Learning/Agent/09_工程化与系统设计/02_Durable与生产运维#10. 如何处理“外部请求已经成功，但 Agent 没收到响应”的未知结果？|Durable 与生产运维题10]]。恢复后继续原任务，并向用户说明进度，避免重复提交。

### 23. Agent 如何进行模型路由和多模型 Fallback？

答：

**路由依据：**

| 维度 | 说明 |
|------|------|
| 任务类型/能力 | 代码、推理、对话、长文本等 |
| 复杂度 | 简单问答 vs 多步规划 |
| 隐私 | 数据能否出境/调用外部模型 |
| 延迟 | 实时交互 vs 离线批处理 |
| 成本/预算 | Token 单价和总额限制 |
| 工具调用能力 | 是否支持结构化 Tool Call |

**适配层：** 给每个模型定义可接受的输入输出合同，适配器统一消息/工具/错误格式。

**Fallback 原则：**
- Fallback 仅切换到合同兼容的模型；原请求结果未知时，先查状态或对账，不要直接重发。
- 记录版本、重试次数和结果差异
- 避免不同模型产生不兼容的工具参数或安全行为
- 重试要考虑副作用

**上线前验证：** 对每个模型跑同一套工具选择、结构化、安全和长尾评测。

---

**追问：如何在质量、延迟、并发和成本之间做取舍？**

把任务按复杂度和风险分级，简单任务用轻量模型/Workflow，复杂任务增加检索、工具或更强模型；同时设置质量下限、安全门槛和 P95/预算上限。用分桶实验确认节省没有来自漏做验证或降低成功标准。

---

**追问：如何为高质量模型、低成本模型和专用模型设计路由与 Fallback？**

定义能力标签、最大 Context/工具支持、延迟/成本和安全等级，先按任务风险和复杂度路由；Fallback 只能去到合同兼容且预算允许的模型，并在结果上做同样验证。记录路由命中、失败原因和效果差异，避免低成本模型被迫承担不适合的任务。

### 24. Agent 如何接入已有业务系统而不破坏原有流程？

答：从只读、可回放的旁路能力开始，通过适配层复用现有 API 和权限，不让模型直接访问数据库；高风险写操作先预览/审批，再逐步灰度。上线前定义回滚、对账、审计和人工接管，确保 Agent 失败不会改变核心业务事实。

### 25. 如何从业务目标反推 Agent 的能力边界和成功标准？

答：把业务目标拆成用户任务、可观察结果、允许的副作用、错误成本和人工兜底，再决定模型能做哪些决策、工具能执行哪些动作。成功标准要同时包含任务结果、时间/成本、错误率、安全和用户接管率。
