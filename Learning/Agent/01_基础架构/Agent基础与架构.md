# 01.1 Agent 基础与架构

## 根据反馈选择下一步

Agent 接收目标后，根据当前信息选择下一步：查资料、调用工具，或向用户澄清。应用程序检查动作能否执行，保存结果，并决定什么时候停止。这里的“自主”，指在已授权范围内选择动作。

| 控制方式 | 路径如何决定 | 典型用途 |
|---|---|---|
| 单次 LLM 调用 | 一次输入得到一次输出 | 改写、分类、提取 |
| Workflow | 代码预先定义主要路径和分支 | 稳定业务流程 |
| Agent | 模型依据反馈选择后续动作 | 路径事先难以完整枚举的任务 |
| RPA | 脚本或规则驱动界面操作 | 稳定重复操作 |

Agent 可以调用 RPA 工具，Workflow 也可以包含受限 Agent 节点。判断属于哪种控制方式，要看后续路径由谁决定、新反馈能否改变路径。

## 同一个问题的三种控制方式

用户问：“帮我查清订单 B 一直没到的原因，并告诉我下一步。”回答需要订单状态、最新物流记录、承诺送达时间和处理规则。这些事实可以提前一次取齐，也可以按查询结果逐步取得：

| 实现 | 事实怎样取得 | 谁决定后续路径 | 模型主要承担的工作 |
|---|---|---|---|
| 一次 LLM 调用 | 应用先取得所需订单与物流记录 | 应用预先确定查询集合 | 根据完整事实组织解释 |
| 固定 Workflow | 按订单状态进入预定义分支 | 代码，例如已发货再查物流 | 解释节点结果或处理受限分类 |
| Agent 闭环 | 逐步查询，读取观察后选择下一动作 | 模型提出候选，运行时检查并执行 | 判断证据缺口、选择查询或澄清 |

如果订单服务和物流接口已经能够覆盖全部情况，固定流程通常就能完成目标。遇到“订单来自不同渠道、返回记录不完整、还需要用户说明收货情况”等变化时，动态决策可以根据新情况补充查询，但也会增加调用轮次和结果检查的成本。

## 观察、动作和下一轮输入

[ReAct](https://arxiv.org/abs/2210.03629) 常用来描述推理与动作交替推进的思路。工程里主要记录三件事：模型提出了什么动作，工具返回了什么，下一步选了什么，无需读取或记录模型的隐藏思维链。

一次工具调用至少涉及三条不同记录：模型要求做什么，程序实际执行了什么，以及外部系统返回了什么。调用 ID 把这些记录配对，避免多个并行结果回填到错误请求。下表先用“只查订单 B 是否发货”这个简化任务说明两轮交互。

| 轮次 | 当前观察 | 决策 | 新增事实 |
|---|---|---|---|
| 第一轮 | 尚未取得订单结果 | 查询订单 B | 工具返回 shipped |
| 第二轮 | 已有可信状态 | 根据结果回答 | 无；沿用第一轮结果 |

第二轮直接使用第一轮查到的 shipped，不必猜测订单状态。执行器怎样检查这次查询，见[工具调用](../04_Tool与协议/Tool%20Calling与MCP.md)。

## 查询结果怎样推进任务

沿用订单 B 的问题，假设订单服务返回“已发货”，物流记录显示仍在转运且尚未超过承诺时间。随着查询推进，未知信息逐渐减少：

| 时点 | 已知事实 | 下一步解决的信息缺口 | 保留下来的结果 |
|---|---|---|---|
| 收到问题 | 用户关心 B 尚未送达 | B 是否发货 | 目标与订单号 |
| 查询订单后 | 已发货，取得物流单号和承诺时间 | 最近物流进度 | 订单结果及调用引用 |
| 查询物流后 | 仍在转运，未超过承诺时间 | 是否已足够回答 | 物流记录与更新时间 |
| 组织回答后 | 当前证据覆盖状态与时效 | 回答是否准确反映这些事实 | 拟好的答案，以及每条结论对应的来源 |

工具结果经执行器整理后，Context Builder 选出下一轮要用的字段。模型取得物流记录后，可以回答“当前仍在转运，尚未超过承诺时间”，并说明后续怎样查询。若记录解释不了未送达的原因，就还需要补查。

订单状态、物流状态和规则分别来自不同来源。将它们按调用 ID 与时间保存，后续可以补充解释或核查，而不必每轮重新从整段对话猜测当前事实。

## 计划与执行的分工

Plan-and-Execute 先把任务列成计划，再逐步执行。计划可以由规则、模型或两者共同生成。每一步开始前，运行时检查输入是否齐全、依赖的上一步是否完成，以及现在能否执行；结束后验证结果，通过才标为完成。

环境变化后，保留已验证结果，只修改尚未执行或已经失效的部分。例如查询发现订单已签收，原先“取消订单”的路径就不再适用，不能为了完成旧计划继续执行。

短任务可以逐步决策，长任务通常先列主要阶段，再随进展细化。计划过细容易过时，完全不做计划又可能反复搜索；能确定的步骤先列清，依赖新信息的步骤留到查询后决定。

## 停止原因与任务成功

模型可能提出工具请求、给出候选答案，也可能被服务拒绝或因长度限制而截断。运行时还可能因用户取消、无进展、超时或费用耗尽而停止。记录停止原因时，要同时保存任务是否成功，便于分清“已经回答完”和“无法继续回答”。

成功条件来自任务要求。例如，“查询状态”需要取得目标资源的可信查询结果；“生成报告”还要检查有没有回答用户要求的问题、引用是否支持结论、最终文件能否正常打开。依据不足时，可以结束并交付部分结果，但要说明哪些要求尚未满足，并记录相应的任务状态。

重复的工具名和参数可作为无进展信号，但重复本身未必错误：轮询等待状态变化就是合法用途。检测还要结合结果版本、允许等待时间和实际进展。

## 从简单循环到完整运行时

几个局部变量足以支撑短循环。需要中断后继续时，就要把目标、进度和调用记录保存下来，具体见[运行时机制与状态流转](运行时机制与状态流转.md)。

## 预算与架构复杂度

调用次数、输入输出 Token、用时、费用和并发可以分别设限。子任务共享父任务的总额度；调用前怎样预留、调用后怎样结算，见[运行时状态流转](运行时机制与状态流转.md)。费用预估应留余量，并设定中止条件。

短任务可以使用普通循环；需要审批等待、并发分支或跨进程恢复时，再引入状态机、队列与持久化。拆分多个 Agent 前，还应估算上下文传递、协调和验收成本，确认各子任务值得独立运行。

接入既有业务系统时，通常可以沿用已有身份、API 和规则，让 Agent 作为新的调用入口。
