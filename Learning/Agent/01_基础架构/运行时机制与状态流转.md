# 01.3 运行时机制与状态流转

运行时接收模型提案，执行工具，把结果交回模型。每轮读取已有事实和预算，结束时保存消息、结果和新状态；下一轮从这些记录继续。

[订单查询完整案例](../案例_订单查询Agent.md#三轮怎样形成结果)会对照代码说明下面的状态与消息关系。首次阅读可以先跟完只读查询的三轮执行，再看中断后如何恢复和接管。

## 工具结果进入下一轮

用户询问订单是否能取消。模型先请求订单状态，再根据查到的状态取得适用制度，最后组织答案。每收到一条新的工具结果，下一轮就多了一项可以据此判断的事实。

| 阶段 | 已知内容 | 当前动作 | 仍未解决的问题 |
|---|---|---|---|
| 接收目标 | 用户关心目标订单的取消条件 | 确定可信身份与可用工具 | 当前订单是什么状态 |
| 查询后 | 订单状态、版本与更新时间 | 获取适用制度 | 哪条规则适用于当前事实 |
| 检索后 | 候选条款及来源 | 形成答案候选 | 引用是否真实、结论是否受支持 |
| 验证后 | 满足或未满足完成条件 | 提交结果、继续或停止 | 是否还有未完成目标 |

这个例子中，每步都要用前一步的结果，所以分成三轮。独立查询可以合并，缺条件时则可能增加澄清或补查。

## 恢复任务所需的状态

恢复任务时，程序要读到目标、当前用户及租户、任务阶段、剩余预算、待确认操作和最终结果。版本也要分清对象，例如任务状态版本、订单资源版本。只看聊天文本，难以可靠地区分“模型刚提议”“正在执行”和“已经执行”。

State 字段要写清用途、由谁更新、何时更新。权限、预算和完成状态由程序维护。模型给出的是计划建议，程序检查后再决定是否更新计划，不能让模型直接改前面这些字段。含义相近的字段也要说明区别，以免恢复时读错。

## 调用前预留额度，调用后保存结果

调用前预留额度，防止并发分支花掉同一份预算；调用后保存结果、消息和实际用量。请求失败或进程中断也可能已经计费，未确认的用量暂记为未知，后续再核对。

例如，进程预留额度后退出，还没来得及把回复存进数据库。检查点中就只有额度记录，看不到完整回复。恢复时需要查清这次调用是否发生、是否产生费用，以及结果能否找回。

只读查询通常可以重查；写操作则通过业务操作 ID、条件更新和结果查询确认进度，不能无条件重放。具体恢复过程见[持久化执行](../09_工程化与系统设计/02_Durable与生产运维.md)。

## 最后一轮也可能完成任务

三次模型请求的上限，限制的是能否发起第四次。第三次已经返回合格答案，就可以提交成功。

若第三次只取得部分工具结果，则停止新增工作，保留进度并说明哪些完成条件尚未满足。

## 用调用 ID 关联结果

每个提案有调用 ID，结果通过相同 ID 回填。调用发出顺序、完成顺序和协议要求的消息顺序可能不同，不能依靠列表位置碰巧一致。

一批调用中的独立查询可以并行，存在依赖的动作需要等待前置结果。有些实现要求“提交最终答案”单独占一轮，以便先把证据写入历史，再验证答案；这是应用策略，不是所有 Provider 的统一要求。

参数错误可以回填给模型修正。运行时按各自策略处理权限拒绝、资源不存在、协议错误和依赖故障，决定后续能否继续，详见[工具的结果与重试](../04_Tool与协议/Tool%20Calling与MCP.md#结果、错误与重试)。

## 完成前核对事实与版本

查询时订单为 pending，不代表回答生成时仍然如此。验证器可以检查目标订单、状态版本、来源版本与条款适用条件，避免把已经失效的观察继续当作当前事实。

固定字段和有限业务规则可以逐项检查。自然语言回答则要判断事实是否准确、引用是否支持结论、有没有回答用户问题；仅核对来源 ID 还不够。

已保存的答案是某次运行的结果。展示历史答案时，要注明当时的状态和时间；查询当前状态时，则按业务要求重新检查数据是否仍有效。历史快照不能直接当作实时缓存使用。

## 状态更新与执行权

用版本作为更新条件，可以拒绝旧状态覆盖新状态，却不一定能阻止两个执行者同时发模型请求或调用外部工具。跨进程接管时，还要确定此刻由谁执行任务，例如使用租约和运行代次；具体做法见下文链接。

新实现能解析旧状态，不代表仍按原含义使用其中的字段。恢复时要核对状态结构、Prompt、工具与策略版本，再判断是否需要迁移。具体的持久化与接管机制见 [[Learning/Agent/09_工程化与系统设计/02_Durable与生产运维|持久化执行与恢复]]。
