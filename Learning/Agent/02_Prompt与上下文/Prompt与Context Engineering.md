# 02 Prompt 与上下文工程

[订单 Agent 的逐轮消息](../案例_订单查询Agent.md#一次提案与结果的实际形状)展示第一轮之后如何加入提案和工具结果，可与本章的上下文选择一起阅读。

## 指令文本与本轮上下文

Prompt 交代任务、做法和输出格式。Context 是本次调用收到的全部信息，包括指令、用户输入、历史、工具说明和检索材料。上下文工程要决定本轮选哪些信息、怎样排列，以及何时更新或压缩。

即使 Prompt 相同，工具结果或保留的历史不同，也可能改变模型的行为。诊断时，要能还原模型实际收到的输入，知道用了哪个模板版本、哪些历史消息和工具结果，不能只比较模板文件。

## 从任务目标推导本轮输入

以已发货的订单 B 为例，用户的问题没有变，模型每轮需要的信息却不同。最初要知道如何查询订单；查到已发货和物流单号后，要补查最近物流记录；事实齐备后，要保留回答要求与证据，无关的工具说明就可以移出本轮输入。

Context Builder 从 State 读取已确认事实，选出本轮可用工具，加入相关的工具结果。历史对话保留交互过程，结构化字段保存当前值。

全量历史越积越长，关键信息就越难定位；只发最新一句，又容易丢掉目标和约束。选取内容时，要让模型看得到事实来源和待解决的问题。

## 区分指令与外部数据

宿主决定哪些消息可以下指令，相互冲突时谁优先。用户请求表达目标，检索文档和工具输出通常只提供待分析的数据；文档中的“忽略规则”不能授予新的执行权限。给内容加标签有助于模型区分来源，但不能单独防止提示注入。

模型先根据目录描述判断是否需要某个 Skill，再按需读取正文。正文放在哪个消息区块、具有怎样的指令优先级，由宿主决定。工具描述帮助模型选择动作，执行层则检查该动作是否获准。

## 消息历史与完整模型请求

完整请求可能同时包含 system 指令、用户消息、工具定义、历史提案、工具结果、模型标识和生成参数。只看 messages，通常只能看到完整请求的一部分。

例如第一轮只有用户问题和可用工具；查询后，历史新增一条 assistant 工具提案和对应结果。下一轮模型据此知道订单状态。结果中的 tool_use_id 需要与原提案 ID 一致，否则内容即使正确，也可能不符合协议。

工具结果是模型输入的数据，可信的租户信息和执行权限则由运行时另行维护。将历史截断到只剩最后一个工具结果，会丢失原目标与调用关系；按字符截断 JSON 还可能破坏结构。

小任务可以在长度上限内保留全部交互消息。长任务需要压缩时，把已经配对的提案和结果一起处理，保留目标、当前事实、来源和待确认动作。原始记录单独保存，便于回查；本轮只发送所需内容。

## 模板、示例和结构化输出

模板把目标、输入含义、约束、工具和输出格式放在固定位置。变量缺失时应报错，或使用事先约定的默认值，避免把空数据当成完整事实。

Few-shot 用少量样例展示输出格式，或说明仅靠文字难以讲清的判断条件。样例过于相似时，模型也可能照搬无关细节，因此要同时观察正常输入、异常输入和无答案的情况。

Schema 或 Grammar 约束输出结构，应用仍要校验字段、核对事实和动作授权。格式错误时，反馈具体出错位置，并限制修正次数。

## 有限窗口中的选择和压缩

用户要求取消订单，工具却返回超时。压缩这段历史时，应留下订单号、操作 ID，以及“取消结果尚未确认”。如果只写“已处理取消”，下一轮就可能把未知结果当成已经成功。

本轮只选有权使用且与目标相关的信息，再按时间、来源权威性和预算取舍。近期对话可以直接保留，大型工具结果按需加载；摘要中写清字段含义和未决冲突。压缩文本不会改变程序中的权限或预算。

上下文窗口限制单次调用的容量，输入之外还要为输出和协议开销留空间。按字符截断不等于按 Token 截断，要使用当前模型的计数方式，并把工具定义和协议字段一起计入。输入过长时，先考虑缩小范围、分阶段处理。

## 澄清与输入缺口

缺失信息会改变后续做法时，先向用户澄清；不影响当前工作的偏好可以稍后确认。调 Prompt 时也一样：缺事实就补事实，工具容易选错就改描述，别把所有问题都归给措辞。
