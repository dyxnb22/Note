# DDD 与领域建模

领域建模先确定业务事实由谁解释、哪些约束必须同时成立，再组织对象与代码。以订单为例，价格计算、库存占用、支付事实和履约进度彼此相关，但变化来源与失败方式不同，不能仅按数据库表机械拆类。

## 从业务语言确定边界

先描述用户要完成的动作、参与角色、状态和外部依赖，再找不变量：同一订单是否只能支付一次，库存是否允许为负，价格快照何时固定。这些约束决定并发修改与事务需要保护什么。

限界上下文让一套业务语言在某个范围内保持一致。例如“商品”在目录侧关心展示属性，在交易侧关心成交快照；两个模型可以各有职责，通过明确契约交换信息，不必共享同一个巨大对象。这里的业务上下文与 Agent 的提示上下文含义不同。

## 身份、值与聚合承担不同责任

| 对象 | 判断依据 | 订单场景中的含义 |
|---|---|---|
| Entity | 身份持续，属性可变 | 订单状态变化后仍是同一订单 |
| Value Object | 按值与约束判断相等 | 金额由数值和币种共同定义 |
| Aggregate | 同次修改需保持的不变量 | 订单与其明细金额保持一致 |
| DTO/Req/Res | 跨接口传输的数据契约 | 只暴露调用方所需字段 |
| PO | 持久化映射结构 | 对应存储字段与读写方式 |
| ACL/Adapter | 外部模型的转换边界 | 把支付供应商状态转换为本系统事实 |

金额不应只是一个无单位数字；值对象可以在创建时验证币种和合法范围。实体则通过行为控制状态，例如支付确认要检查当前状态和付款事实，而非让任意调用方直接改 status 字段。

VO 可能指 Value Object，也可能在另一个项目中指 View Object；ACL 在这里是 Anti-Corruption Layer，在权限领域又常指 Access Control List。缩写必须由当前边界定义，不能只凭名字推断职责。

聚合是保护不变量的边界，通常影响事务与并发范围。聚合过大会放大锁与加载成本，过小又把关键一致性推到跨边界协调。跨聚合流程可用事件与补偿衔接，但采用 DDD 并不意味着必须拆成微服务。

## 依赖方向与运行调用需要区分

```text
编译依赖：API/Trigger → Application → Domain
接口实现：Infrastructure → Domain/Application 定义的端口
运行调用：Application → 端口 → Infrastructure 实现
```

API/Trigger 解析协议、身份与输入；Application 编排一次用例和事务；Domain 保存状态、规则与不变量；Infrastructure 实现仓储、消息或支付等外部适配。领域依赖抽象能力，不直接依赖数据库连接与供应商 SDK。

运行时业务确实会调用数据库，但这不要求领域代码在编译时依赖具体数据库实现。测试可通过同一个端口提供受控实现，验证业务规则与外部故障如何相互作用。

## 状态迁移必须解释竞争与迟到事实

待支付订单可以因确认付款进入履约，也可因超时被关闭，两个动作竞争时须用条件更新或版本检查，避免互相覆盖。状态迁移记录业务号、输入事实和操作者，才能解释一次重复或迟到回调。

订单已经关闭后又确认收到款项，不能删除付款事实，也不能无条件恢复旧订单。应按业务约定进入退款、对账或人工处理流程。领域状态描述业务选择，支付事实描述已经发生的外部结果，两者需要关联但不能混为同一字段。

完整的回调与超时竞争见[场景方案中的支付故障矩阵](08_场景方案库.md#一个完整故障矩阵：支付回调与超时关单)。边界设计最终应能解释谁维护事实、一次修改保护什么，以及失败后由谁继续推进。
