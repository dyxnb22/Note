# 大数据基础：数据放在哪里，计算如何移动

将单机任务放到多台机器后，需要共同处理数据分布、网络交换、资源排队和失败恢复。HDFS、YARN、Spark、Hive 与 HBase 各负责不同部分，应沿一次任务追踪数据与控制信息，而非把它们当成一组必须同时安装的组件。

## 存储、调度与执行的分工

| 角色 | 主要责任 |
|---|---|
| HDFS NameNode / DataNode | 文件元数据 / 实际数据块 |
| YARN ResourceManager / NodeManager | 集群资源分配 / 节点执行资源 |
| ApplicationMaster | 某个应用的资源申请和协调 |
| Spark Driver / Executor | 计算计划和调度 / 分布式任务执行 |
| Hive | 表元数据与 SQL 查询组织，数据由相应存储保存 |
| HBase RegionServer | RowKey 范围内的在线读写 |

Spark 可运行在不同集群管理器上，Driver 与 ApplicationMaster 的部署关系也随模式变化。YARN Container 表达资源和执行配额，不天然等于 Docker 容器。

## HDFS 的块、元数据与读写

客户端向 NameNode 取得块位置，再与 DataNode 交换实际数据，不让每个字节都绕经 NameNode。写入通常按所需副本形成流水线，读取选择相应副本；故障后据块状态重新复制。[HDFS 架构](https://hadoop.apache.org/docs/stable/hadoop-project-dist/hadoop-hdfs/HdfsDesign.html)

Block 便于分布与吞吐，海量小文件却会放大元数据与任务开销。副本或纠删码保护的故障模型不同，也不保护逻辑误删；存储扩容、校验与备份应分别理解。

fsimage 保存元数据基线，edits 记录后续变更，Checkpoint 合并它们以控制恢复工作。Secondary NameNode 负责相应 checkpoint，不是能立即接管的热备；HA 的 Standby、共享编辑日志与旧主隔离属于另一套机制。

## 从 MapReduce 理解 Shuffle

Map 产生键值，中间结果按分区组织、排序并 spill；Reduce 拉取属于自己的分区，合并后按键计算。相同分组键必须到达对应汇总归属，网络、磁盘与热点键都可能成为瓶颈。

Combiner 是可选局部聚合，可能不执行，也可能执行多次，逻辑必须允许这类重组。把“平均数”直接再平均不符合要求，应该传播 sum 与 count：

```python
from functools import reduce


def partial(values):
    return sum(values), len(values)


def combine(left, right):
    return left[0] + right[0], left[1] + right[1]


if __name__ == "__main__":
    partitions = [[0], [100, 100, 100]]
    total, count = reduce(combine, map(partial, partitions), (0, 0))
    assert total / count == 75
    wrong = sum(sum(p) / len(p) for p in partitions) / len(partitions)
    assert wrong == 50
```

局部归并减少传输，但不一定减少分区数量，也不能消除一个极热键的集中工作。加盐拆键后还需第二次合并，并保持原始运算的组合语义。

## Spark 的依赖、惰性与恢复

RDD 的转换构建依赖，Action 才要求执行。窄依赖强调一个子分区只需父 RDD 的少量分区数据；不能反写成“父分区永远只会被一个子分区使用”。宽依赖常需按键重新分布，形成阶段边界与 Shuffle。[Spark 依赖定义](https://github.com/apache/spark/blob/v4.0.1/core/src/main/scala/org/apache/spark/Dependency.scala)

reduceByKey 可局部合并，通常比把全部值先 groupByKey 再聚合少传数据；已有合适分区器时还可能复用分布，并非每次调用必然重新 Shuffle。自定义聚合也需满足相应结合与交换要求，浮点归并顺序可能影响末位结果。

缓存减少重算，lineage 允许恢复部分计算，Checkpoint 可截断长依赖；它们都不让任意外部副作用自动只执行一次。任务重试、推测执行和 Driver 失败要与输出提交协议一致。

## Hive 表与分析访问

Hive 管理表元数据和查询，数据文件位于 HDFS、对象存储等存储系统，并非“没有自己的持久化数据”。实际执行引擎依版本和部署确定，不能把旧资料列出的引擎都当成当前可互换选项。

分区帮助按条件裁剪数据，分桶提供另一种组织规则；列式格式和统计减少扫描、改善计划，但分桶不是通用索引。表类型和删除策略决定 DROP 是否清理数据文件，元数据操作也有数据生命周期后果。

查询应先看粒度、分区裁剪、读取列、倾斜与小文件，而不是为所有慢任务增加执行器。分析扫描与业务事务库也要隔离容量。

## HBase 的 RowKey 与存储路径

HBase 以 RowKey、Column Family、Qualifier 与时间版本组织单元，表按键范围形成 Region。它适合按键和受控范围访问，不能把列族误认为 ClickHouse 式按列扫描分析。

写入涉及 WAL 与 MemStore，按 durability 设置满足确认条件，之后刷为 HFile；不是每次写都同步生成一个 HFile。跳过或异步日志会改变故障窗口，不能仅凭流程图中有 WAL 就宣称所有确认写入都安全。[HBase 日志与持久性](https://hbase.apache.org/book.html#wal)

读取合并内存与有关文件，Compaction 整理版本和删除，Region 可拆分迁移。RowKey 单调增长可能造成尾部热点，加盐又会让范围查询扇出；行内原子性也不能外推成通用跨行事务。

## 资源排队与容量证据

任务排队可能是队列配额、单任务申请过大或资源碎片，不一定是数据处理慢。运行慢则要对齐输入、Shuffle、磁盘、网络、GC、热点分区与失败重试；更多并行度可能反而产生更多小任务和连接。

容量验证应同时包含正常输入、倾斜键和恢复流量，并核对重跑后的结果。更完整的时间、窗口、质量和重放约定见[数据工程与流处理](数据工程与流处理.md)。
