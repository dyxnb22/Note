# Redis：数据结构、确认边界与缓存协议

Redis 用键和数据结构表达低延迟操作，但快不等于任何故障下都能保留相同事实。本章以 Redis 7.2 的通用核心机制为基线，先理解命令和状态，再讨论持久化、复制、缓存与协调。服务常用默认端口 6379，实际连接仍取决于部署配置。

## 数据结构与编码

### 数据类型与访问模式

| 类型 | 表达的状态 | 常见用途 |
|---|---|---|
| String | 字节串或可按命令解释的整数等 | 对象缓存、计数、租约标记 |
| Hash | 字段到值 | 属性、购物车 |
| List | 有序序列 | 两端队列、列表 |
| Set | 不重复成员 | 成员判断、交并差 |
| Sorted Set | 成员与分数 | 排名、按分数取范围 |
| Bitmap | 位状态 | 签到、布尔集合 |
| HyperLogLog | 基数摘要 | 近似 UV |
| GEO | 地理位置索引 | 邻近搜索 |
| Stream | 带 ID 的追加记录 | 消费组与待确认任务 |

选择先看需要的操作，而非只看“能否塞进去”。大集合整体读取、排序与删除仍有数据规模成本，内存访问也不等于常数时间。

### 紧凑表示与通用表示

String 可能使用整数、embstr 或 raw 等编码，字符串数据涉及 SDS；不能只写成“String 的编码都是 SDS”。SDS 保存长度与容量，支持二进制字节和 O(1) 长度获取，末尾的零字节也不定义逻辑长度。

小 Hash/Zset 常用 listpack，较大时分别转为哈希表、skiplist 与字典组合；List 可采用紧凑表示或由多个紧凑节点组成的 quicklist。Set 除整数 intset 和哈希表外，7.2 也有 listpack 路径，具体转换取决于大小、内容和配置。[Redis 7.2 Set 实现](https://github.com/redis/redis/blob/7.2/src/t_set.c)

ziplist 的前项长度字段可能造成连锁更新，listpack 的布局避免相同机制；它们是版本化的实现细节。紧凑编码省空间，也有顺序扫描和搬移成本，越过阈值后不能再按旧编码估算延迟。

### 哈希与有序集合

哈希扩容先创建新表，新增记录进入新表，查询需处理旧、新表并存的迁移状态；逐步迁移后再释放旧表。渐进分摊成本，不等于绝不产生分配或迁移抖动。Zset 的字典负责按成员查分数，有序结构负责范围、排名，字典查找通常按均摊 O(1) 理解，跳表查找按期望 O(log N) 理解；相同分数按成员字节序补充顺序，不能按自然语言排序理解。

### 客户端与序列化

Jedis 连接不应随意跨线程共享；Lettuce、连接工厂、池与框架各有自己的并发使用约定。Spring 中模板名称也不保证实际序列化格式，应明确键、值与旧缓存兼容，不能把某版默认 JDK 序列化当成跨服务协议。

JSON 仍需类型、字段与版本约束；StringRedisTemplate 只提供字符串层能力，不替应用完成对象演进。连接复用、超时和序列化错误也应分别观测。

## 线程模型与原子性

### 网络等待与执行成本

以本章基线的普通核心命令为例，事件循环通过 epoll/kqueue 等多路复用处理连接，网络 I/O 可由配置的线程分担，命令修改路径主要串行执行；后台还有释放和持久化相关工作。不能由“单线程”推断只有一个进程线程，也不能由 I/O 多线程推断所有命令并行。

KEYS、巨大范围查询、复杂脚本与大对象释放可能拖慢共享执行资源。Pipeline 合并通信，减少往返，但服务端仍执行各命令并返回结果，不承诺一批操作具有事务隔离或回滚。

### MULTI、WATCH 与 Lua

MULTI/EXEC 排队并连续执行命令；入队错误与运行期错误不同，运行时某条失败不会普遍撤销其他已完成修改。WATCH 在受监视键发生相关变更时使相应事务放弃，需要客户端重读并重试。

Lua 让一段逻辑执行时不被其他命令穿插，不等于数据库式全有或全无：脚本先写再报错，之前修改可能保留。脚本应在修改前验证类型与条件，限制运行时间，并明确错误后的恢复，不能把“原子执行”直接译成“出错自动回滚”。

## 持久化

RDB 保存状态快照，AOF 记录可重建状态的修改，两者服务于恢复。唯一业务事实、可重建缓存和统计摘要有不同的可接受丢失范围，不能只因启用了某个开关就宣称不丢数据。

### 快照、追加日志与重写

BGSAVE 常通过 fork 子进程生成快照，写时复制让主进程继续修改，代价仍有 fork 停顿和页复制；SAVE 是同步保存。复制还可能使用无盘快照传输，不能把所有 RDB 路径都解释成相同文件操作。

AOF 的 always 在相应追加后同步，可合并同批刷盘；everysec 通常周期同步；no 交给操作系统策略。每秒策略不是硬实时承诺，故障窗口还取决于实际同步与存储。

Redis 7 起多段 AOF 由基础文件、增量文件和 manifest 组织。重写生成新的基础表示，新写入仍进入增量，成功后切换有效文件集合；旧版“把缓冲全部追加进单一新文件”的流程需按历史实现阅读。基础段还可使用 RDB 编码。[持久化机制](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)

备份与恢复必须覆盖有效文件集合及配置，并实际验证加载；复制和快照同样可能保存误删后的状态，不能代替独立保留的备份。

## 过期删除与内存淘汰

### 过期与淘汰的触发条件

TTL 定义键何时过期，访问时检查与主动抽样清理负责逐步释放。键逻辑失效与内存物理释放不是同一时刻，过期通知也不是准时、可靠的任务投递。[过期键处理](https://redis.io/docs/latest/commands/expire/#how-redis-expires-keys)

maxmemory 的淘汰则为内存预算服务，并非只有到 TTL 才删除。复制、AOF 等部分缓冲不计入相同淘汰口径，RSS 也可能受分配器影响，不能把 maxmemory 当作进程绝对内存上限。

| 策略 | 可选择的键 |
|---|---|
| allkeys-lru / allkeys-lfu | 全部键，近似按最近访问或频率选择 |
| volatile-lru / volatile-lfu | 仅带 TTL 的键 |
| allkeys-random / volatile-random | 全部键 / 带 TTL 键中的随机项 |
| volatile-ttl | 带 TTL 键中优先选择较近到期项 |
| noeviction | 不按此机制淘汰，超预算时相关增长写入会被拒绝 |

LRU/LFU 是近似机制。volatile 范围不足时仍可能无法释放足够空间；读、删除等不按同一增长写入规则拒绝。策略应结合真实访问分布、命中与容量判断。[内存淘汰](https://redis.io/docs/latest/develop/reference/eviction/)

## 高可用与集群

### 全量复制与部分复制

全量同步建立 RDB 状态基线并接续期间的增量，基线可通过文件或流传输。重连后，PSYNC 根据复制标识与偏移判断缺失历史是否仍可提供，可提供时补增量，否则重新全量。

Backlog 保留可补发历史，在线副本还有发送进度与缓冲需求；这是逻辑职责，不代表现代实现必须为每个角色独立复制全部缓冲。数据量、断线时长和可保留历史共同影响全量同步成本。[Redis 复制](https://redis.io/docs/latest/operate/oss_and_stack/management/replication/)

### Sentinel 故障检测与切换

单个 Sentinel 的判断是主观下线，达到配置 quorum 才可判定客观下线；授权故障转移还需要相应多数派，不能把 quorum 与多数派选举混为一件事。

选副本需考虑可用、断线、replica-priority、复制进度等条件。选主、其他副本改跟随与客户端重新路由都有窗口，故障检测也不能证明旧主已经停止接受所有写入。

### Cluster 槽位与路由

Redis Cluster 有 16384 个槽，以 CRC16 对相应键或有效 hash tag 计算，再对 16384 取模得到槽位。它不是一致性哈希环；搬迁槽位、客户端缓存和重定向共同完成路由更新。

MOVED 指示相应槽归属，ASK 处理迁移期间的临时目标。要求同槽的多键命令、事务与脚本可用 user:{1001}:profile 等同 tag 键；客户端拆分 Pipeline 可以跨节点发命令，却不能因此获得跨分片原子性。

### 异步复制与确认窗口

默认异步复制下，主节点确认的写入可能尚未到达切换目标。WAIT 与副本健康限制能缩小某些风险，不自动把协议升级为线性一致存储，也不保证所有节点同时断电时的恢复结果。

读副本要接受可见性条件，关键不变量应放在满足所需确认与协调条件的事实存储上。增加副本数不等于已经定义好选主、隔离与数据安全范围。

## 缓存设计

### 事实源与 Cache Aside

缓存保存允许丢失或陈旧的派生值。常见读路径是命中返回、未命中回源并填充；写路径是先提交事实，再删除或更新缓存。进程内缓存避免网络，但每实例一份，也增加失效传播问题。

删除失败可以通过可靠重试和对账恢复，但成功删除也仍有并发窗口：读者取到旧数据库版本，写者提交并删除，随后读者把旧值填回。TTL 限制某些陈旧期限，延迟双删只是减少窗口，均不是线性一致的完整证明。

版本化填充需要保留并原子比较相应版本依据，不能只在值里加个数字就解决竞态。强一致读可直接走事实源或经过明确证明的协调路径。

### 雪崩、击穿与穿透

大量失效或缓存不可用会引起回源洪峰，单热点失效会形成集中重建，不存在的数据也可能持续穿透。随机 TTL、容量隔离、限流、合并同键请求与有界后台刷新分别保护不同环节，不能靠一个全局锁包办。

缓存空值需设置适当寿命并处理新增后的失效。Bloom Filter 只对已正确加入且位未被错误清除的元素提供无漏报性质；若过滤器未覆盖新数据或重建未完成，仍可能误拦真实键，不能盲目用它作事实判断。

## 分布式锁与高并发场景

### 锁的租期、拥有者与释放

```text
SET lock_key unique_value NX PX 10000
```

NX 在当前 Redis 状态上仅在键不存在时创建，租期限制占用时间，随机拥有者标识用于安全释放：

```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
  return redis.call("DEL", KEYS[1])
else
  return 0
end
```

该脚本防止误删别人的新锁，不能阻止旧持有者暂停后继续修改外部资源。续期也有失败窗口；fencing 要求下游检查 token，且 token 来源在所需故障范围内保持顺序，随机 value 或可能回退的计数不自动满足要求。多节点锁方案也需说明时钟与故障假设。

### 大 Key、热 Key 与扫描

大对象影响执行、带宽、复制与删除，热点则可能仅一个小键就耗尽单节点。按实际延迟和资源识别，不把“1 MB/1 万项”当成通用安全线。

bigkeys、MEMORY USAGE、慢日志与业务采样各给不同证据；hotkeys 依赖相应 LFU 统计条件。SCAN 可分步遍历，但可能重复，且不是一个固定快照；UNLINK 将相应释放移到后台，也不保证 RSS 当场下降。

只读热点可用本地缓存或副本缓解，但增加陈旧性；复制多个可写计数键则需重新定义合并与一致性。拆大集合也需保留原查询的分页与顺序合同。

### Redis 队列与投递合同

List 的 pop 后故障可能丢掉已取任务，可采用移入处理中列表等恢复协议；Pub/Sub 没有离线保留；Stream 有消费组与 pending，但仍需恢复、重试和幂等。

XACK 移除消费组的待确认状态，不等于删掉 Stream 记录。只用 XREADGROUP 的新消息路径不会自动接管所有旧 pending，需要受控认领与超时处理；旧执行者未必已停，业务效果仍需幂等。

### 库存预留与最终约束

Redis 可作准入与短暂预留，降低进入数据库的并发，但“预扣成功→发送外部 MQ”有两个资源间的失败窗口。Lua 不能顺便把外部 Broker 纳入同一事务。

一种可恢复路径是：通过者以唯一预留 ID 在数据库中确认订单/预留事实及 Outbox，再由投递者发送；数据库库存仍由条件更新保护。未取得数据库确认的临时预留，回收前需查询真实状态，避免把响应超时当成失败，或重复回补。

```sql
UPDATE goods SET stock = stock - 1
WHERE goods_id = ? AND stock > 0;
```

消费端按业务 ID 幂等，消息和预留可对账。Redis 计数服务于容量与体验，最终不变量由明确事实和恢复协议维护，完整投递见[消息队列](消息队列.md)。

### UV 与延时任务

PFADD/PFCOUNT/PFMERGE 维护和合并 HyperLogLog 基数摘要，约 0.81% 是标准误差口径，不是任何样本都满足的最大误差。摘要不能枚举用户或承担精确结算，稀疏/稠密编码与开销也不同。

Sorted Set 可按到期分数调度，仍需原子领取、执行状态、租期与失败恢复；取出后进程崩溃不能让任务永久消失。过期事件通知依赖清理时机与非持久 Pub/Sub，不能作为唯一可靠调度源。
