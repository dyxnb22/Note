# 消息队列：确认、重放与业务效果

消息系统把生产、存储、读取和业务执行拆到不同进程。学习重点是每次确认究竟证明了什么，以及故障发生后还能从哪里恢复；异步、解耦和削峰的收益，都建立在这些边界清楚的前提上。

## 一条消息有多个完成点

```text
本地业务提交 → 发送 → Broker 接受与确认
→ 消费者取得 → 业务效果提交 → 消费确认或位置提交
```

生产确认不表示消费者已处理，消费者读到也不表示业务提交。发送超时可能是未收到、已存入但响应丢失，不能只据超时决定重新创建一笔业务。

至少一次、至多一次和受限 Exactly-once 表达不同投递语义。常见可靠方案选择允许重放，再保证相同业务效果安全去重；产品和 API 可以提供不同取舍，应先明确所选择的投递保证。

## 生产事务与 Outbox

业务数据库和 Broker 通常不是一个本地事务。先提交业务再发消息有漏发窗口，先发送再提交业务又可能让下游看到最终未成立的事实。

Outbox 将待发布事实和业务修改同事务保存，由投递者重试。投递成功但尚未标记进度时仍会重发，因此 Outbox 解决可恢复发布，不取消消费者幂等需求。不同消费效果应有独立身份，消息 ID 与 payload 还需约定不可随重试改变。

## 消费幂等必须与效果同事务

“先记录已消费，再做业务”若分开提交，会在二者之间宕机后永久漏做；反过来也会重复。相应本地效果与 Inbox 标记应在同一事务中提交，外部 HTTP 或邮件另有幂等与结果查询约定。

下面用独占 SQLite 连接验证本地边界，未连接真实 Broker。金额变化以整数最小单位表示，输入应先验证；故障通过提交前抛异常模拟。consumer_key 表达同一种业务效果，不能因普通部署升级就随意换名。

```python
from contextlib import closing
import hashlib
import json
import sqlite3


def consume(db, message_id, delta, fail_before_commit=False):
    if db.in_transaction:
        raise ValueError("this example owns its transaction")
    payload = json.dumps({"account_id": 1, "delta": delta}, sort_keys=True)
    digest = hashlib.sha256(payload.encode()).hexdigest()
    with db:
        inserted = db.execute(
            "INSERT INTO inbox VALUES (?, ?, ?) "
            "ON CONFLICT(consumer_key, message_id) DO NOTHING",
            ("wallet-credit", message_id, digest),
        ).rowcount
        if inserted == 0:
            old = db.execute(
                "SELECT payload_hash FROM inbox WHERE consumer_key=? AND message_id=?",
                ("wallet-credit", message_id),
            ).fetchone()[0]
            if old != digest:
                raise ValueError("same message id with different content")
            return False
        updated = db.execute(
            "UPDATE accounts SET balance=balance+? WHERE id=1 AND balance+? >= 0",
            (delta, delta),
        ).rowcount
        if updated != 1:
            raise ValueError("missing account or insufficient balance")
        if fail_before_commit:
            raise RuntimeError("simulated failure before commit")
    return True


if __name__ == "__main__":
    with closing(sqlite3.connect(":memory:")) as db:
        db.executescript("""
            CREATE TABLE accounts(id INTEGER PRIMARY KEY, balance INTEGER NOT NULL);
            CREATE TABLE inbox(
                consumer_key TEXT NOT NULL,
                message_id TEXT NOT NULL,
                payload_hash TEXT NOT NULL,
                PRIMARY KEY(consumer_key, message_id)
            );
            INSERT INTO accounts VALUES(1, 100);
        """)
        first = consume(db, "m1", 30)
        repeated = consume(db, "m1", 30)
        assert first is True and repeated is False
        assert db.execute("SELECT balance FROM accounts").fetchone() == (130,)
        try:
            consume(db, "m2", 20, fail_before_commit=True)
        except RuntimeError:
            pass
        else:
            raise AssertionError("expected injected failure")
        assert db.execute("SELECT balance FROM accounts").fetchone() == (130,)
        retry = consume(db, "m2", 20)
        assert retry is True
        assert db.execute("SELECT balance FROM accounts").fetchone() == (150,)
```

m1 的业务提交后即使 ACK 丢了，重投也不再次加款；m2 在提交前失败时，标记与加款一起回滚，重试才能完成。真实消费端在事务成功后再确认，并区分永久拒绝、可重试失败与未知结果。幂等记录保留需覆盖合法重放窗口，过早删除后，旧消息可能再次产生效果。

## 顺序约束的是哪个阶段

入队顺序、交付顺序和业务完成顺序不同。Kafka 常见消费组中一个分区同一时刻有一个分配所有者，RabbitMQ 一个队列却可有多个竞争消费者，不能把前者规则套给所有产品。

按业务键路由只在路由与分区规则保持相应稳定时保留局部顺序；增加分区可能改变键映射。消费者再开线程并行、重试绕到别的队列或旧执行者仍在运行，都可能改变完成顺序，应以业务版本或相应串行协议保护最终状态。

## 积压、恢复与失败隔离

若持续输入 1000 条/秒，可持续处理 1500 条/秒，净追赶只有 500 条/秒；100 万条存量至少需约 2000 秒，还未计重试。增加消费者只有在分区、队列模型与下游容量允许时才有帮助。

队列不让过载消失，只把它变成延迟和存储。恢复速度应留在数据库、HTTP 等预算内，同时观察最老未处理时间与业务终态，不能只看 Offset 差或队列长度。

死信、TTL、长度限制和重试机制各产品不同；并非所有失败都会自动进入 DLQ。失败记录应保留原因、业务键和恢复归属，重投前先修复原因并保持原有的幂等约定。

## Kafka：分区日志与位置提交

控制面管理集群元数据与分区领导者，KRaft 的 Controller Quorum 与用户数据分区的副本有不同职责；控制器可用与某个数据副本是否跟上，应分别观察。[KRaft 元数据与角色](https://kafka.apache.org/39/operations/kraft/)

Partition 是有序追加日志，多个 Consumer Group 可独立读同一份记录。Segment 与索引支持定位，时间/大小保留会清理历史，Log Compaction 保留相应较新键值但不立即消除所有旧版本。

批量、压缩、顺序写、Page Cache 与受支持的零拷贝路径共同影响吞吐；Page Cache 主要减少磁盘访问，不等于所有传输都没有用户态拷贝。

### ISR 与确认阈值

以下按传统 ISR 模型说明，实际还需核对版本、选主和 ELR 等机制。acks=0 不等确认，1 等 Leader，all 等相应 ISR 条件；它不是“固定等待全部配置副本”。

RF=3、ISR=3、min.insync.replicas=2 时，不能把 all 理解成“任意两台就提前完成”；阈值限定能否满足相应写入，当前 ISR 参与确认。ISR 降为 2 仍可能写，降为 1 则无法满足该组合。选主是否允许落后副本、磁盘与同步策略又影响故障窗口。[Kafka 确认与副本配置](https://kafka.apache.org/39/configuration/broker-configs/)

### Offset、重平衡与并行处理

处理完 Offset 41，通常提交下一位置 42。若 40 仍未完成，不能因 41 已完成就把提交越过缺口。先提交再处理可能漏效果，处理后提交可能重放，均需结合业务事务判断。

成员变化、轮询与会话超时、分区变化会触发相应重分配。经典消费组中的 max.poll.interval.ms、session.timeout.ms 与 group.instance.id 等分别涉及轮询、会话和成员身份，实际规则还需核对使用协议。静态成员、协作策略与合理批量能减少某些扰动，但长任务与异步工作仍需明确分区撤销时如何停止、完成或恢复。

### 幂等生产与 Kafka 事务

幂等生产者处理相应协议中的重试重复，不按任意业务 ID 永久去重。事务可把多个 Kafka 输出与相应消费位置协调提交，read_committed 读取相应已提交事务结果；未提交和中止事务不能直接当成普通已完成业务。

这一范围不包含任意外部数据库、邮件或支付。Kafka-only 流程的 Exactly-once 与“HTTP 只被调用一次”不是同一承诺，恢复时仍可能重新执行计算函数。

## RocketMQ：本地事实与事务消息

Topic/Message Queue 与 NameServer 等组件提供的路由信息组织发送和消费。事务消息先有消费者不可见的半消息，再执行生产者本地事务，随后提交或回滚；结果缺失时 Broker 回查生产者保存的事务事实。

回查需依赖可恢复记录，不依赖原线程内存。该机制协调生产端本地事实与消息可见性，不把消费者数据库和所有外部动作也纳入同一事务。[RocketMQ 事务消息](https://rocketmq.apache.org/docs/featureBehavior/04transactionmessage/)

旧版延时等级与新版定时能力有不同接口、上限和精度条件，不能混成任意时刻精确执行。顺序消息同样要定义消息组/队列、生产顺序和消费重试，调度迟到不自动证明业务应立即取消。

## RabbitMQ：路由与两个方向的确认

以 AMQP 0-9-1 模型看，Producer 发给 Exchange，Binding 与 Routing Key 将消息路由到 Queue。direct 精确匹配，fanout 广播绑定，topic 匹配词段模式，headers 按头属性判断；数据保留在队列，持久 Exchange 主要保留路由定义。

### Publisher Confirm 不证明已被消费

消息没有路由到任何队列时，也可能获得发布确认。要按合同处理 mandatory 返回或替代路由，不能只看到 basic.ack 就断言目标队列或消费者已收到。[RabbitMQ 确认语义](https://www.rabbitmq.com/docs/confirms)

消费者 ACK 是另一个方向，应该在本地效果成立后发送。多消息确认需避免覆盖未完成工作，断线重投仍可能发生。普通集群部署不代表每个队列都复制，Quorum Queue 等类型还有多数派与可用性条件。

### Dead Letter 与重试路径

拒绝且不重新入队、到期或相应长度策略等可以触发死信，但需配置有效 DLX 与路由。没有相应配置时，拒绝可能直接丢弃；死信转发本身也有版本、队列类型与安全条件，不能当成无限可靠的错误保险箱。[Dead Letter](https://www.rabbitmq.com/docs/dlx)

## ActiveMQ 与进程内队列

JMS Queue 与 Topic 分别组织竞争消费与订阅；非持久订阅离线期间一般不保留相应消息，持久订阅依稳定订阅身份保留历史，具体客户端 ID、订阅名、共享和事务规则以使用实现为准。

Disruptor 则是进程内 RingBuffer 与序列协调，预分配和复用减少分配，访问局部性与等待策略平衡延迟和 CPU。最慢消费者限制复用进度，阻塞 SQL/HTTP 仍会拖住链路。Blocking 降低空闲 CPU 消耗但有唤醒成本，Yield/Sleep/Phased 等策略作不同折中，Busy Spin 则用持续占用核心换取相应等待延迟。

进程内队列没有自动跨机持久化与重放，跨进程 Broker 也不自动提供整个业务原子性。选型应沿数据模型、确认范围、恢复与容量判断，而不是只按“哪个更快”排名。
