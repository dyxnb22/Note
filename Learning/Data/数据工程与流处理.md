# 数据工程与流处理

本篇建立从业务事件到可分析、可重放数据产品的完整链路。HDFS、Spark、Hive 等组件概览见[大数据基础](大数据基础.md)，消息可靠性见[消息队列](消息队列.md)。

## 1. 数据系统分层

```text
业务数据库/日志/事件
→ 采集与 CDC
→ 消息与对象存储
→ 批/流计算
→ 仓库/湖仓/Serving
→ 指标、报表、特征与下游应用
```

每层都要定义 Schema、时间、幂等、质量、权限、血缘和重放。

## 2. OLTP 与 OLAP

- OLTP：小范围读写、低延迟、事务和并发。
- OLAP：大范围扫描、聚合、历史分析。

不能用大量分析查询拖垮业务主库。通过只读副本、CDC、ETL/ELT 和分析存储隔离工作负载。

## 3. 数据仓库建模

维度建模围绕业务过程：

- 事实表记录可度量事件。
- 维度表描述主体、产品、地区和时间。
- Grain 明确一行代表什么。
- 退化维度、快照事实和累计快照适配不同过程。

事实表粒度一旦混乱，指标很难修复。指标口径应绑定事实源、过滤、时间和去重规则。

## 4. 数据湖与湖仓

数据湖使用对象存储保存开放格式数据，成本低、扩展性高，但容易形成缺少治理的“数据沼泽”。

湖仓表格式在对象存储之上增加：

- Schema 演进。
- Snapshot/事务。
- 分区与元数据。
- Time Travel。
- Compaction 和清理。

产品选择前先理解一致性、并发写、元数据规模和引擎兼容性。

## 5. ETL 与 ELT

- ETL：进入目标系统前转换。
- ELT：先加载原始数据，再在分析平台转换。

稳定 Pipeline 应将原始层、清洗层和服务层分开，保留可重放来源。转换任务应幂等，相同输入与版本产生相同输出。

## 6. CDC

CDC 从数据库日志捕获 Insert/Update/Delete，减少轮询和双写。

需要处理：

- 初始全量快照与增量日志衔接。
- 事务顺序和提交边界。
- Schema 变更。
- Delete/Tombstone。
- 重启 Offset。
- 下游重复与乱序。

CDC 事件是数据库变化，不一定等同于高质量领域事件。下游不应依赖数据库内部列的偶然结构。

## 7. 批处理

批任务对有限数据集计算。关键问题：

- 分区裁剪。
- Shuffle 数据量。
- 数据倾斜。
- 小文件。
- 重试与推测执行。
- 中间结果和资源配额。

宽依赖通常引发 Shuffle；局部预聚合、合理 Partition 和处理热点 Key 可降低成本。

## 8. 流处理

流是持续到达的事件序列。核心语义：

- Processing Time：处理机器时间。
- Event Time：事件实际发生时间。
- Ingestion Time：进入平台时间。
- Watermark：系统对事件时间进度的估计。

迟到事件处理策略包括等待、更新结果、侧输出或丢弃，必须与业务正确性一致。

## 9. Window

- Tumbling：不重叠固定窗口。
- Sliding：固定长度、按步长滑动。
- Session：按活动间隔聚合。
- Global：全局窗口，需自定义触发。

窗口结果是否可更新、何时最终完成、如何处理迟到必须写入输出合同。

## 10. 状态与 Checkpoint

有状态流计算维护聚合、Join 和去重状态。Checkpoint 将状态与输入位置一致保存，故障后从共同进度恢复。

Exactly-once 通常只在引擎状态与受支持 Sink 的限定范围成立。外部 HTTP、邮件和支付副作用仍需幂等、事务或对账。

## 11. Kafka 与流引擎

Kafka 提供分区日志和消费位置；Flink/Spark Streaming 等引擎提供状态、时间、窗口和恢复。

Partition 决定并行度与局部顺序。重新分区会产生网络 Shuffle；Key 选择错误会造成热点和不可扩展状态。

## 12. 编排

Airflow 等编排器把任务组织成 DAG，适合调度、依赖、重试和补数。

任务设计：

- 幂等且可按日期/分区重跑。
- 重试不产生重复副作用。
- Backfill 与日常任务资源隔离。
- SLA、失败和数据延迟有告警。
- 不把业务数据大规模放进编排器元数据库。

## 13. 数据质量

质量维度：

- 完整性：是否缺行/缺字段。
- 唯一性：主键和业务键。
- 有效性：范围、格式和枚举。
- 一致性：跨表/跨层口径。
- 及时性：是否按时到达。
- 准确性：是否反映真实世界。

质量检查分布在入口、转换、发布和消费端。失败时决定阻断、隔离还是带标记发布。

## 14. Schema 演进

新增可选字段通常比删除、改名和修改含义安全。事件和表的 Schema 应进入 Registry/版本控制并执行兼容检查。

迁移顺序：

```text
消费者兼容新旧 → 生产者写新格式
→ 回填/验证 → 切读取 → 停旧格式
```

## 15. 血缘与目录

数据目录记录资产、负责人、Schema、口径、权限和更新频率；血缘连接来源、转换和消费者。

血缘用于评估变更与删除影响，但自动解析 SQL 得到的技术血缘不能替代业务语义和人工所有权。

## 16. 隐私与权限

按数据分类实施最小权限、列/行级控制、脱敏、审计、保留和删除。下游派生数据也要响应删除请求。

测试和开发环境不能随意复制完整生产敏感数据。

## 17. 成本与容量

观察：

- 输入量和增长率。
- Shuffle、扫描和存储字节。
- 小文件和元数据。
- 状态大小和 Checkpoint 时间。
- Slot/Core/Memory 利用。
- 热分区和 Backlog。

优化必须保持数据正确性和可重放性。

## 最小项目

实现“订单 CDC → Kafka → 流式分钟指标 → 湖仓日汇总”：

1. 定义事件和 Schema 演进。
2. 处理重复、乱序和迟到。
3. 使用 Checkpoint 恢复。
4. 建立数据质量和血缘。
5. Backfill 一天数据并与在线结果对账。

## 验收清单

- 能区分 OLTP、OLAP、仓库、湖和湖仓。
- CDC 全量/增量衔接、删除和 Schema 可恢复。
- Event Time、Watermark、Window 和迟到策略清楚。
- Pipeline 幂等、可重放、可补数。
- 数据质量、血缘、权限和成本都有负责人及指标。
