# 数据工程与流处理：从事件到可重放指标

以“订单事件生成分钟成交指标，并汇成日表”为例，指标正确性由事件粒度、重复、时间、迟到、输出更新与失败恢复共同决定。计算引擎、消息系统和表格式只分别承担其中一部分。

## 一行代表什么，一次修改代表什么

订单事实、订单明细、支付尝试与支付成功事件有不同粒度。把一笔订单关联多条明细后重复汇总订单金额，或将支付重试当成新成交，都可能得到语法正确却口径错误的指标。

维度补充商品、地区、用户等解释。若历史要反映当时属性，应保留交易快照或按有效期关联维度版本；重叠有效区间又可能让一条事实匹配两次。指标需绑定事实来源、过滤、时间、币种和去重键。

## 从业务库到可重放来源

```text
业务事实与日志 → 快照/CDC/事件 → 原始可重放层
→ 版本化转换 → 批/流结果 → 仓库、湖仓与服务
```

CDC 观察数据库变化，领域事件表达业务事实，二者不能仅因都含 order_id 就互换。全量快照与日志必须由一致协议衔接：不能任意 SELECT 完以后才开始监听，否则会丢掉交界更新。

来源记录还应包含稳定 ID、Schema/业务版本、事件时间与来源位置。Delete、事务边界和重启位置同样影响下游，重放窗口必须覆盖预计故障与补数时间。

ETL 在进入目标前转换，ELT 先加载再转换；保留原始层有利于修正，但需要相应访问、保留和隐私控制。同一输入和代码版本要可重现，还必须把所用维度、模型、配置等外部依赖也纳入版本。

## 事件时间与处理进度

事件时间是业务发生时间，处理时间是执行机器时间，进入平台时间又是另一项观测。网络、重试与回灌会让到达顺序不同于发生顺序。

Watermark 表达对事件时间进度的估计，不证明更早事件永远不会再来。多输入常受最慢相关输入约束，空闲分区可能拖住进度；标记空闲可以推进，但其恢复后的旧事件仍需遵守迟到处理约定。[Flink 时间与 Watermark](https://nightlies.apache.org/flink/flink-docs-stable/docs/concepts/time/)

## 窗口结果何时能修改

滚动窗口不重叠，滑动窗口可让一条事件进入多个窗口，会话窗口按活动间隔组织，全局窗口需另定义触发。窗口归属、触发、状态清理和输出最终性是四件事。

例如 12:00 窗口先收到 100 和 200，首次输出 300；之后允许范围内迟到 70，应更新为 370。若下游把两次输出都当新增金额累加，会得到错误的 670；应以窗口键和版本替换，或采用明确定义的撤回/增量协议。

### 用小模型验证重复与迟到

下面只模拟单输入的秒级滚动分钟窗，事件 ID 与内容约定不变。watermark 由调用方推进；它没有实现分布式 Checkpoint，outputs 代表示例中的可更新结果表。

```python
class MinuteTotals:
    def __init__(self, allowed_lateness=60):
        if allowed_lateness < 0:
            raise ValueError("negative lateness")
        self.allowed = allowed_lateness
        self.watermark = -1
        self.totals = {}
        self.seen = {}
        self.outputs = {}

    def emit(self, window):
        previous = self.outputs.get(window, (0, 0))
        self.outputs[window] = (self.totals[window], previous[1] + 1)

    def add(self, event_id, occurred_at, amount):
        window = occurred_at // 60
        end = (window + 1) * 60
        if self.watermark >= end + self.allowed:
            return "late"
        ids = self.seen.setdefault(window, {})
        payload = (occurred_at, amount)
        if event_id in ids:
            if ids[event_id] != payload:
                raise ValueError("same id with different content")
            return "duplicate"
        ids[event_id] = payload
        self.totals[window] = self.totals.get(window, 0) + amount
        if self.watermark >= end:
            self.emit(window)
        return "accepted"

    def advance(self, watermark):
        if watermark < self.watermark:
            raise ValueError("watermark cannot go backwards")
        self.watermark = watermark
        for window in list(self.totals):
            end = (window + 1) * 60
            if watermark >= end and window not in self.outputs:
                self.emit(window)
            if watermark >= end + self.allowed:
                del self.totals[window]
                del self.seen[window]


if __name__ == "__main__":
    totals = MinuteTotals(allowed_lateness=60)
    first = totals.add("e1", 10, 100)
    second = totals.add("e2", 50, 200)
    repeated = totals.add("e1", 10, 100)
    assert (first, second, repeated) == ("accepted", "accepted", "duplicate")
    totals.add("e3", 70, 50)
    totals.advance(60)
    assert totals.outputs[0] == (300, 1)
    totals.add("e4", 40, 70)
    assert totals.outputs[0] == (370, 2)
    totals.advance(120)
    assert totals.outputs[1] == (50, 1)
    late = totals.add("e5", 20, 30)
    assert late == "late"
    assert totals.outputs[0] == (370, 2)
```

迟到超限后可侧输出、另做修正或回灌，但不能既清理状态又承诺无限期精确去重。多个生产者若会重复使用 ID，去重键还需来源范围。真实引擎中的窗口精度、触发器与允许迟到设置应按版本核对。[Flink 窗口生命周期](https://nightlies.apache.org/flink/flink-docs-stable/docs/dev/datastream/operators/windows/)

## 状态、Checkpoint 与 Exactly-once

恢复点需要一致地连接算子状态和输入位置；只保存一个 Offset 而丢了聚合状态，或反过来，都会产生缺算或重算。回放期间函数仍可能再次执行，Exactly-once 不等于用户代码每行只跑一次。

端到端效果还依赖 Sink。引擎状态正确恢复，不会自动撤销已经发出的 HTTP、邮件或外部数据库修改；支持的事务 Sink、幂等写或与位置协调的提交协议才覆盖相应边界。

去重、窗口和 Join 的状态都可能增长。TTL、清理与允许迟到决定可提供多长的历史保证，状态版本、序列化与代码升级也需进入恢复验证。

## 批处理、回灌与输出提交

批任务处理有限输入，但重试和推测执行仍可能执行同一逻辑多次。按分区生成临时结果，再由相应原子发布协议替换目标，可避免失败任务留下半份可见表；具体存储与表格式必须支持对应提交。

数据倾斜、Shuffle 和小文件需要容量治理，回灌还需与在线流隔离资源。修正某一天时先固定输入范围与转换版本，计算后按业务键替换或合并，并核对同一天的在线结果，不能简单再追加一遍。

## 仓库、湖仓与快照

仓库以明确模型服务分析；数据湖把文件放入开放存储，仍需 Schema、目录、所有者与质量。湖仓表格式提供相应快照、元数据与并发提交机制，事务范围不能自动扩展到整个多表 Pipeline。

Time Travel 依赖仍被保留的快照与文件，不是独立备份。Compaction、过期清理和读者保留窗口共同决定可恢复历史，不能清完旧文件仍期待旧作业按原样重跑。

## 编排与数据质量的发布边界

DAG 负责调度与依赖，业务数据不应大量塞进编排器元数据库。任务应按明确日期、分区和版本重跑，对重试、回填、空数据和延迟分别定义结果。

完整性、唯一性、有效性、跨层一致性、及时性和真实准确性需要不同证据。例如订单数对齐不证明金额正确，字段非空也不证明来源没有漏事件。失败后选择阻断、隔离或带质量标记发布，而不是统一把任务状态标成成功。

## 血缘、权限与运行成本

血缘连接来源、变换和消费者，目录记录所有者、口径和使用边界。自动解析到表级关系不等于理解业务含义，删除和 Schema 变更还需考虑派生表、索引、特征与缓存。

按数据分类限制访问、保留和导出，原始层也不能无限积累敏感数据。

判断结果是否按预定要求更新时，关联输入位置、数据版本与窗口进度。再查看积压、状态大小、Checkpoint时长、扫描和Shuffle字节，定位处理或资源问题；任务仍在运行不等于结果已经更新。
