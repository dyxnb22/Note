# 如何研究一个协议

研究协议时，先确定要回答的问题：它解决了什么需求，规则怎样运行，参与者为什么使用，以及在哪些条件下会失败。学习、投资判断和工程实现需要的证据深度不同，应在开头说明用途。

## 沿一项操作收集证据

以研究一次借款为例，先找用户提交了什么、合约读取哪些价格与仓位、怎样计算可借额度，以及成功或失败后状态怎样变化。接着检查抵押品下降时谁执行清算、有什么收益、无法执行时由谁承担损失。

文档提供设计意图，源码说明实现路径，链上记录提供实际调用与状态。把价格图或使用量图表对应到这些问题，才能解释指标的含义；仅有图表还不能说明需求、安全或治理效果。

## 把缺少证据的地方写出来

对合约结构、前端、权限和事件索引分别记录已经核对的内容与缺口。运行最小系统可以观察调用和状态，但不能由一次演示推广为实际运营结论。

研究输出可以沿用下面的字段，减少遗漏；每一项应服务于本次问题，不必为填满模板补写没有证据的判断。

## 一页协议研究记录

```yaml
protocol: "待研究协议"
as_of: "2026-08-02"
problem: "解决什么具体摩擦，谁愿意付出什么成本"
mechanism:
  state_transition: "用户输入 → 合约/服务状态 → 输出"
  incentives: "谁获得收益，谁承担风险"
evidence:
  contracts: []
  docs: []
  onchain_metrics: []
risks:
  permissions: []
  oracle_or_bridge: []
  liquidity_and_exit: []
  upgrade_and_governance: []
falsifiers:
  - "若关键用户量/费用/安全指标持续低于阈值，则论点失效"
```


每个结论应能回到合约地址、区块范围、事件、代码版本或官方文档。数据查询记录链、RPC、时间区间和过滤条件；TVL、用户数等指标先统一口径再比较。

## 来源与核验边界

协议地址、部署网络、源码、升级权限、链上指标和监管结论都要记录核验时间。优先核对目标链浏览器、官方文档、已验证源码和可重放查询；二手材料用于发现问题，安全、收入与治理结论仍需对应的一手证据。

记录反例和失败路径，与成功路径一起检查；代币价格、市场情绪和正面叙事不能替代这些工作。
