# 事故响应与复盘

事故响应的目标是先降低用户和数据影响，再保留足够证据定位原因，最后让同类事故更难再次发生。

## 1. 事故分级

分级至少考虑：

- 用户数量和业务范围。
- 数据泄露、篡改和不可逆副作用。
- 金钱、库存、权限和合规影响。
- 持续时间、恢复难度和扩散趋势。

等级要对应通知范围、决策权限、响应时限和升级路径。

## 2. 响应阶段

~~~text
发现 → 确认 → 分级 → 遏制 → 保留证据
→ 恢复 → 验证 → 通知 → 复盘与修复
~~~

遏制动作可以包括停止发布、撤销 Token、关闭工具、限制出站、切换只读、暂停任务或回滚版本。每个动作都要记录影响和恢复条件。

## 3. 证据

保留：

- 时间线和观测窗口。
- 版本、配置、请求 ID 和审计记录。
- 受影响资源和数据范围。
- 执行过的命令、决定和授权人。
- 恢复前后的业务不变量。

日志可能包含敏感数据，证据保留也要遵守最小化和访问控制。

## 4. 复盘结构

- 事实时间线。
- 用户影响和未影响范围。
- 触发条件与放大机制。
- 为什么测试、告警或权限没有阻止它。
- 哪些决策在当时是合理的。
- 立即修复、结构性修复和验证证据。
- 仍接受的残余风险。

复盘不把责任归结为某个人的粗心；如果系统只能靠记忆和小心维持安全，控制设计仍不够。

## 评审真实系统时检查

用 PostgreSQL 锁事故、Agent 工具越权或错误发布中的一个场景，写出分级、Runbook、证据清单和复盘行动项，并为行动项设置验证方式。
