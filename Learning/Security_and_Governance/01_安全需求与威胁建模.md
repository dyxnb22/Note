# 安全需求与威胁建模

威胁建模不是列一张攻击清单，而是把系统中的资产、信任边界、攻击路径和可验证控制连接起来。

## 1. 先列资产和责任

资产可以包括：

- 账户、权限、密钥和身份凭证。
- 个人数据、业务数据、模型输入和内部 Prompt。
- 钱、库存、订单、配置和发布制品。
- 工具执行、网络访问和外部副作用。
- 可用性、完整性、可追溯性和用户信任。

每项资产都要有所有者、允许访问者、失败影响和恢复责任。

## 2. 画信任边界

至少区分：

- 用户输入和上传文件。
- 浏览器、移动端和服务端。
- API Gateway、业务服务和数据库。
- Provider、MCP、插件和第三方回调。
- 构建环境、制品仓库和生产环境。
- Agent 的模型、工具、记忆和审批人。

跨边界的数据默认是不可信的，不能因为字段名叫 system、admin 或 verified 就提升权限。

## 3. 威胁问题

对每个边界询问：

- 谁能伪造身份？
- 谁能读取或修改资产？
- 谁能让系统执行未授权动作？
- 谁能造成拒绝服务或成本失控？
- 谁能删除、篡改或隐藏审计证据？
- 哪些失败会产生不可逆副作用？

## 4. 控制必须可验证

| 威胁 | 控制 | 验证 |
|---|---|---|
| 越权访问 | 资源级授权、最小权限 | 反向权限测试 |
| 注入/不可信输入 | 解析、约束、输出编码 | 恶意输入测试 |
| 秘密泄露 | 秘密存储、轮换、脱敏 | 日志和导出扫描 |
| 重放与重复副作用 | Nonce、幂等键、过期 | 重放测试 |
| 数据外传 | 出站限制、审计、审批 | 工具/网络集成测试 |
| 供应链篡改 | 锁定依赖、签名、可追溯构建 | 制品验证 |

## 5. 残余风险

没有控制能把风险变成零。记录：

- 已接受的风险和接受人。
- 未完成的控制和截止条件。
- 需要人工审批的动作。
- 发生事故时的 Kill Switch 和恢复路径。

## 评审真实系统时检查

为一个 Agent 工具或订单 API 画出资产—边界—威胁—控制—测试表，并至少写出一个无法完全自动化解决的残余风险。
