# 入职成长与职业发展

入职后的学习围绕真实职责展开：理解系统为何如此运行，独立完成可靠修改，再逐步承担更大的结果与协作范围。学习材料提供机制，工作中的证据检验这些机制是否真正掌握。

## 把岗位要求转成能力与证据

| 能力层 | 工作中可观察的证据 |
|---|---|
| 基础 | 能用语言、数据库、网络与操作系统机制解释现象 |
| 工程 | 改动有测试、可发布、可观测，故障能够定位和恢复 |
| 设计 | 讲清状态、不变量、容量与取舍，并验证关键假设 |
| 业务 | 理解规则与指标，判断改动是否产生用户价值 |
| 协作 | 明确责任，推动依赖、Review、决策与反馈闭环 |

“能解释”“能实现”“能在失败条件下验证”“在真实约束下负责”是不同证据等级。下一阶段优先补足当前职责中风险最高、最影响交付的一层，而非同时收集所有技术名词。

## 用 30、60、90 天组织反馈

这些时间点是与团队校准预期的参考，不是所有岗位相同的考核表。初期先理解业务动作、调用链、数据归属、发布与事故处理，完成一个范围可控的小修改，走完真实交付过程。

随后逐步独立负责一条链路，补齐它的测试、观测与恢复路径；再识别一个有证据的改进，说明收益、依赖、验证与回退。约在每个阶段与负责人回看实际职责和阻塞，必要时调整目标。

完成次数不等于独立能力。如果修改始终依赖某位同事手工补救，需要继续查明隐含知识或权限缺口，而不是只增加任务数量。

## 把工作结果保留为可核验证据

一个改进记录应串起问题、个人责任、关键行动、验证结果与适用边界。例如声称降低延迟，应保存改动前后的版本、负载、数据和分位口径，同时检查错误率与资源成本；单次较快请求不足以说明整体改善。

代码、测试、运行指标、事故记录与决策说明提供不同证据。团队成果要说明个人负责的部分，实验相关性也不能直接写成业务因果。详细组织方法见[项目表达与技术决策说明](../Writing_and_Expression/03_Workplace_Communication/项目表达与技术决策说明.md)。

## 扩大责任，而非只增加工作量

持续成长表现为能处理更复杂的约束、减少系统风险，并让协作方更容易完成工作。晋升通常依赖一段时间内稳定承担的责任与影响，具体标准应与所在团队的岗位要求对齐。

技术领导还要建立决策与反馈机制，让知识、权限和交付不依赖个人兜底。授权、分歧处理与复盘见[团队协作与技术领导](团队协作、项目管理与技术领导.md)。

## 定期回看方向与职业风险

按季度比较哪些工作产生了可验证影响，哪些投入只带来忙碌，下一阶段应强化哪一两项能力。保留可公开的成果与可迁移知识，同时遵守组织的数据、隐私与保密边界。

转岗或组织变化时，先确认职责、时间、交接与约束，再决定行动。日常维护清晰文档、可接管的系统与稳定协作关系，既降低团队单点风险，也让自己的成长建立在可解释的结果上。
