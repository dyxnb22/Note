# 职业发展全流程

本篇把求职、面试、Offer、入职、晋升和职业风险连接为一条可执行流程。项目证据来自 [Case Studies](../Case_Studies/README.md)，不能用包装替代真实能力。

## 1. 职业定位

定位由四部分共同决定：

- 希望解决的问题：业务后端、平台、AI 应用、模型系统等。
- 已有证据：代码、上线、测试、事故、性能和业务结果。
- 市场岗位：职责、门槛、地域、薪酬和供需。
- 现实约束：时间、身份、家庭、健康和风险承受。

定位不是给自己贴永久标签，而是选择下一阶段最值得积累的能力组合。

## 2. 岗位能力矩阵

对目标岗位拆解：

| 层 | 证据 |
| --- | --- |
| 基础 | CS、语言、数据库、网络、OS |
| 工程 | 测试、交付、排障、安全、观测 |
| 设计 | 状态、一致性、容量、取舍 |
| 业务 | 目标、规则、结果和影响 |
| 协作 | 需求、Review、推动和复盘 |

每项标记“能解释、能实现、能验证、真实项目使用过”四级，学习优先补影响岗位匹配的最短板。

## 3. 简历

简历让招聘方快速判断是否值得进入下一轮。每段经历回答：

```text
背景/目标 → 我的职责 → 难点
→ 方案与取舍 → 可核验结果 → 技术边界
```

原则：

- 使用岗位语言，但不复制 JD。
- 写清个人贡献和团队成果的边界。
- 数字说明口径和时间范围。
- 不宣称未运行、未审计或未负责的部分。
- 技术名词只保留能被继续追问的内容。

## 4. 作品集

作品集不追求项目数量，优先展示：

- 清晰 README 和运行步骤。
- 架构、数据和失败链路。
- 测试、Benchmark、Eval 或截图证据。
- 安全与权限。
- 取舍、限制和未来改进。
- Commit/Issue/ADR 体现演进。

一个有真实故障与复盘的小系统，通常比多个无法运行的模板更有说服力。

## 5. 求职漏斗

维护：

```text
岗位来源 → 匹配度 → 投递 → 筛选
→ 面试轮次 → 结果 → 反馈 → 下一动作
```

按周观察转化：

- 无筛选：定位、简历或渠道问题。
- 一面失败：基础或项目表达。
- 系统设计失败：容量、边界、取舍不足。
- 终面失败：岗位匹配、协作和影响力。

不要只增加投递量而不诊断瓶颈。

## 6. 技术面试

准备顺序：

1. 语言和 CS 高频机制。
2. 数据库、中间件和网络排障。
3. 项目深挖。
4. 系统设计。
5. Coding。
6. 行为和价值判断。

回答机制题采用：定义 → 为什么存在 → 核心机制 → 适用边界 → 故障/排查 → 项目例子。

## 7. 项目深挖

必须能回答：

- 业务为什么需要它？
- 你负责什么？
- 最难的不变量是什么？
- 为什么选这个方案？
- 替代方案为何没选？
- 故障如何发现和恢复？
- 结果如何测量？
- 如果重做会改变什么？

项目表达入口见[项目表达](项目表达.md)。

## 8. 系统设计

面试中按顺序收敛：

```text
需求/非目标 → 规模估算 → 数据与 API
→ 核心链路 → 一致性/失败 → 扩展
→ 安全/观测 → 取舍
```

先设计正确的单机/单区链路，再扩展。不要一开始堆微服务、Kafka 和 Kubernetes。

## 9. Coding

先确认输入、输出、边界和规模，再提出算法。编码时保持不变量和命名清楚；完成后用正常、边界、空值和反例手动走查。

面试官不仅看最终答案，也看问题澄清、复杂度、测试和修正过程。

## 10. 行为面试

STAR 只是一种结构，核心是：

- 情境和责任边界清楚。
- 行动说明判断和协作。
- 结果有证据。
- 复盘承认限制。

准备冲突、失败、推动、优先级、事故、学习、反馈和领导力各一例，避免所有问题重复同一故事。

## 11. 反向面试

询问：

- 团队目标和成功指标。
- 当前最大技术/业务风险。
- 交付、Review、On-call 和事故文化。
- 岗位前三个月期望。
- 决策权、协作和成长路径。
- 人员流动和招聘原因。

问题用于判断真实工作，不是表演兴趣。

## 12. Offer 评估

比较总回报而不只月薪：

- 固定薪酬、奖金、股权及兑现概率。
- 工作内容和能力复利。
- 经理、团队和组织稳定性。
- 工作时间、通勤、地点和签证。
- On-call、绩效与裁员风险。
- 机会成本和退出选项。

把假设、最坏情况和不可逆因素写下来。

## 13. 谈判

先确认对方希望录用，再基于市场、职责、已有 Offer 和可验证能力讨论。优先澄清总包、级别、入职日期和关键条款。

保持真实，不伪造 Offer。所有重要承诺最终以书面合同为准，法律和税务问题咨询专业人士。

## 14. 入职 30/60/90 天

### 30 天

理解业务、系统、团队、发布和事故；完成小修改并建立信任。

### 60 天

独立负责一条链路，补文档/测试/观测，识别一个可落地改进。

### 90 天

稳定交付，能解释系统风险，推动一次跨边界改进并与经理校准预期。

## 15. 晋升

晋升通常要求持续表现，而不是一次英雄事件。维护证据：

- 复杂度和责任范围。
- 业务结果。
- 可靠性和质量。
- 跨团队影响。
- 培养他人和减少组织摩擦。

定期与经理对齐级别标准，避免只在评审前整理材料。

## 16. 技术领导力

领导力包括：

- 把模糊问题变成共同目标。
- 建立可解释决策。
- 分配所有权而非包办。
- 提前暴露风险。
- 让团队在没有自己时也能运行。

技术最强不自动等于领导有效。

## 17. 转岗、裁员与风险

长期维护：

- 可公开作品和成就记录。
- 简历、联系人和岗位地图。
- 现金缓冲和保险边界。
- 可迁移能力。
- 身份与合同文件。

发生变化时先确认事实、时间、补偿、保险/签证和设备数据边界，再决定谈判与下一步。

## 18. 季度复盘

每季度回答：

1. 哪些工作产生了可验证影响？
2. 哪种能力形成复利？
3. 哪些任务只是忙碌？
4. 当前最大的单点风险是什么？
5. 下一季度只强化哪两个主题？

## 18.1 作品集证据台账模板

把经历写成“行为—证据—结果—边界”，避免只写技术名词。

```yaml
project: "项目名称"
role: "我负责的边界"
problem: "业务目标与约束"
actions:
  - "做了什么关键设计/实现"
evidence:
  - type: test
    link: "测试或报告位置"
  - type: metric
    value: "延迟/错误率/成本/业务结果"
tradeoffs:
  - "为什么选这个方案，放弃了什么"
failure_and_learning:
  - "遇到的失败与下一次改法"
```

面试前用这张台账逐项准备“为什么、怎么验证、出了什么问题、结果是否可归因”；没有证据的指标不要包装成事实。

## 验收清单

- 有目标岗位能力矩阵和证据等级。
- 简历每项都能经受项目深挖。
- 求职漏斗能定位问题阶段。
- Offer 用统一维度比较。
- 入职、晋升和职业风险都有定期复盘。

## 来源与验证边界

职业方法参考结构化面试、STAR、DORA/工程效能与职业管理的一般实践。薪酬、劳动法、签证、税务和合同随地区与时间变化，必须核对当地官方规则或咨询专业人士。
