# 05 后端与系统设计

用语言与异步知识连接请求、领域状态、持久化和外部动作。每条链路都需要资源上限、取消协议和可恢复状态。

## 一次 HTTP 请求穿过哪些边界

框架处理协议，应用服务组织用例，领域类型与数据库约束共同保护状态。客户端断开只改变本地请求生命周期，已经提交的事务还要按业务事实判断。

### Axum、Hyper 与 Tokio 的职责

Tokio 提供 executor、定时器和异步 I/O，Hyper 负责 HTTP 连接/协议基础，Axum 在其上组织路由、提取器、中间件和响应；业务层不应依赖具体 handler 的请求类型。入口要限制请求体/连接/并发，阻塞文件或 CPU 工作放到受控 blocking pool，关闭时停止接收、取消任务、等待句柄并释放连接池。

### 运行时与 I/O 机制的选择

先从 workload、平台、生态、可观测性和维护能力出发；Tokio 适合 Rust 生态中的通用异步运行时，Libuv 适合跨语言/跨平台事件循环边界，io-uring 可能在 Linux 高性能 I/O 场景有收益但带来内核、驱动和兼容成本。不要用“更底层所以更快”下结论，必须用同一 workload、版本、内核和失败模型 benchmark/压测。

### 小型 Web 服务的组织

README 要写清运行、测试、架构决策、已知不足和若有更多时间的改进；代码要有 DTO/领域/存储边界、错误类型与处理约定、输入限制和端点测试。评审时说明哪些地方选择简单内存实现、哪些地方预留持久化/并发扩展，以及如何用测试和指标证明，而不是堆砌框架。

### 异步 HTTP 的超时与错误分类

给真实请求 Future 包上 timeout，携带 request ID/幂等键，响应按 schema 校验并及时释放资源；区分连接失败、服务端错误、解析失败、超时和结果未知。只读请求可按策略重试，副作用请求必须查询状态或对账，不能把 timeout 直接当成没有发生。

### DTO、领域与数据库边界

请求先反序列化 DTO，再做字段和业务状态验证，服务层负责状态机和幂等，Repository 负责参数化查询、连接池和短事务；迁移要版本化并验证空库/旧数据。认证、授权、CORS/CSRF、请求体/分页上限和错误脱敏属于服务接口与运行约定，不能由编译器或 ORM 自动保证。

### API 请求、事务和取消

handler 只做提取、认证和响应映射，服务层把 DTO 转成领域命令，Repository 使用短事务和参数化查询；请求 deadline 传入下游，但事务提交和外部副作用不能因为客户端断开就假设已回滚。慢 I/O、文件和 CPU 任务放入有界 worker，状态表记录任务/幂等键/版本，关闭时通过 cancellation 和 JoinHandle 有界收尾。

## 状态和版本控制并发修改

外部数据经过校验之后，状态机限定下一步允许发生什么。版本条件把“依据旧状态提出的更新”与当前记录关联起来。

### 任务状态机与版本更新

用 enum 表达 Pending/Running/Succeeded/Failed/Cancelled 等有限状态，方法只允许合法迁移并返回新的状态或错误；状态中保存版本、租约、尝试次数和结果引用。持久化时用条件更新防止旧 worker 覆盖新状态，Rust 类型能减少非法状态，但不能替代数据库并发控制。

### 示例：状态和版本共同限制迁移

Enum 防止同一任务同时处于多个互斥状态，版本号拒绝过时的修改。下面是单进程的最小模型，完整数据库实现还要将检查与写入做成一次原子条件更新。

```rust
#[derive(Debug, PartialEq)]
enum State { Pending, Running, Succeeded(String) }
struct Task { version: u64, state: State }
impl Task {
    fn start(&mut self, expected: u64) -> Result<(), &'static str> {
        if self.version != expected || self.state != State::Pending {
            return Err("conflict");
        }
        self.version += 1;
        self.state = State::Running;
        Ok(())
    }
    fn finish(&mut self, expected: u64, receipt: String) -> Result<(), &'static str> {
        if self.version != expected || self.state != State::Running {
            return Err("conflict");
        }
        self.version += 1;
        self.state = State::Succeeded(receipt);
        Ok(())
    }
}
fn main() {
    let mut task = Task { version: 0, state: State::Pending };
    task.start(0).unwrap();
    assert!(task.finish(0, "old".into()).is_err());
    task.finish(1, "receipt-1".into()).unwrap();
    assert_eq!(task.state, State::Succeeded("receipt-1".into()));
}
```

这段代码把检查与修改放在独占的 `&mut self` 内；跨进程竞争则必须由存储系统处理。租约、业务幂等键和远端结果查询仍是独立机制。若取消发生在远端扣款之后，本地状态无法单独证明远端未执行。

### 一次 API 请求怎样穿过各层

Handler 把协议输入映射成命令，领域构造函数拒绝非法值，service 决定合法状态迁移，repository 在短事务内保存事实与待办事件。网络超时或客户端断开后，恢复流程按持久化任务继续定位，不凭进程内 Future 是否还存在判断最终结果。

例如索引服务先保存 task_id、输入文件版本和目标索引版本；worker 发布新索引前写入完成元数据；查询只读已发布版本。中途失败的临时文件和索引都可以独立清理，旧版本仍能服务读取。

## 长任务的执行与恢复

索引等工作超过一次请求的时间范围，需要把进度与版本放入持久化任务。异步网络和阻塞工作分别受容量限制，避免一个慢任务占住整个服务。

### 文件索引服务与 Checkpoint

请求层校验路径、权限和大小，任务表保存索引版本/状态/进度，worker 通过有界 channel 和租约执行；文件按块读取，解析和索引结果分阶段提交，进程重启从 checkpoint 恢复。目录遍历、文件读取和数据库操作都需 timeout/cancel/错误分类，不能让一个坏文件拖垮整个队列。

### 网络服务的阻塞隔离

网络处理使用 async I/O，CPU/同步文件/外部命令放到受控 blocking 线程池或专用 worker；所有入口有并发上限、超时和响应大小限制，连接池与任务 channel 有界。通过 async trace、P95、任务数、线程池饱和和下游指标验证延迟与资源使用是否改善，不能只把函数标成 async。

## 把外部能力封装成受控工具

同样的服务边界也适用于模型工具。参数解析建立结构，权限与资源约束决定能否执行，Checkpoint 保存后续恢复所需的事实。

### 工具注册、参数与权限

注册表保存工具名称、版本、输入 schema、权限 scope、超时和执行器；调用先解析/校验参数、检查租户和授权，再在受限任务中执行，返回结构化状态和调用 ID。工具版本和副作用要幂等，执行记录可回放/审计；trait 负责能力边界，权限不能只写在 trait 或 Prompt 中。

### 文件路径与子进程边界

先规范化路径并检查其位于允许工作区，明确符号链接和 TOCTOU 策略；启动子进程使用参数数组而不是拼接 shell，限制 cwd、环境、网络、运行时间、输出大小和子进程数量。stdout/stderr、退出码、超时和取消都要进入结构化结果，不能只返回一段字符串。

### Provider、Tool 与 Checkpoint

Provider Adapter 只处理认证、DTO、流式事件和错误分类，核心 Runtime 使用稳定的 `ModelOutput`/`Usage`/`ProviderError`；Tool 先做 Serde 解析、业务校验、权限与副作用检查，再执行；Checkpoint 保存版本化状态、预算、工具结果、幂等键和恢复位置。进程崩溃后要能判断动作是否发生，不能仅靠日志或内存 Vec 恢复。

## 从语言保证判断系统成本

内存与类型约束提供局部保证，系统仍要面对远端状态、资源和维护成本。语言选型需要把这些代价与团队实际能力一起比较。

### 内存安全与系统正确性的边界

Rust 主要消除了大量内存安全和数据竞争类别的问题，不保证业务逻辑、死锁、资源耗尽、错误处理、权限和远端一致性正确。仍要设计状态机、超时、背压、审计和测试；类型安全是可靠系统的基础，不是系统验收结论。

### 语言选型与维护成本

当服务需要稳定的低延迟、资源上限、跨平台二进制、内存安全和编译期并发约束，同时团队能承担更复杂的类型/生命周期学习成本时，Rust 的收益更明显。快速变化的业务胶水和数据处理可能更适合 Python，简单高并发服务和团队交付可能更适合 Go；最终用基线、故障成本和维护能力验证。
