# 04 工程基础

用模块、可见性和公开类型保护不变量；用 Cargo 固定构建输入，再把协议转换、配置和观测留在外部边界。

## 构建与模块共同保护边界

Cargo 决定构建输入，模块可见性决定调用方能接触哪些状态。用公开类型表达校验后的状态，内部实现就可以在不破坏调用约定的情况下演进。

### Crate、Module、Workspace 与 Feature

crate 是编译单元，module 组织可见性和命名，workspace 管理多个 crate；Cargo.toml 记录依赖、版本和 feature。公共库应控制暴露 API、错误类型和 feature 组合，应用要锁定依赖和工具链并保证构建可复现；模块边界优先服务所有权和测试边界。

### 工作区与依赖的最小分工

应用 crate 可以负责 HTTP 和装配，核心 library crate 负责规则与公开类型。workspace 共享构建组织和依赖配置，不会自动把各 crate 的领域边界设计好。

| 文件或概念 | 保存的决定 |
|---|---|
| Cargo.toml | package 元数据、依赖约束、feature 和 target |
| Cargo.lock | 解析得到的依赖版本 |
| rust-toolchain.toml | 所选 Rust 工具链及组件 |
| src/lib.rs 与公开 API | 其他 crate 可使用的能力 |
| tests/ 与文档测试 | 对外行为及示例是否仍成立 |

锁文件固定依赖解析结果，工具链和目标平台还需分别固定；构建结果也受 feature、配置和环境影响。

### 工具链、Lockfile 与 Edition

Edition 定义语法和兼容迁移边界，工具链版本决定实际编译器与标准库，二者不是同一个版本号。依赖解析又由 Cargo.toml 与 lockfile 共同确定，需要分别保存。

升级工具链、依赖或 feature 组合时，在 CI 中重新检查公开 API、测试与目标平台构建；只验证默认 feature，不能覆盖用户实际启用的全部组合。

### 可见性与公开 API

模块组织命名空间，默认私有；`pub(super)`、`pub(crate)` 和 `pub` 分别控制父模块范围、crate 范围与公开访问。公开类型可以用私有字段和构造函数保证非法状态无法直接创建，测试优先通过公开行为验证，而不是为了方便把内部实现全部 `pub` 出去。

### 示例：由模块保护合法状态

协议输入可以是任意整数，领域对象只允许范围内的值。私有字段阻止调用方绕过构造函数，返回 Result 则让输入失败成为可处理的正常路径。

```rust
mod domain {
    #[derive(Debug)]
    pub struct Limit(usize);
    impl Limit {
        pub fn new(value: usize) -> Result<Self, &'static str> {
            if (1..=100).contains(&value) { Ok(Self(value)) }
            else { Err("limit must be between 1 and 100") }
        }
        pub fn get(&self) -> usize { self.0 }
    }
}
fn main() {
    assert_eq!(domain::Limit::new(5).unwrap().get(), 5);
    assert!(domain::Limit::new(0).is_err());
}
```

调用方可以请求构造 Limit，却不能直接写 `domain::Limit(0)`。外部 DTO 解析成功后仍要经过这类领域校验，再传给实际用例；Serde 成功只说明编码形状可以映射为 DTO。

## 外部数据进入领域模型

序列化先恢复协议结构，业务校验再建立领域不变量。配置和日志也经过外部边界，因此需要在启动与请求处理时留下可定位的信息。

### Serde、配置与结构化日志

Serde 负责协议/数据映射，边界层先反序列化并校验，再转成领域类型；配置启动时解析、校验和冻结，密钥不进入日志；日志/Trace 记录结构化事件、request/task ID 和错误上下文。序列化格式要定义版本、大小、未知字段、兼容和敏感数据策略。

### DTO 与领域类型

外部 JSON/配置 schema 可能包含别名、缺省、未知字段和不可信值；先反序列化成 DTO，再做范围/权限/状态校验并转换成领域类型，可以把协议变化和业务不变量隔离。版本字段、未知字段策略、迁移失败和日志脱敏都要明确，序列化成功不代表业务输入合法。

## 测试行为，再解释资源成本

所有权减少了部分错误类别，公开行为、错误处理与性能仍要分别观察。借用、复制和优化配置的取舍应落到固定负载上。

### 单元、集成与文档测试

单元测试适合模块内部状态和纯函数，集成测试通过 library crate 的公开 API 验证边界，文档测试验证示例仍可编译运行。测试应覆盖正常、错误、取消、资源释放和协议兼容；断言稳定错误分类和行为，不要把内部字符串或布局当作长期不变的接口约定。

### Clone、借用与零拷贝

借用减少复制但增加生命周期和边界约束，clone 简化所有权并可能降低复杂度，零拷贝只有在数据规模/热点足够大时才值得。先用 profile 证明复制是瓶颈，再选择切片、Cow、Arc 或移动；不要为追求零拷贝让 API 难以维护或把数据生命周期绑定到临时缓冲区。

### Debug、Release 与溢出语义

优化级别、溢出检查、断言和内联策略会影响性能以及部分错误行为；性能必须在接近生产的 release 配置、固定数据和工具链上测量。整数运算不能依赖“当前模式刚好如何处理溢出”，应显式使用 checked/saturating/wrapping 等语义。

### 固定负载下的性能分析

先固定工具链、依赖、release 配置、硬件和工作负载，再分别观察吞吐、尾延迟、分配、存活内存与下游等待。基准用于比较受控输入，采样 profile 用于定位调用栈，异步 trace 用于理解等待与调度，不能互相替代。

例如 clone 出现在热点栈中，还要确认复制字节量、频率与请求延迟贡献；用借用替换后，再比较生命周期复杂度和实际收益。优化要同时检查吞吐、错误率与资源成本。

### 从抽象成本到测量证据

不同抽象增加的成本并不相同：Arc 维护共享引用计数，Mutex 引入等待，dyn Trait 可能增加动态调用，泛型单态化可能增加二进制体积。它们也各自提供能力，不能只因存在开销就删除。

选择工具应对应问题：请求 trace 解释一次等待，采样解释 CPU 时间，分配分析解释内存，二进制分析解释体积。先说明哪项成本影响当前目标，再按同一基线验证改动。

## 让构建结果能够交付

运行说明连接产物、配置与外部服务，工具命令则分别检查格式、类型、行为和性能。

### 服务的运行说明与交付质量

README说明怎样运行和测试，并列出所需配置与外部服务。

服务约定分别说明输入限制、错误分类、日志/Trace、并发上限、超时与取消、安全默认值，以及数据库或对象存储可以怎样替换。

测试覆盖成功、非法输入、下游失败、重复请求与优雅退出。尚未解决的生产问题另行记录，写出当前取舍与可衡量的下一步。

### 常用工具的职责

`cargo check` 检查类型和借用，`cargo test` 运行测试，`cargo fmt --check` 检查格式，`cargo clippy` 提供额外静态诊断。性能数据使用合适的 release 配置，同时记录工具链、依赖、输入与机器；通过编译和测试只覆盖实际检查的路径。
