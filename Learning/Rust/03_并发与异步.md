# 03 并发与异步

所有权约束跨线程的数据流，运行时负责推动异步 Future。先理解线程、同步和任务调度，再讨论取消、背压及退出。

## 线程之间怎样转交和共享数据

所有权可以随消息转交，也可以通过 Arc 共同持有。Send/Sync 与同步原语限制数据如何跨线程使用，通道容量限制生产方能领先多少。

### 线程与异步任务

线程是操作系统调度的执行单元，适合 CPU 并行和阻塞工作；异步任务围绕 Future 保存执行状态，由运行时调度，适合大量 I/O 等待。async 不会自动让 CPU 计算并行，长时间不 yield 的任务会阻塞同一 executor 上的其他任务。

### Channel 的所有权与容量

发送通常把值的所有权转移给接收方，避免双方同时修改同一对象；发送者全部释放后接收端能观察到关闭。无界 channel 可能让生产速度差异变成内存增长，有界 channel 才能形成背压；错误、取消和 receiver 退出都要有明确处理。

### Arc 与 Mutex

Arc 提供跨线程共享所有权，Mutex 保护内部可变数据；它能让多个任务安全访问同一资源，但不自动避免死锁、饥饿、长临界区和业务状态错误。锁的持有范围要尽量短，不要在同步锁内跨越不可控 `.await`，并按所选锁类型处理失败与恢复。

### 示例：有界 Channel 转移数据所有权

```rust
use std::sync::mpsc::sync_channel;
use std::thread;

fn main() {
    let (tx, rx) = sync_channel(1);
    let producer = thread::spawn(move || {
        tx.send(String::from("first")).unwrap();
        tx.send(String::from("second")).unwrap();
        // tx 离开作用域，接收端消费完缓冲后观察到关闭。
    });
    let received: Vec<String> = rx.into_iter().collect();
    producer.join().unwrap();
    assert_eq!(received, vec!["first", "second"]);
}
```

容量为 1 时，生产方不能无限领先。主线程先接收再 join；若先 join 而生产方正阻塞于发送，就可能互相等待。这个例子使用标准库线程，不依赖 Tokio。

## Future 由运行时推进

理解异步代码先看 Future 何时被 poll、何时返回 Pending，以及唤醒后如何继续。Pin 解决的是需要固定位置的值如何保持有效，和任务数量是两件事。

### Async 函数与惰性 Future

`async fn` 返回一个实现 Future 的状态机对象；调用函数通常只是构造 Future，必须被 runtime poll 才推进执行。`.await` 在 Future Pending 时让任务交还 executor，状态机会保存继续执行所需的数据。创建很多 Future 不等于已经发出了同样多的 I/O 请求。

### Executor、Poll 与唤醒

executor 负责 poll task，task 持有 Future 和调度状态；Future 返回 Pending 时注册唤醒条件，事件就绪后 executor 再次 poll；返回 Ready 时任务完成。不要把 `.await` 描述成“开线程”，它更像在异步状态机上切换执行权。

### Future 的 Send 约束

异步状态机需要在挂起时保存后续执行所需的数据。`tokio::spawn` 要求 Future 满足 `Send`；跨 `.await` 保留的值因此需要能够在线程间转移。共享引用能够跨线程使用则与被引用类型的 `Sync` 约束有关。

`Rc` 如果只在一个独立作用域内使用，并在 `.await` 前销毁，未必妨碍整个 Future 满足 `Send`；若它保存在挂起状态中继续使用，就不能交给要求 `Send` 的任务接口。遇到这类编译错误，先检查跨等待点保留了什么，再调整作用域或所有权。[Tokio 任务与 Send](https://tokio.rs/tokio/tutorial/spawning)

### Pin 与 Unpin

某些 Future 状态机内部可能包含指向自身字段的引用，移动它会使引用失效；Pin 通过类型约束保证值在需要时不再移动，Unpin 表示类型可以安全移动。Pin 不等于堆分配，也不等于异步本身；需要结合自引用、poll 接口和实际 API 解释。

## 等待、阻塞与有界调度

异步等待可以交还执行线程，同步阻塞却会占住它。下面把阻塞隔离、通道容量和执行许可连接起来，再用 Tokio 示例观察挂起与收尾。

### 阻塞工作与运行时线程

同步文件、进程、CPU 计算或阻塞网络会占住 executor 线程，使其他任务无法被 poll；应使用真正异步库、`spawn_blocking` 或专用线程池。spawn_blocking 也有容量和取消边界，必须限制并发并考虑任务已开始后不能强制终止。

### 锁的持有范围与 await

`.await` 可能长时间 Pending，持锁会让其他任务无法进入临界区；如果另一个任务需要这把锁才能推进当前 Future，还可能形成死锁。通常先在锁内读取/更新必要的小状态，再释放锁后执行 I/O；确有必要时使用异步锁并明确公平性、取消和锁竞争。

### 有界异步 Worker Pool

使用有界 channel 发送任务，固定数量 task 消费；每项任务带 deadline 和取消信号，首个关键错误通过共享状态取消兄弟任务，关闭 sender 后等待所有 worker 结束。要处理 receiver 被 drop、任务 panic、生产者过快、超时、部分结果和资源释放。

### 异步池的结构

以 Tokio 为例，有界 `mpsc` 通道负责等待任务，`Semaphore` 或固定 worker 限制执行数，`JoinSet`/句柄集合负责回收任务结果。Tokio 的 `mpsc::Receiver` 是单接收者，不能简单克隆成多个消费者；可由单个调度任务接收，再在许可约束下派发。

取消分为停止接单、停止本地等待、请求正在运行的工作结束。丢弃 `JoinHandle` 通常使任务脱离等待关系；应显式取消并等待，确认资源和业务状态能收敛。具体行为见 [Tokio 任务文档](https://docs.rs/tokio/latest/tokio/task/index.html)，版本以项目锁文件为准。

### 服务背压

对入口请求、任务 channel、worker、连接池、spawn_blocking 和下游调用都设置有限容量；满载时选择等待、拒绝、降级或丢弃低优先级任务，并记录队列等待和拒绝指标。无界 channel、无界 `join_all` 和无限重试会把过载延迟转化成内存/成本事故。

### 示例：Tokio 中有界发送与等待结束

新建临时 Cargo 二进制项目，在 `Cargo.toml` 的依赖区加入以下配置。这里固定 Tokio 1.53.1，以便复现同一组 API；运行环境用当前线程模式即可。

```toml
[dependencies]
tokio = { version = "=1.53.1", features = ["rt", "sync"] }
```

将完整程序保存为 `src/main.rs`：

```rust
use tokio::sync::mpsc;

fn main() {
    let runtime = tokio::runtime::Builder::new_current_thread()
        .build().expect("runtime creation failed");
    runtime.block_on(async {
        let (tx, mut rx) = mpsc::channel::<u32>(1);
        let producer = tokio::spawn(async move {
            tx.send(2).await.expect("receiver closed");
            tx.send(3).await.expect("receiver closed");
        });
        let mut total = 0;
        while let Some(value) = rx.recv().await {
            total += value;
        }
        producer.await.expect("producer panicked");
        assert_eq!(total, 5);
    });
}
```

`block_on` 让当前线程运行这个异步计算；`spawn` 将生产者加入运行时调度。第一个消息占满缓冲区时，后续发送需要等接收方腾出位置；挂起的是异步任务，当前线程仍可运行接收方。生产者结束并释放全部 sender 后，接收方消费完剩余消息，`recv` 返回 None，最后通过 JoinHandle 观察生产者终态。行为约定见 [Tokio mpsc](https://docs.rs/tokio/1.53.1/tokio/sync/mpsc/index.html)。

这个例子通过通道关闭和等待句柄正常收尾。取消需要进一步考虑 Future 被丢弃的位置、等待句柄与已经发生的外部动作。若先等待生产者而完全不接收，容量为 1 的通道就可能让双方无法推进。

## 取消和退出需要完整协议

停止等待、停止任务与撤销外部动作对应不同状态。保存句柄并等待收尾，才能判断本地资源是否释放；外部写入则继续沿业务号恢复。

### Drop Future 与本地取消

很多 Future 被 drop 后会停止本地推进，并依赖 RAII 清理资源；但已经提交到外部系统的写操作不能保证被撤销，取消可能发生在任意 `.await` 边界。设计取消安全时要考虑部分写入、锁、channel、临时文件、子进程和远端未知结果。

### Timeout 与远端未知结果

超时通常结束当前等待并返回错误，远端请求可能已经成功。本地 Future 是否停止还要看具体 API：可安全重复的只读操作能够重试，写操作则需要幂等键、终态查询、补偿或对账，避免把“没有收到响应”当作“没有发生”。

### JoinHandle、select 与取消

`JoinHandle` 表示任务的观察/等待句柄，保存它并 await 才能知道任务是否完成或 panic；`select!` 可在 I/O、取消和超时之间竞争，但被 drop 的 Future 是否安全取消要逐个确认。关闭时广播取消、停止生产、等待 handles，再释放连接和临时资源，不能丢掉 handle 后假设任务已停止。

### 优雅退出与等待任务

停止接收新请求/任务，广播 cancellation，关闭 channel sender，等待 worker 和在途请求在 deadline 内结束，再关闭数据库、HTTP client 和其他资源。外部副作用必须记录状态，超时退出后可由持久化任务和租约恢复；不能靠 runtime 直接 drop 所有 task 就认为业务已安全停止。

## 从类型约束走向运行验证

编译通过说明类型层面的约束成立。运行中的超时、关闭与部分结果还需要可控地制造，观察任务是否结束和状态能否恢复。

### 编译期安全与运行时行为

所有权和类型检查能够排除许多生命周期与数据竞争错误，但锁顺序、业务状态机、部分提交、死锁和资源饥饿仍需要运行时设计。单测、并发压力、取消测试以及日志和 Trace 分别观察这些行为。

### 异步异常路径的可控验证

用可控 channel、barrier、fake clock、测试 server 和注入错误的依赖，覆盖任务正常完成、sender/receiver 关闭、panic、timeout、cancel、下游慢和重复副作用。断言任务已结束、资源已 drop、状态可恢复，避免用随机 sleep 制造“看起来并发”的测试。
