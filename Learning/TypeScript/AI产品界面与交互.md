# AI 产品界面与交互

AI 产品的前端不是把聊天框接上模型，而是把不确定的生成过程、工具状态、权限和人工接管变成用户能理解、能控制的交互。

## 1. 状态先于组件

一个 AI 任务至少要区分：

~~~text
Idle
→ Preparing
→ Streaming
→ AwaitingApproval
→ ExecutingTool
→ Completed
→ Failed / Cancelled / NeedsClarification
~~~

不要只用一个 loading 布尔值覆盖所有状态。用户需要知道系统是在生成、等待外部工具、等待审批、部分成功还是已经失败。

## 2. 交互合同

界面要说明：

- 用户请求会做什么和不会做什么。
- 当前使用的资料、工具和权限范围。
- 结果是否仍在生成，哪些内容可以引用。
- 哪些动作有副作用，是否可撤销。
- 失败后可以重试、修改、接管还是回滚。

模型输出不是 UI 的权限边界。按钮可见性、前端校验和服务端授权必须分别设计。

## 3. 流式和长任务

流式输出需要处理：

- 首字节慢和中途断流。
- 重复事件、乱序和重新连接。
- 部分结果与最终结果的区别。
- 用户取消后服务器是否仍在执行。
- 工具调用和审批状态如何持久化。

长任务不要只在浏览器内存里保存。界面状态、服务端 Run 状态和最终业务事实要有明确边界。

## 4. 错误与接管

错误提示应区分：

- 用户输入需要澄清。
- 权限不足。
- 工具或 Provider 暂时失败。
- 任务部分成功。
- 外部副作用已经发生但响应丢失。
- 系统无法安全判断，需要人工接管。

不要把内部堆栈、密钥、完整 Prompt 或第三方错误原样显示给用户。

## 5. 可访问性与可用性

- 不只用颜色表达状态。
- 键盘、读屏和移动端操作可完成核心任务。
- 生成内容、工具结果和审批按钮有清晰层次。
- 长文本、代码、表格和错误信息可定位。
- 高风险动作的目标、权限、影响和确认语义明确。

用任务完成率、误操作、澄清次数、人工接管、恢复成功和用户信任反馈评估交互，不只看停留时间。

## 6. 项目使用时检查

为一个 Agent 任务画状态机和失败矩阵，覆盖：

- 正常完成。
- 流中断。
- 工具超时。
- 权限拒绝。
- 用户取消。
- 等待审批。
- 外部副作用已提交但响应丢失。

然后用键盘和小屏幕完成一次核心任务，记录不可理解或无法恢复的状态。
