# Prompt 与 Context Engineering

> 递进路径：先会写稳定指令，再理解上下文组装，最后处理多轮交互和污染风险。

## Level 1｜基础认知：Prompt 如何表达任务

### 1. 如何构建稳定的 Prompt 模板？

答：把角色、目标、输入、约束、可用工具、输出 Schema 和终止条件分开写，并让变量有明确类型和默认值。稳定性不能只靠文案，还要配合结构化输出、执行层校验和回归样本。

### 2. System Prompt、User Prompt、Tool Description、Retrieved Context 如何分层？

答：System Prompt 放长期规则和安全边界，User Prompt 放本轮目标，Tool Description 描述能力和适用边界，Retrieved Context 放外部事实并标注为数据而非指令。分层既便于控制优先级，也便于审计和替换。

### 3. Prompt 中如何描述角色、目标、约束、工具、输出格式和终止条件？

答：按“任务目标 → 输入事实 → 可用能力 → 不可违反的约束 → 输出 Schema → 何时调用工具/结束”的顺序组织。约束要尽量可验证，例如字段、范围和禁止动作，不要只写“务必准确”。

### 4. 为什么 Skill 常常放在 System Prompt，而不是 User Query？

答：Skill 是系统能力和行为规则，放在更高优先级的位置可以避免被普通用户输入覆盖，**并保持跨回合一致**。它仍不是权限边界，真实执行必须由工具层重新校验。

### 5. 如何写出清晰、可判别、少歧义的 Skill Description？

答：写清适用条件、不适用条件、输入输出、关键限制和示例边界，避免多个 Skill 使用同一组泛化词。Description 只负责帮助模型选择，服务端还应**通过 allowlist 和参数校验防止误用**。

### 6. Prompt 中应该放示例吗？Few-shot 什么时候有效？

答：当任务有**稳定格式、边界案例或不容易口头描述**的风格时，**少量高质量示例（Few-shot）有帮助**；示例不能代替规则，**也要覆盖负例和异常输入**。示例会占上下文预算，必须通过评测验证它提升了目标任务而不是造成过拟合。

### 7. 如何控制模型的语气、格式、长度和拒答边界？

答：用明确的输出 Schema、字段约束、长度上限和拒答条件，必要时使用结构化解码或服务端校验。语气可以由 Prompt 控制，但**长度、敏感信息和业务权限**必须在应用层兜底。

### 8. 如何用 Schema、Grammar、校验和重试保证 JSON 输出稳定？

答：优先使用 Provider 支持的结构化输出或 Grammar，再用服务端 Schema 校验字段、类型、枚举和业务约束；失败时带最小错误信息重试，超过次数就返回可解释错误。合法 JSON 只表示格式正确，不表示事实正确或动作有权限。

### 9. Prompt 调优有哪些常见误区？

答：常见误区是**堆叠规则、暴露互相冲突的指令**、把权限写在 Prompt 里、用一两个样例代表所有场景，以及只看少量成功案例。每次改动应有版本、对照集、长尾样本和失败分类。

### 10. Prompt 调优中“修好一类问题、坏了另一类问题”怎么解决？

答：建立按**任务类型和风险分层的回归集**，记录**改动影响的分支并做分组评测**，而不是只看总平均分。可以把**冲突规则拆成路由、工具约束或验证器**，避免一个全局 Prompt 同时承担所有场景。

### 11. Prompt 调优到极限后，如何判断换模型、调参数、加约束还是做 SFT？

答：如果问题是格式、权限或流程错误，先加 Schema、Workflow/Harness 和验证；如果是采样随机性，**调参数和稳定解码**；如果是广泛的**能力缺口，换模型**；如果任务分布稳定且有高质量数据，再考虑 SFT。选择要用分桶评测和成本/延迟数据证明。

### 12. 如何为不同模型维护同一套 Prompt？

答：维护一个与 Provider 无关的**任务合同**，再为不同模型写**薄适配层**，包括工具格式、消息角色、解码参数和已知限制。每个模型都跑同一套结构化输出、工具选择、安全和长尾回归，不能只比较主观观感。

## Level 2｜原理机制：上下文工作集如何构建、编排和压缩

### 13. 什么是 Context Engineering？它和 Prompt Engineering 有什么区别？

答：Prompt Engineering 主要优化指令文本，Context Engineering 优化运行时提供给**模型的全部工作集**，包括历史、状态、工具、检索结果、计划和压缩策略。它关注在有限窗口内给模型最相关、可信、可执行的信息。

### 14. 如何构建和编排一个 Agent 的上下文工作集？

答：不要把完整聊天记录、所有工具和检索结果直接拼进 Prompt，而应围绕当前任务生成一个最小、可信、可执行的工作集。可以按上下文的职责分成以下部分：

| 上下文部分         | 典型内容                                      | 优先级与筛选策略                                      | 来源与信任边界                                      | 编排与加载方式                                                 |
| ------------- | ----------------------------------------- | --------------------------------------------- | -------------------------------------------- | ------------------------------------------------------- |
| **不可变规则**     | 系统规则、安全规则、权限、全局约束                         | 最高优先级，通常必须保留                                  | 由系统或应用提供，不能被用户输入、历史或检索内容覆盖                   | 作为稳定规则放在前部，关键约束由执行层重复校验                                 |
| **当前任务与状态**   | 当前目标、用户约束、成功标准、结构化 State、未完成任务            | 高优先级，随任务持续更新；当前目标和关键状态不能丢失                    | 来自用户请求和应用 State，保留版本及变更关系                    | 与当前任务绑定，和历史及外部证据分开                                      |
| **输出与终止要求**   | 输出格式、Schema、长度上限、终止条件、拒答边界                | 必须满足的要求常驻；可验证约束优先于风格描述                        | 来自系统规则或任务合同，用户格式要求仍受上层约束限制                   | 与任务目标一起形成输出契约                                           |
| **历史与记忆**     | 会话历史、任务历史、长期记忆、必要的中间结果                    | 只保留当前任务相关内容；重复内容、已验证且可重新查询的结果可以压缩、转为引用 ID 或丢弃 | 按**会话、任务和记忆类型分层**，保留时间、来源和新鲜度，并经过权限过滤        | 依据当前目标、实体、时间和依赖关系召回，再过滤、重排、去重和预算裁剪；全量历史留在数据库，模型只读取当前工作集 |
| **可用能力**      | Tool Schema、Skill 名称、适用条件、不适用条件、输入输出和最小接口 | 首轮只保留候选能力索引，确定需要后再加载完整内容                      | 能力描述只是选择依据，不等于授权；仍须按用户或租户权限过滤                | 先由轻量目录或路由器召回候选，再加载完整说明、Schema 和脚本                       |
| **执行信息**      | 已验证工具结果、计划、Todo、中间结果、待验证假设                | 已验证事实和未完成计划优先；重复且可恢复的结果可以压缩                   | 工具结果标注来源和状态；计划不等于事实，假设不等于结论                  | 按区块组织，Tool Schema 与工具结果、计划与事实、事实与假设分开                   |
| **外部证据与用户数据** | 检索内容、网页或文档、用户提供的材料、外部记忆                   | 按相关性、风险和预算选择，低相关检索块可以裁剪                       | **默认是不可信数据而非指令**，标注来源和时间；进入工作集前做权限、长度和敏感信息处理 | 作为外部证据区块放置，不能取得系统指令地位                                   |

所有进入工作集的内容都应尽量**保留来源、可信度、时间或版本及当前状态**。实际组装时，先做权限和信任过滤，再召回相关历史、证据和候选能力，按任务优先级与 Token 预算排序裁剪，最后按“不可变规则 → 当前任务与状态 → 输出契约 → 可用能力 → 执行信息 → 外部证据”的顺序形成 Context；动态发现能力也不能绕过服务端的参数校验和副作用控制。

### 15. Todo List 为什么能让模型更聚焦？如何生成、更新和校验 Todo List？

答：Todo List 把长任务的**目标、已完成事实和下一步显式化**，减少模型每轮重新回忆的负担。计划要有**状态、依赖和验收条件**，完成状态只能**由工具结果或验证器推动，不能让模型自报完成**。

### 16. 多轮对话中如何区分新任务、补充信息和纠正信息？

答：比较新消息与当前任务 ID、目标和未完成槽位：**补充信息更新当前 State**，纠正信息覆盖对应事实并标记旧值失效，新目标则创建新任务或明确切换。必要时向用户确认，不能仅凭语气猜测状态迁移。

### 17. 如何设计上下文窗口的 Token 预算？

答：先为系统规则、任务目标、工具、历史、检索和输出**预留预算**，再根据**任务动态分配**；为每类设置最小和最大值，超限时**按优先级压缩**。预算要结合输入/输出 Token、延迟和成本监控，而不是只看模型最大窗口。

### 18. 上下文窗口不够时，如何做摘要、压缩、裁剪、分层和检索？

答：先删除**重复和低相关内容**，再把已验证历史压成结构化摘要，把可重新取得的内容转为引用 ID，最后按任务检索需要的细节。摘要要保留事实、约束、未完成事项、错误和来源，且最好用固定 Schema 验证。

### 19. Summary 如何保留关键事实、约束、未完成任务和工具结果？

答：使用**字段化摘要**，例如 goal、constraints、facts、pending_steps、tool_results、risks、sources，并为每项保留时间/来源。摘要不是自由改写；更新时**增量合并并检测冲突**，关键事实可从原始 State 重新核对。

### 20. 长上下文中的旧信息与新信息冲突时，如何处理？

答：按来源可信度、时间、新鲜度、用户明确纠正和业务状态优先级决定，**保留冲突记录而不是静默覆盖**。对关键事实应调用权威工具或询问用户确认，不能让模型自行选择后直接执行副作用。

## Level 3｜设计取舍：查询改写与交互控制

### 21. 什么是查询改写？什么时候需要做查询改写？

答：查询改写把**口语、上下文依赖或多意图请求**转换成更适合检索/工具调用的**结构化查询**。当原问题缺少关键词、指代不清或需要**拆成多个独立检索时使用**；改写结果要**保留原意并可追踪**。

### 22. 多维度查询改写如何做？

答：先识别时间、实体、权限、业务意图和输出格式等维度，再生成带字段的**候选查询或子任务**，并给每个查询**设置合并规则**。不要无条件生成大量查询，按**收益、预算和重复率限制数量**。

### 23. 如何判断信息不足并让用户补充？

答：定义完成任务所需的**最小槽位和不确定性阈值**，缺少关键槽位时**暂停执行并提出最少、可回答的问题**。问题应说明为什么需要、允许哪些取值，避免让用户重新描述整个任务。

### 24. 如何设计澄清问题，避免一次问太多？

答：优先询问能**最大幅度缩小路径或避免高风险动作的信息**，通常一次问 1～3 个；**可用选项**降低用户负担。已有可信历史可预填但要**允许纠正**，确认前不要产生不可逆副作用。

### 25. 用户中途修改目标时，如何更新计划和上下文？

答：把新消息识别为目标变更事件，**暂停旧计划，记录已完成副作用，重新计算未完成步骤和预算**；无关历史移出当前 Context。若变更会影响已经执行的动作，要**先说明不可逆部分并触发补偿或人工确认**。

### 26. 如何把自然语言需求拆成可执行的结构化任务？

答：抽取目标、对象、约束、输入、输出、工具权限、验收标准和截止条件，生成带 ID、依赖和状态的任务结构。解析结果先由**规则/schema 校验**，**关键歧义由用户确认**，再交给 Planner 或 Workflow 执行。

### 27. 如何处理过长、重复、矛盾或恶意的用户输入？

答：先做**大小限制、规范化、去重和敏感信息处理**，矛盾信息进入**澄清或权威来源校验**，恶意指令按输入数据处理并**拒绝越权部分**。输入错误要返回可理解的**修正建议**，而不是让模型无限尝试。

## Level 4｜场景追问：从 Prompt 走到系统

### 28. 一个 Skill 经常被错误选择，你会先改 Description、路由器、上下文还是模型？为什么？

答：

**诊断步骤：** 用 Trace 和误选样本判断是边界描述重叠、候选集过大、上下文缺少关键字段还是模型能力不足。

**修复优先级：**

| 优先级 | 措施 |
|--------|------|
| 1 | Description 包含互斥条件、输入/输出和"不适用"示例 |
| 2 | 缩小候选集，加确定性前置路由 |
| 3 | 修复上下文槽位 |
| 4 | 高风险工具在执行层验证资源和参数 |

**追问：两个 Skill 内容不同但 Description 相似时，如何避免误选？**

在通用诊断基础上，为 Description 增加互斥的适用条件、输入输出和明确的“不适用”例子，路由时先分类再给模型小候选集；高风险或易混淆能力加入确定性前置校验和回归题，必要时合并为一个带显式分支的 Skill。

每次**只改一层**并用**混淆矩阵验证**，不能直接换大模型掩盖工具设计问题。只有格式、候选和约束都正确仍稳定误选，才考虑换模型或训练。

### 29. 上下文窗口只剩一半预算，但任务还需要历史、工具结果和检索文档，如何排序和裁剪？

答：先保留系统安全规则、当前目标、未完成计划和关键 State，再保留能直接证明成功的工具结果；**历史和检索内容按相关性、可信度、新鲜度压缩**，低相关内容只**保留引用 ID**。若仍不足，暂停并请求用户**缩小任务**，而不是静默丢掉约束。

### 30. 用户输入要求覆盖系统约束时，Prompt 层和执行层分别如何防守？

答：Prompt 层明确用户内容是**任务数据、系统规则不可覆盖**，并让模型**解释拒绝或请求澄清**；执行层用身份、资源、动作和策略重新授权，**拒绝越权工具调用**。**真正安全性来自执行层**，不能把“模型听话”当作防护。

### 31. 如何通过评测集证明一次 Prompt 改动没有只修好短样本而伤害长尾任务？

答：按任务类型、难度、输入长度、风险和用户群体**分层建立固定回归集**，比较新旧版本的成功率、工具行为、拒答、安全和成本；**长尾分组设置最低门槛**。通过**灰度和稳定分组**观察线上分布，达不到门槛就回滚。
