# 新增题簇：Agent、RAG 与 AI 后端

> 本页只追加本轮交叉场景题，不改动既有分类内容；回答仍需结合当前项目的模型、框架和部署版本复核。

## 一、AI 后端与 Provider

### 1. 一个 Python AI 服务从请求进入到最终返回，应该经过哪些确定性边界？

答：入口先做身份、租户、请求大小和限流，再用 DTO/schema 校验输入；服务层创建带预算和 deadline 的任务，Provider Adapter 统一模型请求、流式事件、usage 和错误；模型只能返回受限的结构化意图或内容，工具/业务执行器还要做权限、资源状态、幂等和结果校验。最终返回区分增量事件、任务状态和最终答案，不能把 FastAPI 返回 200 当作业务成功。

### 2. LLM/第三方接口超时后，如何处理可能已经执行或扣费的未知结果？

答：按“连接未建立、明确拒绝、服务端处理但响应丢失、客户端 deadline”分类；请求带 provider request ID、业务幂等键和预算，明确可重试错误才退避重试。未知结果优先查任务/账单/调用状态，查不到就进入对账或人工队列；每次尝试、Token、费用、模型版本和最终状态都要可追踪，不能盲目重发。

### 3. SSE/Streaming 输出如何处理跨事件边界的敏感词和断线？

答：不能对每个 chunk 独立匹配，因为敏感词可能被拆到相邻事件；要在有限大小的滑动窗口中拼接检测，同时控制缓存长度、延迟和 Unicode 边界。检测到高风险内容时暂停或终止流并记录策略版本，客户端通过事件 ID/序号去重和续接；流中断不代表最终任务失败，最终结果仍要经过完整内容安全、schema 和业务验收。

## 二、RAG 与内容安全

### 4. RAG 的脱敏策略应该放在哪些位置？如何证明脱敏没有破坏召回？

答：摄取时按数据分类和租户策略清理密钥、个人信息和受限字段，索引和缓存保留最小化的权限/版本元数据；查询召回前做权限过滤，Context 组装和输出前再次做字段级检查，日志/Trace/评测集也使用同一套数据治理。用脱敏前后配对集比较 Recall、MRR/NDCG、答案正确率、引用覆盖和越权率，按文档类型、风险等级和长尾查询分桶，不能只看平均召回。

### 5. 非结构化文档接入 RAG 时，如何处理 PDF、扫描件、表格和图片？

答：先按文件类型选择解析器/OCR，保留页码、坐标、表格结构、来源、版本和置信度；解析结果先做质量门禁，再切分、Embedding 和索引。低置信度 OCR、表格关系丢失、重复页和乱码要进入人工或重试队列，答案引用必须能回到原文位置；不能只把整份文件转成纯文本后宣称知识库完成。

### 6. 如何区分“RAG 没召回”“召回了但没用上”和“模型推理错”？

答：先检查金标准证据是否进入候选集，再检查权限过滤、Rerank、去重和 Context 截断；证据在 Context 但回答未引用，属于上下文组织/模型使用问题；证据充分仍得出错误结论，才进入推理/Prompt 诊断。Trace 要保存查询、候选、最终证据、版本和引用映射，评测拆成解析、召回、排序、引用、答案和越权指标。

## 三、框架、状态与平台取舍

### 7. LangChain、LangGraph 和手写 Workflow 应该如何选择？

答：手写代码适合状态少、流程稳定、需要强控制的服务；LangChain 适合复用 Provider、Prompt、Retriever 和 Tool 等组件；LangGraph 适合显式 State/Node/Edge、循环、并行、Checkpoint、interrupt 和流式事件。选择要看状态复杂度、恢复/回放、团队维护和升级成本，不能因为 Demo 代码短就引入框架，也不能把框架 API 当作 Agent 原理。

### 8. 已有 Agent 平台能力时，为什么还要做定制开发？

答：先列出平台已有的模型路由、工具治理、权限、评测、观测和发布能力，再明确业务缺口是数据源、时延/成本、合规、状态模型还是特定交互；定制部分只拥有不可复用的领域差异，通用能力尽量接入平台。回答要说明维护责任、迁移成本、指标收益和失败时的回退方案，而不是用“平台不灵活”概括。

### 9. LangGraph 的 State、Checkpoint 和 HITL 如何形成可恢复闭环？

答：State 保存结构化任务事实，Node 做有边界的处理，Edge 决定路由，Checkpoint 保存版本、预算、证据、工具结果和恢复位置；HITL 中断时要保存待审批动作、参数、权限、有效期和 State 版本。恢复时重新读取外部状态、重新授权并校验参数，审批不是永久通行证；并发写入需要版本/CAS 或明确的 reducer，不能只把 Python 对象序列化到内存。

## 四、SRE、可观测与项目表达

### 10. 一个 Agent/可观测平台的数据链路如何从“产生”走到“展示”？

答：服务/SDK 产生结构化事件和 Trace，采集层做采样、脱敏和批量传输，消息或日志管道负责缓冲，存储层按实时查询与长期分析分流，计算层聚合延迟、Token、成本、质量和错误，展示层按租户/版本/任务切片并关联 Runbook。要同时说明丢失、重复、迟到、成本和隐私边界，不能只画“日志进数据库”。

### 11. Agent 在 Linux 上运行时，cgroup、内核版本和 profiling 会如何影响线上结论？

答：cgroup 限制 CPU、内存、进程数和 I/O，容器内看到的资源与宿主机、内核调度和文件系统行为可能不同；内核版本会影响网络、epoll、io_uring、OOM 和观测工具。性能问题先区分应用、Runtime、容器配额和下游，再用同一镜像、内核/资源限制、负载和采样开销复现，不能只在开发机跑 benchmark。

### 12. 如何把一个 RAG/Agent 项目讲出业务价值，而不是只讲调用了模型？

答：先说原流程、用户痛点和验收指标，再说明数据摄取、检索/工具、状态、权限和人工兜底的设计；用任务成功率、引用/召回、人工接管、延迟、Token/费用和安全事件证明收益。还要说明失败案例、为什么不用已有能力、技术取舍和下一步验证；“用了 LangChain/Agent”本身不是项目成果。

### 13. 如何评价 AI 编程工具在团队中的真实收益？

答：把“生成速度”拆成需求澄清、代码审查、测试覆盖、缺陷率、回滚率、交付周期和维护成本，按任务类型和人员经验分桶；要求人类负责边界、权限、依赖和验收，生成代码必须经过测试、静态检查、审查和安全扫描。工具不可靠的场景要有拒用边界，不能用一次 Demo 的代码量证明生产收益。
