# 系统设计与取舍面经补充

> 递进路径：先讲清业务因果链，再回答模型、框架、缓存和知识更新的取舍，最后完成高并发 Agent 系统设计。

## Level 1｜项目表达与架构判断

### 1. 面试时如何用一条因果链讲清 Agent 项目，而不是先背技术栈？

答：按“业务目标与约束 → 输入/输出和成功标准 → 任务如何进入 Loop → State/Memory 如何变化 → Tool/RAG 如何提供证据或动作 → 失败/人工接管 → 指标与本人贡献”讲。框架名只放在对应节点后面，重点说明为什么需要它、替代方案是什么、上线后用什么数据证明有效，以及哪些部分不是自己做的。

### 2. 什么时候应该用图状态机或重型框架，什么时候线性链和普通代码更合适？

答：路径固定、分支少、状态短且需要低延迟时，普通代码或线性 Workflow 更简单；需要条件分支、循环、Checkpoint、暂停恢复、人工协同和可视化状态时，图/状态机有价值。判断不能只看功能清单，要比较开发与调试成本、版本升级、可观测性、故障恢复和团队维护能力。

### 3. 如何判断一个图编排方案是否过度设计？

答：看图中的节点和边是否对应真实业务状态/分支，Checkpoint 是否有生命周期和恢复语义，以及它是否解决了线性代码的可测试、持久化或人机协同问题。如果图只是把“调模型 → 调工具 → 再调模型”换成三个节点，却增加抽象跳转、状态膨胀和排障成本，就应回到更轻的实现，或只在动态节点使用受限 Agent。

### 4. 为什么“模型选得更大”不一定是正确的 Agent 优化方向？

答：很多失败来自工具合同、权限、检索、上下文装配、停止条件或网络，而不是模型知识能力；换大模型可能只增加成本和延迟，还掩盖了系统缺陷。应先用 Trace 和分层对照定位首次偏离，再决定改 Schema/Harness、换模型、调整路由或训练，并用同一任务和安全门禁比较。

### 5. 固定标签、数据充足的任务，为什么常常应先用分类器而不是生成式推理？

答：分类器输出空间受约束、目标函数直接对应 Accuracy/F1、推理快、容易校准和监控；固定标签、样本覆盖充分且不依赖外部知识时通常更稳定。生成式推理只有在标签边界依赖动态规则、长尾语义、外部证据或需要统一承载多种标准时才有优势，而且应约束输出标签/证据/置信度，不能把长篇理由当可靠性证明。

### 6. 多业务标准不统一时，单模型如何避免任务冲突和旧任务退化？

答：把任务 ID、标签定义、规则、输出 Schema 和边界样例显式作为条件，区分共享表示与任务私有头/Adapter/能力；按任务分桶训练、评测和路由，监控新任务加入后的旧任务回归。若梯度、标签或数据分布长期冲突，应拆专家或模型，而不是用一个总分掩盖某个业务的退化。

## Level 2｜性能、成本与稳定性

### 7. 高频核心路径为什么适合缓存、固定模板或直接调工具，而不是每一步都让模型重新推理？

答：高频问题的意图、参数和结果验收稳定时，固定模板/分类路由/直接工具调用能减少模型轮次、Token、延迟和随机性；模型只处理真正需要澄清或组合推理的长尾。缓存必须绑定参数、权限、数据版本和新鲜度，固定路径仍要做结果校验和异常回退，不能为省一次调用跳过业务规则。

### 8. 促销或突发流量下，如何设计 Agent 的分层路由、限流、降级和成本预算？

答：先用轻量分类/规则识别低风险高频路径，复杂或高价值任务再进入强模型和多步工具链；对租户、模型、工具和队列分别限流，设置 Token/时间预算、熔断和背压。过载时可降级到缓存、结构化 FAQ、只读结果或人工队列，但必须明确告知能力范围并保留审计，恢复后再逐步放量。

### 9. 一个 Agent 配置了十几个 Tool，如何降低选错工具和无效并行调用？

答：先按任务类型、资源和权限做候选路由，只把少量相关能力摘要给模型；Tool 描述要包含输入、输出、适用/不适用条件和失败示例，执行器再做 Schema、权限和参数校验。默认只允许必要的并行调用，记录候选集合、选择准确率、无效/重复调用和误触发，按数据优化路由而不是只在 Prompt 里写“请选对”。

### 10. 工具返回超长结果时，如何做剪裁、摘要、分页和后续追问？

答：优先在工具侧按字段、权限、时间和业务相关性过滤，提供分页/游标或聚合接口；需要模型理解时，用可追溯摘要保留原始结果引用、统计范围和截断原因。把摘要和原文分开存储，后续追问能回取原始片段；不能静默截断导致模型误以为“全集只有这些数据”。

### 11. 如何把任务复杂度、风险和实时性用于模型路由？

答：用可解释特征或轻量分类器估计是否需要多步规划、外部证据、代码执行、实时数据和高风险动作，再匹配小/大模型、Workflow/Agent、同步/异步和人工审批路径。路由本身要有低置信兜底，并按任务分桶比较成功率、P95、Token、转人工和安全事件，不能只按问题长度选模型。

### 12. 流式输出、异步任务和后台执行如何共存？用户如何知道任务仍在进行？

答：短任务可以流式返回已验证的进度和可展示文本，但不能把未经执行的计划当结果；长任务应提交带任务 ID 的后台 Job，前端通过事件/轮询看到阶段、工具状态、预计等待和人工请求。最终结果从持久化 State 读取，取消/重试由服务端状态机处理，连接断开不应丢失任务或重复副作用。

### 13. 如何在多租户 Agent 中设计数据权限、工具权限和审计？

答：把用户、租户、会话、资源和操作组成真实授权上下文，检索时做行/文档级过滤，工具执行时再次鉴权，网络和 Sandbox 也按租户隔离。日志记录原始请求、委托链、实际执行者、资源、参数摘要、策略结果和版本，并对敏感值脱敏；模型生成的角色声明、Skill 文本和缓存命中都不能改变权限。

### 14. 线上成本突然上升，你会从哪些维度拆解和止损？

答：按模型、任务类型、租户、Tool、轮数、Token、重试、缓存命中、队列和人工处理拆解 Trace，先判断是流量、输入长度、循环、错误重试、路由漂移还是新功能导致。止损可先限额、关闭非核心 Skill、缩短/压缩 Context、启用小模型/缓存和停止无进展任务，同时保留质量和安全监控；根因确认后再做架构或训练优化。

## Level 3｜知识与系统设计

### 15. 知识更新很快时，Agent 如何决定查实时 API、搜索索引、缓存还是长期知识库？

答：按事实的时效要求、权威性、查询成本和权限路由：当前状态/交易结果优先实时 API，频繁变化的公开内容用带版本和时间的搜索索引，短时间重复读用有 TTL 的缓存，稳定制度和历史知识进长期库。路由结果要携带来源时间、版本和新鲜度，不能让过期缓存覆盖实时事实。

### 16. 如何设计缓存失效、版本切换和过期知识的处理？

答：缓存键包含数据源/租户、查询参数、权限、索引或业务版本和时间条件；更新时用事件失效、版本号或 TTL，读到旧版本则重新获取并记录原因。无法确认新鲜度时应降级为“需要核实”或实时查询，高风险动作不应只依赖过期缓存；版本切换还要支持双读/灰度和回滚。

### 17. 设计一个需要输出长报告的 Agent，如何处理权限、目标读者、证据覆盖、审校和成本？

答：先澄清数据范围、读者、格式、截止时间和证据标准，按权限过滤来源；检索阶段覆盖主题和关键子问题，分析阶段保存带引用的中间事实，写作阶段只读取已验证证据，最后由引用/事实/格式审校器检查。长任务采用分段并行、阶段摘要和预算控制，报告生成失败时保留证据包和部分结果，避免全量重跑。

### 18. 如何判断应该采用单次 RAG、Agentic RAG 还是多个专用检索器？

答：单次 RAG 适合问题边界清楚、一次召回即可覆盖的事实问答；Agentic RAG 适合需要拆解、补检索、跨文档或根据工具结果调整路线的任务；多个专用检索器适合数据源、权限、排序目标明显不同且可独立评测的场景。先做混合检索/重排基线，只有多步检索对长尾、多跳或覆盖率有稳定收益时才承受额外延迟和错误传播。

### 19. 选择或自研 Agent 框架时，如何保留迁移路径、避免版本和供应商锁定？

答：把 Provider、Tool、State、事件、Checkpoint、评测和可观测性抽象成内部稳定接口，业务逻辑不要散落在框架回调和供应商特有字段中；为模型、工具和编排层保留 Adapter 与最小基线实现。选型用真实任务做 POC，记录迁移成本、调试能力、流式/恢复/权限支持和版本策略，重要数据与轨迹用自有格式保存。

### 20. Checkpoint、短期 State 和长期 Memory 应如何分层？

答：Checkpoint 保存能恢复当前执行的版本化状态、待处理事件和幂等信息；短期 State 保存本任务推进所需的结构化字段和最近证据；长期 Memory 保存跨会话且经过筛选、带来源/时间/权限的偏好或经验。不要把海量历史塞进 Checkpoint，也不要让未经确认的对话内容直接升级为长期事实。

## Level 4｜综合场景追问

### 21. 设计一个高并发客服 Agent：既要回答知识问题，又要查询订单并处理高风险操作，如何组织链路？

答：入口先做意图/风险路由：稳定 FAQ 走缓存或检索，订单查询走只读工具，高风险退款/改址进入规则校验、身份确认和人工审批；Workflow 控制状态和权限，Agent 只负责澄清、选择有限工具和组织回答。系统层加入多租户鉴权、限流/队列、缓存新鲜度、工具超时/幂等、流式进度、Trace 和按任务分桶评测，过载时降级到只读/人工而不是继续消耗长链推理。

### 22. 系统平均效果提升但 P95 延迟、Token 和人工接管都上升，你如何决定是否上线？

答：先按任务价值、风险和复杂度分桶，确认收益是否来自关键长尾而不是平均数；比较新增成功率/人工节省/安全收益与 P95、成本、接管和 SLO 违约，并检查是否是重复调用、错误重试或路由失控造成。可只对高价值复杂任务灰度，简单任务保留旧路径；安全硬门禁、预算和延迟不达标时先回滚或修复，不以平均效果掩盖尾部退化。
