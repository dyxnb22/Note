# Agent 生产工程与系统设计

> 递进路径：先画服务边界，再解决并发和成本，接着补可靠存储，最后完成完整系统设计。

## Level 1｜基础认知：服务边界和请求形态

### 1. 如何设计 Agent Gateway？

答：Gateway 负责身份、租户、请求校验、任务创建、模型/工具路由、限流配额、流式协议和 Trace 入口，不直接承担所有业务逻辑。它应把同步短任务和异步长任务统一成可追踪的 task/trace，并将权限和预算传递到下游。

### 2. 如何设计模型路由和多供应商 Fallback？

答：按任务能力、数据敏感性、延迟、成本、上下文和工具协议选择模型，适配器统一消息、工具、usage 和错误；每个 Fallback 必须有兼容合同和预算。切换后记录版本与原因，不能对非幂等任务无脑重发。

### 3. 同步调用、异步任务、轮询、WebSocket 和 SSE 如何选择？

答：短且确定的请求用同步；长任务用异步任务 + 状态查询；需要服务端持续推送可用 SSE，双向交互/协商多时用 WebSocket，轮询最简单但延迟和请求量较高。选择还要考虑断线重连、取消、鉴权、代理兼容和状态一致性。

### 4. 如何把 Agent 中间过程实时推送到前端？

答：把模型、工具、审批、状态和进度统一成版本化事件，服务端以 task/trace ID 推送安全摘要，前端按序号去重和恢复。用户可见事件与内部调试 Trace 分开，断线后从游标/状态补发，而不是重新执行工具。

### 5. FastAPI 的 SSE 如何与 LangGraph 联动，把节点结果实时推给前端？

答：把图运行产生的节点开始/结束、消息、工具和状态事件转换为 SSE `event/id/data`，通过异步生成器发送；客户端用 `Last-Event-ID` 或任务状态恢复，服务端处理断开取消和心跳。节点事件不能直接等同于成功，最终仍需业务验证和持久化。

### 6. 如何设计长任务的任务表、状态机、队列、Worker 和 Checkpoint？

答：任务表保存目标、状态、版本、预算、租户和结果引用；队列投递可重试任务，Worker 用租约/心跳领取，节点在安全边界提交 Checkpoint 和事件。状态机区分 running、waiting、succeeded、failed、cancelled 等，数据库和副作用状态要有一致性/幂等策略。

### 7. 如何实现任务的取消、暂停、恢复、重试和幂等？

答：取消写入持久化标记并传播取消令牌，Worker 和工具在安全点检查；暂停保存待执行动作和 State，恢复先检查版本/外部事实；重试按错误分类和幂等键执行。任务状态变化与幂等记录要能在重启后恢复。

### 8. 跨机器任务接管时，如何避免两个 Worker 同时执行？

答：领取任务时写入有期限的 Lease、owner 和单调版本，Heartbeat 只允许当前 owner 续租；Checkpoint 与完成提交都用 CAS/版本条件，旧 Worker 即使恢复也会因 fencing token 过期而被拒绝。接管前还要核对未完成副作用，不能仅凭租约过期就重放。完整恢复状态机见 [[../12_课程深化/03_Durable与生产运维/Durable与生产运维|Durable Execution 与生产运维]]。

## Level 2｜性能机制：并发、限流与成本

### 9. 如何做限流、配额、优先级和成本预算？

答：入口按用户/租户/全局限制请求，内部按模型、工具、Embedding、队列和并发进一步限制；任务记录 Token、费用、步数和时间预算，调度按优先级和剩余预算处理。限流响应要说明重试时间或降级路径，不能只返回 429。

### 10. 令牌桶、漏桶、固定窗口和滑动窗口如何选择？

答：令牌桶允许一定突发并控制平均速率，漏桶输出平滑但可能增加排队；固定窗口简单但边界突发明显，滑动窗口更精确但存储/计算开销高。根据是要限制平均调用、平滑下游负载还是严格统计选择，并结合分布式一致性和成本。

### 11. 如何控制 Agent 平台总并发和内部 fan-out？

答：入口按租户和优先级配额，任务层限制同时运行数、fan-out 深度和总预算，模型/工具/Embedding 分别设置 Bulkhead 与有界队列；过载时拒绝、延后或降级。监控队列等待、P95、下游错误和 Token 放大，容量由压测决定。单个多 Agent 工作流中哪些子任务可并行，见 [[../05_Multi-Agent与Workflow/Multi-Agent与Workflow|Multi-Agent 与 Workflow]]。

### 12. 如何处理高并发下的请求排队和背压？

答：入口快速判定配额和任务类型，长任务进入有界队列，Worker 按优先级消费；队列满时拒绝、延迟接受或降级，不继续无限堆积。背压信号要传到模型/工具并发层，并给用户可查询的任务状态。

### 13. 如何估算 Token、GPU、内存、网络和数据库容量？

答：先用真实 Trace 得到每任务输入/输出 Token、调用次数、并发、工具结果大小和峰值分位数，再按 QPS、SLO、批处理和冗余计算容量；模型服务看显存/吞吐，状态/Trace 看存储增长和保留期。容量估算必须包含重试、fan-out 和长尾。

### 14. 如何降低延迟？网络、排队、模型、工具、数据库和序列化分别怎么优化？

答：先分段打点找瓶颈：连接复用/地域优化网络，限并发和扩容解决排队，模型路由/缓存/批处理解决推理，工具并行/缓存/超时解决外部等待，索引和字段选择解决数据库，减少大对象和重复序列化。不能只换更快模型而忽略工具等待。

### 15. Prefix Cache、KV Cache 和结果缓存有什么区别？

答：KV Cache 缓存同一生成过程中的注意力 K/V，减少后续 token 重算；Prefix Cache 复用相同前缀的推理状态，适合重复系统 Prompt/上下文；结果缓存直接复用完整请求结果。缓存都要绑定模型/Prompt/数据/权限版本，避免跨租户或过期数据泄露。

### 16. 如何避免缓存脏数据和越权读取？

答：缓存键包含租户、用户/权限 Scope、资源版本、模型/Prompt/索引版本和请求参数摘要，敏感结果默认不跨用户共享；更新/删除事件主动失效，读取前仍做权限检查。缓存命中要写 Trace，便于发现错误复用。

### 17. 如何在质量、延迟、并发和成本之间做取舍？

答：把任务按复杂度和风险分级，简单任务用轻量模型/Workflow，复杂任务增加检索、工具或更强模型；同时设置质量下限、安全门槛和 P95/预算上限。用分桶实验确认节省没有来自漏做验证或降低成功标准。

## Level 3｜可靠工程：消息、存储与高可用

### 18. Kafka、Redis、数据库、对象存储和 OLAP 在 Agent 系统里分别适合放什么？

答：Kafka 适合事件/任务流和可回放消息，Redis 适合短期缓存、限流和低延迟状态，数据库保存任务/业务一致性状态，对象存储保存大文档、代码和 Trace 附件，OLAP 做行为/成本/质量分析。不要把 Redis 当唯一持久化事实，也不要把模型上下文全塞 OLAP。

### 19. Kafka 如何处理消息重复？如何保证消息不丢失？

答：通过生产者确认、持久化、副本、消费者提交策略和重试/DLQ降低丢失；消费端必须幂等，因为至少一次投递会重复。Exactly-once 只在特定边界内成立，外部副作用仍需业务幂等和对账。

### 20. 如何设计消息去重、幂等和重放机制？

答：消息带事件 ID、任务 ID、版本和业务幂等键，消费者在提交副作用前检查持久化去重表/唯一约束；事件本身不可变，重放使用版本/时间范围和安全 Fixture。去重记录要和业务状态有一致性边界，否则可能出现“去重成功但动作没提交”。

### 21. 如何设计 Trace、Event Log 和 replay？

答：事件包含稳定 ID、父子关系、时间、版本、状态、错误、工具/模型摘要和租户 Scope；原始敏感 payload 单独受控。Replay 固定模型/工具响应、输入和知识版本，验证状态转移和停止原因，不重复真实副作用。

### 22. 如何做多租户架构和数据隔离？

答：身份和租户 Scope 贯穿 Gateway、模型、工具、队列、State、Memory、索引、缓存、Trace 和对象存储；查询和缓存键强制带 Scope，服务端再次授权。跨租户聚合只输出脱敏统计，异步 Worker 不得丢失租户上下文。

### 23. 如何做跨区域部署和故障转移？

答：无状态入口可多区域，任务/State 需要明确主从、分片、复制延迟和租约归属；故障转移前确认 Checkpoint、幂等和外部副作用，避免双 Worker 执行。模型/工具提供商也要有区域/供应商 Fallback，跨区域会增加一致性和隐私成本。

### 24. 如何处理模型或工具供应商故障？

答：适配器统一错误并设置超时/熔断/重试，按任务合同切换兼容供应商或降级为只读/固定流程；未完成长任务保留 State，未知副作用先对账。故障策略要在压测和演练中验证，不是线上临时写 Prompt。

### 25. 如何设计系统的容量评估、压测和故障演练？

答：用真实任务分布和最坏 fan-out 生成负载，测模型、工具、队列、数据库、Trace 的吞吐、P95/P99、成本和错误；注入超时、限流、Worker 崩溃、网络断开、重复投递和供应商故障。验收包括恢复时间、任务丢失率、重复副作用和用户可见状态。

### 26. 如何从 Demo 演进到生产系统？

答：先把 Prompt/模型/工具/数据/策略/状态 Schema 版本化，再补身份、权限、预算、持久化、错误合同、Trace、Eval、限流、灰度和回滚。每一步都用任务成功和安全指标验证，不要先扩张 Agent 数量或堆框架。

## Level 4｜系统设计：从需求到上线

### 27. 设计一个企业级文档问答 Agent。

答：离线摄取解析、权限元数据、切分、混合索引和版本；在线根据用户 Scope 召回、Rerank、组装带来源 Context，生成前后做引用/权限/事实校验。长任务和更新走队列与 Checkpoint，Trace 记录文档版本、检索结果、答案和拒答原因。

### 28. 设计一个带 OCR、切分、Embedding、索引和权限的知识库系统。

答：摄取任务可重试且按文档版本幂等，OCR/表格结果保留页码和置信度；索引写入新版本后原子切换，查询使用强制权限过滤和有效版本。删除/权限事件传播到索引和缓存，离线评测拆开解析、召回、排序、引用和越权指标。

### 29. 设计一个可以执行 Python 或 SQL 的数据分析 Agent。

答：模型只提出分析计划/代码，执行器在沙箱和只读数据连接中运行，限制资源、网络和结果大小；输出经过语法、数据行数、类型和关键业务规则校验，再生成解释。代码、输出、数据版本和验证结果写入 Trace，失败时可重试或请求澄清。

### 30. 设计一个广告事件聚合系统，使用 Kafka、Flink、Redis 和 OLAP。

答：事件进入 Kafka 做持久化和分区，Flink 按事件时间窗口聚合/去重，Redis 提供实时热点/状态，OLAP 保存可查询明细和聚合；需要处理乱序、重复、迟到、水位、回溯和 Exactly-once 边界。Agent 只负责查询/分析和策略建议，不直接绕过权限写入指标。

### 31. 设计五十万商品批量上传系统，支持对象存储、异步任务、重试和进度查询。

答：客户端分片上传对象存储，提交文件版本和校验值后创建任务；队列/Worker 分批解析、校验、落库并记录进度，失败项进入可重试/DLQ，最终用版本切换保证商品目录一致。查询进度读任务状态，重试按批次幂等，不能重复写入商品。

### 32. 设计一个代码 Agent，能够查看仓库、编辑文件、运行测试并根据失败结果修复。

答：先用搜索/索引定位相关文件，补丁写入隔离 workspace，命令在资源受限沙箱中运行；测试结果和 diff 作为事实回填，Agent 只能在范围内修复并设置循环预算。每次变更可预览、回滚、审计，不能覆盖用户未提交改动。

### 33. 设计一个支持人工审批的客服 Agent。

答：身份和订单权限先确定，查询/知识回答可自动，退款/改地址等副作用生成结构化预览并进入审批状态；审批后重新校验订单版本并用幂等键执行，结果回写并通知用户。超时、拒绝、断线和未知结果都要有恢复和人工处理路径。

### 34. 设计一个多租户 Agent 平台，支持配额、隔离、观测和回放。

答：入口认证并生成租户 Scope，所有模型、工具、队列、State、Memory、索引、缓存和 Trace 强制带 Scope；按租户/用户/模型/工具配额限流，任务用 Checkpoint 支持恢复。每次运行保存版本和脱敏事件，可在隔离 Fixture 中 Replay，平台层不能让业务 Agent 绕过策略。

## Level 5｜发布、降级与运行控制

### 35. 生产发布、灰度、预算、降级和事故响应如何连成闭环？

答：把代码、模型、Prompt、工具、策略、索引和 State Schema 作为组合版本发布，用稳定分组和 Eval/SLO 比较；入口、任务、模型/工具、队列和执行层共同限制预算与并发。异常时按预案降为低成本、只读、固定流程或人工处理，高风险事故用独立 Kill Switch 撤权并保全证据。详细的版本矩阵、运行中任务、告警和恢复题统一见 [[../12_课程深化/03_Durable与生产运维/Durable与生产运维|Durable Execution 与生产运维]]。
