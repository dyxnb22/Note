# Agent 评测与可观测性

> 层级说明：本页定义基础评测、Trace 和 Badcase 诊断；`12_课程深化/08_评测实验与项目表达` 负责 Harness、隔离场景、Replay 和发布门禁的实验化落地。两者都讨论数据集隔离，但这里回答“为什么/评什么”，深化页回答“如何跑/如何阻断发布”。

> 递进路径：先定义成功，再建立数据集和评分器，最后用 Trace、Badcase 和发布机制形成闭环。

## Level 1｜基础认知：什么叫做得好

### 1. Agent 系统应该评估哪些层次：模型、Prompt、Tool、Workflow、任务和产品？

答：模型层评估生成/推理能力，Prompt/路由层评估意图和格式，Tool 层评估选择与参数，Workflow/Runtime 层评估执行和恢复，任务层评估是否完成目标，产品层评估用户价值、成本和安全。分层能避免最终答案偶然正确掩盖中间错误。

### 2. 如何定义 Agent 的任务成功率？

答：先定义可观察的业务验收条件，再统计满足条件且没有未处理副作用/安全问题的任务比例；部分成功、人工接管和超时要单独计分。不能只用模型自评或字符串相似度作为唯一成功标准。

### 3. 如何评估最终答案正确性、完整性、相关性和可读性？

答：正确性看事实/计算是否符合金标准，完整性看必需字段和步骤，相关性看是否回答目标，可读性看结构、语言和引用；可结合确定性断言、人工标注和受控 Judge。指标要按任务类型和风险分桶，避免平均分掩盖关键错误。

### 4. 如何评估工具选择准确率、参数正确率、调用顺序和不必要调用率？

答：建立带正确工具、必要参数、依赖顺序和可选替代路径的标注集，分别计算选择/参数/顺序准确率和无效调用率；高风险动作还看越权阻断。工具选择正确但最终任务失败时要继续看执行和验证层。

### 5. 如何评估检索 Recall、Precision、MRR、NDCG 和上下文利用率？

答：用查询—相关文档/段落标注计算检索指标，再检查正确证据是否进入最终 Context、是否被回答引用；上下文利用率不能简单等于召回块数量。按题型、文档类型和权限场景分桶，并联合延迟/Token 分析。

### 6. 如何评估幻觉、Groundedness、安全性和拒答质量？

答：构造有证据、无证据、冲突证据、恶意内容和高风险动作样本，检查回答是否有支持、是否会安全拒答、是否越权或编造工具结果。Groundedness 不能只看引用格式，还要判断引用是否真正支持具体结论。

### 7. 如何同时评估质量、延迟、Token、成本和稳定性？

答：把任务成功、P50/P95/P99 延迟、TTFT、输入/输出 Token、单任务费用、错误/超时/重试率放在同一个实验报告中，按模型、任务、租户和版本分桶。上线门槛用多目标约束，不能用降低质量换来的低成本称为优化。

### 8. 如何判断 Agent 是否真的节省了用户时间？

答：比较基线流程和 Agent 流程的端到端完成时间、人工操作数、重试/纠正次数、转人工率和任务成功率，并控制用户和任务难度差异。只看模型响应时间不够，工具等待和用户确认也应计入。

## Level 2｜评测机制：如何测量质量

### 9. 没有标准答案时如何评测？

答：把任务拆成可验证约束、必要事实、工具轨迹、风险和输出质量，使用规则断言、执行结果、人工标注和多维 Judge 组合评分。允许多种正确答案时评估是否满足目标和安全边界，而不是要求文本完全一致。

### 10. LLM-as-a-Judge 的优点、问题和改进方法是什么？

答：优点是能评估开放式质量、规模化和解释性较好；问题是偏好偏差、对 Prompt 敏感、可能被格式/模型风格影响，甚至与被测模型同源。用明确 rubric、参考证据、盲评/多评委、人工校准和确定性断言约束它，并监控 Judge 与人工的一致性。

### 11. 如何构建人工标注规范和一致性检查？

答：先定义任务成功、部分成功、安全违规和可接受答案的正反例，再规定字段、等级、证据和不确定处理；多标注员独立标注，测一致性并复盘分歧。标注规范要随 Badcase 更新并版本化。

### 12. 如何构建离线数据集、沙箱、回放集和回归集？

答：离线集覆盖代表性任务和长尾，沙箱提供可控工具/数据，回放集固定历史失败轨迹，回归集包含每次修复和安全边界案例；每条样本保存目标、约束、版本和评分器。避免把生产敏感数据未经脱敏直接复制。

### 13. 如何避免评测集泄漏、重复和过拟合？

答：按用户/模板/实体去重，训练/调优/验证/测试隔离，保留隐藏集和新分布集；限制对测试集的手工调参次数并记录变更。线上随机抽样和新 Badcase 定期加入，但要冻结一部分基准集用于长期比较。

### 14. 如何处理模型输出的随机性？

答：固定能固定的版本、参数、工具 Fixture 和随机种子，对任务做多次运行并报告均值、分位数和失败率；高风险任务用确定性约束和验证器。不要因为一次成功样本就判定系统可靠。

### 15. 如何设计 benchmark，保证不同方案在相同环境下公平比较？

答：固定任务集、输入、知识/工具环境、权限、模型预算和评分器，只改变一个方案变量；记录版本、调用次数、Token、延迟和失败路径。对不同方案能力不一致时明确允许能力集合，避免基线被人为限制或候选方案带入额外信息。

### 16. 如何做 Prompt、模型、工具和策略的 A/B 测试？

答：固定稳定分组键，把用户/任务随机分到版本，保持数据、预算和评测一致；同时看任务成功、长尾、安全、成本、延迟和人工接管。高风险改动先影子流量/小灰度，预先定义停止和回滚条件。

### 17. 如何做线上离线一致性评测？

答：把线上真实 Trace 脱敏后回放到冻结的模型/工具 Fixture，比较离线评分与线上任务结果/人工反馈；差异通常来自数据新鲜度、随机性、外部依赖或版本漂移。记录环境和版本，不能只重放一段 Prompt。

### 18. 如何验证一个优化确实提升了长尾场景，而不是只提升平均分？

答：按任务难度、输入长度、业务分支、风险和用户类型分桶，设置每个关键桶的最低门槛并观察置信区间；同时比较最差分位数和失败类型分布。平均分提升但关键桶退化时不应直接上线。

## Level 3｜诊断方法：如何知道错在哪里

### 19. 如何把线上 Badcase 自动回流？

答：按错误/低反馈/人工接管/安全告警触发采样，脱敏后保存任务、Trace、版本、工具结果和用户目标，自动分类并进入标注队列；确认根因后选择回归、Prompt、工具、数据或训练修复。回流样本要去重、分级和可追溯。

### 20. 如何给 Badcase 分类：路由、上下文、检索、工具、规划、模型、执行还是展示？

答：沿运行链路寻找第一个偏离验收条件的节点：候选路径错是路由，必要事实没进 Context 是上下文/检索，工具选择/参数错是 Tool，步骤和依赖错是规划，执行状态/副作用错是 Runtime，事实对但表达错是展示。分类要指向可修改组件。

### 21. 如何从 Trace 中定位第一个错误节点？

答：按时间和父子关系回放 State 转移，先看停止原因和成功证据，再逐个比较 Context、模型输出、工具输入输出、授权和验证结果；第一个不满足 Schema/前置条件或引入错误事实的事件通常是根因。后续错误可能只是传播。

### 22. Trace 应该包含哪些字段？

答：至少有 trace/task/tenant ID、父子关系、版本、状态转移、模型请求摘要与 usage、工具调用/授权/审批/结果状态、检索来源、验证结果、耗时、错误码和停止原因。原始敏感内容单独受控，公共字段稳定便于查询和评测。

### 23. 如何设计结构化日志和关联 ID？

答：请求生成 trace_id，任务、模型调用、工具调用和外部请求各有稳定 ID，并通过 parent_id 关联；日志用结构化字段而非只写字符串。ID 要贯穿网关、队列、Worker、模型适配器和工具服务，同时做脱敏和租户隔离。

### 24. 如何追踪一次请求跨越的多个 Agent、模型、工具、队列和数据库？

答：使用分布式 Trace 的 span/event，把 task_id/trace_id 作为传播上下文，记录每个边界的版本、状态、耗时、错误和输入输出摘要；异步队列保存父任务和事件 ID。不要只依赖框架节点名，因为真实副作用可能发生在框架之外。

### 25. 如何回放一次历史 Agent 运行？

答：冻结用户目标、Context 版本、模型响应、工具响应、知识版本和策略，再在隔离环境按原事件顺序执行；真实支付、写库等副作用全部替换为 Fixture。回放结果和原 Trace 对比，能定位是代码、模型、数据还是外部状态变化。

### 26. 如何识别“最终答案错，但每个工具结果看起来都合理”的问题？

答：检查工具结果是否覆盖目标、Context 是否正确组织、模型是否错误合并/推断、验证器是否缺失；设计跨工具一致性和最终验收检查。局部结果合理不等于任务结论合理，必须有端到端任务级评测。

### 27. 如何做失败路径分析？

答：把 Trace 转成状态转移和错误序列，按第一个错误节点、停止原因、重试/回退路径、资源消耗和用户影响聚类，找出高频/高风险组合。每个修复要绑定回归样本和指标，避免只修一个表面案例。

### 28. 如何把 Badcase 反馈到 Prompt、工具、评测集、模型或 SFT？

答：先确认根因再选手段：指令/格式问题改 Prompt/Schema，工具合同或权限问题改执行器，知识问题改解析/检索，能力分布稳定且有数据才考虑 SFT，评测集同步新增回归。所有修复都要比较基线和副作用。

## Level 4｜生产闭环：如何持续变好

### 29. 如何监控延迟、Token、成本、吞吐、错误率、超时和任务成功率？

答：按任务、模型、工具、版本、租户和复杂度记录端到端及分段指标，重点看 P95/P99、每任务而非仅每请求；Token/成本与成功率联合分析。告警要绑定可执行动作，如限流、降级、暂停或转人工。

### 30. 如何建立线上告警和人工抽检机制？

答：为成功率、长尾延迟、工具拒绝/失败、异常重复、预算耗尽、安全事件和人工接管设置阈值与趋势告警；随机抽检高风险/新版本/异常 Trace，脱敏后由标注员复核。告警必须有负责人、Runbook 和回滚/降级动作。

### 31. 如何监控模型选错工具、重复调用和无效规划？

答：保存候选工具集、选择、参数、调用顺序、结果、重复哈希和任务目标，计算工具选择准确率、无效调用率、重复率、无进展步数和任务成功关联。单看工具调用次数会误把必要复杂任务当成低效。

### 32. 如何做版本管理、灰度发布和回滚？

答：代码、模型、Prompt、工具 Schema、策略、索引、State Schema 和评测版本独立记录但组成可回溯版本矩阵；先离线/影子/小流量灰度，再按稳定用户分组扩大。回滚要覆盖所有行为相关对象，并处理已运行任务的状态兼容和副作用。

### 33. 如何在模型输出随机的情况下做线上实验？

答：使用稳定分组和足够样本，固定可控参数和工具环境，报告分布/置信区间而不是单次结果；高风险任务先离线和影子验证。实验中把模型版本、Prompt、随机参数和外部数据版本写入 Trace。

### 34. 如何发现一次改动伤害了某个长尾人群或业务分支？

答：按租户、任务类型、输入长度、语言、风险、模型路由和用户群体切片监控，设置长尾最低门槛和异常分布检测；抽查变化最大的 Trace。发现问题时暂停扩大、回滚或对该分支路由到旧版本。

### 35. 如何为 Agent 设置 SLO、SLA 和安全指标？

答：SLO 定义系统可观测目标，如任务成功率、P95 完成时间、可恢复率和工具可用性；SLA 是对外承诺，通常更保守；安全指标包括越权阻断、敏感泄露、审批绕过、注入成功和审计完整率。指标应按业务风险分级，不要只用 API 200 率。

## Level 5｜场景追问：从一次 Badcase 到版本发布

### 36. 最终答案错误，但检索、工具结果和中间步骤看起来都合理，你会如何定位第一个错误节点？

答：先对照任务验收条件检查证据是否覆盖目标，再逐步查看 Context 的拼装、摘要/截断、模型合并和最终验证；找到第一次丢失约束、错误归因或未执行校验的事件。用固定工具 Fixture Replay 重现，避免仅凭最终文字猜模型问题。

### 37. 一次 Prompt 改动平均分提升，但某类长尾任务下降，如何设计回归集和灰度策略？

答：把长尾任务按业务分支、风险、输入长度和错误类型独立成门禁桶，设置最低分/最大退化阈值；线上按稳定键小流量灰度，实时监控分桶指标，超过阈值停止扩大并回滚。平均分只作为辅助指标。

### 38. 如何证明一个 Agent 优化不仅减少了 Token，还提升了任务成功率？

答：在相同任务集和预算环境下比较成功率、工具行为、延迟、Token、费用和错误分布，确认没有通过少做步骤或降低覆盖换来节省。线上再观察不同复杂度和长尾分桶，只有质量和效率都改善才称为有效优化。
