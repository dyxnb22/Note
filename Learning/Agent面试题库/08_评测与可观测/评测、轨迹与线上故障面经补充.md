# 评测、轨迹与线上故障面经补充

> 递进路径：先定义一次运行和指标，再区分离线/在线、单轮/多轮评测，最后把 Badcase 变成可复现、可修复的工程闭环。

## Level 1｜轨迹与指标

### 1. 离线评测与在线评测的目标、数据和反馈速度有什么区别？

答：完整的“离线评测 / 在线评测 / 生产监控”职责边界见 [[评测与可观测性#38. 离线评测、在线评测和生产监控分别回答什么问题？|主线第 38 题]]。本题只补充两个面试维度：离线使用冻结任务与环境，反馈快、可重复；在线面对真实分布、权限、并发和用户行为，反馈更慢但更接近业务价值。线上 Badcase 需经抽样、标注和归因后再进入稳定回归集。

### 2. 单轮任务和多轮任务应该如何分别评测？

答：单轮重点看输入到输出的正确性、证据、格式、工具选择和一次调用延迟；多轮还要看状态是否正确演化、上下文压缩、记忆污染、用户插入/中断、恢复、重复动作和长程成功率。多轮评测的样本必须包含不同长度、失败恢复和人工接管路径，不能把每一轮拆开平均后假装等价于一次任务。

### 3. 任务成功率、步骤成功率、工具选择准确率和最终答案质量有什么关系？

答：步骤成功是过程信号，工具选择/参数正确是局部能力，最终答案质量是用户可见结果，任务成功还应包含业务副作用和验收条件。步骤都正确不保证目标完成，最终答案看似正确也可能没有真实执行；应同时记录分层指标并建立“哪个步骤失败导致任务失败”的映射。

### 4. 如何衡量 Agent 是否“少走弯路”，而不是只看最终答对没有？

答：在不损害成功率的前提下，比较有效 Tool Call 数、重复调用率、无效 Token、规划改写次数、重试次数、端到端时延、人工接管和单位任务成本；对于必须的多步任务，不能简单把步骤越少当成越好。最好按任务难度分层，并将“更短但漏证据”和“更长但可靠”区分开。

## Level 2｜评测设计

### 5. 新模型上线前，如何设计模型替换评测？

答：冻结同一任务集、工具/知识环境、权限、Prompt、预算和评分器，只替换模型，比较任务成功、关键安全门、工具调用、长尾、P95、Token 和成本。然后做按任务类型的分桶、影子流量和小比例灰度；如果新模型在平均分提升但高风险或某类工具调用退化，应阻止全量发布或只做路由。

### 6. 新增一个 Tool、Skill 或 Middleware 后，如何证明它真的带来收益？

答：做消融实验：固定模型、输入和其他工具，只改变新增能力，并同时保留没有触发该能力的对照样本。除了目标成功率，还要看误触发、选择错误、上下文 Token、延迟、权限拒绝、卸载残留和长尾回归；如果收益来自额外信息而不是设计本身，要把新增信息量纳入对照。

### 7. LLM-as-Judge 有哪些偏差？如何与规则、程序验证和人工评审组合？

答：LLM-as-Judge 的基础优缺点、Rubric、多评委与人工校准见 [[评测与可观测性#10. LLM-as-a-Judge 的优点、问题和改进方法是什么？|主线第 10 题]]。本题只补充验证器分工：格式、数值、代码测试、权限和真实工具状态优先程序验证；开放式质量再交给 Judge；高风险或评审分歧进入人工复核。

### 8. 评测集应该怎样按简单、长尾、对抗、不可回答和高风险样本分层？

答：按任务复杂度、工具依赖、数据新鲜度、权限边界、失败模式和业务风险建立标签，保证每层都有可验证的期望结果。简单集看基本能力，长尾集看覆盖，对抗集看注入/越权，不可回答集看拒答与澄清，高风险集看审批和副作用门禁；汇总分之外必须查看各层和硬性安全指标。

### 9. 采集 Rollout 时，如何处理隐私、敏感数据、用户授权和可删除性？

答：采集前说明用途并按最小化原则只保留调试所需字段，敏感内容做脱敏、哈希、分离加密和访问控制；用户撤回授权或要求删除时能定位并清理相关轨迹及派生索引。训练/评测使用前还要去标识化、审查跨租户泄露和保留期限，不能因为“只是日志”就绕过数据治理。

### 10. 怎样做 Agent Trajectory 的 Replay？哪些部分应该冻结，哪些部分可以重新执行？

答：回放分析通常冻结输入、版本、模型响应、工具响应、权限结果、时间和随机种子，把执行器改为只读 Fixture，避免真实写操作再次发生。若要验证修复，可以只重新执行选定节点并明确替换的变量，同时保存新旧轨迹；外部事实和副作用必须通过模拟、沙箱或幂等对账处理。

### 11. 如何防止评测集泄漏到 Prompt、检索库、示例或训练数据中？

答：对评测样本、近似改写和答案做隔离清单，限制它们进入开发 Prompt、Few-shot、知识库和训练流水线；发布前做文本/语义近邻扫描并保留数据血缘。测试时使用隐藏集、时间切分或真实新样本，发现泄漏后重新构造评测集，而不是继续用已被优化过的分数。

## Level 3｜线上观测与故障闭环

### 12. 线上任务没有即时人工标签时，如何监控 Agent 质量？

答：结合可观测代理指标和延迟标签：工具参数校验失败、无进展率、重复调用、验证通过率、转人工、用户重问/撤销、任务耗时、成本、权限拒绝和抽样人工审查。对关键任务建立延迟回传的业务结果，并按用户、版本、任务类型和租户分桶，避免只看全局平均。

### 13. 如何把用户反馈转化为可执行的 Badcase 修复闭环？

答：先把反馈与 Trace、输入、版本和业务结果关联，再区分需求理解、检索/知识、工具/权限、模型生成、状态推进和产品交互问题；高风险样本由人工复核。修复动作可能是数据/检索、Schema/校验、Workflow/Harness、Prompt/路由、模型或训练，修复后加入分桶回归、影子流量和线上监控，确认没有改善一类问题却伤害另一类。

### 14. 一次 Agent 事故复盘应该包含哪些环节？

答：先保留现场和影响范围，建立按时间排序的 Trace 与配置变更；再定位触发条件、首次偏离、故障传播、检测/拦截为何失效和用户影响。行动项要有负责人、优先级、回归用例、监控/告警和发布门禁，并区分临时止损与根治，不能只写“加强 Prompt”。

### 15. 如何判断问题来自模型、Prompt、Context、RAG、Tool、网络还是 Harness？

答：沿着第一处偏离分层做对照：给模型正确且最小 Context 的基线，替换为固定工具结果，绕过/替换检索，重放网络和权限，检查 State/StopReason，再比较错误是否消失。若输入、证据、工具合同和执行状态均正确仍稳定失败，才更像模型能力；如果某一层替换后恢复，就把修复归因到该层并补对应回归。

### 16. Agent 连续得到相同工具结果却不停止，如何从 Trace 定位并修复？

答：检查工具结果是否写回了正确的 State 版本、模型是否看到结果、解析器是否丢失成功字段，以及任务验收条件是否可判定；随后用参数/结果指纹做重复检测，加入无进展 StopReason 和最大重试。若工具本身缓存或数据未更新，应增加新鲜度和版本信息；若是模型策略问题，再调整 Prompt、路由或更换模型，而不是只提高轮数上限。

### 17. RAG 的召回、工具调用和最终回答各自正常，但整体任务仍失败，如何分析？

答：检查三者之间的接口语义：召回证据是否被正确注入、工具返回字段是否和后续节点 Schema 对齐、时间/权限是否一致、最终验收是否要求了召回和工具没有提供的事实。还要看 State 聚合、引用映射、排序和停止条件；这类问题通常是跨模块契约或目标定义错误，不能只重新调 Embedding 或模型温度。

## Level 4｜发布与场景题

### 18. 离线评测明显提升，但线上成功率下降，你会如何排查？

答：先确认离线集是否泄漏、分布是否变化、线上版本/权限/工具/流量路由是否一致，再按用户、任务、模型版本和长尾分桶比较 Trace。重点检查新模型是否增加 Token/延迟导致超时，缓存是否污染，工具依赖是否受限，以及线上用户目标是否与离线答案评分不同；必要时回滚或缩小灰度，同时把真实失败样本补入隐藏评测。

### 19. 如何为一个可运行数十分钟、允许人工介入的长程 Agent 设计完整评测体系？

答：离线准备多阶段任务、环境 Fixture、故障注入和人工事件，评测目标推进、State/Checkpoint、恢复、取消、权限、证据和最终结果；过程指标包括每阶段成功、重复/无进展、Token、延迟、恢复时间和人工介入质量。线上用任务级 Trace、延迟业务标签、抽样审查和安全硬门禁，发布时做影子/灰度并保留中断、恢复、版本迁移和副作用对账的回归。
