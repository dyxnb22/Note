# Agent 基础与架构｜逐题答案

> 回答顺序：先给定义，再讲运行机制，最后说明边界、取舍和工程约束。下面编号与题目版一致。

## Level 1｜基础认知

### 1. 什么是 Agent？与普通 LLM Chat、Workflow、RPA 和传统后端服务有什么区别？

答：Agent 是围绕目标运行的有限循环：读取状态，让模型提出下一步，校验并执行动作，再根据结果继续或结束。普通 Chat 主要生成一次回复，Workflow 的路径预先确定，RPA 按固定规则操作；Agent 的部分路径由模型根据中间结果动态决定，但权限、事实和成功判定仍应由代码控制。

### 2. Agent 的最小闭环是什么？

答：目标 → 读取当前状态 → 模型决定下一步 → 校验/授权 → 执行工具 → 回填结果 → 判断继续或结束。最小闭环必须有预算上限和明确停止原因，否则只是一个可能无限循环的模型调用。

### 3. 一次 Agent 请求从用户输入到最终回答经过哪些阶段？

答：先解析目标和权限，再加载相关 Context/Memory，调用模型得到文本或工具调用；工具执行器负责校验、授权和执行，结果写回 State 后进入下一轮。最后必须经过成功证据、格式和安全校验，才把结果返回用户。

### 4. Agent 如何理解任务、制定计划、调用工具、观察结果并结束任务？

答：系统先把自然语言目标转成带约束的任务状态，模型根据状态选择直接回答、规划或调用工具；执行器返回事实结果，模型再基于新状态调整计划。结束条件不能只看模型说“完成”，还要看业务验证器是否拿到成功证据。

### 5. Agent 的自主性体现在哪里？自主性越强一定越好吗？

答：自主性主要体现在任务分解、路径选择、工具选择和根据观察结果重规划。不是越强越好；高风险、有副作用或路径稳定的任务应减少自由度，用 Workflow、规则、审批和硬预算换取可控性。

### 6. 什么场景适合 Agent，什么场景应该使用确定性的 Workflow？

答：步骤固定、输入输出稳定、合规要求高的流程优先 Workflow；目标明确但路径取决于检索、工具结果或环境反馈的任务才适合 Agent。通常先做 Workflow 基线，只有动态性带来可测量的成功率或覆盖率收益时才引入 Agent。

### 7. Agent 系统中哪些部分应该由模型决定，哪些部分应该由代码决定？

答：模型适合做意图理解、候选计划、工具选择和自然语言生成；代码应负责权限、参数校验、状态持久化、预算、幂等、沙箱、成功判定和审计。凡是不可逆副作用和安全边界，都不能只依赖 Prompt。

### 8. Agent Framework、Agent Runtime 和 Agent Application 有什么区别？

答：Framework 提供抽象和编排 API，Runtime 负责循环、状态、工具、恢复、观测和执行边界，Application 才是面向具体业务的提示词、工具、数据和产品体验。面试时要能把框架 API 翻译回这些通用机制。

### 9. 如何从 Demo 演进到生产级 Agent？

答：先固定任务合同和成功指标，再补工具合同、权限、状态/Checkpoint、预算、失败恢复、Trace、Eval、限流和灰度发布。生产化的关键不是加更多 Agent，而是让每次运行可控、可解释、可恢复和可回滚。

### 10. Agent 系统最重要的设计部分是什么？

答：最重要的是把模型的开放式决策放在一个可验证的执行边界内：明确 State、工具权限、终止条件和成功证据。架构图上少画一个 Agent，通常比没有边界地增加 Agent 更可靠。

## Level 2｜原理机制

### 11. ReAct 是什么？Reasoning、Action、Observation 如何循环？

答：ReAct 把任务拆成“根据当前信息判断下一步 → 执行动作 → 观察结果”的循环，直到得到答案或触发停止条件。工程实现中不需要暴露模型的私有思维链，只需记录可审计的动作、工具结果、状态变化和停止原因。

### 12. Agent Loop 在什么条件下继续执行、什么条件下结束？

答：有合法工具调用且预算允许时继续；有满足业务验收的成功证据时成功结束；取消、权限拒绝、不可恢复错误、无进展或预算耗尽时停止/失败。每种结束都应有结构化 reason，不能用一个模糊的 `done` 覆盖所有情况。

### 13. Plan-and-Execute 与 ReAct 有什么区别？

答：ReAct 每轮根据最新观察决定下一步，灵活但可能反复探索；Plan-and-Execute 先生成可检查的任务计划，再逐步执行，适合步骤较多且可拆分的任务。计划必须允许失效和局部重规划，不能把初始计划当成事实。

### 14. Reflection、Critic、Self-Consistency 分别解决什么问题？

答：Reflection 让系统对结果或过程进行复盘，Critic 负责按标准找问题，Self-Consistency 通过多次候选和聚合提高部分推理任务的稳定性。它们都会增加调用成本，只有存在可操作的验证标准时才值得使用。

### 15. Router 模式是什么？如何设计路由条件和兜底分支？

答：Router 先判断请求属于哪个领域、复杂度或风险等级，再进入专用 Workflow/Agent。路由条件应尽量可评测，设置低置信度兜底、人工转接和未知类别分支，避免错误路由后继续自动执行高风险动作。

### 16. Planner、Executor、Critic 分别负责什么？

答：Planner 负责把目标拆成可执行步骤，Executor 负责按权限执行工具和状态更新，Critic 负责检查中间产出是否满足标准并提出修正建议。三者不是必须拆成三个模型，固定步骤可以由代码实现。

### 17. 如何让 Agent 判断任务已经完成？

答：定义可检查的验收条件，例如数据库状态、测试通过、引用齐全或业务字段满足约束；由确定性验证器或受信工具产生成功证据。模型文本只能解释结果，不能独立充当完成证明。

### 18. 如何避免每一步重新规划导致路径震荡？

答：把稳定的计划和已完成事实写入 State，只有触发事件或前提变化时才重规划；给计划版本、重规划次数和无进展次数设置上限。还可以让 Planner 输出变更原因，检测来回切换的路线。

### 19. 如何避免 Agent 重复调用同一个工具？

答：在 State/Trace 中保存工具调用摘要、参数哈希、结果和副作用状态，执行器对有副作用操作强制幂等键；Loop 层检测相同动作和无进展。只读查询可以短缓存，但不能用缓存替代权限检查。

### 20. 如何处理计划执行到一半发现前提不成立的情况？

答：先把失败事实写入 State，判断是可修正参数、需要补充信息、需要换路径还是任务不可行；只对可恢复部分局部重规划。已经发生的外部副作用要先对账，不能为了让计划“看起来完成”直接重复执行。

### 21. 长任务应该一次性规划还是边执行边规划？为什么？

答：通常采用分阶段规划：先得到粗粒度计划，执行到检查点后根据事实细化。一次性计划容易被环境变化打破，完全逐步规划又会增加调用和震荡；分阶段方式更容易控制成本、恢复和审计。

### 22. 如何为 Agent 设置最大步数、超时、Token 和成本预算？

答：在任务级 State 中维护步数、墙钟时间、输入/输出 Token、估算费用和并发额度，每次模型或工具调用前预扣/检查预算。达到阈值就进入明确的 stopped、降级或人工接管状态，并保存可解释的部分结果。

## Level 3｜设计取舍

### 23. 单 Agent、多 Agent、Agent + Workflow 如何选型？

答：先用单 Agent 或 Workflow 建立基线，再看任务是否存在清晰的职责边界、可并行性、权限差异或上下文隔离需求。只有拆分后的成功率、可维护性或安全性收益能抵消通信、延迟和故障传播成本时才用多 Agent。

### 24. Master + Sub-Agent 架构的优点和问题是什么？

答：Master 负责任务分解、路由和聚合，Sub-Agent 负责专长执行，适合能力边界清楚的复杂任务。问题是 Master 可能成为瓶颈，子任务状态和错误容易失控，因此需要任务合同、权限边界、超时、结果 Schema 和失败回退。

### 25. 多 Agent 拆分的依据是什么？如何决定任务边界？

答：依据应是目标、工具权限、数据域、验收标准和并发关系，而不是“每个步骤一个 Agent”。一个子 Agent 应有单一职责、明确输入输出、独立错误语义和可测试结果；否则用函数或 Workflow 节点更简单。

### 26. 多 Agent 相比单 Agent 增加了哪些通信、状态和调度成本？

答：增加了消息序列化、上下文传递、状态一致性、调度、结果聚合、权限配置和故障传播成本，还可能重复消耗 Token。设计时要测量每个 Agent 的增量成功率、延迟、成本和失败率，而不是只看最终平均分。

### 27. 如何设计一个客服 Agent、搜索 Agent、数据分析 Agent 或代码 Agent？

答：先定义任务成功证据和不能做的事，再设计最小工具集、状态、权限和人工接管点；随后补检索/执行环境、验证器、Trace、Eval 和预算。不同产品的区别主要在工具和风险边界，不在是否画成多个 Agent。

### 28. 如果让你从零设计一个企业级 Agent 平台，模块如何拆分？

答：至少包括请求入口与身份、模型适配、Context/Memory、编排 Runtime、Tool Gateway、策略/审批、状态与任务队列、Trace/Eval、配置版本和运营后台。平台层提供通用约束，业务层只声明任务、工具和验收标准，避免把权限逻辑散落在 Prompt 中。

### 29. Agent 如何支持暂停、恢复、取消、人工接管和重新执行？

答：把运行状态、待审批动作、已完成步骤和副作用状态持久化到 Checkpoint/任务存储，取消通过协作式信号传播到模型、工具和 Worker。恢复前要校验版本和外部事实，重试通过幂等键和对账避免重复副作用。

### 30. 如何设计 Agent 的状态机？

答：至少区分 running、waiting_human、executing_tool、succeeded、failed、stopped、cancelled 等状态，并为每条转移定义触发事件、前置条件、持久化动作和可重试性。状态机的价值是让恢复、审计和指标有确定语义。

### 31. 如何让长任务跨进程、跨机器持续运行？

答：把任务放入持久化队列，Worker 用租约/心跳领取，节点完成后提交 Checkpoint 和事件；Worker 崩溃后由新 Worker 从最近检查点恢复。外部动作必须幂等或先查状态，不能把任务进度只放在进程内存里。

### 32. 如何处理 Agent 运行中模型、工具、数据库或网络故障？

答：先区分暂时性故障、未知结果、权限拒绝和不可恢复错误；只有幂等且暂时性的调用才限次退避重试。必要时切换模型/工具、降级为只读或固定流程，所有失败都要写入 Trace 并向用户说明任务是否部分完成。

### 33. Agent 如何进行模型路由和多模型 Fallback？

答：依据任务类型、复杂度、隐私、延迟、预算和工具调用能力选择模型，并给每个模型定义可接受的输入输出合同。Fallback 不能只换模型重发；要记录版本、重试次数和结果差异，避免不同模型产生不兼容的工具参数或安全行为。

### 34. Agent 如何接入已有业务系统而不破坏原有流程？

答：从只读、可回放的旁路能力开始，通过适配层复用现有 API 和权限，不让模型直接访问数据库；高风险写操作先预览/审批，再逐步灰度。上线前定义回滚、对账、审计和人工接管，确保 Agent 失败不会改变核心业务事实。

### 35. 如何从业务目标反推 Agent 的能力边界和成功标准？

答：把业务目标拆成用户任务、可观察结果、允许的副作用、错误成本和人工兜底，再决定模型能做哪些决策、工具能执行哪些动作。成功标准要同时包含任务结果、时间/成本、错误率、安全和用户接管率。

## Level 4｜场景追问

### 36. 设计一个客服 Agent：哪些步骤用 Workflow，哪些步骤交给 Agent？

答：身份校验、订单查询、退款规则和审批状态用确定性 Workflow；意图理解、问题澄清和在多个只读知识源之间选择工具可交给 Agent。退款、改地址等副作用动作必须经过权限、规则和必要的人工确认，并用订单状态验证成功。

### 37. 设计一个 Coding Agent：如何处理仓库读取、命令执行、测试和失败恢复？

答：先用索引/搜索定位文件，再以受限 workspace 生成补丁；命令执行在沙箱中，限制网络、时间和文件范围，测试结果作为工具事实回填。每次修改都记录 diff 和 Checkpoint，失败时优先读取错误并小范围修复，不能无限重写或直接覆盖用户改动。

### 38. 设计一个数据分析 Agent：如何保证模型不能跳过计算直接编造结论？

答：让模型只能生成查询/分析计划，实际 SQL/Python 必须由执行器运行；结果经过 schema、数值和数据行数校验后才允许生成结论。把“已执行的代码、输出摘要、验证状态”作为成功证据，并在评测中专门检测假分析。

### 39. 如果单 Agent 已经能完成任务，什么证据能证明拆成多 Agent 值得？

答：至少需要对照实验显示多 Agent 在任务成功率、长尾覆盖、权限隔离或可维护性上有稳定收益，并量化它带来的 Token、延迟、故障和运维成本。若收益只来自更多调用而没有业务指标提升，应退回单 Agent/Workflow。

### 40. 如果线上任务偶发卡死，你会优先检查 Loop、State、工具还是外部依赖？为什么？

答：先看 Trace 的最后状态、停止预算、重复动作和租约/心跳，确定卡在模型等待、工具等待、状态提交还是队列调度；再检查对应依赖。不能直接归因于模型，因为无进展循环、未释放租约和未知副作用都可能表现为卡死。
