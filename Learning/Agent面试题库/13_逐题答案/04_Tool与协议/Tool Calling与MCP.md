# Tool Calling、MCP 与 A2A｜逐题答案

> 回答顺序：先区分模型意图和实际执行，再讲工具合同、失败处理，最后比较 MCP/A2A 的协议边界。编号与题目版一致。

## Level 1｜基础认知

### 1. Function Calling 的完整流程是什么？

答：应用把工具名称、用途和参数 Schema 提供给模型，模型返回结构化的工具调用；宿主解析、校验、授权并执行，再把带 `call_id` 的结果回填给模型，模型决定继续、换工具或结束。模型只产生动作意图，不直接执行代码。

### 2. Tool Calling 与普通函数调用有什么区别？

答：普通函数调用由程序确定函数和参数，Tool Calling 的函数选择和参数往往由模型提出，因此需要处理不确定性、Schema 错误、权限和提示注入。真正执行仍是普通代码，但外面多了一层模型提案和安全执行边界。

### 3. 工具 Schema 应该包含哪些字段？

答：至少包括稳定名称、清晰描述、输入字段及类型/必填/范围/枚举、输出格式、错误码、权限动作、是否有副作用、超时、幂等和结果大小限制。Schema 负责表达合同，服务端还要做业务校验和授权。

### 4. 如何设计清晰、可判别、少歧义的工具 Description？

答：说明何时使用、何时不用、输入前提、输出含义和副作用，并给出互斥的边界例子；不要把多个业务能力塞进一个含糊的工具。Description 只帮助模型选择，不能作为唯一安全控制。

### 5. 工具参数校验应该由模型、服务端还是两者共同完成？

答：两者都做，但职责不同：模型通过 Schema 生成较合法的参数，服务端重新校验类型、范围、资源、权限和跨字段约束。模型校验失败可以提高体验，服务端校验才是安全边界。

### 6. 工具结果如何重新放入模型上下文？

答：执行器返回与调用 ID 配对的结构化结果或稳定错误，适配器转成 Provider 要求的 tool result 消息，再由 Loop 追加到下一轮 Context。结果应限长、脱敏、标记来源，并区分事实数据和外部文本。

### 7. 工具返回过大时如何截断、分页或摘要？

答：优先让工具支持过滤、分页和字段选择，避免先返回全量；仍过大时按任务保留必要字段、生成带引用的摘要，并提供继续读取的游标。摘要不能替代关键原始证据，必要时存对象并只把引用放进 Context。

### 8. 如何设计数据库查询、搜索、代码执行、发邮件和支付工具？

答：每类工具都要有最小权限、明确资源范围、输入/输出合同和副作用标记；数据库优先参数化只读查询，代码执行用沙箱，邮件/支付先预览和审批。高风险工具还要有幂等键、对账、审计和撤销/补偿方案。

### 9. 哪些动作必须经过用户确认？

答：删除、付款、发信、发布、修改权限、提交代码、改变订单等不可逆或高影响动作应确认；确认内容要展示对象、参数、影响和有效期。低风险只读或可逆动作可自动执行，但仍需权限和审计。

### 10. 工具调用如何支持预览、审批、撤销和回滚？

答：先生成结构化 Action Plan 和副作用预览，进入 `waiting_human` 状态并持久化，用户批准后用审批 ID 执行；可逆动作保留反向操作或快照，不可逆动作只能通过补偿和人工流程处理。审批后再次检查权限和资源版本，防止状态已变化。

## Level 2｜原理机制

### 11. 工具调用失败如何分类：模型错误、参数错误、权限错误、业务错误和服务错误？

答：模型错误通常表现为未知工具或不符合意图，参数错误是 Schema/业务约束不合法，权限错误是主体不能操作资源，业务错误是系统拒绝合法请求，服务错误是超时、限流或依赖不可用。分类决定是否修参数、换路径、请求审批还是限次重试。

### 12. 如何设计工具的超时、重试、熔断、降级、幂等和补偿？

答：每个工具声明超时、可重试错误和幂等能力；只对暂时性且幂等的动作做指数退避和上限控制，连续失败触发熔断或降级。副作用未知时先查询状态，不直接重做；不可逆操作准备人工对账或补偿流程。

### 13. 什么操作必须幂等？如何生成幂等键？

答：创建订单、发信、扣款、发布、写数据库等可能产生副作用的操作需要幂等；读取通常天然幂等但仍要考虑时效和权限。幂等键应绑定租户、任务、业务对象、操作类型和稳定的请求摘要，由持久化存储记录结果和状态。

### 14. 工具调用如何避免重复执行外部副作用？

答：执行前查幂等记录或业务状态，提交时用唯一键/事务，执行后记录外部返回和可核对标识；网络超时造成未知结果时先查询再决定。Loop 的重复检测只能作为辅助，不能代替业务端幂等。

### 15. 工具返回的数据如何校验可信度？

答：校验来源身份、Schema、时间、权限、版本和关键字段，再用业务规则或第二个权威查询验证；外部自由文本应标记为不可信数据。可信度不足时让模型引用不确定性、继续查证或请求人工，而不是直接执行下一步副作用。

### 16. 如何防止工具返回值中的恶意指令影响 Agent？

答：把工具结果与系统指令分区并标记为外部数据，限制它只能提供事实，不能改变权限、工具白名单或系统规则；对网页/文档结果做内容扫描和最小化。执行层重新授权，即使模型被诱导也不能越权。

### 17. 如何做工具权限、配额、审计、版本和兼容性管理？

答：工具目录登记版本、动作、资源类型、副作用和所需 Scope，运行时按 actor/tenant/task 动态过滤；配额和并发在入口及工具层共同限制。每次调用记录版本、策略决策、审批、结果状态和耗时，Schema 变更进入回归和灰度。

### 18. 工具数量非常多时，如何做发现、分组、路由、动态加载和淘汰？

答：先按领域、权限和风险建立目录，首轮只给模型小型候选集，确定领域后再动态加载详细 Schema；高频、低风险工具可缓存，长期不用或高歧义工具需要淘汰/合并。工具选择要用混淆矩阵和不必要调用率评估。

### 19. 线上 Agent 选错工具，如何从候选集、Description、参数、上下文和模型分别排查？

答：先看 Trace 中模型实际看到的候选集和 Context 是否包含关键槽位，再检查 Description 是否互斥、参数是否能表达意图，最后才判断模型能力。缩小候选集和补字段通常优先于换大模型，并用离线工具选择集验证修复。

### 20. 并行 Tool Calling 如何提升吞吐，同时保证一致性、顺序和可回放？

答：只并行互不依赖、无冲突的只读或独立任务，给每个调用独立 ID、超时和取消；写操作按资源依赖串行或采用事务/版本校验。聚合结果按稳定顺序写入 Trace，部分失败有明确合并和重试策略。

## Level 3｜协议设计

### 21. 什么是 MCP？它解决了什么问题？

答：MCP 是 Host/Client 与外部工具、资源和 Prompt Server 之间的标准化发现与调用协议，主要解决跨应用复用和能力合同问题。它不等于 Agent Loop，也不自动提供业务授权、可靠恢复或安全合规。

### 22. MCP 与 Function Calling、插件、REST API 有什么区别？

答：Function Calling 描述一次模型到应用的动作提案，REST API 是服务接口，MCP 规定 Host 如何发现并调用跨进程/跨服务的工具、资源和 Prompt，插件通常是产品层集成概念。MCP Server 返回的描述和结果仍是不可信输入，Host 必须保留权限与执行控制。

### 23. MCP Server 如何设计？工具、资源和 Prompt 如何组织？

答：Server 声明能力和版本，Tools 表示可执行动作，Resources 表示可读取资源，Prompts 表示可复用模板；每项都要有 Schema、错误语义、权限边界和版本。Host 根据任务、用户和策略筛选可见能力，不能把 `list` 当成全部允许使用。

### 24. MCP 工具的入参、出参、错误码和版本如何定义？

答：入参用可验证 Schema 和资源范围，出参区分结构化数据、文本和外部来源，错误码区分参数、权限、超时、依赖和未知结果；工具 ID 与 Schema 版本稳定可追踪。兼容升级应支持旧客户端或明确拒绝并可回滚。

### 25. MCP 有什么优点和短板？

答：优点是能力发现、跨 Host 复用、协议边界统一和独立部署；短板是增加网络/进程、认证、版本、供应链、延迟和治理复杂度，且不替代业务权限、Eval 和 Durable Execution。单应用内部函数优先直接 Tool Calling。

### 26. SSE 与 Streamable HTTP 有什么区别？

答：SSE 是服务端向客户端推送事件的流式通道，适合单向进度/结果传递；Streamable HTTP 是面向远程协议交互的 HTTP 流式传输形态，可承载更完整的请求响应和会话语义。实际选型要以协议版本和客户端能力为准，不能只看“能不能流式”。

### 27. MCP 返回结果如何流式传递？

答：Transport 传递进度或增量事件，Client 负责关联调用 ID、处理取消、限速、结果拼接和最终状态；模型 Context 不应每个 token 都无条件回填。对用户推送的进度和用于模型决策的最终结构化结果应分开。

### 28. 没有 MCP 时，大模型调用工具的完整流程是什么？

答：应用本地注册工具并把 Schema 传给模型，模型返回 ToolCall，应用校验/授权/执行后回填 ToolResult，再继续 Loop。MCP 主要把发现和调用的能力合同抽到可复用的 Server/Client 边界，并没有改变这条执行逻辑。

### 29. MCP 如何处理认证、权限、租户隔离和审计？

答：认证确认连接方身份，业务授权还要校验 actor、tenant、resource 和 operation；Client/Server 之间传递或恢复最小 Scope，异步 Worker 重新校验。每次发现、调用、拒绝、审批和结果都写入带版本的审计 Trace，不能把长期用户 Token 放进模型 Context。

### 30. MCP 工具如何做超时、重试和取消？

答：Client 为每次调用设置预算和取消信号，Server 也应有自己的超时；只对可确认幂等的暂时错误限次重试，未知副作用先查状态。取消要传播到网络、Server 和执行任务，取消失败则记录为未完成/未知状态并进入人工或对账。

## Level 4｜设计取舍

### 31. A2A 解决了什么问题？什么时候应该用 A2A？

答：A2A 主要用于 Agent 之间发现能力、委派任务、传递状态和结果，适合跨团队/跨系统的 Agent 协作；同一应用内部的函数或工具不必先引入 A2A。使用前要明确任务合同、身份、权限、进度、超时、回退和结果可信度。

### 32. MCP、A2A 和普通 Function Calling 的本质区别是什么？

答：Function Calling 是一次模型调用提出动作，MCP 是 Host 与工具/资源服务的能力协议，A2A 是 Agent 之间的任务委派与协作协议。三者可以组合，但都不自动解决业务成功判定、权限、可靠恢复和评测。

### 33. 什么时候用 API，什么时候用 MCP，什么时候让一个 Agent 调另一个 Agent？

答：单一业务、强类型、稳定调用优先 API/内部函数；多个 Host 需要发现和复用独立工具时考虑 MCP；需要跨边界委派一个有自己状态、计划和验收的任务时才用 Agent-to-Agent。协议复杂度必须有复用或自治收益支撑。

### 34. 如何设计跨团队、跨语言、跨供应商的工具协议？

答：先定义与语言/SDK 无关的输入输出、错误、权限、版本、幂等、超时和审计合同，再用适配器接入各实现；所有外部结果都带来源和可追溯 ID。兼容性用契约测试、版本协商和灰度验证，不依赖某个框架的内部对象。

### 35. 如何保证协议升级时的向后兼容？

答：Schema 采用向后兼容的新增字段和可选能力，保留旧版本解析与错误语义，先协商能力再使用新特性；重要变更做双读/双写、契约测试、灰度和回滚。运行 Trace 必须记录协议和工具版本，避免无法解释历史任务。

### 36. 一个工具既可以通过 REST API 调用，也可以封装成 MCP，你会如何选择？

答：如果只有一个应用、调用合同稳定且需要最大可控性，直接 REST/内部 Tool 更简单；如果多个 Host 需要发现、复用和独立部署，MCP 才有价值。无论哪种方式，业务权限、幂等、审计和错误语义都由系统负责。

### 37. 一个高风险工具被模型正确选中但参数有误，哪一层负责阻断？

答：Schema 负责第一层格式检查，服务端业务校验、资源权限和审批策略负责最终阻断；模型选择正确不代表有权执行。阻断结果应返回稳定错误或进入审批，不应把内部细节暴露给模型或让模型绕过。

### 38. 设计一个支持并行工具调用、取消、重试、审计和回放的工具执行器。

答：执行器接收带任务/调用 ID 的 ToolCall，先做 allowlist、Schema、授权和预算检查，再按依赖图并行调度；每个调用有取消令牌、超时、幂等键和持久化状态，结果统一成成功/失败/未知。Trace 记录决策、版本、耗时和安全摘要，回放使用冻结的工具 Fixture，不重复真实副作用。
