# 编码题与后端基础｜逐题答案

> 回答顺序：先说算法/数据结构，再讲并发与后端机制，最后把答案放回 Agent 的任务、工具和可靠性场景。编号与题目版一致。

## Level 1｜编码基础

### 1. 接雨水。

答：双指针维护左右最大高度，较矮的一侧决定当前位置能接的水；移动较矮指针并更新该侧最大值，时间 O(n)、空间 O(1)。面试时先说明暴力按列求左右最高是 O(n²)，再给双指针不变量。

### 2. LC53：最大子数组和。

答：维护以当前位置结尾的最大和 `best_end = max(x, best_end+x)`，同时更新全局最大值，时间 O(n)、空间 O(1)。核心是局部最优状态只依赖前一个位置，遇到负贡献就从当前元素重新开始。

### 3. LC78：子集。

答：回溯从当前位置开始，递归中选择或不选择每个元素，把当前路径加入答案；每层推进索引，回退时撤销选择，时间 O(n·2^n)、空间 O(n)（不计输出）。若元素有重复需先排序并跳过同层重复。

### 4. 两数之和。

答：遍历数组，用哈希表记录已见值到下标；对当前 x 查 `target-x`，找到即返回，时间 O(n)、空间 O(n)。关键是先查后存，避免同一个元素被使用两次。

### 5. 滑动窗口最大值或最小覆盖子串。

答：滑动窗口最大值用单调队列维护窗口内候选下标，进出队各一次，O(n)；最小覆盖子串用计数器扩张右边界、满足条件后收缩左边界，O(n)。回答时先定义窗口有效条件，再说明每个元素为什么最多进出一次。

### 6. 根据无序边重建路线。

答：若每个节点出度和入度满足唯一链，先建立邻接表和入度/出度，再从起点沿边走并处理分叉；若要求使用全部边且可能有回路，用 Hierholzer 算法从栈构造欧拉路径，时间 O(V+E)。边界包括断链、重复边和不存在唯一起点。

### 7. 计算带障碍棋盘上 Queen、Bishop、Rook 可到达的位置。

答：从棋子所在位置沿各合法方向逐格扫描，遇到边界或障碍停止；Rook 4 个正交方向，Bishop 4 个对角方向，Queen 为两者合集，时间与可扫描格数线性相关。要先澄清“可到达”是否只算一步、是否允许越过棋子/障碍。

### 8. 合并区间和区间覆盖。

答：按左端点排序，维护当前合并区间；下一区间左端点不超过当前右端点就扩展右端点，否则输出并开启新区间，时间 O(n log n)。若端点开闭不同，要先统一比较规则。

### 9. 二叉树遍历、最近公共祖先和树的层序遍历。

答：前/中/后序可递归或显式栈，层序用队列按层处理；最近公共祖先在二叉树中递归返回左右子树命中情况，若左右各有命中当前节点就是答案。要说明空树、节点不存在和父子关系的假设。

### 10. 图遍历、拓扑排序和环检测。

答：无权可达性用 BFS/DFS，拓扑排序用入度队列或 DFS 三色标记；处理完节点数少于总数说明有环。任务依赖调度通常用 Kahn 算法，并维护前驱/后继和失败传播。

### 11. 动态规划：背包、编辑距离和最长公共子序列。

答：先定义 `dp[state]` 的含义和最后一步，再写转移、初始化和遍历顺序；背包要区分 0/1 与完全背包的容量遍历方向，编辑距离看插入/删除/替换，LCS 看相等与不等。面试重点是状态不重不漏及复杂度。

### 12. 根据任务依赖进行调度并检测循环依赖。

答：把任务作为节点、依赖作为有向边，计算入度并用队列执行入度为 0 的任务；完成后减少后继入度，剩余节点表示循环。生产实现还要结合优先级、资源并发、失败重试和租约，不能只返回一个拓扑序。

## Level 2｜工程基础

### 13. 设计 LRU Cache。

答：哈希表 O(1) 找节点，双向链表维护新旧顺序；访问/更新时移到表头，超容量删除表尾，时间 O(1)、空间 O(capacity)。并发服务还要考虑锁、过期、权重、缓存击穿和权限 Scope。

### 14. 设计布隆过滤器，并说明误判处理方式。

答：用位数组和多个哈希函数，插入置位，查询全部命中才认为“可能存在”；它没有假阴性，但有假阳性，不能用于权限或唯一正确性判断。可配合真实数据库二次确认，容量和误判率决定位数/哈希数，删除需计数布隆或其他方案。

### 15. 实现令牌桶、漏桶或滑动窗口限流。

答：令牌桶按时间补充令牌、请求消耗令牌，支持一定突发；漏桶把请求按固定速率排队处理；滑动窗口统计最近时间段请求数，精确但存储/计算较高。分布式实现要用原子操作/脚本、时钟策略、租户 Scope 和拒绝/排队语义。

### 16. 滑动窗口限流结构体有哪些字段？

答：通常包含租户/资源键、窗口大小、限额、当前时间桶/请求时间、计数、清理策略和版本/原子更新信息；分布式场景还要考虑节点时钟和存储过期。实现题中应说明空间上限和并发更新一致性。

### 17. 令牌桶、漏桶和滑动窗口如何比较？

答：令牌桶限制平均速率且允许突发，漏桶平滑输出但会排队，滑动窗口直接限制时间段内次数且边界更公平；选择取决于是否允许突发、下游是否需要平滑和实现成本。模型/工具调用常用多层组合而不是只选一种。

### 18. 实现带指数退避和抖动的重试策略。

答：第 k 次等待 `min(cap, base*2^k)` 加随机 jitter，区分可重试错误并限制次数/总时间；每次重试带幂等键和 trace，不对未知副作用直接重做。退避解决雪崩，jitter 避免大量客户端同时重试。

### 19. 如何实现幂等请求和任务去重？

答：客户端生成稳定幂等键，服务端持久化键、请求摘要、状态和结果，用唯一约束/事务保证并发下只有一个执行；重复请求返回已有状态/结果。任务队列的消息 ID 去重不能代替业务副作用幂等。

### 20. 如何实现可重入锁？

答：锁记录持有者标识和递归计数，同一持有者重复获取只增加计数，释放时递减到零才真正解锁；其他持有者等待或超时。分布式锁还要处理租约、续期、故障释放和 fencing token，不能只依赖过期时间。

### 21. Python 是否真正支持多线程？为什么有 GIL？

答：CPython 的 GIL 使同一进程内通常只有一个线程执行 Python 字节码，因此 CPU 密集型代码难以通过线程并行；I/O 等待、C 扩展或多进程可绕开部分限制。Agent 服务的网络/模型调用适合异步 I/O，但共享状态仍需并发保护。

### 22. Lock 和 RLock 有什么区别？

答：Lock 不允许同一线程重复获取，重复获取会阻塞；RLock 记录持有线程和递归次数，允许同一线程嵌套获取，但必须对应次数释放。RLock 不能解决跨线程竞争，也不能替代事务和分布式一致性。

### 23. 如何处理竞态条件、死锁和饥饿？

答：用最小临界区、固定加锁顺序、超时/尝试锁、不可变消息和事务减少共享写；检测循环等待、锁持有时间和队列等待。Agent 任务更推荐分区 State、幂等事件和队列，而不是让多个模型线程共享可变大对象。

## Level 3｜后端机制

### 24. Redis 常用数据结构和底层机制是什么？

答：String 适合值/计数，Hash 适合对象字段，List 适合队列，Set 适合去重，Sorted Set 适合带分数排序，Stream 适合消息流；底层根据数据类型和大小使用不同编码。回答还应补充过期、持久化、内存淘汰、原子命令/脚本和集群边界。

### 25. Redis 的过期、淘汰、持久化和集群如何工作？

答：过期通过惰性和定期清理，内存不足按策略淘汰；RDB 是快照，AOF 记录写操作，集群按槽分片并处理主从/故障转移。它适合缓存、限流和短状态，但关键任务 State 要有可靠持久化和恢复策略。

### 26. MySQL 索引为什么会失效？

答：常见原因是对索引列做函数/隐式类型转换、前导模糊匹配、联合索引不满足最左前缀、低选择性、范围条件后无法继续使用后列或优化器估计不划算。应结合执行计划和数据分布判断，不能背成“用了函数必然失效”。

### 27. LIKE 在什么情况下会导致索引失效？

答：`LIKE 'prefix%'` 通常可利用 B-Tree 的前缀范围，`LIKE '%middle%'` 或前导通配符通常无法有效利用普通索引；字符集、排序规则和函数也会影响。全文检索、倒排或专用搜索适合复杂包含查询。

### 28. MySQL 事务隔离级别和一致性如何保证？

答：隔离级别从读未提交到串行化逐步减少并发异常，InnoDB 常用 MVCC 处理普通读、锁处理写和当前读；一致性还依赖事务边界、约束和正确的重试。Agent 任务不要把跨服务副作用假设成一个数据库事务，要用 Outbox/幂等/对账。

### 29. MVCC 和 Read View 原理是什么？

答：InnoDB 通过隐藏版本信息和 undo 记录保存行的历史，普通一致性读根据 Read View 判断哪个版本对当前事务可见；写入仍需锁。它减少读写阻塞但不自动解决业务级状态一致性和跨表/跨服务副作用。

### 30. MySQL 中有哪些锁？

答：有表锁、行锁、意向锁、记录锁、间隙锁、临键锁等；InnoDB 根据索引和隔离级别锁定记录/范围，用于并发写和防幻读。面试回答要结合查询是否走索引、锁范围、死锁和超时，而不是只列名称。

### 31. Kafka 分区、顺序性、重复消费、消息丢失和 Exactly-once 的边界是什么？

答：同一分区内按 offset 有序，跨分区不保证全局顺序；至少一次通常会重复，消费者需幂等；生产确认、副本和提交策略降低丢失。Exactly-once 只覆盖特定 Kafka 处理链路，外部数据库/API 副作用仍需幂等和事务边界。

### 32. Kafka 如何保证高吞吐？

答：依靠分区并行、顺序追加写、批量发送/拉取、压缩和顺序消费，消费者组把分区分配给多个实例。吞吐优化会影响延迟、顺序、重平衡和重复处理，需要按 Agent 任务的优先级和可恢复性设计。

### 33. ClickHouse 有什么特性？适合什么场景？

答：ClickHouse 是面向分析的列式 OLAP，适合大规模聚合、扫描和时间序列/事件分析，写入和查询模型与事务型 OLTP 不同。Agent Trace、成本、质量和事件数据可进入 OLAP，但任务状态、权限和幂等事实应放事务存储。

### 34. Kafka 和 ClickHouse 如何配合做事件分析？

答：Kafka 作为事件缓冲和解耦层，消费者/流处理把事件清洗、去重、补充版本和租户字段后批量写入 ClickHouse；要定义迟到、重复、schema 演进和重放策略。查询分析结果不能直接当作生产副作用授权事实。

## Level 4｜场景追问

### 35. 代码单测分支覆盖率怎么统计？代码插桩原理是什么？

答：在运行测试时对语句/分支插入计数探针，记录实际执行路径，再用覆盖分母统计覆盖率；分支覆盖比行覆盖更能发现条件路径缺口。覆盖率是测试范围指标，不等于逻辑正确或 Agent 任务成功。

### 36. 单元测试中的 Mock 如何实现？

答：在依赖边界替换真实模型、工具、数据库或时间为可控对象，预设输入输出/异常并验证调用合同；Mock 不应把实现细节锁死到无法重构。关键链路还要用 Fixture/集成测试验证真实协议、权限和序列化。

### 37. AST/LSP 难以生成单测的代码如何处理？

答：先把副作用和纯逻辑拆开，给工具/文件/网络建立稳定接口；AST 可做结构分析，LSP 可提供符号/类型信息，但无法替代运行时语义。对难生成代码采用人工补充、录制回放和端到端沙箱测试，并降低单测对内部实现的依赖。

### 38. 如何设计可测试的 Agent 代码？

答：把模型适配、Context 组装、策略、工具执行、状态机和验收器分层，依赖通过接口注入；模型/工具用固定 Fixture，Loop 用状态转移单测，关键任务用 Replay/Eval 和集成测试。每次测试都能说明验证的是决策、执行还是业务结果。

### 39. 如何设计一个带 TUI 界面的交互式视频剪辑工具？

答：分为 TUI 交互层、命令/状态层、媒体分析与编辑服务、任务队列和文件存储；长任务异步执行并实时展示进度、日志和取消状态。Agent 可以把自然语言转成受限编辑计划，但实际 FFmpeg/文件操作要校验、沙箱和可回滚。

### 40. 如何设计模块边界、接口、错误处理和并发模型？

答：接口传递结构化输入输出和版本，模块只拥有必要依赖，错误区分参数/权限/依赖/未知结果；CPU/IO 任务分别选择进程、线程或异步队列，并设置背压。边界要方便单测、重试、Trace 和替换实现。

### 41. 如何做代码审查、灰度发布和回滚？

答：审查关注行为变更、权限/副作用、错误/超时、测试和可观测性；发布先离线/影子/小流量灰度，记录版本矩阵和停止条件；回滚不仅是 Git 代码，还要覆盖 Prompt、模型、Tool Schema、配置、索引和 State Schema 兼容。

### 42. Java 类加载机制是什么？

答：类加载通常经历加载、验证、准备、解析和初始化，并由类加载器按双亲委派等机制查找和隔离类；静态初始化发生在初始化阶段。面试重点是类唯一性、父子加载器、打破委派的场景以及类卸载条件。

### 43. 设计一个 Agent 任务队列：如何处理重复投递、超时、租约、取消和恢复？

答：消息带任务/幂等 ID，Worker 通过租约和心跳领取，状态存持久化任务表；超时先判断外部副作用再重试，取消写状态并传播信号，崩溃后从 Checkpoint 恢复。重复投递由持久化幂等记录和业务唯一约束处理。

### 44. 设计一个工具调用网关：如何做限流、权限、幂等、审计和供应商故障转移？

答：网关统一 Tool Contract、身份/租户 Scope、Schema、策略和预算，按用户/工具/下游限流；副作用使用幂等键，所有调用记录版本、授权、耗时、结果状态。供应商故障按兼容合同切换或降级，未知结果先对账，不能直接重复。

### 45. 如何为 Agent 代码设计单测、Mock、回放测试和端到端评测？

答：纯逻辑和状态转移用单测，模型/工具用可控 Mock/Fixture，真实协议/权限用集成测试，历史失败用 Replay，完整任务用离线/线上 Eval。测试报告同时覆盖成功率、工具行为、错误恢复、延迟、成本和安全，而不是只看代码覆盖率。
