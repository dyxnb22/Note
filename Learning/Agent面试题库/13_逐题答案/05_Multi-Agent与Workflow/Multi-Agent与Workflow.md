# Multi-Agent、Workflow 与 Harness｜逐题答案

> 回答顺序：先建立单 Agent/Workflow 基线，再说明拆分收益，最后讲通信、约束、故障传播和场景。编号与题目版一致。

## Level 1｜基础认知

### 1. 单 Agent、多 Agent、Agent + Workflow 如何选型？

答：先用确定性 Workflow 解决固定路径，用单 Agent 解决一个边界清楚但路径动态的任务；只有存在清晰职责、权限隔离或可并行收益时才拆多 Agent。选型必须由任务成功率、延迟、成本和维护复杂度的对照实验支持。

### 2. 多 Agent 相比单 Agent 的收益和代价是什么？

答：收益是职责隔离、专业上下文、并行执行和权限分层；代价是通信、调度、共享状态、结果聚合、Token、延迟和错误传播。没有可测量的收益时，多 Agent 只是把一个问题变成多个不稳定问题。

### 3. Master + Sub-Agent 架构如何设计？

答：Master 负责任务拆分、分派、预算和结果聚合，Sub-Agent 负责有明确输入输出合同的子任务；每个子 Agent 只拿到最小权限和必要 Context。Master 不能盲信子结果，必须校验 Schema、来源、状态和验收条件。

### 4. Planner、Executor、Critic、Router、Supervisor 分别负责什么？

答：Planner 规划步骤，Executor 执行工具和状态更新，Critic 按标准验收，Router 选择路径，Supervisor 协调多个子 Agent。它们可以是节点、规则或同一个模型的不同提示，不必机械拆成五个独立 Agent。

### 5. 多 Agent 拆分的依据是什么？如何决定任务边界？

答：按目标、数据域、工具权限、验收标准和并行依赖拆分，而不是按自然语言段落拆分；每个 Agent 应能独立说明输入、输出、失败和权限。若两个 Agent 需要共享大量上下文或频繁来回调用，通常边界划错了。

### 6. 什么场景适合多 Agent，什么场景只是增加复杂度？

答：研究、复杂客服或跨系统任务中，若子任务相对独立、工具和权限不同且可并行，多 Agent 可能合适；简单问答、固定 ETL、单次工具调用和高度一致流程通常不需要。先建立单 Agent/Workflow 基线再决定。

### 7. Workflow 与 Agent 的边界是什么？

答：Workflow 的节点、顺序和分支主要由代码确定，Agent 的部分路径由模型根据状态动态选择；前者可预测、易测试，后者灵活但不确定。生产系统常用 Workflow 负责骨架、Agent 负责局部决策，并为动态部分加硬约束。

### 8. Workflow 的优点和问题是什么？

答：优点是可解释、可测试、可控、易做权限和 SLO；问题是遇到未知分支需要提前枚举，维护成本可能随场景增长。应把稳定路径保留为 Workflow，把真正需要开放决策的节点封装成受限 Agent。

### 9. 如何让 Workflow 中的某一步具备 Agent 的灵活性？

答：给该节点定义严格输入输出和预算，让模型只在候选动作集合中选择，并由执行器验证结果；Workflow 负责前置条件、后置验收、重试和回退。这样保留全局可观测性，局部获得动态能力。

### 10. 如何避免多 Agent 之间重复劳动、循环调用和责任不清？

答：为每个 Agent 定义能力/权限边界、任务状态和完成标准，消息中携带任务 ID、依赖和已完成事实；设置最大委派深度、调用次数和无进展检测。父 Agent 负责最终验收，子 Agent 不得把未验证的计划当成结果。

## Level 2｜原理机制

### 11. 多 Agent 如何通信？消息、共享状态、黑板和事件总线分别有什么特点？

答：消息适合显式请求/响应和解耦，共享状态便于读取当前事实但并发冲突多，黑板适合多个角色贡献中间结果，事件总线适合异步长任务和回放。选择取决于一致性、实时性、任务规模和审计要求，不能让所有 Agent 直接修改一个大对象。

### 12. 多 Agent 如何共享 State？如何处理状态一致性和并发写入？

答：优先使用分区 State 或子任务结果，父节点在固定聚合点合并；共享字段用版本、事务、乐观锁或事件顺序控制，并定义冲突策略。所有写入都带来源和任务 ID，模型不能决定最终覆盖规则。

### 13. 如何控制 Agent 并发量？

答：同时设置任务级、Agent 级、工具级和租户级并发上限，并通过队列、信号量和背压控制 fan-out；调度时优先级和预算要可观测。并发上限要结合下游限流、平均 Token、P95 延迟和失败率压测得到。

### 14. 哪些子任务适合并行，哪些必须串行？

答：互不依赖、只读、没有共享写冲突的检索或独立分析适合并行；依赖上一步事实、更新同一资源、需要审批或顺序有业务意义的动作必须串行。并行结果还要统一超时、取消、排序和部分失败语义。

### 15. 并行 Agent 的结果如何合并？冲突如何解决？

答：先要求子 Agent 返回结构化结果、证据、置信度和状态，再由确定性聚合器去重、校验和排序；冲突按来源、时间、任务权威性处理，无法判断就标为冲突并人工/权威工具确认。不要让一个模型凭感觉拼接互相矛盾的事实。

### 16. 一个 Agent 如何把任务委派给另一个 Agent？

答：委派请求应包含目标、输入、权限、预算、截止时间、验收 Schema 和回调/结果位置，子 Agent 返回状态、结果引用和失败原因。父 Agent 仍负责授权和最终验收，委派不能绕过租户、工具和人工审批策略。

### 17. 如何设置子 Agent 的权限和能力边界？

答：按任务最小化工具、数据、网络和副作用权限，使用独立身份或短期 Scope，并在工具执行时重新校验。子 Agent 看到的 Context 也要最小化，不能因为父 Agent 有权限就全量继承。

### 18. 子 Agent 失败时，父 Agent 如何重试、降级和接管？

答：读取结构化失败类型，参数错误可修正，暂时依赖故障可对幂等任务限次重试，权限/不可行错误应换路径或停止；结果未知时先对账。父 Agent 要保留部分成功结果，必要时进入人工接管而不是无限重新委派。

### 19. 如何让多 Agent 任务支持取消、暂停、恢复和重放？

答：为整棵任务树设置可传播的取消令牌和状态，关键节点保存 Checkpoint，子任务记录租约、结果和副作用状态；恢复时先检查版本和外部事实。重放使用冻结消息/工具 Fixture，避免真实副作用再次发生。

### 20. 多 Agent 并发会产生哪些性能问题？

答：问题包括模型调用 fan-out、上下文复制、下游限流、队列堆积、结果聚合、锁竞争和尾部延迟放大。优化顺序是减少不必要拆分、限制并发、并行独立读、缓存稳定上下文和使用模型路由，同时监控任务级而非只看单请求延迟。

## Level 3｜工程约束

### 21. 什么是 Harness？它如何约束和增强模型？

答：Harness 是包围模型的确定性执行层，提供工具、Context、状态、权限、验证、预算、恢复和观测。它让模型负责候选决策而不是直接拥有能力，能够把“应该做什么”和“实际允许做什么”分开。

### 22. Harness 与 Skill、Prompt、Tool、CLI 的关系是什么？

答：Prompt 表达规则，Skill 组织可按需加载的能力说明和流程，Tool 执行结构化动作，CLI 是一种具体工具接口，Harness 负责把它们编排、约束、验证和恢复。它们不是同一层，不能用 Skill 文本代替工具权限。

### 23. Harness 如何降低幻觉？

答：让关键事实来自工具或检索，让每个动作有 Schema 和成功证据，并在输出前执行校验、引用检查或测试；不满足条件就要求补证据、降级或拒答。它减少的是“没有执行却声称执行”的空间，不会消除模型所有错误。

### 24. 如何通过 Harness 强制 Agent 先取数据、再执行分析、最后生成结论？

答：把流程拆成状态节点和前置条件：分析节点只能在取数结果通过 Schema/新鲜度校验后运行，结论节点只能读取已执行代码和验证输出。模型可提出计划，但状态机和执行器阻止跳过步骤。

### 25. 如何防止模型跳过工具调用、假装执行或伪造结果？

答：工具执行必须由系统产生带调用 ID、状态和结果的事实，模型文字不能创建成功证据；最终回答引用工具/测试结果，验证器检查证据存在。检测到未执行或结果缺失就停止、重试或向用户说明无法完成。

### 26. 如何让 Agent 的每个关键步骤都可验证？

答：为步骤定义输入 Schema、输出 Schema、验收函数和失败语义，例如查询结果行数、测试退出码、订单状态或引用来源。验证结果写入 State/Trace，后续节点只依赖验证后的字段，不依赖自由文本描述。

### 27. 如何设计模型不可绕过的权限边界？

答：权限检查放在工具执行器、数据库/API 网关和沙箱层，基于真实 actor、tenant、resource 和 operation 计算；Prompt 只作提示。工具目录也按权限过滤，任何模型生成的“我已获授权”都不能改变策略。

### 28. 如何把确定性校验、重试和人工确认插入 Agent Loop？

答：把它们建模为独立状态转移：模型提案 → 校验 → 授权/审批 → 执行 → 验证 → 回填；失败按错误类型进入修正、重试、降级或人工。每个转移持久化，避免在一个 Prompt 里隐含整个流程。

### 29. 如何设计 Harness 的日志、Trace 和回放能力？

答：记录任务、状态转移、模型版本/预算、工具调用、权限决策、验证结果和外部副作用摘要，敏感原文单独受控；回放时冻结模型/工具响应和输入。日志要能回答“模型想做什么、系统允许什么、实际发生什么、为何结束”。

### 30. 如何评估增加 Harness 后的收益和额外成本？

答：对比任务成功率、幻觉/伪执行率、工具错误、人工接管、安全事件、延迟和 Token/开发维护成本。若只是增加规则但没有改善目标指标，或把正常任务阻塞，应缩小约束到真正高风险环节。

## Level 4｜场景追问

### 31. 一个研究任务包含检索、分析、写作三个阶段，你会选择 Workflow、Supervisor 还是多个独立 Agent？

答：如果三个阶段和输出格式稳定，优先 Workflow，检索/分析节点可以内部使用受限 Agent；只有检索来源、分析方法和写作策略高度动态且边界清晰时才考虑 Supervisor/多 Agent。最终写作必须读取已验证证据，并由引用/事实检查收尾。

### 32. 两个子 Agent 对同一个事实给出冲突结论，父 Agent 如何判断、合并或升级人工？

答：比较来源权威性、时间、任务上下文和证据引用，能用权威工具验证就回查；不能判定时保留冲突并向用户说明/升级人工，而不是按置信度数字盲选。冲突事件应写入 Trace 和评测集。

### 33. 多 Agent 的平均效果提升了，但延迟和成本翻倍，如何判断是否值得上线？

答：按业务价值比较任务成功率、长尾收益、人工节省和安全收益与新增成本/延迟/SLO 违约；分用户和任务类型灰度，可能只对复杂或高价值任务启用多 Agent。若简单任务收益不明显，应做复杂度路由而不是全量启用。

### 34. 如果子 Agent 经常重复调用同一个工具，应该修改拆分、通信协议、Harness 还是 Prompt？

答：先从 Trace 判断重复是因为父子状态没共享、任务合同不清、工具结果未被识别还是模型策略问题；优先修复状态/协议和执行层幂等，再优化 Prompt。不能只加“不要重复调用”一句话，因为它没有事实和执行约束。
