# Multi-Agent、Workflow 与 Harness

> 递进路径：先建立单 Agent 基线，再决定是否拆分，随后处理通信、约束和故障传播。

## Level 1｜基础认知：什么时候需要多 Agent

### 1. 如何从 Workflow/单 Agent 基线逐步引入多 Agent？

答：

**演进路径：**

| 阶段 | 适用场景 |
|------|---------|
| Workflow | 路径固定、输入输出稳定 |
| 单 Agent | 边界清楚但路径动态 |
| 多 Agent | 职责清晰、权限隔离、可并行 |

**选型判据（满足任一才考虑拆分）：**

| 判据 | 说明 |
|------|------|
| 职责边界 | 子任务目标是否独立 |
| 可并行性 | 是否可同时执行 |
| 权限差异 | 所需权限是否有层别 |
| 上下文隔离 | Context 是否需要隔离 |

**收益：**

| 收益 | 说明 |
|------|------|
| 职责隔离 | 每个 Agent 只关注自己的领域 |
| 专业上下文 | 子 Agent 拿到更聚焦的 Context |
| 并行执行 | 独立子任务可同时进行 |
| 权限分层 | 不同 Agent 不同权限边界 |

**代价：**

| 代价 | 说明 |
|------|------|
| 消息序列化 | Agent 间通信需要编解码 |
| 上下文传递 | 跨 Agent 传递 Context 增加 Token |
| 状态一致性 | 共享状态并发写入需协调 |
| 调度开销 | 任务分派、优先级、背压控制 |
| 结果聚合 | 多个子结果需要去重、校验、合并 |
| 故障传播 | 子 Agent 失败可能影响父 Agent |
| 延迟放大 | fan-out + 聚合 + 通信叠加 |

**成本收益权衡：** 只有拆分后的成功率、可维护性或安全性收益能抵消通信、延迟和故障传播成本时才用多 Agent。测量每个 Agent 的增量成功率、延迟、成本和失败率，而不是只看最终平均分。

---

**追问：什么证据证明多 Agent 比单 Agent 或 Workflow 更值得？**

在相同任务、模型预算和环境下，多 Agent 应在成功率、长尾覆盖、权限隔离、并行效率或可维护性上有稳定收益，并量化通信、延迟、Token、故障和运维成本。没有基线和消融实验时，"角色更多"不是证据。

---

**追问：三倍 Token 仅换来少量成功率提升，是否保留？**

按任务切片判断那一点提升是否集中在关键长尾或安全场景，并计算人工节省、延迟、可靠性和运维收益；做去掉某个角色、减少上下文或改成 Workflow 的消融。若没有达到业务价值/成本门槛，就回退到更简单的架构。

---

**追问：效果提升但延迟与成本翻倍，是否上线？**

按业务价值比较任务成功率、长尾收益、人工节省和安全收益与新增成本/延迟/SLO 违约；分用户和任务类型灰度，可能只对复杂或高价值任务启用多 Agent。若简单任务收益不明显，应做复杂度路由而不是全量启用。

### 2. Workflow 与 Agent 的边界是什么？

答：

**Workflow 的优缺点：**

| 优点 | 缺点 |
|------|------|
| 可解释、可测试、可控 | 遇到未知分支需提前枚举 |
| 易做权限和 SLO | 维护成本随场景增长 |

**如何让 Workflow 某一步具备 Agent 灵活性：** 给该节点定义严格输入输出和预算，让模型只在候选动作集合中选择，并由执行器验证结果；Workflow 负责前置条件、后置验收、重试和回退。保留全局可观测性，局部获得动态能力。

**原则：** 把稳定路径保留为 Workflow，把真正需要开放决策的节点封装成受限 Agent。

---

**追问：轻量 while Loop、显式 Workflow 和图编排分别适合什么场景？**

固定几步、少量工具和短生命周期任务用普通函数或 Loop 足够；存在明确分支、循环、并行、审批和恢复时用 Workflow/图；复杂框架只有在状态、观测和运维收益能抵消抽象成本时才引入。选型从任务不变量出发，不从框架流行度出发。

---

**追问：如何判断现有项目是否真的需要引入 Agent Framework？**

先画出当前 Loop 的状态、分支、恢复、工具和观测需求；如果普通代码可以清楚表达且没有持久化/并行/人工中断需求，就不必引入框架。只有当显式图、Checkpoint、流式事件或团队协作能明显降低复杂度时才升级。

---

**追问：什么时候用图状态机或重型框架，什么时候线性链和普通代码更合适？**

路径固定、分支少、状态短且需要低延迟时，普通代码或线性 Workflow 更简单；需要条件分支、循环、Checkpoint、暂停恢复、人工协同和可视化状态时，图/状态机有价值。判断不能只看功能清单，要比较开发与调试成本、版本升级、可观测性、故障恢复和团队维护能力。

---

**追问：LangChain、LangGraph 和手写 Workflow 应该如何选择？**

手写代码适合状态少、流程稳定、需要强控制的服务；LangChain 适合复用 Provider、Prompt、Retriever 和 Tool 等组件；LangGraph 适合显式 State/Node/Edge、循环、并行、Checkpoint、interrupt 和流式事件。选择要看状态复杂度、恢复/回放、团队维护和升级成本，不能因为 Demo 代码短就引入框架，也不能把框架 API 当作 Agent 原理。
---

## Level 2｜角色、架构模式与协作机制

### 3. Planner、Executor、Critic、Router、Supervisor 分别负责什么？

答：

| 角色 | 一句话职责 | 所属层级 | 适用场景 |
|------|-----------|---------|----------|
| **Planner** | 把目标拆成可执行步骤 | 单 Agent 内部 | 计划与执行分离 |
| **Executor** | 按权限执行工具、更新状态 | 单 Agent 内部 | 有明确验收标准的产出 |
| **Critic** | 按标准验收产出，提出修正 | 单 Agent 内部 | 产出检查 |
| **Router** | 判断请求该走哪条路径/交给谁 | 多 Agent 编排 | 领域边界清晰的路由 |
| **Supervisor** | 协调多个子 Agent，聚合结果 | 多 Agent 编排 | 动态拆分和聚合 |

前三个是单 Agent 内部的微观循环——规划、执行、验收；后两个是多 Agent 系统的宏观编排。五者不一定要拆成五个独立模型，节点、规则或同一个模型的不同提示都可以实现。

---

**追问：Master + Sub-Agent 架构如何设计？优点和问题是什么？**

| 角色 | 职责 | 设计要点 |
|------|------|---------|
| **Master** | 任务拆分、路由、聚合 | 不能盲信子结果，需校验 Schema、来源、状态、验收条件 |
| **Sub-Agent** | 专长执行 | 最小权限、必要 Context、明确输入输出合同、独立错误语义 |

优点是职责清晰、可独立评测和替换；问题是通信/延迟/成本增加，Master 判断错误会放大失败。演进路径：单 Agent → 规则拆分 → 简单 Master-Worker → 动态 Supervisor → 独立 Agent 服务。

### 4. 多 Agent 如何通信？消息、共享状态、黑板和事件总线分别有什么特点？

答：消息适合显式请求/响应和解耦，共享状态便于读取当前事实但并发冲突多，黑板适合多个角色贡献中间结果，事件总线适合异步长任务和回放。选择取决于一致性、实时性、任务规模和审计要求，不能让所有 Agent 直接修改一个大对象。

### 5. 哪些子任务适合并行，哪些必须串行？

答：互不依赖、只读、没有共享写冲突的检索或独立分析适合并行；依赖上一步事实、更新同一资源、需要审批或顺序有业务意义的动作必须串行。并行结果还要统一超时、取消、排序和部分失败语义。

### 6. 并行 Agent 的结果如何合并？冲突如何解决？

答：

**合并流程：**
1. 子 Agent 返回结构化结果、证据、置信度和状态
2. 确定性聚合器去重、校验和排序
3. 冲突按来源、时间、任务权威性处理

**State 并发写入防护：**

| 措施 | 说明 |
|------|------|
| 字段 owner | 每个字段指定写入者，避免多 Agent 覆盖同一大对象 |
| 写入语义 | 事件、版本/CAS、Reducer 或分区状态 |
| 冲突记录 | 显式记录冲突来源、依据和版本 |
| 仲裁规则 | 按业务规则仲裁，无法判断转人工 |

**关键原则：** 不能用"最后写入者获胜"掩盖错误。不要让一个模型凭感觉拼接互相矛盾的事实。

### 7. 如何避免多 Agent 之间重复劳动、循环调用和责任不清？

答：为每个 Agent 定义能力/权限边界、任务状态和完成标准，消息中携带任务 ID、依赖和已完成事实；设置最大委派深度、调用次数和无进展检测。父 Agent 负责最终验收，子 Agent 不得把未验证的计划当成结果。

---

**追问：子 Agent 经常重复调用同一个工具，应该修改拆分、通信协议、Harness 还是 Prompt？**

先从 Trace 判断重复是因为父子状态没共享、任务合同不清、工具结果未被识别还是模型策略问题；优先修复状态/协议和执行层幂等，再优化 Prompt。不能只加"不要重复调用"一句话，因为它没有事实和执行约束。

### 8. 一个 Agent 如何把任务委派给另一个 Agent？

答：委派请求应包含目标、输入、权限、预算、截止时间、验收 Schema 和回调/结果位置，子 Agent 返回状态、结果引用和失败原因。父 Agent 仍负责授权和最终验收，委派不能绕过租户、工具和人工审批策略。

### 9. 如何设置子 Agent 的权限和能力边界？

答：按任务最小化工具、数据、网络和副作用权限，使用独立身份或短期 Scope，并在工具执行时重新校验。子 Agent 看到的 Context 也要最小化，不能因为父 Agent 有权限就全量继承。

### 10. 子 Agent 失败时，父 Agent 如何重试、降级和接管？

答：读取结构化失败类型，参数错误可修正，暂时依赖故障可对幂等任务限次重试，权限/不可行错误应换路径或停止；结果未知时先对账。父 Agent 要保留部分成功结果，必要时进入人工接管而不是无限重新委派。

### 11. 如何让多 Agent 任务支持取消、暂停、恢复和重放？

答：为整棵任务树设置可传播的取消令牌和状态，关键节点保存 Checkpoint，子任务记录租约、结果和副作用状态；恢复时先检查版本和外部事实。重放使用冻结消息/工具 Fixture，避免真实副作用再次发生。

### 12. 多 Agent 并发会产生哪些性能问题？

答：问题包括模型调用 fan-out、上下文复制、下游限流、队列堆积、结果聚合、锁竞争和尾部延迟放大。优化顺序是减少不必要拆分、限制并发、并行独立读、缓存稳定上下文和使用模型路由，同时监控任务级而非只看单请求延迟。

## Level 3｜工程约束：Harness 如何把模型变得可控

### 13. 什么是 Harness？它如何约束和增强模型？

答：Harness 是包围模型的确定性执行层，提供工具、Context、状态、权限、验证、预算、恢复和观测。它让模型负责候选决策而不是直接拥有能力，能够把"应该做什么"和"实际允许做什么"分开。

### 14. Harness 与 Skill、Prompt、Tool、CLI 的关系是什么？

答：Prompt 表达规则，Skill 组织可按需加载的能力说明和流程，Tool 执行结构化动作，CLI 是一种具体工具接口，Harness 负责把它们编排、约束、验证和恢复。它们不是同一层，不能用 Skill 文本代替工具权限。

### 15. Harness 如何降低幻觉？

答：让关键事实来自工具或检索，让每个动作有 Schema 和成功证据，并在输出前执行校验、引用检查或测试；不满足条件就要求补证据、降级或拒答。它减少的是"没有执行却声称执行"的空间，不会消除模型所有错误。

### 16. 如何通过 Harness 强制 Agent 先取数据、再执行分析、最后生成结论？

答：把流程拆成状态节点和前置条件：分析节点只能在取数结果通过 Schema/新鲜度校验后运行，结论节点只能读取已执行代码和验证输出。模型可提出计划，但状态机和执行器阻止跳过步骤。

### 17. 如何防止模型跳过工具调用、假装执行或伪造结果？

答：工具执行必须由系统产生带调用 ID、状态和结果的事实，模型文字不能创建成功证据；最终回答引用工具/测试结果，验证器检查证据存在。检测到未执行或结果缺失就停止、重试或向用户说明无法完成。

### 18. 如何让 Agent 的每个关键步骤都可验证？

答：为步骤定义输入 Schema、输出 Schema、验收函数和失败语义，例如查询结果行数、测试退出码、订单状态或引用来源。验证结果写入 State/Trace，后续节点只依赖验证后的字段，不依赖自由文本描述。

### 19. 如何设计模型不可绕过的权限边界？

答：权限检查放在工具执行器、数据库/API 网关和沙箱层，基于真实 actor、tenant、resource 和 operation 计算；Prompt 只作提示。工具目录也按权限过滤，任何模型生成的"我已获授权"都不能改变策略。

### 20. 如何把确定性校验、重试和人工确认插入 Agent Loop？

答：把它们建模为独立状态转移：模型提案 → 校验 → 授权/审批 → 执行 → 验证 → 回填；失败按错误类型进入修正、重试、降级或人工。每个转移持久化，避免在一个 Prompt 里隐含整个流程。

### 21. 如何设计 Harness 的日志、Trace 和回放能力？

答：记录任务、状态转移、模型版本/预算、工具调用、权限决策、验证结果和外部副作用摘要，敏感原文单独受控；回放时冻结模型/工具响应和输入。日志要能回答"模型想做什么、系统允许什么、实际发生什么、为何结束"。

### 22. 如何评估增加 Harness 后的收益和额外成本？

答：对比任务成功率、幻觉/伪执行率、工具错误、人工接管、安全事件、延迟和 Token/开发维护成本。若只是增加规则但没有改善目标指标，或把正常任务阻塞，应缩小约束到真正高风险环节。

## Level 4｜场景追问：从单 Agent 演进到多 Agent

### 23. 一个研究任务包含检索、分析、写作三个阶段，你会选择 Workflow、Supervisor 还是多个独立 Agent？

答：如果三个阶段和输出格式稳定，优先 Workflow，检索/分析节点可以内部使用受限 Agent；只有检索来源、分析方法和写作策略高度动态且边界清晰时才考虑 Supervisor/多 Agent。最终写作必须读取已验证证据，并由引用/事实检查收尾。

### 24. 两个子 Agent 对同一个事实给出冲突结论，父 Agent 如何判断、合并或升级人工？

答：

**处理者：** 父 Agent 或确定性聚合器。

**判断依据（按优先级）：**

| 依据 | 说明 |
|------|------|
| 来源权威性 | 优先信任权威工具或原始数据 |
| 时间 | 优先当前有效版本 |
| 适用范围 | 判断数据是否适用于当前任务上下文 |
| 证据引用 | 要求提供可追溯的证据链 |
| 任务验收标准 | 按业务目标判断哪个结论更符合 |

**处理流程：**
1. 能用权威工具验证就**回查**
2. 不能判定时**保留冲突、标记不确定性**，向用户说明并升级人工
3. **不按置信度数字盲选**

**事后改进：** 冲突事件写入 Trace 和评测集，冲突样本加入回归集。
