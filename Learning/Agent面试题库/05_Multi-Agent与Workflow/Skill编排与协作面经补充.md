# Skill 编排与协作面经补充

> 递进路径：先理解 Skill 是可版本化的能力资产，再比较单 Agent 加 Skill 与多 Agent，最后处理委托、权限、通信和自我改进。

## Level 1｜Skill 基础

### 1. “一个 Agent × N 个 Skill”与“多个专用 Agent”的核心差异是什么？

答：前者通常共享同一个 Loop、身份、State 和基础模型，只按任务加载不同的能力包；后者拥有相对独立的上下文、策略、生命周期和权限，需要通信与结果聚合。Skill 更适合流程相近、共享事实多的能力；独立 Agent 只有在模型/权限/上下文隔离、并行执行或独立生命周期带来明确收益时才值得引入。

### 2. 为什么说 Skill 是经验编排，而不只是换了名字的 Prompt？一个合格 Skill 应包含什么？

答：Skill 不只描述“要说什么”，还应把触发条件、不适用场景、输入输出、步骤、工具依赖、权限、边界、失败/退出条件、示例、版本和评测用例组织成可加载资产。它可以包含 Schema、脚本或验证器，但实际权限仍由执行层授予；如果只是几段无法验证的文字，就很难复用、回归和迭代。

### 3. Skill 的渐进式披露应该分几层？为什么不能首轮把全部正文和工具 Schema 都塞给模型？

答：常见做法是元数据目录层、能力摘要/接口层、进入 Skill 后的完整说明层，必要时再按步骤加载脚本、示例和详细 Schema；具体层数可按上下文预算调整。首轮全量注入会增加噪声和冲突，降低选择质量并消耗 Token，还可能把模型暴露给不必要的工具；渐进披露能让“发现能力”和“执行能力”分开。

### 4. 嵌套 Skill 和参数化 Skill 有什么价值？如何防止递归、参数污染和能力越权？

答：嵌套能复用通用步骤，参数化能让同一流程适配不同数据源、输出格式或风险等级。工程上要定义允许的子 Skill、最大深度、调用预算、参数 Schema 和默认值；参数必须在边界处校验，子 Skill 只能继承明确授予的能力，不能因为父 Skill 传入一个“管理员”字符串就获得更高权限。

### 5. Skill 如何做版本、依赖和兼容性管理？

答：给 Skill、工具 Schema、脚本和评测集建立可追踪版本，记录依赖、输入输出兼容范围和变更类型；发布前跑发现、加载、执行、卸载和安全回归，灰度后保留回滚版本。不要只升级一份 Markdown，因为工具合同、权限和上下文模板的变更也可能破坏旧任务。

### 6. Skill、Prompt、Tool、Workflow 和 Agent 的边界分别是什么？

答：Prompt 是给模型的规则和上下文，Skill 是可发现、可加载、可版本化的能力流程，Tool 是执行原子动作的接口，Workflow 是由代码确定节点和分支的编排，Agent 是围绕目标动态选择和执行的运行系统。它们可以组合，但 Skill 不等于权限，Prompt 不等于验证，Tool 也不等于完整任务成功判定。

## Level 2｜多 Agent 协作模式

### 7. Agent Handoff 与 Agent as Tool 有什么区别？分别适合什么任务边界？

答：Handoff 是把当前任务的后续控制权交给另一个 Agent，由对方继续负责一段会话或目标；Agent as Tool 把另一个 Agent 封装成有输入输出合同的黑盒子，调用方仍拥有主流程控制权。需要连续接管、上下文切换或专业权限时可用 Handoff；需要边界清楚、可超时重试、只返回结果的子任务更适合 Agent as Tool。

### 8. Leader-and-Workers、Supervisor 和 Peer-to-Peer 三种协作方式如何取舍？

答：Leader-and-Workers 适合中心节点拆分独立子任务并聚合结果；Supervisor 更适合持续观察、验收、重试和调整路线；Peer-to-Peer 灵活但状态和终止条件更难控制。优先选择通信拓扑最简单、责任最清晰的模式，并用任务成功、延迟、Token、故障传播和维护成本证明复杂拓扑的必要性。

### 9. 一个 Agent 委托另一个 Agent 时，结构化任务合同至少应包含哪些字段？

答：至少包含任务 ID、目标、输入或数据引用、硬约束、输出 Schema、验收标准、调用方身份与权限范围、模型/工具预算、截止时间、取消语义、重试策略、幂等键和成功/失败/部分成功状态。合同还应说明哪些事实已验证、哪些只是待处理建议，避免子 Agent 把上游猜测当成事实。

### 10. 如何避免多 Agent 因上下文复制、自然语言闲聊和反复确认而失控？

答：只传递完成子任务所需的结构化字段和证据引用，长内容放在受控存储中按需读取；共享状态由明确的拥有者写入，消息只传增量和版本。对每种消息定义回应条件、最大深度、调用次数、Token/时间预算和无进展检测，禁止用自然语言对话替代任务状态机。

### 11. 如何隔离被委托 Agent 的身份、数据和副作用权限？

答：为委托请求创建带过期时间和 Scope 的子身份，明确可访问的租户、资源、工具、网络和操作；服务端在每次 Tool 调用时重新鉴权，并记录原始用户、委托链和实际执行者。父 Agent 的权限不能默认全量下传，尤其不能让子 Agent 通过修改任务文本或返回结果来提升权限。

### 12. A2A、普通 API 和进程内节点的边界是什么？什么时候不应该引入跨 Agent 协议？

答：进程内节点适合同一应用、共享状态、低延迟和统一发布；普通 API 适合稳定的服务合同和明确的请求/响应；A2A 适合独立 Agent 之间的能力发现、任务委托、异步进度和独立生命周期。若参与者由同一团队部署且不需要跨系统发现、异步长任务或独立权限，引入 A2A 往往只增加协议、身份、超时和排障成本。

### 13. 跨 Agent 调用遇到超时、取消、重复投递或部分成功时，协议需要表达什么？

答：协议应有任务状态、进度、截止时间、取消令牌、幂等键、重试语义和结果引用，并区分“未开始、执行中、已成功、已失败、结果未知、部分成功”。取消只保证停止后续工作，不一定能撤销已经发生的外部副作用；因此必须配合对账、补偿或人工处理，而不是只返回一个布尔值。

### 14. 多 Agent 对同一事实给出冲突结果，应该由谁、依据什么合并？

答：由父 Agent 或确定性聚合器按来源权威性、时间、适用范围、证据和任务验收标准处理，优先回查权威工具或原始数据。置信度数字不能替代证据；无法判定时应保留冲突、标记不确定性并升级人工，同时把冲突样本加入评测和回归集。

## Level 3｜工程化与评测

### 15. 什么情况下“单 Agent + Skill”比“多 Agent”更稳定、更容易评测？

答：当能力共享大量 Context 和 Memory、任务在同一 Loop 内自然衔接、权限差异不大且无需独立并行时，单 Agent 加 Skill 少了通信、状态同步和结果聚合故障。它仍需要 Skill 选择和工具权限评测；只有当隔离、并行、不同模型或独立部署带来可量化收益时，才将 Skill 升级为独立 Agent。

### 16. 如何评测 Skill 的发现、加载、使用和卸载质量？

答：分别构造应触发、不应触发和相似 Skill 混淆样本，测发现准确率、误触发率、加载延迟、上下文增量、工具选择、任务成功和卸载后的残留行为。再加入权限、版本升级、依赖缺失、参数边界和长任务中途切换用例，防止只测“能不能跑通一个 Demo”。

### 17. Skill 如何做安全的自我改进？如何防止把错误经验或恶意内容沉淀进去？

答：先把成功/失败轨迹和用户反馈转成候选变更，经过脱敏、来源检查、人工或规则审核，在离线评测集和隐藏集上比较后再灰度发布。任何自动生成的 Skill、示例或规则都不能直接获得新权限；保留版本、变更原因、回滚点和异常监控，发现收益只在某类样本上出现时就按场景路由，而不是全量覆盖。

### 18. 两个 Skill 描述相似导致误选，你会改描述、路由器、上下文还是模型？

答：先用误选样本判断是边界描述重叠、候选集过大、上下文缺少关键字段还是模型本身能力不足；通常先让描述包含互斥条件、输入/输出和“不适用”示例，再缩小候选集并加确定性前置路由。若工具高风险，还要在执行层验证资源和参数；只有格式、候选和约束都正确仍稳定误选，才考虑换模型或训练。

### 19. Skill 指导模型执行危险操作时，如何与工具权限、审批和 Sandbox 配合？

答：Skill 只声明流程和风险提示，工具网关按真实身份、资源、操作和风险等级授权；高风险步骤先生成结构化提案，经过策略检查和人工确认后才执行。代码或文件操作放在隔离 Sandbox，设置网络、目录、进程和资源限制；审批前后的 State 与参数都要冻结并审计，防止模型在等待期间偷偷替换动作。

## Level 4｜场景追问

### 20. 设计一个研究型 Agent：它同时具备检索、数据分析、写作和审校能力。哪些能力做成 Skill，哪些环节才值得拆成独立 Agent？

答：默认用一个主 Agent 加检索、分析、写作、引用检查等 Skill，并由 Workflow 固定“取证 → 分析 → 写作 → 审校”的骨架；这样共享证据和任务目标，评测与回放更简单。只有在分析需要隔离代码环境、审校必须独立于写作者、子任务可大规模并行，或权限/模型/生命周期明显不同的情况下，才拆出独立 Agent，并为每次委托定义输入、证据、验收和失败合同。
