# Loop 控制与 Harness 面经补充

> 递进路径：先把一次 Agent 运行拆成 Session/Turn，再处理干预、压缩和工具错误，最后回答 Harness、Sandbox 与长程任务的系统问题。

## Level 1｜Loop 基本语义

### 1. LoopSession 与 LoopTurn 分别表示什么？为什么不直接用一串 message 表示？

答：Session 是一次任务或会话的长期容器，通常包含目标、身份、权限、预算、State、Checkpoint、控制事件和完整 Trace；Turn 是其中一次“组装 Context → 调模型 → 处理工具/停止原因”的推进单元。一串 message 只能表达对话表面，难以表达状态版本、待审批动作、恢复点、预算和可回放边界，因此生产系统需要更结构化的运行记录。

### 2. 一个 LoopTurn 的最小生命周期是什么？模型调用和工具调用如何处理批量 Tool Call？

答：先读取版本化 State，按固定规则组装 Context，调用模型并解析结构化输出；若模型请求工具，就校验名称和参数、创建调用记录、执行工具、写回结果，再决定是否进入下一轮。批量 Tool Call 只有在调用之间无数据依赖、权限和副作用允许并行时才并行执行，并为每个调用保留独立状态、超时和错误结果，不能把“批量返回”误当成“全部成功”。

### 3. natural finish、StopReason、达到最大轮数、超时、审批暂停和异常终止有什么区别？

答：natural finish 表示模型或验收器认为任务已经完成；StopReason 是更一般的结束原因，例如完成、工具请求、用户中断、预算耗尽或安全拒绝。最大轮数和超时是系统预算触发，审批暂停是等待外部事件，异常终止是执行器或依赖失败；它们必须分别记录，否则系统会把“被迫停止”错误地当成成功。

### 4. Steer、Followup、Interrupt 分别是什么？它们适合插入 Agent 的哪个阶段？

答：这组词在不同框架里不一定是统一 API，通用语义可以理解为：Steer 是在当前运行中改变后续方向或约束，Followup 是在一个可提交的 Turn 之后追加用户/系统事件继续任务，Interrupt 是立即暂停或取消当前执行。面试时要说明它们的边界、是否丢弃未提交输出、是否需要 Checkpoint，以及对正在运行的工具副作用如何处理。

### 5. PreTurn、MidTurn、PostTurn Middleware 分别能解决什么问题？

答：PreTurn 适合做身份与权限检查、预算检查、Context 装配和输入脱敏；MidTurn 适合拦截模型输出、Tool Call、敏感动作和需要人工审批的节点；PostTurn 适合验收结果、写 Trace、压缩上下文、更新 Memory 和决定下一状态。它们不是把规则塞进 Prompt，而是在模型前后建立可执行的确定性边界。

### 6. Stop-Resume 与 Hang-Wait 的语义有什么区别？如何选择？

答：Stop-Resume 是任务明确停在某个 Checkpoint，之后由显式 Resume 事件重新加载状态；Hang-Wait 是任务进入等待态，保持任务句柄，等用户输入、审批、Webhook 或队列事件到达后继续。前者适合边界清晰、需要释放资源的暂停，后者适合等待外部事件但希望保留任务订阅的长任务；两者都要持久化状态、版本和幂等信息，不能只依赖进程内内存。

## Level 2｜上下文与执行控制

### 7. 如何保证每一轮 Context Assembly 稳定、可解释且可回放？

答：把系统规则、任务合同、当前 State、必要 Memory、工具 Schema、已验证工具结果和用户输入划分成固定区块，并记录来源、版本、裁剪原因和最终 Token 预算。组装过程应是确定性代码，Trace 保存输入摘要和版本；这样能回答“模型当时看到了什么”，也能在回放时复现同一上下文，而不是只保留最终回答。

### 8. 多轮对话变长时，如何做上下文压缩而不破坏任务状态和证据链？

答：先保留任务目标、硬约束、当前状态、未完成动作、已验证事实、证据引用和冲突，再压缩闲聊、重复观察和已消费的中间推理。压缩结果要经过结构化 Schema、关键事实回查和长度检查；原始内容放在可审计存储中，摘要只作为当前上下文视图，不能覆盖原始事实。

### 9. 什么是 Prefill 阶段的干预？它和生成中途的 Steering 有什么不同？

答：Prefill 是模型读取输入上下文、建立首轮激活和 KV Cache 的阶段；所谓 Prefill 干预通常是指在模型开始生成前完成 Context 路由、敏感内容过滤、工具候选筛选或前缀缓存选择。生成中途的 Steering 则发生在 Decode 或一次模型调用返回后，可能需要停止当前生成并追加控制事件；两者的可行性取决于推理服务是否暴露相应接口，不能把它们当成纯 Prompt 技巧。

### 10. Tool 返回错误时，Loop 应该怎样区分修参、重试、换工具和终止？

答：执行器先把错误归类为参数/Schema 错误、暂时性依赖错误、权限错误、业务不可行、结果未知或系统故障。参数错误可以把字段级反馈交给模型修正；暂时性错误只对幂等调用限次退避；权限和业务不可行通常应换路径、请求用户或终止；结果未知要先查询或对账，不能直接重放可能已经成功的副作用。

### 11. 如何检测 Agent 的无进展循环，例如反复调用同一个工具或重复输出相同计划？

答：对工具名、规范化参数、返回摘要和 State 版本做指纹，检查连续多轮是否没有新事实、状态变化或任务距离变化；同时设置轮数、时间、Token 和同类调用预算。触发后可以要求改变策略、缩小问题、换工具、转人工或结束，并把“无进展”作为独立 StopReason 和回归样本，而不是无限追加“请继续尝试”。

### 12. 如何利用 StopReason 决定继续 Loop、请求用户补充、转人工还是结束？

答：先把 StopReason 映射到状态机：工具请求进入校验执行，缺少用户信息进入等待，风险动作进入审批，预算耗尽进入降级/人工，安全拒绝直接结束并说明边界，验收通过才标记成功。关键是“结束原因”和“业务成功”分开保存；一个超时或达到最大轮数的运行即使有部分输出，也不能自动计为成功。

## Level 3｜Harness 与运行环境

### 13. Harness 的执行面和控制面分别包含什么？为什么要把两者分开？

答：执行面是 Agent 实际接触的环境，如 Sandbox、浏览器、文件系统、Shell、网络和 Tool；控制面是 Loop、Context 策略、Hooks/Middleware、Skill、压缩、Memory、预算、审批和协作策略。分开后可以让多个执行环境复用同一套控制策略，也能让权限在执行面强制落地，避免模型通过改 Prompt 或 Skill 文本绕过工具网关。

### 14. 如何为代码 Agent 划分浏览器、文件系统、Shell、网络和进程权限？

答：默认拒绝，按任务授予最小范围：文件系统限定工作区和读写目录，Shell 使用命令白名单或受限用户，网络限制域名、方法和出站策略，浏览器隔离 Cookie、下载目录和站点权限，进程限制资源与信号能力。每次 Tool 执行仍要依据真实用户、租户、资源和操作重新授权，不能只相信模型声明的参数或 Prompt 中的权限。

### 15. Sandbox 的 cold start、resume、snapshot、idle 分别解决什么问题？有什么取舍？

答：cold start 是从镜像创建新环境，隔离最干净但启动慢；resume 是恢复已有环境，适合多轮任务但要处理租约、版本和残留状态；snapshot 保存某一时刻的文件与环境，便于快速复制和回放；idle 是暂存空闲环境以节省资源，但会占用容量并带来过期清理问题。设计时要明确哪些状态可恢复、哪些凭证不能快照、如何清理敏感数据，以及恢复后是否需要重新验证依赖。

### 16. Skill 从管理、发现、加载、注入到卸载的生命周期如何设计？卸载最容易漏掉什么？

答：管理阶段登记版本、依赖、适用/不适用条件和权限；发现阶段只返回轻量元数据；加载阶段解析依赖并检查授权；注入阶段把必要说明、Schema 或脚本放入当前上下文；卸载阶段移除上下文候选、工具映射、临时文件、进程、缓存和订阅。最常漏的是“文本已经不再展示，但旧 Skill 的工具、环境变量或上下文摘要仍然生效”，因此卸载应有可验证的资源清单和回归测试。

### 17. 为什么 Skill 不必强绑定 Sandbox？什么情况下又应该把 Skill 与 Sandbox 绑定？

答：Skill 可能只是检索、写作、分析或决策流程，不需要操作系统环境；强绑定会增加启动成本、权限面和部署复杂度。若 Skill 需要执行代码、访问特定依赖、操作文件或浏览器，就应声明所需 Sandbox 类型、网络和资源范围，并由执行器按实例绑定，不能把“会写 Shell 命令”当成已获得 Shell 权限。

### 18. 长任务中途切换模型或 Agent 时，如何传递状态、证据、预算和未完成动作？

答：传递任务目标、硬约束、已验证事实及引用、产物位置、当前状态、未完成动作、失败原因、剩余预算、截止时间和停止原因；不要默认把完整原始上下文或未验证的自然语言计划全量复制。新 Agent 还要重新检查自身能力、权限和工具版本，外部副作用用幂等键或对账状态表示，避免切换后重复执行。

### 19. Agent Loop 如何利用 KV Cache、请求批处理和结果缓存降低延迟？哪些缓存不能盲目复用？

答：对完全一致且仍在有效生命周期内的系统前缀或工具 Schema，可以利用 KV Cache；对相同输入、权限、数据版本和新鲜度要求下的纯读工具，可以复用结果；服务端用 Continuous Batching 提高并发利用率。缓存键必须包含模型/Tokenizer、Prompt 版本、租户权限、资源版本、参数和时间条件；带用户隐私、随机性、权限差异或副作用的结果不能只按自然语言问题复用。

### 20. 如何设计 Loop Trace，使它既能解释决策，又能安全回放而不重复真实副作用？

答：记录每轮输入摘要、模型版本与预算、结构化决策、Tool Call、权限判断、验证结果、State 版本、延迟、Token 和 StopReason；可以记录可审计的决策摘要，不必把隐藏思维链当成生产日志。回放时冻结模型响应和工具 Fixture，副作用工具默认模拟或只读；Trace 中的敏感内容需要脱敏、访问控制和过期策略。

## Level 4｜场景追问

### 21. 设计一个代码 Agent Harness：从用户提出修改需求，到生成 Patch、运行测试、人工确认和交付，状态如何流转？

答：可以设计为“需求澄清 → 读取基线和工作区 → 生成受限 Patch → 静态检查/格式化 → 运行白名单测试 → 汇总 Diff 与证据 → 高风险变更人工确认 → 应用或交付”。每一步都有输入输出 Schema、权限和 Checkpoint；应用 Patch 前保留用户已有修改，测试失败只允许在受限环境中迭代，最终交付必须展示实际 Diff、测试结果和未解决风险。

### 22. 一个长程任务出现目标漂移、上下文爆炸和错误累积，你如何定位根因并设计恢复策略？

答：先用 Trace 分开看目标是否被改写、压缩是否丢失约束、工具错误是否被当成事实、State 是否没有推进，以及模型是否在错误策略上继续循环。恢复时冻结已验证产物，重新生成精简任务合同，按里程碑压缩上下文，加入进度/验收检查和无进展停止；必要时切换模型或 Agent、回到最近 Checkpoint，涉及副作用则先对账再重试。
