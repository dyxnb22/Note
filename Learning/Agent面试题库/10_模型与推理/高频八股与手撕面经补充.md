# 高频八股与手撕面经补充

> 递进路径：先补模型与推理基础，再连接到 Agent 的循环、工具和检索，最后练习能落到工程边界的手撕题。

> 本页强调 Agent 场景下的性能、推理预算和工程取舍；通用模型原理题以 [AI 面试题库](../../AI/面试题库/README.md) 为主答案，本页只保留与 Agent 行为直接相关的追问，避免两份题库长期漂移。

## Level 1｜模型与推理基础

### 1. Scaled Dot-Product Attention 的公式是什么？计算和显存复杂度如何随序列长度变化？

答：核心公式是 `Attention(Q,K,V)=softmax((QK^T)/sqrt(d_k)+mask)V`。长度为 `n` 时，`QK^T` 形成 `n×n` 的注意力矩阵，时间和中间显存大致随 `n²` 增长，另有 Q/K/V 投影和矩阵乘法成本；这也是长上下文和 Agent 多轮历史容易变慢、爆显存的原因。实际复杂度还取决于层数、头数、批量和实现是否物化中间矩阵。

### 2. MHA、MQA 和 GQA 的 Q/K/V 头如何组织？为什么 GQA 能降低 KV Cache？

答：MHA 中每个 Q 头都有对应 K/V 头；MQA 让所有 Q 头共享一组 K/V；GQA 把 Q 头分成若干组，每组共享一组 K/V。因此 GQA 保留多 Q 头的部分表达能力，同时把缓存的 K/V 头数从 Q 头数降到组数，KV Cache 近似按 `KV 头数 / Q 头数` 缩小；代价是共享增加，质量和速度要在目标模型上实测。

### 3. 如何估算单个请求 KV Cache 的显存占用？

答：若每层有 `H_kv` 个 KV 头、每头维度 `D`、序列长度 `L`、元素字节数为 `B`，K 和 V 两份缓存的近似大小是 `2 × 层数 × H_kv × D × L × B`，批量或并发请求再乘相应数量，并加上分页/元数据开销。实际还要考虑 Prefix Cache、序列共享、对齐、量化和最大/平均长度；面试时说明 GQA/MQA 会降低 `H_kv`，不要只背一个总显存数字。

### 4. FlashAttention 解决了标准 Attention 的什么瓶颈？它是否改变了注意力结果？

答：FlashAttention 用分块、片上内存和在线 Softmax 减少 HBM 与片上内存之间的数据搬运，并避免完整物化 `n×n` 注意力矩阵，主要改善 IO 和显存峰值。它在数学目标上仍是精确 Attention（实现会有正常浮点数差异），不是把复杂度从二次变成线性；它也不能解决 KV Cache、模型调用次数或工具等待造成的延迟。

### 5. BPE 与 WordPiece 的基本思路有什么差别？它们对 Agent 有什么实际影响？

答：BPE 通常从字节/字符单元出发，按频率或合并规则逐步合并高频子词；WordPiece 也学习子词词表，但常用基于似然/评分的合并准则，具体实现和训练细节会因模型而异。对 Agent 的实际影响主要是 Token 数、上下文预算、代码/中英文/特殊工具名的切分和费用；不能只依据算法名推断某模型一定更省 Token，应在目标语料上测量。

### 6. RoPE 如何把位置信息注入注意力？长上下文外推为什么会变难？

答：RoPE 按位置对 Q/K 的二维子空间做旋转，使不同位置的内积带有相对位置信息。训练时模型只见过有限位置范围，超过范围后旋转相位、频率分布和注意力模式可能失配，导致远距离关系退化；长上下文方案通常要调整频率或位置缩放，并在真实长任务评测，不能只把最大 Token 参数改大。

### 7. MoE 的路由、专家容量和负载均衡分别解决什么问题？

答：路由器根据 Token 选择少量专家，专家容量限制单个专家一次能接收的 Token 数，负载均衡机制避免少数专家过载、其他专家闲置。MoE 能在较大总参数下只激活部分计算，但会带来路由通信、丢 Token/溢出策略和推理调度复杂度；Agent 场景还要关注工具格式、停止行为和长尾任务是否被某些专家覆盖。

### 8. GPTQ 与 AWQ 都是权重量化方法，核心思路和适用关注点有什么区别？

答：GPTQ 通常在后训练阶段按层估计量化误差并用近似二阶信息做权重补偿；AWQ 强调用激活统计识别对输出更敏感的权重通道，优先保护它们再量化。两者都依赖校准数据、位宽、Kernel 和模型结构，实际效果不能只按名字判断；要对困惑度、工具调用格式、长上下文、吞吐和显存做目标模型验证。

### 9. Prefill、Decode 和 Continuous Batching 分别是什么？它们如何影响 Agent 的时延？

答：Prefill 一次性处理输入上下文，通常计算密集；Decode 自回归地产生新 Token，通常受 KV Cache 和逐步生成影响；Continuous Batching 在请求不断到达/完成时动态把不同阶段的序列放入批次，提高 GPU 利用率。Agent 每多一次模型轮次都会重复部分 Prefill 并增加排队/Decode，Context 压缩、Prefix Cache、模型路由和减少无效循环往往比只优化单次生成更有效。

### 10. Speculative Decoding 如何加速生成？什么情况下收益不明显？

答：小 Draft Model 先提出一段 Token，大 Target Model 并行验证并接受其中一部分，不接受的部分由目标模型修正；在保持目标模型分布的前提下减少昂贵模型逐 Token 生成。若 Draft 与 Target 不相似、输出很短、验证/调度开销高或请求本身主要耗在 Prefill/工具等待，接受率低，收益可能不明显；需要测接受率、端到端 P95 和显存，而不是只看 Decode 吞吐。

### 11. SFT、LoRA/QLoRA、DPO、PPO 和 GRPO 分别解决什么问题？

答：SFT 用示范数据学习任务格式、工具协议和基础行为；LoRA/QLoRA 是降低微调参数/显存成本的参数高效方法，可与 SFT 或其他训练目标组合；DPO 用偏好对直接优化相对偏好，省去显式 Reward Model 的一部分流程；PPO 是带策略约束和价值估计的强化学习方法；GRPO 常用同组样本的相对奖励估计优势，减少对独立 Value Model 的依赖。选型要看数据、奖励是否可验证、稳定性和线上收益，不是 Agent 必须做 RL。

### 12. 为什么训练或部署低精度模型时，不能只看平均精度？

答：量化误差可能集中在少数层、通道、长上下文位置或特殊 Token 上，平均任务分数掩盖了工具参数、JSON 格式、拒答、安全和长尾退化。应按模型调用、工具选择/参数、RAG 证据、长任务、并发、显存、吞吐和 P95 分桶评测，并检查是否需要混合精度、敏感层保留高精度或更换 Kernel。

## Level 2｜Agent 与检索连接

### 13. 如何写出一个最小但可控的 ReAct Agent Loop？

答：核心是有限状态循环：组装任务与观察 → 调模型 → 解析“最终答案”或结构化 Tool Call → 校验工具白名单与参数 → 执行并写入 Observation → 检查验收/预算/无进展 → 继续或停止。伪代码可以是：

```text
while budget_ok and not finished:
    decision = model(context(state))
    if decision.final: return verify(decision.answer)
    call = validate(decision.tool_call)
    result = execute(call)
    state = append_observation(state, result)
return stop_with_reason(state)
```

关键不在“有一个 while”，而在最大轮数、超时、权限、结构化结果、幂等、失败分类和业务验收都由代码控制。

### 14. Plan-and-Execute 为什么可能减少长任务中的重复规划？它又会引入什么风险？

答：先生成粗粒度计划，再按步骤执行，可以复用计划、限制每一步范围并减少每次都从目标重新分解的 Token；执行结果异常时仍需要局部重规划。风险是初始计划过时、错误被后续步骤放大、计划本身过细导致僵化，或模型把计划当成已完成事实；应使用可验证里程碑、动态修订、最大计划深度和工具结果驱动的状态转换。

### 15. Tool Calling 的 Schema、参数校验和执行结果应该如何衔接？

答：Schema 描述名称、参数类型、必填/枚举、约束和返回结构，但不等于授权；执行前由服务端做严格解析、资源/租户/风险校验，执行后返回带调用 ID、状态、错误类型、数据版本和可引用结果。后续模型只应看到验证后的字段和失败语义，不能把自然语言“调用成功”当作真实执行证据。

### 16. 工具调用失败时，重试、退避、换工具和人工接管如何组合？

答：按错误分类：参数问题让模型修正一次，暂时性网络/限流错误对幂等调用指数退避，能力不支持或权限拒绝换受限路径/请求用户，结果未知先查询对账；高风险或多次失败进入人工。每类错误有次数、时间和总预算上限，失败状态写入 Trace，不能让统一重试策略把业务错误变成无限循环。

### 17. 如何保证带副作用的 Tool 在重复投递下仍然安全？

答：为一次业务意图生成幂等键，由服务端持久化请求、执行状态和结果；重复请求先返回已知结果或进入对账，不直接再次扣款/发信/改数据。工具还应使用业务状态机、唯一约束、权限和审批记录，区分“未执行、执行中、成功、结果未知”；消息队列的 exactly-once 不能替代业务层幂等。

### 18. 并行调用多个只读 Tool 后，如何聚合、去重、排序并处理部分失败？

答：先为每个调用记录 correlation ID、来源、版本、状态和超时，再由确定性聚合器按实体/证据键去重、按权威性/时间排序，并显式保留部分失败。只有相互独立且无共享副作用的调用才并行；聚合器不能把缺失结果当空事实，最终回答应说明覆盖范围和不确定性。

### 19. 滑动窗口、摘要记忆和向量记忆如何组合，才能避免上下文无限增长？

答：滑动窗口保留近期交互和未完成动作，摘要记忆压缩已完成阶段的目标、事实、决策和未决问题，向量/结构化记忆保存跨会话且经过筛选的偏好或经验。写入长期记忆要经过来源、时间、冲突、权限和用户意愿检查；检索后仍要按当前任务相关性和新鲜度过滤，不能把相似旧内容直接当当前事实。

### 20. 混合检索、Rerank、查询扩展和 Grounding Check 分别解决什么问题？

答：关键词/BM25 擅长精确术语和编号，向量检索擅长语义相似，混合检索提高召回覆盖；Rerank 对候选按问题相关性重新排序；查询扩展补充同义词、实体和子问题；Grounding Check 检查回答是否被证据支持。它们增加延迟和误召回风险，应按召回、证据覆盖、答案忠实度、P95 和成本做分层消融，而不是全部叠加。

### 21. 如何用程序验证和 LLM 评审共同判断一条 Agent 轨迹是否成功？

答：先用程序检查结构化输出、工具状态、测试退出码、业务状态、权限和引用存在性，再用规则或 LLM Judge 评估答案是否覆盖目标、解释是否基于证据和交互是否合适；最终成功由任务级验收定义。LLM 评审不能覆盖真实副作用或任意事实校验，应使用 Rubric、校准样本和人工复核处理高风险/分歧样本。

## Level 3｜手撕与后端追问

### 22. 手撕一个带最大轮数、工具白名单和结构化结果校验的 Agent Loop，关键状态有哪些？

答：至少有 `task_id`、当前 State/版本、轮数、截止时间、Token/调用预算、允许工具集合、每轮决策、Tool Call 状态、已验证结果、错误计数、幂等键和 StopReason。实现时把 `parse -> validate -> execute -> verify -> transition` 分开，工具异常不能直接跳到成功；每次状态更新要可持久化，恢复后重新检查版本和权限。

### 23. 手撕一个带超时、指数退避、幂等键和错误分类的 Tool Executor，如何避免重复副作用？

答：入口先用幂等键查询本地执行记录：已成功直接返回，执行中返回可轮询状态，结果未知进入对账；只有未开始才写入“执行中”并调用下游。对瞬时错误按有上限的指数退避重试，对参数/权限/业务错误立即返回结构化失败；超时后不能假设失败，要根据下游查询或人工对账决定状态。

### 24. 手撕一个异步 Fan-out/Fan-in 调度器，如何处理并发上限、超时、取消和部分结果？

答：为每个子任务记录状态和 Deadline，用信号量限制并发，完成或超时后把结果写入统一集合；总任务取消时传播 Cancellation Token，并等待/标记已启动任务，不能遗留无限后台协程。聚合阶段按成功、失败、超时、取消分开处理，返回部分结果和缺口；对可重试的只读任务使用明确的幂等键与预算，最终由验收器判断是否足够完成主任务。
