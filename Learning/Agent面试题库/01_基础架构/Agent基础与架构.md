# Agent 基础与架构

> 递进路径：先判断边界，再讲运行时，最后完成架构设计和场景取舍。

## Level 1｜基础认知：是什么，为什么需要

### 1. 什么是 Agent？与普通 LLM Chat、Workflow、RPA 和传统后端服务有什么区别？

答：Agent 是围绕目标运行的有限循环：读取状态，让模型提出下一步，校验并执行动作，再根据结果继续或结束。与其它范式的区别：

| 维度 | Agent | 普通 LLM Chat | Workflow | RPA | 传统后端服务 |
|------|-------|--------------|----------|-----|------------|
| 决策方式 | 模型根据中间结果动态决定 | 一次回复 | 路径预先确定 | 按固定规则操作 | 代码逻辑确定 |
| 循环 | 有限循环，有预算上限 | 单轮/多轮但无工具循环 | 有向图或状态机 | 顺序脚本 | 请求-响应 |
| 执行能力 | 工具调用 + 状态回填 | 仅文本生成 | 仅流程编排 | GUI/脚本操作 | API 调用 |
| 权限边界 | 代码控制权限和成功判定 | 无外部副作用 | 代码控制 | 规则控制 | 代码控制 |


### 2. Agent 的执行流程是什么

答：**解析目标和权限** → 加载 Context/Memory → 模型根据当前 State 选择直接回答、规划或调用工具 → **校验/授权**（代码层强制检查权限、参数合法性、副作用范围） → **执行工具** → 结果回填 State → **业务验证器判定成功证据**（如数据库状态、测试通过、字段约束满足） → 满足则结束并经格式和安全校验后返回用户，不满足则携带新 State 进入下一轮。整个循环必须预设 **预算上限**（步数、Token、时间、费用）和 **明确停止原因**（成功/取消/权限拒绝/无进展/预算耗尽），否则就只是一个可能无限循环的模型调用。

### 3. Agent 的自主性体现在哪里？什么场景该用 Agent，什么场景该用 Workflow？

答：

**自主性体现：**

| 维度 | 说明 |
|------|------|
| 任务分解 | 把目标拆成子步骤 |
| 路径选择 | 根据中间结果决定下一步 |
| 工具选择 | 从候选工具中挑选合适的 |
| 重规划 | 根据观察结果调整计划 |

**但不是越强越好——选型对比：**

| 维度 | Workflow | Agent |
|------|----------|-------|
| 决策方式 | 节点、顺序、分支由代码确定 | 路径由模型根据状态动态选择 |
| 可预测性 | 可预测、易测试 | 灵活但不确定 |
| 适用场景 | 步骤固定、输入输出稳定、合规要求高 | 目标明确但路径取决于检索、工具结果或环境反馈 |
| 控制手段 | 代码控制 | 规则、审批、硬预算 |

**演进原则：** 先做 Workflow 基线，**只有动态性带来可测量的成功率或覆盖率收益时才引入 Agent**。高风险、有副作用或路径稳定的任务应减少自由度，用规则、审批和硬预算换取可控性。生产系统常用 Workflow 负责骨架、Agent 负责局部决策，并为动态部分加硬约束。

### 4. Agent 系统中哪些部分应该由模型决定，哪些部分应该由代码决定？

答：模型适合做意图理解、候选计划、工具选择和自然语言生成；代码应负责权限、参数校验、状态持久化、预算、幂等、沙箱、成功判定和审计。凡是不可逆副作用和安全边界，都不能只依赖 Prompt。

### 5. Agent Framework、Agent Runtime 和 Agent Application 有什么区别？

答：Framework （**LangChain / LangGraph**）提供抽象和编排 API，Runtime （**LangGraph 的 executor**）负责循环、状态、工具、恢复、观测和执行边界，Application 才是面向具体业务的提示词、工具、数据和产品体验

### 6. 如何从 Demo 演进到生产级 Agent？

答：

**第一步：固定合同与指标**

| 合同类型 | 说明 |
|---------|------|
| 任务合同 | 明确输入、输出、成功标准 |
| 工具合同 | 每个工具的 Schema、权限和错误语义 |
| 状态 Schema | State/Checkpoint 版本化 |

**第二步：补工程能力**

| 能力 | 说明 |
|------|------|
| 权限与身份 | 真实 actor、tenant 级别控制 |
| 预算 | 步数、Token、费用、超时 |
| 持久化/Checkpoint | 状态、副作用、恢复点 |
| 失败恢复 | 错误分类、重试、降级、对账 |
| Trace | 每轮输入/输出/决策/工具结果 |
| Eval | 任务成功率、安全、长尾 |
| 限流 + 灰度 | 并发上限、按用户/任务灰度 |
| 回滚 | 版本化 Prompt/模型/工具/数据/策略，可回退 |

**核心原则：** 生产化的关键不是加更多 Agent 或堆框架，而是让每次运行**可控、可解释、可恢复和可回滚**。每一步都用任务成功和安全指标验证。

### 7. Agent 系统最重要的设计部分是什么？

答：最重要的是把模型的开放式决策放在一个可验证的执行边界内：明确 State、工具权限、终止条件和成功证据。架构图上少画一个 Agent，通常比没有边界地增加 Agent 更可靠。

## Level 2｜原理机制：如何运行，如何结束

### 8. ReAct 是什么？Reasoning、Action、Observation 如何循环？

答：ReAct 把任务拆成“根据当前信息判断下一步 → 执行动作 → 观察结果”的循环，直到得到答案或触发停止条件。工程实现中不需要暴露模型的私有思维链，只需记录可审计的动作、工具结果、状态变化和停止原因。

### 9. Agent Loop 在什么条件下继续执行、什么条件下结束？

答：有合法工具调用且预算允许时继续；有满足业务验收的成功证据时成功结束；取消、权限拒绝、不可恢复错误、无进展或预算耗尽时停止/失败。每种结束都应有结构化 reason，不能用一个模糊的 `done` 覆盖所有情况。

### 10. Plan-and-Execute 与 ReAct 有什么区别？

答：ReAct 每轮根据最新观察决定下一步，灵活但可能反复探索；Plan-and-Execute 先生成可检查的任务计划，再逐步执行，适合步骤较多且可拆分的任务。计划必须允许失效和局部重规划，不能把初始计划当成事实。

### 11. Reflection、Critic、Self-Consistency 分别解决什么问题？

答：Reflection 让系统对结果或过程进行复盘，Critic 负责按标准找问题，Self-Consistency 通过多次候选和聚合提高部分推理任务的稳定性。它们都会增加调用成本，只有存在可操作的验证标准时才值得使用。

### 12. Router 模式是什么？如何设计路由条件和兜底分支？

答：Router 先判断请求属于哪个领域、复杂度或风险等级，再进入专用 Workflow/Agent。路由条件应尽量可评测，设置低置信度兜底、人工转接和未知类别分支，避免错误路由后继续自动执行高风险动作。

### 13. Planner、Executor、Critic、Router、Supervisor 分别负责什么？

答：前三个是单 Agent 内部的微观循环——规划、执行、验收；后两个是多 Agent 系统的宏观编排。详细职责、适用场景和设计要点见 [[../05_Multi-Agent与Workflow/Multi-Agent与Workflow|Multi-Agent 与 Workflow]]。

### 14. 如何让 Agent 判断任务已经完成？

答：定义可检查的验收条件，例如数据库状态、测试通过、引用齐全或业务字段满足约束；由确定性验证器或受信工具产生成功证据。模型文本只能解释结果，不能独立充当完成证明。

### 15. 如何避免每一步重新规划导致路径震荡？

答：把稳定的计划和已完成事实写入 State，只有触发事件或前提变化时才重规划；给计划版本、重规划次数和无进展次数设置上限。还可以让 Planner 输出变更原因，检测来回切换的路线。

### 16. 如何避免 Agent 重复调用同一个工具？如何检测无进展循环？

答：

**防重复机制：**

| 措施 | 说明 |
|------|------|
| State/Trace 记录 | 保存工具调用摘要、参数哈希、结果和副作用状态 |
| 幂等键 | 执行器对有副作用操作强制幂等键 |
| 缓存策略 | 只读查询可短缓存，但不能用缓存替代权限检查 |

**检测手段：**

| 指纹维度 | 说明 |
|---------|------|
| 工具名 + 规范化参数 | 比对是否重复相同调用 |
| 返回摘要 | 比对是否没有新事实 |
| State 版本 | 比对状态是否没有推进 |
| 任务距离 | 比对目标是否没有靠近 |

同时设置**轮数、时间、Token 和同类调用预算**作为安全上限。

**触发后处理：** 要求改变策略、缩小问题、换工具、转人工或结束；把"无进展"作为独立 StopReason 和回归样本，而不是无限追加"请继续尝试"。

多 Agent 场景下的重复劳动、循环调用和责任不清问题见 [[../05_Multi-Agent与Workflow/Multi-Agent与Workflow|Multi-Agent 与 Workflow]]。

---

**追问：长任务如何避免死循环、重复计划和无效重试？**

维护已执行动作和进展指标，设置最大步数/时间/Token/费用、重复调用和无进展检测；重试只针对可恢复、可幂等错误。计划变化需有原因，超过阈值就降级、请求用户或转人工。

### 17. 如何处理计划执行到一半发现前提不成立的情况？

答：先把失败事实写入 State，判断是可修正参数、需要补充信息、需要换路径还是任务不可行；只对可恢复部分局部重规划。已经发生的外部副作用要先对账，不能为了让计划“看起来完成”直接重复执行。

### 18. 长任务应该一次性规划还是边执行边规划？为什么？

答：通常采用分阶段规划：先得到粗粒度计划，执行到检查点后根据事实细化。一次性计划容易被环境变化打破，完全逐步规划又会增加调用和震荡；分阶段方式更容易控制成本、恢复和审计。

### 19. 如何为 Agent 设置最大步数、超时、Token 和成本预算？

答：

**预算维度（任务级 State 维护）：**

| 预算类型 | 说明 |
|---------|------|
| 步数 | 最大工具/模型调用轮数 |
| 墙钟时间 | 最大运行时长 |
| 输入/输出 Token | 分别限制输入和生成量 |
| 估算费用 | 按模型单价计算上限 |
| 并发额度 | 同时执行的工具调用数 |

**检查机制：** 每次模型或工具调用前**预扣/检查预算**，子任务不能绕过父任务额度；不同任务类型可有不同上限。

**停止后处理：** 达到阈值就进入明确的 `stopped` / `budget_exhausted` 状态，**保存可解释的部分结果**，不要静默截断；可降级或转人工接管。

## Level 3｜设计取舍：如何选型，如何拆分

### 20. Master + Sub-Agent 架构如何设计？优点和问题是什么？

答：Master 负责任务拆分、路由和聚合，Sub-Agent 负责专长执行。核心要点是最小权限、结果 Schema 校验和失败回退。详细设计、优缺点和演进路径见 [[../05_Multi-Agent与Workflow/Multi-Agent与Workflow|Multi-Agent 与 Workflow]]。

### 21. 多 Agent 拆分的依据是什么？如何决定任务边界？

答：

**拆分依据：**

| 依据 | 说明 |
|------|------|
| 目标 | 子任务目标是否独立 |
| 工具权限 | 所需工具/权限是否有差异 |
| 数据域 | 数据是否天然分区 |
| 验收标准 | 是否能独立验收 |
| 并发关系 | 是否可并行执行 |

一个子 Agent 应有**单一职责、独立错误语义和可测试结果**，不是“每个步骤一个 Agent”；否则用函数或 Workflow 节点更简单。

**运行时定义（每个子任务必须声明）：**

| 属性 | 说明 |
|------|------|
| 输入/输出 Schema | 明确合同 |
| 数据域 | 隔离范围 |
| 工具权限 | 最小权限 |
| 预算 | Token/费用上限 |
| 超时 | 墙钟时间 |
| 验收标准 | 成功证据 |
| 失败回退 | 降级/重试策略 |

**反模式警告：**

| 🚩 危险信号 | 说明 |
|------------|------|
| 共享大量上下文 | 通常边界划错了 |
| 频繁来回调用 | 能用函数/Workflow 节点更简单 |

### 22. 如何设计一个客服 Agent、搜索 Agent、数据分析 Agent 或代码 Agent？

答：先定义任务成功证据和不能做的事，再设计**最小工具集、状态、权限和人工接管点**；随后补检索/执行环境、验证器、Trace、Eval 和预算。不同产品的区别主要在工具和风险边界，不在是否画成多个 Agent。

### 23. 如果让你从零设计一个企业级 Agent 平台，模块如何拆分？

答：至少包括请求入口与身份、模型适配、Context/Memory、编排 Runtime、Tool Gateway、策略/审批、状态与任务队列、Trace/Eval、配置版本和运营后台。平台层提供通用约束，业务层只声明任务、工具和验收标准，避免把权限逻辑散落在 Prompt 中。

### 24. 为什么长任务不能只靠一次 Agent Loop 持续运行？

答：可以从三个层面来理解。

**模型层（最根本）**：Agent Loop 每跑一轮，上下文都在膨胀——上一轮的 tool_call 和 tool_result 会被追加进上下文。Loop 越多，上下文越长，最终会撞上模型的 token 上限（如 128k）。即使没超限，长上下文下模型注意力分散，早期步骤的结果容易被忽略（Lost in the Middle），推理质量下降。同时每轮都要发送完整上下文，token 成本和延迟也随 Loop 次数线性增长。

**架构层**：一次 Loop 绑定当前进程、连接和内存。排队、人工审批、模型重试、版本发布等场景都会中断 Loop，无法可靠跨进程持久运行。

**基础设施层**：要让长任务可靠运行，必须提升为显式任务状态机，把状态、Checkpoint 和事件持久化，并由独立 Worker 接管。Lease、幂等、未知副作用和跨版本恢复统一见 [[../12_课程深化/03_Durable与生产运维/Durable与生产运维|Durable Execution 与生产运维]]。

三个层面加在一起，才能完整解释为什么长任务不能只靠一次 Agent Loop 跑到底。

### 25. 如何处理 Agent 运行中模型、工具、数据库或网络故障？

答：

**错误分类：**

| 类型 | 处理策略 |
|------|---------|
| 暂时性故障 | 幂等调用限次退避重试 |
| 未知结果 | 先查询或对账，不能直接重放 |
| 权限拒绝 | 换路径或请求用户 |
| 不可恢复错误 | 停止并保留部分结果 |

**系统级防护：**

| 措施 | 说明 |
|------|------|
| 依赖隔离 | 超时和错误隔离，避免一个故障拖垮所有任务 |
| 健康检查 | 监控模型/工具/数据库/网络可用性 |
| 限流 + 重试预算 | 控制重试频率和总次数 |
| 切换/降级 | 切换备用提供商、降级为只读或固定流程 |
| 只读降级 | 写操作不可用时只返回查询结果 |

**事后处理：** 所有失败写入 Trace，未知副作用进入对账；故障期间保留任务状态，恢复后可以继续而不是让用户重复提交；向用户说明任务是否部分完成。

### 26. Agent 如何进行模型路由和多模型 Fallback？

答：

**路由依据：**

| 维度 | 说明 |
|------|------|
| 任务类型/能力 | 代码、推理、对话、长文本等 |
| 复杂度 | 简单问答 vs 多步规划 |
| 隐私 | 数据能否出境/调用外部模型 |
| 延迟 | 实时交互 vs 离线批处理 |
| 成本/预算 | Token 单价和总额限制 |
| 工具调用能力 | 是否支持结构化 Tool Call |

**适配层：** 给每个模型定义可接受的输入输出合同，适配器统一消息/工具/错误格式。

**Fallback 原则：**
- 只切换兼容模型，不能只换模型重发
- 记录版本、重试次数和结果差异
- 避免不同模型产生不兼容的工具参数或安全行为
- 重试要考虑副作用

**上线前验证：** 对每个模型跑同一套工具选择、结构化、安全和长尾评测。

---

**追问：如何在质量、延迟、并发和成本之间做取舍？**

把任务按复杂度和风险分级，简单任务用轻量模型/Workflow，复杂任务增加检索、工具或更强模型；同时设置质量下限、安全门槛和 P95/预算上限。用分桶实验确认节省没有来自漏做验证或降低成功标准。

---

**追问：如何为高质量模型、低成本模型和专用模型设计路由与 Fallback？**

定义能力标签、最大 Context/工具支持、延迟/成本和安全等级，先按任务风险和复杂度路由；Fallback 只能去到合同兼容且预算允许的模型，并在结果上做同样验证。记录路由命中、失败原因和效果差异，避免低成本模型被迫承担不适合的任务。

### 27. Agent 如何接入已有业务系统而不破坏原有流程？

答：从只读、可回放的旁路能力开始，通过适配层复用现有 API 和权限，不让模型直接访问数据库；高风险写操作先预览/审批，再逐步灰度。上线前定义回滚、对账、审计和人工接管，确保 Agent 失败不会改变核心业务事实。

### 28. 如何从业务目标反推 Agent 的能力边界和成功标准？

答：把业务目标拆成用户任务、可观察结果、允许的副作用、错误成本和人工兜底，再决定模型能做哪些决策、工具能执行哪些动作。成功标准要同时包含任务结果、时间/成本、错误率、安全和用户接管率。

## Level 4｜场景追问：把架构落到真实业务

### 29. 设计一个客服 Agent：哪些步骤用 Workflow，哪些步骤交给 Agent？

答：身份校验、订单查询、退款规则和审批状态用确定性 Workflow；意图理解、问题澄清和在多个只读知识源之间选择工具可交给 Agent。退款、改地址等副作用动作必须经过权限、规则和必要的人工确认，并用订单状态验证成功。

### 30. 设计一个 Coding Agent：如何处理仓库读取、命令执行、测试和失败恢复？

答：先用索引/搜索定位文件，再以受限 workspace 生成补丁；命令执行在沙箱中，限制网络、时间和文件范围，测试结果作为工具事实回填。每次修改都记录 diff 和 Checkpoint，失败时优先读取错误并小范围修复，不能无限重写或直接覆盖用户改动。

### 31. 设计一个数据分析 Agent：如何保证模型不能跳过计算直接编造结论？

答：让模型只能生成查询/分析计划，实际 SQL/Python 必须由执行器运行；结果经过 schema、数值和数据行数校验后才允许生成结论。把“已执行的代码、输出摘要、验证状态”作为成功证据，并在评测中专门检测假分析。

### 32. 如果线上任务偶发卡死，你会优先检查 Loop、State、工具还是外部依赖？为什么？

答：先看 Trace 的最后状态、停止预算、重复动作和租约/心跳，确定卡在模型等待、工具等待、状态提交还是队列调度；再检查对应依赖。不能直接归因于模型，因为无进展循环、未释放租约和未知副作用都可能表现为卡死。

## Level 5｜代码 Agent 的通用运行边界

### 33. 为什么模型输出的工具调用只能算提案，不能算命令？

答：模型输出是非确定性的文本，可能被用户输入、文件内容或工具结果诱导，也可能参数错误或越权。程序必须重新解析参数、收集真实环境事实、执行权限策略，必要时请求人工审批；只有通过这些步骤的内部对象才能触发副作用。

### 34. ReAct 或 Tool-use Loop 的最小状态是什么？

答：至少需要用户目标、当前阶段、历史观察、待执行提案、预算、错误/重试状态和终止状态。生产系统还需要证据账本、权限上下文、版本信息和持久化恢复点，不能只用一串聊天消息表示全部状态。

### 35. Context、State、ModelResult 和 Trace 为什么要分开？

答：State 是程序维护的运行事实，Context 是本轮选择后展示给模型的输入，ModelResult 是模型刚返回的提案，Trace 是用于审计和回放的事件记录。分开后**可以压缩上下文而不丢状态**，并在不重新执行副作用的情况下重放历史。

### 36. 为什么循环必须有多种预算，而不只是最大轮数？

答：轮数无法反映并行工具数量、Token、费用、墙钟时间、输出大小和副作用次数。应按风险设置步数、工具调用、时间、Token、成本、并发和结果大小上限，并在每次模型调用和工具执行前检查。

### 37. Agent 的“自然结束”和“成功”有什么区别？

答：自然结束只表示模型没有继续提出工具调用；**成功还要求满足任务类型对应的可验证标准**，例如修改后的差异存在、检查在最后一次写入后通过且没有安全违规。**模型文本只能解释结果，不能单独证明成功**。
