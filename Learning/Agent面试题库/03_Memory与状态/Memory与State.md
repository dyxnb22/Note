# Memory 与 State

> 递进路径：先区分记忆和状态，再设计读写策略，最后解决并发、恢复和隐私。

## Level 1｜基础认知：记忆、上下文和状态的边界

### 1. 短期记忆、长期记忆、任务记忆、工作记忆分别是什么？

答：短期记忆是当前对话或上下文窗口中的**近期信息**，长期记忆是**跨会话保存的稳定事实/偏好**，任务记忆是**某个任务的目标、计划和中间产出**，工作记忆是**当前一轮推理需要的临时变量**。工程上应**按生命周期和权限分开**，而不是都塞进聊天历史。

### 2. 对话历史、Summary、结构化状态和向量 Memory 如何配合？

答：原始历史用于**审计和必要回放**，Summary 用于压缩连续对话，结构化 State 保存当前任务事实和状态，**向量 Memory 用于按语义召回长期信息**。进入模型前由 Context 层组合相关部分，任何一种存储都不应自动等于可信指令。

### 3. 什么信息应该写入长期记忆？什么信息不应该写？

答：适合写入的是用户**明确表达、长期稳定、未来有用且有授权**的偏好或事实；临时情绪、一次性任务细节、未经验证的模型推测和敏感信息默认不写。写入前要做**来源、置信度、权限和可删除性判断**。

### 4. 用户偏好、事实、任务进度和工具结果应该分别如何保存？

答：偏好/事实用带**来源和时间的结构化 Memory**，任务进度放任务 State/Checkpoint，工具结果保存为**可追溯的事件或结果引用**，原始大对象放外部存储。分开保存可以分别控制更新、过期、权限和上下文暴露。

### 5. 跨 Session 应该保留哪些信息？

答：只保留经用户授权、对未来任务确实有用且不会造成明显隐私风险的信息，例如**稳定偏好或未完成任务摘要**。跨 Session 读取前仍要按租户、用户、场景和时间过滤，并允许查看、修改和删除。

### 6. Memory 与 RAG 的边界是什么？

| 维度         | RAG                       | Memory                      |
| ---------- | ------------------------- | --------------------------- |
| **数据来源**   | 外部知识库、业务文档                | 用户/任务个性化事实                  |
| **核心特征**   | 版本、权限、引用、新鲜度              | 写回、遗忘、冲突、隐私                 |
| **成功标准**   | 召回准确、引用正确、答案有据            | 个体化状态正确、隐私安全                |
| **治理要求**   | 版本控制、权限治理、文档更新            | 可删除性、冲突处理、来源追踪              |
| **更新机制**   | 文档级版本管理、增量索引              | 实时写回、异步抽取、用户确认              |
| **权限策略**   | 租户/文档级权限过滤                | 用户/任务级字段过滤                  |
| **典型场景**   | 企业知识问答、文档检索               | 个性化助手、任务状态跟踪                |
| **数据生命周期** | 随源文档版本、保留和删除策略同步    | 按用途、授权、过期和用户删除策略管理 |
| **冲突处理**   | 多版本文档冲突，优先权威来源            | 用户纠正旧信息，生成新版本并失效旧版本         |
| **隐私要求**   | 取决于知识源，企业场景通常同样很高          | 较高，需支持删除、审计、敏感信息检测          |
| **存储形式**   | 文档块 + 元数据（页码、坐标等）         | 结构化字段 + 文本引用 + 向量索引         |
| **评估指标**   | Recall、Precision、MRR、NDCG | 写入准确率、召回率、任务成功率、用户纠正率       |
| **用户交互**   | 只读检索                      | 读写操作，支持查看、修改、删除             |
| **共用基础设施** | ✓ 向量检索、混合召回、Rerank        | ✓ 向量检索、混合召回、Rerank          |
| **关键约束**   | 索引命名空间和授权策略不能混为一谈         | 不要用长期 Memory 代替有版本和权限治理的知识库 |

### 7. Memory 与普通数据库、缓存和日志的边界是什么？

答：数据库保存**结构化业务事实**，缓存优化访问速度，日志记录**发生过的事件**，Memory 是经过选择、**可被未来任务召回的上下文资产**。Memory 可以引用这些系统，但不能成为订单、权限或审计事实的唯一来源。

## Level 2｜原理机制：Memory 如何读写和检索

### 8. Memory 的写回时机如何设计？实时写、任务结束写还是异步写？

答：用户**明确确认的稳定偏好可在会话中实时写**；任务状态随关键节点同步 Checkpoint；**需要模型抽取的长期 Memory 可以异步写**，但必须经过校验和权限检查。异步写要有**幂等键**、失败重试和可追踪状态，不能阻塞主流程也不能无条件写入。

### 9. Memory 的读取时机如何设计？

答：在意图和权限确定后读取**与当前任务相关的 Memory**，避免一开始把所有历史塞给模型；需要实时事实时**优先查权威业务系统**。**读取结果要带来源、时间和可信度**，供后续 Context 选择和冲突处理。

### 10. Memory 如何分层、过滤、召回、重排和衰减？

答：先按用户/租户/任务/类型和权限过滤，再用**关键词或向量召回候选**，按相关性、新鲜度、来源可信度和使用历史**重排**，最后按**过期策略衰减或归档**。召回规模受 Token 和隐私预算限制，不能只按相似度排序。

### 11. 为什么可以用 RAG 检索 Memory？向量方式有什么优缺点？

答：Memory 往往是自然语言片段，向量检索能找出**语义相近但词面不同的历史信息**；缺点是可能**召回相似但不适用、过期或越权的内容**。因此需要**结构化过滤、时间/权限约束、重排和事实验证**，不能把向量相似当成事实正确。

### 12. 结构化记忆与文本记忆如何避免重复？

答：为每类记忆**定义主存储**：**可验证的字段放结构化记录**，**解释性或原始上下文放文本引用**；写入时**做实体/事实去重和版本关联**。Context 中优先展示**结构化当前值，必要时再加载原文证据**。

### 13. 如何判断一条 Memory 是否有用？

答：看它是否被相关任务召回、是否改变了正确的决策或减少了用户重复输入，并同时检查误召回、冲突和隐私代价。可以用**带/不带该 Memory 的离线对照、线上任务成功率和用户纠正率评估。**

### 14. 如何防止错误信息被长期记忆放大？

答：记录**来源、时间、置信度和验证状态**，模型推测**默认不写**；高影响事实**要求用户确认或权威系统验证**。召回时把**未验证信息标成候选事实**，发现冲突时暂停自动执行**并更新/删除旧记忆**。

### 15. 用户明确纠正旧信息时，如何更新和删除旧记忆？

答：创建新版本并把**旧版本标记为失效或删除，同时更新向量索引、缓存和引用**；后续查询**按有效版本过滤**。操作要**记录主体、时间、原因和影响范围**，确保**恢复/回放不会重新使用已撤销信息**。

### 16. 记忆冲突怎么解决？

答：先按来源权威性、用户最新明确确认、时间和业务状态**排序**；若无法确定就**保留冲突并向用户澄清**，不要让模型静默选一个。对关键业务事实**应回查权威系统，冲突解决结果也应有审计记录**。

### 17. 记忆的时间衰减如何设计？

答：不同类型采用**不同生命周期**：临时偏好短期过期，稳定偏好可长期保存**但允许复核**，业务事实**以权威系统为准**；可以结合**最后确认时间、使用频率和错误率衰减**。衰减不应悄悄改变用户可见事实，过期后应**重新确认或降级为低可信候选**。

### 18. 如何处理不同来源、不同可信度的记忆？

答：为每条记忆记录来源类型、采集时间、确认人/系统、置信度和权限，召回时按**可信度与任务相关性共同排序**。用户**明确陈述和权威系统结果通常高于模型推断**，但仍要按业务语境校验。

### 19. 如何做 Memory 的离线评测和线上监控？

答：离线测写入准确率、召回 Recall/Precision、冲突处理、删除生效和带记忆任务成功率；线上监控召回使用率、**纠正率、越权/隐私事件、延迟和成本**。评测必须包含错误记忆、过期记忆和跨租户隔离案例。

## Level 3｜设计取舍：State、Checkpoint 与并发一致性

### 20. State 全局管理如何做？

答：定义单一 State Schema 和字段所有者，明确**哪些节点可读写、哪些字段只能由系统更新**；状态迁移通过事件或事务提交并**带版本号**。模型只看到 Context 选择出的必要字段，不能直接修改内部权限和审计字段。

### 21. 多 Agent 并行更新共享 State 时，如何避免覆盖？

答：

**避免覆盖机制：**

| 措施 | 说明 |
|------|------|
| 独立命名空间 | 子任务写自己的分区，避免直接写共享字段 |
| 聚合点合并 | 父节点在固定位置合并子任务结果 |
| 版本号/乐观锁 | 写入前校验版本，冲突时拒绝或合并 |
| 事务或事件顺序 | 用事务保证原子性，或按事件时间戳排序 |
| 冲突策略 | 定义优先级、取最新或人工仲裁 |

**关键原则：**
- 所有写入都带来源和任务 ID
- 模型不能决定最终覆盖规则
- **不要让多个 Agent 直接对同一个自由格式 JSON 全量覆盖**

### 22. 如何设计 State Schema 和状态版本？

答：Schema 应包含任务 ID、状态、目标、计划、已验证事实、待办、预算、工具轨迹引用和错误/审批信息，并为每次变更记录版本和时间。**兼容升级提供迁移器或双读双写**，不能只改字段名后期待旧 Checkpoint 自动可用。

### 23. 如何用乐观锁、事件溯源或事务保证状态一致性？

答：乐观锁用版本号检测并发更新，冲突时**重新读取并合并**；事件溯源**保存不可变事件**，再按顺序重建 State；事务适合把**业务状态和幂等记录一起提交**。选择取决于一致性、吞吐、回放和运维复杂度，不能只为“看起来分布式”而上事件溯源。

### 24. 进程崩溃后如何从 Checkpoint 恢复？

答：

**恢复步骤：**

| 步骤 | 说明 |
|------|------|
| 取得合法 Lease | 新 Worker 先取得任务租约，防止重复执行 |
| 读取 Checkpoint | 读取最新有效、带版本的 Checkpoint |
| 版本校验 | 验证任务、代码/图、工具和策略版本是否兼容 |
| 副作用核对 | 检查未完成操作的外部状态是否已发生 |
| 安全重试 | 可安全重试的动作才重试，否则先查询或进入人工处理 |

**恢复后处理：**
- 从明确节点边界继续，**避免从头重复全部步骤**
- 写入新的状态/事件
- **记录 resume 事件**，便于审计
- 不兼容或未知副作用进入人工处理

### 25. State 中哪些字段应该对模型可见，哪些字段只能由系统维护？

答：**目标、必要事实、计划和用户可见进度**可通过 Context 暴露；**权限决策、Secret、内部策略、审计原文、租约和系统时间**等只能由系统维护。模型即使看到某字段，也不能因此获得写权限。

### 26. 如何避免把内部状态和敏感信息泄露给模型？

答：使用字段级 allowlist 组装 Context，先**脱敏和最小化，再按任务提供**；**敏感动作通过受控工具返回必要结果而不是原始凭证**。还要记录 Context 版本和来源，便于发现错误暴露。

### 27. 多租户场景下如何隔离 Memory、State 和 Checkpoint？

答：所有键、查询、索引和缓存都带不可伪造的 **tenant/user scope**，权限过滤在**存储查询和应用层双重执行**；跨租户聚合需**显式授权**。异步 Worker、日志、Trace 和向量索引也必须**继承同一隔离上下文**。

### 28. State 过大时如何压缩和归档？

答：把当前可执行状态、历史事件、原始工具结果**和大对象分开**，当前 State 只保留**必要摘要和引用**；历史写入不可变日志或对象存储，按策略归档。压缩后保留版本、来源和可恢复证据，不能只删除文本。

### 29. 如何处理并发任务对同一份 State 的读写？

答：先决定是否允许并发：不允许就用**任务级锁或串行队列**；允许则隔离写集、**使用版本校验和确定性合并**，**冲突交给系统或人工处理**。模型不能充当并发控制器。

## Level 4｜场景追问：把 Memory 放进真实产品

### 30. 设计一个多角色对话系统，用户和多个 AI 角色的记忆如何隔离和共享？

答：按用户、角色和会话建立命名空间，**角色只能读自己的私有记忆和明确共享区**；共享内容经过**权限和来源标记**，不能因为同一会话自动互通。角色写回要带 owner、scope、时间和可删除标记，召回时按当前角色过滤。

### 31. 用户先说“我住在上海”，后来改成“我住在深圳”，旧记忆如何处理？

答：把新陈述视为用户明**确纠正，生成新版本并使上海记录失效**，同时更新索引、缓存和当前 Context；如果业务允许保留历史，也**只能作为审计**，不作为当前居住地使用。关键动作前仍可向用户确认当前值。

### 32. 长任务运行到一半进程崩溃，如何判断哪些工具副作用已经发生，再从 Checkpoint 恢复？

答：读取 **Checkpoint 和工具执行日志**，使用幂等键/业务查询确认外部状态；已成功提交的不重做，**结果未知的先对账，未开始的才继续**。恢复过程写入新的事件和停止/重试原因，并在无法确认时转人工。

### 33. 记忆召回明显提升了回答相关性，但隐私风险增加，如何设计权限、删除和审计？

答：把 Memory 按用户/租户/用途分类，读取采用**最小权限和字段级过滤**，写入**前提供授权和敏感信息检测**；支持按条目、用户和来源删除并使缓存/索引同步失效。审计记录谁在什么任务读取/修改了哪类记忆，评测同时看质量和越权率。
