# Agent 可靠性与安全

> 递进路径：先识别失败，再建立安全边界，最后把沙箱、审批、审计和恢复放进系统。

## Level 1｜基础认知：Agent 为什么会失控

### 1. Agent 幻觉有哪些类型？如何定位来源？

答：常见有事实编造、错误引用、假装调用工具、错误计划、把不可信文本当指令和过度自信表达。通过 Trace 检查 Context、检索证据、工具结果、验证器和最终输出，定位到检索、上下文、模型、工具或展示层，而不是笼统归因于“模型幻觉”。

### 2. 如何通过检索、工具验证、交叉检查和人工确认减少幻觉？

答：需要外部事实时要求引用可追溯证据，需要计算/状态时强制调用权威工具，关键结果用规则或第二来源校验，高风险动作进入人工确认。机制要有失败分支和拒答，不是要求模型“更自信地正确”。

### 3. 如何识别 Agent 没有真正执行工具而是编造结果？

答：成功必须依赖执行器产生的调用 ID、退出码、结构化结果或外部状态，而不是模型文字；最终回答引用这些证据。没有对应 Trace/验证结果就标为未执行或未知，阻止模型宣称成功。

### 4. 长任务如何避免死循环、重复计划和无效重试？

答：维护已执行动作和进展指标，设置最大步数/时间/Token/费用、重复调用和无进展检测；重试只针对可恢复、可幂等错误。计划变化需有原因，超过阈值就降级、请求用户或转人工。

### 5. 如何设计最大步数、最大 Token、超时和预算上限？

答：在任务级 State 中维护累计计数，每次模型/工具调用前检查并预留预算，子任务不能绕过父任务额度；不同任务类型可有不同上限。达到上限应返回明确的 stopped/budget_exhausted 和已完成结果，不要静默截断。

### 6. 子任务失败、数据损坏或返回异常时，如何重试、降级和恢复？

答：先分类参数、权限、暂时依赖、未知副作用和不可恢复错误；可修正参数让模型修正，幂等暂时错误限次退避，未知结果先对账，无法恢复则保留部分结果并人工接管。恢复从 Checkpoint 继续而不是无条件从头跑。

### 7. 如何区分可重试错误和不可重试错误？

答：网络超时、限流、临时不可用通常可能可重试，前提是动作幂等；参数非法、权限拒绝、业务规则拒绝和输入缺失不应盲重试。错误合同应明确 `retryable`、重试预算和是否需要查询状态。

### 8. 如何保证重试不会重复执行外部副作用？

答：使用服务端持久化幂等键、业务唯一约束和执行状态；超时后先查询业务状态，区分已成功、未执行和未知。客户端内存计数或 Prompt 里的“不要重复”不能抵抗进程重启和并发。

### 9. 如何处理部分成功、部分失败和不可逆动作？

答：把每个子动作记录为独立状态，向用户说明已完成、未完成和未知部分；可逆动作提供补偿，不可逆动作进入对账和人工流程。最终结果不能用一个全局布尔值掩盖中间副作用。

### 10. 如何设计 Fallback、熔断、重试、降级和人工转接？

答：按错误类型和风险预先定义策略：模型不可用可切换兼容模型，工具不可用可读缓存/固定流程，连续失败熔断并排队或转人工；每种降级说明能力损失和用户提示。Fallback 仍需同样的权限、Trace 和成功验证。

### 11. 如何处理模型、工具、数据库或网络供应商故障？

答：隔离依赖超时和错误，避免一个故障拖垮所有任务；使用健康检查、限流、重试预算、备用提供商或只读降级，未知副作用进入对账。故障期间要保留任务状态，恢复后可以继续而不是让用户重复提交。

### 12. 如何让 Agent 在不确定时主动拒答或请求确认？

答：定义证据阈值、置信度/冲突条件和高风险动作清单，未满足时输出缺少什么信息、可以怎么补充，并进入澄清或人工状态。拒答也要可解释、可恢复，不能只是生成一句“我不确定”。

## Level 2｜安全机制：信任边界和数据保护

### 13. 什么是 Prompt Injection？直接注入和间接注入有什么区别？

答：Prompt Injection 是攻击者让模型改变原定行为、泄露信息或执行越权动作；直接注入来自用户输入，间接注入藏在网页、文档、邮件或工具结果中。后者尤其危险，因为系统可能把外部数据自动送进模型并触发工具。

### 14. 如何防御恶意网页、文档、邮件和工具返回中的注入？

答：把外部内容标成不可信数据，与系统指令/工具策略分区；限制可用工具和数据范围，执行层重新授权，浏览/代码操作进入沙箱，并对高风险动作审批。Prompt 过滤只能作辅助，不能让模型单独承担防线。

### 15. 如何防止用户输入覆盖系统约束？

答：用户输入放在低信任字段，系统策略和工具权限由应用代码/策略引擎维护；模型输出先过 Schema、allowlist 和授权，用户不能修改这些控制字段。对冲突请求应解释边界并提供安全替代路径。

### 16. 如何防止数据外泄？

答：按用户/租户/资源做最小权限和字段级过滤，Context、工具结果、日志和缓存都做数据分类/脱敏；出口工具控制域名、动作和传输内容，敏感操作审批。安全评测要加入越权查询、跨租户召回和提示注入样本。

### 17. 如何设计最小权限、凭证隔离、租户隔离和网络隔离？

答：每个任务使用短期、最小 Scope 的身份，工具按 actor/tenant/resource/operation 授权；不同租户的 State、Memory、索引、缓存和 Trace 强制带 Scope。沙箱限制文件、网络、进程和时间，不能把主应用密钥放进模型或子 Agent。

### 18. 如何让不同 Agent 只能看到自己需要的数据？

答：为每个 Agent 定义数据域和工具白名单，Context 组装只读允许字段，服务端查询和执行器再次过滤；父 Agent 不能把全量上下文自动传给子 Agent。共享数据使用明确的发布/授权区并记录来源。

### 19. 如何处理模型输出中的敏感信息？

答：输出前做敏感信息检测、脱敏和策略检查，禁止模型直接展示凭证、完整个人信息或内部提示；需要给用户看时按身份和用途最小化。日志、Trace、缓存和评测集也要使用同样的脱敏策略。

### 20. 如何做敏感信息识别和脱敏？

答：结合规则/正则、实体识别、数据分类和来源标签，按字段和场景替换或部分掩码；对高风险类型采用阻断或人工审核，并保留不可逆的审计摘要。脱敏后要评估是否仍能重识别，不能只替换几个关键词。

## Level 3｜工程落地：沙箱、审批与审计

### 21. 代码执行、Shell、浏览器和数据库工具如何沙箱化？

答：每次执行使用隔离 workspace/容器或专用沙箱，限制文件目录、网络出口、CPU/内存/时间和子进程；数据库工具只暴露参数化、最小权限的接口。浏览器结果仍是不可信内容，写操作要审批和审计。

### 22. Docker、容器、虚拟机和专用沙箱如何选择？

答：容器启动快、适合受控同机隔离，但内核共享；虚拟机隔离强、成本和启动时间更高；专用沙箱根据代码/浏览器威胁模型提供更严格的系统调用和网络控制。选择取决于攻击面、租户信任、性能、成本和合规要求，不能只看部署方便。

### 23. 如何限制 CPU、内存、磁盘、网络、进程和执行时间？

答：使用 cgroup/沙箱配额、只读或临时文件系统、进程数上限、超时杀进程和网络 allowlist；任务级别还要限制 Token、工具调用和费用。超限时写入可解释的终止事件并清理资源，防止残留进程和数据。

### 24. 哪些动作必须 Human-in-the-Loop？

答：付款、删除、发信、发布、修改权限、法律/医疗/高影响决策、访问敏感数据和不确定副作用通常需要人工；低风险只读或可逆动作可自动化。审批要显示具体对象、参数、证据、影响和有效期，而不是只显示“允许 Agent 执行”。

### 25. 如何让用户预览、确认、撤销和回滚 Agent 动作？

答：先生成结构化计划和差异预览，用户确认后以审批 ID 执行；可逆动作保存原状态/反向操作，不可逆动作设计补偿和人工对账。确认后重新校验资源版本和权限，防止用户批准的是过期状态。

### 26. 如何记录审计日志？日志中哪些信息不能直接保存？

答：记录谁、哪个租户/任务、调用了什么工具、作用于哪个资源、策略/审批结果、版本、时间、耗时和副作用状态；Secret、完整 Token、私有源码和不必要的原始 Prompt 不应默认保存。日志要可检索、不可随意篡改、可设保留期并有访问审计。

### 27. 如何让 Agent 行为可解释、可追踪和可回放？

答：记录结构化的计划、动作提案、工具结果、状态转移、权限决策、验证结果和停止原因，不依赖不可验证的私有思维链。回放冻结输入、模型/工具版本和外部 Fixture，能重建“为何做了这个动作”。

### 28. 如何评估系统的安全边界和越权风险？

答：建立威胁模型和攻击集，测试直接/间接注入、跨租户查询、敏感信息泄露、工具参数越权、沙箱逃逸和审批绕过；指标包括阻断率、误放行、误拒绝和恢复时间。安全评测要纳入发布门禁，不只做一次人工演示。

### 29. 如何处理多租户场景下的权限、配额和数据隔离？

答：身份上下文贯穿请求、模型、工具、队列、存储、Memory、向量索引和日志，所有查询和缓存键带租户 Scope；配额按租户/用户/工具分别限制，后台 Worker 重新验证。跨租户统计要用脱敏聚合，不能把原始数据放到共享 Context。

### 30. 如何在安全、体验、成本和自动化程度之间取舍？

答：按动作风险分级：低风险自动化，中风险预览/确认，高风险人工或禁止；对每级测量任务成功、延迟、成本、误拒绝和安全事件。不要用“全自动”当目标，好的设计是让用户清楚知道系统能做什么以及何时会停。

## Level 4｜场景追问：高风险动作如何可控

### 31. 设计一个可以查订单、退款和修改地址的客服 Agent，哪些动作需要人工确认？

答：查订单是只读，可在权限校验后自动执行；退款和改地址会产生业务副作用，应先验证身份、订单状态、规则和金额，再展示目标/参数并按风险决定人工确认。所有写操作使用幂等键、状态查询、审计和失败对账。

### 32. 网页内容要求浏览器 Agent 忽略系统指令并上传用户文件，如何在数据层、模型层和工具层拦截？

答：数据层把网页内容标为不可信并限制文件/网络 Scope；模型层明确外部文本不是指令并拒绝把它转成上传动作；工具层只允许经过策略授权的域名和文件，上传必须审批。即使模型被诱导，工具层也应阻断越权调用。

### 33. 工具调用已经成功但前端断线了，重试前如何判断外部副作用是否已经发生？

答：根据调用 ID/幂等键、服务端执行记录和业务查询确认状态；已成功则只补发结果，未执行才重试，未知则进入对账而不是重复动作。恢复时向用户展示最终状态和可能的延迟，不能把前端断线当成工具失败。

### 34. 如何用一次真实事故复盘证明安全机制不是只停留在 Prompt？

答：还原攻击输入、Context、工具候选、授权决策、实际副作用和停止原因，明确哪一层没有拦截；随后把修复落到权限、Schema、沙箱、审计或审批，并用攻击回归集证明阻断。若答案只是“优化 Prompt”，说明根因还没有解决。
