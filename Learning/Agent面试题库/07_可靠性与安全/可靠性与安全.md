# Agent 可靠性与安全

> 递进路径：先识别失败，再建立安全边界，最后把沙箱、审批、审计和恢复放进系统。

## Level 1｜基础认知：Agent 为什么会失控

### 1. Agent 幻觉有哪些类型？如何定位来源？

答：常见有**事实编造、错误引用、假装调用工具、错误计划、把不可信文本当指令和过度自信表达**。通过 **Trace** 检查 Context、检索证据、工具结果、验证器和最终输出，定位到检索、上下文、模型、工具或展示层，而不是笼统归因于“模型幻觉”。

### 2. 如何通过检索、工具验证、交叉检查和人工确认减少幻觉？

答：需要外部事实时**要求引用可追溯证据**，需要计算/状态时**强制调用权威工具**，关键结果用规则或第二来源校验，高风险动作进入人工确认。机制要有失败分支和拒答，不是要求模型“更自信地正确”。

### 3. 如何识别 Agent 没有真正执行工具而是编造结果？

答：成功必须依赖执行器产生的**调用 ID、退出码、结构化结果或外部状态**，而不是模型文字；最终回答引用这些证据。没有对应 Trace/验证结果就标为未执行或未知，阻止模型宣称成功。

### 4. 子任务失败、数据损坏或返回异常时，如何重试、降级和恢复？

答：先分类参数、权限、暂时依赖、未知副作用和不可恢复错误；可修正参数让模型修正，幂等暂时错误限次退避，未知结果先对账，无法恢复则保留部分结果并人工接管。恢复从 Checkpoint 继续而不是无条件从头跑。

### 5. 如何区分可重试错误和不可重试错误？

答：网络超时、限流、临时不可用通常可能可重试，前提是**动作幂等**；参数非法、权限拒绝、业务规则拒绝和输入缺失不应盲重试。**错误合同应明确 `retryable`、重试预算和是否需要查询状态**。

### 6. 如何处理部分成功、部分失败和不可逆动作？

答：把每个子动作记录为**独立状态**，向用户说明已完成、未完成和未知部分；可逆动作提供补偿，不可逆动作进入**对账和人工流程**。最终结果不能用一个全局布尔值掩盖中间副作用。

### 7. 如何设计 Fallback、熔断、重试、降级和人工转接？

答：按错误类型和风险预先定义策略：**模型不可用可切换兼容模型，工具不可用可读缓存/固定流程，连续失败熔断并排队或转人工**；每种降级说明能力损失和用户提示。Fallback 仍需同样的权限、Trace 和成功验证。

### 8. 如何让 Agent 在不确定时主动拒答或请求确认？

答：定义证据阈值、置信度/冲突条件和高风险动作清单，未满足时输出缺少什么信息、可以怎么补充，并进入澄清或人工状态。拒答也要可解释、可恢复，不能只是生成一句“我不确定”。

## Level 2｜安全机制：信任边界和数据保护

### 9. 什么是 Prompt Injection？直接注入和间接注入有什么区别？

答：Prompt Injection 是攻击者**让模型改变原定行为、泄露信息或执行越权动作**；直接注入来自用户输入，**间接注入藏在网页、文档、邮件或工具结果中**。后者尤其危险，因为系统可能把外部数据自动送进模型并触发工具。

---

**追问：Prompt 层如何降低用户输入覆盖系统约束的概率？为什么仍然不够？**

在消息和模板中把系统规则、可信 Context 与用户数据分区，**明确指令优先级**、引用边界和冲突处理，并避免把外部文本拼成系统指令。这只能降低模型误解；真正的 allowlist、授权、沙箱和副作用审批**统一由执行层负责，不能由 Prompt 自证安全**。

---

**追问：如何防止检索内容中的 Prompt Injection？**

防御层次包括：标记（检索内容明确标记为不可信数据）、隔离（不能改变系统规则、工具权限或输出策略）、最小化（字段隔离，对高风险文档做内容检测）、重授权（执行器再次授权）、沙箱（浏览/代码操作进入沙箱）、审批（高风险动作需人工确认）。**必要时让模型只提取事实，不把原文指令直接拼入高优先级 Prompt**。Prompt 过滤只能作辅助，不能让模型单独承担防线。

---

**追问：如何防止工具返回值中的恶意指令影响 Agent？**

把工具结果与系统指令分区并标记为外部数据，**限制它只能提供事实，不能改变权限、工具白名单或系统规则**；对网页/文档结果做内容扫描和最小化。执行层重新授权，即使模型被诱导也不能越权。

---

**追问：为什么模型输出和其他 Agent 输出都应被当作不可信数据？**

**输出可能包含幻觉、注入指令、恶意参数、越权建议或错误的外部事实**，即使来自受信模型也不是授权证明。下游应做 Schema、业务/权限、来源和安全校验，尤其不能让输出直接拼接命令或高风险操作。

---

**追问：UI 中的模型文本和仓库文本为什么也要视为不可信输入？**

文本可能包含 ANSI 控制序列、伪造提示、超长内容或恶意 Unicode。**渲染前应清理控制字符、限制长度和行数，并区分显示文本与可执行命令**；UI 防显示注入，不能替代工具权限和沙箱。

### 10. 如何防止用户输入覆盖系统约束？

答：用户输入**放在低信任字段**，系统策略和工具权限由应用代码/策略引擎维护；模型输出先过 Schema、allowlist 和授权，用户不能修改这些控制字段。对冲突请求应解释边界并提供安全替代路径。

### 11. 如何防止数据外泄？

答：按用户/租户/资源做**最小权限和字段级过滤**，Context、工具结果、日志和缓存都做数据分类/脱敏；出口工具控制域名、动作和传输内容，敏感操作审批。安全评测要加入越权查询、跨租户召回和提示注入样本。

### 12. 如何设计最小权限、凭证隔离、租户隔离和网络隔离？

答：每个任务使用短期、最小 Scope 的身份，工具按 actor/tenant/resource/operation 授权；不同租户的 State、Memory、索引、缓存和 Trace 强制带 Scope。沙箱限制文件、网络、进程和时间，不能把主应用密钥放进模型或子 Agent。

### 13. 如何让不同 Agent 只能看到自己需要的数据？

答：为每个 Agent 定义数据域和工具白名单，Context 组装只读允许字段，服务端查询和执行器再次过滤；父 Agent 不能把全量上下文自动传给子 Agent。共享数据使用明确的发布/授权区并记录来源。

### 14. 如何处理模型输出中的敏感信息？

答：输出前做**敏感信息检测、脱敏和策略检查**，禁止模型直接展示凭证、完整个人信息或内部提示；需要给用户看时按身份和用途最小化。日志、Trace、缓存和评测集也要使用同样的脱敏策略。

**追问：如何做敏感信息识别和脱敏？**

结合规则/正则、实体识别、数据分类和来源标签，按字段和场景替换或部分掩码；高风险类型阻断或人工审核，并保留不可逆审计摘要。还要评估脱敏后是否可被重识别。

## Level 3｜工程落地：沙箱、审批与审计

### 15. 代码执行、Shell、浏览器和数据库工具如何沙箱化？

答：每次执行使用**隔离 workspace/容器或专用沙箱**，限制文件目录、网络出口、CPU/内存/时间和子进程；数据库工具只暴露参数化、最小权限的接口。浏览器结果仍是不可信内容，写操作要审批和审计。

### 16. Docker、容器、虚拟机和专用沙箱如何选择？

答：容器启动快、适合受控同机隔离，但内核共享；虚拟机隔离强、成本和启动时间更高；专用沙箱根据代码/浏览器威胁模型提供更严格的系统调用和网络控制。选择取决于攻击面、租户信任、性能、成本和合规要求，不能只看部署方便。

### 17. 如何限制 CPU、内存、磁盘、网络、进程和执行时间？

答：使用 cgroup/沙箱配额、只读或临时文件系统、进程数上限、超时杀进程和网络 allowlist；**任务级别还要限制 Token、工具调用和费用**。超限时写入可解释的终止事件并清理资源，防止残留进程和数据。

### 18. 哪些动作必须 Human-in-the-Loop？

答：付款、删除、发信、发布、修改权限、法律/医疗/高影响决策、访问敏感数据和不确定副作用通常需要人工；低风险只读或可逆动作可自动化。审批要显示具体对象、参数、证据、影响和有效期，而不是只显示“允许 Agent 执行”。

### 19. 如何让用户预览、确认、撤销和回滚 Agent 动作？

答：先生成结构化计划和差异预览，用户确认后以审批 ID 执行；可逆动作保存原状态/反向操作，不可逆动作设计补偿和人工对账。确认后重新校验资源版本和权限，防止用户批准的是过期状态。

### 20. 如何记录审计日志？日志中哪些信息不能直接保存？

答：记录谁、哪个租户/任务、调用了什么工具、作用于哪个资源、策略/审批结果、版本、时间、耗时和副作用状态；Secret、完整 Token、私有源码和不必要的原始 Prompt 不应默认保存。日志要可检索、不可随意篡改、可设保留期并有访问审计。

### 21. 如何让 Agent 行为可解释、可追踪和可回放？

答：记录结构化的计划、动作提案、工具结果、状态转移、权限决策、验证结果和停止原因，不依赖不可验证的私有思维链。回放冻结输入、模型/工具版本和外部 Fixture，能重建“为何做了这个动作”。

### 22. 如何评估系统的安全边界和越权风险？

答：**建立威胁模型和攻击集**，测试直接/间接注入、跨租户查询、敏感信息泄露、工具参数越权、沙箱逃逸和审批绕过；指标包括阻断率、误放行、误拒绝和恢复时间。安全评测要纳入发布门禁，不只做一次人工演示。

### 23. 如何在安全、体验、成本和自动化程度之间取舍？

答：按动作风险分级：低风险自动化，中风险预览/确认，高风险人工或禁止；对每级测量任务成功、延迟、成本、误拒绝和安全事件。不要用“全自动”当目标，好的设计是让用户清楚知道系统能做什么以及何时会停。

## Level 4｜场景追问：高风险动作如何可控

### 24. 网页内容要求浏览器 Agent 忽略系统指令并上传用户文件，如何在数据层、模型层和工具层拦截？

答：数据层把网页内容标为不可信并限制文件/网络 Scope；模型层明确外部文本不是指令并拒绝把它转成上传动作；工具层只允许经过策略授权的域名和文件，上传必须审批。即使模型被诱导，工具层也应阻断越权调用。

### 25. 如何用一次真实事故复盘证明安全机制不是只停留在 Prompt？

答：还原攻击输入、Context、工具候选、授权决策、实际副作用和停止原因，明确哪一层没有拦截；随后把修复落到权限、Schema、沙箱、审计或审批，并用攻击回归集证明阻断。若答案只是“优化 Prompt”，说明根因还没有解决。

## Level 5｜代码 Agent 的安全与恢复边界

### 26. 代码 Agent 如何防止路径越界？

答：对用户和模型提供的路径做规范化，使用工作区根目录进行边界判断，拒绝 `..`、越界符号链接、受保护路径和不允许的文件类型，并在执行前后验证实际目标。错误应返回稳定的拒绝结果，而不是泄露系统路径。

### 27. 为什么一般 Shell 工具比专用工具更危险？

答：Shell 包含解释器、重定向、管道、环境变量、命令替换和任意程序组合，难以精确分类副作用。应优先提供窄而明确的工具；确需执行命令时使用 argv、固定环境、工作目录、超时、输出/资源限制和 OS 沙箱。

### 28. 沙箱能保证什么，不能保证什么？

答：沙箱可以限制文件、网络、进程和资源访问，降低执行的爆炸半径；它不能替代身份授权、参数校验、审计、版本检查和结果验证，也不能自动证明进程没有隐藏副作用。必须明确平台差异和失败时的默认行为。

### 29. Prompt Injection 为什么不能只靠更强的 System Prompt 防御？

答：注入可能来自仓库文件、网页、Issue、工具返回和用户内容，模型可能把数据误当指令。真正的权限边界必须由工具层、策略、沙箱、数据隔离和人工审批强制执行，不可信文本不能修改确定性规则。

### 30. 工具错误应该如何分类？

答：至少区分未知工具、参数错误、权限拒绝、审批拒绝、资源冲突、超时、供应商故障、业务失败和未知副作用。分类决定是否修正参数、重试、请求人工、恢复或终止，不能把所有失败都包装成“请模型再试一次”。

### 31. Evidence Gate 应该验证什么？

答：应验证任务对应的客观产物，例如实际 diff、最后一次写入后的检查结果、退出码、资源版本和确定性审查结果。模型文本只能作为解释，不能单独证明修改成功；检查若发生在最后一次修改之前，也不能证明最终内容通过。

### 32. 为什么执行命令的输出不一定是成功证据？

答：命令可能读取错误目录、没有覆盖真实改动、输出被截断，或只是打印“通过”而没有执行验证。系统应记录检查配方、工作区、退出状态、版本和执行时机，并用独立规则核对 diff 与结果。

## Level 6｜证据门禁与副作用恢复

### 33. 为什么“模型说已经修复”不能作为 Coding Agent 的成功标准？

答：

**为什么模型自述不可信：** 模型文本可能是推测、误读或被失败工具结果影响。

**修改任务的验证要求：**
- 实际代码差异（diff）
- 最后一次写入后的验证结果
- 资源版本和安全审查
- 隐藏测试、行为正确性、回归、边界
- Patch 是否最小、是否保留用户修改
- 测试是否真实运行
- 任务成本和时间

**只读任务：** 也要有明确范围、预算和停止原因，不能把自然结束等同于成功。

**代码 Agent 还应评估：** 导航、工具调用、失败修复和人工审查负担。“编通通过但改错文件”仍是任务失败。

### 34. 为什么检查必须发生在最后一次写入之后？

答：如果检查发生后又修改了文件，检查证明的是旧内容而不是最终产物。证据账本应记录编辑和检查的顺序，成功判定只接受位于最后一次写入之后且针对同一工作区版本的检查。

### 35. 如何防止恢复流程本身再次产生副作用？

答：恢复前核对外部副作用的完整机制见 [[../12_课程深化/03_Durable与生产运维/Durable与生产运维#8. 长任务恢复前为什么必须核对外部副作用？|Durable 与生产运维第 8 题]]。安全层只补充：恢复检查阶段必须只读，后续自动动作重走授权、幂等和资源版本边界；Replay 只投影事件或使用 Fixture，不调用真实工具。

### 36. 受保护资源被工具或子进程修改时，为什么仍要让调用失败？

答：OS 沙箱可能无法覆盖所有控制面路径，工具层还需要通过前后快照检测受保护资源变化。即使主要目标完成，控制面被篡改也意味着运行不可信；系统应记录安全失败并阻止把结果报告为成功。
