# 推理服务与模型行为

> 递进路径：先掌握 KV Cache、批处理和量化等服务基础，再理解额外推理预算、工具连续性，最后判断应改 Prompt、Schema、Harness 还是训练。

## Level 1｜推理服务基础

### 1. KV Cache 为什么能降低自回归生成延迟？代价是什么？

答：生成新 token 时，历史 token 的 Key/Value 不变，缓存后下一步只计算新增部分，减少重复计算。代价是缓存随序列长度、并发和层数占用显存，长 Context 的容量和调度会成为瓶颈。

### 2. Continuous Batching 解决了什么吞吐问题？

答：它按迭代把新请求加入批次、把完成请求移出，不必等待整批最长请求结束，因此更好利用 GPU、提高吞吐。它会带来调度、显存和公平性取舍，Agent 侧仍需设置租户配额、超时和背压。

### 3. 量化的收益和风险是什么？

答：把权重或部分激活用更低精度表示，减少显存并可能提升吞吐/并发；代价是精度、工具调用格式、长上下文和特定领域任务可能退化。要用目标 Agent Eval 验证，而不是仅看困惑度或跑通模型。

### 4. 推理框架的调度优化如何影响 Agent？

答：Paged KV、连续批处理、并发调度和高效采样能改善首 token、每 token 延迟和吞吐，但不会修复 Agent 的坏 Prompt、重复工具或错误状态。Agent 仍需把模型当有超时、限流和故障的下游，做路由、重试和降级。

### 5. Speculative Decoding 的基本思路是什么？

答：用较小的草稿模型快速生成候选，再由大模型批量验证并接受其中一部分，从而降低有效生成延迟。收益依赖草稿质量、任务分布和实现，不能保证所有 Agent 场景都更快或更便宜。

### 6. SFT、RLHF/RL 和 DPO 分别在训练什么？

答：SFT 用高质量示例学习输入到输出/工具轨迹的模仿；RLHF/RL 根据奖励进行策略优化，能表达偏好或程序结果但训练复杂；DPO 直接用 chosen/rejected 偏好对优化相对倾向，减少显式奖励模型的一部分流程。选择取决于数据、奖励可验证性和稳定性。

### 7. Agent 的端到端延迟应如何拆解？

答：包括网络/排队、模型首 token、生成时间、检索/工具/数据库等待、重试、审批和人工等待；语音还要加 ASR、端点检测和 TTS。分别记录 TTFT、每 token、工具等待和任务完成 P95，才能判断优化点。

### 8. 为什么减少 Agent 轮次和 Context 往往比先优化推理内核更重要？

答：每轮都会重复输入 Context、产生网络往返和工具等待，重复调用还会放大成本和尾延迟；删除无效步骤、压缩输入、并行独立查询和合理路由通常收益更直接。推理内核优化应建立在真实瓶颈和质量不退化的证据上。

## Level 2｜额外推理预算与工具调用

### 9. 可见的 Thinking/Reasoning 摘要为什么不能当成原始思维链或审计证据？

答：Provider 返回的摘要可能是选择性、压缩或加密连续性状态，并不等同于模型内部全部计算，也不能证明事实正确或授权合法。审计应依赖输入版本、工具动作、权限决定、工具结果、验证证据和最终状态。

### 10. 自适应推理和固定推理预算的工程差异是什么？

答：自适应方式由模型根据任务决定是否及如何深入，应用通过等级/模式调节总体投入；固定预算给出更明确的目标上限，兼容性和成本控制直观但可能浪费或不足。两者都必须通过 Provider Adapter 隔离，不能把某一家字段当通用协议。

### 11. 开启额外推理预算会增加哪些成本和尾延迟？

答：通常增加输出侧计算/推理 token、首 token 等待、总耗时和长任务 P95/P99，也可能增加工具规划和重复调用。应分别记录推理 token、文本 token、模型/工具成本、TTFT、总时长和成功率。

### 12. 推理模式下为什么仍然需要 Streaming？

答：额外推理可能让最终文本更晚到达，流式可以保持连接、上报安全的进度状态并改善首响应体验。Streaming 仍不代表任务完成，界面应展示“分析/调用工具”等状态，不应伪装成内部思维逐字输出。

### 13. 工具调用回合中的 thinking 状态或 typed output 为什么必须遵守 Provider 连续性合同？

答：某些协议要求把上一轮模型生成的内容块、签名或 typed items 原样带回，以便服务端验证上下文连续性；删除、重排或自行改写可能导致请求失败或语义断裂。这个规则是 Provider 合同，Adapter 要做兼容测试；执行器仍需独立负责权限、幂等和验证。

### 14. 什么任务值得提高 reasoning/effort，什么任务不值得？

答：多假设诊断、复杂代码分析、算法证明、长链规划和需要整合多次工具结果的任务可能受益；简单分类、字段提取、固定 FAQ 和高吞吐低延迟路径通常不值得。先确认失败原因是推理不足，而不是缺数据、坏工具或错误流程。

### 15. 如何设计额外推理投入的评测实验？

答：固定任务、工具、Context、模型版本和预算环境，对普通/低/中/高投入做多次运行，记录任务成功、关键错误、首 token、总耗时、推理 token、工具调用、成本和分片结果。用质量收益与资源代价制定路由阈值，不以“最高档最好”为前提。

### 16. 为什么高推理预算不能弥补坏工具、缺数据或错误权限？

答：模型再多思考也不能凭空获得不存在的证据、修复返回错误的工具或提升被拒绝的权限。应先修 Context、工具合同、数据质量和策略；推理只处理剩余的决策复杂度。

## Level 3｜模型行为诊断与训练

### 17. Agent 行为由预训练、指令微调、偏好训练和 Harness 如何共同决定？

答：预训练提供语言/代码和世界知识，SFT 教格式与任务示例，偏好或强化训练影响选择、修正和拒绝倾向，Harness 决定工具、Context、权限、反馈和停止条件。线上行为是四者与环境的合成，不能把所有问题都归因于 Prompt 或模型。

### 18. 工具调用训练轨迹应该包含哪些成功和失败样本？

答：包含任务、可用工具、选择与参数、工具结果、成功/失败/超时/权限拒绝、澄清、人工确认、停止原因和程序化成功证据。只收集成功轨迹会让模型学会无条件调用，却不会处理错误、拒绝和不确定性。

### 19. 什么时候先改 Prompt，什么时候改 Tool Schema，什么时候改 Context？

答：协议/格式错误先修消息和 Schema；工具选错先改名称、描述、枚举和工具集合；参数缺字段补 required/服务端校验；信息缺失或噪声大改 Context 选择、检索和状态注入。只有这些层稳定后仍在固定分布中出现模型行为问题，才考虑换模型或训练。

### 20. 结构化输出为什么不能保证工具选择正确或任务完成？

答：结构化输出主要保证可解析的形状，不保证选择了正确工具、参数符合业务语义、没有越权或外部状态真的改变。工具执行器、权限层和程序化验收仍必须独立存在。

### 21. 什么时候值得训练或微调工具调用模型？

答：工具集合和任务分布相对稳定，有大量获授权的高质量成功/失败轨迹，已有 Eval 能证明基线问题来自模型行为，且 Prompt、Schema、Context 和 Workflow 优化不足时才值得。训练要能带来可测量的选择、参数、停止或恢复改善。

### 22. 哪些情况不适合贸然训练？

答：任务还在快速变化、没有可靠标注或程序化验收、失败原因未定位、真正缺的是新工具/新知识、没有安全回归集，或数据授权不清时不适合。训练可能把未解决的系统问题固化成新行为。

### 23. 工具调用训练数据应有哪些安全要求？

答：确认数据用途和授权，脱敏个人信息、密钥、私有代码和危险参数，标注 actor/tenant、工具权限、审批和数据版本，保留拒绝/失败/澄清样本，并隔离训练、验证和攻击集。训练后要做越权、泄露和工具滥用回归。

### 24. SFT、Preference/RL 和程序化奖励各自适合什么监督信号？

答：SFT 适合学习稳定格式、工具选择和停止轨迹；Preference 适合比较规划、解释和安全边界；RL/可验证奖励适合测试通过、Exact Match、状态断言等可程序判断的结果，但要防奖励黑客。优先使用便宜且能定位问题的监督方式。

### 25. 训练后至少要做哪些行为回归？

答：检查该调用是否调用、不该调用是否拒绝、参数合法率、Schema 违反、超时/空结果/5xx 恢复、越权/危险参数、成本/步数、与基座模型对比和训练秘密泄露探针。若成功率升高但空转或拒绝下降，说明训练可能改变了错误的行为分布。

### 26. 为什么 Harness 不能被训练模型替代？

答：训练只能提高在给定观察下的平均决策质量，不能可靠提供权限、预算、幂等、沙箱、审计和外部状态验证。安全边界必须由确定性执行器和策略层强制，即使模型完全不可信也能阻止危险动作。

## Level 4｜场景追问

### 27. 一个 Agent 经常不调用应该调用的工具，你会如何区分 Schema、Context、模型能力和执行层问题？

答：先在固定任务和 Mock 执行器中检查工具是否出现在可用集合、名称/描述/required/schema 和消息协议是否正确；再看 Context 是否给出足够目标和证据；随后比较同一模型/不同模型的选择；最后检查工具是否被策略拒绝或结果未正确回填。只有定位到模型决策且可重复，才考虑训练。

### 28. 微调成功轨迹后模型开始“什么都调用工具”，你会如何修复？

答：补充不需要工具、澄清、拒绝、工具失败和提前停止的负例/正例，重新定义成功监督，检查工具描述和训练集比例，并用“该调/不该调/参数/停止”分桶回归。不要只增加训练步数，否则可能进一步强化无条件调用。

### 29. 一个复杂诊断任务开启高 reasoning 后质量提升但成本翻倍，你会如何制定路由规则？

答：把任务按复杂度、风险和历史失败原因分桶，比较普通/中等/高投入的成功、关键错误、P95、推理 token、工具调用和费用；只对多步推理收益显著的桶提高投入，其余使用低档或固定 Workflow，并保留预算、超时和安全降级。

### 30. 如果 Provider 升级了消息协议和推理字段，你会如何保证工具回合不丢状态？

答：在 Adapter 中分别实现新旧协议映射，保存内部 typed items/ToolCall/ToolResult 和版本，按 Provider 合同原样维护需要连续回传的块或引用；用 Mock、流式断连、多个工具、取消和恢复测试验证。上线前做影子/灰度，Trace 记录协议、模型和错误版本，失败可回滚到兼容组合。
