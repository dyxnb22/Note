# 评测实验、实践路线与项目表达

> 递进路径：先把完整 Agent 任务拆成可验证证据，再建立 Harness、Replay 和发布门禁，最后把实践项目讲成有边界、有数据的项目经历。

> 与基础评测页的关系：基础页保留指标、Trace 和根因分类的通用答案；本页只深化为可运行的 Case/Harness、隔离环境、Replay、CI 门禁和项目表达，不再复制基础定义。

## Level 1｜Agent 专项评测

### 1. 一个 Agent Case 除了输入和答案，还应描述什么？

答：还要描述 workspace/数据环境、允许工具和资源、允许/禁止副作用、任务约束、预期文件/外部状态、程序化成功证据、风险等级和清理方式。这样才能在隔离环境中判断“完成”而不是只比较文本。

### 2. Unit、Mock Provider、Isolated Scenario 和 Replay 各证明什么？

答：Unit 验证确定性逻辑、Schema、预算和状态机；Mock Provider 验证消息配对、Loop 和错误处理；隔离场景验证真实任务、文件/外部状态和副作用；Replay 固定历史输入/工具/环境，用于版本回归。任何一层都不能单独代表完整生产质量。

### 3. 一条可重放的 Agent 记录至少包含什么？

答：至少有 task_id、Agent/模型/Prompt/Tool/Policy 版本、输入/Context hash、工具调用与结果、State 事件、环境或 workspace 快照、输出/成功证据、停止原因、usage、耗时和成本。敏感数据要脱敏或用固定引用，实时外部依赖需替换为 Fixture。

### 4. 为什么程序验证优先于 LLM Judge？

答：文件 diff、测试、数据库状态、权限和是否重复扣款等可以由确定性规则判断，Judge 不能可靠证明这些事实。Judge 适合相关性、完整性和表达等开放式质量，但需要 rubric、人工校准和版本记录。

## Level 2｜Harness 与发布

### 5. 一个最小 Eval Harness 由哪些组件组成？

答：Case 数据集及版本、Runner、Metric/Checker、结果存储、分片报告、Baseline/Candidate 比较和 CI/发布门禁。每条 Case 都要保留失败证据和 reason，不能只输出一个平均分。

### 6. 测试集如何同时覆盖正常、边界、事故和对抗样本？

答：组合 Golden path、空/超长/歧义/无答案、历史事故、Prompt Injection、越权、工具错误、超时、重复请求、审批和恢复 Case，并按语言、租户、任务类型、数据来源和难度切片。生产样本需脱敏，合成样本要人工抽查。

评测集隔离、去重、隐藏集和调参边界统一见[[../../08_评测与可观测/评测与可观测性#13. 如何避免评测集泄漏、重复和过拟合？|基础评测页]]；本页不再重复定义，只讨论 Harness 如何落地。

### 7. Mock Provider 的价值和边界是什么？

答：它用固定响应验证协议、工具结果配对、停止条件、重试、取消和状态恢复，快速且可重复；它不能证明真实模型的工具选择、推理能力、延迟或数据分布效果。真实任务仍需隔离场景和线上抽样。

### 8. 如何设计隔离场景，避免真实副作用污染测试？

答：使用临时 workspace、容器、测试租户和模拟/沙箱外部服务，限制网络、文件、数据库和凭据，运行后检查并清理所有状态。成功条件、禁止动作、Trace、成本和退出原因都要由程序验证，Case 之间不能共享未清理状态。

### 9. Baseline、Candidate 和 Slice 应如何比较？

答：固定任务、模型预算、工具/数据和评分器，只改变一个待测因素；总体比较成功、风险、成本和延迟，按任务类型、长度、风险、租户和语言切片。为高风险 Slice 设置最低门槛/最大退化，不能让平均分掩盖长尾伤害。

### 10. CI 中的 Agent 测试应如何分层？

答：每次提交跑 Unit、Schema、State 和 Mock；每个 PR 跑核心回归、安全、工具/RAG Case；每日或发布前跑完整隔离场景、Judge 和分片报告；线上抽样、漂移监控和失败脱敏回灌。测试数据、Prompt、模型、Tool Schema 和策略版本都要记录。

### 11. Online feedback、Replay 和永久回归集如何形成闭环？

答：从重新提问、人工接管、撤销、投诉和异常 Trace 发现候选失败，脱敏并冻结环境做 Replay，定位根因和修复，随后把该 Case 与安全断言加入永久回归集。线上信号发现问题，不能替代发布前的隔离验证。

### 12. 如何设计一次 Prompt/模型/工具改动的发布门禁？

答：先固定版本矩阵和基线，跑协议/安全/任务 Eval，再做影子和稳定分组灰度；比较质量、长尾、安全、成本、延迟和人工接管，预先写停止/回滚条件。未授权副作用、秘密泄露和审批绕过等安全硬门槛失败时直接阻止发布。

## Level 3｜实践项目与项目表达

### 13. 一个 Agent 项目应该如何从一次调用逐步演进到服务化、图编排、Memory、RAG 和 MCP？

答：先验证 Provider/Adapter 和消息输入输出，再加入 Tool Schema/执行器和有限 Loop；需要外部接口时做服务化，再用显式 State/Node/Edge 表达分支，确有跨轮需求才加 Memory/Checkpoint；知识问题进入 RAG，跨宿主工具复用时再引入 MCP。每一步都应说明新增能力、约束、验证和成本。

### 14. 为什么实践项目中的 Mock Provider、内存 Checkpointer 和关键词检索不能直接当生产方案？

答：它们是为了隔离变量和观察机制，缺少真实 Provider 波动、持久化、并发、权限、数据规模和更新语义。面试时应说明它们验证了什么、未验证什么，以及生产升级需要补的适配、存储、Eval 和安全边界。

### 15. Tool Calling 实践中，`tool_call → execute → tool_result` 的关键合同是什么？

答：模型只提出带 call_id、工具名和参数的调用；宿主按 Schema、权限、超时和幂等执行；结果必须用同一 call_id 回填成功值或结构化错误，下一轮模型再决定继续/结束。工具结果是事实输入，不能让模型直接执行函数或伪造结果。

### 16. LangGraph Tool Agent 的 Planner、ToolNode 和 Final Answer 如何分工？

答：Planner/模型根据 State 提出工具调用或结束，ToolNode 做实际执行并回填结果，Final Answer 汇总已验证观察并满足输出合同。条件边只允许进入显式节点；框架不替代权限、预算、幂等和成功验证。

### 17. MCP Server 中 Tool、Resource、Prompt 的边界是什么？

答：MCP 中 Tool、Resource、Prompt 的完整定义与 Server 组织方式见 [[../../04_Tool与协议/Tool Calling与MCP#20. MCP Server 如何设计？工具、资源和 Prompt 如何组织？|Tool Calling 与 MCP 第 20 题]]。本题作为项目表达检查点只强调边界：Tool 是可执行动作，Resource 是读取型数据，Prompt 是可复用模板；MCP Server 暴露能力，但不拥有宿主的授权、审批、停止与结果验收。

### 18. DevPilot 这类 Coding Agent MVP 为什么先生成建议级 diff？

答：建议级 diff 能先验证 Router、Analyzer、Fixer、Approval、Reviewer、PR Creator 的状态和责任边界，避免模型未经授权直接改文件。后续再加入真实 patch、`apply --check`、测试、回滚和 PR，能把风险逐步引入并评测。

### 19. 如何把一个练习项目讲成“自己解决了什么工程问题”？

答：按“业务问题与约束 → 个人负责范围 → 架构/关键链路 → 最难的工程问题及取舍 → 一个失败与修复 → 指标、测试和失败证据 → 后续边界”表达。不要只报 RAG、Agent、MCP 等组件名或 API；要说明数据如何进入、State 和工具如何推进、权限和风险如何控制，以及结果如何验证。

### 20. RAG 项目面试时应重点准备哪些追问？

答：准备解析/OCR/表格、Chunk 边界、Embedding/关键词/混合检索、Rerank/Query Rewrite、权限过滤、版本删除、Grounding/引用和 Recall/任务成功评测。参数不要凭经验拍定，要能说明对照实验和失败样本。

### 21. Agent 项目面试时应重点准备哪些追问？

答：准备 Loop/Workflow/图、工具 Schema、State/Checkpoint、预算、幂等、人工审批、失败恢复、权限、Trace、Eval 和模型路由。还要能解释为什么某些步骤由代码控制、为什么没有继续拆多 Agent。

### 22. Agent 系统设计题应该如何从业务目标开始回答？

答：先澄清用户、任务成功、数据、延迟、成本、权限、可用性和失败代价；再画入口、Context、模型、工具、状态、策略、观测、验证和人工兜底；最后说明版本、灰度、回滚和降级。模型输出不是执行权限，服务端负责硬边界。

## Level 4｜场景追问

### 23. 设计一个最小的 10 条 Agent Eval 集，你会覆盖哪些 Case 和验证器？

答：至少包含正常完成、直接回答、工具成功、参数错误、工具超时、权限拒绝、Prompt Injection、重复副作用、长 Context/预算耗尽和中断恢复。验证器分别检查最终任务/文件状态、工具选择与参数、禁止访问、Trace/停止原因、成本和清理结果；所有 Case 在隔离环境运行。

### 24. 面试官问“你的 Agent 线上效果怎么样”，在没有完整线上数据时如何准确回答？

答：如实区分已观测、离线测量和估算：说明任务集规模、成功定义、关键指标、样本/环境、限制和未观测项；没有数据就说没有记录，不编造线上百分比。可以进一步说明如何建立 Baseline、Replay、灰度和 SLO。

### 25. 如何把一次失败的实践实验转化成项目亮点，而不是只说“代码跑通了”？

答：描述失败现象和影响，定位到具体层（如工具结果未配对、State 被覆盖、检索召回为空或重复副作用），说明改动、验证和新增回归 Case。失败能体现边界意识和工程闭环，但要明确实验代码与生产级实现的差距。
