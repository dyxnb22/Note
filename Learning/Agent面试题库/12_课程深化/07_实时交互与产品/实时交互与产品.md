# 实时交互、语音 Agent 与产品协同

> 递进路径：先理解语音通道的实时约束，再回答自主性、审批、进度和接管，最后掌握 Tool/Skill/MCP 与渐进式披露。

## Level 1｜语音与实时通道

### 1. 语音 Agent 的端到端链路包括哪些组件？

答：典型链路是音频输入、ASR、端点检测/VAD、打断处理、Agent 理解与工具/策略、文本或事件输出、TTS 和播放。延迟要拆成识别尾延迟、模型首 token、工具往返、合成首包和播放恢复。

### 2. 语音 Agent 与文本 Agent 的核心差异是什么？

答：语音输入是持续且会修正的部分假设，用户可随时打断，输出要短且可听，数字/专名更容易听错；文本可以查看、编辑和回溯。语音还要处理噪声、回声、旁人指令、音频保留和实时取消。

### 3. 为什么 ASR 的中间结果不能直接驱动不可逆工具？

答：中间识别可能在 endpoint 前被修正，同音词、金额和人名错误会直接变成错误副作用。默认等稳定结果或置信度达到阈值；若要边听边查，只能做可撤销的只读操作，并在写操作前确认。

### 4. Barge-in/打断时应该取消哪些对象？

答：应取消 TTS 播放、尚未执行或可安全取消的模型/工具等待，并让取消信号传播到流和 Worker；已经发出的支付、发信或写入不能假设被取消，要查外部状态并依靠幂等/补偿处理。

### 5. 金额、订单号和地址为什么需要复述或屏显确认？

答：语音识别对数字、专名、同音词和噪声敏感，单次识别错误可能造成高风险副作用。应复述关键槽位、要求用户确认，或切到可视界面核对，且把确认绑定到具体资源和操作。

### 6. 语音 session、thread_id 和用户身份应如何关联？

答：语音和文本通道应使用统一的、经过授权的用户/租户身份和任务 thread_id，让状态和记忆可追踪；不能仅用设备或电话号码作为长期授权。切换通道时重新校验身份和 Scope，避免记忆、审批或权限分裂。

### 7. 语音 Agent 的隐私边界有哪些？

答：明确原始音频、转写、摘要和 Trace 的保留期、脱敏、访问者和第三方 ASR/TTS 数据边界；播放和日志不应泄露不必要的敏感字段。调试时优先记录摘要、hash 和错误，而不是默认保存完整录音。

### 8. 语音场景如何设计进度播报和长任务异步化？

答：用短而诚实的状态语告知“正在查询/需要确认”，不要朗读内部推理；长任务先口头确认范围，返回任务 ID 或可听进度，后台执行完成后回调。工具等待不能让通话无限静默，且用户可取消或转人工。

### 9. 什么任务不适合使用语音 Agent？

答：长表格、精确代码编辑、需要完整可检索书面证据、对数字极敏感或必须高可视确认的任务不适合纯语音。可以保留文本/可视主通道，让语音做唤醒、摘要或导航。

### 10. 语音 Agent 应评测哪些指标和环境切片？

答：看端到端和打断恢复延迟、关键槽位准确率、误触发工具率、重复副作用率、任务成功和转人工，并按噪声、口音、设备、网络和语言切片。不能只看 ASR 字错率或平均响应时间。

## Level 2｜产品自主性与人机协同

### 11. 一个 Agent 任务规格至少应包含哪些字段？

答：包括用户/触发器、输入、目标、允许资源和工具、禁止副作用、成功证据、失败成本、澄清条件、审批点、截止时间和停止/接管方式。任务规格把模糊目标转成产品和执行器都能遵守的边界。

### 12. Agent 自主性可以如何分级？

答：可从仅给建议、每次执行前确认、范围内自动执行到后台自治运行分级。级别应按风险、可逆性、资源范围和用户信任设置，不是为了展示能力而默认最高自治。

### 13. 什么情况下应该澄清，什么情况下应该请求审批？

答：当目标、资源、关键参数或成功标准缺失，且不同答案会改变任务时澄清；当动作不可逆、高风险、超出预授权范围或影响第三方时审批。低风险且范围明确的选择可由 Agent 自动做，并记录依据。

### 14. 产品进度事件应该展示什么，为什么不能展示模型内部思维？

答：展示稳定的阶段、工具状态、等待原因、预计下一步和可取消/接管入口，如“正在查询订单”。内部推理摘要不等于完整思维或事实证据，展示它可能误导用户、泄露敏感信息，也不应成为审计依据。

### 15. Agent 失败时，用户界面应说明哪些信息？

答：说明已完成什么、未完成什么、是否发生外部副作用、失败/等待原因、可验证证据、用户可选的重试/修改/取消/接管方式。避免只显示“出错了”，也不要编造一个已经完成的结果。

### 16. 人工接管和恢复入口如何设计？

答：保留任务状态、上下文摘要、工具结果、审批和待处理动作，给人工一个可审查的操作预览与权限范围；人工修改后重新验证 State 和策略，恢复从明确节点继续。接管不是把全部后台权限交给用户，而是缩小范围并保留审计。

### 17. Agent 产品应关注哪些质量、效率和安全指标？

答：任务成功/首轮成功、人工接管和恢复、澄清接受率、审批拒绝/撤销、P95 完成时间、成本、重复操作、未授权调用和安全事件都应关注。指标按任务类型、风险和用户群体分片，不能用响应速度替代任务价值。

## Level 3｜Tool、Skill 与渐进式披露

### 18. Tool、Skill 和 MCP Server 的边界是什么？

答：Tool 是一个可执行原子动作；Skill 是一组按场景加载的能力说明、流程、约束和示例；MCP Server 是跨宿主暴露 Tool/Resource/Prompt 的协议服务。Skill 可以组织和指导 Tool，但不等同于执行权限或自主 Agent。

### 19. 什么是渐进式披露？为什么一次把所有能力塞进 Context 会有问题？

答：先向模型提供能力名称和适用场景，再按需要加载摘要/步骤，真正执行时才加载完整 Schema、示例和脚本。全部展开会消耗 Context、增加工具选择混淆、扩大注入面和成本，还会让无关知识干扰判断。

### 20. 一个 Skill 应该包含哪些内容？

答：应包含用途与不适用场景、触发条件、步骤、依赖/权限、输入输出、错误和退出条件、示例与必要脚本。Skill 应是可执行的能力包，不是把整套百科复制到 Prompt。

### 21. Skill 可以调用 MCP 吗？Skill 是否等于权限？

答：Skill 可以把 MCP Server 当作后端能力，但真正的 Tool 调用仍由宿主/网关执行并经过身份、资源、参数、预算和审批。Skill 只描述“如何使用”，不能自行授予权限，也不能绕过服务端策略。

### 22. “能力、知识、Context”三者分别回答什么问题？

答：能力回答“能做什么”，知识回答“需要知道什么”，Context 回答“当前发生了什么”。设计时要把三者分开，按任务动态加载能力和知识，同时保护 Context 的清晰、最小化和权限边界。

### 23. 为什么 Agent 应从 3–5 个核心能力开始逐步增加复杂度？

答：少量能力更容易让模型选择、执行器校验、评测和用户理解；只有固定失败证据表明缺能力时才增加。工具数量增加会扩大 schema、权限、成本、攻击面和调试空间，不是能力越多越好。

### 24. 如何设计一个既能自主执行又不会失控的产品工作流？

答：让 Agent 在明确的任务 State、工具白名单、预算、成功证据和停止条件内选择下一步；高风险动作预览/审批，进度对用户透明，失败可恢复/接管，后台用 Trace 和 Eval 监控。自主性只存在于被验证的能力空间中。

## Level 4｜场景追问

### 25. 设计一个电话客服 Agent，如何处理低置信识别、用户打断、退款审批和后台异步任务？

答：低置信时复述关键槽位并澄清，稳定前只做只读查询；用户打断取消播放和未开始的安全操作，已发副作用做状态核对；退款先展示金额/订单/规则并按风险审批；长任务返回短进度和任务状态，完成后回调或转人工。全程使用统一身份、幂等和审计。

### 26. 一个 Agent 总在不必要时追问用户，你会如何调整任务合同和澄清策略？

答：分析 Trace 区分真正缺少关键信息、工具可自行查询和模型过度谨慎；在任务合同中明确默认值、可自动判断的低风险范围和只有会改变目标才澄清的条件。用分桶 Eval 监测澄清率、接受率、错误副作用和任务成功，不用简单压低追问次数。

## Level 5｜事件驱动 UI 与任务状态

### 29. 为什么 UI 应通过事件和 Presenter 渲染，而不是直接调用业务对象？

答：UI 负责接收用户意图和展示状态，业务层负责权限、执行和状态转移。通过事件流和 Presenter 隔离后，CLI、TUI 和 Replay 可以共享同一套状态投影，权限不会因为新增一个按钮而出现第二份实现。

### 30. 什么是纯 Reducer？它为什么适合 Agent UI？

答：纯 Reducer 接收旧状态和一个事件，返回新状态，不直接做 I/O、调用模型或操作 Widget。这样可以离线测试状态转移、错误和恶意文本，也能用历史事件重建界面；真实 UI 只负责把状态渲染出来。

### 31. UI 中的模型文本和仓库文本为什么也要视为不可信输入？

答：文本可能包含 ANSI 控制序列、伪造提示、超长内容或恶意 Unicode。渲染前应清理控制字符、限制长度和行数，并区分显示文本与可执行命令；UI 防显示注入，不能替代工具权限和沙箱。

### 32. 流式 UI 如何处理瞬态事件和权威事件？

答：Token 增量、进度和调试输出是瞬态信息，过载时可以合并或丢弃；状态转移、审批请求、错误、Checkpoint 和完成事件是权威信息，必须持久化或施加背压。队列关闭和取消时仍要写出最终停止状态。

### 33. TUI 的取消为什么不能只关闭窗口？

答：关闭窗口只改变界面，不一定停止模型请求、工具进程或数据库任务。取消应沿运行时、Provider、子进程和队列传播，在安全点保存状态并记录命名停止原因；如果副作用状态未知，还要进入恢复流程。

### 34. 如何测试事件驱动的 Agent UI？

答：直接构造事件序列调用 Presenter/Reducer，测试审批、失败、取消、超长文本、控制字符和重复事件；再用少量端到端测试验证 Widget 接线。Replay 与实时运行应使用同一事件投影，避免只测屏幕截图而漏掉状态语义。

### 27. 工具数量从 5 个增长到 100 个后，你会如何用 Skill/路由/渐进式披露保持工具选择质量？

答：先用任务类型/权限做候选路由，只把少量相关 Skill/能力摘要给模型；进入某 Skill 后再加载必要工具 Schema，执行前仍由服务端做 allowlist 和授权。记录候选集合、选择准确率、无效/重复调用和长尾失败，按证据调整路由。

### 28. 如何设计一个既支持自动执行又支持人工接管的研究助手产品？

答：把研究任务拆成检索、阅读、提取、分析、引用和发布，允许 Agent 自动做低风险只读步骤；涉及外发、修改或不确定结论时生成证据包并审批。用户能查看来源、进度、未完成项和成本，接管后沿 Checkpoint 继续，最终回答必须通过引用/事实验证。
