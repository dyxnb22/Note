# Durable Execution 与生产运维

> 递进路径：先掌握长任务的状态、幂等与恢复，再讲部署对象、预算、灰度和降级，最后回答事故处置。

## Level 1｜长任务可靠性基础

### 1. Agent 长任务为什么需要显式任务状态机？

答：长任务会跨请求、进程、Worker 和人工等待，不能靠内存中的一个循环变量表示进度。状态机把当前阶段、允许转移、失败语义和恢复入口固定下来，便于重试、审计、指标和人工接管。

### 2. `pending`、`running`、`waiting_approval`、`succeeded`、`failed`、`cancelled` 和 `expired` 应如何区分？

答：`pending` 尚未领取，`running` 正在执行，`waiting_approval` 等待人或策略决定；`succeeded` 有成功证据，`failed` 是不可继续或超过策略的失败，`cancelled` 是主动取消，`expired` 是超过有效期。状态转移要记录事件、操作者、版本和原因。

### 3. Agent 系统为什么通常只能以至少一次执行为现实基线？

答：网络重试、Worker 崩溃和消息重复投递都可能让同一动作被再次尝试；跨模型、队列和外部 API 很难提供端到端 exactly-once。工程上应把“至少一次调度 + 业务幂等/对账”作为基线，而不是假设消息系统能替所有副作用去重。

### 4. 幂等键应该由哪些信息组成？

答：应绑定任务/业务主体、逻辑操作、规范化参数和必要的版本或尝试语义，例如 `task_id + operation + resource + args_hash`。服务端保存键、参数摘要、状态和结果；相同键不同参数应拒绝，避免把错误请求误合并。

### 5. Checkpoint 和 Journal 分别解决什么问题？

答：Checkpoint 保存从哪里继续所需的最小快照，如节点、状态摘要、预算和待审批动作；Journal 保存有序事件和操作结果，用于审计、诊断和必要时重放。Checkpoint 便于恢复，Journal 便于解释，两者不能互相完全替代。

### 6. Queue、Lease 和 Heartbeat 如何配合？

答：Queue 保存待处理任务，Worker 领取时获得有时限的 Lease，Heartbeat 证明仍在运行；租约过期后任务可被其他 Worker 接管。领取、续租和完成要有版本/CAS 或唯一约束，避免两个 Worker 同时认为自己拥有任务。

### 7. 重试、超时和取消在语义上有什么区别？

答：重试是对可恢复错误再次尝试，超时是超过等待上限的运行结果，取消是用户或系统主动要求停止。它们都要向工具和下游传播，但已发出的副作用不能靠取消撤销，必须查询状态、幂等或补偿。

### 8. Outbox 能解决什么一致性问题，不能解决什么问题？

答：Outbox 可在同一数据库事务中把任务状态变化和待发布事件一起写入，避免“状态成功但事件丢失”。它不能让外部支付、发信或第三方 API 与本地事务自动原子化，外部动作仍需幂等、对账和补偿。

### 9. 长任务恢复前为什么必须核对外部副作用？

答：Checkpoint 可能写在外部调用之前或之后，崩溃时本地状态与真实世界可能不一致。恢复先查询订单、文件、消息或其他资源的实际状态，再决定跳过、继续、补偿或转人工，不能仅凭“最后一个节点未完成”重做动作。

### 10. 任务状态、会话记忆和长期 Memory 为什么不能混为一谈？

答：任务状态描述当前工作流进度和事实，会话记忆服务于当前线程，长期 Memory 是跨请求可检索且有来源/策略的用户或业务信息。三者的生命周期、权限、删除和恢复语义不同，混存容易把临时事实写成长期记忆或让恢复污染新任务。

## Level 2｜生产运行机制

### 11. Worker 崩溃后如何从 Checkpoint 恢复一个任务？

答：新 Worker 先取得合法 Lease，读取带版本的 Checkpoint，验证任务、代码/图、工具和策略版本，再检查未完成操作的外部状态。确认可安全继续后从节点边界恢复，写入新的状态/事件；不兼容或未知副作用进入人工处理。

### 12. 如何处理“外部请求已经成功，但 Agent 没收到响应”的未知结果？

答：把结果标记为 unknown，不直接重试；用幂等键或查询接口核对外部状态，已成功则补写本地记录，未成功且可安全重试才重试，无法确定就人工对账。用户界面要明确说明部分完成和当前状态。

### 13. 如何设计多租户任务的并发、资源和状态隔离？

答：所有任务、队列、Checkpoint、缓存、向量、工作区和 Trace 都带 tenant/actor Scope，查询和执行前做服务端过滤；按租户设置并发、费用和文件/网络配额。隔离不能只靠 Prompt 或租户字段展示，底层存储和 Worker 也要执行授权。

### 14. 什么时候应该重试，什么时候应该进入 DLQ 或人工处理？

答：只对明确的暂时性、幂等且未超过总预算的错误做限次退避；权限拒绝、参数错误、业务规则失败和未知副作用不应盲目重试。达到次数/时间上限或无法自动恢复时写入 DLQ，保留上下文和证据供人工处理。

### 15. Agent 服务为什么需要内部队列和背压？

答：一个用户请求可能 fan-out 多次模型、检索和工具调用，入口 QPS 不能代表真实负载。队列和背压限制每个租户、模型、工具和 Worker 的并发，在过载时选择拒绝、延后、降级或转人工，而不是无限堆积导致尾延迟和成本失控。

### 16. Worker 优雅关闭时应完成哪些动作？

答：停止领取新任务，向运行中的节点发送取消或在安全点停下，在 Lease 到期前保存 Checkpoint/释放租约，关闭流式连接并写明终止原因，最后确认外部副作用状态。这样新 Worker 接管时不会重复执行或丢失进度。

### 17. Agent 的 SLI/SLO 不应只监控哪些 HTTP 指标？

答：还要监控任务创建/继续/取消成功率、任务成功、人工接管、越权和秘密泄露、TTFT/任务 P95、工具超时、重试、stuck loop、恢复成功率和每任务成本。代码 Agent、知识问答和批处理的目标应按任务类型分开。

### 18. Agent 的一次生产发布对象为什么不只是代码？

答：模型、Prompt、Few-shot、工具 Schema/执行器、策略、RAG 索引/Embedding、Workflow 图、State Schema、配置和 Eval 门槛都会改变行为。必须记录组合版本，否则只回溯 Git SHA 也无法解释线上结果。

### 19. Prompt、模型、工具、策略、索引和 State Schema 应如何版本化？

答：每类对象有不可变版本，Trace 记录本次运行使用的组合；State Schema 提供迁移器或兼容范围，工具和策略变更要重新跑安全/协议回归。发布和回滚以版本矩阵为单位，而不是把所有变化隐含在配置文件里。

### 20. 稳定分组的灰度和回滚为什么重要？

答：稳定地把同一用户/租户分到同一版本，才能比较质量、成本、延迟和安全变化，避免同一用户在两版之间来回跳。回滚还要处理正在运行的任务：兼容的继续，不兼容的暂停、迁移或人工接管。

### 21. 预算、限流和背压应该在哪些层同时控制？

答：入口控制请求速率，任务层控制步数、Token、费用和墙钟时间，模型/Embedding/工具层控制并发，队列层控制等待长度，执行层控制单次命令/网络资源。只在入口限流无法阻止内部调用放大。

### 22. Agent 生产环境应准备哪些降级档位？

答：可按风险从完整 Agent 降到低成本模型、只读 Agent、固定 Workflow、仅生成建议不执行工具、静态帮助或人工处理。每档必须明确允许的工具、数据、审计、提示和恢复方式，Fallback 不能绕过原有权限。

## Level 3｜运维与事故响应

### 23. 如何为 Agent 设计可执行的告警，而不是只有监控曲线？

答：每个告警绑定范围、证据和动作，例如 Provider 错误升高切换/降级，stuck loop 增多降低预算并冻结版本，越权尝试立即冻结高风险工具。告警必须带 task、tenant、版本和关联 ID，并有负责人和 Runbook。

### 24. P0、P1、P2 事故可以如何划分？

答：P0 是数据外泄、未授权写入、批量破坏或权限绕过；P1 是大面积失败、成本失控、关键租户不可用或无法恢复；P2 是局部质量、延迟或工具退化。分级依据是影响和风险，不是单纯错误数量。

### 25. Agent 事故响应的标准流程是什么？

答：发现后定级，先用 Kill Switch、撤权或冻结遏制，再保全 Trace、审计和工作区快照，判断影响范围，修复或回滚，分阶段恢复并验证，最后复盘和新增回归 Case。复盘要定位到可修复的 Context、模型、工具、策略、数据或运维层。

### 26. Kill Switch 应该控制什么，为什么不能只写在文档里？

答：它可以禁止写工具、网络出口、特定 MCP、后台队列或降低预算，也可以强制人工审批。开关必须独立于模型 Prompt，有明确操作者权限、审计、传播时延、已有任务处置和恢复演练，否则事故时不可靠。

### 27. 新版本发布时，如何处理仍在运行的旧任务？

答：先停止旧版本接收新任务，按 State/Tool/Policy Schema 判断哪些任务可由旧版完成、哪些可迁移；兼容任务继续或安全迁移，不兼容任务暂停并保留 Checkpoint。不能让旧状态在新图中静默解释成不同动作。

### 28. 如何防止成本、延迟和 stuck loop 在内部 fan-out 下失控？

答：在任务级维护步数、Token、费用、并发和重复意图预算，在模型/工具级设置配额，在 Loop 中检测相同动作和无进展，在队列过载时背压或降级。Trace 记录每次预算消耗与停止原因，不能只统计一次外部请求。

### 29. State Schema 或策略前向迁移后，为什么不能只回滚应用代码？

答：旧代码可能无法读取新字段或已经写入的新语义，策略/索引/工具版本也可能与旧代码不兼容。回滚必须覆盖相关对象或提供向后兼容迁移；已发生的外部副作用还需要对账，不能只恢复进程镜像。

### 30. 如何设计一个能跨进程、跨机器、跨版本恢复的 Agent 任务系统？

答：持久化任务 FSM、Checkpoint 和 Journal，队列通过 Lease/Heartbeat 分配，所有副作用使用幂等键并保留结果；运行记录包含代码、模型、Prompt、Tool、Policy 和 State 版本。恢复时做版本兼容、外部对账和预算重算，不满足条件就转人工。

## Level 4｜场景追问

### 31. 一个支付类 Agent 在调用下游后超时，你会如何决定重试、对账或人工介入？

答：先把结果标为未知并用同一幂等键查询支付状态；若已支付则补写本地状态，若明确未支付且操作可安全重试才按预算重试，若查询失败或金额/账户不一致就冻结后续动作并人工对账。不能因为 HTTP 超时就再次扣款。

### 32. 新模型灰度后任务成功率上升，但高风险工具拒绝率下降，你会如何处置？

答：安全指标是硬门槛，先暂停扩大并冻结高风险工具或回滚相关版本，抽取 Trace 确认是模型、工具描述还是策略组合导致；修复后用安全回归和分片 Eval 验证。平均成功率提升不能抵消授权边界退化。

### 33. 线上出现大量任务卡在 `running`，你会从 Queue、Lease、Checkpoint 和外部依赖哪几层排查？

答：先看 Trace/任务事件判断最后是领取、模型等待、工具等待还是状态提交，再检查 Lease 是否过期、Heartbeat 是否停止、Checkpoint 是否成功写入和下游是否普遍超时。确认没有未知副作用后再批量重置/接管，避免盲目重放。

### 34. 设计一个从完整 Agent 降级到只读、固定 Workflow 和人工处理的运行方案。

答：用独立策略配置和 Kill Switch 控制档位：完整档允许经过授权的读写工具；只读档撤销写权限；固定 Workflow 只执行白名单路径；人工档只生成建议和证据。每次切换写审计、提示用户当前能力，并定义已有任务是继续、暂停还是转人工。
