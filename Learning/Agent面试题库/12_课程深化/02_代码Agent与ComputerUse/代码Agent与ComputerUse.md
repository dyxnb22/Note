# 代码 Agent 与 Computer Use

> 递进路径：先讲代码库导航和可审查修改，再讲验证、Git/Worktree 与失败恢复，最后比较 API、DOM 自动化和视觉操作。

## Level 1｜代码 Agent 基础

1. 一个代码 Agent 的最小工具集应该有哪些？
2. 代码 Agent 为什么要先定位代码，而不是直接生成代码？
3. 文本搜索、符号搜索、AST 和 LSP 分别适合什么问题？
4. 代码库地图有什么用？为什么不能把它当成事实来源？
5. 代码 Agent 的 Context 应该选择哪些内容？
6. 为什么代码中的精确名称和类型关系通常不能只用向量检索替代？
7. 直接覆盖、唯一替换和 Unified Diff 各有什么风险？
8. 模型提出 patch 和 patch 被应用之间为什么必须有边界？

## Level 2｜修改与验证闭环

9. 应用代码 patch 前至少检查什么？
10. 代码 Agent 写完后应按什么顺序验证？
11. 工具执行结果应包含哪些字段，才能支持后续调试？
12. 如何区分任务开始前已有的 diff 和 Agent 新产生的 diff？
13. Git Worktree 对并行 Coding Agent 解决了什么问题？没有解决什么问题？
14. 如何防止 Agent 因为测试失败进入重复修复循环？
15. 如何用覆盖率、变更过滤和定向测试判断修改有效？
16. 代码 Agent 如何处理用户已有的未提交修改？
17. 为什么“生成了代码”不等于“任务完成”？

## Level 3｜Computer Use 机制与边界

18. Computer Use 与普通 Tool Calling 的执行循环有什么不同？
19. GUI Agent 的原子动作合同至少应包含什么？
20. 为什么动作发送成功不等于界面状态已经成功？
21. API、Playwright/Selenium 和 Computer Use 应如何选择？
22. Computer Use 为什么应该运行在隔离的容器或虚拟机中？
23. GUI Agent 的成本和延迟应该如何拆解？
24. GUI 场景中的高风险动作如何做审批和二次验证？
25. GUI Agent 的评测集应该覆盖哪些异常？

## Level 4｜场景追问

26. 设计一个能够修复代码并提交建议级 diff 的 Coding Agent，如何划分观察、修改、验证和审批边界？
27. 一个 patch 应用失败且仓库同时有用户修改，你会如何恢复？
28. 如果一个网页自动化任务既有稳定 DOM 又需要视觉判断，你会如何组合 API、DOM 和 GUI？
29. 如果 GUI Agent 重复点击导致重复提交，你会如何从动作、状态和外部副作用三层修复？
