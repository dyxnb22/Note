# Provider 适配与框架选型

> 递进路径：先分清 Provider、应用和 Runtime 的边界，再理解流式/结构化输出与图编排，最后回答框架选型和兼容性问题。

## Level 1｜Provider 与应用边界

### 1. 为什么 Agent 应该在 Provider SDK 外面增加 Adapter 层？

答：不同 Provider 的消息形状、工具调用字段、流式事件、错误和 usage 定义不同。Adapter 把外部协议翻译成内部稳定合同，Runtime 只依赖内部类型，换模型时只改适配层并重新跑兼容测试。

### 2. 一个内部统一的 `ModelResult` 至少应该包含哪些字段？

答：至少包括文本、规范化的工具调用、usage、request_id、finish_reason 和结构化错误状态；必要时还要带 provider/model 版本和原始响应引用。原始 payload 作为受控调试附件，不能成为业务状态的唯一格式。

### 3. `messages`、Context、State 和调用元数据分别解决什么问题？

答：`messages` 是发给模型的对话或内容序列；Context 是本轮实际装配的输入；State 是跨节点/跨恢复保存的任务事实；元数据是 request_id、token、耗时和版本等观测信息。它们不能混成一个大对象，否则会把审计信息、模型输入和可恢复状态互相污染。

### 4. 为什么不能把某一家 Provider 的响应字段直接传到 Agent Runtime？

答：这样会把厂商的 stop reason、content block 和工具参数语义泄漏到编排层，导致换 Provider、重放和测试都困难。更严重的是，Provider 的“已生成工具调用”可能被误当成“工具已执行”，破坏执行边界。

### 5. Streaming 只解决了什么问题？它没有解决什么问题？

答：Streaming 主要降低首字节等待并让客户端看到进度；它不保证任务成功、工具执行完成、结果持久化或副作用可取消。最终结果仍要汇总、验证和保存，断连时还要能从任务状态恢复。

### 6. JSON mode、结构化输出和业务语义校验之间是什么关系？

答：前两者主要约束输出形状，例如字段、类型和必填项；它们不能证明值符合业务规则、权限范围或真实外部状态。服务端仍需做 schema 解析、业务校验、授权和程序化成功验证。

### 7. 为什么要记录 `request_id`、usage 和稳定的错误码？

答：`request_id` 用于跨 Provider 和日志定位，usage 用于成本与预算，稳定错误码用于重试、降级、告警和评测。只有保存这些元数据，才能区分模型失败、限流、超时、格式错误和未知结果。

### 8. 多模态输入接入时，Adapter 和业务层分别负责什么？

答：Adapter 负责把图片、音频、文件等外部载荷转换为 Provider 所需的内容块，并统一大小、格式和错误；业务层负责判断是否允许使用、数据分类、权限、保留和结果验证。不能因为模型能“看懂”就跳过敏感数据治理。

## Level 2｜运行机制与框架抽象

### 9. Provider 的 typed content block 如何归一化为内部 `ToolCall` 和 `ToolResult`？

答：先按 Provider 合同解析内容块，提取稳定的 call_id、工具名和参数，再验证 JSON 与业务 Schema，生成内部 `ToolCall`。工具执行完成后用同一个 call_id 绑定成功值或结构化错误，形成 `ToolResult`；解析和执行必须是两个阶段。

### 10. `tool_call`、工具执行结果和最终文本在一次请求中的职责有什么不同？

答：`tool_call` 是模型提出的动作提案，不能当作已发生事实；工具结果是宿主经过授权和执行得到的事实；最终文本是模型基于事实生成的表达。真正的副作用只应发生在执行器，并由外部状态或验证器确认。

### 11. 流式调用遇到断连、取消和重复事件时，系统如何保证结果一致？

答：事件要有序号或事件 ID，消费端做去重，最终结果采用一次提交或可恢复的聚合状态；取消要同时通知 Provider、工具和 Worker。断连时不能依据半截文本判定成功，应从 Checkpoint/任务状态读取最终状态，未知副作用先对账再决定是否重试。

### 12. 轻量 `while` Loop、显式 Workflow 和图编排分别适合什么场景？

答：固定几步、少量工具和短生命周期任务用普通函数或 Loop 足够；存在明确分支、循环、并行、审批和恢复时用 Workflow/图；复杂框架只有在状态、观测和运维收益能抵消抽象成本时才引入。选型从任务不变量出发，不从框架流行度出发。

### 13. 低代码 Agent 平台的价值和边界是什么？

答：低代码适合快速验证连接器、提示词和流程，能降低初始开发成本；但细粒度权限、复杂状态迁移、幂等、性能、测试和供应链控制通常需要代码补齐。生产上可以混合使用，把平台当编排入口，把关键执行和策略放在可测试的服务中。

### 14. 如何把 LangGraph 的 State、Node、Edge、Checkpoint 映射到通用 Agent Runtime？

答：State 是结构化任务事实，Node 是一次确定边界的处理，Edge 是路由规则，Checkpoint 是可恢复快照，Graph 是状态转移图。这个映射与具体框架无关，换框架时仍应先保留这些语义。

### 15. 为什么生产环境不能只用内存 Checkpointer？

答：进程重启、扩容或 Worker 崩溃会丢失状态，用户也无法跨进程恢复。生产 Checkpoint 至少要持久化任务节点、关键状态、版本、审批和未完成操作，并处理并发写、Schema 迁移和敏感字段保护。

### 16. 图中的条件边应该如何设计，才能避免模型输出直接成为任意跳转？

答：模型只输出受限的意图或候选动作，路由器把它解析成枚举并按当前 State、权限和前置条件映射到 allowlist 节点。未知值、低置信度和不满足前置条件必须进入兜底或人工分支，不能把任意字符串当节点名执行。

### 17. `interrupt/resume` 怎样实现人工审批，而且恢复时不会绕过策略？

答：中断时保存待审批动作的完整参数、资源、证据、策略版本、有效期和 State 版本；恢复时重新读取外部状态并重新授权，确认参数没有变化后才执行。审批不是永久通行证，过期、撤回或参数变化都应重新审批。

### 18. LangGraph 中共享 State、Reducer、子图和并行 Send 分别解决什么问题？

答：共享 State 传递任务事实，Reducer 定义多个节点写同一字段时如何合并，子图隔离局部流程，Send 把多个独立输入分发给并行节点。并行并不自动解决冲突、取消、限流和部分失败，仍需显式定义合并与恢复语义。

## Level 3｜选型与兼容性设计

### 19. 如何判断现有项目是否真的需要引入 Agent Framework？

答：先画出当前 Loop 的状态、分支、恢复、工具和观测需求；如果普通代码可以清楚表达且没有持久化/并行/人工中断需求，就不必引入框架。只有当显式图、Checkpoint、流式事件或团队协作能明显降低复杂度时才升级。

### 20. 选择框架时如何权衡控制力、开发速度和运维成本？

答：比较状态表达能力、Provider/工具生态、测试与回放、持久化/恢复、可观测性、部署方式和升级风险。用一个真实任务做基准，而不是只看 Demo 代码长度；高控制力通常伴随更多状态和运维成本。

### 21. 如何设计 Provider 替换，使业务代码不依赖某个模型厂商？

答：定义内部请求/结果、工具调用、流式事件、错误码和能力声明，Provider Adapter 负责翻译，业务只依赖这些类型。对不具备的能力要显式返回 unsupported，而不是静默模拟；替换前用同一组协议、工具和 Eval 回归。

### 22. 模型、工具 Schema、Prompt 和 State Schema 升级时，兼容性应如何管理？

答：每个对象单独版本化，并记录组合版本；State 需要迁移器或明确只允许兼容版本恢复，Tool Schema 变更要校验旧任务和审批动作。发布与回滚不能只切 Git SHA，还要处理正在运行的任务和已写入的 Checkpoint。

### 23. Adapter 层应该测试哪些异常和边界？

答：至少覆盖空响应、未知 stop reason、无效 JSON、多个工具调用、工具结果配对、流式断连/重复、超时、限流、取消、usage 缺失和 Provider 错误映射。测试应同时检查内部结果、错误码、资源释放和 Trace 元数据。

### 24. 为什么“框架节点数量”不能直接等同于“多 Agent 数量”？

答：图节点可能只是确定性的解析、校验或工具执行步骤；Agent 的判断标准是是否有独立的模型决策边界、任务合同和权限/上下文隔离。把每个节点都称为 Agent 会夸大复杂度，也会掩盖真正的状态和通信成本。

## Level 4｜场景追问

### 25. 设计一个支持多 Provider、工具调用、流式输出和人工审批的 Agent Runtime，你会如何分层？

答：入口层负责身份和任务合同；Adapter 层统一请求、结果、流式事件和错误；Runtime 管 Loop/Graph、State、预算和恢复；Tool Gateway 负责 Schema、授权、幂等和执行；Approval、Checkpoint、Trace 和 Eval 作为横切能力。模型只提出候选动作，执行器和策略层决定能否发生。

### 26. 一个简单问答项目逐渐加入循环、持久化、并行和恢复，你会在哪些信号出现后从 Loop 升级到图编排？

答：当分支和循环开始难以用有限条件表达、需要暂停/恢复或并行聚合、多个团队要维护节点、或者需要逐节点 Trace 和回放时升级。升级前应先固化 State 和成功条件，不能只把旧代码机械搬进框架。

### 27. 如果切换 Provider 后工具调用频繁失败，你会从协议、Adapter、Prompt 还是模型能力哪一层开始定位？

答：先用固定请求和 Mock/协议测试确认请求字段、工具 Schema、消息配对和 Adapter 归一化，再检查 Provider 是否支持该能力；之后看 Prompt/工具描述，最后才判断模型选择能力。用 Trace 对比旧新版本的 stop reason、参数和错误码，避免直接归因于模型。

### 28. 如果一个图编排系统上线后出现状态覆盖和恢复错乱，你会如何排查并改造？

答：先按 trace/task 找到并发写入、Reducer、Checkpoint 版本和恢复节点，确认是否存在共享字段覆盖、旧 Schema 静默解释或重复提交。改造为明确的 State ownership、版本/CAS、事件顺序和迁移器，并为并发、恢复、部分失败和审批重放增加固定测试。
