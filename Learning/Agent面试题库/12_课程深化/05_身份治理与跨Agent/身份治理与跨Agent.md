# 身份治理、多 Agent 与跨 Agent 协议

> 递进路径：先区分身份、权限和数据治理，再讲能力授权与委托合同，最后判断多 Agent/A2A 是否真的有必要。

## Level 1｜身份与数据治理

### 1. Agent 系统中 Actor、Agent、Service 和 Resource 分别是什么？

答：Actor 是发起或代表操作的主体，可以是用户、管理员或另一个 Agent；Agent 是执行任务的逻辑主体；Service 是承载能力的程序；Resource 是被读取或改变的业务对象。授权要说明“谁以谁的身份对哪个资源做什么”，不能只看调用来源服务。

### 2. 一个授权判断至少应包含哪些维度？

答：至少包含 actor/agent 身份、tenant、resource、operation、当前任务/上下文、策略版本和审批状态，必要时还要有时间、数据分类、目的和风险等级。模型提出的动作不能自带授权结论，服务端必须重新计算。

### 3. 为什么数据分类不能只分“公开/私密”两类？

答：公开、内部、机密、受限数据的访问主体、用途、保留、脱敏和模型传输边界不同；粗粒度分类无法表达支付、凭据、个人信息和专有代码的不同风险。分类应进入检索、工具、日志、缓存和 Provider 路由策略。

### 4. 数据最小化在 Agent 系统里如何落地？

答：只向当前任务提供完成目标所需的字段、时间范围、文档片段和工具能力，按用途限制读写，并在 Context、日志和训练数据中删除无关敏感信息。最小化不是只在 Prompt 中说“不要泄露”，而是从查询、权限和数据返回层减少暴露。

### 5. Secret 的生命周期应如何管理？

答：密钥从秘密系统受控注入，限定作用域和有效期，使用时避免进入模型 Context、普通日志和 Trace，轮换/撤销后使旧凭证失效。工具和 Provider 适配层应提供最小权限，错误输出也要做脱敏。

### 6. 多租户隔离为什么要覆盖数据库、向量库、缓存、工作区、队列和 Trace？

答：任何一层遗漏都可能通过搜索、缓存命中、文件路径、任务重放或日志访问泄露数据。隔离要由底层查询过滤、资源命名/分区、Worker Scope 和访问审计共同实现，不能只在界面上显示 tenant_id。

### 7. 数据删除请求为什么不能只删除主数据库中的记录？

答：内容可能复制到倒排/向量/图索引、缓存、摘要、Checkpoint、Trace、回放集、备份和训练派生物。删除流程应追踪所有派生存储并验证不可访问；法定保留的审计也要最小化、脱敏和限制访问。

## Level 2｜能力授权与委托

### 8. 面向 Agent 的能力授权凭证应绑定哪些条件？

答：应绑定 actor、能力、资源范围、操作类型、参数/操作 hash、租户、策略版本、过期时间和必要的单次使用标记。这样即使凭证被复用，也不能把一个已审批的“给资源 A 做操作 X”扩大成任意写权限。

### 9. 人工审批合同至少要展示什么？

答：展示谁发起、将执行什么动作、目标资源、完整参数、权限范围、风险/影响、依据证据、执行者、有效期和撤销入口。用户确认的是具体可理解的副作用，不是一个脱离上下文的“允许 Agent”。

### 10. 为什么审批不能只是一个布尔值？

答：布尔值没有绑定动作、资源、参数、版本和时间，容易被复用到已变化或更危险的操作。审批记录应可验证、可过期、可撤回，恢复时重新检查 State、策略和操作 hash。

### 11. Tool、MCP 和 A2A/Task API 的边界分别是什么？

答：Tool 是宿主调用的单个动作；MCP 是跨宿主发现和调用 Tool/Resource/Prompt 的协议边界；A2A/Task API 是一个 Agent 把有状态任务委托给另一个 Agent 的任务边界。协议不等于自主决策，宿主仍负责 Loop、策略和停止。

### 12. 为什么跨 Agent 返回值不能直接作为高权限执行依据？

答：对方可能错误、被注入、权限不足或返回过期事实；“另一个 Agent 说可以”不等于业务授权。上游要验证 Schema、来源、证据、资源权限和当前状态，必要时重新审批和程序化检查。

## Level 3｜多 Agent 设计与评估

### 13. 子任务合同应如何定义输入、输出、权限和终止条件？

答：输入要明确目标、上下文和约束；输出有版本化 Schema、证据和成功/失败状态；权限绑定资源和操作；终止条件包括完成、预算耗尽、超时、拒绝、无进展和人工升级。没有这些字段，子 Agent 会变成不可控的自由文本黑盒。

### 14. 多 Agent 如何处理部分成功、超时、失败和过期结果？

答：每个子任务有独立状态、attempt、deadline 和副作用记录；聚合器按合同决定可接受的部分结果、补偿、重试或降级。过期结果不能无条件覆盖新状态，未知副作用先对账，父任务保留未完成列表。

### 15. 多 Agent 之间出现结论冲突时如何仲裁？

答：优先使用程序/业务事实和可复核证据，其次按明确的审查规则或人工确认；不能简单平均两个模型的意见。结果应保留冲突来源、依据、版本和最终裁决，必要时让任务转人工而不是继续扩大传播。

### 16. 如何避免委托循环、语义漂移和错误传播？

答：限制最大委托深度、总预算和重复目标，使用稳定任务/能力 Schema、版本和状态摘要；每次委托验证输入输出和证据，检测相同任务来回转发。下游失败要结构化回传，不能把不确定文本包装成成功。

## Level 4｜场景追问

### 17. 设计一个跨租户、多 Agent 的研究系统，如何防止子 Agent 越权读取和回传敏感资料？

答：父任务为每个子 Agent 颁发绑定 tenant、资源、用途、字段和时限的最小能力凭证；检索/工具在服务端预过滤，返回最小化、脱敏且带证据的内容。跨 Agent 结果再次做 Schema、来源、权限和敏感数据检查，Trace 分租户隔离并审计委托链。

### 18. 一个 Reviewer Agent 认为 Executor 的结论错误，但两者都没有完整证据，你会如何处理？

答：把状态标为需要补证据/人工，而不是让两个模型继续互相说服；要求引用原始数据、程序验证或重新执行只读查询。若无法取得可靠证据，保留冲突和影响范围，按风险降级或拒答。

### 19. 一个委托 Agent 超时后上游想重新派发任务，如何避免重复副作用？

答：重新派发使用同一业务 task_id/operation idempotency key，先查询原子任务和外部状态；只有确认未执行或下游已安全失败才允许继续。不同 attempt 记录在同一父任务下，不能仅凭“请求超时”创建一个全新副作用。
