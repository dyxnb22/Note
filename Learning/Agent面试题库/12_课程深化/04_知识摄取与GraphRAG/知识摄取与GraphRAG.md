# 知识摄取、检索与 GraphRAG

> 递进路径：先建立文档生命周期和权限边界，再讲 PDF/OCR/表格摄取、混合检索与更新，最后判断是否需要 GraphRAG。

## Level 1｜知识系统基本模型

### 1. 一个生产知识系统的对象生命周期可以如何表示？

答：可抽象为 `Source → Document → DocumentVersion → Chunk → IndexRecord → Citation`。Source、版本、所有者、权限和删除状态是事实；Chunk/倒排/向量/图索引是可重建的派生产物，引用要能回到原始版本和位置。

### 2. 为什么 Source、DocumentVersion 和权限是事实，而向量索引是可重建产物？

答：索引可能因模型、分块或存储升级而重建，不能成为唯一真相；原文版本和授权决定什么内容存在、谁能看、何时生效。把事实和索引分开，才能做权限变更、删除、回滚和重新索引。

### 3. 文档摄取的标准流水线应有哪些阶段？

答：发现变化、抓取并校验安全、解析与标准化、质量检查、生成不可变版本、切分和写元数据、建立索引、验证后原子发布。每一步要幂等、可重试、可观测，失败不能让旧索引和新索引半混合。

### 4. 文档元数据至少应该包含什么？

答：来源 URI、文档/版本 ID、所有者、作者、时间、有效期、权威等级、内容 hash、解析器版本、语言/类型、租户、数据分类、允许用途和权限范围。元数据既服务检索过滤，也服务引用、审计和删除。

### 5. 为什么权限必须在检索前过滤，而不能只在回答阶段过滤？

答：未授权片段一旦进入召回、重排或模型 Context，就可能通过摘要、推断或日志泄露，即使最后删除引用也无法证明没有被使用。应在向量/倒排/图扩展前按 actor、tenant、resource 和 action 做服务端过滤。

### 6. 引用如何回指到具体版本、页码和区域？

答：Chunk 和引用记录保存 document_version_id、页面/段落/表格/区域坐标、原文 hash 和必要的行列信息；回答中的 citation ID 映射到这些记录。这样可以复核证据、处理版本变化和向用户展示准确位置。

### 7. 知识系统如何处理更新、删除、重命名和权限变化？

答：用内容 hash 和不可变版本检测变化，更新生成新版本并原子切换，删除要标记真相并从倒排、向量、图、缓存和派生摘要中清理；重命名更新引用映射，权限变化立即影响查询过滤。旧版本是否保留由保留策略决定，但不能继续被默认召回。

## Level 2｜文档解析与质量

### 8. 为什么摄取前要先分类 PDF、扫描件、Office 和表格？

答：数字 PDF、扫描 PDF、混合 PDF、Office 和表格需要不同的解析策略；分类错误可能比模型或向量检索小幅误差更严重，例如把图片当空文本或把表格顺序打散。分类结果还应保留置信度和人工复核入口。

### 9. PDF 解析中的阅读顺序问题有哪些？

答：多栏、页眉页脚、脚注、旋转文字、水印和字体编码都可能让文本顺序错乱。解析时应恢复标题层级和阅读顺序，同时保留页码、边界框和原始区域，不能只输出一段无定位纯文本。

### 10. OCR 质量应该如何评估？为什么不能只给一个总体准确率？

答：至少按字符/行/块或文档质量桶记录置信度、空文本、乱码、数字/专名错误和需要人工复核的比例。总体平均值会掩盖关键表格或金额区域的低质量，应对低置信片段降权、标记或转人工。

### 11. Word、PPT 和 Excel 的解析重点分别是什么？

答：Word 要保留标题、段落、表格、批注和隐藏文本语义；PPT 要区分幻灯片正文、备注、图形和顺序；Excel 要识别工作表、表头、关键列、合并单元格和公式/值。解析结果应能回指原文件和位置。

### 12. 表格为什么不能简单按纯文本切成普通 chunk？

答：合并单元格、重复表头、跨页、无边框和行列关系会在纯文本中丢失；用户问题可能依赖列名、单位和整行条件。应保留结构、表头和行级定位，数值密集查询必要时直接走 SQL/API，检索只负责发现证据。

### 13. 为什么要在切分前先标准化文档？

答：先统一编码、标题层级、语言/类型、租户/分类、解析质量、表格指针和版本信息，后续切分才能沿语义与结构边界进行。直接对脏文本切块会把乱码、页眉和跨表关系固化进索引。

### 14. 文档摄取应设置哪些质量门禁？

答：检查是否为空/乱码、OCR 置信度、标题/表格结构、页码可定位性、敏感数据分类、提示注入、重复、版本和权限元数据完整性。任一关键门禁失败应隔离或人工复核，不应悄悄发布到线上索引。

### 15. 如何设计解析失败隔离、重试和可观测性？

答：每个文档/版本有独立任务和错误码，暂时性依赖错误限次重试，解析器确定性错误进入隔离队列；保留输入 hash、解析器版本、失败阶段和质量指标。单份坏文件不能阻塞整批摄取，也不能用重试掩盖格式不支持。

## Level 3｜检索系统工程

### 16. 一个检索服务合同至少要定义哪些能力和指标？

答：应定义 Chunk/版本 ID、可搜索字段、权限过滤、更新/删除语义、无结果/冲突/过时处理，以及延迟、吞吐和召回目标。合同还要说明返回分数、来源和引用位置，供上层 Context Builder 和验证器使用。

### 17. 检索服务为什么要保留 BM25、向量和融合排序的分阶段证据？

答：只保留最终候选无法判断问题来自词面召回、语义召回、融合权重还是 Reranker。每阶段应记录候选 ID、来源、原始/归一化得分、过滤原因和版本，再按查询类型比较召回、排序、延迟与权限结果。三种检索的适用场景和融合方式统一见 [[../../06_RAG与知识库/RAG与检索|RAG 与检索]]。

### 18. Embedding 版本和 ANN 索引选型会影响什么？

答：Embedding 模型变化会改变向量空间，旧新向量不能无条件混用；ANN 结构在召回、内存、延迟、过滤和更新能力上有取舍。选型需结合数据规模、隐私、资源、更新频率和可运维性，而不是只记产品名称。

### 19. Chunk、metadata 和权限过滤应该放在哪个阶段？

答：Chunk 在解析标准化后生成，metadata 与每个 Chunk/版本绑定；权限应尽可能在倒排/向量/图检索之前过滤，重排和回答阶段再做一次防御性校验。后过滤会让 TopK 被未授权文档占满并产生泄露风险。

### 20. 混合检索中为什么常用“召回 → 去重 → RRF → 重排 → TopK”？

答：BM25 和向量分数通常不可直接相加，先各取候选并去重，再用基于排名的 RRF 融合，避免分数尺度不一致；随后用 Cross-Encoder 或其他重排模型精排，最后控制送入 Context 的 TopK。每一步都要保留来源和权限。

### 21. Query Rewrite、MultiQuery、HyDE 和 Reranker 分别解决什么问题？

答：Query Rewrite 改善问题表达，MultiQuery 用多个视角增加召回，HyDE 用假设性答案生成检索表示，Reranker 在候选集上做更精细相关性判断。它们会增加延迟和成本，必须用分片 Eval 证明收益，不应默认叠加。

### 22. 检索系统如何实现增量更新、幂等、删除和 Embedding 升级？

答：以 source/version/content hash 作为幂等依据，更新时原子替换新版本并删除旧 Chunk，删除任务要覆盖所有派生索引和缓存；Embedding 升级可双写/双索引、离线重建后切换，并准备回滚和部分失败修复。

### 23. 如何评估检索质量、权限安全和时效性？

答：离线看 Recall@K、Precision、MRR/NDCG、零结果和引用覆盖，专项看权限泄露必须为零、过时命中和冲突处理；线上观察点击、引用采纳、纠正、人工抽检和尾部分桶。检索分数高不代表最终回答正确。

### 24. 如何估算向量索引的容量、延迟和成本？

答：先估算文档量、Chunk 数、向量维度、数据类型和副本，再加索引结构、metadata、缓存和增长率；用代表性过滤条件测召回、P95/P99、更新和重建时间。实际工作负载下比较成本/质量，不能只按理论 QPS。

## Level 4｜GraphRAG 与关系检索

### 25. GraphRAG 解决什么类型的问题？为什么不应该默认使用？

答：它适合实体消歧、多跳关系、路径约束和跨大量文档的全局主题总结；普通事实问答通常用权限感知的混合检索更简单。图会引入抽取错误、实体合并、更新、权限扩展、延迟和成本，必须先证明基线不足。

### 26. 一个可追溯的知识图谱对象模型应如何设计？

答：可用 `DocumentVersion → Entity → Relation → Community`，Relation 至少保存证据片段、来源版本、置信度、时间和有效性，Entity 要有规范化 ID 与别名映射，Community 摘要要能回链原文。图边不能脱离证据成为无来源事实。

### 27. Graph-first、retrieve-first 和 community summary 有什么差异？

答：Graph-first 先找实体和关系再回到文档，适合明确的多跳路径；retrieve-first 先召回文本再在局部建图/扩展，降低全图搜索成本；community summary 适合全局主题和群落级问题，但必须能回链具体证据。

### 28. 图扩展为什么也必须做权限过滤？

答：用户可能从一个有权实体沿关系扩展到无权文档、实体或社区摘要；图结构本身也可能泄露资源存在性。应在实体/边/文档版本层按当前 actor、tenant 和 action 过滤，再执行扩展和聚合。

### 29. GraphRAG 的实体合并、关系抽取和时效性有哪些风险？

答：实体过度合并会把不同主体事实混在一起，合并不足会丢失关系；模型可能抽取不存在或过时的边，来源变化后图也可能滞后。需保留证据、置信度、版本和有效期，支持增量更新、冲突标记与删除。

### 30. 如何评估 GraphRAG 是否值得相对普通混合检索增加复杂度？

答：用相同任务集和权限环境做基线对比，按多跳成功率、实体消歧、证据链完整性、泄露率、延迟、Token、更新成本和运维复杂度分片。只有在关键任务有稳定收益且安全门槛不退化时才引入图。

## Level 5｜场景追问

### 31. 设计一个支持权限、版本、表格和引用的企业知识库，如何保证索引不会出现半新半旧？

答：以不可变 DocumentVersion 为单位完成解析、质量和索引，所有派生记录带版本 ID；新版本全部通过门禁后原子切换可见版本，旧版本延迟清理但不再默认召回。查询先按权限和有效版本过滤，返回引用映射到页/表格区域。

### 32. 一个扫描 PDF 的问答系统回答错了，你会先检查 OCR、切分、召回、重排还是生成？

答：先看 Trace 和引用确认错误证据是否已被正确解析：空文本、乱码、数字/表格 OCR、阅读顺序是第一层；证据存在后看 chunk/权限/召回和重排；证据正确但结论错才检查 Context 组织、生成和答案验证。按流水线第一处丢失事实定位，不直接归咎模型。

### 33. 企业问题需要跨文档、多跳关系推理，你会如何证明 GraphRAG 比混合检索更适合？

答：建立包含实体消歧、两跳/多跳、冲突和权限边界的标注集，先跑混合检索基线，再比较证据链完整性、任务成功、泄露率、P95 和成本。若图只提升少量平均分却增加大量错误边和运维负担，就不应采用。

### 34. 用户被撤权后，如何保证旧向量、缓存、Trace 和图关系不会继续泄露内容？

答：授权服务立即在查询和图扩展前拒绝，索引按版本/资源撤销或隔离，语义/结果缓存键包含 actor/tenant/权限版本并失效；删除任务覆盖向量、倒排、图、派生摘要、日志/Trace、回放和备份，保留数据也必须脱敏或不可访问。
