# 06 Agent 开发

## LLM 调用

- 显式设置超时(连接 / 首字节 / 总)和最大输出长度。
- **超时只表示这次等待结束，不代表模型没执行。** 对有计费或副作用的调用，记录调用标识；仅在提供商明确支持时使用幂等键或状态查询，否则保留结果未知状态并避免盲目重试。
- 先区分限流、暂时服务故障、输入错误与策略拒绝，再按提供商协议判断是否重试。429、部分 5xx 和网络故障可能可恢复；错误输入通常需要先修正。所有重试都应受次数、时间与费用预算限制。
- 流式输出：首事件超时、总超时、响应大小上限要分别设。
- 记录 token 用量和成本，便于预算和异常检测。

## 消息与 Prompt 结构

- 角色常见有 system、user、assistant、tool，但实际名称和约束依提供商协议；不要把一套消息格式当作所有模型的通用接口。
- 输入分区要清晰并标注来源：系统指令 / 用户输入 / 检索上下文 / 工具输出。
- 上下文有窗口上限，超了要裁剪或摘要，裁剪策略要可解释。
- **提示注入**：外部内容(网页、文档、工具结果)一律当不可信输入，不能让它覆盖系统约束。

## 结构化输出

- 需要机器读取的结果时，优先使用服务支持的结构化输出能力，并对实际返回数据进行校验。不要只依靠正则从自由文本中提取关键字段。
- 解析失败时，明确返回错误、重新请求或终止的条件，并限制重试次数。不要用默认值掩盖未获得有效结果的事实。
- 校验通过 ≠ 业务合法，业务规则在代码里再校一次；模型输出还要限制枚举、长度、未知字段和 schema 版本。
- 适配层负责解析外部数据，服务层检查权限、资源状态和幂等条件，执行器接收经过授权的受限命令。
- 将结构校验、业务判断和外部操作分开，有助于分别测试失败路径，避免一个处理器承担过多职责。

## Tool Calling

工具调用包含两个阶段：模型提出调用请求，应用决定是否执行并返回结果。模型生成了合法参数，不代表它已经获得执行权限。

- 工具 schema 要精确：类型、必填、枚举、描述。描述是**给模型看的**，要写清什么时候用。
- 流式返回时工具参数是**增量分片**的：依据具体协议的调用 ID、索引和完成事件组装完整参数再解析；断开时要区分“尚未形成调用”和“可能已经形成但未执行”。
- 执行前校验：参数合法、调用方有权限、资源存在、幂等键；高风险动作进入拒绝 / 澄清 / 人工审批分支。
- 工具调用可能只读，也可能产生外部副作用；按能力设置超时、资源范围与审计，执行代码等能力再采用合适的隔离。
- 执行结果返回稳定状态、调用 ID 和可程序化验证的成功证据；未知字段、低置信和越权不静默放行。
- 工具结果要能区分“成功”、“业务失败”、“执行异常”，不能都当成功。

## Agent 循环与分层

- 分层：`Provider`(模型客户端)/ `Tool`(工具注册与执行)/ `State`(会话与中间状态)/ `Loop`(编排与控制)。
- 循环需要明确的停止条件，例如最大轮次、总超时、预算上限或完成信号。根据业务组合限制，并测试它们是否覆盖实际调用路径。
- 需要跨进程重启恢复的会话，可在明确边界保存检查点（Checkpoint），记录输入、结果与执行状态。短期、可丢弃的会话可以只保存在内存中。
- 幂等：同一轮重放不应重复产生副作用。
- 观测：每轮记录输入摘要、工具调用、token、耗时、结束原因。

## RAG

- 流程：切分 → 嵌入 → 检索 → (重排) → 拼进上下文。
- 切分按语义边界，保留来源元数据(路径、标题、位置)。
- 排查知识回答错误时，先确认需要的内容是否被检索到，再检查排序、上下文组织和生成过程，避免只改提示词而忽略缺失的依据。
- 向量检索可与关键词检索混合，再重排。
- 引用要能回到原文位置，便于核对。

## 评测

- 没有标准答案的任务要建评测集：输入 + 期望特征 + 判据(规则 / 模型裁判 / 人工)。
- 区分离线评测和线上指标；线上看任务成功率、失败类型、成本、延迟。
- 修改提示词或更换模型后，使用同一组评测输入比较结果，记录质量、延迟和成本的变化。
- 记录版本：Prompt 版本、模型版本、检索索引版本。

## 安全与执行边界

- 工具权限最小化：只给必要的工具，只给必要的资源范围。
- 根据动作影响设置权限、资源范围、限额或审批。只读查询、可恢复的本地写入与不可逆的外部操作，通常需要不同控制。
- 沙箱执行代码 / shell，限制网络和文件系统访问。
- 审计：谁在什么时候让 Agent 做了什么，可追溯。
