# 完整案例：订单查询脚本

输入订单号，脚本读取当前身份可见的订单，输出订单状态，以及按示例规则能否申请取消。

阅读前建议先熟悉[语言核心](01_语言核心.md)中的基本类型、容器、函数、类与对象、异常和模块与包。案例使用 pathlib、argparse、JSON 等标准库；源代码与数据都在[共享案例目录](../AI/实践/order_assistant/README.md)。

## 从命令到结果

准备 Python 3.12 或更高版本。从 Notes 根目录执行：

```bash
cd "Learning/AI/实践/order_assistant"
python3 query_orders.py A
```

程序只依赖标准库，无需 pip 安装。结果为：

```json
{
  "order_id": "A",
  "status": "pending",
  "version": 1,
  "policy_id": "cancel-v1",
  "can_request_cancellation": true
}
```

A 订单处于 pending，符合示例 cancel-v1 的状态条件。这个结果只回答能否申请，没有修改订单。真实业务可能还要检查发货、结算和审批，不能直接套用这条简化规则。

## 文件怎样配合

| 文件 | 在案例中的职责 |
|---|---|
| [data/orders.json](../AI/实践/order_assistant/data/orders.json) | 三条固定的教学订单 |
| [orders.py](../AI/实践/order_assistant/orders.py) | 读取记录、限制可见范围、取得规则并形成结果 |
| [query_orders.py](../AI/实践/order_assistant/query_orders.py) | 解析命令行，调用业务函数，将结果写到标准输出 |
| [agent.py](../AI/实践/order_assistant/agent.py)与[providers.py](../AI/实践/order_assistant/providers.py) | 后续 Agent 版本；阅读脚本时可以暂时略过 |

命令行入口依次执行：

```text
order_id = A
    ↓
load_orders：读取 JSON 并检查记录结构
    ↓
lookup_order：在 demo 的可见范围中查 A
    ↓
lookup_policy：用实际的 pending 状态取得 cancel-v1
    ↓
consultation：组合订单与规则
    ↓
json.dumps：生成输出文本
```

入口用函数串起固定路径，订单规则留在业务模块中，后续 Agent 也调用同一组函数。

## 数据从哪里进入

argparse 将命令行中的 A 解析为字符串；--data 可以由本机运行者指定其他订单文件。没有指定时，路径从 orders.py 所在目录定位到 data/orders.json，因此从其他工作目录启动脚本也能找到默认数据。

Path.read_text 读取 UTF-8 文本，json.loads 把它转换成 Python 的列表与字典。JSON 语法正确之后，还要检查根节点、必需字段和订单状态，确认版本号为正整数、同一租户下没有重复订单号。

同一租户内订单号不能重复，因此用 tenant_id 和 order_id 共同识别订单。load_orders 逐项检查输入，类型注解供阅读和静态检查使用。

## 可见范围怎样影响查询

样例中的 A、B 属于 demo；X 属于 private。入口用固定的 demo 模拟已登录身份，调用 lookup_order 时从程序传入 tenant_id，订单查询参数只有 order_id。

lookup_order 同时按租户和订单号查询，只返回 order_id、status、version，咨询结果不输出租户字段。这里演示可信身份怎样传入业务函数；生产环境中的身份应由认证入口取得。

数据文件在本机，读者可以直接查看全部内容。案例只演示业务查询范围，未提供操作系统层面的文件隔离。

## 状态怎样进入规则判断

lookup_policy 接收实际查到的订单状态，返回规则 ID、适用状态与布尔结论。consultation 再检查订单状态和规则状态一致，才生成最终字典。

```python
order = lookup_order(rows, tenant_id="demo", order_id=args.order_id)
result = consultation(order, lookup_policy(order["status"]))
```

上面两行是入口中的局部片段，完整文件已经包含参数解析、导入与错误处理。

查询 B 时，程序正常完成，返回 shipped 和 can_request_cancellation=false。false 是规则判断的结果，并不表示查询失败。

## 失败怎样成为明确输出

| 运行情形 | 输出或行为 | 退出码 |
|---|---|---:|
| 查询 A | pending、规则 cancel-v1、申请条件为 true | 0 |
| 查询 B | shipped、规则 cancel-v1、申请条件为 false | 0 |
| 查询 X 或不存在的编号 | error 为 not_found；说明当前可访问范围内找不到订单 | 2 |
| 文件无法读取、JSON 不合法或记录结构不符合约定 | error 为 invalid_data | 1 |

业务函数抛出 OrderNotFound，命令行入口将它转成输出。接入 HTTP 时，只需在新入口转换同一异常，查询逻辑可以复用。缺少命令行参数则由 argparse 给出用法说明。
