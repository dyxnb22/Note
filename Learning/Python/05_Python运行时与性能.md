# Python 运行时与性能

本篇补齐 Python 从“会写代码”到“能解释运行行为和性能”的中间层。语法见[核心语法](01_Python核心语法.md)，项目、依赖和测试见[工程化](02_Python工程化.md)。

## 1. CPython 执行模型

CPython 通常先把源码编译为字节码，再由解释器执行。函数调用、属性访问、对象分配和异常都有运行时成本；不同 Python 实现不必具有完全相同的内部机制。

排查时区分：

- Python 源代码语义。
- CPython 的具体实现。
- C 扩展是否释放 GIL。
- 操作系统和外部服务等待。

## 2. 对象、引用与可变性

变量保存对象引用，赋值通常不会复制对象。浅拷贝只复制外层容器，深拷贝递归复制可达对象，但可能成本高且破坏共享关系。

可变默认参数只在函数定义时创建一次：

```python
def append_item(item: str, items: list[str] | None = None) -> list[str]:
    result = [] if items is None else items
    result.append(item)
    return result
```

优化前先明确对象身份、共享和生命周期，避免为了减少复制引入隐藏可变状态。

## 3. 属性查找与描述符

实例属性、类属性、继承和描述符共同决定 `obj.attr` 的结果。`property`、绑定方法、`classmethod` 和许多 ORM 字段都建立在描述符协议上。

`__getattr__` 只在普通查找失败后调用；`__getattribute__` 拦截所有属性访问，错误实现容易无限递归。元类和动态属性适合框架基础设施，不应成为普通业务代码的默认抽象。

## 4. 引用计数与 GC

CPython 主要通过引用计数回收对象，并用循环垃圾收集器处理部分引用环。

“对象不再使用”不等于内存立即归还操作系统：

- 引用仍被全局缓存、闭包、任务或容器持有。
- 内存分配器可能保留 Arena 供后续复用。
- C 扩展可能在堆外持有资源。
- 循环对象可能等待 GC。

使用 `tracemalloc`、Heap Profile 和对象增长趋势定位，不能只观察 RSS 下结论。

## 5. GIL 的准确边界

CPython 的 GIL 使同一解释器中通常只有一个线程执行 Python 字节码。它不表示：

- Python 没有并发。
- 所有操作天然线程安全。
- I/O 多线程没有价值。
- C 扩展不能并行。

I/O 密集任务可以使用线程或 asyncio；CPU 密集的纯 Python 通常考虑多进程、原生扩展或外部计算服务。共享复合操作仍需同步。

## 6. asyncio 调度

协程在 `await` 处主动让出执行权。事件循环负责调度 Task、Timer 和 I/O 就绪事件。

关键规则：

- 不在事件循环中执行长时间阻塞调用。
- 为外部调用设置超时。
- 限制并发量。
- Task 必须被等待、管理或记录结果。
- 取消是正常控制流，需要清理资源后继续传播。

使用 `TaskGroup` 等结构化并发机制，让子任务生命周期不超过父作用域。`gather`、`wait` 和 `as_completed` 的异常及取消语义不同，应通过最小实验确认。

## 7. 线程、进程与协程

| 模型 | 适合 | 主要成本 |
| --- | --- | --- |
| asyncio | 大量可异步 I/O | 阻塞调用、取消和背压 |
| 线程 | 阻塞 I/O、现有同步库 | GIL、锁、线程栈 |
| 进程 | CPU 密集、故障隔离 | 启动、序列化、内存 |

选择前测量计算与等待比例。多进程会复制或重建状态，数据库连接、锁和事件循环不能直接跨进程复用。

## 8. 序列化与进程边界

JSON 可互操作但类型有限；Pickle 能保存更多 Python 对象，却不能安全加载不可信数据，也不保证跨版本长期兼容。

跨进程或持久化合同应明确：

- Schema 和版本。
- 字节编码。
- 大对象是否复制。
- 失败和部分读取。
- 安全边界。

## 9. CPU Profiling

推荐流程：

1. 固定工作负载并建立基线。
2. 区分 CPU、等待和外部依赖。
3. 用采样或确定性 Profiler 找热点。
4. 查看调用者—被调用者关系和火焰图。
5. 做最小修改并复测。

微优化只有在热点路径占比足够高时才有意义。内置函数、向量化库和批处理经常比 Python 层循环更高效。

## 10. 内存 Profiling

观察：

- 当前与峰值分配。
- 按调用栈增长的对象。
- 缓存是否有上限。
- Task、回调和闭包是否持有大对象。
- 大文件是否一次性读入。

生成器可以降低峰值内存，但它是一次性惰性计算；若下游最终仍把全部结果收集为列表，并不会节省最终占用。

## 11. 数据结构与局部优化

- `list` 适合连续存储和尾部追加。
- `deque` 适合两端操作。
- `set/dict` 适合哈希查找，但占用更高。
- `array`、NumPy 或 Arrow 适合紧凑同类型数据。

不要用 `sys.getsizeof` 估算整个对象图；它通常只返回当前对象的浅层大小。

## 12. 服务性能

服务还要观察：

- Worker/进程数量。
- Event Loop Lag。
- 连接池和队列等待。
- Pydantic/JSON 序列化成本。
- 日志和 Trace 开销。
- 下游超时与重试放大。

提高 Worker 数前确认 CPU、内存、数据库连接和负载均衡是否允许。

## 12.1 异步资源生命周期（注释版）

性能优化不能以遗留 Task、连接或文件句柄为代价。取消路径要显式清理资源。

```python
import asyncio


async def fetch_with_cleanup(client, url, *, timeout_s=5):
    response = None
    try:
        # 超时包住真实 I/O；只在外层设置超时而不传播取消容易留下后台任务。
        async with asyncio.timeout(timeout_s):
            response = await client.get(url)
            return await response.json()
    finally:
        if response is not None:
            await response.close()
```

具体 HTTP 客户端的关闭方法可能不同；验收时用任务计数、连接池指标和取消测试证明资源确实回收。

## 出现性能或资源问题时验证

1. 比较线程、进程、asyncio 处理 I/O 和 CPU 任务。
2. 制造未关闭 Task 和引用环，用工具定位。
3. 对一个 API 做 CPU/内存 Profile。
4. 比较逐条处理、批处理和向量化。
5. 验证取消后 HTTP、文件和数据库资源被释放。

## 生产项目使用时检查

- 能区分语言语义、CPython、GIL 和 C 扩展行为。
- 能解释对象引用、GC 与 RSS 不下降。
- 所有异步任务都有超时、取消和生命周期。
- 性能修改前后有可复现基准与 Profile。
- 序列化和进程边界有明确 Schema 与安全合同。

## 来源与验证边界

运行时语义参考 Python Language Reference、CPython 文档和标准库文档。实现细节会随 Python 版本变化，性能结论必须在项目锁定的解释器、依赖和工作负载上验证。
