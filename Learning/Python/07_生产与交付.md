# 07 Python 服务的构建、运行与交付原理

部署到另一台机器时，先准备构建环境、安装产物和配置，确定持久数据的位置。服务跑起来后，再看健康检查、退出清理和版本回退。

## 固定构建输入

源代码、Python 版本、依赖声明、锁定结果、构建后端和目标平台共同影响产物。原生依赖还受系统库、架构与编译条件影响。

锁文件之外还要记录系统条件。基础镜像要固定时用摘要，标签可能更新。验证结论写清达到哪一步：依赖相同、能够安装、行为一致，还是构建结果逐字节相同。

## 多阶段镜像与构建缓存

构建阶段可能需要编译器、构建后端和开发工具，运行阶段通常只需要解释器、已安装应用及其运行依赖。多阶段构建使这两类环境分开，减少最终镜像的体积和无关工具。

构建时通常先复制变化较少的依赖声明并安装依赖，再复制源码。只改源码时，依赖安装层便有机会复用；缓存实际是否命中，取决于对应构建输入和层之间的依赖。

采用普通安装（非 editable）后，要确认程序从安装位置加载代码，避免仍依赖开发目录。复制虚拟环境时，目标解释器、系统与路径仍需兼容；它不是跨平台通用的复制方案。[uv 容器构建说明](https://docs.astral.sh/uv/guides/integration/docker/)

## 分开管理应用文件、持久数据与密钥

应用文件随版本发布，数据库、上传文件和任务状态单独持久保存，密钥由受控部署配置提供。代码发布、数据备份和凭证轮换因此可以分开；避免把密钥写进镜像层和普通日志。

删除容器时，可写层中的数据也会丢失，需要保留的数据放到持久卷中。即使用非 root 用户运行，也要正确设置文件权限。EXPOSE 只描述端口，服务监听哪个地址、宿主机发布哪个端口，需要分别配置。

关键配置在启动时校验，缺失或不合法就报错。

## 健康检查与业务验证

| 层次 | 主要关注 | 可能出现的情况 |
|---|---|---|
| liveness | 进程是否仍可继续运行 | 进程存活，但下游暂时不可用 |
| readiness | 当前实例是否适合接收流量 | 初始化尚未完成，不应接流量 |
| 业务成功 | 用户目标是否得到正确处理 | 接口返回成功，但实际状态不符合要求 |

把下游短暂故障全部当作进程死亡，可能导致反复重启、增加压力。先确定哪些依赖故障会让实例无法处理请求，再决定 readiness 要检查哪些服务，不必每次查询所有外部服务。

## 优雅退出的处理顺序

服务器收到停止信号后，通常先停止接收新请求，再处理或取消在途工作，随后关闭应用级客户端与连接池。容器的停止期限应给这些清理留出时间，超过期限后仍可能被强制终止。

exec 形式的容器启动命令有助于应用直接接收信号。finally 会在正常返回或异常退出时执行，但进程收到 SIGKILL 或机器断电时，清理代码可能来不及运行。需要在进程结束后保留的进度，应提前持久保存。

判断退出是否正常时，同时看退出码、关闭日志和数据状态。某些服务器完成清理后，仍会因信号退出返回非零退出码。[Uvicorn 进程退出行为](https://www.uvicorn.org/server-behavior/#graceful-process-shutdown)

## Worker 数量与下游容量

增加 Worker 可以提高并发，也会多占数据库连接、内存和下游容量。SQLite 同时只有一个写事务，增加进程可能带来更多写锁竞争；远端有配额时，更多请求也可能只是遭到限流。

排查耗时时，分别记录排队、线程池等待、数据库锁、模型调用和网络等待。统计 P95 前，先写清是哪段时间、哪些请求；多个实例的 P95 不能直接平均成全局 P95。

## 发布回退与数据兼容性

新增字段可以先允许旧代码忽略，再发布写入逻辑；删除或改名字段则可能影响旧实例和历史检查点。回退程序前，需要确认旧版本仍能读取当前数据。

Agent 的状态结构、Prompt、工具和模型配置也可能随发布改变。恢复旧检查点时，新代码既要能解析旧数据，也要正确理解旧字段的含义。不兼容时，可以迁移数据、沿用旧读取器或停止恢复，见[持久化执行](../Agent/09_工程化与系统设计/02_Durable与生产运维.md)。

付款、取消和通知已经发生后，回退代码不会撤销它们。回退时分别检查程序版本、数据兼容和外部业务状态；权限仍按当前授权，制度仍按当前有效版本处理。

## 构建与部署的验收范围

语法与静态检查、行为测试、安装和容器验证分别记录结果。容器要在目标平台实际运行，上线后继续观察真实负载与依赖条件下的表现。

交付时可以直接写“安装包可导入，容器可启动，尚未做负载验证”，让接手者知道已查到哪一步。
