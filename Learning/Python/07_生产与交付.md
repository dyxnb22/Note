# 07 生产与交付

## 容器与部署

- 多阶段构建将编译与运行环境分开，最终镜像保留程序、运行依赖与必要系统库，通常不带编译工具链。
- 固定基础镜像版本；按项目的锁定流程安装依赖(如 `uv sync --locked`，或对已固定的 requirements 使用 `python -m pip install --no-cache-dir -r requirements.txt`)；先装依赖再 copy 源码，利用层缓存。
- 尽量以非 root 用户运行，可行时使用只读根文件系统。应用监听地址、容器端口与宿主机端口映射应分别配置；Dockerfile 的 EXPOSE 只描述端口，不会自动发布。
- 健康检查区分 liveness(要不要重启)和 readiness(能不能接流量)。

## 配置与环境

- 配置来自环境变量或配置中心，不写死在镜像里。镜像保存程序与依赖，同一镜像可以通过不同配置运行于不同环境。
- 启动即校验配置，缺项快速失败。
- 密钥使用受控注入渠道，不进入源码、日志或镜像层；可以按平台通过受限权限的挂载文件等方式提供，不能把所有磁盘形式一概视为不合法。

## 可观测性

日志记录事件，指标汇总数值，Trace（链路追踪）记录一次请求跨组件的执行过程。它们互相补充，不能仅靠大量日志代替全部观测。

- 日志：结构化，带 trace_id，可检索；敏感数据(token、Prompt、用户内容)脱敏。
- 指标同时观察请求量、错误率、延迟和资源使用。P95 表示约 95% 的样本延迟不超过该值；分位数有助于观察较慢请求，但仍需结合吞吐和错误率判断。
- Trace：跨服务、跨模型调用串起来，标出下游耗时。
- 三者用同一套 ID 关联起来。

## 容量与可靠性

- 外部依赖需要明确超时和资源上限；可重试的操作再设置重试预算。持续失败时，可按需要增加熔断，让调用暂时快速失败，而非让所有依赖机械套用同一套机制。
- 队列达到容量上限时，应按约定等待、拒绝或降级，避免无限堆积任务。背压表示让上游感知处理能力不足，不一定要求立即失败。
- 限流既保护自己，也保护下游。
- SLO（服务水平目标）定义可接受的可靠性或性能范围。错误预算表示目标允许的失败空间，可用于平衡发布速度与稳定性。

## 优雅退出

- 收到退出信号后，先停止接收新工作，按约定等待或取消在途请求及后台任务，让它们执行清理，再关闭其依赖的连接池等资源。具体步骤由服务框架与资源依赖关系决定，避免先关连接再让任务收尾。
- 设退出上限时间，超时强制退出。
- 长任务要能被取消，或标记为可恢复。

## 灰度与回滚

- 发布用滚动 / 蓝绿 / 金丝雀；先小流量看指标，再放量。
- 数据库变更加迁移脚本，且要向后兼容：先加后用，最后清理。
- 回滚路径要提前演练，不能只写在文档里。

## 事故响应

- 先止损(回滚 / 限流 / 降级)，再定位。
- 保留现场：日志、Trace、指标、堆栈。
- 复盘关注机制和检测手段，不只写“某人操作失误”。

## 依赖与供应链

- 构建时按项目锁文件安装依赖，不要在部署阶段无意中重新解析出另一组版本。
- 定期扫已知漏洞；升级要有测试覆盖。
- 慎用不活跃依赖，评估许可证。
