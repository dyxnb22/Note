# 02 语言进阶与异步

这一篇先看迭代器、生成器、装饰器和上下文管理器，再讲类型注解与异步。重点是代码何时执行、状态存在哪里、退出时怎样清理。

## 迭代协议

可迭代对象提供开始遍历的入口，迭代器保存当前进度。列表可以反复遍历；对列表调用 iter 得到的迭代器，则会逐步耗尽。

```python
values = [10, 20]
iterator = iter(values)
assert iter(iterator) is iterator  # 迭代器返回自身，不会重置进度。
assert next(iterator) == 10
assert list(iterator) == [20]  # 从当前位置继续取值。
assert list(iterator) == []  # 已耗尽，不会从头开始。
assert list(values) == [10, 20]  # 列表本身仍可重新遍历。
```

- 可迭代对象的 `__iter__` 返回迭代器。迭代器的 `__iter__` 返回自身，`__next__` 每次取出一个值，耗尽时抛 `StopIteration`。有些对象没有 `__iter__`，Python 也会尝试按 0、1、2……调用 `__getitem__` 取值。
- for、解包和 list() 使用迭代协议；成员判断 in 优先使用 `__contains__`，没有时才可能退回迭代等协议。
- 类型注解里区分 `Iterable`(可迭代)和 `Iterator`(迭代器本身)。

## 生成器

```python
def gen(n):
    for i in range(n):
        yield i

g = gen(3)
assert next(g) == 0
assert list(g) == [1, 2]
assert list(g) == []
```

调用 gen(3) 时创建生成器对象；第一次 next 才开始执行函数体。每到 yield，函数产出一个值并暂停。下一次取值从暂停位置继续，所以第一个 list 只得到剩余的 1 和 2，第二个 list 得到空列表。

`yield from` 把一段迭代过程交给另一个可迭代对象。只需要逐项转交结果时，它比手写 for 与 yield 更直接：

```python
def combined():
    yield "开始"
    yield from [1, 2]
    yield "结束"

assert list(combined()) == ["开始", 1, 2, "结束"]
```

- **只能消费一次**；要重复用就重新生成或缓存成 list。
- `send(value)` 恢复生成器，并让暂停处的 yield 表达式取得 value；启动时只能先取值或发送 None。`throw()` 在暂停处注入异常，`close()` 请求结束生成器并执行相应清理。
- 生成器表达式适合简单的逐项变换。需要多步控制流、局部状态或异常处理时，通常用生成器函数更清楚，不必强行压成一个表达式。

## 装饰器

```python
from functools import wraps

events = []

def record(function):
    events.append("装饰")

    @wraps(function)
    def wrapper(*args, **kwargs):
        events.append("调用")
        return function(*args, **kwargs)

    return wrapper

@record
def add(left, right):
    return left + right

assert events == ["装饰"]
assert add(2, 3) == 5
assert events == ["装饰", "调用"]
assert add.__name__ == "add"
```

常见函数装饰器接收函数并返回可调用对象；装饰器也可用于类，返回值不必是普通函数。

`@record` 在定义 add 时执行一次，让 add 指向 wrapper。以后调用 add，才进入 wrapper，再由它调用原函数。`wraps` 保留函数名等信息；调用原函数、传参数和返回结果，都要在 wrapper 里自己写。

### 带参数的装饰器

下面的装饰器分三步创建：`repeat(2)` 记下配置并返回装饰器；装饰器接收 greet；最后返回 wrapper，供以后调用。外层函数结束后，内部函数仍引用 times，这就是闭包的用途。

```python
from functools import wraps

def repeat(times):
    def decorate(function):
        @wraps(function)
        def wrapper(*args, **kwargs):
            return [function(*args, **kwargs) for _ in range(times)]

        return wrapper

    return decorate

@repeat(2)
def greet(name):
    return f"你好，{name}"

assert greet("小明") == ["你好，小明", "你好，小明"]
```

`@repeat(2)` 可按 `greet = repeat(2)(greet)` 理解：定义时先创建配置好的装饰器，再包装原函数；两次实际调用发生在之后执行 greet 时。

- 包装器需要等待异步函数并处理执行结果或异常时，通常写 async def wrapper 并 await；同步包装器也可只转发协程对象，二者语义不同。
- 常用：`functools.lru_cache` / `functools.cache`、`staticmethod` / `classmethod` / `property`。

## 上下文管理器

```python
from pathlib import Path
from tempfile import TemporaryDirectory

with TemporaryDirectory() as directory:
    path = Path(directory) / "message.txt"
    path.write_text("hello", encoding="utf-8")
    with path.open(encoding="utf-8") as file:
        data = file.read()
    assert file.closed
    assert data == "hello"
```

文件对象支持 with：进入代码块时得到文件对象，离开时关闭文件。所以 with 外的 file.closed 为 True，已经读出的 data 仍可使用。

进入 with 时调用 `__enter__`，离开时调用 `__exit__(exc_type, exc, tb)`。代码块里出现异常时，`__exit__` 返回真值，外层就收不到这个异常；返回假值，异常则继续向外抛出。

- `contextlib.contextmanager` 可以把一个生成器写成上下文管理器。
- `contextlib.ExitStack` 管理数量不定的资源。

### 用生成器定义上下文管理器

with 在代码块开始和结束时调用上下文管理器。关闭文件、提交或回滚事务，具体由管理器实现。

普通对象实现 `__enter__` 与 `__exit__`，就可以参与 with 协议。进入成功后，`__enter__` 的返回值绑定到 as 变量，退出时调用 `__exit__`。对象创建或 `__enter__` 失败时，退出方法不会被调用，已取得的资源要在失败处清理。

下面是独立可运行的执行顺序示例：

```python
from collections.abc import Generator
from contextlib import contextmanager

@contextmanager
def managed(events: list[str]) -> Generator[None, None, None]:
    events.append("进入")
    try:
        yield
    finally:
        events.append("退出")

events: list[str] = []
with managed(events):
    events.append("执行")
assert events == ["进入", "执行", "退出"]

events.clear()
try:
    with managed(events):
        events.append("即将失败")
        raise ValueError("example")
except ValueError:
    events.append("外层捕获")
assert events == ["进入", "即将失败", "退出", "外层捕获"]
```

调用带 yield 的函数会得到生成器对象，函数体暂不执行。contextmanager 让 with 先将生成器推进到 yield，暂停后执行 with 体，再继续执行生成器的后半部分。这个生成器必须恰好 yield 一次。

如果 with 体抛异常，异常会在暂停的 yield 处重新出现，因此生成器中的 try/except/finally 可以处理与清理。如果捕获异常后正常结束，with 外的调用方就收不到这个异常；需要继续传播时，应重新抛出。

`Generator` 的三个类型参数分别描述产出值、send 传入值与最终返回值；上例都为 `None`。这里使用 Python 3.12 支持的完整标注形式。

`@contextmanager` 相当于 `managed = contextmanager(managed)`：定义时包装函数，后续进入 with 时才开始执行，离开时完成退出动作。

## 描述符

类的某个属性对象定义了 `__get__`、`__set__` 或 `__delete__` 后，Python 在读取、赋值或删除这个属性时，就可能调用这些方法。这套机制叫描述符。例如，读取 property 定义的属性，看起来只是在取值，实际会执行一个方法。

- `property`、`classmethod`、`staticmethod`、普通函数本身就是描述符。
- 只在需要复用属性逻辑时才自己写；大多数场景 `property` 够用。

### 属性访问为什么会触发代码

描述符与实例字典里可能有同名属性。下面比较定义了 `__get__` 的描述符，说明通常读取 `obj.x` 时谁优先：

| 类型 | 定义的方法 | 通常读取 `obj.x` 时 |
|---|---|---|
| 数据描述符 | 定义了 `__set__` 或 `__delete__` | 优先于实例字典中的同名值 |
| 非数据描述符 | 只有 `__get__` | 可能被实例字典中的同名值遮住 |

普通方法绑定属于后一类，property 属于前一类。下面用描述符校验订单版本；即使往实例字典里写入同名值，也不会绕过这个描述符。

```python
class PositiveVersion:
    def __set_name__(self, owner, name):
        self.storage_name = "_" + name

    def __get__(self, instance, owner=None):
        if instance is None:
            return self
        return instance.__dict__[self.storage_name]

    def __set__(self, instance, value):
        if type(value) is not int or value < 1:
            raise ValueError("version must be a positive integer")
        instance.__dict__[self.storage_name] = value

class Record:
    version = PositiveVersion()

    def __init__(self, version):
        self.version = version

record = Record(1)
record.__dict__["version"] = 99
assert record.version == 1  # 数据描述符仍优先，真正的值保存在 _version。
try:
    record.version = 0
except ValueError:
    pass
else:
    raise AssertionError("无效版本应被拒绝")
```

只有一个类需要校验时，property 往往更直接。这里检查的是对象属性值；数据库中的版本冲突仍由存储事务检查。

## dataclass

```python
from dataclasses import dataclass, field, FrozenInstanceError

@dataclass(frozen=True, slots=True)
class User:
    id: int
    tags: list[str] = field(default_factory=list)

first = User(1)
second = User(2)
first.tags.append("reader")
assert second.tags == []
try:
    first.id = 3
except FrozenInstanceError:
    pass
else:
    raise AssertionError("冻结实例应拒绝重新绑定字段")
try:
    hash(first)
except TypeError:
    pass
else:
    raise AssertionError("含 list 的对象不能直接成功哈希")
```

dataclass 根据字段声明生成初始化、显示和相等比较等方法。上例中 User(1) 使用生成的初始化方法；default_factory=list 在每次创建实例时单独调用 list，所以修改 first.tags 不影响 second.tags。

- 为每个实例生成独立的可变字段，使用 `field(default_factory=...)`。Python 3.12 的 dataclass 会拒绝列表等不可哈希默认值；这种检查并不等于识别了所有可变对象。
- 默认 `eq=True` 时，`frozen=True` 通常会生成哈希方法，但字段值仍须可哈希。上例中的 list 可以修改，也不能哈希：冻结只限制给字段重新赋值，不会冻结列表内部的内容。`slots=True` 可减少部分实例开销。
- `__post_init__` 在生成的初始化方法末尾执行，可放自定义校验；dataclass 本身不根据类型标注自动验证输入。需要系统化的运行时转换与约束时，可以使用 Pydantic。

## 类型注解

```python
def frequencies(items: list[str]) -> dict[str, int]:
    result: dict[str, int] = {}
    for item in items:
        result[item] = result.get(item, 0) + 1
    return result

assert frequencies(["a", "b", "a"]) == {"a": 2, "b": 1}
```

- Python 本身不按类型注解校验输入；注解作为元数据保存，可通过 `__annotations__` 读取。
- 3.9+ 用内置泛型 `list[int]`；3.10+ 用 `X | Y`；3.12+ 有 `type` 别名语句。
- `Optional[X]` 表示 `X | None`。阅读旧代码时可以按这个含义理解；它并不表示调用时可以省略参数，是否可省略仍由默认值决定。现代代码通常直接写 `X | None`。
- 常用：`X | None`、`Literal`、`TypedDict`、`Protocol`、`Callable`、`Iterable` / `AsyncIterator`、`Annotated`、`TypeVar`、`Generic`。
- `Protocol` 描述调用方需要哪些属性和方法。对象只要满足这个结构，静态检查器就可以认为它兼容，不要求它显式继承 Protocol。
- `abc.ABC` + `@abstractmethod` 阻止尚有抽象方法的类被实例化，但不会自动验证覆盖方法签名或业务语义；仍需静态检查与测试。
- `NewType("UserId", int)` 只做静态标记，运行时还是 `int`，用于区分底层类型相同、用途不同的值。
- 运行时校验要另找工具：`pydantic`、`typeguard`。静态检查用 `mypy` 或 `pyright`。

### 返回类型与容器兼容性

`list[str]` 表示列表里的元素是字符串，`str | None` 表示允许字符串或 None；参数能否省略，仍由默认值决定。`-> Self` 表示返回类型随调用它的实例或类变化，子类调用时，返回类型也对应子类。它适合返回 self 或构造同类实例的方法，但不保证返回的就是原对象。

list[子类] 通常不能传给接收 list[父类] 的参数。接收方可能加入另一种父类实例，原列表就不再只包含子类，破坏调用方的类型假设。

### `Protocol`、`Self` 与 `Annotated` 的独立例子

```python
from typing import Annotated, Protocol, Self

class Named(Protocol):
    name: str

class Person:
    def __init__(self, name: str):
        self.name = name

    def rename(self, name: str) -> Self:
        self.name = name
        return self

def greet(person: Named) -> str:
    return f"你好，{person.name}"

person = Person("小明")
assert greet(person) == "你好，小明"
assert person.rename("小红") is person

PositiveInt = Annotated[int, "必须为正数"]
value: PositiveInt = -1
assert value == -1  # 标准 Python 不执行字符串元信息中的约束。
```

`Person` 无需继承 Named，静态检查器可以根据它提供的属性判断是否兼容。

`rename` 返回 `self`，所以 `person.rename("小红") is person` 为真：改完名字，拿到的还是同一个对象。

`Annotated` 用来附加元信息，具体含义要由使用它的库读取并执行；标准 Python 不会因为写了“必须为正数”就拒绝 -1。

## 序列化

- JSON 要用来计算哈希、生成缓存键或签名时，需固定键顺序、数值、字符和时间格式，让同一数据生成一致的文本。普通数据交换不一定要求逐字相同。
- 常用写法：`json.dumps(obj, sort_keys=True, separators=(",", ":"))`。
- 持久化内容摘要使用 hashlib；内置 hash 不承诺跨进程、跨版本稳定，其中 str/bytes 等类型通常带进程随机化。
- `pickle` 反序列化可能执行代码，不应用于不可信输入。跨信任边界交换数据时，优先采用 JSON 等数据格式，并继续检查输入大小和数据结构。

## 同步并发原语

- `threading.Lock` / `RLock`：保护共享可变状态，用 `with lock:`。`Lock` 是基础互斥；`RLock` 记录持有线程和递归计数，适合递归或回调会重入同一段代码的场景。
- `queue.Queue`：线程安全队列，实现生产者—消费者。
- `threading.Event` / `Condition` / `Semaphore`：事件通知、条件等待、限流。`Semaphore` 适合连接池和并发上限；Event 是可通过 set/clear 重置的广播状态开关，常用于停止信号。
- `concurrent.futures`：线程池 / 进程池，统一 `submit` / `map` 接口。
- `multiprocessing`：跨进程共享用 `Value` / `Array` / `Queue`，或干脆传消息。
- 多步读取、计算和写回不应默认视为原子操作。GIL 不会自动保证这些步骤满足业务上的并发一致性要求。

## 竞态、死锁与饥饿

- 两个线程都读到旧值，再分别写回，可能丢掉一次更新。结果取决于执行先后、又不符合预期的问题，叫竞态。把相关的读取、计算和写回放在同一把锁保护的代码中，或通过队列交给一个执行者统一修改状态。只缩短加锁范围，可能漏掉必须一起保护的步骤。
- 死锁：固定加锁顺序、用 `acquire(timeout=...)` 或非阻塞获取留退路、避免持锁状态下调用未知回调。
- 饥饿是某些任务长期得不到所需资源。控制持锁时长和任务粒度有助于缓解，但是否公平仍取决于调度与同步机制。
- 并发测试覆盖竞争、超时和资源释放。可控调度、压力测试和代码审查互相补充，都不能单独穷尽线程交错。

## CPython 执行模型与 GIL

- 源码 → 字节码 → 解释执行；`dis` 可看字节码。
- 常规 CPython 通常在引用计数归零时释放对象，循环引用还可能由垃圾回收器处理。文件和连接等资源仍应显式管理生命周期。
- 对常规带 GIL 的 CPython 构建，同一解释器同一时刻只有一个线程执行 Python 字节码。
  - 等待 I/O 或调用释放 GIL 的扩展时，多个线程仍可能获得并发或并行收益。
  - 自由线程构建的支持状态按目标 Python 版本核对，不能将 GIL 构建的约束推广到所有构建。

- GIL ≠ 线程安全。

## 线程 / 进程 / 协程怎么选

| 场景 | 选择 |
|---|---|
| I/O 密集、连接多 | `asyncio` |
| I/O 密集、只能用同步库 | 线程池 `ThreadPoolExecutor` |
| CPU 密集 | 多进程 `ProcessPoolExecutor` |

- 普通进程各有独立地址空间。进程池传参和回传结果通常涉及序列化与复制；共享内存是另一种机制，需要额外同步。小任务可能因这些开销而得不到加速。
- 对带 GIL 的 CPython，线程适合包装阻塞调用；纯 Python 的 CPU 密集计算通常不能靠增加线程获得多核加速。释放 GIL 的扩展与自由线程构建需要分别判断。

## asyncio 核心

```python
import asyncio

async def double(value):
    await asyncio.sleep(0)
    return value * 2

async def main():
    return await asyncio.gather(*(double(value) for value in [1, 2, 3]))

assert asyncio.run(main()) == [2, 4, 6]
```

上例中 double(value) 先创建协程对象；gather 将这些协程安排为并发任务，并按传入顺序收集结果。`await asyncio.sleep(0)` 提供让出执行机会的位置，没有阻塞线程。asyncio.run 创建事件循环、执行 main 并返回结果，因此最终得到 [2, 4, 6]。

- 不含 yield 的 `async def` 定义协程函数；调用后得到协程对象，经 await 或调度为 Task 后执行。含 yield 的 async def 则定义异步生成器函数，使用 async for 消费。
- 常规事件循环在一个线程内协作调度；await 遇到尚未完成的等待时才可能让出控制权，不是每个 await 都必然发生任务切换。
- 不应在事件循环线程上直接执行耗时阻塞操作，例如 `time.sleep()` 或同步 HTTP 请求。可以改用异步接口，或将合适的同步操作交给 `asyncio.to_thread()`。取消对 to_thread 的等待不会强行终止已经运行的线程；线程中的操作仍需自身超时、停止信号或结果核对。

下面几个 API 用来安排任务、等待结果：

| API | 主要用途 |
|---|---|
| gather | 并发等待，按传入顺序收集结果 |
| as_completed | 尽早处理已经完成的结果 |
| wait | 返回已完成、未完成的任务集合 |
| TaskGroup | 管理一组任务，退出时等待它们结束并处理异常 |

Semaphore 则限制同时进入某段代码的任务数，不自动限制每秒请求数。

- 选择 `gather` / `wait` / `as_completed` 时，比较异常传播、兄弟任务取消和超时清理的行为。
- `asyncio.timeout(5)` 为代码块设置超时，`wait_for` 为一次等待设置超时。先说清总预算是否包含排队、重试和清理。两者都需要任务响应取消：耗时同步代码不会被立刻打断，外部操作也不会因为本地超时而撤销。
- 取消：`Task.cancel()` 通常在任务下一次获得执行机会时注入 `CancelledError`，不会自动中断耗时同步代码。捕获后在 `finally` 中释放连接、文件和锁，再继续传播取消。
- 本地等待超时后的外部状态核对，见下文“超时是否意味着操作没有发生？”。
- gather 自身被取消时，会取消尚未结束的子任务。某个子任务失败时的传播行为，以及它与 TaskGroup 的区别，见后文 TaskGroup 一节。

## 异步资源与生命周期

- 异步上下文管理器：`async with` + `__aenter__` / `__aexit__`。
- 异步迭代：`async for` + `__aiter__` / `__anext__`；异步生成器用 `async def` + `yield`。
- 退出时，通常先取消或等待未完成任务，让任务执行清理，再关闭其依赖的连接池等资源。具体顺序应与资源依赖关系一致。
- 可以用 shield 保护里面的清理任务，避免等待者的取消直接传给它。等待 shield 的外层任务仍可能收到 CancelledError，因此还要保留清理任务的引用，规定怎样等待、何时超时。

## 上下文传递

- `contextvars.ContextVar`：在异步任务链条里传 `request_id`、租户、trace 上下文的标准做法。
- Task 默认复制创建时的上下文，也可显式传入 context。若上下文中的值指向同一个可变对象，修改该对象仍会影响其他共享者。asyncio.to_thread 会传播当前上下文。
- 自建线程池、进程、消息队列和独立后台任务的传播规则不同，要按 API 和版本传递所需字段。
- 在请求入口调用 `set()`，并在 `finally` 中用 token `reset()`。不要用模块级全局变量保存请求上下文。同一个线程可以交错运行多个协程，`threading.local()` 无法为它们分别保存请求数据。

## TaskGroup 为什么会取消兄弟任务？

结构化并发把一组子任务放在同一生命周期内。某个子任务发生未处理的普通异常时，TaskGroup 会取消尚未完成的其他任务，等待清理结束，再向外传播异常组；这避免父任务已经失败、子任务仍在后台无限运行。

例如订单查询失败、物流查询仍在等待，过程是“订单分支抛错 → 物流分支收到取消 → finally 清理 → 外层接收异常组”。如果允许部分失败，可以在分支内部处理预期错误，返回带失败状态的结果，再由聚合器决定哪些结果可以交付。

默认 gather 的行为不同：它通常先向等待者传播异常，不因这一异常自动取消其他任务。选择 API 时，结合结果顺序、任务归属和失败后的收尾方式决定。

## 超时是否意味着操作没有发生？

不一定。假设远端已经接受取消请求，本地仍在等待回执，此时超时只终止本地等待，已经发生的订单变更仍然存在。finally 释放连接，也不会撤销外部业务状态。

发生超时时，asyncio.timeout 通常通过取消当前任务结束等待，并在退出上下文时抛出 TimeoutError。内部协程清理资源后应继续传播 CancelledError；若把取消吞掉后正常返回，外层可能收不到预期的超时错误。

等待超时、任务取消、操作失败和结果未知分别记录。带副作用的请求通过稳定操作 ID 查询或对账，再决定是否重试，见[后端服务](05_后端服务.md#幂等：让重试对应同一次操作)。

## 子任务为什么可能看不到最新的 ContextVar？

Task 默认复制创建时的上下文，而不是每次读取父任务当前的值。父任务先把 request_id 设为 A、创建子任务、再改成 B，子任务通常仍看到 A；父任务看到 B。

set 返回的 token 用于 reset，让当前 ContextVar 重新指向之前的值。但 reset 不会撤销字典等可变值内部的修改。上下文复制也不是深拷贝：多个上下文中的值如果指向同一个字典，仍可能相互影响。

ContextVar 适合关联请求与日志，不能代替权限判断。跨进程、队列或独立后台任务需要按相应接口显式传递可信身份和必要元数据。

## 性能与内存排查

- 排查前固定测试负载和对照版本，再看时间主要花在 CPU 计算、I/O、序列化，还是等待下游服务上。
- CPU：`cProfile` + `pstats`，线上用 `py-spy`。
- 内存：`tracemalloc`、`objgraph`。
- RSS 是进程当前驻留在物理内存中的空间。Python 对象释放后，内存可能先留在分配器中复用，因此 RSS 不一定立即下降。
- 优化后复测 P95 和错误率，不只看平均值。
