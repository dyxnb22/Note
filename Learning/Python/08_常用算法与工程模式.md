# 08 常用算法与工程模式

常用算法处理查找、分组和缓存；工程模式则处理并发、资源预算、失败恢复与交付。

## 常见算法

### 哈希表查找互补值

遍历输入，用字典记录已经遇到的数值及下标。处理当前值 x 时，先查找 target - x；找到后返回两个下标，否则再记录 x。

先查后存可以避免重复使用当前元素。平均时间复杂度为 O(n)，空间复杂度为 O(n)。接口还需约定无解、重复值以及返回一组或多组结果的行为。

### 区间合并

先按区间左端点排序，再维护当前合并区间。下一个区间与它重叠时扩展右端点；不重叠时输出当前区间，开始处理新区间。

排序耗时 O(n log n)，扫描耗时 O(n)。端点是否包含、相邻区间是否合并，以及空输入返回什么，都是区间合并接口的一部分。

### 无重复子串与滑动窗口

维护一个没有重复字符的窗口，并用字典记录字符最近出现的位置。右端扩展时，如果新字符在窗口内出现过，就将左端移到该位置之后，再更新最大长度。

左端不能回退。每个位置只需处理常数次，时间复杂度为 O(n)；额外空间取决于需要记录的字符种类数。

### LRU 缓存

用字典定位节点，用双向链表维护最近使用顺序。访问或更新后将节点移到最近使用的一端；超过容量时，从另一端移除最久未使用的节点。

平均 get/put 可以做到 O(1)。还要约定容量为零、重复写入和并发访问的行为。如果加入过期时间或统计功能，应单独说明它们如何影响操作复杂度。

### 高频元素与 Top K

Top K 表示取排序最靠前的 K 项；这里按出现频次选择。先统计每个元素的频次，再用大小为 K 的最小堆保留当前频次最高的元素。设输入长度为 n，不同元素数为 m，且 1 ≤ K ≤ m：统计耗时 O(n)，维护堆通常记作 O(m log K)；包含 K=1 边界时可统一写成 O(m log(K+1))。计数表占用 O(m) 空间。

也可以按频次建立桶，但要权衡额外空间。返回元素还是频次、同频时如何排序，以及 K 超出范围时如何处理，都由接口约定决定。

### 栈与括号匹配

遇到左括号就入栈；遇到右括号时，检查栈顶是否有对应的左括号。处理完输入后，栈应为空。时间复杂度为 O(n)，最坏空间复杂度为 O(n)。

简单的括号匹配算法只处理指定括号。如果输入还包含字符串、转义或注释，应先明确解析规则，不能直接把这个算法当作完整的代码解析器。

## 并发与数据处理

### 有界异步并发

先定义每项任务的输入、并发上限、执行超时和结果状态。每项任务进入并发控制范围后执行请求，成功、失败或取消都需要释放相应资源。

还应明确排队时间是否计入超时、父任务取消后怎样收尾，以及结果如何保留部分失败。下面的示例先展示并发限制和错误收集，不实现全部生产调度机制。

```python
import asyncio


async def fetch_all(urls, fetch, *, limit=10, timeout_s=5):
    if limit <= 0:
        raise ValueError("limit must be positive")
    semaphore = asyncio.Semaphore(limit)

    async def one(url):
        async with semaphore:
            try:
                async with asyncio.timeout(timeout_s):
                    return url, "ok", await fetch(url)
            except asyncio.CancelledError:
                raise
            except Exception as exc:
                return url, "error", exc

    return await asyncio.gather(*(one(url) for url in urls))


async def check():
    async def fake_fetch(value):
        if value == "bad":
            raise OSError("example")
        return value.upper()

    results = await fetch_all(["ok", "bad"], fake_fetch, limit=1)
    assert results[0] == ("ok", "ok", "OK")
    assert results[1][1] == "error"
    assert isinstance(results[1][2], OSError)
    try:
        await fetch_all([], fake_fetch, limit=0)
    except ValueError:
        pass
    else:
        raise AssertionError("无效并发上限应被拒绝")


asyncio.run(check())
```

这段例子限制同时进入 fetch 的数量，但仍会为所有输入安排协程；timeout_s 不包含等待信号量的时间。它不实现重试，也不覆盖文字提到的全部调度需求。规模很大时应考虑有界队列、固定消费者或分批提交，明确排队与执行的总时间预算。

### 指数退避与随机抖动

指数退避让重试等待时间逐轮增长，随机抖动让多个调用方不总在同一时刻重试。先确定哪些错误允许重试，再设置次数、单次等待和总时间预算。可以采用 full jitter，例如 `random.uniform(0, min(cap, base * 2**attempt))`，使随机等待也不超过上限。base 是初始等待尺度，cap 是单次等待上限，attempt 从 0 开始计数；这些限制不自动等于整个操作的总时间预算。

有外部副作用的操作，需要明确的幂等保证。若请求结果未知，应先查状态或进入对账流程，不能仅因为收到了超时就重新执行。

### 生产者、消费者与背压

使用有容量上限的 asyncio.Queue，并安排固定数量的消费者。队列满时，生产者按约定等待或拒绝新任务；消费者取出一项后，应在对应处理流程的 finally 中配对调用 task_done，表示该队列项的处理阶段结束；它本身不保证业务执行成功。

关闭时先停止生产，再等待任务完成或取消剩余工作。还要规定消费者异常、任务超时和退出信号的处理方式，避免队列中的任务无人继续处理。

### JSON Lines 流式处理

逐行读取、解析和校验，记录行号及错误。需要生成完整输出文件时，可以先写临时文件，再按约定发布最终结果。

对不可信或超大输入，还应限制单行大小。失败记录可以单独保存，但必须说明它们能否重放，以及重复处理是否会产生副作用。

### 令牌桶限流

保存桶容量、补充速率、当前令牌数和上次更新时间。请求到来时，先根据经过时间补充令牌，再检查并扣减，整个更新过程需要保持一致。

单进程可用锁保护状态；分布式实现需要存储端的原子更新能力。计时通常使用单调时钟，并明确突发容量、拒绝或排队规则，以及不同调用方是否共享额度。

## 系统设计

### 任务持久化与恢复

持久化任务 ID、输入、状态、重试信息和结果。Worker 领取任务时记录租约或其他所有权信息，执行中续期，完成时按状态或版本条件提交结果。

进程崩溃后可以重新领取，但租约过期不代表旧 Worker 一定停止。并发执行和外部副作用仍需幂等、条件更新或其他协调机制；不能只靠任务重试保证“恰好执行一次”。

### API、服务与存储的职责

API 层处理请求协议和身份信息，服务层组织用例，数据访问层管理持久化与事务，后台队列执行需要独立调度的慢任务。Redis 的用途应与可靠性要求匹配，不默认承担全部业务事实。

如果创建数据库记录后必须可靠发布任务，可考虑 Outbox：在同一数据库事务中保存业务记录与待发消息，再由独立流程投递。投递仍可能重复，因此接收方需要幂等处理。缓存还要明确失效和回源规则，并通过数据库约束与测试验证关键状态变化。

### 大文件处理与资源预算

请求入口限制大小与类型，将上传内容写入受控存储，再按需要交给后台任务。处理过程按块读取，并设置时间和资源预算。

状态记录应能区分等待、执行、成功、失败和取消。临时文件、部分产物及下载权限也要纳入清理和验收，不能只验证正常上传路径。

### 下游调用与部分失败

为下游调用设置连接复用、并发限制、超时及重试规则。可以并发执行独立请求，但父请求仍要控制总体时间和取消行为。

聚合结果要保留部分失败，不用默认值掩盖错误。涉及副作用时还需幂等或状态确认；观测数据应能区分等待、调用、重试和结果处理的耗时。

## 性能分析与问题记录

### 性能优化的测量依据

性能优化记录包括原来的现象、测量条件、瓶颈定位、改动和复测结果。指标可以包括延迟分布、吞吐、资源占用与错误率。

优化结论还取决于维护成本与副作用。异步能否改善性能，需要通过等待位置和相同负载下的测量结果判断。

### 故障分析与恢复记录

故障记录包括影响范围、时间线、发现方式、临时处置、根因与修复，判断依据来自日志、指标或可重复实验。

如果涉及超时、重试或重复操作，还应说明是否存在结果未知状态，以及如何恢复。最后记录能改善检测或降低复发概率的措施。

### 从同步脚本到服务

任务的输入规模、并发量、延迟目标、副作用和可靠性要求，共同决定同步接口、后台任务或批处理是否合适。

服务还需要约定结果持久化、失败重试、取消和权限处理。给脚本增加 HTTP 入口，只解决调用方式，并不会自动具备这些能力。

### 可重复交付

可重复交付依赖稳定的环境、配置、入口与验证命令，以及与实际风险匹配的测试、日志、超时和退出流程。部署还涉及构建、发布与回退。

验收至少覆盖正常处理和主要失败路径。是否需要容器、灰度或分布式组件，应由交付环境决定，而不是固定清单。

## 测试验证

### 重试与幂等性测试

用可控的替身模拟断连、超时、重复响应和状态查询，验证程序在每种情况下如何决定重试。若协议支持幂等键，检查同一业务操作是否始终携带同一标识。

还要验证重试预算、退避与最终状态。替身测试无法证明服务提供商的实际协议，因此关键外部语义仍需在相应测试环境验证。

### 取消与副作用的测试

设置两个可控暂停点：一个位于外部操作之前，另一个位于操作已完成但确认信息尚未提交时。分别注入取消或崩溃，观察程序如何记录和恢复。

前者应避免启动尚未授权继续的操作；后者需要处理结果未知或已执行的情况。除了用户看到的状态，还要检查任务、连接和临时资源是否完成清理。
