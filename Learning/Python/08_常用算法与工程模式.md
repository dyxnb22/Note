# 08 常用数据结构的时间与空间开销

数据多了，一次查找扫描多少项、队列积压多少任务、结果占多少内存，就会直接影响性能。下面分别看哈希表、堆、有界队列和流式处理。

## 按数据访问方式选择算法

订单去重用按键查找，最近访问记录要维护顺序，日志统计要计数和排序。先看六种基本做法，完整算法训练另见 [[Learning/CS/算法/01 哈希表与状态映射|哈希表与算法基础]]。

写成函数时，把输入范围、无解或空输入、重复值和返回顺序一并定义清楚。下面各节只展开与算法直接相关的约定。

### 哈希表查找互补值

遍历输入，用字典记录已经遇到的数值及下标。处理当前值 x 时，先查找 target - x；找到后返回两个下标，否则再记录 x。

先查后存，避免同一个元素被使用两次。平均时间复杂度为 O(n)，空间复杂度也是 O(n)。这里找到一组就返回；若要找全所有组合，需要调整结果收集方式。

### 区间合并

先按区间左端点排序，再维护当前合并区间。下一个区间与它重叠时扩展右端点；不重叠时输出当前区间，开始处理新区间。

排序耗时 O(n log n)，扫描耗时 O(n)。判断重叠前，先约定端点是否包含、相邻区间是否合并。

### 无重复子串与滑动窗口

维护一个没有重复字符的窗口，并用字典记录字符最近出现的位置。右端扩展时，如果新字符在窗口内出现过，就将左端移到该位置之后，再更新最大长度。

左端不能回退。每个位置只需处理常数次，时间复杂度为 O(n)；额外空间取决于需要记录的字符种类数。

### LRU 缓存

用字典定位节点，用双向链表维护最近使用顺序。访问或更新后将节点移到最近使用的一端；超过容量时，从另一端移除最久未使用的节点。

平均 get/put 可以做到 O(1)。容量为零、重复更新和并发访问需要单独处理；增加过期时间或统计后，再核算这些操作的复杂度。

### 高频元素与 Top K

Top K 表示取排序最靠前的 K 项；这里按出现频次选择。先统计每个元素的频次，再用大小为 K 的最小堆保留当前频次最高的元素。

设输入长度为 n，不同元素数为 m，且 1 ≤ K ≤ m：统计耗时 O(n)，维护堆通常记作 O(m log K)；包含 K=1 边界时可统一写成 O(m log(K+1))。计数表占用 O(m) 空间。

也可以按频次建桶，代价是额外空间。下面的实现直接给出返回内容、同频排序和 K 越界时的规则。

### 栈与括号匹配

遇到左括号就入栈；遇到右括号时，检查栈顶是否有对应的左括号。处理完输入后，栈应为空。时间复杂度为 O(n)，最坏空间复杂度为 O(n)。

这个算法只匹配指定括号。字符串、转义和注释中的括号未必是代码里的语法括号，需要先按语言规则识别它们。单靠栈还不能解析完整代码。

## Top K 的实现与返回规则

```python
from collections import Counter
from heapq import nsmallest

def topk(items, k):
    if type(k) is not int or k < 0:
        raise ValueError("k must be a non-negative integer")
    counts = Counter(items)
    return nsmallest(k, counts.items(), key=lambda item: (-item[1], item[0]))

assert topk(["B", "A", "B", "A", "C"], 2) == [("A", 2), ("B", 2)]
assert topk([], 3) == []
assert topk(["A"], 0) == []
```

实现接受任何可比较的元素，频次相同时按元素本身排序，k 超过不同元素数时返回全部。内存预算需要计入 Counter 保存的全部不同键。计数表放不下时，考虑外部划分或排序，见[海量数据处理](../Data/海量数据处理.md)。

## 用有界队列控制待处理任务

Semaphore 限制同时进入某段代码的任务数，但调用方可能已经创建了十万个 Task。它不会减少已经创建的任务，等待中的 Task 也占内存。

也可以只启动固定数量的消费者，把待处理项放进有界队列。队列满时，生产者暂停；消费者取走任务、空出位置后，生产者再继续。下游处理不过来，上游就放慢读取，这就是背压。一个生产者和 w 个消费者只需要大约 w+1 个执行任务，队列容量另行限制等待项数量。

最终若把结果收成列表，仍需 O(n) 空间。按输入顺序输出，还可能缓存先完成的后续结果，等待前面的任务。逐项消费或流式写出能减少保留量，但要处理顺序和中途失败。

TaskGroup 将生产者与消费者放在同一组中管理。消费者抛出未处理的普通异常时，TaskGroup 会取消其他分支并等待清理，避免生产者一直卡在满队列上。如果业务允许部分成功，就在分支内部处理预期错误，返回带失败状态的结果，再由聚合器汇总。

## 逐行处理与完整输出

逐行处理通常经历“读取带行号的文本 → 解析 JSON → 校验字段 → 规范化 → 输出”。处理完当前行就可以释放它；不过，整行仍会进入内存，所以单行长度和总输入大小都需要上限。

处理订单号时，先检查字段是否存在、类型是否为字符串，再用 strip 清理首尾空白，检查清理后是否为空。缺字段、类型错误与空字符串分别报告。

如果第一行已输出、第二行解析失败，直接覆盖的正式文件就留下半成品。先写临时文件、全部成功后原子替换，可以让读取者看到完整旧版本或完整新版本。原子替换控制单个文件的可见性，跨文件事务和断电持久性需另行设计。

## 重试等待与速率限制

指数退避和随机抖动可以减少多个调用方同时重试。full jitter 可使用 `random.uniform(0, min(cap, base * 2**attempt))`；attempt 从零开始，cap 控制单次等待，总期限另行计算。重试前先判断：操作能否安全地再做一次，这类错误是否适合重试。业务幂等实现见后端章节。

令牌桶维护容量、补充速率、当前令牌与上次更新时间。使用单调时钟计算 elapsed，先令 tokens=min(capacity, tokens+elapsed*rate)，足够时扣减；读取、补充与扣减要处于同一临界区。

容量控制突发请求量，速率控制长期平均请求速率。同一时刻还没结束的请求数，需要单独限制。

例如容量为 2、速率为每秒 1，初始满桶时允许两次，第三次拒绝；半秒后只有半个令牌，一秒后才能再接受一次。配置限流时分别设置突发容量、平均速率和在途请求上限。

## 复杂度与实际性能

只查一次列表，先建 set 未必划算；反复查询才可能摊薄构建成本。小规模数据还容易受哈希、比较、内存分配和缓存局部性影响。

流式读取后又把全部结果收集进列表，峰值内存仍可能很高。排查时用同一份输入测试，分别记录准备和处理的耗时，以及输入、缓冲和结果各占多少内存，才能看出成本花在哪里。
