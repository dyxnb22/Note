# 专题｜Python 环境与依赖管理

虚拟环境隔离项目依赖，包管理器解析和安装包，依赖声明与锁文件记录需要哪些包、选中了哪些版本。同一个工具可以兼做几项工作。

首次运行可从[Python 阅读路线](00_阅读路线.md)的解释器检查开始。[订单查询案例](案例_订单查询脚本.md)只用标准库，暂时无需安装依赖。需要第三方包时，可先在项目目录使用下面这一套标准工具：

```bash
python3 -m venv .venv
.venv/bin/python -m pip --version
```

以上路径适用于 macOS／Linux，Windows 对应 .venv\Scripts\python.exe。后续用这个解释器执行 -m pip install 包名，就会装入当前项目环境。团队已有工具约定时沿用即可，下面可按工具查阅。

## 解释器、环境与依赖

| 层次 | 解决的问题 | 常见形式 |
|---|---|---|
| Python 解释器 | 用哪个 Python 版本运行 | 系统 Python、pyenv、`uv python`、Conda |
| 环境隔离 | 项目之间如何隔离解释器和已安装包 | `venv`、Conda 环境、uv 创建的 `.venv` |
| 依赖声明 | 项目直接需要哪些包、允许什么版本 | `pyproject.toml`、`requirements.txt`、`environment.yml` |
| 解析与安装 | 根据声明找到兼容包并安装 | `pip`、Conda、uv |
| 锁定与复现 | 如何重建一组确定的依赖版本 | `uv.lock`、`poetry.lock`、锁定版 requirements、Conda 导出/锁定文件 |

同一个工具可能覆盖多个层次。Conda 同时管理环境、包和部分二进制依赖；uv 覆盖解释器、项目、环境和依赖工作流；pip 主要负责安装 Python 包。

## 四种常见工具

### `venv`：标准库虚拟环境

`venv` 为当前 Python 解释器创建隔离环境。它本身不安装 Python 版本，也不负责描述项目依赖或锁定依赖。

Windows 的 cmd 使用 `.venv\Scripts\activate.bat`，PowerShell 使用 `.venv\Scripts\Activate.ps1`。也可以不激活，直接调用环境里的 Python，例如 `.venv/bin/python`。项目应将 `.venv/` 加入 `.gitignore`；不要把一个平台或 Python 版本的虚拟环境目录复制到另一台机器复用。

### `pip`：Python 包安装器

pip 从包索引、源码或本地分发包安装 Python 包。用 `python -m pip` 能明确让当前 `python` 解释器运行对应的 pip，减少“装到另一个 Python 里”的问题。

`requirements.txt` 是供 pip 读取的安装清单，可以固定版本；`pyproject.toml` 声明项目元数据、直接依赖和工具配置。两者用途不同，可以同时存在。

`pip freeze` 只是列出当前装着哪些包，不会替你重新计算一组相互兼容的依赖版本。pip 还提供实验性的 `pip lock`；使用时要核对所用版本的限制，不能把它当作适用于任意平台的通用锁文件。

### Conda：环境、包和二进制依赖管理

Conda 可以创建独立环境，并解析、安装 Python 包及部分非 Python 的二进制依赖；因此在科学计算、数据分析或依赖底层库的项目中比较常见。包来自 Conda channels，channel 混用可能带来兼容性问题。

`environment.yml` 描述环境中的包，便于分享。要严格重建同一套环境，还需固定平台、channel、包构建版本，并选择相应的锁定或导出方式。

```yaml
# environment.yml
name: analysis
channels:
  - conda-forge
dependencies:
  - python=3.12
  - numpy
  - pandas
```

上面的文件用 conda env create --file environment.yml 创建，再用 conda activate analysis 进入。

同一环境需要同时使用 Conda 和 PyPI 包时，通常先安装 Conda 可提供的依赖，再用该环境中的 pip 安装其余包。

Conda 不一定能完整追踪 pip 安装和更新造成的依赖变化，尽量减少两者反复交替更新。依赖关系复杂时，修改声明后重建环境，通常比持续修补旧环境更容易核对。

### `uv`：集成式 Python 项目与工具管理

uv 将解释器、虚拟环境、依赖声明、锁定与运行等流程整合在一起。它同时提供项目级命令和 `uv pip` 这样的低层接口。

`uv pip` 的命令用法与 pip 相似，但不是直接调用 pip。迁移时仍要核对实际使用的选项和行为。

- `pyproject.toml` 保存项目元数据和直接依赖；`uv.lock` 保存解析结果，通常应一并提交。
- 默认 uv run 会检查并按需要更新锁文件、安装运行所需依赖，再执行命令；它通常保留环境中的额外包，与默认精确同步的 uv sync 不同。
- `uv sync --locked` 适合 CI/构建检查：锁文件过期时失败，而不是静默改写锁文件。
- 默认 uv sync 会把环境调整为这次选中的依赖，不在安装范围内的包会被删除。即使某个可选依赖在锁文件中，本次未启用也不会保留。需要保留额外包时使用 --inexact。
- 如果只需要 pip 风格地管理一个已有环境，可使用 `uv pip` 子命令；它和 uv 的项目模式是两套不同的接口。

## 依赖声明与锁定结果的区别

### `pyproject.toml`

Python 项目的标准配置文件之一。`[project]` 可声明名称、支持的 Python 版本和直接依赖；`[tool.*]` 可放各工具配置。它通常表达“项目需要什么/允许什么范围”，而不是某台机器最终解析安装的所有版本。

### `requirements.txt`

供 pip 读取的安装清单，可写宽松的依赖范围，也可逐项固定版本。文件用途要结合内容和生成方式判断；项目元数据由 pyproject.toml 等文件声明。

### 锁文件

锁文件记录解析器选出的版本及必要的来源/平台信息，以便团队和 CI 重建更一致的环境。比如 `uv.lock` 与 `poetry.lock` 由相应工具生成和维护；不要手工编辑锁文件，也不要只提交锁文件而忘了项目声明。更新依赖时应检查锁文件变更并跑测试。

### Conda 环境文件

`environment.yml` 描述 Conda 环境，包含 channels 和依赖；`pyproject.toml` 描述 Python 项目。一个项目可以同时有这两类文件，分别供不同工具使用。

## 常用命令的作用

| 命令形式 | 含义 |
|---|---|
| python -m venv | 为指定解释器创建隔离环境 |
| python -m pip install | 让该解释器对应的安装器处理依赖 |
| uv add | 修改项目依赖声明，并更新选定的具体依赖版本 |
| uv run | 根据项目环境与同步选项执行命令 |
| uv sync --locked | 要求已有锁定结果仍满足声明，否则停止 |
| conda create / env create | 根据包条件或环境描述创建 Conda 环境 |

重建环境时，按保存的声明、锁定结果和平台条件安装，再运行项目的验证命令。

## 如何选择

| 场景 | 可优先考虑 | 理由与注意点 |
|---|---|---|
| 新建常规 Python 应用/服务 | uv 项目模式 | 声明、锁定、环境和运行入口整合；团队约定和部署环境仍优先 |
| 简单脚本、教学或已有传统项目 | `venv` + pip | Python 标准工具链清晰；用 `python -m pip` 确保解释器对应 |
| 科学计算、原生库、多语言依赖 | Conda | 同时处理环境和非 Python/二进制依赖；注意 channel 与 pip 混用 |
| 已采用 Poetry / pip-tools 的仓库 | 延续现有工具 | 除非有明确痛点，不要为“换新”而迁移；让团队只维护一套声明和锁定流程 |

一个项目指定一套主要的声明和锁定流程，避免多个工具分别维护出冲突版本；已有约定时优先沿用。

## 常见错误

- 用 `pip install` 后才发现装进了另一个解释器；用 `python -m pip --version` 检查目标路径。
- 把虚拟环境目录当作可移植交付物；应提交声明/锁文件，在目标机器重新创建环境。
- 只看文件名就判断 `requirements.txt` 陈旧或已经锁定；实际用途要看内容和生成流程。
- 用 `pip freeze` 代替依赖解析锁定；它只列出当前安装内容。
- 在 Conda 和 pip 之间反复交替更新同一环境；先约定主要由哪套工具计算依赖版本，减少两者轮流修改环境。
- 只固定依赖版本，却不声明 Python 版本、操作系统/架构和测试命令；这些也会影响能否重现。

## 修改依赖声明时，锁文件何时失效？

例如原来锁定的是 1.5，新声明要求 >=2，旧版本就不再满足要求，锁文件需要更新；要求锁文件有效的检查也应失败。放宽范围后，旧版本则可能仍然可用。是否需要更新，不能只看范围文字有没有改，还要按工具的规则判断。

更新锁文件后，查看直接和传递依赖改了哪些版本，用相应工具同步环境，并在目标解释器与平台验证实际安装结果。
