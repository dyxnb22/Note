# 专题｜Python 环境与依赖管理

> 本专题补充 [[04_工程基础]] 中的虚拟环境与依赖管理。目标是先分清职责，再选工具；不是要求每个项目都迁移到同一套工具。

## 先分清几个层次

| 层次 | 解决的问题 | 常见形式 |
|---|---|---|
| Python 解释器 | 用哪个 Python 版本运行 | 系统 Python、pyenv、`uv python`、Conda |
| 环境隔离 | 项目之间如何隔离解释器和已安装包 | `venv`、Conda 环境、uv 创建的 `.venv` |
| 依赖声明 | 项目直接需要哪些包、允许什么版本 | `pyproject.toml`、`requirements.txt`、`environment.yml` |
| 解析与安装 | 根据声明找到兼容包并安装 | `pip`、Conda、uv |
| 锁定与复现 | 如何重建一组确定的依赖版本 | `uv.lock`、`poetry.lock`、锁定版 requirements、Conda 导出/锁定文件 |

工具会跨越多个层次：Conda 同时管环境和包解析，也能管理非 Python 的二进制依赖；uv 可管理 Python 版本、项目、环境、依赖和锁文件；pip 的主要职责是安装 Python 包。它们不是严格一对一的替代品。

## 四种常见工具

### `venv`：标准库虚拟环境

`venv` 为当前 Python 解释器创建隔离环境。它本身不安装 Python 版本，也不负责描述项目依赖或锁定依赖。

```bash
python -m venv .venv
source .venv/bin/activate   # macOS / Linux
python -m pip install requests
```

Windows 激活命令是 `.venv\Scripts\activate`。也可以不激活，直接调用环境里的 Python，例如 `.venv/bin/python`。项目应将 `.venv/` 加入 `.gitignore`；不要把一个平台或 Python 版本的虚拟环境目录复制到另一台机器复用。

### `pip`：Python 包安装器

pip 从包索引、源码或本地分发包安装 Python 包。用 `python -m pip` 能明确让当前 `python` 解释器运行对应的 pip，减少“装到另一个 Python 里”的问题。

```bash
python -m pip install requests
python -m pip install -r requirements.txt
python -m pip show requests
```

`requirements.txt` 仍然有用，不是废弃格式：它常用于给 pip 提供安装清单，也可以记录固定版本。它和 `pyproject.toml` 侧重点不同：后者适合声明项目元数据与直接依赖，前者通常是安装输入。`pip freeze` 只是报告当前环境已安装的包，不会计算或验证锁定方案；新版 pip 还提供实验性的 `pip lock`，其生成结果目前只保证适用于当前 Python 版本和平台，使用前要确认所用 pip 版本及其限制。

### Conda：环境、包和二进制依赖管理

Conda 可以创建独立环境，并解析、安装 Python 包及部分非 Python 的二进制依赖；因此在科学计算、数据分析或依赖底层库的项目中比较常见。包来自 Conda channels，channel 混用可能带来兼容性问题。

```bash
conda create -n demo python=3.12 numpy
conda activate demo
python -c "import numpy; print(numpy.__version__)"
```

环境可以用 `environment.yml` 描述并分享。环境文件让别人知道要创建哪些包，但若要求严格一致，还要考虑平台、channel、包构建版本和相应的锁定/导出方式。

```yaml
# environment.yml
name: analysis
channels:
  - conda-forge
dependencies:
  - python=3.12
  - numpy
  - pandas
```

可用 `conda create --file environment.yml` 创建环境，再用 `conda activate analysis` 进入；较早的项目也常见 `conda env create --file environment.yml`。

若同一环境必须同时使用 Conda 和 PyPI 包，通常先用 Conda 安装可用依赖，再在隔离环境里用 pip 安装剩余包；pip 安装的包可能不在 Conda 的依赖记录中。避免反复交替运行 Conda 和 pip 修改同一个环境，复杂变更时重建环境通常更稳妥。

### `uv`：集成式 Python 项目与工具管理

uv 是一个快速的 Python 工具，覆盖项目依赖、虚拟环境、锁文件和 Python 版本管理等工作流。它既有更高层的项目命令，也有 `uv pip` 这类与常见 pip 工作流兼容的低层接口；`uv pip` 不会调用 pip 本身，兼容行为也不等于逐项完全相同。

```bash
uv init
uv add requests
uv run python -c "import requests; print(requests.__version__)"
uv lock
uv sync
```

- `pyproject.toml` 保存项目元数据和直接依赖；`uv.lock` 保存解析结果，通常应一并提交。
- `uv run` 会确保项目环境与声明/锁文件同步后再运行命令。
- `uv sync --locked` 适合 CI/构建检查：锁文件过期时失败，而不是静默改写锁文件。
- 默认 `uv sync` 会精确同步环境，移除锁文件里没有的额外包；不要把它当成对已有环境无副作用的普通安装命令。
- 如果只需要 pip 风格地管理一个已有环境，可使用 `uv pip` 子命令；它和 uv 的项目模式是两套不同的接口。

## 声明文件和锁文件不是一回事

### `pyproject.toml`

Python 项目的标准配置文件之一。`[project]` 可声明名称、支持的 Python 版本和直接依赖；`[tool.*]` 可放各工具配置。它通常表达“项目需要什么/允许什么范围”，而不是某台机器最终解析安装的所有版本。

### `requirements.txt`

pip 可消费的安装清单。可以是较宽松的安装需求，也可以逐项固定版本；文件的确切含义取决于内容和生成方式，不应简单视为过时格式，也不自动等同于项目元数据。

### 锁文件

锁文件记录解析器选出的版本及必要的来源/平台信息，以便团队和 CI 重建更一致的环境。比如 `uv.lock` 与 `poetry.lock` 由相应工具生成和维护；不要手工编辑锁文件，也不要只提交锁文件而忘了项目声明。更新依赖时应检查锁文件变更并跑测试。

### Conda 环境文件

`environment.yml` 描述 Conda 环境及其 channels/依赖。它与 PyPI 项目的 `pyproject.toml` 不完全同义；项目也可以有两类文件，分别服务不同工具和需求。

## 三种常见工作流

### 新建一般 Python 应用：项目声明 + uv

```bash
uv init
uv add fastapi
uv add --dev pytest
uv run python -m pytest
```

将 `pyproject.toml`、`uv.lock` 提交版本控制。CI 中用锁定模式同步，例如 `uv sync --locked`，再运行同一套测试和检查命令。

### 简单脚本或既有 pip 项目：venv + pip

```bash
python -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt
```

使用时确认 requirements 清单表达的目标：它可能只是顶层依赖，也可能是固定环境快照。不要把一次 `pip freeze` 输出误认为经过审查的依赖策略。

### 科学计算或需要原生库：Conda

```bash
conda create -n analysis python=3.12 numpy pandas
conda activate analysis
```

将可由 Conda 提供的核心包优先放入环境文件；确有 PyPI 专属依赖再谨慎使用 pip。需要严格复现时，确认导出方式是否适合目标平台，而不只看环境文件是否存在。

## 如何选择

| 场景 | 可优先考虑 | 理由与注意点 |
|---|---|---|
| 新建常规 Python 应用/服务 | uv 项目模式 | 声明、锁定、环境和运行入口整合；团队约定和部署环境仍优先 |
| 简单脚本、教学或已有传统项目 | `venv` + pip | Python 标准工具链清晰；用 `python -m pip` 确保解释器对应 |
| 科学计算、原生库、多语言依赖 | Conda | 同时处理环境和非 Python/二进制依赖；注意 channel 与 pip 混用 |
| 已采用 Poetry / pip-tools 的仓库 | 延续现有工具 | 除非有明确痛点，不要为“换新”而迁移；让团队只维护一套声明和锁定流程 |

核心原则：**先看项目现状、依赖类型、部署目标和团队工具链，再选工具。**不要在同一项目里让多个工具同时成为依赖声明/锁文件的权威来源。

## 常见错误

- 用 `pip install` 后才发现装进了另一个解释器；用 `python -m pip --version` 检查目标路径。
- 把虚拟环境目录当作可移植交付物；应提交声明/锁文件，在目标机器重新创建环境。
- 认为 `requirements.txt` 必然陈旧或必然是锁文件；检查它的内容、用途和生成流程。
- 认为 `pip freeze` 就等于依赖解析锁定；它只列出当前已安装内容。
- 在 Conda 和 pip 之间反复交替更新同一环境；尽量确定一个主要解析来源。
- 只固定依赖版本，却不声明 Python 版本、操作系统/架构和测试命令；这些也会影响能否重现。
