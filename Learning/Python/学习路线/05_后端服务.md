# 05 后端服务

> 前提同 01。这章讲用 Python 写出能扛住的服务。

## HTTP 客户端

```python
import httpx

client = httpx.Client(
    timeout=httpx.Timeout(5.0, connect=2.0),
    limits=httpx.Limits(max_connections=100),
)
r = client.get(url)
r.raise_for_status()
```

- 必须显式设置:连接超时、读超时、总超时、连接池上限。
- 复用客户端(连接池),不要每次请求都新建;服务关闭时释放连接。
- 重试只对幂等操作和明确的瞬时错误(连接失败、502 / 503 / 504、429),带退避 + 抖动,尊重 `Retry-After`。
- **超时不代表对方没执行**;有副作用的调用要用幂等键 + 查询或对账。
- 响应要设大小上限,别把无限流读进内存。
- `requests` 是同步阻塞;异步服务里用 `httpx.AsyncClient`。复用长生命周期 Client,调用 `raise_for_status()` 或统一映射状态码,并区分网络错误、非 2xx 和 JSON 解析失败。

## FastAPI

```python
from fastapi import FastAPI, Depends

app = FastAPI()

@app.get("/users/{uid}")
async def get_user(uid: int, svc: UserService = Depends(get_service)):
    ...
```

- 路径 / 查询 / 请求体 / 头自动解析并校验,校验失败返回 422;422 只说明没通过输入校验,不代表业务授权、资源存在或状态迁移成功。
- 依赖注入用 `Depends`;资源生命周期用 `lifespan`(不要用旧的 `on_event`)。请求级资源在请求结束释放,应用级客户端/连接池在启动时创建、关闭时释放,**不要在每个 handler 里创建**。
- 同步 `def` 端点跑在线程池,`async def` 跑在事件循环。**在 `async def` 里做阻塞 I/O 会卡住整个服务。**
- 错误处理:业务异常映射成统一错误体,不要把堆栈泄漏给客户端。
- 鉴权放在依赖层,业务层再做授权判断。

## Pydantic / DTO 分层

- Pydantic 负责**外部数据的结构与类型校验**;校验通过后再转成领域命令。
- 请求 DTO、响应 DTO、领域模型分开,不要一个类走到底。
- Schema 合法 ≠ 有权限、资源存在、副作用成功。
- v2 用 `model_validate` / `model_dump`;直接吃 JSON 用 `model_validate_json`。
- 校验非模型类型用 `TypeAdapter(list[User]).validate_python(data)`。
- 注意 strict 模式与类型强转的边界,别让 `"1"` 静默变成 `1`。

## 数据库

- 连接池要设上限和超时;池上限和并发模型一起算。池不是越大越好,过大可能把应用排队转移成数据库过载;观察活跃连接、等待时间、慢查询和错误率。
- 事务边界画在应用层,一个用例一个事务;不要在循环里逐条提交。事务中避免不可控网络调用和长时间等待;提交后再发事件,或用 Outbox 衔接。
- 跨服务调用不能假设共享一个事务,必须用幂等、状态机、补偿或对账。
- 长事务会锁资源并膨胀 MVCC,尽量短。
- ORM 方便,但要注意 N+1、隐式全表扫描、会话生命周期。
- SQLite 适合单机、低并发、读多写少;并发写要开 WAL,并明确锁模式、事务边界、忙等待、迁移和写入者数量;异步包装库不会让写锁消失。

## Redis 与缓存

- 适合:缓存、限流计数、简单队列。
- 不适合:强一致数据、复杂查询、大对象;关键事实和必须长期可靠的任务状态不应只放 Redis。
- 缓存要想清三件事:过期策略、更新 / 失效时机、击穿与雪崩防护(空值缓存、随机过期、互斥重建)。
- 更新策略(Cache Aside、写穿、失效通知)要匹配数据新鲜度要求;更新失败不能让缓存和数据库永久分叉,关键数据应有版本、重试、对账或直接回源。
- 缓存与数据库只能做到最终一致,别期望强一致。

## 后台任务与队列

- 轻量用 `asyncio.Task`;要持久化和重试用 Celery / RQ / Arq / Dramatiq;CPU 密集考虑进程池。选择看任务是否必须可靠执行、是否有副作用、队列规模和运维成本。
- 任务**必须幂等**:至少一次投递意味着可能重复执行。
- 任务要有稳定 ID、持久化状态、租约/心跳、超时、重试预算;Worker 崩溃后靠租约过期或可验证 Checkpoint 恢复,未知副作用先查询再重试。
- 任务表记录状态,失败可重试、可对账。
- 别用 `BackgroundTasks` 扛重要业务,它不保证执行。
- 有界队列 + 固定 worker:队列满时阻塞、拒绝或降级,任务带 deadline;不要用无界队列掩盖下游过慢。

## SSE 与 WebSocket

- SSE:服务端到客户端单向事件流,适合进度 / token 推送,基于 HTTP,自带重连。
- WebSocket:双向会话,适合交互。
- 两者都要处理:事件 ID、断线重连、去重、心跳、取消、最终状态落库;断线可用 Last-Event-ID 或任务状态续接。
- 流结束前不能把半截文本当最终成功,最终结果要持久化并经过 schema / 业务校验。
- 客户端断连要能中断上游调用,别让模型 / 下游白跑。

## 鉴权与安全边界

- 认证(你是谁)和授权(你能干什么)分开。
- 不要把外部输入直接拼进 SQL / shell / 正则 / 模板;禁止对不可信输入用 `eval` 或不安全反序列化。
- 限制请求大小、字段深度、文件类型、正则复杂度和解析时间。
- 路径校验与防穿越的做法见[03 标准库](./03_标准库.md);安全上还要考虑 TOCTOU。
- 子进程用列表参数:`subprocess.run([...], shell=False)`。
- 供应链:锁版本、扫漏洞、最小权限。
