# 05 后端服务

## HTTP 客户端

```python
import httpx


# 内存响应桩，不访问网络；生产中复用客户端，并按实际服务设置连接池。
def respond(request: httpx.Request) -> httpx.Response:
    return httpx.Response(200, json={"ok": True})


with httpx.Client(
    transport=httpx.MockTransport(respond),
    timeout=httpx.Timeout(5.0, connect=2.0),
    limits=httpx.Limits(max_connections=100),
) as client:
    response = client.get("https://example.test/status")
    response.raise_for_status()
    assert response.json() == {"ok": True}
```

- 明确连接、读、写、池等待和端到端预算；HTTPX 的分阶段超时不自动等于总 deadline。
- 复用客户端(连接池)，不要每次请求都新建；服务关闭时释放连接。
- 重试需要同时满足两项条件：操作可安全重复，错误也有恢复可能。连接失败、429 或部分 5xx 可作为候选，仍需结合协议及错误含义判断，并设置退避、随机抖动、次数与总时间预算；服务提供 Retry-After 时按其规则处理。
- **超时不代表对方没执行**；有副作用的调用要用幂等键 + 查询或对账。
- 读取响应时应考虑大小上限；对持续输出或大响应，使用适当的流式处理，避免无限增长的内存占用。
- `requests` 是同步阻塞；异步服务里用 `httpx.AsyncClient`。复用长生命周期 Client，调用 `raise_for_status()` 或统一映射状态码，并区分网络错误、非 2xx 和 JSON 解析失败。

## Web 框架(FastAPI)

- 路径 / 查询 / 请求体 / 头的校验失败返回 422；422 只说明没通过输入校验，不代表业务授权、资源存在或状态迁移成功。
- async def 端点里直接执行耗时阻塞 I/O 会阻碍对应事件循环调度；同步 `def` 端点跑线程池，受线程池容量限制。
- 可以复用的客户端和连接池，通常在应用启动时创建、关闭时释放。临时客户端也应使用上下文管理器或显式关闭。
- 错误处理：业务异常映射成统一错误体，不要把堆栈泄漏给客户端。
- 鉴权放在依赖层，业务层再做授权判断。

## Pydantic 与数据传输对象（DTO）

- Pydantic 可校验外部数据的结构与类型。校验后的模型可以直接用于简单逻辑；输入协议与内部规则不同、需要隔离时，再转换为内部对象。
- 当请求、响应和内部规则确实不同，分别定义 DTO 与领域模型；简单场景不必复制多套相同结构。DTO 契约(别名、额外字段策略、序列化开关)决定对外形态。
- 数据通过结构校验，只能说明符合声明的规则；仍需检查权限、资源状态和操作结果。
- 按接口明确转换与未知字段策略；严格模式和 extra="forbid" 按实际边界选择。对外校验错误可包含安全的字段位置、错误码与说明，避免直接透传内部消息或敏感原始输入；校验非模型类型用 `TypeAdapter`。

## 数据库

事务用于将一组相关更新作为一个整体提交或回滚；连接池则复用连接并限制资源占用。两者解决的问题不同。下面的要点用于设计边界，具体行为仍需结合数据库实现。

- 连接池要设上限和超时；池上限和并发模型一起算。池不是越大越好，过大可能把应用排队转移成数据库过载；观察活跃连接、等待时间、慢查询和错误率。
- 根据用例的一致性要求确定事务边界。需要一起成功或失败的更新应放在同一事务中；避免在事务内等待不可控的网络调用。数据库变更与消息发布需要一致时，可采用 Outbox 等机制。
- 跨服务调用不能假设共享一个事务，必须用幂等、状态机、补偿或对账。
- 长事务可能长期持有锁或快照，使其他操作等待，并阻碍旧版本数据回收；具体影响取决于数据库与隔离级别，应避免不必要地延长事务。
- ORM 将对象操作映射为数据库操作，仍需观察实际 SQL。N+1 是一次读取列表后又逐项额外查询；也要关注缺少索引导致的扫描，以及会话何时提交、回滚与关闭。
- SQLite 常用于本地与嵌入式存储；WAL 可改善部分读写并发，但并非所有场景都必须开启，也不会让写入者同时提交。需明确事务、忙等待和备份方式；异步包装库不会消除写锁。

## Redis 与缓存

- 适合：缓存、限流计数、简单队列。
- Redis 的持久性与故障切换语义取决于配置。关键状态不能只因“已经写入 Redis”就视为永久可靠；需要结合持久化、复制、备份与丢失容忍度设计。复杂关联查询或大对象存取也应评估成本。
- 缓存穿透是反复查询不存在的数据，可用短期空值缓存等方式缓解；击穿是热点键失效后大量请求同时回源，可合并重建；雪崩是大量键或缓存服务同时失效，可通过分散过期时间、限流与降级减轻影响。
- 更新策略(Cache Aside、写穿、失效通知)要匹配数据新鲜度要求；更新失败不能让缓存和数据库永久分叉，关键数据应有版本、重试、对账或直接回源。
- 独立更新缓存和数据库通常存在一致性窗口；需要更强保证时必须额外协调，不能假设简单双写就有原子性。

## 后台任务与队列

- 轻量用 `asyncio.Task`；要持久化和重试用 Celery / RQ / Arq / Dramatiq；CPU 密集考虑进程池。选择看任务是否必须可靠执行、是否有副作用、队列规模和运维成本。
- 至少一次投递意味着可能重复执行；需用幂等操作、去重或业务状态约束控制重复副作用，不能把任意操作假定为可安全重试。
- 需要可靠恢复的任务通常有稳定 ID、持久化状态、超时和重试预算。Worker（后台执行任务的进程或组件）可以用租约或心跳记录任务归属，用检查点保存可恢复进度；外部副作用未知时应先确认状态。轻量进程内任务不必具备完整调度系统。
- 需要跨进程重启保留、恢复或重试的任务，不应只依赖 `BackgroundTasks`。它适合当前进程中的轻量后台工作。
- 有界队列 + 固定 worker：队列满时阻塞、拒绝或降级，任务带 deadline；不要用无界队列掩盖下游过慢。

## SSE 与 WebSocket

- SSE 是服务端到客户端的 HTTP 事件流；浏览器 EventSource 提供重连能力，但普通 HTTP 流客户端不自动拥有相同语义，仍需设计事件 ID 和恢复。
- WebSocket：双向会话，适合交互。
- 需要恢复的事件流通常设计事件 ID、重连与去重；长连接还应考虑心跳、超时与关闭。浏览器 EventSource 可用 Last-Event-ID 续接 SSE，WebSocket 则需应用自行设计恢复协议，不能直接套用同一机制。
- 若传输的是任务的中间结果，应区分进度事件与最终成功事件；是否持久化及如何校验，由该任务的可靠性要求决定。普通实时消息不一定需要最终结果落库。
- 客户端断开后，应按业务约定取消不再需要的上游调用，或将仍需完成的任务交给独立调度流程，避免无意义的持续消耗。

## 鉴权与安全边界

- 认证(你是谁)和授权(你能干什么)分开。
- 不要把外部输入直接拼进 SQL / shell / 正则 / 模板；禁止对不可信输入用 `eval` 或不安全反序列化。
- 限制请求大小、字段深度、文件类型、正则复杂度和解析时间。
- 文件访问要限制在允许的目录范围内。路径检查与实际使用之间，文件或符号链接仍可能变化；这种检查与使用之间的竞争称为 TOCTOU。
- 子进程用列表参数：`subprocess.run([...], shell=False)`。
- 供应链：锁版本、扫漏洞、最小权限。
