# 05 Python 后端服务的请求、状态与事务

取消订单看似只是一次请求，实际可能碰上并发修改、提交后超时和客户端重试。下面跟着这次请求，看身份、状态和事务怎样配合。

## 请求进入后的四类检查

参数校验检查数据结构与取值，身份认证确定调用者，授权限制可操作的资源，业务规则检查当前状态是否允许该动作。

取消订单时，既要检查版本号格式，也要检查订单归属和当前状态。租户与角色从可信身份取得，请求体中的 tenant 不作为授权依据。

## 同步与异步端点

异步端点在事件循环上执行，适合等待异步数据库和 HTTP 客户端。耗时同步调用会阻塞这个事件循环；把 def 改成 async def 不会自动改变底层库的行为。

FastAPI 的普通同步路由通常在线程池执行，能够把阻塞操作移出事件循环，但仍受线程池、数据库连接和下游容量限制。扩大线程数可能只是把排队转移到数据库。框架细节见 [FastAPI 专题](专题_FastAPI.md)。

## 用 HTTP 状态码区分失败

| 情况 | 常见状态码 | 含义 |
|---|---|---|
| 缺失或无效凭证 | 401 | 需要提供有效凭证；服务器用 WWW-Authenticate 告知认证方式 |
| 身份有效但不允许操作 | 403 | 当前授权不足 |
| 当前可访问范围内找不到资源 | 404 | 资源不存在，或服务按约定隐藏其存在性 |
| 输入不符合接口约束 | 422 | FastAPI 常用的请求校验失败状态 |
| 版本或业务状态发生冲突 | 409 | 重新读取状态，再决定是否继续原操作 |
| 服务内部发生未处理错误 | 500 | 服务未能按约定完成处理 |

业务层用 NotFound、Conflict 等固定的异常类型或结果类型表示失败，HTTP 入口再转成状态码和错误体。调用方据此补凭证、改参数或重试，无需解析提示文字。

## 幂等：让重试对应同一次操作

客户端超时时，服务端可能已经提交了变更。例如订单已取消，回执却在网络中丢失；此时重新发起一笔操作，就可能重复执行。

业务操作使用稳定 ID，将同一意图的重试关联到同一记录。同号同参数返回原结果，同号不同参数返回冲突。模型重新生成调用 ID，不代表业务上又有了一次新操作。

| 到达顺序 | 订单状态 | 操作记录 | 应返回的结果 |
|---|---|---|---|
| 首次取消前 | pending，版本 1 | 无 | 检查前置条件 |
| 首次取消提交后 | cancelled，版本 2 | 保存原输入与回执 | 返回取消结果 |
| 相同操作重试 | cancelled，版本 2 | 已存在且输入一致 | 返回原回执，不再增加版本 |
| 相同操作 ID 换参数 | 以当前事实为准 | 输入不同 | 返回操作冲突 |

## 将业务更新与幂等记录一起提交

订单已更新，操作记录却没保存下来，重试时就难以判断原请求是否完成。反过来，只留下成功记录却没修改订单，又会报出假成功。

同一数据库事务可以让业务变更与操作记录一起提交或回滚。以 SQLite 为例，BEGIN IMMEDIATE 提前取得写事务；读取旧操作、检查订单版本、修改状态、保存回执可以位于同一事务中。SQLite 同一时刻只允许一个写事务。

事务只覆盖其管理的资源。数据库提交与发送邮件通常不在同一事务，常见设计是将待发送事件与业务变更一起保存，再由发送者处理重复与失败。这也是 Outbox 模式的基本出发点。

## 连接生命周期与事务范围

`sqlite3.Connection` 配合 with 使用时，正常退出代码块会提交事务，异常退出会回滚，但不会关闭连接，需要另外关闭。使用连接池时，“关闭”又可能只是把连接归还池中。

在事务里等待模型回复或远程接口响应，会延长锁占用。排查慢请求时，区分等待连接、执行事务和释放连接这几个阶段。使用 ORM 后，也要检查事务范围、锁竞争和 N+1 查询。

## 复用 HTTP 客户端并设置总期限

HTTP 客户端通常持有连接池、认证和超时配置。复用它能减少建连成本，应用退出时再统一释放资源。

连接、读取、写入和等待连接池各有超时，任务总期限还要覆盖排队、请求、重试与清理。例如三次请求各允许五秒，单是请求等待就可能累计十五秒。

遇到 429、暂时性 5xx 或断连时，结合接口约定、操作可重复性、Retry-After 与剩余预算决定是否重试。

## 后台任务、缓存与流式响应

进程内后台任务在响应后运行，重启后可能丢失。需要在重启后继续执行的任务，先持久保存任务 ID 和执行状态，再交给 Worker。接口返回“已接收”时，业务可能还没开始。

缓存可以减少重复读取，但要约定哪些版本可以复用、何时失效。只依赖 TTL 时，状态变化后仍可能读到尚未过期的旧值。例如订单已经取消，缓存却仍返回 pending，用户就可能误以为取消没有生效。

SSE 适合服务端持续发送事件，WebSocket 适合双向消息。重连时，用状态快照、事件序号或游标恢复进度，并继续使用原来的任务 ID，避免另建任务而重复执行。

浏览器原生 EventSource 不能像普通 HTTP 客户端那样随意设置认证请求头。认证方式需要按它实际支持的接口设计，不能直接照搬依赖自定义请求头的做法。

## 成功、冲突与结果未知

订单已取消并得到确认，可以报成功；版本或状态不满足前提，返回冲突；提交后没收到回执，则暂记结果未知。未知时先查原操作，并告诉用户还有什么没确认。
