# 04 工程基础

## 虚拟环境与依赖

- 开发依赖应装在项目隔离环境里，例如 `python -m venv .venv`；不要依赖全局环境。
- 项目元数据和直接依赖写在 `pyproject.toml`；requirements 文件仍适用于 pip 安装清单、部署输入或简单脚本，不是废弃格式。
- 锁文件记录依赖解析结果，用于在不同机器上重建一致环境；应按所用工具提交对应锁文件。
- `uv`、`poetry`、`pip-tools` 等会覆盖不同的项目、解析、锁定和安装工作流，不只是“更快的 pip”。

## 项目结构

程序较小时，一个入口文件加几个功能模块就足够。文件增多后，可以按职责组织：接收请求、执行规则、访问外部系统，分别放到不同模块。这样修改数据库或请求协议时，不必同时修改所有计算逻辑。

```text
src/app/
  main.py        # 创建对象、连接各模块并启动程序
  api/           # 读取请求、组织响应、转换错误
  domain/        # 保存业务规则与核心数据概念
  infra/         # 访问数据库、文件和外部 HTTP 服务
tests/
```

启动时创建数据库客户端，再把它交给需要读写数据的对象，这个集中装配依赖的位置常称为“组合根”。它是一个职责名称，不要求额外定义某种基类。

“领域层”指描述业务规则的部分。例如计算费用的规则通常不需要知道请求来自 HTTP，或记录存在哪一种数据库。把这些细节留在外层，可以单独运行和验证规则。

模块依赖指谁需要导入谁。核心规则不导入具体框架或数据库代码时，外部实现较容易替换。简单程序也可以直接调用具体对象；只有需要隔离实现时，才引入接口。

Service 通常组织一项完整操作，Client 封装外部服务调用，Repository 封装某类数据的存取。这些名称表达职责，不意味着每个程序都必须同时具备三层对象。

## 配置与密钥

- 配置从环境变量读；用 `pydantic-settings` 做校验和默认值。
- 密钥不进仓库、不进日志、不进镜像；`.env` 只用于本地并写进 `.gitignore`。
- 启动时检查必要配置。缺少必填项或值不合法时，立即报告原因，避免等到处理请求时才暴露问题。

## 日志

- 用标准库 `logging`；库代码只 `getLogger(__name__)`，不在库里调 `basicConfig`。
- 结构化日志用固定字段记录信息，例如 JSON 中的事件名、级别和耗时。服务处理请求时可加入 request_id 或 trace_id，便于关联同一次请求；普通脚本不必虚构请求标识。
- DEBUG 记录调试细节，INFO 记录正常运行事件，WARNING 表示异常迹象但程序仍可继续，ERROR 表示某项操作失败。是否告警还需结合影响、频率和服务目标，不能只看级别。
- CLI 可以用 print 输出用户需要的结果；诊断信息使用 logging，避免污染机器消费的标准输出。不要把密钥和整段敏感数据打进日志；完整 token、Prompt 和用户内容也不无边界写入日志，先脱敏。

## 从一个普通函数开始验证

下面的例子只使用标准库，保存为独立脚本后可直接运行：

```python
import unittest


def normalize_name(text: str) -> str:
    result = text.strip()
    if not result:
        raise ValueError("name must not be blank")
    return result


class NameTests(unittest.TestCase):
    def test_trims_whitespace(self):
        self.assertEqual(normalize_name("  小明  "), "小明")

    def test_rejects_blank(self):
        with self.assertRaises(ValueError):
            normalize_name("   ")


if __name__ == "__main__":
    unittest.main()
```

先用正常和异常两条路径说明函数的预期行为，再决定是否需要其他测试工具。`unittest` 属于标准库，`pytest` 需要单独安装。

示例中的 assertEqual 比较结果，assertRaises 检查指定异常是否发生；两者由 unittest 提供。普通 Python 的 `assert 条件` 语句则可能被 `python -O` 移除，不能用来代替外部输入校验或授权检查。

## 测试

- pytest：`test_*` 函数 + `assert`；`conftest.py` 放共享 fixture。
- fixture 管理资源生命周期，`yield` fixture 做前后清理。
- 单元测试关注小范围行为，集成测试验证多个真实组件协作，端到端测试覆盖完整使用路径；契约测试关注接口约定，属于另一种划分角度。响应桩可隔离 HTTP 调用，但不能证明真实网络集成正确。
- 测试替身有不同用途：Stub 提供预设结果，Fake 提供简化但可工作的实现，Mock 记录和验证交互。仅验证“调用过某方法”，不能证明最终结果正确。
- 时间、随机、并发要可控：注入时钟 / `freezegun`、固定随机种子；必要时用事件屏障、虚拟时钟和故障注入让竞态可重复，测不变量而不是脆弱的 `sleep`。
- 异步测试用 `pytest-asyncio`；HTTP 用 `httpx.MockTransport` / `respx`。Mock 适合精确控制状态码、断连、超时和响应顺序；TLS、连接池和真实协议仍需要少量真实集成测试，Mock 不能证明线上 Provider 的所有语义。
- 异步测试优先等待明确的事件或状态条件，避免用固定休眠时间猜测任务何时结束。
- 断言要覆盖：调用次数、退避上限、超时/取消后任务结束与资源释放、异常没有被吞；对已发出副作用的调用，还要测响应丢失、重复投递和对账路径。
- 不要把所有内部实现细节固定成测试，也不要用 Mock 掩盖真实协议、权限和超时问题。

进阶三种测试：

- **契约测试**：验证对外接口的约定(请求 / 响应形状、错误码)不漂移，不测具体实现。
- **快照或基准输出测试（golden test）**：将经过确认的结果保存为基线，后续输出与它比较。更新基线前仍需确认行为变化是预期的，不能把“更新后测试通过”当作正确性的证明。
- **属性测试**(`hypothesis`)：声明不变量让工具生成用例，适合边界和往返性质，例如“解码(编码(x)) 等于 x”。

## 代码质量

- `ruff`：格式 + lint(替代 flake8 / isort / black)。
- mypy 或 pyright 做静态类型检查。pyproject.toml 可以保存目标 Python 版本、依赖和工具配置；运行命令由脚本或 CI 配置保存，例如 `python -m mypy src`。有意忽略的检查应说明原因。
- `import-linter`：约束模块依赖方向(比如领域层不许 import 基础设施)。
- 根据规模选择格式、类型和依赖边界检查并纳入 CI；import-linter 不是所有小脚本的前置要求。各类检查互不替代：类型正确不代表依赖方向正确，格式正确不代表运行时输入合法。

## 打包与入口

- 安装构建工具 build 后，`python -m build` 根据项目的构建配置生成 wheel（可安装分发包）和 sdist（源码分发包）。`[project.scripts]` 将命令行名称映射到 Python 可调用对象，安装项目后才能使用对应命令。
- CLI 退出码也是契约：0 成功，非 0 表示失败；是否进一步区分原因，由命令行工具约定，而非所有程序通用。
