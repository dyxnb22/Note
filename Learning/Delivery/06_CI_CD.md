# CI_CD

CI/CD把构建、验证与发布步骤保存为可重复执行的流程，减少遗漏和环境差异。

## CI 和 CD 分别是什么

- `CI`：Continuous Integration，持续集成
  目标是让代码一提交就自动跑构建、测试、静态检查，尽早发现问题
- `CD`：Continuous Delivery / Deployment，持续交付 / 持续部署
  目标是让通过校验的版本能够稳定地交付到测试或生产环境

一句话理解：

- `CI` 关注“代码合进来后是否仍然健康”
- `CD` 关注“健康的版本能否稳定发布出去”

## 一条典型流水线长什么样

```text
push / pull request
-> install dependencies
-> lint
-> unit test
-> build
-> package image / artifact
-> deploy to staging
-> smoke test
-> manual approval or auto deploy
-> production
```

## 为什么需要 CI/CD

- 减少“我本地没问题”的不确定性
- 降低手工上线漏步骤的概率
- 让构建和发布过程可审计、可复现
- 把测试和发布前移，问题更早暴露
- 团队协作时减少口头约定

## CI 常见内容

### 代码质量检查

- `lint`：代码风格、明显错误
- `format check`：格式统一
- `type check`：静态类型检查
- `security scan`：依赖漏洞、密钥泄露检查

### 测试

- 单元测试：验证局部逻辑
- 集成测试：验证模块协作
- API / E2E 测试：验证完整链路

### 构建产物

- Java：`jar` / `war`
- Node：构建后的前端静态资源
- Python：wheel、Docker image

除构建是否成功外，还要核对部署使用的是否就是这次验证过的产物。

## CD 常见内容

### 部署策略

- 直接覆盖部署：简单，但风险高
- 滚动发布：逐台替换，影响面较小
- 蓝绿发布：新旧两套环境切换，回滚快
- 金丝雀发布：先给少量流量，观察后再放大

### 发布前后检查

- 发布前确认数据库变更是否兼容
- 发布前确认环境变量和 secrets 已配置
- 发布后跑健康检查和 smoke test
- 观察错误率、延迟、CPU、内存、日志

## 常见平台

- GitHub Actions
- GitLab CI/CD
- Jenkins
- Argo CD

选型不是重点，重点是把流程拆清楚：

- 谁触发
- 跑哪些检查
- 产物存哪里
- 谁批准上线
- 失败怎么回滚

## 一个最小可用流程

对中小项目，最小可用版本通常是：

1. PR 自动跑 `lint + unit test`
2. 合并到主干后自动构建 Docker 镜像
3. 推送镜像到仓库
4. 测试环境自动部署
5. 生产环境人工审批后部署

这个流程已经能覆盖大部分“别手工漏步骤”的问题。

## 常见坑

- 流水线和本地环境不一致
- 测试通过，但部署脚本用的是另一份配置
- 数据库变更不可回滚
- 只做自动部署，不做自动验证
- 流水线里打印了 secrets
- 构建太慢，团队开始绕过 CI

## 流水线与产物关系

流水线将检查、构建、制品保存和部署串成可重复流程。验证应作用于将要发布的版本，部署应使用已记录的制品；发布身份与权限由平台控制，密钥不进入日志或产物。

代码检查、测试、构建和线上观察分别提供不同证据，任何一步成功都不能替代其余阶段。

## 自查清单

- PR 是否自动跑测试
- 主干是否只接收通过校验的代码
- 是否有统一构建产物
- 发布流程是否文档化
- 是否有回滚方案
- 发布后是否有健康检查
- secrets 是否和代码分离
