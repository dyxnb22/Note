# 日志、指标与链路追踪

日志描述事件，指标描述分布与趋势，Trace 描述调用路径。把三者关联到同一时间窗口与业务目标，才能解释故障。


Java 的 SLF4J、Logback、MDC 将这些通用机制落实到应用代码，具体实现见 [Java 日志与可观测性](../Java/16_Java日志与可观测性.md)。

## 日志、指标与 Trace 的信息

日志记录离散事件和上下文，指标把大量事件聚合成可告警的时间序列，Trace 展示一次请求跨服务、队列和数据库的因果链。排障时先用指标发现范围，再用 Trace 定位路径，最后用结构化日志解释具体状态，不能只依赖一种信号。

## 生产日志的字段与边界

至少记录时间、级别、服务、实例、环境、请求/Trace ID、接口或业务动作、耗时、结果和错误类型；必要时记录订单号或任务 ID。密码、Token、身份证号和完整请求内容等敏感信息不能直接写入日志，日志字段和保留周期也应有数据治理规则。

## 采集、缓冲、存储与检索

应用输出结构化日志，采集器负责缓冲、解析、脱敏和批量发送，存储按实时查询与长期分析分流，展示层按服务、版本、租户和 Trace 关联查询。设计时必须说明采集失败、重复、迟到、单条大小、保留周期和日志系统故障时的降级方式。

## RED 与 USE 指标方法

RED 关注请求类服务的 Rate、Errors、Duration，适合判断接口是否变慢或失败；USE 关注资源的 Utilization、Saturation、Errors，适合判断 CPU、内存、磁盘、连接池等资源是否饱和。它们是组织指标的抓手，不是替代业务成功率和队列积压的固定面板。

## 跨线程、消息与服务的上下文

Trace ID 把同一业务请求的多个处理片段串起来，跨 HTTP、RPC、消息和异步任务时必须通过 Metadata/Header/Message Header 传递，并在异步任务完成后保留父子关系。线程池复用、消息重试和后台任务不能隐式假设当前上下文仍然有效。

## 观测链路的容量与故障

高基数标签会拖垮指标存储，日志级别过高会增加磁盘和网络成本，Trace 采样过低会丢失长尾，采集器阻塞又可能拖慢业务。应设置采样、限流、脱敏、保留和成本预算，并用一次真实故障演练验证观测链路本身不会成为单点。


观测结果还要连接告警、SLO、Runbook 与事故复盘：指标指出用户影响，Trace 和日志解释执行路径，恢复记录再检验告警与处置是否有效。敏感字段、采样和保留策略贯穿这条链路。
